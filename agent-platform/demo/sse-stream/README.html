1. 要解决什么问题

智能体的一轮对话可能跑几十分钟甚至几小时，过程中的每一步（模型在打字、调了哪个工具、需要谁审批）都要实时推给浏览器。 可这么长的时间里，两头都会出状况：

哪一头会发生什么
浏览器刷新页面、切到后台、断网、同时开好几个标签页
服务端多实例部署，发消息的请求和看事件的请求落在不同实例；Redis 重启；实例停机发布

所以这条事件流要做到：

要求意思
不丢断开期间产出的事件，重连后要补上
不重已经显示过的，重连后不能再显示一遍（打字效果重复一段话很难看）
跨实例A 实例上跑的 run，连在 B 实例上的浏览器也要看得到；B 停机了，换到 A 也能接着看
不拖垮服务流可能挂几个小时、开很多条，不能把服务端的连接、内存耗光

这个 demo 用最小的场景演示整个过程：两个实例 A、B，用户在一个会话里说了两句话，中间经历了断网、Redis 重启、B 停机。

2. 读懂这个 demo 需要的五个概念

① SSE：一个不关闭的 HTTP 响应

SSE（Server-Sent Events）就是一个普通的 HTTP GET，只是服务端返回 Content-Type: text/event-stream 之后不关闭响应， 有新事件就往里写一段文本。每个事件叫一帧，帧之间用空行隔开： 

id: 4
event: tool.started
data: {"thread_seq": 4, "run_id": "r1", "type": "tool.started", "data": {...}}

: ping

retry: 1000
行含义本 demo 怎么用
id:这一帧的编号。客户端重连时把最后收到的 id 放进请求头 Last-Event-ID写 thread_seq，就是续传游标
event:事件类型run.started、message.delta、tool.started……
data:内容整个事件的 JSON
: ...冒号开头是注释，客户端忽略心跳（§6.5）
retry:建议客户端隔多久重连（毫秒）停机时发给浏览器（§6.8）

浏览器自带的 EventSource 会自动重连并带上 Last-Event-ID，但它设不了自定义请求头（放不了认证信息）。 所以 Atlas 前端用 fetch 自己解析帧、自己重连（packages/chat-ui/src/lib/sse.ts），本 demo 的 Browser 照它写。

② 创建和订阅是两个请求

请求做什么返回
POST /threads/{id}/runs发消息，把 run 交给执行器立刻返回 202 {run_id}，不等它跑完
GET /threads/{id}/events订阅这个会话的事件流SSE，永不自己结束，可带 Last-Event-ID 续传

订阅的单位是会话而不是 run：一条流带着这个会话里所有 run 的事件，跨越多轮对话。为什么这么拆，见 §6.1。

③ 游标：会话内单调递增的 thread_seq

每个事件发布时分到一个 thread_seq，同一个会话内从 1 开始严格递增。它写进帧的 id，浏览器记住处理过的最大值， 断线重连时放进 Last-Event-ID，服务端只发比它大的。浏览器这边也只认比它大的，小于等于的一律当重复丢掉。

④ Redis Stream：实例之间的中继

所有实例共用一个 Redis。每个会话一条 Stream（一个只能追加的日志）：

命令谁用做什么
XADD … MAXLEN n执行器（发布事件）追加一条；超过 n 条就把最早的裁掉
XRANGE事件流（刚连上时）读出流里现有的全部条目
XREAD BLOCK t事件流（之后一直）阻塞等新条目，最多等 t 毫秒；超时返回空，正好用来发心跳
INCR执行器分配 thread_seq（§6.2）

run 在 A 上跑，事件写进 Redis；浏览器连在 B 上，B 从 Redis 读出来推给它。这就是「跨实例」。

⑤ 归档表：Postgres 里的那一份

Redis 会裁剪、会重启丢数据，所以事件还要归档进 Postgres 的 run_event 表，主键是 (thread_id, thread_seq)。 归档不是每个事件写一次，而是在检查点（一批工具结果收齐时）和一轮结束时批量写，所以它比 Redis 滞后一点。 message.delta（打字效果的增量）不归档：回放历史时，正文由 message.completed 一次给全。

3. 核心思路：一句话 + 三个要点

一句话：事件发布时从共享计数器分到一个会话内单调递增的 thread_seq，写进 SSE 帧的 id； 事件先进 Redis Stream（实时、跨实例），关键事件随检查点归档进 Postgres（持久）。 浏览器记住处理到的最大 thread_seq，断线后带 Last-Event-ID 重连到任意实例， 服务端先从归档补、再从 Redis 接，按 thread_seq 拼成一条不重不漏的流。

要点 1：游标是会话级的 thread_seq，由共享计数器分配

同一个会话可能有好几个生产者同时在写（并行委派的几个子 run），序号只能由 Redis 里的一个计数器分配。 Redis 重启后计数器没了，就用 DB 水位（归档里最大的 thread_seq）接着数，保证序号永远往上走。见 §6.2。

要点 2：归档和 Redis 两段接力

Redis StreamPostgres 归档
新不新最新，发布即到滞后：检查点和一轮结束时才写
全不全只留最近 MAXLEN 条，重启就没了全，但不含 delta
能不能阻塞等新事件能（XREAD BLOCK）不能，只能轮询

重连时：先从归档读出所有 > 游标 的事件，读到哪，游标就推到哪；再从 Redis 读 > 新游标 的；之后阻塞等新事件。 两段谁也替代不了谁，见 §6.3。

要点 3：会话流永不自己结束，所以连接要管起来

措施防的是什么见
心跳 : ping空闲连接被代理、负载均衡掐掉§6.5
每个实例的连接数闸门，超限 503长连接把服务端资源耗光，拖慢所有请求§6.7
停机时发 retry: 后主动关流实例停不下来§6.8

6. 几个「为什么」

6.1 为什么创建和订阅要拆成两个请求？

最直接的写法是 POST /runs 直接返回一个流，跑完就关。它扛不住这几件事：

情况POST 直接返回流拆成 POST + GET 流
刷新页面 / 断网流断了，run 还在跑，但再也接不上：POST 不能重发（会变成第二条消息）GET 可以随便重发，带游标接着收
多个标签页只有发消息的那个标签页看得到每个标签页各自订阅
多实例run 必须在接 POST 的实例上跑，而且这个实例停机时流就断了run 在哪跑无所谓，流可以连在任意实例
一轮跑完之后流关了，下一轮、挂起期间子 run 的审批请求都看不到会话流一直开着

6.2 为什么游标是会话级的 thread_seq，而且必须由共享计数器分配？

  • 会话级：一条流里有多个 run 的事件。如果用 run 内的序号当游标，两个 run 的序号都从 1 开始，重连时没法说「从哪里接着」。
  • 共享计数器：同一个会话可能同时有好几个生产者（并行委派的几个子 run 同时在写，可能还在不同实例上），各自在内存里数一定会撞号。
  • 用 DB 水位初始化：Redis 重启后计数器没了。如果从 0 重新数，新事件的序号全部小于浏览器的游标， 服务端按游标过滤掉、浏览器按游标当重复丢掉，界面再也不更新，而且没有任何报错（实验 2）。 唯一的报错出现在后面：归档时撞了主键。
  • 必须原子：「计数器不存在就用水位初始化」和「递增」之间不能有空隙，否则两个生产者可能各自初始化一次。真实系统用一段 Lua 脚本，demo 是单线程事件循环，天然原子。

6.3 为什么要「归档 + Redis」两段，只用一个不行吗？

只用问题
Redis流有 MAXLEN，断开久一点，中间的事件就被裁掉了；Redis 重启更是全没了。 实验 1 里断网期间的 #4 tool.started 被裁掉，浏览器上那个工具调用就不显示了，没有任何报错
Postgres不能阻塞等新事件，只能轮询，实时性和数据库压力二选一；而且归档滞后，最新的那几条还不在里面

拼接的关键是按 thread_seq 接，不按位置接：归档读到 #5，Redis 就从 #5 之后读。 Redis 的 entry id 重启后会变，thread_seq 不会变，所以 Redis 重启后浏览器的游标依然有效。

为什么 delta 不归档：一个长会话的 delta 能有几十万条，绝大多数永远不会被回放；回放历史时正文由 message.completed 一次给全。 代价是断开太久（delta 已被裁出 Redis）时，那一段的打字效果没了，但正文最终是完整的。

6.4 为什么 run.finished 之后流也不关？

订阅的单位是会话，一轮结束了后面还有下一轮；更要紧的是挂起：父 run 挂起等子智能体时，父 run 自己不产出事件， 可子 run 的审批请求正发生在这段时间里（姊妹篇讲的挂起）。流要是跟着某个 run 的结束一起关，这些就都看不到了。

所以 run.finished 对浏览器的意思只是「这一轮完了，可以去取最终用量、刷新消息列表了」，不是「流结束」。 流被服务端关掉，一律当作意外：退避后带游标重连。

6.5 为什么要心跳？

nginx、云负载均衡一般会把一段时间（比如 60 秒）没有数据的连接当成死连接掐掉。智能体在想、在等审批的时候，可能几分钟没有事件。 所以 XREAD BLOCK 等到超时还没有新事件，就发一行 : ping。它是注释行，客户端解析时直接忽略。 Atlas 是 15 秒一次，demo 是 0.3 秒。

6.6 为什么没有游标的首连只回放最近 N 条？

一个会话可以有几百轮、上万个事件，打开老会话时全量回放会把页面灌死；历史消息本来就走消息列表接口分页加载。 所以要区分两种情况：

请求意思服务端
不带 Last-Event-ID「我没有游标」只回放最近 N 条（Atlas 500，demo 3）
Last-Event-ID: 0「从头给我」全量
Last-Event-ID: 11「我处理到 11 了」补 11 之后的缺口，不限量

所以服务端的游标缺省值是 None 而不是 0，浏览器在没有游标时也不带这个请求头。缺省成 0 的后果见实验 3。

6.7 为什么每个实例要有连接数闸门，而且要在路由里先查？

每条流都要占服务端资源（真实系统里每条占一个 Redis 连接），而且一挂就是几个小时，一个用户开三个标签页就是三条。 不设上限的话，症状不是「第 N+1 个连不上」，而是连接池耗尽后所有 HTTP 请求一起变慢，根因离症状很远。 所以超限时要明确返回 503 + Retry-After，客户端退避重连。

检查必须放在路由函数里，在构造 StreamingResponse 之前。StreamingResponse 是先发出 200 响应头、再迭代生成器的： 在生成器里才检查、才抛异常，响应头早就发出去了，客户端拿到的是 200 加上一个被掐断的响应体（实验 4′）。这比 503 糟糕得多：

  • 客户端以为连上了，把退避重置了，于是每 0.5 秒重试一次，而不是越来越慢；
  • 服务端每次都打一份 Exception in ASGI application 的堆栈。

Atlas 现在的 stream/gate.py 就是在生成器里检查的，用真实的 StreamGate 实测，超限时客户端收到的是 RemoteProtocolError: peer closed connection without sending complete message body，而不是 503。

占用计数仍然放在生成器里（随流结束而释放），路由里只做检查。两者之间有一个很小的窗口，几个同时到达的请求可能一起通过， 所以这是一个软上限，用来防资源耗尽足够了。

6.8 为什么停机时要主动关流？

uvicorn 收到停机信号后，会等所有进行中的响应结束再退出。会话流永远不会自己结束，所以它会一直等到宽限期（K8s 的 terminationGracePeriodSeconds）用完、被强制杀掉。 这段时间里本该做的停机工作（比如把正在跑的 run 交接给别的实例）都排不上。

所以停机时先把实例标成 draining：新连接 503，负载均衡把它摘掉；已有的流在下一次醒来（最迟一个心跳周期）时发一行 retry: 1000 然后结束。 浏览器带游标重连，落到别的实例上，一条不丢。实验 5 去掉主动关流，B 停机从 0.3 秒变成 2 秒。

6.9 为什么 run.finished 要先落库再发布？

浏览器收到 run.finished 后会立刻去取这一轮的最终用量。如果先发布后落库，它可能读到 status=running、tokens=0。 先落库再发布，就保证了「看到收尾事件，DB 一定已经是最终状态」。demo 里打印的「落库（归档 #8 #9）后再发布 #9」就是这条顺序。

8. 动手实验

每个实验只改一两处，结果都是实际运行得到的。

#改动观察到的现象说明了什么
1 Instance.stream 里把 archived = self.archive.after(thread_id, cursor) 改成 archived = []（只读 Redis） 重连那一行变成「归档段：无；Redis 段：#5 #6」，#4 tool.started 没收到。最终界面上第一轮的工具是「无」，全程不报错 §6.3：Redis 有 MAXLEN，断开期间的事件可能已经被裁掉
2 FakeRedis.next_thread_seq 里把 self.counters[thread_id] = floor 改成 = 0（Redis 重启后从 0 数） 第二轮的事件序号是 #1 #2 #3……，浏览器一条都没收到（打印「等了 3 秒也没等到：浏览器收到 #11」）； 第二轮结束时 A 打印「归档失败：主键冲突 (t1, 1)」；新标签页只看到第一轮 §6.2：序号倒退的表现是界面静默不更新，唯一的报错在归档那里
3 Instance.stream 里把 cursor = self.archive.window_floor(thread_id, REPLAY_WINDOW) 改成 cursor = 0 新标签页回放了整个会话的归档：#1 #4 #5 #8 #9 #10 #13 #14 §6.6：这里只有 8 条，真实的老会话是上万条
4 把 SSE_LIMIT 改成 1 新标签页连 A 时收到 503，Retry-After=1，按 0.5、1、2 秒退避重试了 3 次 §6.7：超限明确拒绝，客户端退避
4′ 同 4，并把 events 路由里的闸门检查挪进 stream() 开头，改成 raise RuntimeError("事件流已满")（Atlas 现在的写法） 新标签页收到的不是 503，而是「peer closed connection without sending complete message body」； 3 秒里重试了 6 次（退避没有增长）；服务端打了 6 次 Exception in ASGI application §6.7：响应头先发、生成器后跑，在生成器里拒绝已经来不及了
5 删掉 Instance.stream 里 if self.draining: 那一段（停机时不主动关流） B 停机用时从 0.3 秒变成 2.2 秒；uvicorn 打印「Cancel 1 running task(s), timeout graceful shutdown exceeded」； 浏览器收到的是断开的连接，而不是 retry:。之后照样带游标重连到 A，没丢事件 §6.8：游标保住了数据，但停机被拖到宽限期用完；真实系统里这段时间本该用来交接 run

9. demo 和真实系统的差别

方面demo真实系统
Redis / Postgres内存模拟真实的 Redis Stream 和 run_event 表
序号分配的原子性单线程事件循环，天然原子一段 Lua 脚本：不存在就用水位初始化，然后 INCR
参数MAXLEN 2，首连窗口 3，心跳 0.3 秒，闸门 10MAXLEN 10000（近似裁剪），首连窗口 500，心跳 15 秒，闸门 200
事件种类7 种30 多种（审批、子智能体、用量、上下文压缩……）；子 run 的事件也进同一条会话流，用 depth=1 区分
检查点工具结果收齐时归档同样的时机，但消息、事件归档、序号在一个事务里写，并且校验租约（防止接管者和假死复活的旧实例双写）
数据库连接无流开始前一次读完归档，然后马上归还连接：流可以挂几个小时，不还的话每个观看者占死一条
鉴权无构造流之前先校验会话归属，让 404 以 JSON 返回，而不是变成一个 200 的空流
客户端Python，照 sse.ts 写TypeScript 的 sse.ts + run-reducer.ts；连续失败 6 次后放弃
停机main() 手动调用SIGTERM 触发：事件流 drain，同时把正在跑的 run 交接出去
闸门检查的位置路由里先查，超限 503在生成器里检查，超限时客户端拿到 200 + 断流（§6.7）
