1. 要解决什么问题

一个「智能体」（Agent）的工作方式很朴素：大模型想一步 → 调一个工具 → 看结果 → 再想一步，直到它认为可以回答用户了。 大多数时候这个循环一口气就能跑完，但有两种情况必须停下来等：

场景在等什么可能等多久
人工审批模型想删文件、发邮件……这类危险操作要先等人点「批准」几分钟，也可能到第二天上班
子智能体委派把一个子任务交给另一个智能体去做，等它的结论可能要一个小时

让程序原地干等显然不行：进程会重启、会被调度到别的机器、会占着资源。所以我们需要：

  1. 挂起：在「需要等」的地方干净地停下来，把该记的都记进数据库，然后进程就可以退出了。
  2. 恢复：等的东西到了以后，任何一个进程都能从数据库里把现场拼回来，从停下的地方接着跑。

这个 demo 用最小的场景演示整个过程：用户让智能体删一个文件，删除需要人工审批。

2. 读懂这个 demo 需要的五个概念

没接触过 LangChain / LangGraph 也没关系，下面这五个概念就够用了。

① 消息（Message）：对话就是一串消息

智能体的全部「记忆」就是一个按顺序排列的消息列表，只有三种消息：

类型谁产生的例子
human用户「帮我删掉 /tmp/demo.txt」
ai大模型可以是一句回答；也可以是「我要调用工具 delete_file(path=…)」——这叫一个 tool_call，带一个编号，比如 call_1
tool工具工具的执行结果，比如「已删除 /tmp/demo.txt」。它会注明自己回应的是哪个编号（tool_call_id=call_1）
一条硬规则：交给模型的消息里，每个 tool_call 都必须有且只有一条对应编号的 tool 消息（一问一答，必须配对）。 缺了，模型厂商的 API 直接报错（HTTP 400）；同一个调用有两条结果，也会被拒绝（Atlas 的模型网关遇到过）。
注意它约束的是交给模型的那一刻：图里暂时有一个没回答的 tool_call 是允许的，只要调用模型之前补上结果就行。本 demo 的挂起就是利用这一点实现的。

② 图（Graph）：把「想 → 做 → 再想」画成一张流程图

LangGraph 把智能体的循环表示成一张有向图：每个方框是一个节点（一段代码），箭头决定下一步去哪。 LangChain 的 create_agent() 会帮你生成下面这张图，你只需要提供模型和工具：

黑色实线是 create_agent() 自带的流转；红、绿两条虚线是本 demo 用 jump_to 加上的「捷径」。

注意 before_model 的位置：工具跑完以后、下一次调用模型之前，一定会经过它。 这时候整批工具结果都已经出来了，模型还没被调用，是做「要不要继续」判断的最佳时机。

③ 中间件（Middleware）：在图的固定位置插入你自己的代码

你不用改图的结构，只要写一个中间件类，实现对应的「钩子」方法，框架会在对应时机调用它。demo 用到三个钩子：

钩子什么时候被调用demo 里用它做什么
before_agent(state)每次 invoke 开头，只跑一次（上图没画，在「开始」和 before_model 之间） PatchToolCallsMiddleware：给被放弃的悬空 tool_call 补一条「was cancelled」
before_model(state)每次调用模型之前 SuspensionMiddleware：看 waiting_on，决定「正常调模型 / 跳到结束 / 跳到工具」
wrap_tool_call(request, handler)每次执行工具时，把执行过程包一层 ApprovalMiddleware：调用 handler(request) 就是真执行；不调用、只返回一个登记 waiting_on 的 Command，就是拦下来不执行

④ jump_to：钩子可以改变「下一步去哪」

before_model 返回 {"jump_to": "end"}，图就直接结束；返回 {"jump_to": "tools"}，就跳过模型去执行工具。 这就是上面那张图里的两条虚线。返回 None 表示不干预，按默认流程走。 钩子要用 @hook_config(can_jump_to=[...]) 声明能跳去哪；子类覆盖这个钩子时要重新声明，否则 jump_to 会被悄悄忽略。

⑤ state：除了消息，还能放自定义字段

图在运行时持有一个 state。create_agent() 默认的 state 主要就是消息列表 state["messages"]， 中间件可以通过 state schema 加自己的字段。本 demo 加了两个：

字段内容谁写谁读
waiting_on{tool_call_id: {reason, token}}：哪个调用在等什么 审批中间件（挂起时登记、放行后删除）；server 续跑时交回before_model、Patch；server 落库、过关卡
decisions{token: "approved" / "rejected"}：已经做出的审批决策 server 续跑时交进来before_model、审批中间件

state 只活一次 invoke，下一次 invoke 不会自动保留。所以 server 要从返回值里取出 waiting_on 存进 run 表，续跑时再传回去。 LangGraph 官方的「暂停/恢复」方案 checkpointer + interrupt 会把整个图的现场序列化存起来；本 demo 故意不用，原因见 §6.1。

3. 核心思路：一句话 + 三个要点

一句话：不用 checkpointer。危险工具被拦下时不执行、也不写结果，tool_call 留着悬空，「在等什么」登记在 state 的 waiting_on 里； before_model 看到 waiting_on 非空就跳出图（挂起）。server 把消息和 waiting_on 一起落库； 等到结果后，把消息、waiting_on 和审批结果 decisions 一起交给一个新建的图，before_model 看到有了决策就跳去执行工具（恢复）。

要点 1：依据有两份，必须一起存、一起交回

消息表本来就要存下来给用户看历史；waiting_on 记的是消息里没有的信息：哪个调用在等、等的是什么。 两份都是依据，缺一不可：只看消息表，只能看出 call_1 还没有结果，看不出它在等什么。 所以 demo 只在 run_segment() 一处落库、只在 resume_payload() 一处组装入参；真实系统里两者要在同一个事务里写入。 漏传的后果见实验 4（§8）。

要点 2：悬空的 tool_call 有两种含义，靠 waiting_on 区分

悬空的原因例子续跑时该怎么办谁处理
在等审批中间件挂起时故意不写结果保持悬空，等有了决策再执行 在 waiting_on 里 → Patch 跳过；before_model 决定继续挂起还是放行
被放弃进程在工具执行到一半时退出，结果没写进去补一句「was cancelled」，让模型自己决定要不要重试 不在 waiting_on 里 → Patch 补上

为什么 Patch 必须看 waiting_on，见 §6.3。

要点 3：按等待原因判断能否续跑

续跑之前先过一道关卡（barrier）：根据 waiting_on 里每一项的 reason，去查对应的东西是不是已经有结果了。

reason关卡条件本 demo
approval审批表里这一条不再是 pending已实现
delegation子智能体的 run 已经跑完没有实现，只用来说明为什么要区分 reason

为什么一定要区分 reason，见 §6.4，那里有一张「不区分就会死循环」的时序图。

6. 几个「为什么」

6.1 为什么不用 LangGraph 官方的 checkpointer？

checkpointer + interrupt本方案：消息表 + waiting_on
状态存在哪checkpoint 表（图的完整现场）+ 消息表（给用户看的历史）消息表 + run 表里的 waiting_on 字段
两份数据会不会不一致会。checkpoint 是整个现场的副本，上下文压缩、手动修历史以后，两份对不上，排查很难 waiting_on 不是消息的副本，只记消息里没有的那一点信息；两者在同一个事务里写入
恢复需要什么反序列化图的现场重新建图，把消息、waiting_on、decisions 交进去，靠 jump_to 决定从哪继续
额外需要的东西checkpoint 表、序列化兼容性（升级代码后旧存档还能不能读）两个 state 字段 + 三个中间件

关键在于：create_agent() 这种图的现场本来就只有消息列表，下一步去哪也能从消息和 waiting_on 推断出来， 没有必要再存一份完整的现场。

6.2 为什么挂起时不写一条占位 tool 消息？

很容易以为：工具被拦下了，也得写一条「等待审批」之类的 tool 消息，才能满足 §2 ① 的配对规则。逐条看：

以为的理由实际情况
每个 tool_call 都要有结果，否则模型 API 报错 这条规则只约束交给模型的消息。挂起时 before_model 直接 jump_to "end"，不调模型； 续跑时先执行工具再调模型，模型拿到的消息是配对完整的
ToolNode 要求返回的 Command 里带一条对应的 ToolMessage ToolNode 只检查工具自己返回的 Command，不检查 wrap_tool_call 的返回值，只返回 waiting_on 可以
续跑时 tool_call 必须没有结果，jump_to "tools" 才会执行它 jump_to "tools" 时 ToolNode 执行最后一条 ai 消息里的全部 tool_call，不看有没有结果（所以才有 §9 说的兄弟调用重跑问题）
图入口的 PatchToolCallsMiddleware 会给悬空的调用补「was cancelled」 Patch 先看 waiting_on，在等的调用不补（§6.3）

写了占位反而有坏处：

  • 续跑执行工具前要先把它删掉，否则同一个调用有两份结果。
  • 续跑时如果漏传 waiting_on，模型会把「等待审批」当成工具的真实结果往下说。
  • 消息表如果只追加、不整表覆盖，占位那一行会一直留在表里，还得另加去重规则。

6.3 为什么 PatchToolCallsMiddleware 要看 waiting_on？

Patch 是 Atlas kernel 里的中间件（deepagents 自带），本 demo 放了一个精简版。它的本职工作是崩溃恢复： 进程在工具执行到一半时退出，消息表里会留下没有结果的 tool_call，续跑时直接交给模型会 400。 Patch 在图入口给它补一句「was cancelled」，模型看到后自己决定要不要重试。

本 demo 的挂起也会留下悬空的 tool_call。Patch 如果不区分，续跑时会这样（实验 5）：

  1. 图入口：Patch 给 call_1 补上「was cancelled」；
  2. before_model：call_1 有了决策 → jump_to tools，工具真正执行，又写了一条结果；
  3. 调用模型：call_1 有两条结果 → 400。
修法评价
Patch 照补，before_model 放行时按 tool_call_id 把补的那条删掉 先补后删。before_model 必须知道 Patch 会插消息，是一个隐式依赖； 审批还在 pending 时如果图被调起，返回的消息里会留下一条假的「was cancelled」；每次续跑，Patch 都要把整个消息列表重写一遍
Patch 跳过 waiting_on 里的调用（本 demo） 「悬空是在等还是被放弃」只在 Patch 一处判断；before_model 放行时只要 jump_to "tools"

6.4 为什么挂起时必须记下「等待原因」？

续跑之前要问一句「等的东西有结果了吗」。不同原因的判断标准完全不同：委派要看「子 run 跑完没有」，审批要看「人批了没有」。 如果只记了凭证、没记原因，所有挂起都按委派的标准判断，那么一个审批挂起会这样：

这就是「续跑后又挂起」的死循环：审批挂起时根本没有子 run，「子 run 都跑完了吗」这个问题的答案永远是「是」，关卡形同虚设。 记下 reason 后，关卡按原因分别判断，审批挂起的 run 会一直安静地等到有人做出决策。

实验 3（§8）可以在 demo 里亲眼看到「续跑后又挂起」。

6.5 为什么 waiting_on 要自己写 reducer？

def merge_waits(old, new):
    """按 tool_call_id 合并；值为 None 表示删除。"""
    merged = {**(old or {}), **(new or {})}
    return {k: v for k, v in merged.items() if v is not None}

class SuspendState(AgentState):
    # 不加可见性标注：挂起时要从返回值里取出来落库，续跑时要原样传回去
    waiting_on: NotRequired[Annotated[dict[str, dict[str, str]], merge_waits]]
    # 只进不出：续跑时由 server 交进来
    decisions: NotRequired[Annotated[dict[str, str], OmitFromOutput]]
写法问题
不写 reducer审批通过后写入的 {call_1: None} 会原样覆盖旧值，state 里留下 {"call_1": None}， before_model 读 w["token"] 时报 TypeError（实验 6）。一批多个工具同时挂起时，还会报 InvalidUpdateError
operator.add只能往里加，审批通过后没法把这一项删掉
merge_waits同一步的多个写入按 key 合并；值为 None 表示删除

6.6 为什么 decisions 只放已经决策的审批？

before_model 只看 token 在不在 decisions 里，在就放行；它不认识 approved / rejected 这些值， 因为不同 reason 的结果长得不一样。如果把 pending 也放进去：before_model 放行 → 审批中间件发现还是 pending， 又登记一次 waiting_on → 回到 before_model 又放行……在图里来回跳，直到 GraphRecursionError（实验 3′）。 正常流程有关卡挡着，碰不到这种情况；但关卡一旦判断错，就是死循环而不是安静地再挂起一次。 所以 resume_payload() 只把已经决策的审批放进 decisions。

7. 代码导读

按阅读顺序列出：

代码作用
MESSAGES / APPROVALS / RUN代替数据库里的消息表、审批表、run 表
merge_waits / SuspendStatestate schema：waiting_on 和 decisions 两个字段（§2 ⑤、§6.5）
delete_file需要审批的工具（只打印，不真删）
ScriptedModel假模型：最后一条是用户消息就调工具，否则汇报结果。内含一条断言，模拟 API 的配对规则：每个 tool_call 恰好一条结果
PatchToolCallsMiddleware图入口：给被放弃的悬空调用补「was cancelled」，跳过 waiting_on 里的（§6.3）
ApprovalMiddleware没批准就拦下：只登记 waiting_on；有了决策就执行（或返回「拒绝」），并删掉这一项
SuspensionMiddleware唯一的图内判断点：等的有了决策 → 跳工具；还在等 → 跳结束

waits_are_settled续跑前的关卡，按 reason 判断
resume_payload组装续跑的入参：消息 + waiting_on + 已决策的 decisions（§6.6）

8. 动手实验

每个实验只改一两处。下面的结果都是实际运行得到的。

#改动观察到的现象说明了什么
1 main() 里把 APPROVALS[token] = "approved" 改成 "rejected" 段 2 没有打印 [tool] 执行删除；消息表变成 tool: '用户拒绝了这次操作'、ai: '好的，用户拒绝了这次操作。' 拒绝走的是同一条恢复路径：照样跳到工具节点，只是审批中间件这次返回「拒绝」而不是执行工具
