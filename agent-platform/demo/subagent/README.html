1. 要解决什么问题

智能体遇到多步骤的活（调研三个方案、跑一遍压测），想交给 SubAgent 去做，自己只要结论；SubAgent 干活时也可能发现需要再交给别的 SubAgent。放进真实环境，要同时满足：

要求意思
上下文隔离SubAgent 的过程（工具调用、读过的资料）不进父会话，父会话只看见结论
并行「同时调研三个方案」要能一批派出去一起跑，总耗时接近最慢的那个，而不是加起来
可以嵌套SubAgent 也能派 SubAgent，层数不设上限，每一层的规则都一样
不在内存里等一个 SubAgent 可能跑一小时。这一小时里发布一次、OOM 一次，父 run 和子 run 已经干完的活都不能丢
失败可恢复SubAgent 跑挂了、派给了不存在的 SubAgent，父 run 的模型应该能看到原因、改派或自己动手，而不是整轮失败
机制只有一套审批已经有一套挂起 / 续跑机制（姊妹篇 suspend-resume），SubAgent 不该再发明第二套

这个 demo 的做法：每次派 SubAgent 都挂起。task 工具只负责起子 run，不等结果；当前 run 当场结束这一段、落库； 子 run 全部结束时叫醒它，用一张全新的图接着跑。主智能体和 SubAgent 用的是同一套图、同一条执行路径，所以嵌套就是这条路一层层叠起来。

场景：用户要选一个消息队列。主智能体分两波派 SubAgent，每一波都是同一批并行发出、每一波都挂起； 其中调研 Kafka 的 researcher 自己又派了一个 benchmarker 去压测，于是它也挂起、被叫醒、再交结论。

2. 读懂这个 demo 需要的四个概念

① 子 run 和 SubAgent 的会话

SubAgent 没有发明新的存储，直接复用「会话」（thread 表）和「一轮执行」（run 表）：

概念是什么关键字段
SubAgent 的会话每次派 SubAgent 新建一个 thread，第一条消息就是任务书parent_thread_id、subagent_name
子 run这个会话上一个普通的 run，和根 run 走同一个执行器、同一条路parent_run_id 指回派出它的 run；id 由 (父 run, tool_call_id) 派生
结论子 run 最后一条 ai 消息；失败时是一段说明续跑时作为那次 task 调用的工具结果

id 一层层派生下去就是祖先链：r1 是根 run，r1-c1 是它的 c1 调用派出的，r1-c1-c1 是 r1-c1 的 c1 调用派出的。 每次都是新会话，所以 SubAgent 之间互不共享状态，同一个 SubAgent 在同一批里派几次都可以并行。

② task 工具和 SubAgentSpawner

每个智能体（包括 SubAgent）都有一个 task 工具，参数是 subagent_type 和 description（任务书）。它的全部行为在 SubAgentMiddleware.awrap_tool_call 里， 工具函数本身永远不会被执行。中间件在图里，不认识数据库，起子 run 时只调一个注入进来的协议： 

class SubAgentSpawner(Protocol):
    async def spawn(self, name: str, task: str, call_id: str) -> str: ...   # 起子 run，返回它的 id，不等它跑完

server 侧的 SubAgentService 实现它：建会话、建子 run、交给执行器。这条边界对应 Atlas 的 DelegationProtocol。

③ waiting_on：悬空的 task 调用在等哪个子 run

和姊妹篇的审批一模一样，只是 reason 从 approval 换成了 subagent、token 从审批 id 换成了子 run id：

waiting_on = {
    "c1": {"reason": "subagent", "token": "r1-c1"},
    "c2": {"reason": "subagent", "token": "r1-c2"},
    "c3": {"reason": "subagent", "token": "r1-c3"},
}

起了子 run 后，task 不写工具结果，调用留着悬空，只在 state 的 waiting_on 里登记。续跑时 server 再把子 run 的结论放进另一个字段 results（子 run id → 结论文本，只进不出），对应姊妹篇的 decisions。

④ barrier 和 CAS：谁来叫醒、叫醒几次

名词意思demo 里
barrier续跑的前提：waiting_on 里等的东西全都有结果了Executor.pending_waits：每个 token 对应的子 run 都到终态了吗
CAS「还是旧值才改成新值」，一条语句原子完成Store.claim_for_resume：status 还是 suspended 才改成 queued

每个子 run 结束时都去试着叫醒它的父 run：barrier 不满足就算了；满足了再用 CAS 抢「续跑权」，只有一个能抢到。

3. 核心思路：一句话 + 三个要点

一句话：task 只起子 run 不等：登记 waiting_on、不写结果，before_model 看到 waiting_on 就结束这一段； 消息和 waiting_on 一起落库，当前 run 挂起；子 run 全部结束时 CAS 叫醒它，新建一张图，入参是消息 + waiting_on + results， jump_to tools 让 task 再执行一遍，这次直接把结论当工具结果返回。每个 run 都走这同一条路，所以 SubAgent 可以无限嵌套。

要点 1：每次派 SubAgent 都挂起，等待交给数据库

run 不在内存里等任何东西。一段结束时，「在等谁」就在 run.waiting_on 里，执行这一段的任务随即结束，这时重启进程什么都不丢。 叫醒的入口有两个：子 run 结束时、自己落库后复查（真实系统还有周期补扫），都走同一个 resume_if_ready：先过 barrier，再 CAS。

要点 2：并行靠「每个 tool_call 一个子 run」，嵌套靠「所有 run 同一条路」

环节怎么做
派出同一批的几个 task 由 LangGraph 并行执行（每个 tool_call 一个 Send），各起一个子 run
登记它们在同一步里各写一次 waiting_on，靠自定义 reducer 合并成一份
执行子 run 各自在自己的会话上跑，互不依赖。demo 里四次工具调用串行要 1.1 秒，整轮约 0.7 秒
嵌套子 run 的图里也有 task：它派出孙 run 后同样挂起，孙 run 结束叫醒它，它续跑、结束后再叫醒自己的父 run
汇合barrier 等齐这一批，父 run 只续跑一次，模型一次看到全部结论

要点 3：续跑时让 task 再走一遍，兄弟调用原样返回

续跑不改写消息表，而是把三样依据原样交回一张新图：messages（task 调用还悬空着）、waiting_on（它们在等谁）、results（等到的结论）。 入口的 Patch 看到悬空的调用在 waiting_on 里，不补 cancelled；before_model 看到结论到了，jump_to tools； ToolNode 把最后一条 ai 消息里的调用全部再执行一遍：在等的 task 这次返回结论，同一批里早就有结果的兄弟调用原样返回，不重跑。

4. 文件结构：按功能模块拆分

拆分的依据是 Atlas 的分层：图这一侧（kernel）不认识存储，只认协议；server 侧负责存储、执行和叫醒。依赖只从上往下（tracing.py 谁都可以用）：

main.py                      剧本入口
└─ executor.py               执行器（server）
   ├─ subagent_service.py    SubAgentSpawner 的实现（server）
   ├─ agents.py              组装图（kernel）
   │  ├─ middleware.py       三个中间件 + task 工具 + SubAgentSpawner（kernel）
   │  │  └─ state.py         state schema（kernel）
   │  └─ scripted.py         假模型 + 假工具
   └─ store.py               外部存储（server）
tracing.py                   输出前缀（谁都可以用）
文件层负责什么不知道什么
store.pyserverthread / run / message 三张表；建子 run（幂等）、落一段、失败、领取、续跑的 CAS图、中间件
state.pykernelSubAgentState：waiting_on（reducer）、results（只进不出）一切存储
middleware.pykernelPatch / Suspension / SubAgent 三个中间件，task 工具，SubAgentSpawner 协议子 run 是一行 run、会话是一行 thread
agents.pykernelbuild_agent：主智能体和 SubAgent 同一套中间件；SubAgent 名录存储
subagent_service.pyserverSubAgentService（SubAgentSpawner 的实现）；子 run 结局 → 结论文本图的内部

scripted.py—一个假模型演所有角色（按剧本出牌）、假工具、配对规则断言—
tracing.py—输出：每行带上是哪个 run 的哪一段在说话，按嵌套深度缩进（contextvar）—
main.py—用户说话 → 提交根 run → 等结束 → 打印各表—

模块之间用裸模块名互相导入（from store import Store），因为脚本的目录会被放进 sys.path 第一位。这是 demo 的简化；放进正式代码库应该是一个包。 输出模块叫 tracing.py 而不是 trace.py，是为了不遮住标准库的 trace。

7. 几个「为什么」

7.1 为什么每次派 SubAgent 都挂起，不当场等一会儿？

方案好处代价
当场等一会儿，超时再挂起（Atlas 现在的做法，窗口 60 秒）秒级的 SubAgent 不分段，少一次建图和落库两条路径：当场等到的、续跑补上的，结论整形、失败话术要两边保持一致；还多一个「等多久」的配置和它的边界竞态
一律挂起（本 demo）只有一条路径；run 从不在内存里等，部署、OOM 都不丢东西每派一批多一段：多一次建图、一次读库、一次叫醒的延迟

多出来的那一段不多调模型：续跑时 before_model 直接 jump_to tools，模型调用次数和当场等完全一样。代价只是一次建图加几次数据库往返，相对一次 SubAgent（至少一整轮智能体）可以忽略。

7.2 为什么 SubAgent 能继续派 SubAgent，又不用写任何额外的代码？

因为根 run 和子 run 之间没有区别，除了有没有 parent_run_id：

  • 图一样：build_agent 给主智能体和 SubAgent 装同一套中间件，SubAgent 只是多了自己的工具。
  • 执行路径一样：Executor._execute 对所有 run 都是「跑一段 → 挂起就复查自己 / 结束就叫醒父 run」。
  • id 派生一样：SubAgentService 绑定的是「正在跑的那个 run」，派出去的子 run 自然挂在它下面，id 自然多一层。

所以第 2 层的 r1-c1-c1 结束时叫醒的是 r1-c1，r1-c1 续跑、交出结论后叫醒的是 r1。r1 完全不知道 r1-c1 中间挂起过：它看到的只是「r1-c1 比较慢」。

去掉深度上限的代价：递归停不停完全由模型决定。模型如果陷入「再派一个 SubAgent 去查」的循环，会一层层派下去，每层都占一个 run（acp 的还占一个 Pod）。 真实系统需要别的护栏，比如整棵树的 token / run 数预算、可配置的最大深度、或在准入时按祖先链检测重复任务。demo 没有做。

7.3 为什么挂起方式要和审批一样？

审批（suspend-resume）SubAgent（本 demo）
登记{"reason": "approval", "token": 审批 id}{"reason": "subagent", "token": 子 run id}
barrier审批行被决策子 run 到终态
续跑时交进来decisionsresults
续跑时工具干什么批准 → 真正执行；拒绝 → 回一句拒绝把结论当工具结果返回

Patch 和 Suspension 两个中间件共用。同一批里既有审批又有 SubAgent 也不用特殊处理：waiting_on 里两种 reason 各管各的，barrier 按 reason 分别判断。 SubAgent 自己调危险工具要审批时，挂起的是那个子 run，它的父 run 照常等它，机制一样。

Atlas 现在的 SubAgent 挂起不是这套做法：它让 task 返回一个 __ATLAS_SUSPENDED__:delegation:<子 run id> 哨兵字符串作为占位结果，续跑时 server 在内存里把哨兵换成结论。 按本 demo 迁移，需要和姊妹篇一起改（见 §10）。

7.4 为什么续跑要 jump_to tools 让 task 再执行一遍，而不是 server 直接把结论写进消息表？

  • 消息表只追加，不改写：server 不需要知道「换哪一条、换成什么」，也不会出现「表里写了结论、子 run 里又是另一份」两个事实源。
  • 工具结果由图自己产生：和普通工具一样，结果从 ToolNode 出来，waiting_on 的删除和结果的写入在同一个 Command 里，不会一边成功一边失败。
  • 和审批是同一条路：审批续跑也是 jump_to tools，只是这次工具真正执行。

7.5 为什么 waiting_on 必须有自定义 reducer？

同一批的三个 task 并行执行，在同一步里各返回一个 Command(update={"waiting_on": {...}})。普通字段一步只能收一个值， 实验 1 去掉 reducer，r1 段 1 直接以 At key 'waiting_on': Can receive only one value per step 失败。 不用 operator.add 是因为续跑时要把等到的那一项删掉（值为 None 表示删除），add 只能加不能删。

7.6 为什么 barrier 要等齐一整批？

实验 8 把 barrier 改成「永远满足」：每个 run 落库后的复查都立刻续跑，续跑后 before_model 发现还在等，又挂起，又复查…… r1 跑了三十七八段，r1-c1 跑了 20 段，绝大多数是「在等 → jump_to end」的空转。结论最终是齐的（子 run 不会重复起、兄弟调用原样返回），但白白建了几十次图。

等齐一整批还有一个好处：模型一次看到全部结论再决定下一步，而不是看到一份就动手。

7.7 为什么续跑时，已经有结果的兄弟调用要原样返回？

jump_to tools 直接进 ToolNode，它会把最后一条 ai 消息里的全部调用再执行一遍，不管哪些已经有结果。 第 2 波的 c5 派给了不存在的 writer，段 2 当场就回了一句错误文本；段 3 续跑时 c5 又会被执行一遍。

SuspensionMiddleware.awrap_tool_call 发现这个调用在消息里已经有结果，就把那条消息本身原样返回。消息按 id 合并，同一个 id 只会替换、不会追加，于是结果还是恰好一条。 实验 7 去掉这段，r1 段 3 以 tool_call ['c5'] 的结果不是恰好一条 失败（真实 API 是 400）。 同一批里混着普通工具时也一样：已经执行过的工具不会因为续跑再执行一次（副作用不重放）。

7.8 为什么子 run 的 id 要由 (父 run, tool_call_id) 派生？

一段的结果是在图跑完之后才落库的。如果起了子 run 之后、落库之前进程崩了，接管者会把这一段重跑一遍，task 会再被调用一次。

  • id 可复现（r1-c2）：重跑时 create_child 发现已存在，什么都不做，返回同一个 id。实验 6 让每一段都跑两遍，每一层都打印「已存在，不重复起」，最后还是 5 个子 run。
  • id 随机：实验 6′ 一共起了 12 个子 run，其中 7 个是孤儿。嵌套让它成倍增加：孤儿 researcher 自己也会再派出孤儿 benchmarker。

这和姊妹篇提到的「approval_id 必须可复现」是同一个道理。实验 5″ 里它还顺带兜住了「同一段被并发跑了两遍」的情况。

7.9 为什么 run 落库之后还要自己再查一次？

子 run 一被起就开始跑，而父 run 要等这一段图跑完才落库。如果子 run 跑得比父 run 落库还快：

  1. 子 run 结束，去叫醒父 run：父还是 running，resume_if_ready 直接返回，这次唤醒落空，没有任何输出；
  2. 父 run 落成 suspended，之后再没有人来叫它。

实验 4 让 r1 第 1 段落库前多等 1 秒，它的子 run（包括 r1-c1 那条嵌套链）都在这段时间里结束，全靠复查续上；实验 4′ 再删掉复查，r1 永远停在 suspended，没有报错。 真实系统还有周期补扫兜底：子 run 收尾那一刻进程正好重启，唤醒也会丢。

7.10 为什么叫醒要用 CAS？

一批子 run 可能同时结束，每个都会来叫醒。实验 5 让 r1-c2、r1-c3 同时结束：一个「CAS 抢到」，一个「CAS 没抢到，别人已经续上了」。 demo 里其实有两道 CAS：续跑的 claim_for_resume，和执行器领取 run 的 claim（真实系统是 SELECT … FOR UPDATE SKIP LOCKED）。

实验去掉了什么结果
5′续跑的 CAS两个唤醒都打印「CAS 抢到」，但领取那道兜住了，段 2 只跑一次
5″两道都去掉r1 段 2 被并发跑了两遍（两次模型调用）；可复现的子 run id 让第 2 波没有重复起；run 表显示「共 3 段」，实际跑了 4 段：并发的读改写丢了更新

7.11 为什么 SubAgent 失败要回成文本？

  • 派不出去（SubAgent 不存在）：当场回一条工具结果，不挂起。模型看到「可用的是 researcher、benchmarker」，可以改派。
  • 子 run 失败：子 run 落成 failed，结论文本照实说「以 failed 结束：搜索服务超时。没有拿到结论，需要的话重新派」。主智能体据此在第 2 波重新调研了 Pulsar。
  • 两种都不抛给父 run：一个 SubAgent 失败是局部问题，抛出去会让整个父 run 失败。也不能让模型把失败读成「没有发现」。

方面demo真实系统（Atlas 现状）
