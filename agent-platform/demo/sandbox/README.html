1. 要解决什么问题

原来的执行环境有三块自研代码：Pod 里的守护进程 sandboxd、持有 rclone 口令的 barrier sidecar，以及唯一有 K8s 权限、负责建删 Pod 的 cluster 服务。迁移到 OpenSandbox 之后：

原来现在demo 里对应
sandboxd（执行、幂等、断线接上）OpenSandbox 的 execd（后台命令 + 游标日志）；幂等、截断等由 Atlas 的 PodSandbox 补齐execd.py、sandbox_client.py
rclone sidecar + barrier（执行前 forget、执行后等写回）整桶 PVC + 按会话 subPath（写穿式 CSI）；文件工具在沙箱运行期间路由进沙箱，和命令共用一个挂载storage.py、workspace.py
cluster（建删 Pod、幂等、配额、孤儿回收、git 档案）OpenSandbox 的 lifecycle server（两个实例）+ BatchSandbox 控制器；按会话的判断搬进 Atlasopensandbox.py、provision.py、acp.py

迁移要守住的语义：不设命令时长上限；重放同一个 tool_call 不重跑；断线后接上，输出不丢、不重复；文件工具与命令看到同一份数据；工具结果返回时产物已在对象存储里；沙箱的任何故障都是工具错误、不让整轮失败；凭据不进沙箱。

不在 demo 里：卡死判定（无输出且容器 CPU≈0）、network: none / 白名单、暂停 / 恢复、预热池、ACP 的协议细节。

2. 读懂这个 demo 需要的五个概念

① OpenSandbox 的三层，以及为什么有两个 server 实例

层做什么Atlas 怎么用
lifecycle serverREST：POST/GET/DELETE /v1/sandboxes、GET …/endpoints/{port}、POST …/credential-vault；把请求和模板合并成 BatchSandbox CR部署两个：opensandbox-sbx（原生沙箱，strict 模板）和 opensandbox-acp（ACP，模板里挂模型 key）。模板是 server 级全局的，所以只能按 kind 分实例
BatchSandbox 控制器CR → Pod；所有 Pod 都注入 execd；restartPolicy: Never（容器崩了 → Failed，不原地重启）一个，管两个命名空间
execd（Pod 里）命令、文件、指标、反向代理原生沙箱的命令和文件都经它；ACP 的 Pod 里也有，但不用
egress（可选 sidecar）网络策略、Credential Vault（按域名注入凭据）ACP 有 git 档案时开

② 工作区怎么挂：整桶 PVC + 按会话 subPath

运维建一个覆盖整个桶的静态 PVC（atlas-oss），每个沙箱在创建请求里用 volumes[].subPath 只挂自己的前缀，比如 u1/t1/workspace。对象存储凭据只在 CSI 驱动手里，Pod 里没有。驱动是 s3fs 系的写穿式：

  • 写：文件 close 时同步上传。工具结果返回时，产物已经在对象存储里，界面马上看得到。
  • 读别人的写入：界面上传、别的 Pod 改了对象存储，这个挂载要等元数据缓存过期才看得到。demo 固定为 CACHE_TTL_S = 0.6 秒，真实系统的目标是 1 秒以内。

Atlas 碰不到挂载器（它在节点上），所以不能再做「执行前 forget、执行后等写回」。一致性改由下面这条保证。

③ 工作区读写路由：文件系统的两套实现

文件工具 ─▶ WorkspaceFilesystem ── 查 Redis 路由表 sbx:route:{ws}
              ├─ 没有记录（多数会话） ─▶ OssStore    直连对象存储
              └─ 有记录（沙箱在跑）   ─▶ ExecdStore  经 execd 的文件 API 读写 Pod 里的 /workspace
                                                   ↑ 和命令是同一个挂载

路由表由 ensure 写入（建好或复用到沙箱时），由回收删除。所有 server 实例共用这张表：r3 换实例 B 来跑，它没 ensure 过，但照样知道该走沙箱。

④ execd 的后台命令

接口要点
POST /command {background: true}回一个 SSE 的 init 事件，里面是命令 id（由 execd 生成，客户端不能指定），然后连接就结束了。命令和这条连接从此无关
GET /command/{id}/logs?cursor=游标之后的全部输出，新游标在响应头 EXECD-COMMANDS-TAIL-CURSOR。游标是字节偏移（规范写的是行号），客户端只用服务端给的值
GET /command/status/{id}running / exit_code。不认识的 id → 404：命令记录只在 execd 的内存里
POST /command {background: false}前台：输出跟着 SSE 走，连接一断 execd 就 SIGKILL 整个进程组（实验 1）

⑤ 四个标识

标识谁生成存在哪用来做什么
沙箱 id（sbx-1）lifecycle serverCR 名；Redis 的端点缓存与路由表变了 = 环境重建过，结果前提示
命令 id（cmd-5）execdserver 进程内存：{run}:{tool_call} → (沙箱, 命令 id, 游标)重放、断线后接上
{run}:{tool_call}（r2:c9）Atlas同上同一个调用不重跑
令牌Atlas创建请求的 env 里；Redis 的 token:{沙箱 id}连 execd / bridge。GET /sandboxes 不会把 env 还回来，只能 Atlas 自己存（实验 8）

3. 核心思路：一句话 + 四个要点

一句话：命令交给 execd 的后台模式，文件跟着命令走同一个挂载，Pod 的生命周期交给 OpenSandbox；Atlas 只保留认识会话的判断，也就是复用、配额、回收和凭据授权。

要点 1：命令属于 execd，不属于连接

提交用后台模式，拿到命令 id 后只轮询。连接断了、Pod 换了 IP，都是用同一个 id 和游标接着读（r2）；只有「新沙箱不认识这个 id」才算命令丢了（r5）。

要点 2：一致性靠结构，不靠对账

旧方案是两个客户端（文件工具直连对象存储、命令走 FUSE）在执行边界上对账（屏障）。新方案让沙箱运行期间只剩一个客户端：同一个挂载、一个缓存、一个写入顺序。刚写的 count.py 命令马上看得到（r1），后台进程正在写的 progress.log 文件工具读得到此刻的内容（r2）。剩下的窗口只有「外部写入」这一种（r3）。

要点 3：cluster 的判断搬进 Atlas，metadata 是索引，锁保证一个会话一个沙箱

按 atlas.kind / atlas.thread / atlas.user 这几个 metadata（会成为 Pod 的 label）查找，就能做复用、配额和孤儿回收。创建请求不能由客户端指定 id，所以 ensure 必须在会话级锁里「查了再建」（实验 2）。

要点 4：凭据不进沙箱

对象存储凭据在 CSI 驱动里；git 凭据在 egress 的 Credential Vault 里，出站时注入（r6）；模型 key 只以文件形式挂在 ACP 的命名空间里，原生沙箱拿不到。

7. 几个「为什么」

7.1 为什么命令一律用后台模式？

execd 的前台命令把输出放在那条 SSE 连接上，连接断开时执行 ctx.Done() 分支，SIGKILL 整个进程组（上游 runtime/command.go）。实验 1 把 FOREGROUND 打开：r2:c9 写到第 2 行时连接被重置 → execd「是前台命令，连接断了 → SIGKILL 整个进程组」→ ran.log 只有 2 行，模型拿到「结果未知」。后台模式下同一处断线，c9 用同一个命令 id、游标 10 接上，ran.log 5 行。

后台模式唯一的空窗是「提交那一刻」：init 事件到达之前就断了，Atlas 不知道命令 id。ExecdClient.start 在这种情况下报「命令可能已开始，结果未知」，不重跑。

7.2 为什么沙箱在跑时，文件工具要绕进沙箱？

对 Pod 的挂载来说，经对象存储 API 写进来的就是「别人的写入」，要等元数据缓存过期才看得到。实验 3 把 ROUTING 关掉：c4 write_file count.py 直连对象存储 → 挂载「0.6 秒内还是旧的」→ c5 报 python3: can't open file '…/sbx-1/workspace/count.py': [Errno 2] No such file or directory，exit 2 → c6 读到一个空的 top.txt（重定向先建了空文件）。

路由之后只有一个客户端，还附带两个好处：后台进程在命令结束之后写的文件，文件工具照样读得到（r2:c8），旧方案的屏障管不到这种情况；命令和文件工具交替写同一个文件时，也没有「写回队列里的旧版本覆盖新版本」的丢更新。

7.3 外部写入为什么有窗口？窗口多大？

r3：界面上传新的 notes.txt，对象存储立刻是新的（界面直接读它）；沙箱的挂载 0.6 秒内还是旧的，命令（c12）和 read_file（c13）看到的一样旧，两者之间是一致的；c14 等 1 秒后再跑，读到新版。实验 4 把 CACHE_TTL_S 设为 0，c12 就直接读到 alpha 3。

真实系统靠 s3fs / ossfs 的短 stat 缓存加 attr_timeout=0，目标是 1 秒以内。旧方案实测过的「新内容按旧长度截断」这种错数据，在写穿式驱动上会不会出现，是设计 P0-1 的必测项，demo 模拟不了。

7.4 为什么 ensure 要加锁？为什么 Pending 不能删？为什么要留「上次用的那个」？

创建请求不能由客户端指定 id，并发的两个 ensure 都会「查不到 → 建」。实验 2 去掉锁，并在「查」和「建」之间加 50 毫秒放大窗口：r1 的 c2、c3 各建了一个沙箱（sbx-1、sbx-2），c2 跑在 sbx-1 上，c3 跑在 sbx-2 上（HOME 被分裂了，c3 还收到一条莫须有的「环境已重建」）。两个挂载就是两个客户端，sbx-1 看 sbx-2 的写入也有 0.6 秒窗口。

第一版 demo 的 _reusable 有两个问题，都是在这个实验里暴露的：

  • 把 Pending 当成坏的删掉。并发的另一个 ensure 正在等它 Running，结果拿着已经删掉的 id 去解析端点。现在改成 Pending 先等。
  • 有多个可用沙箱时取列表里的第一个。r2 断线后重新 ensure，接到了多出来的那个 sbx-1，它的 execd 不认识原来的命令，模型收到一个假的「沙箱重启」。现在改成优先端点缓存里上次用的那个，其余的立即删掉；实验 2 里 r2 打印「会话 t1 有多个沙箱：留 sbx-2，删掉 sbx-1」。

7.5 为什么不能用模板给沙箱加 sidecar？

这是之前「保留 rclone sidecar + 屏障」进不了 OpenSandbox 的根因。opensandbox.py 的 deep_merge 照搬上游的 _deep_merge：遇到列表，运行时值整体覆盖。运行时清单自带 initContainers: [execd-installer] 和 containers: [sandbox(, egress)]，模板里的同名列表整个被换掉；事后 merge_pod_spec_extras 只补回 volumes、主容器的挂载和 securityContext。实验 5 在 SBX_TEMPLATE 里加一个 oss-workspace（rclone）init 容器，Pod 就绪时打印的仍然是 init [execd-installer]。

同样的原因，模型 key 能通过模板注入（它是卷 + 主容器挂载），git 档案却不能（它要按会话选）。

7.6 为什么令牌要由 Atlas 存？

令牌是 Atlas 生成、经创建请求的 env 交给沙箱的，GET /sandboxes 不会把 env 还回来。实验 8 在 r2 之前删掉 Redis 里的端点缓存和 token:sbx-1：ensure 按 metadata 找到运行中的 sbx-1，却拿不到令牌 →「用不了 → 删掉重建」→ sbx-2，模型看到「环境已重建」，HOME 里装的东西没了。令牌的存储要和路由表一样可靠（见 §11 问题 1）。

7.7 回收为什么先删路由、再删沙箱？为什么不用排空？

先删路由，之后的文件操作就走对象存储（r4:c15 读 top.txt 不需要沙箱）。如果先删沙箱，正在路过的文件操作会打到一个不存在的 Pod；WorkspaceFilesystem 会问 lifecycle server，确认沙箱确实不在了，再删路由、改走对象存储重试，但这是兜底，不是主路径。写穿下挂载里没有待上传的数据，所以不需要旧方案的「排空写回队列」。回收和 ensure 拿同一把会话级锁，避免一边回收、一边复用。

7.8 为什么沙箱消失是工具错误？为什么不撤销副作用？

r5 执行到一半，Pod 被删（节点故障），BatchSandbox 进入 Failed（restartPolicy: Never，不会原地重启）。PodSandbox 连不上 → 重新 ensure：Failed 的删掉，建 sbx-3 → 去 sbx-3 的 execd 查 cmd-2 → 404 → SandboxUnavailable → 工具错误。模型决定重跑（c18），这一轮继续，不会整轮失败。第一次跑到一半写的 3 行还在 reg.log 里（共 11 行）：平台不撤销已经发生的副作用，与 native 设计 §08 的 regenerate 语义一致。

7.9 git 凭据怎么做到不进 Pod？

r6：OpenSandboxPods 先判定档案能不能用（teamflow-gitee 只给 source_app=teamflow 的会话），创建请求带上 networkPolicy 和 credentialProxy（于是 Pod 里有 egress sidecar），建好后把凭据写进 Credential Vault。CLI 的环境里有模型 key（bridge 从模板挂的文件读的），没有任何 git 凭据；git push 的请求不带认证，经过 egress 时命中 gitee.com 的绑定，被注入 Basic 认证。实验 6 不写 Vault：Gitee 返回 401，CLI 报「git push 失败」。

7.10 配额为什么是软上限？超额为什么只是工具错误？

配额（两种沙箱合计）是「先数再建」，同一时刻并发的两个 ensure 可能一起通过。这与现在子智能体准入的已知问题同类，靠会话级锁只能挡住同一会话的并发。实验 7 把 QUOTA_PER_USER 设为 0：r1 的三个 execute 都是「沙箱启动失败：该用户已有 0 个沙箱（上限 0）…」，文件工具照常走对象存储，r1 正常结束。

11. 顺带发现的问题（回写设计）

状态（2026-10-20）：三条都已回写设计 §13 / §14，并在 Atlas 代码里实现（providers/opensandbox/provision.py），单测见 agent-platform/tests/test_sandbox_provisioner.py。

问题 1：令牌的持久化没写进设计

设计 §12 只写了「bridge 和 execd 的令牌由 Atlas 生成、经 env 传入」。但 GET /sandboxes 不会返回 env，Atlas 不存就再也拿不回来，丢了只能删掉重建，用户的 HOME 跟着丢（实验 8）。建议在 §13 / §14 补上：令牌按沙箱 id 存进 Redis（或数据库），与路由表同级的可靠性；随沙箱删除一起清理。

问题 2：ensure 遇到 Pending 不能当坏的删

设计 §14 的流程只写了「有但 Failed / Terminated → DELETE 后重建」，没说 Pending。Pending 可能是并发的另一个 ensure 正在建（锁失效时），也可能是建到一半崩掉的进程留下的；直接删会让前者拿着已删的 id 去解析端点。demo 的做法：先等它离开 Pending，Running 且令牌在就复用，否则删掉。

问题 3：一个会话有多个沙箱时，选哪个

设计 §13 写的是「万一出现重复，由孤儿回收删掉多余的」。实验 2 说明这不够：在回收之前，断线重连按列表顺序可能接到另一个沙箱，命令就「丢」了。而且两个挂载就是两个客户端，又回到了缓存不一致。建议在 §14 的复用规则里写明：优先端点缓存里上次用的那个，其余的当场删掉。
