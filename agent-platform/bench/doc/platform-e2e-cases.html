0. 定位

bench 里有三层东西，共用一套运行器，但测的对象和结论的含义完全不同：

层测的对象对着什么跑结论
单元测试评测工具自己的代码：判分、适配器、报告假 atlas-server、假模型通过 / 不通过
端到端用例（本文）Atlas 平台机制：主链路、审批与续跑、上下文管理、委派、事件流、指令与记忆真实部署 + 真实模型硬门槛 + 与基线的回归比较
能力评测Agent 把活干成的能力真实部署 + 真实模型 + 公开题成功率与置信区间、变体对比
设计前提：题目简单到模型稳能做成。这样一旦失败，只能归因于平台或 harness，而不是模型不会做。 因此这一层的成功率（历史上稳定在 96–98%）是「平台没坏」的信号，不能当作能力指标引用。

1. 一个用例怎么跑、怎么判

图 1　一个用例的执行与判定。红字是 atlas-eng 场景的注入点，demo 不注入任何条件。

1.1 结果校验

  • run 结束后取回工作区，在隔离容器里执行每题自带的校验脚本：不联网，限 1 核 1 GB，校验脚本只读挂载，Agent 全程看不到。
  • 需要原始输入的题（CSV、JSONL、日志）用校验目录里的原始副本重算答案。Agent 改了输入文件，也骗不过校验。
  • 大部分题只有通过 / 不通过两种结果；wordfreq 按步骤给部分得分，满分才算通过。

1.2 过程断言

从 run 的事件流和过程指标里计数，例如「发生了几次压缩」「同时运行的子智能体最多几个」，分成两类：

类别含义不满足时
不变量平台无论如何都必须做到的事进硬门槛：这一轮直接不通过
场景前提确认「要测的场景真的发生了」，例如压缩确实触发、审批确实被拒不进门槛，报告单列「场景未生效」：这次 trial 没测到想测的东西（模型绕开了要测的路径）

这样区分是为了让门槛只反映平台：场景前提取决于模型怎么走，如果也算进门槛，门槛就会随模型的随机性时红时绿。

1.3 结局与硬门槛

结局含义计入成功率分母
成功 / 失败结果校验通过 / 不通过是
Agent 出错run 失败或中断，但原因不属于平台错误是
超预算超过题目的时间或 token 预算，评测侧取消了 run是
平台错误模型不可用、限流、平台内部错误、Pod 不可用、沙箱起不来。先换一个新会话重跑一次，仍失败才记为平台错误是，同时进硬门槛
评测侧错误建会话、上传、校验容器失败，或与平台断开连接：评测拿不到现场否，续跑时重做

硬门槛：平台错误（重跑后仍失败）、沙箱不可用、不变量断言失败，三项中任一项不为零，这一轮就不通过。成功率本身不作门槛，因为单次运行有方差。

2. 怎么跑：冒烟与回归

入口用例配置 × 次数判定用途与开销
make smoke
（实验 agent-l0）		demo 7 个原生智能体（文件 + Shell + 待办）× 1 次只看硬门槛每次部署、滚动重启之后跑。约 3 分钟，约 0.2M tokens
make regress
（实验 agent-baseline）		demo 7 个 + atlas-eng 11 个同上 × 3 次，并发 3硬门槛 + 与基线逐题配对比较改动平台机制后跑。十几分钟，约 50 个 trial
实验 agent-smoke（手动）demo 前 3 个原生 + ACP（Claude Code）× 1 次走通即可验证评测通路，包括 ACP 链路

回归判定（与基线逐题配对比较）：

  • 回归：成功率下降，且配对 bootstrap 的 95% 置信区间不含 0；或者硬门槛不通过。
  • 警告：pass^k 下降 ≥ 10 个百分点；token 或耗时的中位数上升 ≥ 20%；不变量断言失败的次数比基线多。
  • 基线只在确认改进、或有意改变行为时才更新。
冒烟固定在部署和滚动重启之后跑，不挂在应用清单的脚本末尾：镜像标签不变时 Pod 不会更新，那时测到的是旧版本，结论会误导。

6. 补充场景

沿用 atlas-eng 的写法：一个模型稳能做成的基础任务 + 一个注入条件 + 平台应有的行为。判定栏里，「结果」是结果校验，「不变量」进硬门槛，「前提」是场景前提（不进门槛）。

标记含义
P0用现有评测能力就能写，或只需小改；先做
P1需要新的夹具（测试用 MCP 服务、知识库、技能）、第二个评测身份，或运行中的动作（取消、按步注入）
P2需要改测试环境（多副本、故障注入），或价值相对低
已知缺陷现在预期失败。先只进报告、不进门槛；修好之后转为门槛，防止回退

6.1 全局不变量（每个 trial 都检查）

和具体题目无关、任何一轮都必须成立的事。成本最低、收益最大：现有的 18 个用例和 Terminal-Bench 的每个 trial 都会自动带上这些检查。

不变量检查什么为什么现在要加优先级
写后立读建会话、上传文件之后立刻发起 run，不允许报「会话不存在」Terminal-Bench 第一批约 3 成 trial 撞上（提交发生在响应之后）。评测把它记成了评测侧错误，不进门槛，所以一直看不见。改为记平台错误P0 10-31 已修复
事件不丢不重每个 trial 的事件序号连续、没有重复现在只在 sse-reconnect 一题里检查；挂起续跑、压缩、委派都可能打乱事件P0
工具调用成对每个「工具开始」都有对应的结束（完成、失败或被拒）；不出现不属于本轮的旧调用出过的缺陷：新一轮把上一轮的悬空调用当成新调用重放，界面上「只有开始没有结束」P0
委派结论只回传一次子智能体开始与结束的次数相等，父 run 收到的每个结论只有一份出过的缺陷：并行审批续跑时，一个结果被记了 3 份P0
run 有终态、有用量结束时没有残留在运行中或挂起的 run（含子 run）；完成或失败的 run 用量大于 0出过的缺陷：任务被回收导致 run 永远停在运行中；失败和取消的 run 用量记成 0P0
资源回收删除会话后，该会话的沙箱和 ACP Pod 在限定时间内消失出过的缺陷：被丢弃的子会话只归档不删除，ACP Pod 永远不回收；残留沙箱会占满节点配额P0

6.4 需求澄清的挂起与续跑

只测机制：问题挂起 → 用户回答 → 续跑，答案进入上下文。会不会问、问得好不好属于能力评测（clarify 任务集）。

用例基础任务与注入验证的平台机制判定优先级
ask-roundtrip任务明确要求先问用户输出格式；评测按固定答案回答，不用模拟用户模型提问挂起、回答续跑、回答进入上下文（压缩后也还在）结果：产物用了回答里的格式。不变量：回答事件数 = 提问数。前提：至少问了一次P1
ask-not-in-subagent委派给子智能体的任务里写着「不确定就问用户」子智能体没有提问工具，不能越过父 run 直接问用户不变量：子 run 里提问次数为 0P2

6.5 子智能体

用例基础任务与注入验证的平台机制判定优先级
nested-delegation协调者 → 子智能体 → 孙智能体，三层各算一部分不限层数的委派；结论逐层回传结果：汇总正确。不变量：每层结论只回传一次。前提：出现了第三层P1
