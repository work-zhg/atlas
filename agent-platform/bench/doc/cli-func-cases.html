0. 定位、分层与判定

CLI 智能体和原生智能体对用户是同一个产品：同样的会话、同样的事件流、同样的审批弹窗。区别在执行：模型调用、工具执行、上下文管理都由会话 Pod 里的 CLI 自己做，平台只负责把 Pod 和能力备好、把这一轮交给它、把 CLI 的输出翻译成平台事件、把权限请求转成平台审批。所以 CLI 的功能用例主要回答四个问题：

  • 能不能用：Pod 起得来、多轮能接上、文件进得去出得来、做完的东西用户看得见。
  • 和原生是否一致：事件长得一样（前端不加分支）、审批走同一套、用量照样记账。平台给原生智能体的东西（提示词、技能、标题）CLI 有没有。
  • 管不管得住：权限模式按配置生效、取消停得下、CLI 读不到平台的凭据。
  • 出事时结果是否明确：server 换实例、断网、Pod 没了、CLI 崩溃时，这一轮要么接着完成，要么给出原因明确的失败，不把同一句话交给 CLI 做两遍。

分层同沙箱用例，只是没有模型反应（M）这一层：CLI 的失败不以工具结果的形式回到模型，而是直接结束这一轮，由用户决定是否重发。

层对着什么跑适合放在哪
L1 集成测试pytest + 假 bridge / 假 CLI（atlas_bridge.testing）、假 OpenSandbox协议细节和要卡准时机的情况：补发与确认点、取消不回应、恢复失败、模式降级。现有覆盖已经很多（各用例里注明）agent-platform/tests/test_cli_*.py、pod/bridge/tests
L2 端到端真实部署 + 会话 Pod 里的真实 Claude Code，不注入故障功能、权限模式、能力下发、子智能体、安全边界bench 新任务集 cli-eng
L3 故障集同上，运行中注入故障：删 server Pod、滚动部署、删会话 Pod、断网、结束 CLI 进程接续、Pod 重建后的恢复、失败原因同一任务集的 chaos 标签，串行，只在测试环境

判定沿用平台端到端用例 §1：结果是结果校验；不变量进硬门槛；前提是场景前提，不进门槛；已知缺陷现在预期失败，先只进报告，修好后转为门槛。

每题都带的不变量（CLI 版的全局不变量）
  • run（含子 run）都有终态；完成的 run 用量大于 0；事件序号连续、不重复（同平台端到端用例 §6.1）。
  • 正文一致：每个 run 的 message.completed 正文，等于这个 run 的 message.delta 按顺序拼起来；思考内容（thinking.delta）不混进正文（EVT-01）。
  • 工具调用成对：每个 call_id 恰好一条 tool.started、恰好一条终态；工具名非空、只有一行（EVT-02）。
  • 用量可计价：usage.updated 带模型名；至少一条 context.usage（basis = cli）（EVT-03）。
  • 没有预期之外的 session.lost；没有预期之外的失败（预期失败由任务声明，见 §4）。
副作用计数：沿用沙箱用例的 marks/mark.sh
会话 Pod 的 /workspace 也是 s3fs 挂载，计数脚本原样能用：start 文件数 = 命令执行了几次，end 文件数 = 跑完了几次，工具结果里的随机令牌 = CLI 拿到了真实输出，start 文件里的 hostname 就是会话 Pod 名（一个会话用过几个 Pod）。两处不同：
  • CLI 的 Shell 工具不叫 execute，工具名是命令本身的第一行（截到 80 字）。识别调用改为看参数里的 command 是否调用了 mark.sh，不看工具名。
  • 「平台有没有替 CLI 多跑」的判据不变：start 文件数 ≤ 调用它的 call_id 数。CLI 自己决定重跑会有新的 call_id，算 CLI 的事。
按人共享之后（2026-11-09）
会话 Pod 改为一个人共用：同镜像、同凭据集合的 CLI 会话至多 4 个进同一个 Pod，每个会话起自己的 bridge；整个用户目录挂在 /data，CLI 的 cwd 是根会话的工作区；CLI 的会话记录在 /data/home/.claude（一人一份），HOME 改在本地盘（/tmp/home，Pod 重建后清空）；技能一人一份、可写；会话之间不隔离（用户 11-04、11-09 定的）。下面几条的期望因此改了：
  • POD-04、SUB-03：删会话 / 子会话归档只停这个会话的 bridge，Pod 还有别的会话时不退役。回收看「这个会话的 bridge 停了」（Pod 没了也算）。
  • SES-02、CRS-01：Pod 重建后留下的是工作区和 CLI 的会话记录；HOME 里的文件不再保留，只记录不判定。
  • ISO-04（同一个人的两个会话互相看不见）、ISO-05（/skills 只读）与上面的规则相反，不做。跨用户隔离要第二个评测用户，归到之后。

C8⑤ CLI 进程崩溃bridge 重启 CLI 并恢复同一个会话（10 分钟内最多 3 次，间隔 1 / 5 / 30 秒）；超过节制就结束会话、bridge 退出这一轮 run.failed（runtime_crashed）；下一轮正常CRS-02、03
C9⑤ 两条更新之间静默太久：等模型时超过 idleS（120 秒），工具执行中超过 toolIdleS（600 秒）bridge 取消这一轮。这是唯一的「卡死」判据，一轮本身没有时长上限run.failed（agent_stalled）STP-04
C10⑤ 用户取消turn.cancel → CLI 的 session/cancel；15 秒宽限内不结束就杀掉 CLI 并重启；挂着的权限请求一并作废run.cancelled；超过宽限 runtime_crashed 取消后 CLI 没有响应，已被终止并重启STP-01～03、STP-05
