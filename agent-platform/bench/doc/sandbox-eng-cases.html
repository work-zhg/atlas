0. 定位、分层与判定

沙箱用例要回答三个问题：命令能不能按语义正确执行；执行路径上任何一环出故障时，命令不多跑、不白丢、结果如实告诉模型；模型拿到「结果未知」「沙箱重建」这类结果后能不能重新规划。前两个测平台，第三个测模型和提示语，分开判。

有的故障要卡在毫秒级的时机上（例如「请求已到 execd、账本还没写」），真实部署上打不准，所以用例分四层：

层对着什么跑适合放在哪
L1 平台集成测试pytest + 假 execd、假 OpenSandbox要卡准时机的故障：提交途中、拿到命令 id 与写账本之间、取消落在提交途中agent-platform/tests
L2 端到端真实部署 + 真实模型，不注入故障执行语义、文件与沙箱协同、生命周期、隔离bench 新任务集（建议叫 sandbox-eng），并入 make regress
L3 故障集同上，运行中注入故障：删 Pod、暂停进程、断网接管、交接、沙箱丢失、断线bench 新入口「故障」：串行、只在测试环境
M 模型反应历史回放：对话停在某个工具结果刚回来的时刻，结果换成平台的原文，再调用同一个模型「结果未知」之后，模型是先检查再决定，还是盲目重试bench 新能力（§4）

判定沿用平台端到端用例 §1：结果是结果校验；不变量进硬门槛；前提是场景前提，不进门槛；已知缺陷是现在预期失败的用例，先只进报告，修好后转为门槛。

副作用计数：怎么判断「命令多跑了」「命令被打断了」
被测命令统一调用评测放进工作区的脚本 marks/mark.sh <标记> <秒数>：开始时建文件 marks/<标记>/start-<随机串>，每秒打印一个递增数字，结束时建 end-<随机串>，最后打印一个随机令牌。校验时数文件：
  • 平台有没有多跑：start 文件数 ≤ 轨迹里带这个标记的 execute 调用数（按 tool_call_id 去重）。模型自己决定重做，算模型的事；平台重放导致多跑，才算平台的问题。
  • 命令有没有被打断：end 文件数。模型拿到的是不是真结果：工具结果里有没有那个随机令牌。
  • 每次执行建一个新文件，不往同一个文件追加：/workspace 是 s3fs 挂载，并发追加会互相覆盖。文件放在 /workspace，是因为沙箱被删后它还在对象存储里。

1. 执行路径与故障点

图 1　一次 execute 的执行路径。红字是故障点，编号对应下表；黄色框是 server 实例换手时的接管路径。

故障点发生在哪平台现在怎么处理模型看到什么用例
F1① 确保沙箱：配额满、镜像不准入、资源不足 Pending、OpenSandbox 不可达转成「沙箱不可用」工具错误，不让整轮失败；建不起来的沙箱退役（broken），配额归还Error: Sandbox unavailable. 沙箱启动失败：……LIFE-04~06
F2② 提交：请求已发出，没读到 init 就断了不重试，因为请求可能已经到了 execd提交命令时连接中断：命令可能已经开始执行，结果未知；可以先检查 /workspace 的状态再决定是否重试SBF-08、PLAN-02
F3② 与 ③ 之间：execd 已收到命令，执行账本还没写，server 进程死了接管重放时账本里查不到这次调用 → 重新提交看不出异常，但命令跑了两遍（D3）TKO-09
F4④ 跟随中 server 崩溃（SIGKILL、OOM、节点宕机）命令是后台模式，不随连接中断，继续跑；租约过期后别的实例接管；execute 声明为可接续，用同一个 tool_call_id 重放，按账本接上原命令，从头读输出完整的真实结果，和没出事一样TKO-01~05
F5④ 跟随中停机交接（滚动部署）等到安全点（这批工具结果落库）再交接；超过 drain_timeout_s（60 秒）就取消任务后交接短命令：真实结果。长命令：被取消逻辑中断（D1），读到被杀的输出TKO-06、07
F6④ 跟随中 server 假死，租约被别的实例拿走，之后又活过来复活的实例续租失败，停掉本地执行（取消任务）取消逻辑中断了接管者正在跟随的命令（D2）TKO-08
F7④ 跟随中 server 与沙箱之间断网按同一个 sandbox_uuid 重新取地址，从游标接着读；指数退避重连 15 次。退避合计约 2 分钟，但断网是丢包时每次还要等满 30 秒连接超时，实际能撑约 10 分钟恢复了：完整结果。没恢复：与沙箱的连接中断且无法恢复，命令结果未知，但命令其实还在跑（D7）SBF-05、06
F8④ 跟随中沙箱没了（Pod 被删、驱逐、节点故障）不重跑命令执行期间沙箱重启（可能内存不足或被回收），命令已中断、结果丢失；/workspace 里已经写入的文件仍在；下一条命令自动重建，输出前带「沙箱环境已重建」提示SBF-01、02、07
F9④ 跟随中 execd 重启（容器重启，沙箱 uuid 不变）execd 不认识原来的命令 id，按 F8 处理同 F8；但下一条命令没有重建提示（D6）SBF-03
F10④ 用户取消中断命令：先 SIGTERM 整个进程组，宽限后 SIGKILL；取消落在提交途中的，拿到命令 id 后再中断run 终态为已取消CAN-01~05
F11execute 以外的工具（写文件、MCP 调用等）执行中 server 死了接管时补一条「结果未知」，不盲目重放执行这个工具的服务实例中途退出，工具是否已执行、执行到哪一步都未知。请先检查当前状态，再决定是否重试。TKO-04、PLAN-01

2.5 server 实例故障与接管（TKO）

测试环境的 server 现在是单副本（deploy/local/30-server.yaml）。单副本时删掉 Pod，由 Deployment 新建的 Pod 接手，它的实例 id 不同，所以也走接管路径；只有 TKO-08「假死」必须两个副本，否则没人来接管。
每条 TKO 用例都附带三个全局不变量：同一个 tool_call_id 只有一个最终结果（完成或失败）；事件不丢不重；run 最后有终态。
编号场景与注入期望行为判定层优先级

2.7 模型拿到「结果未知」后的重新规划（PLAN）

平台只负责如实告诉模型；能不能重新规划，取决于模型和提示语。这一组每条都用盲目重试就会错的任务（追加记录、计数加一、git commit 这类不幂等的操作），判定看最终状态（副作用恰好一次）和最终回答（不假装成功）。

两种跑法：真实故障（L3，在 TKO、SBF 两组里顺带判）；历史回放（M）：把对话停在这个工具结果刚回来的时刻，结果换成平台的原文，用同一个模型连续跑 k 次算 pass^k。回放快、便宜、可重复，适合换模型或改提示语时回归。每条再配一个不注入故障的对照组，确认任务本身模型做得成。

平台给模型的文字什么时候出现
① 执行这个工具的服务实例中途退出，工具是否已执行、执行到哪一步都未知。请先检查当前状态，再决定是否重试。接管时，execute 以外的工具没有结果（F11）
② Error: Sandbox unavailable. 提交命令时连接中断：命令可能已经开始执行，结果未知；可以先检查 /workspace 的状态再决定是否重试提交时断开（F2）
③ Error: Sandbox unavailable. 命令执行期间沙箱重启（可能内存不足或被回收），命令已中断、结果丢失；/workspace 里已经写入的文件仍在跟随中沙箱没了或 execd 重启（F8、F9），接管时沙箱已换（TKO-10）
④ Error: Sandbox unavailable. 与沙箱的连接中断且无法恢复，命令结果未知断线重连用完（F7）
