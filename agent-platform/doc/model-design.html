0. 方案概览

图 0　方案总览：Atlas、Pod 里的 CLI、平台功能都只连模型网关；网关按 Key 认人、按用户中心判权（平台功能按应用和用途放行），边转发边计量，再带上网关凭据转发给 Higress；供应商 Key 只在 Higress，Higress 只认模型网关

问题方案
模型怎么接入先在 Higress 上声明供应商（供应商 Key、协议、同一个模型的多个上游），再在模型网关登记一个稳定的平台模型名，上游指向 Higress。接入检查、能力探测通过，管理员确认属性后才可用
模型的属性谁维护模型网关是模型目录的唯一事实源：类型、模态、协议、能力、上限、参数规则、价格、合规、生命周期都在这里。Atlas、知识库从它读，不再写死在代码和部署配置里。能力靠探测加人工确认，不靠猜
谁能用哪个模型唯一事实源是用户中心的数据权限，数据编码属于模型网关这个应用：一个对话模型一条数据，"使用"级别 = 能选、能调。按这一轮的权限主体判，规则同 MCP：以人为权限的 Agent 是使用者本人，以 Agent 为权限的是它的数字员工
平台功能用什么模型会话标题、记忆补记、知识库的入库增强与检索这类平台功能，由模型管理员按用途指定模型。调用方带上应用身份和用途，网关按用途放行，不按人判权
网关怎么认人每个主体一把模型 Key，只表示"我是谁"，不带权限；第一次被取用时自动生成，不需要手工发放。和 MCP 的 Key 分开
谁能调 Higress只有模型网关。供应商 Key 只在 Higress；ACP 的 Pod 里不再有供应商 Key，只有主体 Key。直连 Higress 或供应商都调不通
两道闸门Atlas 侧：编辑器只列能用的模型，保存时校验，Run 开始时检查。模型网关：每个请求都认人、判权、查模型状态，兜住 Pod 里的 CLI 和泄露的 Key
用量和成本网关边转发边读用量，每次调用都记到主体、模型、用途上，按请求时的价目折算成本；可以按人、部门、Agent、用途汇总；额度将尽、用量突增、供应商出错都会预警。预算和限流本期不执行
调用失败怎么办无权、停用、下线：本轮不开始，或者停下并说明该找谁。暂时不可用：沿用现有的退避重试，用尽后本轮失败。Key 刚被重置：重新取一次 Key 再发
模型怎么下线分弃用、下线两步，替代模型和下线日期提前公布；弃用期间照常可用并提示；下线后不自动换成别的模型
出了问题怎么止血模型有问题：在模型网关停用，立即对所有路径生效。Key 泄露：停用或重置。供应商出事：在 Higress 切到同一个模型的其他上游。网关凭据泄露：轮换

1. 背景与目标

1.1 现状

已经有的能力（已对照代码）：

  • Atlas 维护一张模型能力表：上下文窗口、最大输出、是否支持思考、档位、温度、提示词缓存、最小可缓存长度。这些值是对着网关逐个实测出来的，例如某些模型传了温度就直接 400。
  • Atlas 定时拉取上游的模型列表来标记"是否可用"。上游的模型列表只给标识，没有能力信息。
  • 构造模型请求时，不支持的参数一律不发；Agent 配置里的思考、档位保存的是意图（自动 / 开 / 关），由 Atlas 按模型能力翻译。
  • 429、5xx 由 SDK 退避重试；单次请求按两段数据之间的静默判断卡死，一轮本身不设时长上限。
  • Higress：MCP 已经收口到它；模型的供应商接入也放在 Higress 的 AI 路由上配置。

存在的问题：

问题说明
谁都能用没有模型授权：任何人、任何 Agent 都能用全部模型。贵的模型、数据会出境的模型，没法只开给一部分人
用量和成本说不清只有 Native 的 Run 记了 token。ACP Pod、知识库、会话标题这些调用没有统一记录，说不出谁、哪个部门、哪个 Agent 花了多少
没有额度预警所有服务共用一个供应商账号。10-22 账户余额不足，所有模型调用同时失败，事先没有任何提示
供应商 Key 进了 PodACP 会话 Pod 里挂着平台的供应商 Key 原文。Pod 里的代码可以绕过平台直接调供应商，用了多少、给谁用的都查不到
Key 和地址散落Atlas、知识库、ACP 的部署配置里各存一份地址和 Key。换 Key 要改好几处，还要重新部署
模型知识写死在代码里哪个模型收不收温度、支不支持思考，一份在能力表里，另一份按模型名写死在代码里兜底，两份要人工同步；写死的那份只覆盖 Claude 系列的模型名，实际在用的模型并不在里面。接一个新模型就要改代码
模型名写死在部署配置里会话标题、记忆补记、知识库、ACP 用哪个模型由部署配置决定，换模型要重新部署
"协议"要编辑者来选Agent 配置里要选 anthropic 还是 openai。这是模型的接入属性，不该让编辑者判断；现在 DeepSeek 的模型也得填 anthropic
下线没有流程模型下线以后，引用它的 Agent 要到运行时才报错，维护者事先不知道

1.2 目标

  • 收口：所有模型调用都经自研模型网关；Higress 只接受模型网关的请求；供应商 Key 只在 Higress。
  • 授权只有一个事实源：用户中心的数据权限；人、部门、数字员工用同一套授权。
  • 用量和成本看得清：每次调用都记到主体、模型、用途上，能按人、部门、Agent、用途汇总；额度和异常能提前预警。
  • 模型目录只有一份：能力、上限、参数规则、价格、生命周期都在模型网关维护；接新模型、改能力，不改代码、不重新部署。
  • 和 MCP 是同一套模式：权限主体、Key、两道闸门、只认网关都相同，运维和用户只需要理解一次。
  • Higress 可替换：Higress 只是模型网关的一种上游；以后替换时，Atlas、Pod、授权都不受影响。

1.3 非目标

  • 预算、配额、限流的执行：本期只计量、展示和预警，以后怎么加见 10.4。
  • 个人在 Atlas 之外用 Key 调模型：网关按 Key 认人、按授权判权，已经具备条件；但本期 Key 只给 Atlas 用，不显示原文。
  • 换模型的自动回退、自动跟随新版本的别名：都会让 Agent 的行为在维护者不知情的情况下改变（5.3、9.4）。
  • 内容安全护栏、按数据密级限制模型：合规属性本期只记录和展示，作为授权时的判断依据。
  • 进程内的本地模型：知识库在进程里运行的本地向量、重排模型不经网关，也不登记。
  • 记录提示词和输出：网关只记调用的元数据和用量，不记内容。语义缓存、提示词改写也不做。
  • 其他类型：本期只管对话、嵌入、重排三类；图像、语音等以后再加。
  • 微调、自部署推理服务的运维。
  • 安全加固：Key 的加密存储、内网接口的访问控制、Pod 网络隔离等，后续统一设计。"只有模型网关能调 Higress"不在此列，本期就做（9.3）。

2. 业界怎么管理模型

2.1 几类做法

类别代表怎么管

2.2 共同的做法，以及本方案怎么取舍

#业界的共同做法本方案
1对外的逻辑模型名和上游部署分开平台模型名稳定不变，上游可以换（4.3）
2供应商 Key 只在网关里，对外发网关自己签发的 Key供应商 Key 只在 Higress；对外发主体 Key（6.5）
3谁能用哪个模型，挂在 Key、团队、项目上，由网关自己存不同：事实源是用户中心的数据权限，网关每次去问（带缓存），不在 Key 上或网关里另存一份（6.3）
4用量按 Key、用户、团队、项目归集；价目表有版本，和供应商账单对账网关边转发边计量，按请求时生效的价目折算成本（10）

10护栏、内容安全、只走不留存数据的路由本期只记录合规属性，不执行（1.3）

和多数网关的主要差别在第 3 条。网关自己存授权（Key 白名单、团队、订阅）的做法，在只有一个网关的公司里很自然；但 Atlas 已经把人、部门、数字员工、Agent、知识库、MCP 服务的授权都放在用户中心，再让模型网关另存一份，就会出现两个事实源：部门调整、人员停用都要同步，还会有延迟和不一致。HiMarket 那种"订阅后把白名单下发到 Higress"的做法也有同样的问题，MCP 方案已经否掉了"授权进 Higress"（MCP 方案 8.3）。

3.4 为什么自建模型网关

做法好处问题
自建模型网关在 Higress 前面，判权问用户中心（本方案）授权只有一个事实源；人、部门、数字员工一套规则；只有它看得到全部调用，能按主体计量；和 MCP 是同一套模式多一跳；关键路径上多一个服务，要按数据面的标准来做（9.2）
把授权同步进 Higress：每人一个消费者，加上路由白名单和配额插件；或者像 HiMarket 那样订阅后下发请求路径不依赖控制面，用的是 Higress 现成的能力授权有两份：用户中心一变就要同步，部门授权、全部授权都要展开到人，存在延迟和不一致；Higress 不认识用户中心。MCP 方案已经否掉了这条路
并进 MCP 网关，一个服务管两类少部署一个服务；Key、判权、登记数据对象的代码只写一份两类流量的特征差别很大：模型调用是长时间的流式输出，并发高，还要计量。故障也会绑在一起：MCP 网关出问题只影响工具，模型网关出问题所有 Agent 都不能对话。扩缩容和发布节奏也不同

两个网关里相同的部分（主体 Key、判权缓存、在用户中心登记数据对象、接入检查）共用一份实现，部署成两个独立的服务。

5. 模型目录：属性、能力、生命周期

5.1 模型网关是事实源

  • 只有一份：模型的全部属性都在模型网关。Atlas 的模型能力表和代码里按模型名写死的规则一起退役；知识库、ACP 的模型名也不再写在部署配置里。
  • Atlas 读目录并缓存：缓存在多副本共享的存储里；编辑器、保存校验、Run 开始检查都读缓存。目录变化后由网关通知或定期刷新；刷新失败时保留旧的目录。
  • 和 MCP 的差别：MCP 的工具定义能从上游拉取；模型的属性拉不到，上游的模型列表只给标识，所以由管理员维护，并靠探测保证准确（4.4）。

6. 权限

结论先行：谁能用哪个对话模型，事实源只有一个，就是用户中心的数据权限（"使用"级别），数据编码属于模型网关这个应用。Key 只是持有人在模型网关上的凭据，本身不带权限。Agent 的权限类型决定这一轮的权限主体，也就决定了按谁的权限选模型、带谁的 Key，规则和 MCP 相同。平台功能是例外：它们不是某个人的选择，按应用和用途放行。鉴权只在模型网关做，Higress 只认模型网关这一个调用方。

6.2 权限主体

图 4　两种调用身份：Agent 的推理按权限主体、问用户中心；平台功能按应用和用途、看用途配置。两者的用量分别记到主体和用途上

权限主体的确定方式和 MCP 完全相同（MCP 方案 5.2）：以人为权限的 Agent 是私人助理，主体是使用者本人；以 Agent 为权限的 Agent，主体是它的数字员工。判定一律走 Agent 的数据权限；主体取"当前这个人"，不取创建者；内联的 SubAgent 沿用父 Run 的主体，委派给另一个独立 Agent 时按目标 Agent 重新确定。

和 MCP 的一个重要差别：MCP 工具缺一个可以跳过，模型缺了这一轮就做不了。所以主体没有模型权限时不是"跳过并提示"，而是本轮不开始，并说明缺的是哪个模型、按谁的权限判的、该找谁（7.1）。这对以 Agent 为权限的 Agent 尤其要紧：数字员工没有任何模型授权，这个 Agent 就运行不了。编辑器和"身份"面板要把这一点讲清楚（11）。

6.3 模型授权：用户中心数据权限

  • 模型网关是用户中心里的独立应用，拥有"模型"这个数据编码。用户中心规定数据编码只能由所属应用登记和查询，所以登记数据对象、查询主体能用哪些模型都由模型网关来做；Atlas 要知道主体能用哪些模型，就问模型网关。
  • 一个对话模型是一条数据，标识就是平台模型名。嵌入、重排模型只供平台功能使用，不按人授权（6.7）。
  • 级别：使用 = 能在 Agent 里选、能经模型网关调用；所有者 = 能给人、部门、数字员工授权和收回，登记人自动成为所有者。"读写"级别不用：模型属性由模型管理的操作权限管。
  • 常见的授法：通用模型授给根部门（含下级）；贵的、数据会出境的、还在试用的，只授给需要的人或部门；数字员工逐个模型授权。

6.4 两道闸门

图 5　两道闸门：闸门一让问题在 Run 开始前暴露；闸门二在模型网关，每个请求都认人、判权、查模型状态，兜住 Pod 里的 CLI 和泄露的 Key。平台功能的调用在闸门二按应用和用途放行（6.7）

  • 编辑器：只列主体能用、状态可用的模型（问模型网关）；没权限的模型不列出，只显示个数，并说明是按谁的权限列出的（11.2）。
  • 保存：只校验新选的或者换了的模型，主体没有"使用"就拒绝保存；已经选着的不重判，免得授权被收回以后连提示词都改不了。参数按模型规则校验（5.2）。切换权限类型时不重判，主体变了以后无权的模型在"身份"面板里标红。
  • 以 Agent 为权限的 Agent 第一次保存：保存之后才有数字员工，这时还不可能有授权，所以不校验模型授权，编辑器按"状态可用"列出全部对话模型并提示"保存后请模型所有者给数字员工授权，授权之前不能运行"。
  • Run 开始：检查这一轮用到的模型（7.1）。
  • 为什么还要网关这一道：闸门一只管经过 Atlas 代码的调用。ACP 会话里 CLI 直接调模型网关；Key 泄露以后可以在 Atlas 之外调用。这两种情况只有模型网关拦得住。两道闸门问的是同一份授权。

6.5 模型 Key

决策理由
一个主体一把，只表示身份同 MCP（MCP 方案 5.5）："能用什么"交给数据权限，重置 Key 不丢授权，也不会有"Key 的权限"和"人的权限"两份数据
和 MCP 的 Key 分开两个网关各自认人：一把泄露不影响另一把；停用模型 Key 不影响工具，反过来也一样。共用一把的话，两个服务要共享一份 Key 库，耦合在一起
自动生成，不手工发放（和 MCP 不同）能用 Atlas 的人都要用模型。手工发放等于上线时给所有人、所有数字员工批量发一遍，漏发一个就有人用不了 Atlas。Key 不带权限，自动生成不会扩大任何人的权限。第一次被取用时生成；主体在用户中心是停用状态时不生成
不过期；停用、重置立即生效；启用时重新生成；不提供删除同 MCP：靠重置、停用止血；停用期间 Key 可能已经泄露，所以启用时不恢复旧值；只停用不删除，审计记录永远能对上持有人

7.3 调用失败

  • SubAgent：内联的 SubAgent 沿用父 Run 的主体，它用的模型同样要有权；委派给另一个独立 Agent 时，按目标 Agent 的权限类型重新确定主体和 Key，在它自己的 Run 开始时检查。
  • 上下文压缩：用 Agent 配置里的压缩模型（没配就用主模型），属于 Agent 的推理，按主体判权，在 Run 开始时一起检查。

8. 运行时：ACP Agent

ACP Agent 的模型客户端是会话 Pod 里的 CLI，Atlas 拦不到单次调用，所以对 ACP 来说，模型网关是唯一的治理点。

8.1 下发

图 8　ACP 下发：检查规则和 Native 相同；Pod 里只有模型网关地址、主体 Key 和模型名，不再有供应商 Key

  • 模型从 Agent 配置来：现在 ACP 用哪个模型由部署配置决定，改为在 Agent 配置里选。编辑器只列出 CLI 能用的协议的模型，例如 Claude Code 要求 Anthropic Messages（原生支持，或者经转换且探测通过）。
  • CLI 自己的轻量模型：有的 CLI 会用另一个轻量模型做标题这类旁路工作。轻量模型也要指向主体有权的模型：默认就是主模型，Agent 配置里可以另选。不指定的话，CLI 会去找一个它默认的、平台上未必有的模型，然后被网关拒绝。
  • 撤掉 Pod 里的供应商 Key：Pod 里原来挂着的供应商 Key 撤掉，换成主体 Key。
  • 会话级快照不是问题：配置只在建会话、恢复会话时下发，但每个调用都经过模型网关，收回授权（缓存时长内）、停用模型（立即）对已打开的会话同样生效。

8.2 主体 Key 进 Pod

Key 会进 Pod，这是有意接受的风险，和 MCP 相同（MCP 方案 7.2）：

  • Key 的能力不超出主体的授权。Key 泄露了，也拿不到主体本来没有的模型。
  • 数字员工的 Key：以 Agent 为权限时，数字员工的 Key 会出现在所有使用者的会话 Pod 里，使用者可以诱导 Agent 把它打印出来，然后在 Atlas 之外按数字员工的授权用模型。这些调用 Atlas 看不到，但模型网关的访问日志和用量里有，主体就是这个数字员工，用量也算在它头上。缓解办法：发现泄露就重置 Key；远期改为下发 Run 级的短期令牌。
  • 和现在相比：现在 Pod 里是供应商 Key，能调供应商账号下的全部模型，用多少都没有记录。换成主体 Key 之后，范围缩小到主体的授权，每次调用都有记录。

8.3 ACP 的调用失败

  • 由 CLI 自己处理：Atlas 拦不到单次调用，也不替它重试。网关能做的是按调用协议的格式把拒绝原因写清楚（7.3），CLI 会把它展示出来。各家 CLI 拿到原因后怎么表现，待验证。
  • Key 被重置或停用：这个会话之后的调用都会被拒，直到会话重建；恢复会话时 Atlas 重新取 Key 下发。
  • 记录只在网关：ACP 的调用和失败 Atlas 看不到，网关的访问日志和用量是唯一完整的记录。

9.3 只有模型网关能调 Higress

做法和 MCP 相同（MCP 方案 8.3），只是凭据各用各的：

  • Higress 只认一个调用方：模型路由只接受带模型网关凭据的请求。这不是按人鉴权：没有按人的消费者、白名单和配额，授权变化不进 Higress。
  • 凭据只在两处：模型网关和 Higress，不下发给 Atlas、Pod、知识库，不进日志和事件。可以不停机轮换：Higress 先同时接受新旧两把，网关切到新的，确认没有旧凭据的请求后再撤掉旧的。
  • 网关凭据不流到供应商：Higress 校验以后，换成供应商 Key 再调供应商。
  • 接入检查：登记模型、刷新探测时，先不带凭据访问一次上游，必须被拒绝；能访问通说明漏开了认证。登记时不通过就不能登记，刷新时发现了要告警。
  • 直连要告警：正常情况下 Higress 上不会有因为凭据不对被拒的请求，一旦出现，说明有进程在尝试绕过模型网关。
  • 供应商那一侧：供应商 Key 只在 Higress，Pod 里不再有，所以 Pod 也不能绕过平台直接调供应商。

9.4 回退和协议转换放在 Higress 时的规则

  • 回退只在同一个模型的上游之间：主备供应商账号、托管同一个模型的不同云厂商，都可以在 Higress 的 AI 路由上配回退和权重；多个供应商 Key 的轮换、故障摘除也在 Higress。
  • 不配换模型的回退：Higress 在网关后面，看不到授权，主体可能根本无权用备选模型，换模型的回退等于绕过了授权。另外，换了模型，能力不同（上下文窗口、工具调用）、价格不同，行为变化用户也看不到。需要备选时，由 Agent 维护者自己换模型。
  • 协议能直通就直通：上游原生支持的协议直接透传；需要转换的，要先通过能力探测（4.4），否则不标为支持。
  • 用量记的是请求里的模型：Higress 在同一个模型的上游之间回退，不影响记账。不同上游价格不同的，按平台模型的价目记，差额在和供应商对账时处理。

数字员工的 Key 会进 Pod使用者可以把它取出来，在 Atlas 之外按数字员工的授权用模型网关有完整记录；重置；远期改为 Run 级短期令牌（8.2）
协议转换会丢内容例如思考内容在转换中丢失，开着思考的多轮工具调用会被拒能直通就直通；转换要先探测通过（4.4）
判权结果有缓存在用户中心收回授权，要等缓存过期才生效缓存时长取短；紧急止血用停用 Key 或停用模型，立即生效
价格靠人工维护价格填错或没及时更新，成本就不准价目带生效时间；没有价格的模型成本显示"未知"，不按 0 计；定期和供应商账单对账

10. 用量与成本

模型网关是唯一看得到全部模型调用的地方，包括 ACP Pod 里的 CLI、平台功能和泄露的 Key。用量和成本以网关的记录为准。

10.1 记什么

图 9　用量记账：网关在转发时读出用量，按请求时的价目折算成本，记到主体、部门、模型、用途上，再汇总成报表和预警

  • 可信的：主体（来自 Key）、应用与用途、模型、用量、结果、耗时（首字延迟、总耗时）。
  • 只作参考的：使用者、Agent、Run、会话，来自调用方的请求头。以 Agent 为权限时主体就是数字员工，按 Agent 归集本身就是可信的。
  • 部门按请求时记：记下主体当时所在的部门，以后部门调整不改历史。
  • 不记内容：提示词和输出不记。

10.2 成本口径

  • 价目带生效时间：成本按请求时生效的价目折算，改价不影响历史。分段价（输入超过某个长度另计）按每次请求的实际长度算。
  • 价格未知不按 0 计：没有填价格的模型，成本显示"未知"；不回报用量的模型，用量和成本标为"估算"。
  • 两个数字：对话里显示的本轮 token 是 Atlas 自己算的，用于即时展示；成本报表以网关为准。两者可能因重试等原因略有差别。
  • 对账：定期把网关的汇总和供应商账单对照，差额大说明价目或计量有问题。

10.3 报表与预警

内容给谁
按模型、人、部门、Agent、用途、时间汇总的用量和成本；趋势模型管理员看全部；模型所有者看自己的模型
自己的用量本人（只读）
额度预警：网关不持有供应商 Key，查不了余额，所以按"管理员登记的额度 − 估算花费"预警；第一次出现余额不足的错误时立即告警模型管理员
异常：某个主体、某个 Agent 的用量突增（可能是死循环，或者 Key 泄露）；拒绝率、供应商错误率升高模型管理员

10.4 以后：预算与限流

  • 先软后硬：先做软预算（到了只告警、不拦），观察一段时间再做硬预算。
  • 硬预算不打断正在进行的一轮：到了预算，新的一轮不开始；正在进行的一轮照常做完。和"不设到点就结束的上限"是同一个原则。
  • 按主体限流：防止某个 Agent 死循环地反复调用。
  • 上游账号的限流：供应商给的每分钟请求数、token 数由 Higress 和供应商执行，网关只用它估算容量。

  • 模型网关：转发延迟（网关自身增加的部分）、错误率、按原因统计的拒绝次数、判权缓存命中率、用户中心查询量、用量记录积压。

  • 弃用模型的剩余引用数和调用量：到下线日期前应当降到零。
  • Higress 因凭据不对拒绝的请求数；接入检查发现能直连的上游数。都应当为零。
