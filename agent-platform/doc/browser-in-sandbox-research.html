沙箱里让 AI 操作浏览器并登录：业界做法与 Atlas 落地建议

调研 · 2026-11-14 · 沙箱用的是 OpenSandbox

业界的做法已经比较一致，分三件事：
① AI 怎么操作浏览器：主流是读页面的「无障碍树」，按元素编号点击和填写，纯文本模型就能用。看截图点坐标（computer use）是补充手段，需要能看图的模型。
② 登录怎么解决：遇到密码、短信码、验证码时，AI 暂停，人在实时画面里自己操作（接管），操作完交还给 AI。登录态保存下来，以后复用；密码不进模型上下文。
③ 人怎么看到画面：沙箱里跑有界面的 Chromium（放在虚拟屏幕上），通过 VNC/noVNC 嵌进前端。
Atlas 的大部分基础已经有了：Shell、技能、挂起机制、OpenSandbox 的端口暴露。缺三样：镜像里的浏览器、前端实时画面、登录态的存放。

1　先认识几个词

词白话解释例子
无障碍树（accessibility tree）浏览器为读屏软件整理的页面结构：每个按钮、输入框、链接各占一行，标出它是什么、叫什么名字。button "登录"、textbox "用户名"
元素编号（ref）拍快照时给每个元素编的短号。模型说「点 e4」，程序就点到对应的元素。页面一变，旧编号就作废。click e4
CDP（Chrome DevTools Protocol）Chrome 对外开放的控制接口。Playwright、开发者工具都通过它控制浏览器：打开网址、点击、执行脚本、读 cookie。端口通常是 9222
computer use模型看截图，回答「在某个坐标点一下 / 输入一段字」，再由程序去执行。需要能看图的模型。「在 (320, 410) 点击」
Xvfb / VNC / noVNCXvfb 是没有显示器的虚拟屏幕，让有界面的 Chromium 能在服务器上跑。VNC 把这块屏幕的画面传出去、把键盘鼠标传进来。noVNC 是网页版 VNC 客户端，能嵌进网页。noVNC 常用 6080 端口
profile（user-data-dir）Chromium 存 cookie、本地存储、历史记录等的目录，里面有 SQLite 等文件。整个目录在，登录就在。--user-data-dir=/tmp/chrome
storageStatePlaywright 导出的登录态快照，一个 JSON 文件，主要是 cookie 和 localStorage。新浏览器导入后就是登录状态。比整个 profile 小，但不是 profile 的全部内容。state.json
接管（Takeover）AI 暂停，人直接在实时画面里操作浏览器，操作完再交还给 AI。Manus 的「Take Over」

2　AI 怎么操作浏览器

方式代表对模型的要求优点缺点
无障碍树 + 元素编号Playwright CLI / Playwright MCP、Vercel agent-browser、browser-use、chrome-devtools-mcp纯文本模型即可省 token、点得准canvas、图形验证码、纯图片界面不行
截图 + 坐标（computer use）Anthropic computer use、OpenAI CUA、Gemini Computer Use必须能看图任何界面都能点，桌面程序也行慢、贵，坐标会点偏
混合browser-use、Manus能看图更好默认读页面结构，卡住了再看截图实现复杂一些

图 1　按无障碍树操作浏览器的循环：模型只读文字清单，说「点 e4」就点到「登录」按钮

CLI 还是 MCP

  • Playwright 官方建议：能执行 Shell 的智能体用 CLI，没有 Shell 的才用 MCP。
  • 原因：两种方式拍出的快照一样大，差别在固定开销和快照放哪。MCP 每次请求都要带约 4.4k token 的工具定义，快照也会进对话历史。CLI 不用时只占几十 token，快照写到文件里，模型按需读取。
  • 实测：有人测同一个任务，MCP 约 114k token，CLI 约 27k token。
  • 代价：用 CLI 时页面变了要重新拍快照，才能拿到新编号；MCP 每次操作后会自动拍。

3　登录怎么解决

业界有 4 种做法，通常组合使用：

做法代表要点
人接管Manus「Take Over」、Browserbase Live View、AgentBay 论文输入密码、短信码、验证码时 AI 暂停，人在实时画面里操作完再交还。Manus 在接管期间不收集、不截获用户的输入。AgentBay 实测：加上人接管后成功率超过 95%，人平均只花 15–30 秒。
保存登录态Browserbase Contexts、Manus 云浏览器、Playwright storageState登录一次，之后的会话自动带上。Browserbase 保存整个 user-data-dir，单独加密存储；Manus 会自动保存登录，跨会话、跨设备同步。
占位符代填browser-use sensitive_data、agent-browser auth save / auth login、1Password 集成模型只看到 x_pass 这样的占位符，填表时程序换成真实值。agent-browser 把凭据用 AES-256-GCM 加密存在本地。注意：browser-use 有过两个域名用同一个占位符名、导致真实值泄漏的 bug（#5592），每个站点要用不同的占位符名。
用用户自己的浏览器Manus Browser Operator、Claude in ChromeAI 在用户电脑上的浏览器里操作，直接用现成的登录态；用的是用户自己的网络出口，也不容易触发风控。
共识：人登录一次，登录态保存下来复用；密码和验证码不经过模型。

图 2　接管登录：AI 只负责把人带到登录页，敏感输入由人完成

4　人怎么看到画面

做法怎么做优点缺点
VNC / noVNCChromium 以有界面模式跑在 Xvfb 上，x11vnc 读屏幕，noVNC 在网页里显示并转发键鼠成熟、通用，桌面上任何程序都能看能操作；OpenSandbox 的 desktop、chrome 例子都是这么做的多跑几个进程；镜像大一些
CDP 推画面浏览器可以没有界面，通过 CDP 持续推送页面截图，用户的键鼠再通过 CDP 发回去不用虚拟屏幕，进程少只能看到网页本身，看不到浏览器弹窗、文件选择框；要自己写前端

前端是 HTTPS 时，浏览器不允许在页面里嵌入 http 的 noVNC，WebSocket 也要走同一个 HTTPS 源。所以要么在 OpenSandbox 前面加 TLS 反向代理，要么由业务服务转发。OpenSandbox 的 desktop 例子文档给了 Nginx 的写法。

5　业界产品速览

产品 / 项目类型和本题相关的做法
Manus终端用户产品云浏览器自动保存登录；遇到复杂验证提示用户「Take Over」，接管期间不收集用户输入；另有 Browser Operator 插件，直接操作用户本机的浏览器
Browserbase云浏览器服务Contexts 保存整个 user-data-dir（加密存储，persist: true 才回写）；Live View 可以嵌进自己的应用，用来做人接管
Playwright CLI / MCP微软开源按无障碍树 + 元素编号操作；CLI 适合有 Shell 的智能体，附带技能说明
agent-browser（Vercel）开源 CLI本地加密凭据库，密码不进模型上下文；支持域名白名单（白名单开启时禁止接管已有的浏览器）
browser-use开源 Python 库sensitive_data 占位符代填，可按域名限定；支持 TOTP 二次验证
chrome-devtools-mcpChrome 官方经 CDP 操作已运行的 Chrome；OpenSandbox 的 chrome 例子推荐用它
OpenSandbox 例子开源chrome：Chromium + VNC(5901) + CDP(9222)；desktop：Xvfb + x11vnc + XFCE + noVNC(6080)；aio-sandbox：接入 agent-infra/sandbox 一体化镜像（浏览器、VNC、CDP、MCP、Shell 都在一个镜像里）
AgentBay（论文）研究人机混合沙箱：密码由人直接输入，智能体拿不到；接管后成功率超过 95%

6　对照 Atlas 现状

需要的能力Atlas 现状
浏览器默认沙箱镜像（docker/sandbox/Dockerfile）里没有 Chromium，也没有中文字体
操作浏览器的工具原生智能体有 Shell 和技能：装一个 CLI、写一个技能就行，不用加新工具。CLI 智能体（Claude Code）也一样
把画面给人看OpenSandbox 有 GET /sandboxes/{id}/endpoints/{port}，Atlas 已在用（sandbox/base/lifecycle/server.py）。前端是 HTTPS，noVNC 的 WebSocket 要经 Atlas 转发
暂停、等人操作已有 waiting_on 挂起和 ask_user_question，接管可以做成其中一种等待类型。平台原则是等人不设超时
登录态放哪/data 是 s3fs，Chromium 的 profile（SQLite）不能放在上面。只能导出 storageState 这类 JSON 文件持久化；{user}/home/ 是现成的个人目录
凭据egress 的 Credential Vault（sandbox/base/network/vault.py）只能往请求头里注入，适合 API token，用不了表单登录
视觉模型DeepSeek 不能看图，MiniMax 能不能看图待确认 → 主路线必须走无障碍树。文件工具读图片会返回图片块，视觉模型可以直接看截图
资源沙箱内存上限 4Gi，够一个 Chromium；日本服务器只有 2 核，会比较紧
沙箱归属一人一个沙箱，这个人的会话共用：天然适合「一人一个浏览器、一份登录态」，但同一个人的多个会话会同时用这个浏览器

7　落地建议

P0：能浏览网页（不涉及登录）

  • 镜像：新建一个带浏览器的沙箱镜像，在默认镜像基础上加 Chromium、@playwright/cli（或 agent-browser）和 fonts-noto-cjk（没有它，中文页面截图全是方块）。
  • 镜像细节：浏览器要在构建时装进镜像，因为 strict 档的根目录只读。容器里要带 --no-sandbox。
  • 技能：写一个 browser 技能，教模型用打开、拍快照、点击、填写、截图这几个命令。
  • 截图：截图存成 png，再用文件工具读，视觉模型就能看，不用加工具。
  • 准入：新镜像的前缀加进镜像白名单，按智能体选择用不用这个镜像。

P1：人接管登录

  • 画面：浏览器改成有界面模式，跑在 Xvfb 上，加 x11vnc + noVNC。可以照搬 OpenSandbox 的 desktop 例子。
  • 转发：Atlas 加一个 WebSocket 转发：先校验会话是不是这个人的，再转到沙箱的 noVNC 端口。前端在对话里嵌入实时画面。
  • 挂起与续跑：模型请求接管 → 本轮挂起，等待类型记为浏览器接管 → 用户登录完点「交还」→ 续跑。不设超时。
  • 登录态：一人一个持久浏览器，profile 放 Pod 本地盘。沙箱存活期间登录态一直有效。沙箱被回收前，把 storageState 导出到这个人的个人目录（或加密存进库里），新沙箱启动时再导入。同一个人的多个会话各开各的标签页。

图 3　P1 的组成：模型经 Shell 操作浏览器，人经 Atlas 转发看画面、输密码

P2：按需再做

  • 占位符代填：常用站点的账号密码存起来，模型只用占位符，省掉每次接管。
  • 用用户自己的浏览器：通过「本机 CLI 智能体」操作用户电脑上的 Chrome（如 Claude Code 的 --chrome）。登录态是现成的，网络出口也是用户自己的，同时解决登录和风控两个问题。这条通道 Atlas 已经有了。
  • computer use：接入能看图的模型后，作为无障碍树搞不定时的补充。

8　风险与限制

最重要的一条：模型能拿到 cookie。浏览器和模型在同一个沙箱、同一个用户身份下，模型有 Shell，能直接读 profile，也能通过 CDP 执行脚本读出 document.cookie。接管只能保证密码不进模型上下文和日志，不能保证模型碰不到登录态。沙箱出网已定为放开，所以模型被提示注入后，cookie 有可能被发出去。
真正隔离的做法是：浏览器单独一个容器、换一个用户身份，只开放受限的接口，不给原始 CDP（agent-box #837 的思路），代价很高。
建议：P1 先接受这个风险（智能体本来就代表这个人），浏览器能力按智能体单独开关。
风险说明
服务器 IP 会被风控GCP 日本和内网服务器的出口 IP，在淘宝、微信这类国内站点上很容易遇到验证码或被拦截。这也是 Manus 另做本地浏览器插件的原因。
资源每人一个 Chromium + Xvfb，大约 0.5–1.5 GB 内存；2 核的机器同时开不了几个。
账号可能被封有些平台会封自动化操作的账号（2026 年 2 月 X 就发过这类警告）。
会话之间共用一个浏览器沙箱一人一个，同一个人的多个会话同时操作同一个网站时可能互相干扰。
登录态不完整storageState 主要是 cookie 和 localStorage，不是整个 profile；少数把登录态放在别处的网站，换了新沙箱后可能还要重新登录。
现成的 AIO 镜像agent-infra/sandbox 自带浏览器、VNC、CDP、MCP，OpenSandbox 有接入例子；但能不能在 strict 档（非 root、根只读）下运行还没验证，镜像也大。倾向于自己做镜像。
