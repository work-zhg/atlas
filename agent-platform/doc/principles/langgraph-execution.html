0. 一页看懂

图 0　构建、编译、执行三个阶段，以及一次调用在时间上的展开

  • 编译：StateGraph 只是构建器。compile() 把它翻译成 Pregel：state 的每个字段变成一个 channel；每个节点变成一个 PregelNode，订阅自己的 branch:to:<节点>；边变成"上游节点跑完后往这个 channel 写一条"。节点之间没有直接的调用关系。
  • 执行：按 BSP 模型分超步执行。每一步先算出要跑的任务，这些任务并行执行、读同一份 state；它们的写入先攒在各自身上，全部跑完后按 reducer 统一合并，再存一个 checkpoint。
  • 调度：引擎里没有"当前执行到哪个节点"的指针。一个节点该不该跑，只看它订阅的 channel 版本号是否比它上次见过的新。所以拿到任意一个 checkpoint，都能算出同样的下一步。
  • 结束：某一步算不出任务就正常结束；超步数超过 recursion_limit 抛 GraphRecursionError（1.2.17 默认 10007，旧资料里的 25 已经过时）。

PregelNode 在执行时被组装成一个 RunnableSeq(bound, *writers)：先跑用户函数，再依次跑各个 writer。所有 writer 都只往任务自己的 writes 列表里追加，不直接改 channel。

3. channel：state 和边的载体

channel 的类型决定两件事：一个超步里收到多个写入怎么办；值能保留多久。超步结束时，apply_writes 把这一步所有任务的写入按 channel 分组，调用各 channel 的 update(values)。值变了，版本号就加一。

图 3　同样是"收到写入"，不同 channel 的处理不同。边用的是只活一个超步的 EphemeralValue

类型一步收到多个写入值保留多久用在哪
LastValue报 InvalidUpdateError一直保留没有声明 reducer 的 state 字段
BinaryOperatorAggregate用 reducer 逐个合并；写入 Overwrite(值) 可以绕过 reducer 直接覆盖一直保留Annotated[T, reducer] 字段，如 messages（add_messages）
EphemeralValueguard=False 时取最后一个一个超步：下一步没人写就清空__start__、branch:to:<节点>
Topic全部收下accumulate=False 时每步清空__pregel_tasks（Send 队列）
NamedBarrierValue记下写入者的名字名字集齐才可用；被消费后重置等待边 join:a+b:c

"可用"（is_available）是调度的前提：一个 channel 版本变了但已经清空（不可用），不会触发订阅它的节点。这正是边能"只生效一次"的原因。

4. 执行循环

invoke 是 stream 的包装；stream 打开一个 SyncPregelLoop（异步是 AsyncPregelLoop），然后反复执行"tick → 并行执行 → after_tick"。源码里的注释把规则说得很直接：Channel updates from step N are only visible in step N+1。

图 4　一次调用的主循环（pregel/main.py 的 stream、pregel/_loop.py、pregel/_runner.py）

  1. 调用开始：取这个 thread 最新的 checkpoint（没有 checkpointer 就是一个空的），用它还原所有 channel。输入是普通值时，把它写进 __start__，存一个 step=-1 的 checkpoint；输入是 None 或 Command 时按"接着跑"处理。stop = step + recursion_limit + 1 在这里算好。
  2. tick：prepare_next_tasks 根据 checkpoint 算出这一步的任务（第 5 节）。算不出就以 done 结束。如果是从中断或出错处恢复，checkpoint 上挂着的 pending writes 会先交回给已经成功的任务，这些任务这一步不再执行。
  3. 执行：只执行还没有写入的任务。只有一个任务时直接在当前线程跑；多个任务时，同步节点提交到线程池，异步节点创建 asyncio task。实测三个各 sleep(0.5) 的同步节点总耗时 0.51 秒，分别跑在 ThreadPoolExecutor-6_0/1/2 上。
  4. 任务完成：每个任务一结束就 commit：写入交给 checkpointer（put_writes），同时产出 updates 流事件。不等同一步的其他任务。
  5. after_tick：所有任务都结束后，apply_writes 合并写入、更新版本号，存一个 checkpoint，step 加一，回到 tick。

5. 调度：下一步跑谁

prepare_next_tasks（pregel/_algo.py）每一步产出两类任务：

  • PUSH 任务：__pregel_tasks 里每个 Send 一个，目标是 Send.node，输入是 Send.arg（不是 state）。
  • PULL 任务：对每个节点检查 _triggers：它订阅的 channel 里，只要有一个可用，并且版本号 大于 versions_seen[节点][channel]，这个节点就要跑。为了不每步遍历所有节点，引擎先用 trigger_to_nodes 找出"上一步被更新的 channel 有哪些订阅者"，只检查这些节点。

任务跑完后，apply_writes 把它当时看到的 trigger 版本记进 versions_seen。下面是 a ⇄ b 循环（route 在 log 满 3 条时返回 END）每个 checkpoint 上的实测版本号：

图 5　版本号只取整数部分。绿色格：版本比节点见过的新、且可用 → 下一步触发；虚线格：版本变了但值已清空 → 不触发

  • step 0 → a：branch:to:a 版本 2，a 没见过（视为 0），可用 → 触发。
  • step 1 → b：a 跑完、route 返回 "b"，写了 branch:to:b。branch:to:a 这一步没人写，被清空（版本 2→3，但不可用），所以 a 不会再被触发。
  • step 2 → a：b 的静态边写了 branch:to:a，版本 4 > a 见过的 2 → a 再跑一次。循环就是这样形成的：不需要"回到 a"的指针，只要 a 订阅的 channel 又被写了。
  • step 3 → 结束：route 返回 END，什么都没写；所有 trigger channel 都不可用，算不出任务。

任务 id 也是算出来的：对 (checkpoint_id, 命名空间, step, 节点名, PULL, triggers) 做哈希。同一个 checkpoint 无论在哪个进程上算，得到的任务和 id 都一样，恢复时就靠这个把 pending writes 对回各自的任务（见 checkpoint 一文第 6 节）。

6. 并行与合并

图 6　同一超步的任务读同一份快照，写入在超步结束时按确定的顺序合并

  • 互相不可见：同一步的任务读的都是本超步开始时的 state。想用另一个节点的结果，只能放到下一步。
  • 合并顺序是确定的：apply_writes 先按任务路径排序再逐个 reduce。PULL 任务的路径里是节点名，PUSH 任务是 Send 的序号，所以顺序与谁先跑完无关。实测并行的 z（快）和 a（慢）：updates 流先出 z 后出 a，但合并后的 log 是 ['a(慢)', 'z(快)']；12 个 Send 任务按 11→0 的顺序完成，合并结果仍是 0→11。
  • 同一个目标只跑一次：一步里多个任务都写 branch:to:X，EphemeralValue(guard=False) 只保留一个值，X 下一步只跑一次。create_agent 里两个并行的工具调用都路由回 model，model 只跑一次（第 10 节）。

8.1 一个任务失败

图 9　出错和中断用的是同一套机制：成功任务的写入挂在 checkpoint 上，续跑时只重跑没成功的任务（需要 checkpointer）

8.2 相关配置

机制作用默认
RetryPolicy（add_node(retry_policy=…)）任务失败后在同一超步内重试，指数退避（0.5 秒起，×2，最多 128 秒，带抖动），连同第一次最多执行 3 次。默认的 retry_on 重试 ConnectionError、HTTP 5xx，以及不属于 ValueError、TypeError、RuntimeError、OSError 等常见错误的异常不配置就不重试
error_handler（add_node 参数，或 set_node_defaults）重试用尽后，在同一超步里调用处理函数，它的返回值代替失败节点的写入。失败节点原来的出边不会触发，要继续往下走需要返回 Command(goto=…)（实测）无
timeout（add_node 参数）每次尝试的超时，超时抛 NodeTimeoutError，由重试策略决定是否重试。只对异步节点生效无
step_timeout（Pregel 属性）整个超步的超时无
recursion_limit（config）一次调用最多执行多少个超步，超出抛 GraphRecursionError。数的是超步，不是节点执行次数10007，可用环境变量 LANGGRAPH_DEFAULT_RECURSION_LIMIT 修改
interrupt() / 断点抛 GraphInterrupt，不算失败、不重试，以中断状态返回见 checkpoint 一文第 5 节

9. 子图

编译好的图可以直接作为另一个图的节点。父图的这个任务执行时，子图在同一个进程里跑自己的一整套超步循环，命名空间是 节点名:任务id，有自己的 checkpoint（checkpoint_ns 不为空）。子图结束后，它的输出作为这个节点的返回值，交给父图的 writer。

图 10　子图作为节点：输出的是完整 state，不是增量

  • 重复累加：子图拿到的输入里已经有父图的旧值，返回时又整个交回去，父图的 reducer 会再合并一次。解决办法：子图用和父图不同的字段；或者用一个普通函数节点包住子图调用，只返回增量。
  • 流式输出：stream(..., subgraphs=True) 时，事件带命名空间元组，主图是 ()，子图是 ('sub:<任务id>',)。
  • 中断：子图里的中断会冒泡到最外层；恢复时父图里调用子图的那个节点会从头重跑（见 checkpoint 一文 6.3）。
  • checkpointer：compile(checkpointer=None) 的子图继承父图的 checkpointer；False 不用；True 让子图在多次调用间保留自己的状态。

10. 实例：create_agent 的一轮工具调用

langchain v1 的 create_agent 生成的就是一张 StateGraph。不带中间件时只有 model 和 tools 两个节点，靠两个条件边来回走；中间件的每个钩子（before_model、after_model 等）会各自再加一个节点。下面用假模型实测：模型第一次返回两个工具调用，第二次直接回答。

图 11　create_agent 的图结构（上）和一轮工具调用实测的超步（下）

  • channel：实测有 messages（BinaryOperatorAggregate，reducer 是 add_messages）、jump_to（EphemeralValue，中间件用来跳转）、structured_response（LastValue），加上 __start__、branch:to:model、branch:to:tools、__pregel_tasks。
  • 工具并行靠 Send：model_to_tools 对每个还没有结果的工具调用返回一个 Send("tools", [tool_call])，所以 tools 节点在同一步里有多个 PUSH 任务并行，各自只处理一个调用。Send 里只放调用本身，工具需要的 state 在执行时再读。
  • 汇合靠 EphemeralValue：两个 tools 任务都经 tools_to_model 写 branch:to:model，下一步 model 只跑一次。
  • ToolMessage 的顺序：两条 ToolMessage 按 Send 的序号合并，与哪个工具先返回无关，所以和 AI 消息里 tool_calls 的顺序一致。
  • 结束条件：model_to_tools 发现最后一条 AI 消息没有工具调用，返回 END，什么都不写，下一步算不出任务。

11. 使用要点

要点原因做法
会被并行写的字段必须有 reducerLastValue 一步只收一个值，否则 InvalidUpdateError声明 Annotated[T, reducer]；要整体替换时写 Overwrite(值)
同一步的节点看不到彼此的写入BSP：写入在超步结束时才合并需要别的节点结果的逻辑放到下一步，或放到汇合节点里
条件边只看到本节点的写入route 读的是"本步开始的值 ＋ 本任务写入"依赖多个并行结果的路由放在汇合之后
不要依赖完成先后合并按任务路径排序；updates 流按完成先后需要顺序的数据自己带序号，不要从流事件的顺序推断
节点返回未声明的 key 会被静默丢弃只取 state schema 里有的 key拼写错误不会报错，测试里检查最终 state
扇入路径不等长时目标会跑多次两条单独的边各自触发用等待边 add_edge([a, b], c)，或 defer=True
同步节点跑在线程池里并行任务各占一个线程；失败时停不下来节点里用到的共享对象要线程安全；能用异步节点就用异步节点
子图共用累加字段会重复子图返回完整 state，父图再合并一次子图用独立字段，或用函数节点包住子图、只返回增量
有待决中断时不要直接发新输入新输入会把上一次没完成的任务丢弃，从入口重新走（实测旧中断被丢弃，生成了新中断）先用 Command(resume=…) 回答，或明确放弃后再发新输入
显式设置 recursion_limit1.2.17 默认 10007，死循环要跑很久才停有循环的图按业务估一个上限传进 config
需要失败后续跑就配 checkpointer成功任务的写入只有存在 checkpointer 里才能在续跑时回放生产用持久化的 saver；续跑用 invoke(None, config)
