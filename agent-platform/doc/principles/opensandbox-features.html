0. 一页看懂

OpenSandbox 是一个自托管的 AI Agent 沙箱平台（Apache-2.0，属于 Linux Foundation 下的 Agentic AI Foundation）。对外是一套统一的生命周期 API，背后可以接 Docker、Kubernetes 或 Fast Sandbox（Firecracker microVM）；沙箱里由 execd 提供命令、文件、代码执行，由 egress 管控出站流量。

图 0　三条路径。容器后端的 egress 是每个沙箱一个 sidecar；Fast Sandbox 是每个 Fastlet Pod 一个共享进程

类别主要功能
生命周期从镜像 / 快照 / 模板创建；TTL 与续期、访问即续期；暂停与恢复；快照；生命周期钩子；Pod 故障自愈；诊断
沙箱内执行命令（前台流式 / 后台轮询）、bash 会话、PTY 终端、Jupyter 代码执行、完整文件 API、bubblewrap 隔离会话、资源指标、端口反代
网络端点解析与统一入口网关、Secure Access（令牌与签名 URL）；出站按域名 / IP / 端口的策略，透明 TLS 拦截，Credential Vault 注入凭据
规模BatchSandbox 批量创建与任务编排、Pool 预热池、SDK 端的客户端池、Fast Sandbox 毫秒级创建
隔离runc / gVisor / Kata / Firecracker；execd 进程加固（Landlock、syscall 黑名单）；按租户分命名空间
运维OpenTelemetry 指标、Node Agent 收集 stdout/stderr、Web 控制台、Helm chart、镜像签名
客户端Python / JS / Kotlin / Go / C# SDK、osb CLI、MCP server；Claude Code、Codex 等 20 多个集成例子

2. 运行时后端

server 的 [runtime].type 只有 docker 和 kubernetes 两个值。kubernetes 模式下由 CompositeSandboxService 分派：带 templateId 的创建请求交给 Fast Sandbox，带 image / snapshotId 的交给 K8s 容器提供者（kubernetes.workload_provider 选 batchsandbox 或 agent-sandbox）；已有沙箱按 ID 前缀分派，fsb- 开头的走 Fast Sandbox。

后端形态适合要点
Docker直接调 Docker daemon 建容器，把 execd 二进制拷进容器再启动 entrypoint本地开发、单机网络模式 host / bridge / none / pasta / slirp4netns / 自定义网络；为 execd 和服务端口分配宿主端口；egress 是独立容器，沙箱加入它的网络命名空间；server 重启后恢复过期计时
K8s · BatchSandbox（默认）OpenSandbox 自己的 CRD 和控制器；init 容器把 execd 拷进 emptyDir生产、批量、评测与 RL模板文件与每次请求合并；Pool 预热；任务编排；rootfs 暂停 / 恢复；Pod 卡在拉镜像等故障时自动换节点重建
K8s · agent-sandbox用 kubernetes-sigs/agent-sandbox 的 CRD已经在用 SIG agent-sandbox 的集群官方实测交付 100 个沙箱要 23～76 s（并发 1～50），BatchSandbox 加池是 0.92 s
Fast Sandbox外部 fast-sandbox 平台：预热的 Fastlet Pod 里跑多个 Firecracker microVM，创建绕开 K8s 调度和 kubelet高密度、要求毫秒级创建只能从模板创建；创建 64 ms P50（串行）/ 125.4 ms P99（10 并发）；暂停 / 恢复保留内存和磁盘；不支持 volumes

2.1 安全容器运行时

隔离强度在创建时由运行时决定。Docker 模式通过 daemon 注册 runtime，K8s 模式通过 RuntimeClass；可以部署多个 server profile，各自对应一种运行时。

运行时隔离机制启动开销内存开销适合
runc（默认）进程级（namespace + cgroup）约 0 ms很小可信负载、本地开发
gVisor用户态内核，拦截 syscall约 10～50 ms约 50 MB一般负载、开销低
Kata（QEMU）完整 VM约 500 ms约 20～50 MB兼容性和隔离都要最好
Kata（Firecracker）microVM约 125 ms约 5 MB高密度
Kata（Cloud Hypervisor）VM约 200 ms约 10～20 MB性能与隔离折中
gVisor 有两处限制：egress 的出站控制和 Credential Vault 在 gVisor 下不能用（官方建议改用 Kata）；K8s 的 rootfs 快照不支持 gVisor（runsc）。

2.2 其他形态

  • Windows 沙箱：platform.os=windows，基于 dockur/windows 在 Linux 容器里用 KVM / QEMU 跑 Windows guest；宿主需要 /dev/kvm 和 /dev/net/tun。
  • QEMU VM 状态快照：在 runc 里跑 QEMU 的沙箱可以选择检查点模式，暂停时保留 guest 内存。
  • GPU：resourceLimits 里的 GPU 在 K8s 上翻译成扩展资源。

3. 沙箱生命周期

3.1 创建

POST /v1/sandboxes，三种来源三选一：image（容器镜像，可带私有仓库认证）、snapshotId（从快照恢复）、templateId（Fast Sandbox 模板）。请求的其他字段：

字段作用
entrypoint / env启动命令与环境变量
timeoutTTL（秒），到期自动删除；为 null 时不过期。SDK 高层接口默认 10 分钟，模板沙箱必须显式给
resourceLimits / resourceRequestsCPU、内存、GPU 等
platformOS / 架构约束
metadata自定义键值，K8s 上会成为资源 label，列表接口可以按它过滤
volumes挂载存储（第 7 节）
networkPolicy / credentialProxy出站策略、启用凭据注入（第 6 节）
secureAccess入站端点要求凭据（第 5 节）
lifecyclepreStart / periodic 钩子、renewalPolicy（访问即续期）、idlePolicy（自动暂停，1.2.0）
extensions后端相关的扩展，例如 poolRef（从预热池分配）

创建在 API 层面是异步的：客户端要轮询 GET /v1/sandboxes/{id} 或用 SDK 的就绪等待。

3.2 状态

状态含义从哪来
Pending正在供给创建
Running就绪，可接受请求Pending、Resuming
Pausing → Paused暂停中 → 已暂停（状态保留）Running 上请求暂停
Resuming从暂停恢复中Paused 上请求恢复
Stopping → Terminated终止中 → 已终止Running / Paused 上删除，或 TTL 到期
Failed严重错误Pending / Running / Paused / Resuming 出错

状态还带 reason（如 ttl_expiry、provision_timeout）、message 和 lastTransitionAt。规范要求客户端容忍将来新增的状态值。

3.3 过期与续期

  • 手动续期：POST /sandboxes/{id}/renew-expiration。
  • 访问即续期（OSEP-0009）：创建时声明 lifecycle.renewalPolicy.extendSeconds（300～86400）。server 代理收到请求，或 ingress 经 Redis 投递续期意图时，把过期时间推到 max(now + extendSeconds, 当前过期时间)，每个沙箱有冷却间隔。Docker 和 K8s 支持（包括池模式），Fast Sandbox 回 400。1.1.x 用的是 extensions["access.renew.extend.seconds"]，1.2.0 改成结构化字段，旧键在 1.x 内仍可用。

3.4 暂停与恢复

POST /sandboxes/{id}/pause / resume，sandbox ID 前后不变。各后端的做法差别很大：

后端做法保留什么限制
Docker容器级 pause（冻结）；有 egress 时先冻沙箱再冻 sidecar，恢复反过来进程原地冻结不释放资源
BatchSandbox（rootfs-v1，默认）建内部 SandboxSnapshot，在源节点跑 commit Job，把根文件系统提交成 OCI 镜像推到仓库，然后释放 Pod / 池位；恢复时改模板镜像并重建根文件系统、环境变量；进程和内存不保留；Credential Vault 不保留（要重新写入）；volume 看类型仅 replicas=1；不支持 gVisor；镜像仓库和推送凭据配在控制器上；快照 Succeed 之后才算持久
BatchSandbox（qemu-v1，可选）QEMU-in-runc 的 VM 状态检查点QEMU 进程和 guest 内存要求镜像按 QEMU 快照约定构建
Fast SandboxFastPath 做 microVM 检查点，可以在别的 Fastlet 上恢复内存和磁盘恢复后要重新解析端点

3.5 自动暂停与按访问唤醒（1.2.0，仅 Fast Sandbox）

创建时声明 lifecycle.idlePolicy（idleTimeoutSeconds 30～86400、onIdle: pause、wakeOnAccess、可选 activeProbe）。ingress 把每个经过的请求记成活动写进 Redis，server 每 15 s 扫一次，闲置超时的就暂停。之后有请求到达时，ingress 先把请求挂住、触发恢复，恢复好了再转发；超出等待预算就回 503 + Retry-After + OpenSandbox-Wake: expired，五种 SDK 都会据此自动重试。

  • server、ingress、沙箱三方都要开启，默认全关。
  • 只有经 ingress 的新 HTTP 请求算活动，已建立的 WebSocket / SSE 里的帧不算；走 server 代理的流量既不记活动也不会唤醒。
  • 过期时间是绝对的，暂停不会延长它。暂停的沙箱不会自己醒，定时任务要由外部先调 resume。

3.6 快照与模板

  • 公开快照 API（/snapshots、/sandboxes/{id}/snapshots）：Docker 把容器提交成本地镜像；BatchSandbox 建 SandboxSnapshot 并推到 OCI 仓库；之后可以用 snapshotId 新建沙箱。和暂停的区别：快照是复制出一个新起点，原沙箱继续运行；暂停是同一个沙箱停下再接着跑。
  • 模板（/templates）：只用于 Fast Sandbox。把 OCI 镜像构建成 golden image（预置 init 和 execd），运行形态在构建时就固定。1.2.0 起模板和快照可以发布到 OCI 仓库、从仓库启动（OverlayBD）。Docker 模式回 501。

3.7 生命周期钩子

钩子个数何时运行失败时
preStart0～1execd 开始监听之后、用户 entrypoint 之前，阻塞entrypoint 不启动
periodic0～多preStart 成功后按计划运行（如 @every 5m），不阻塞记日志，下次照常；超时进程杀不掉时停用该钩子

目前只有 K8s 提供者支持，Docker 和 Fast Sandbox 拒绝；不能和 poolRef 同时使用。钩子在沙箱里以可信代码运行，只是便利功能，不是安全边界。

3.8 自愈与诊断

  • Pod 供给失败恢复：从未 Ready 过的 BatchSandbox，如果 Pod 卡在 ImagePullBackOff 或被 kubelet 准入拒绝（OutOfcpu、Evicted 等）超过阈值（默认 1 分钟），控制器就删掉 Pod 让它重新调度，最多 3 次。镜像本身不存在、无权限这类在哪个节点都会失败的情况不浪费重试。配置在 feature-flags ConfigMap，热加载。
  • 诊断：GET /v1/sandboxes/{id}/diagnostics/context（1.2.0）返回后端类型、后端标识和状态，不需要连 execd，Pod 还没分配时也能查；另有日志 / 事件描述符，以及给运维和 AI 排障用的纯文本诊断路由（osb devops）。
  • 删除语义（1.2.0）：删除后先报 Stopping，运行时真正清理完才返回 404。多个沙箱共享同一个持久目录时，要等旧沙箱 404 之后再建替代的。

4. 沙箱内执行：execd

execd 默认监听 44772 端口。平台配置了访问令牌时，除健康检查外每个接口都要带 X-EXECD-ACCESS-TOKEN（令牌在解析端点时下发）。注入方式：Docker 把二进制拷进容器；K8s 用 init 容器；Fast Sandbox 预置在模板镜像里。

能力接口说明
命令/commandshell 语法或 argv 两种写法。前台：SSE 流式返回输出，跟随连接；后台：立即返回命令 id，之后轮询状态、按游标取增量日志，完成后输出保留 24 小时。中断时 SIGTERM 整个进程组，宽限后 SIGKILL
bash 会话/session跨调用保留 cwd 和环境变量的持久 shell；镜像没有 bash 时退回 POSIX sh
终端/pty（WebSocket）真正的 PTY，编辑器、REPL、Agent CLI 都能正常交互。一个 holder 输入，任意多个 viewer 旁观（先回放已有输出再跟随）。1.2.0 起浏览器可以用 WebSocket 子协议携带令牌
代码执行/code、/code/contexts以 Jupyter kernel 作为上下文，多次调用共享状态，像 notebook。官方 code-interpreter 镜像带 Python、Java、Node.js、Go 及对应 kernel
文件/files/*、/directories上传、下载（支持 Range）、列表、按 glob 搜索、移动、chmod、删除、原地替换内容。1.1.1 起可以加 /v1/filesystem/{uid}/{gid} 前缀，以指定的 Linux 身份执行文件操作
隔离会话/v1/isolated/*见 4.1
指标/metrics、/metrics/watchCPU、内存的快照或实时流，可导出 OTel。1.2.0 起设了资源上限时取沙箱自己 cgroup 的数字（之前读的是宿主的 /proc，是整机数字），并上报 OOM kill 次数
反向代理/proxy/{port}只暴露 execd 一个端口，就能访问沙箱里所有端口（Docker 单机网络用）
健康检查/ping、/ready不需要令牌

4.1 隔离会话

在一个沙箱里用 bubblewrap 起多个互相隔离的长驻 bash，每个会话有独立的 PID、mount、tmpfs、环境变量命名空间。创建约 100 ms，之后每次 run 复用同一个 bash 进程，开销几乎为零。适合 RL rollout、批量判题、多工具 Agent 运行：一个 worker 一个沙箱，里面跑很多互相隔离的任务。

工作区模式语义
overlay（默认）overlayfs 写时复制，写入落在会话自己的 upper 目录，删除会话即丢弃
rw读写绑定挂载，写入直接落到原目录
ro只读挂载，写入报 EROFS

另外支持显式 bind 挂载和可写白名单（按解析后的真实路径校验，符号链接逃不出去），创建会话时会报告当前环境支持哪些能力。限制：只是 namespace + seccomp，挡不住内核漏洞（要配合 gVisor / Kata）；仅 Linux；同一会话里的 run 串行执行；diff / commit 尚未实现（返回 503）。

4.2 进程管理与加固

  • execd 作 PID 1（execd_run_as_init）：回收僵尸进程、转发信号、把 entrypoint 的退出码传给运行时，Terminated / Failed 反映进程的真实结果。
  • 每次分配一份新身份：池里预热的沙箱在分配时才收到 sandbox ID、环境变量、令牌、钩子，原子生效。拿到之前除 /ping、/ready 外一律 503，上一个使用者的环境不会泄漏给下一个。
  • 加固底线（运维开启）：用户进程都经一个 native launcher 启动，drop 能力、设 no_new_privs、装 syscall 黑名单、用 Landlock 限制可写路径。
  • eBPF 审计（可选的 execd-ebpf 构建，需要 CAP_BPF）：记录 exec、网络 connect、提权，范围限于沙箱自己的 cgroup。
  • 每一层都报告自己是 active、degraded 还是 unsupported，客户端可以核实实际生效了什么。

5. 入站访问

5.1 端点解析

GET /v1/sandboxes/{id}/endpoints/{port} 返回沙箱里某个端口的可达地址，以及访问时必须带的请求头。地址有三种：

形态场景
Docker 映射的宿主端口单机
Pod 地址或 ingress 网关地址K8s
server 代理 /sandboxes/{id}/proxy/{port}开 use_server_proxy 时；支持 HTTP 和 WebSocket，也能触发访问即续期

端点只承载 HTTP、SSE、WebSocket，不是通用的 TCP / UDP 隧道。端点背后可以是 execd，也可以是镜像自己的服务（例如 AIO 镜像在 8080 端口上的 shell / 浏览器 API）。

5.2 ingress 网关

  • 路由：header 模式用 OpenSandbox-Ingress-To: <id>-<port> 或主机名 <id>-<port>.example.com；URI 模式用 /<id>/<port>/<path>。路由数据来自 BatchSandbox 的 endpoints 注解、agent-sandbox 的 serviceFQDN，或向 FastPath 查询。
  • 错误码：404 沙箱不存在、503 存在但未就绪、502 基础设施故障；沙箱自己的响应原样透传，网关不跟随重定向。
  • WebSocket：单条消息最大 64 MiB，子协议和关闭码原样传递。
  • TLS：网关只说明文 HTTP/1.1，不终止 TLS。前面的 L7 代理要把 WebSocket 升级降成 HTTP/1.1，不能用 HTTP/2 上的 WebSocket。

5.3 Secure Access

仅 K8s 且 ingress 为 gateway 模式时可用（Docker 回 400）。secureAccess: true 的沙箱，解析端点时返回一个静态令牌，调用方放在 OpenSandbox-Secure-Access 头里；带 ?expires= 时还能签出一个有时效的路由令牌，可以直接放进 URL。网关先看请求头（不匹配直接 401，不再尝试签名），没有请求头才校验签名；通过后剥掉凭据再转发，沙箱里的程序看不到它。

6. 出站控制与 Credential Vault

6.1 egress 策略

egress 和沙箱共享网络命名空间，所有出站包都经过它，应用不用做任何配置，沙箱里也绕不过去。策略在创建时用 networkPolicy 声明，运行期可以修改。

能力说明
规则按域名、通配域名（*.pypi.org）、IP、CIDR 允许或拒绝，加 defaultAction。1.2.0 起可以按 TCP 目的端口限定（只限端口时 target 可省略，域名规则不能带端口）
dns 模式（默认）53 端口流量都被重定向到 egress 的 DNS 代理，被拒绝的域名返回 NXDOMAIN；程序直连 IP 可以绕过
dns+nft 模式nftables 默认拒绝，只放行静态规则和 DNS 解析出来的地址；解析出的地址有租期，不会变成永久放行
平台底线镜像里的 deny.always / allow.always 文件每分钟热加载，优先级 deny.always > allow.always > 用户策略；reachable.ports.cap 是 TCP 端口白名单，用户策略写 defaultAction: allow 也打不开白名单以外的端口
运行期修改容器后端直接调 egress 的 GET / PATCH / DELETE /policy（端口 18080）；Fast Sandbox 走 lifecycle API 的 /sandboxes/{id}/networkpolicy
透明 TLS 拦截拦截 80 / 443（可以再加端口），能看到、控制、认证出站 HTTPS；可以串接上游代理（[egress.upstream_proxy]），可以额外信任一组 CA
失败即关闭装不上规则时 egress 直接退出，不会以「没有规则」的状态放行流量
部署形态
Docker独立容器，沙箱加入它的网络命名空间
K8s追加到沙箱 Pod 里，是 Pod 里唯一有 NET_ADMIN 的容器（主容器会被 drop 掉）
池化沙箱预热的 Pod 没法逐请求加 sidecar，出站控制要写进 Pool 模板；请求里同时带 networkPolicy 和池引用会被拒绝
Fast Sandbox每个 Fastlet Pod 一个共享 egress 进程，每个沙箱是其中的一个 subject
egress 假定自己是网络命名空间里唯一的透明拦截层：同一个 Pod 里注入了 Istio / Envoy 这类 mesh sidecar 时，策略、TLS 拦截和 Credential Vault 都不可靠。

6.2 沙箱之间的网络隔离

K8s 上沙箱默认能互相直连 Pod IP。OpenSandbox 不依赖 K8s NetworkPolicy（沙箱 label 由平台注入、无法区分，沙箱又频繁创建销毁），推荐在 egress 的 deny.always 里写入集群 Pod CIDR 和 Service CIDR，再按需放行合法的集群内服务；逐沙箱的 NetworkPolicy 是备选方案。

6.3 Credential Vault

真实凭据存在 egress 里，沙箱里的进程只拿到假值或空值。Claude Code、git、curl、包管理器、模型 SDK 发出的 HTTPS 请求匹配到某条绑定时，egress 在出站途中注入认证信息。

auth 类型注入方式
bearerAuthorization: Bearer <凭据>
basicAuthorization: Basic <凭据>，凭据要预先 base64 编码 user:password
apiKey写进指定的请求头，如 x-api-key
customHeaders多个请求头，各自对应一个凭据
passthrough不注入请求头，配合 substitutions 把凭据替换进路径、query 或 body 里的占位符
  • 前提：server 配 [egress].mode = "dns+nft"（DNS 模式下会被直连 IP 绕过，所以拒绝启用）；创建请求同时带 networkPolicy 和 credentialProxy.enabled；策略建议 defaultAction: deny 并放行绑定涉及的 host（默认放行目前仍兼容，但会告警）；沙箱里的工具要信任 MITM CA。
  • 管理接口：容器后端调 egress 的 /credential-vault；1.2.0 起 lifecycle API 也有 /sandboxes/{id}/credential-vault（Fast Sandbox 走这条），所有公开读接口都不返回凭据值。
  • 持久性：容器后端只存在 egress 内存里，rootfs 暂停 / 恢复之后要由可信控制面重新写入；Fast Sandbox（1.2.0）随检查点密封转移。

volume 类型含义支持
host宿主路径（受 storage.allowed_host_paths 限制）Docker（bind mount）、K8s（hostPath）
pvc平台管理的命名存储，可以挂子路径、只读Docker（named volume）、K8s（PersistentVolumeClaim）

  • Fast Sandbox 目前不支持 volume。官方例子还有 rclone 挂载、K8s PVC 挂载等；整体（OSEP-0003）仍处于 implementing。
  • rootfs 快照不包含 volume 里的数据。要扛住意外终止（OOM、驱逐、节点故障）的数据应放在持久卷或外部服务里，rootfs 快照只用来复现环境。

8. 规模：池化与批量

8.1 Pool CRD（服务端预热池）

字段作用
template预热 Pod 的模板
capacitySpecbufferMin / bufferMax 控制空闲就绪的数量，poolMin / poolMax 限制总量
scaleStrategy / updateStrategy每轮最多增删多少 Pod（默认 25%），模板变更时滚动替换空闲 Pod
recycleStrategy沙箱用完归还时：Delete（默认，换新 Pod）、Restart（原地重启容器）、Noop（原样复用，状态会泄漏给下一个）

从池分配是常数时间的认领。没有空位时 BatchSandbox 带 PoolAllocationPending 条件，server 在有限时间内等不到就回可重试的 429。poolRef 为空时可以按插件（容量、镜像、资源、节点选择器）自动选池。池里的 Pod 是事先建好的：entrypoint / env 作为分配后的任务下发，volumes 和 networkPolicy 必须写在池模板里。

8.2 BatchSandbox 批量与任务编排

  • replicas 一次建一批；shardPatches 让每个副本的镜像、env、资源可以不同。
  • taskTemplate / shardTaskPatches：分配后每个副本跑一个任务，可以在 task-executor 容器里（Local）或经 nsenter 在主容器里（Remote）执行，带 preStart / postStop。
  • taskResourcePolicyWhenCompleted：任务结束后保留资源（Retain）或立即释放（Release）。
  • 状态分开报告运行时健康（ready / phase）和任务进度（running / succeed / failed 计数）。面向评测和 RL 训练这类高吞吐场景，带池交付 100 个沙箱实测 0.92 s。

8.3 客户端池（SDK，实验性）

SDK 在服务端保持一小批已就绪的沙箱，acquire() 直接拿一个，省掉创建延迟。池里存的是沙箱 ID，不是连接；用 Redis 做状态存储时可以跨进程、跨 Pod 共享，补货只由持有主锁的节点做。没有 release()：拿到的沙箱用完要自己删。空池时的策略：FAIL_FAST、DIRECT_CREATE（默认，直接新建）、RETRY_NEXT_IDLE、RETRY_NEXT_IDLE_THEN_CREATE。C# SDK 没有客户端池。

8.4 Fast Sandbox 的密度

Fastlet Pod 预先准备好网络槽位，egress 和 DNS 由同一 Pod 里的沙箱共享，创建时不经过 K8s 调度、watch 和 kubelet。镜像块通过 DART 在节点间 P2P 分发。1.2.0 新增按资源放置（ResourceAware，可设 CPU / 内存超卖比）。

9. 多租户与安全分层

9.1 多租户（OSEP-0014）

一个 server 服务多个租户：每个租户一个或多个 API Key，请求按 Key 自动落到该租户的 K8s 命名空间，建、列、查、删都只作用于这个命名空间。租户来源可以是文件（热加载）或 HTTP 服务。命名空间要由集群管理员预先建好，建议配 ResourceQuota 和 LimitRange。只支持 K8s，Docker 模式开租户会直接拒绝启动；多租户模式下代理路由也要带 API Key。

9.2 安全分层

层机制
工作负载边界runc / gVisor / Kata / Firecracker；资源上限；能力 drop；seccomp、AppArmor

1.1.1 → 1.2.0 与 Atlas 相关的变化
  • execd 指标：1.1.1 的 /metrics 读的是容器里看到的宿主 /proc，CPU 是整个节点的数字，不是这个沙箱的。Atlas 的卡死判定依据它，在 1.1.1 上判断依据不准。1.2.0 在设了资源上限时改为沙箱 cgroup 的数字（Atlas 设了 resourceLimits）。
  • 删除：1.2.0 删除后先报 Stopping，清理完才 404。Atlas 的 get() 把 404 当作「已不存在」，语义对得上。1.1.1 上返回 404 时旧 Pod 可能还在跑；1.2.0 下等到 404 再建新沙箱，就不会和旧 Pod 同时写同一个工作区前缀。
  • BatchSandbox Pod 默认 restartPolicy: Never、过期报 Terminated：Atlas 模板已显式写 Never、也不设 TTL，没有影响。
  • networkPolicy 的未知字段回 422：ACP 请求里只用了 defaultAction，预计没有影响。
