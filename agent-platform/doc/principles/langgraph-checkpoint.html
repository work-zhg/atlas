0. 一页看懂

图 0　checkpointer 挂在图上，按 thread 存下每一步的快照；箭头指向父 checkpoint

  • 存什么：每个超步结束时整张图的快照（各 channel 的值和版本号），加上依附在它上面、还没合并的任务写入（pending writes）。
  • 怎么中断：节点里调用 interrupt(value)，第一次调用抛出 GraphInterrupt。引擎把它记成这个任务的一条 __interrupt__ 写入，这一步没走完，所以不生成新的 checkpoint。之后进程可以直接退出。
  • 怎么恢复：用同一个 thread_id 调用 Command(resume=值)。恢复值记成一条 __resume__ 写入；被中断的任务从头重跑，这一次 interrupt() 不抛出，直接返回恢复值。同一步里已经成功的任务只回放写入，不重跑。
  • 代价：节点重跑带来的副作用要自己保证幂等；快照里存的是全量 state，存储量随轮数增长；快照和图结构绑定，改图后要考虑旧快照能不能恢复。

2. 执行模型：超步

LangGraph 的执行引擎叫 Pregel，按 BSP（bulk synchronous parallel）模型运行：一个超步里，所有该跑的节点并行执行，读的是同一份 state，彼此看不到对方的写入；全部执行完以后，写入按各 channel 的 reducer 统一合并，然后存一份 checkpoint，进入下一个超步。

图 1　一个超步的五个阶段。checkpoint 只在超步边界产生，中途的写入以 pending writes 的形式挂在当前 checkpoint 上

这套模型能从任意 checkpoint 恢复，关键在于"下一步跑什么"不存在内存里，而是可以从 checkpoint 推算出来：

  • 每个节点订阅若干 channel。某个 channel 的版本号比节点上次见过的新，这个节点就该跑。边本身也是 channel：普通边写 branch:to:<节点>，Send 写 __pregel_tasks。
  • checkpoint 里同时存了 channel_versions（每个 channel 当前的版本）和 versions_seen（每个节点见过的版本），所以任何一个进程拿到它，都能算出同样的下一步。

4. 什么时候存、存在哪

4.1 checkpoint 的来源

metadata.source什么时候产生step
input调用开始，输入还没合并进 state 时（输入作为 pending writes 挂在它上面）-1

update调用方用 update_state 手动改 state接着上一个

4.3 checkpointer 接口

方法作用什么时候被调用
get_tuple(config)取一个 checkpoint 及其 pending writes；config 里不带 checkpoint_id 就取最新的每次调用开始；get_state
list(config)按时间倒序列出 thread 的 checkpointget_state_history
put(config, checkpoint, metadata, new_versions)存一个 checkpoint；new_versions 是这一步版本变了的 channel每个超步结束（受 durability 影响）
put_writes(config, writes, task_id)存某个任务的写入，挂在当前 checkpoint 上每个任务结束，包括中断和出错
delete_thread / prune / copy_thread删除 thread、裁剪历史、复制 thread由调用方按需使用；具体 saver 是否实现以各自为准

每个方法都有对应的异步版本（aget_tuple、aput …）。值用 JsonPlusSerializer 序列化，消息等 LangChain 对象可以原样存取。

4.4 PostgresSaver 的表

图 4　PostgresSaver 的三张主表。None、字符串、数字、布尔这类基础类型的值直接存在 checkpoints.checkpoint 里，其余按 (channel, version) 存进 blobs

存储量的增长：一个 channel 每变一次就多一个版本的 blob。messages 每步都变，所以每步都要把完整的消息列表再存一份，存储量随轮数近似平方增长。LangGraph 有一个 beta 阶段的 DeltaChannel，只存增量（deepagents 的 messages 就用了它）。开源版 saver 不会自动清理旧数据，需要自己调用 delete_thread / prune。

5. 怎么中断

5.1 动态中断：interrupt()

在节点（或节点里调用的中间件、工具）中调用 interrupt(value)。下图以第 7 节的审批例子为例：中断发生在 step 2 的 tools 任务里。

图 5　中断的时序。最新的 checkpoint 仍是 step 2，被中断的任务只留下一条 __interrupt__ 写入

  1. 判断有没有恢复值：每个任务有一个 scratchpad，记着这个任务已经收到的恢复值和本次执行中 interrupt() 被调用了第几次。第一次执行时没有恢复值。
  2. 抛出 GraphInterrupt：异常里带一个 Interrupt(value, id)。id 是对任务命名空间（如 tools:<task_id>）做 xxh3 哈希得到的，恢复时用它指明回答的是哪个中断。
  3. 记成一条写入：引擎把 GraphInterrupt 当作"正常停下"而不是失败，不走重试，而是调 put_writes，记一条 (task_id, "__interrupt__", [Interrupt])。同一步里其他任务照常跑完，它们的写入也都记下。
  4. 不前进：这个超步有任务没完成，所以不合并、不生成新的 checkpoint，循环以 interrupted 状态退出。
  5. 交给调用方：invoke(..., version="v2") 的返回值带 interrupts；流式调用会产出一条 __interrupt__；之后也可以用 get_state() 查 tasks[].interrupts。

到这一步，恢复所需的一切都在存储里了：快照（step 2）、待执行的任务（__pregel_tasks），以及哪个任务停在哪里（__interrupt__）。进程可以直接退出，恢复可以在另一个进程里进行。

5.2 静态断点：interrupt_before / interrupt_after

动态中断 interrupt()静态断点
在哪里设置节点代码里，可以带条件编译或调用时传节点名列表
停在哪节点执行到一半指定节点执行之前或之后，停在超步边界
能带什么给调用方任意 value（以及 response_schema）没有自定义内容
怎么恢复Command(resume=值)invoke(None, config) 接着跑；需要改值时先 update_state
典型用途人工审批、向用户提问调试、单步执行

6. 怎么恢复

6.1 恢复的时序

图 6　恢复的时序。__resume__ 写入挂在中断时的同一个 checkpoint（step 2）上，被中断的任务跑完后才生成 step 3

  1. 判断是恢复：输入是 Command，而且 thread 已经有 checkpoint，就按"接着跑"处理，不当成一次新的输入。
  2. 取现场：get_tuple 取最新的 checkpoint 及其 pending writes。
  3. 写入恢复值：Command(resume=值) 被翻译成一条 (NULL_TASK_ID, "__resume__", 值) 写入，挂在同一个 checkpoint 上。
  4. 重建任务：用快照里的版本信息和 __pregel_tasks 算出这一步的任务，结果和中断前完全一样。有成功写入的任务把写入原样交回、不再执行；被中断的任务重新执行。
  5. 重跑：被中断的任务从节点开头执行。执行到同一个 interrupt() 时，scratchpad 里已经有恢复值，直接返回，不再抛出。
  6. 前进：所有任务完成后合并写入，生成 step 3 的 checkpoint，继续后面的超步。

6.2 恢复值怎么对上中断

写法含义适用
Command(resume=值)只有一个待决的中断时，直接交给它只有一个待决中断。有多个时引擎会报错，要求指明 id
Command(resume={interrupt_id: 值, …})key 全是中断 id 时，按 id 分别交给对应的任务同一步里有多个任务各自中断（如并行的多个工具调用都要审批）
同一个任务里多次调用 interrupt()按调用顺序一一对应：第 1 次调用拿第 1 个恢复值，依此类推一个节点里连续问几个问题

interrupt() 可以带 response_schema。如果给的是 Pydantic 模型、TypedDict 或 dataclass，恢复值会先按它校验；校验失败时抛 ValidationError，这次恢复不会被保存，可以重新回答。

6.3 节点从头重跑

图 7　恢复不是从 interrupt() 那一行接着往下执行，而是把整个节点重新执行一遍

引擎不保存 Python 的调用栈，能恢复的只有 checkpoint 里的数据，所以只能把节点重新执行一遍，靠 scratchpad 让 interrupt() 这一次返回恢复值。由此有两条要求：

  • interrupt() 之前不放有副作用的操作，或者保证它们幂等。比较稳妥的做法是把副作用拆到 interrupt() 之后，或者放到下一个节点里。
  • 两次执行要走同一条路径：决定要不要中断、按什么顺序中断的条件，在重跑时必须得出相同的结果。

子图同理。子图的中断会一直冒泡到最外层图，恢复时调用子图的那个父节点也会从头重跑。

6.4 并行任务：只重跑被中断的那个

图 8　pending writes 的作用：同一步里已经成功的任务，恢复时不会再执行一遍

7. 实例：create_agent 的人工审批

langchain v1 的 create_agent 生成的就是一张 LangGraph 图，中间件的钩子各占一个节点。人工审批由 HumanInTheLoopMiddleware 提供，它必须配合 checkpointer 使用。它有两种模式，中断发生的位置不同：

图 9　create_agent 的图结构，以及两种审批模式各自的中断位置

对每个待审的调用，审批人可以做四种决定（每个工具允许哪几种由配置决定）：

决定结果
approve按原参数执行
edit用审批人改过的参数执行
reject不执行，模型收到一条 status=error 的 ToolMessage，说明被用户拒绝（可附原因）
respond不执行，审批人的回复代替工具结果交给模型（status=success）
agent = create_agent(model, tools=[send_email],
                     middleware=[HumanInTheLoopMiddleware(interrupt_on={"send_email": True},
                                                          interrupt_mode="per_call")],
                     checkpointer=saver)
config = {"configurable": {"thread_id": "t1"}}

r = agent.invoke({"messages": [{"role": "user", "content": "给 alice 发封邮件"}]}, config, version="v2")
# r.interrupts[0].value == {"type": "tool_approval", "tool_call_id": "call_A", "name": "send_email", ...}

agent.invoke(Command(resume={r.interrupts[0].id: {"type": "approve"}}), config, version="v2")

用假模型实测这个例子，下面是两种模式各自产生的 checkpoint 链：

图 10　实测的 checkpoint 链（InMemorySaver + 假模型）。中断和恢复都发生在同一个 checkpoint 上，链本身没有"中断"这种节点

两种模式的差别：

  • batched：模型一轮发出的所有待审调用合成一个中断，审批人一次给出全部决定，按位置对应。如果 when 谓词在重跑时对其中一部分调用的判断变了，决定和调用就对不上，恢复会报错。
  • per_call：每个调用单独中断，恢复值带 response_schema 校验。源码里有两条提醒：
    • 一次提交多个答案时，只要有一个不合法，其他调用可能已经执行了，重新提交会执行两遍；
    • 排在 HITL 前面的中间件在恢复时会重跑到暂停点，不能有副作用。
  • 两种模式都一样：when 谓词重跑时如果返回了 False，审批答案会被跳过，工具照样执行，即使审批人选的是拒绝。

8. 历史、分叉与改写

图 11　parent 指针让 checkpoint 构成一棵树：从历史上的某一步出发再跑，就长出一个新分支，原来的分支不受影响

接口作用
get_state(config)返回 StateSnapshot：values（state）、next（下一步要跑的节点）、tasks（含待决的 interrupts）、config、metadata、parent_config
get_state_history(config)按时间倒序列出这个 thread 的全部快照
update_state(config, values, as_node=…)像某个节点那样写一次 state，生成一个 source=update 的新 checkpoint，后续调度按"这个节点刚跑完"来算
config 里带 checkpoint_id 调用从那个历史 checkpoint 重新出发（time travel）。新产生的 checkpoint 以它为父，形成分叉；在那里调用 interrupt() 会重新触发，不会沿用当时的恢复值

9. 使用要点

要点原因做法
中断必须配 checkpointer中断的现场只存在 checkpoint 里；没有 checkpointer 时 Command(resume) 直接报错生产用持久化的 saver（Postgres 等），不要用 InMemorySaver
interrupt() 之前的代码会执行两次恢复时节点从头重跑把副作用移到 interrupt() 之后或下一个节点；做不到就保证幂等
重跑必须走同一条路径多次中断按调用顺序对应；审批中间件的 when 谓词翻转会跳过审批答案中断的条件只依赖 state 里已有的数据，不依赖时间、随机数、外部状态
多个待决中断要按 id 回答只给一个值时引擎不知道交给谁，会报错用 {interrupt_id: 值} 的形式
存储会持续增长每个变了的 channel 每步存一份完整的值；开源 saver 不会自动清理定期 delete_thread / prune；消息很长时考虑 DeltaChannel（beta）
快照和图结构绑定快照按节点名、channel 名和序列化格式保存改节点名、删 state 字段、换消息类型之前，确认旧 thread 还能恢复，或者给出迁移办法
durability 选择exit 只在退出时写，中途崩溃全丢需要崩溃后能接着跑的场景用 sync 或默认的 async
