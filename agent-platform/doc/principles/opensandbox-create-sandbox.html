0. 一页看懂

  • 接口：POST /v1/sandboxes，请求头 OPEN-SANDBOX-API-KEY，请求体 JSON，共 16 个顶层字段。
  • 同步：server 建出 BatchSandbox 后一直等到 Pod 拿到 IP 才返回（状态码 202，但语义是「已就绪」），最长等 [kubernetes].sandbox_create_timeout_seconds（默认 60 秒，我们配了 180 秒），超时回 504 并删掉已建的 CR。
  • 启动来源四选一：image（镜像）、snapshotId（快照）、extensions.poolRef（预热池）、templateId（Fast Sandbox 模板）。决定了其余字段哪些必填、哪些禁止（第 2 节）。
  • 最常用的形态（镜像启动）只有三个必填：image、entrypoint、resourceLimits。
POST /v1/sandboxes
OPEN-SANDBOX-API-KEY: <key>

{
  "image": {"uri": "python:3.11"},
  "entrypoint": ["tail", "-f", "/dev/null"],
  "resourceLimits": {"cpu": "500m", "memory": "512Mi"},
  "timeout": 3600
}
最容易踩的四点（详见第 7 节）
  1. metadata 会被原样写成 K8s label：值最长 63 个字符，只能用字母、数字和 -_.。规范示例里的 "name": "Data Processing Sandbox"（带空格）在 1.1.1 上会回 400。
  2. 拼错字段名不会报错，未知字段被静默丢弃。例如把 networkPolicy 写错，结果是不挂 egress sidecar、出站全放行。
  3. 返回的 Running 只表示 Pod 有了 IP，不表示 execd 已经在监听。调用方要自己轮询 execd 的 /ping。
  4. env 以明文写进 BatchSandbox 和 Pod spec，接口不支持 secretKeyRef。

1. 接口

项内容
方法与路径POST /v1/sandboxes（server 也挂了不带 /v1 的同名路由）

4. 嵌套对象

4.1 image（ImageSpec）

字段类型说明
uri 必填string标准镜像引用，如 python:3.11、registry.example.com:5000/app:v1。拉取策略由 server 的 [kubernetes].image_pull_policy 决定，不能在请求里改
auth.username / auth.passwordstring私有仓库凭据。给了 auth 就两个都要填。server 建 Secret build_image_pull_secret_name(id) 并挂到 imagePullSecrets；也可以不传，改在模板或 ServiceAccount 上配

4.2 platform（PlatformSpec）

字段取值说明
os 必填linux / windows大小写不敏感（server 会转小写）；注入 kubernetes.io/os
arch 必填amd64 / arm64注入 kubernetes.io/arch

os: windows 会走 Windows profile，改写 Pod 的多处配置，并对 resourceLimits 做额外校验。不传 platform 时 server 不加任何 OS / 架构约束，镜像能不能在节点上跑由调用方自己保证。

4.3 resourceLimits / resourceRequests

键例子到 K8s
cpu"500m"、"2"原样
memory"512Mi"、"4Gi"原样
gpu"1"改名为 nvidia.com/gpu。值是 "all" 时回 400（K8s 的扩展资源只接受整数）；解析不了的值被丢掉
其他"ephemeral-storage": "10Gi"原样透传，能不能用由 K8s 决定

4.4 env 的保留与分流

变量去向说明
普通变量主容器 sandbox以明文 value 写进 Pod spec
OPENSANDBOX_LIFECYCLE拒绝（422）保留给 lifecycle 字段
OPENSANDBOX_EGRESS_*（白名单内）egress sidecar白名单：LOG_LEVEL、DNS_UPSTREAM_TIMEOUT、MITMPROXY_SSL_INSECURE、MITMPROXY_TRANSPARENT、MITMPROXY_EXTRA_PORTS、DENY_WEBHOOK、METRICS_EXTRA_ATTRS、CREDENTIAL_VAULT_REQUIRE_TLS、CREDENTIAL_VAULT_REQUIRE_SCOPED_MATCH、CREDENTIAL_VAULT_TRUSTED_PROXY_CIDRS、POLICY_FILE（都带 OPENSANDBOX_EGRESS_ 前缀）。其中 MITMPROXY_TRANSPARENT 主容器也会收到一份
OPENSANDBOX_EGRESS_*（白名单外）拒绝（400）例如 UPSTREAM_PROXY 这类只能由 server 配置注入的变量
OPENSANDBOX_EGRESS_*（没带 networkPolicy）丢弃没有 sidecar 可以接收；server 只打一条 warning 日志，不报错

server 另外往主容器注入以下变量。请求里传了同名变量会被覆盖或重复，不要这么做：

  • OPENSANDBOX_ID（沙箱 id）
  • EXECD=/opt/opensandbox/execd
  • EXECD_INIT=1（仅在 server 配了 execd_run_as_init 时）
  • OPENSANDBOX_EGRESS_MITMPROXY_TRANSPARENT=true（仅在开了 credentialProxy 时）
  • OPENSANDBOX_LIFECYCLE（仅在传了 lifecycle 时）

execd 本身会读的变量（如 EXECD_ACCESS_TOKEN、EXECD_ENVS）也走 env 传入，server 对它们不做特殊处理。

4.5 metadata

整份 metadata 被 labels.update(metadata) 合进 BatchSandbox 的 label。GET /v1/sandboxes?metadata=k%3Dv 就是用 label selector 过滤，所以规则和 K8s label 完全一致：

项规则
键[前缀/]名字。名字最长 63 个字符，匹配 [A-Za-z0-9]([-A-Za-z0-9_.]*[A-Za-z0-9])?。前缀可选，是最长 253 个字符的 DNS 子域名。键不能以 opensandbox.io/ 开头
值最长 63 个字符，可以为空；非空时首尾必须是字母或数字，中间只能有字母、数字和 -_.
不符合回 400 INVALID_METADATA_LABEL

中文、空格、/、@、: 都放不进值里。要存人类可读的名字或 URL，只能放到调用方自己的库里。

4.6 networkPolicy 与 credentialProxy

字段类型说明
networkPolicy.defaultActionallow / deny没有规则命中时的动作。省略时 sidecar 按 deny 处理
networkPolicy.egress[]NetworkRule[]按顺序匹配的规则
egress[].action 必填allow / denyK8s 路径上 server 不校验取值，原样交给 sidecar
egress[].target 必填string域名、通配域名、IP、CIDR 都支持（sidecar 的 normalizePolicy 已实现；规范里「IP/CIDR not yet supported」的说法已过时）。*.example.com 不匹配 example.com 本身
credentialProxy.enabledbooleansidecar 开透明 MITM，并把 MITM CA 装进主容器，供 Credential Vault 注入凭据。默认放行（defaultAction: allow）仍可用，但 server 会打弃用告警

只要带了 networkPolicy（哪怕是空对象），server 就会：

  • 加一个 egress sidecar；
  • 生成一个 egress 令牌，存进 annotation，并作为 sidecar 的环境变量；
  • 给主容器 drop: [NET_ADMIN]，保证只有 sidecar 能改网络栈。

空对象等于全拒绝：规范说空对象或 egress 为空时以全放行启动，但 1.1.1 的 sidecar 在 defaultAction 缺省时一律按 deny 处理，{} 的结果是只能访问 DNS 服务器和平台的 allow.always。要全放行必须显式写 defaultAction: allow。之后可以通过 /networkpolicy 接口修改策略。

server 配了 [egress.upstream_proxy] 时，带 networkPolicy 的请求还必须满足以下其中之一，否则回 400：

  • 开 credentialProxy.enabled；
  • 在 env 里设 OPENSANDBOX_EGRESS_MITMPROXY_TRANSPARENT=true。

4.7 lifecycle（SandboxLifecycle）

字段类型约束语义
preStart.command 必填string[]至少 1 项，首项非空白execd 的 HTTP 服务就绪后、用户 entrypoint 之前执行，每次容器启动都会跑。失败或超时则 entrypoint 不启动。argv 不经 shell，需要 shell 语法时写 ["sh","-c","..."]
preStart.timeoutSecondsinteger1～10800，缺省 60超时时间
periodic[].name 必填string去掉首尾空白后非空，同一沙箱内唯一钩子名
periodic[].schedule 必填string五段 cron、@hourly 或 @every 30s（整秒，至少 1 秒）运行期由 execd 调度。同名钩子不会重叠，上一次还没跑完就跳过本次
periodic[].command 必填string[]同 preStart—
periodic[].timeoutSecondsinteger1～300，缺省 60—

只有这三个对象设了 extra = "forbid"，写错字段名会回 422。池模式下不能用 lifecycle，因为池里的 Pod 是事先建好的，那时还不知道本次请求的钩子。

4.8 volumes（Volume[]）

字段类型约束 / 说明
name 必填stringDNS label（小写字母数字和 -，最长 63 个字符），本请求内唯一，不能与内部卷 opensandbox-bin 等重名
mountPath 必填string容器内的绝对路径
readOnlyboolean缺省 false
subPathstring后端路径下的子目录。必须是相对路径，不能包含 ..
pvc / host / ossfsobject后端，必须恰好一个。K8s 只支持前两个
后端字段说明
pvc.claimName 必填同命名空间里的 PVC 名
pvc.createIfNotExists缺省 true：PVC 不存在时 server 先建一个。为 false 且 PVC 不存在时，server 不提前报错，Pod 会一直 Pending，直到创建超时回 504（按代码推断，未实测）
pvc.deleteOnSandboxTermination缺省 false。只对本次自动建的 PVC 生效：server 给 PVC 打上 label 和 ownerReference，CR 被删（包括到期删除）时随之回收
pvc.storageClass / storage / accessModes只在自动建 PVC 时使用。缺省分别是集群默认 StorageClass、[storage].volume_default_size（默认 1Gi）、["ReadWriteOnce"]
host.path 必填宿主机绝对路径，以 DirectoryOrCreate 挂载。必须在 [storage].allowed_host_paths 之下，该列表为空时一律拒绝；不能含 ..、// 或结尾的 /
ossfs.*Docker 运行时专用。K8s 下回 400（Supported backends: pvc, host）

同一个 PVC 挂多次（不同 subPath 挂到不同目录）是支持的，规则如下：

  • Pod 里只生成一个卷，卷名取第一个条目的 name；
  • 只有所有挂载都只读时，卷源才只读；
  • 各条目的 createIfNotExists 和 deleteOnSandboxTermination 必须一致，否则回 400。

server 会对每个 PVC 先 get 一次，检查它是否属于别的沙箱（防止被别人的清理误删）。因此 server 的 RBAC 需要 PVC 的 get 权限，没有时回 500。

4.9 extensions

键值作用
poolRefPool 名，或 "*"切到池模式。Pool 不存在回 404 K8S_POOL_NOT_FOUND；在 pool_acquisition_timeout_seconds（默认 30 秒）内等不到空位，回 429 并带 Retry-After
access.renew.extend.seconds十进制整数字符串，300～86400按访问自动续期（OSEP-0009）：每次访问把过期时间往后推这么多秒。需要 server 开 [renew_intent]，并且流量经过 server 代理或 ingress 网关。值不合法回 400
bootstrap.execd.isolation"enable"execd 隔离会话：主容器加 SYS_ADMIN，seccomp 和 AppArmor 设为 Unconfined，并挂一个 emptyDir 到 /var/lib/execd/isolation。会明显放宽容器权限
opensandbox.extensions.<x>任意字符串原样写到 annotation opensandbox.io/extensions.<x>，并在响应和 GET 的 extensions 里回显
其他键—不报错，也不保存

5. 参数落到 Pod 的哪里

镜像启动、非池模式下，server 把 BatchSandbox 模板文件（我们的是 sbx.yaml / acp.yaml / bench.yaml）和本次参数合并成 BatchSandbox，再由控制器建出 Pod。图中蓝色等宽字是请求字段。

合并规则（template_manager._deep_merge）：字典递归合并，列表整体替换。server 生成的 containers、initContainers、volumes 会覆盖模板里的同名列表，所以 server 会另外把以下三样从模板捞回来：

  • 模板里的 Pod 卷；
  • 模板 sandbox 容器的 volumeMounts；
  • 模板 sandbox 容器的 securityContext。

模板容器上的其他字段（如 env、resources、workingDir）以及模板里的其他容器都会丢失。Pod 级的标量和字典字段（如 Pod securityContext、tolerations、nodeSelector）在请求没有涉及时保留。

6. 校验顺序与错误

6.1 顺序

  1. pydantic 模型（api/schema.py）：检查类型、必填、范围（如 timeout ≥ 60）、格式（卷名、PVC 名、storage），以及 model_validator 里的互斥规则。失败回 422。
  2. extensions：只检查 access.renew.extend.seconds，失败回 400。
  3. 快照解析：对应 404 / 409。
  4. 建 CR 前的业务校验（kubernetes_service.create_sandbox），依次检查：
    • 池模式下不兼容的字段
    • entrypoint 非空
    • metadata 是否符合 label 规则
    • platform 取值
    • timeout 上限
    • secureAccess
    • egress 配置、gVisor
    • image.auth
    • egress 环境变量白名单与 upstream proxy
    • 卷
    • 池是否存在
    失败回 400 / 404，此时没有任何副作用。
  5. 建 PVC、建 CR：provider 的预检失败（如 ossfs、平台冲突）回 400。
  6. 等待就绪：失败时先删掉 CR 再返回，对应 400 / 403 / 429 / 500 / 504。

6.2 错误码

状态码格式典型原因
422FastAPI 默认格式 {"detail": [{loc, msg, type}]}，不是 {code, message}
  • image 和 snapshotId 都给了或都没给
  • 镜像启动缺 entrypoint
  • 非池模式缺 resourceLimits
  • timeout < 60
  • env 里有 OPENSANDBOX_LIFECYCLE
  • credentialProxy.enabled 但没带 networkPolicy
  • 一个卷给了零个或多个后端
  • lifecycle 字段写错或钩子重名
  • templateId 带了禁止字段
  • poolRef 同时带了 snapshotId 或 lifecycle
400{code, message}
  • INVALID_PARAMETER：platform、timeout 上限、secureAccess、egress 未配、dns+nft、gVisor、image.auth、池模式冲突、egress 变量白名单、ossfs、平台调度不上（POD_PLATFORM_UNSCHEDULABLE）、命名空间不存在
  • INVALID_METADATA_LABEL
  • INVALID_ENTRYPOINT
  • 卷系列：DUPLICATE_VOLUME_NAME、INVALID_HOST_PATH、HOST_PATH_NOT_ALLOWED、INVALID_SUB_PATH、INVALID_PVC_NAME 等
401{code, message}API key 缺失或错误
403{code, message}KUBERNETES::QUOTA_EXCEEDED：命名空间 ResourceQuota 不够。规范说 batchsandbox provider 下不会快速失败，而是等到超时；但 1.1.1 的等待循环会识别状态消息里的 exceeded quota，是否生效取决于控制器有没有把拒绝原因写进状态（未实测）
404{code, message}快照、Pool、模板不存在
409{code, message}快照未就绪
429{code, message} + Retry-After池在 pool_acquisition_timeout_seconds 内没有空位
500{code, message}K8S_POD_FAILED（Pod 进入 Failed）、K8s API 错误、没有 PVC 的 get 权限
503{code, message}并发建同名 PVC 时，复查归属失败（可重试）
504{code, message}K8S_POD_READY_TIMEOUT：在 sandbox_create_timeout_seconds 内 Pod 没拿到 IP，常见原因是镜像拉取慢、调度不上、PVC 不存在

7. 规范与实现的出入

#现象影响
1metadata 就是 K8s label。规范示例 "name": "Data Processing Sandbox" 在 1.1.1 上回 400不能存可读名称、URL、邮箱、中文；只能放 id 类短值
2CreateSandboxRequest 和大多数嵌套对象没设 extra = "forbid"（只有 lifecycle 的三个对象设了），未知字段被静默丢弃；规范写的 additionalProperties: false 在 server 端不生效拼错 networkPolicy 会得到一个出站全放行的沙箱。另外 server 开了 populate_by_name，resource_limits 这类下划线写法也被接受。1.2.0 对 networkPolicy 里的未知字段改为回 422
3结构错误回 422，格式是 FastAPI 默认的 {"detail": [...]}；规范只列了 400 和 ErrorResponse客户端解析错误时要同时兼容 message 和 detail
4返回 Running 时，实际可能只是 Allocated（Pod 有 IP，但 init 容器或主容器还没就绪）拿到响应后立刻调 execd 可能连不上，必须轮询 /ping
5resourceLimits: {} 能通过校验，Pod 不设任何 resources，resourceRequests 也被丢掉沙箱变成 BestEffort，只受命名空间 LimitRange 约束
6env 只能传明文值令牌、密钥会出现在 BatchSandbox 和 Pod spec 里，能读这两类对象的人都能拿到
7规范列了 ossfs 卷，K8s 运行时不支持回 400
8createIfNotExists 缺省是 trueclaimName 写错时不会报错，而是悄悄建一个新的空 PVC（默认 1Gi）
9OPENSANDBOX_EGRESS_* 在没带 networkPolicy 时被丢弃，只打一条 warning 日志以为配上了，实际没生效
10池模式下 image、resourceLimits、resourceRequests 可以传，但不会被使用以为覆盖了池模板，实际没有
11规范说 networkPolicy: {} 是全放行，sidecar 的实际行为是全拒绝只想挂上 sidecar（比如为了 Credential Vault）却没写 defaultAction: allow，沙箱就断网了
12规范说 target 不支持 IP / CIDR，sidecar 其实支持可以直接按网段放行或封禁，比如封掉集群内网段

8.2 Atlas 实际发出的请求

原生沙箱（providers/opensandbox/provision.py 中的 sandbox_spec），strict 档：

{
  "image": {"uri": "<AgentSpec.sandbox.image 或默认镜像>"},
  "entrypoint": ["tail", "-f", "/dev/null"],
  "timeout": null,                                  // 不自动过期，回收由 Atlas 负责
  "resourceLimits":   {"cpu": "...", "memory": "..."},
  "resourceRequests": {"cpu": "...", "memory": "..."},
  "env": {
    "EXECD_ACCESS_TOKEN": "<令牌>",               // ★ 明文进 Pod spec（第 7 节 #6）
    "EXECD_INIT": "1",
    "EXECD_ENVS": "/tmp/.execd/env",                // strict 档根目录只读
    "TMPDIR": "/tmp",
    "HOME": "/home/agent"                           // 评测档不设；配了代理时改为设 http(s)_proxy / no_proxy
  },
  "metadata": {"atlas.managed": "true", "atlas.kind": "sbx", "atlas.profile": "strict",
               "atlas.thread": "<ws>", "atlas.user": "<user>"},
  "volumes": [
    {"name": "workspace", "pvc": {"claimName": "atlas-oss", "createIfNotExists": false},
     "mountPath": "/workspace", "subPath": "<user>/<ws>/workspace", "readOnly": false},
    {"name": "skills",    "pvc": {"claimName": "atlas-oss", "createIfNotExists": false},
     "mountPath": "/skills",    "subPath": "<user>/<ws>/skills",    "readOnly": true}
  ]
}

ACP Pod（providers/opensandbox/acp.py）与原生沙箱的不同点：

  • entrypoint 是 sh 包装：把令牌写进文件，把模型 key 读成环境变量。
  • env 多了 ATLAS_BRIDGE_* 与 agent 环境变量白名单。
  • 多挂一个 state 卷，作为 CLI 的 HOME。
  • 工作区挂父会话的前缀。
  • 有 git 档案时加 networkPolicy: {defaultAction: allow} 和 credentialProxy: {enabled: true}。
对照结论
metadata 是否符合 label 规则键是 atlas.xxx（无前缀名字，含 .，合法）。值里 <ws> 和 <user> 必须是不超过 63 个字符、只含字母数字和 -_. 的 id。UUID 没问题；如果以后改成邮箱这类用户标识，创建会直接 400
同一 PVC 挂多次两三个条目都是 atlas-oss，标志位一致（都是 createIfNotExists: false 且没设删除），合法。Pod 里只有一个卷，名为 workspace；因为 workspace 可写，卷源可写
createIfNotExists: false整桶 PVC 是预先建好的，所以设成 false 是对的。如果 PVC 丢了，症状是 180 秒后回 504，而不是 404
超时配合server 最多等 180 秒，Atlas 的 LifecycleClient 超时是 200 秒，能收到 server 的 504，不会先在客户端超时
错误解析lifecycle.py::_detail 先取 message，再取 detail，422 和 400 两种格式都能带出原因
未用到的能力lifecycle 钩子、platform、networkPolicy（原生沙箱）、secureAccess、池、快照
