Atlas 记忆方案设计

日期：2026-10-24（第三版）· 状态：方案设计；服务端、Atlas 后端与前端已实现（2026-10-27），未部署
本文只讲方案：服务端和客户端怎么分工、数据怎么规划、怎么入库、怎么读取、冲突怎么解决。接口、表结构、配置、分期等内容在方案确定后的详细设计中展开（见 §9）。
本文取代 记忆设计（基于 Mem0） 中的方案部分。该文的以下结论保持不变：§01 信任模型（Agent 知识不走记忆）；§09 隔离原则（落在 Atlas 一侧：关联主键由 Atlas 按会话确定，不出现在工具参数里）；§10 用户权利。

本版相对 10-23 版的主要变化
  • 方案拆成两块：服务端是独立的记忆服务，只定义作用域、主题、条目这几个逻辑对象和它们的规则，不关心存的是不是"记忆"；客户端是 Atlas，决定存什么、怎么取、冲突怎么解决。
  • 作用域实例由"作用域编码 + 关联主键"定位，两个值都由调用方通过接口传入。作用域之间没有关联关系，人和项目的组合单独配成"用户项目"作用域。
  • 主题由客户端通过接口创建、自行管理。主题大小上限也由客户端自己定、自己保证（不同使用场景可以不同），服务端不管上限；超限的主题由 Atlas 在会话后补记时拆小，服务端只负责把拆分在一个事务里提交，不扫描、不调用 LLM。
  • 读取改为按主题整块加载：主题目录和常驻主题放进系统提示词，其余主题由 Agent 按需加载。去掉了语义检索、按上下文标签常驻和后台整理。
  • 并发：服务端按作用域实例加分布式锁，串行写入；每次写入都带时间，以时间晚的为准；一次写入（删除 + 新增）在一个事务里完成。
  • 数据权限：作用域可以打开数据权限开关，打开后记忆服务按用户中心的数据权限校验调用用户。Atlas 建会话时请记忆服务登记实例归属，用户的记忆只有本人能读写。
实现记录（2026-10-26 / 10-27）：记忆服务、Atlas 后端（10-26）与前端（10-27：记忆页按主题浏览、更正、移动、恢复、彻底删除、修订历史撤销、暂停与全部删除；对话里保存 / 遗忘记忆后当场显示「已记住 #N［撤销］」；对话页显示「会话结束后补记了 N 条［查看］」）已按本方案实现，未部署。与方案的差异：
  • 实例锁用数据库行锁：同一实例的写入在事务里先锁实例行，锁随事务提交释放，多副本同样有效；记忆服务因此不依赖 Redis。条目编号、版本号都在这把锁里递增。
  • 版本号按实例统一递增（§9.1 的选项）：主题拆掉后再建同名主题，版本号也不会和客户端记着的旧值撞上。主题的描述、扩展属性变了也换版本号（常驻快照里有它们）。
  • 本期只接「用户」作用域：项目身份（Q1）未定，「用户项目」作用域等项目实体有了再接。记忆服务本身支持多字段关联主键和按部分主键列实例。
  • 读取对所有开启记忆的原生会话生效（常驻块 + 加载主题，SubAgent 也有）；写入（保存、遗忘）要在智能体里勾选「记忆」，SubAgent 勾了也不挂。写入不走审批（当场可见、可撤销）。
  • ACP 会话只有会话后补记：常驻块怎么注入 CLI、记忆工具怎么给（§9.2）留到下一期。
  • 更新提示（§5.5）附在请求末尾，随上下文管理一起工作：智能体关了上下文管理时不附提示（写入前的版本检查照常）。
  • 补记一次调用：把整个实例在篇幅内的主题条目一起交给抽取模型；超出篇幅、没展开的主题这一轮不往里写。触发：空闲 30 分钟或归档、且有新变化；连续失败 3 次后等会话有新消息再试。
  • 写入的目标主题不存在与已被拆分分开报（前者 404、后者 409），两种都带当前主题目录。删除主题只允许删空主题。
  • Mem0 与它的抽取、收敛、语义注入、只读检索工具已移除（Q5：旧记忆不迁移）。

0. 方案概览

图 0　方案总览：Atlas 负责记忆的语义（包括超限主题怎么拆），记忆服务只提供按作用域实例隔离的主题与条目存储，并负责并发和事务

问题方案
怎么分工服务端（记忆服务）：定义作用域、作用域实例、主题、条目；保证实例之间隔离；负责并发、事务和修订历史。不解释条目内容，也不解释关联主键。
客户端（Atlas）：决定用哪些作用域、传什么关联主键、建哪些主题、哪些常驻、存什么、冲突怎么判断、超限的主题怎么拆
数据怎么规划作用域 → 作用域实例（作用域编码 + 关联主键）→ 主题 → 条目。Atlas 使用用户（关联主键是 uid）和用户项目（关联主键是 uid + 项目编码）两个作用域
怎么入库两条路径：过程中存（主路径，当轮生效、当场提示）和会话后补记（补漏，下次会话提示）。写之前先看完目标主题的全部条目；一次写入 = 删除旧条目 + 新增一条，在一个事务里完成
怎么读取常驻：主题目录和标为常驻的主题放进系统提示词，按会话存快照。按需：Agent 根据主题目录自行决定加载哪个主题，一次取出全部条目。不做语义检索。本地的主题内容是否最新，按服务端的版本号判断
谁能读写作用域可以打开数据权限开关。打开后，记忆服务按用户中心的数据权限校验调用用户对实例的权限，没登记的实例一律拒绝。Atlas 的两个作用域都打开开关，建会话时请记忆服务登记"这个实例归这个用户"，所以用户的记忆只有本人能读写
冲突怎么解决主题有大小上限，写入方能看到主题的全部条目，在此基础上判断。取代只在同一作用域实例内进行，按来源规定谁能取代谁。并发写入由服务端加锁串行，以时间晚的为准
主题太大怎么办大小上限由客户端按自己的使用场景定、自己保证，服务端不管上限，只报告每个主题的当前大小。Atlas 的上限是给 LLM 的软上限，超了也能写入；Agent 在对话中可以自己把大主题拆小，没拆的由会话后补记拆分。服务端只负责把客户端给的拆分在一个事务里提交

1. 背景与目标

1.1 现状的问题

问题说明
写入只有后台抽取这一条路现在每个 Run 结束后，由 Mem0 在后台抽取记忆。用户看不到写入了什么，也没法当场纠正；"记住这个"这类明确要求，要等到下次会话才生效；每个 Run 都要多调用一次 LLM
没有稳定的"项目"现在的"项目"其实是会话的工作区，每个新会话都不一样，所以项目记忆没法跨会话复用
记忆没有分层不区分用户级和项目级，也没有主题。结果是：每次都需要的记忆不能保证出现，也做不到"写 Java 代码时才加载 Java 相关的记忆"
检索效果差Mem0 的关键词检索对中文基本无效。另外现在是每轮用用户的提问去检索，但偏好类记忆和提问在语义上并不接近，所以经常召回不到
冲突看不全、处理粗糙写入时只能看到检索出来的几条，相关的旧记忆没检索到就发现不了冲突；只能新增，冲突靠事后硬删除来解决：判断错了无法恢复，还可能跨项目误删

1.2 目标

  • 存储做成独立服务：只按作用域隔离、按主题组织数据，不关心存的是不是记忆，其他应用也能使用。
  • 记住两类信息：跨项目都成立的用户偏好和事实；只在某个项目里成立的约定和决策。
  • 两条写入路径：用户明确要求的当轮生效；Agent 漏掉的由补记补上。两条路径写入的内容都对用户可见，都可以撤销。
  • 常驻 + 按需：每次都需要的记忆稳定出现，不依赖检索；其余的按主题整块按需加载。
  • 冲突看得全、可控：写入方能看到目标主题的全部内容；冲突能判定、能追溯、能恢复。用户能查看、更正、删除自己的记忆，删除就是彻底删除。

1.3 为什么有了抽取，仍然不用 Mem0

  • 补记必须知道"已经写了什么"：它要先知道本会话里 Agent 已经写入了哪些记忆，只补缺的部分。
  • 两条路径必须用同一套规则：作用域、主题、取代限制、来源标记、通知和撤销，都要和过程中存保持一致。
  • Mem0 的数据模型不够：它只会新增，作用域只有 user_id，没有主题，也没有"已取代 / 已遗忘"这样的状态。

1.4 非目标

  • 跨用户共享的知识：团队约定写进仓库的 ATLAS.md（经过评审，会作为持久指令加载）；Agent 知识走知识库。记忆服务本身支持按项目共享的作用域，但 Atlas 本期不用（Q2）。
  • 语义检索：本期不做，靠主题目录 + 整主题加载（5.4）。
  • 知识图谱、多跳推理、自动遗忘：本方案不涉及。

2. 分层：服务端与客户端

记忆方案分成两块。服务端是独立的记忆服务，它只定义逻辑对象（作用域、主题、条目）和这些对象的规则，不关心条目里存的是什么，所以它存的不一定是记忆。客户端是 Atlas，决定存什么、什么时候取、冲突怎么判断。

方面服务端（记忆服务）客户端（Atlas）
作用域在管理平台配置：编码、描述、是否校验数据权限决定用哪些作用域；每次调用都传入作用域编码和关联主键
隔离作用域实例之间数据隔离；合并、取代只在实例内进行保证只传当前用户有权访问的关联主键
数据权限作用域打开开关时：代客户端在用户中心登记实例归属；每次读写按用户中心校验调用用户建会话时登记本会话用到的实例；调用时带上调用用户
主题提供创建、列出、读取、移动条目、拆分；拆分只按客户端给的分组执行决定建哪些主题、写到哪个主题、哪些常驻、什么时候加载；定主题的大小上限，超限的主题怎么拆
条目保存内容、时间、来源；删除的条目保留历史，可以恢复，也可以彻底删除决定写什么、删除哪几条；根据来源判断谁能取代谁
并发按作用域实例加分布式锁，串行写入；以时间晚的为准；一次写入在一个事务里完成；主题每次变化都更新版本号每次写入带上时间；根据主题的版本号判断本地内容是否最新
写入路径—过程中存、会话后补记（补记时顺带拆分超限的主题）
用户控制提供撤销、恢复、彻底删除的能力管理界面；对话里的提示和撤销入口

3. 服务端：记忆服务

3.1 逻辑对象

图 1　逻辑对象：作用域在管理平台配置；"作用域编码 + 关联主键"确定一个实例，实例之间隔离；实例下的主题由客户端通过接口创建；主题下是一条条条目

对象由谁创建包含什么规则
作用域管理员在管理平台配置编码、描述、数据权限开关作用域之间没有关联关系
作用域实例不用单独创建，由"作用域编码 + 关联主键"定位若干主题实例之间数据完全隔离；合并、取代只在实例内进行
主题客户端通过接口创建编码、描述、扩展属性、当前大小、版本号编码在实例内唯一；服务端不限制大小
条目客户端写入内容、编号、时间、来源、出处编号在实例内递增，之后不再改变；删除的条目保留历史

3.2 作用域与作用域实例

  • 作用域由管理员在管理平台配置：编码、描述，以及是否校验数据权限（3.7）。主题大小上限不在作用域上配置，由客户端自己定（3.3）。
  • 读写某个作用域的数据时，调用方在接口参数里传两个值：作用域编码和关联主键。这两个值一起确定一个作用域实例。
  • 关联主键是什么，由作用域的用途决定、由调用方传入，服务端不解释它。例如：
    作用域关联主键数据属于
    用户用户 uid某个人，跨项目都成立
    项目项目编码某个项目，项目成员共用
    用户项目uid + 项目编码某个人在某个项目里
  • 作用域之间没有关联关系。用户作用域和项目作用域互不影响；需要"人 × 项目"的数据，就单独配一个用户项目作用域，而不是让两个作用域互相引用。
  • 同一个作用域实例允许多个应用、多个会话同时读写。同一个应用的多个会话本来就会并发读写，所以统一用 3.5 的并发规则处理，不按应用做访问控制。
服务端默认不校验关联主键属于谁。服务端是抽象服务，不知道关联主键是用户 uid、项目编码还是别的东西，只按调用方传入的值定位实例。"这个调用方能不能访问这个实例"默认由客户端负责，例如 Atlas 只传当前会话所属用户的 uid，以及当前会话关联的项目编码（4.1）。需要服务端把关的作用域，打开数据权限开关，由记忆服务按用户中心的数据权限校验（3.7）。

3.3 主题

  • 由客户端管理：客户端通过接口创建主题，建哪些、叫什么、多大算满、什么时候拆，都由客户端决定。
  • 主题包含：
    • 编码：实例内唯一。
    • 描述：说明这个主题收什么内容，客户端据此选择写到哪个主题、决定要不要加载。
    • 扩展属性：由客户端定义，服务端原样保存、不解释。例如 Atlas 用它标记"常驻"。
    • 当前大小、版本号：主题里的条目有任何变化（新增、删除、移动、撤销、恢复），版本号就会变。
  • 版本号由服务端分配：在实例锁内分配，只增不减，不依赖任何时钟。列出主题目录、加载主题时，返回每个主题的当前版本号；写入、拆分时，返回目标主题写入前和写入后的版本号。客户端靠这些判断本地的内容是否最新（5.5）。
  • 为什么不用更新时间：条目的时间由客户端给出，表示信息成立的时间，补记写入的时间还可能早于已有条目（6.4），用它看不出主题变没变；服务端多副本的时钟也不严格一致。
  • 服务端不管大小上限：同一个作用域可能被不同客户端、不同场景使用，合适的上限不一样，所以上限由客户端自己定、自己保证。服务端只报告每个主题的当前大小，写入不会因为主题大小被拒绝，服务端也不主动拆分。超限的主题由客户端拆分（3.6）；Atlas 的做法见 4.2。
  • 为什么客户端要限制大小：主题小，客户端才能一次取出全部条目。写入方能看到主题的全部内容，冲突就不会因为"没检索到"而漏掉；读取也不需要语义检索。
  • 移动条目：服务端提供把条目从一个主题移到另一个主题的操作，用户在管理界面调整主题时用它。移动不改变条目的内容、编号、时间和来源。

3.4 条目

属性说明
内容一段文本，服务端不解释。对 Atlas 来说是一个原子事实
编号实例内递增，例如 #131，移动、拆分后都不变。客户端引用某一条（例如要删除它）时用编号
时间客户端写入时给出，表示这条信息成立的时间，用来判断先后（3.5）。服务端另外记录入库时间，用于追溯
来源客户端给的标签，服务端原样保存、不解释。Atlas 用它区分"用户亲自 / Agent 写入 / 会话后补记"
出处客户端给的说明（可选），例如在哪个会话、哪一轮写入的
修订历史每次写入删除了哪些、新增了哪一条，都留下记录，用于撤销、恢复和追溯

图 2　条目的生命周期：只有"有效"的条目会被列出和加载；删除的条目保留在修订历史里，可以撤销；彻底删除只在用户要求时由客户端调用

3.5 写入：事务、锁与时间

一次写入对应一条记忆，可以同时包含"删除若干旧条目"和"新增一条"，两部分在一个事务里完成：要么都生效，要么都不生效。例如把"测试命令是 pytest"（#96）改成"测试命令是 make test"，就是一次写入：删除 #96，再新增一条。

  • 串行：服务端按作用域实例加分布式锁，同一个实例的写入（包括拆分主题的提交）一次只执行一个。服务端多副本部署时同样有效。
  • 先后：每次写入都带时间，由客户端给出，服务端落库时一并保存。以时间晚的为准：已经写入了 11 点的数据，10 点的同一件事再到达时就丢弃。

图 3　写入：同一作用域实例的写入串行执行；要删除的条目已被别的写入处理过时，按时间决定本次写入是作废还是继续

  • 取代关系：一次写入删除了 #96、新增了 #131，就记下"#96 被 #131 取代"。要删除的条目已经被取代过，就沿着这条关系找到它现在对应的有效条目再比较时间。如果它是被遗忘的（只删除、没有新增），就和那次遗忘的时间比较：遗忘更晚就丢弃本次写入，否则只做新增。
  • 只管"针对同一批旧条目"的先后：两次写入如果互相没看到对方，又都只做新增，两条会同时存在。读取时按时间以新的为准，下一次写入这个主题时由写入方清理（6.2）。
  • 时间由客户端给出，依赖各客户端的时钟基本一致。Atlas 各场景下时间取什么，见 6.4。

3.6 拆分主题

服务端不管大小上限（3.3），也就判断不了哪个主题该拆。什么时候拆由客户端按自己的上限决定；怎么拆（分几组、每组叫什么、条目归哪组）属于语义判断，也由客户端决定。Atlas 在会话后补记里做（4.5）。服务端只提供拆分操作，保证它和其他写入不冲突：

  • 一个事务提交：客户端给出分组（每组的编码、描述、扩展属性和条目编号），服务端加实例锁，新建子主题、移动条目、删除原主题，要么都生效，要么都不生效。
  • 提交时确认主题没变：客户端分组时看到的是主题在某一时刻的内容。提交时主题的版本号和客户端分组时看到的不一致（分组期间有新的写入），或者分组没有正好覆盖原主题的全部有效条目，服务端就拒绝这次拆分。
  • 只移动，不改写：条目的内容、编号、时间、来源都不变，只是换了所属主题。
  • 写入的目标主题已被拆掉：服务端拒绝这次写入，并返回当前的主题目录，由客户端重新选择主题。要删除的条目按编号定位，拆分后仍然有效。

3.7 数据权限

服务端默认不校验关联主键属于谁（3.2）。需要服务端把关的作用域，可以在管理平台打开数据权限开关：打开后，记忆服务按用户中心的数据权限，校验调用用户能不能访问这个实例；关闭时行为和现在一样。

图 4　数据权限：客户端建会话时请记忆服务登记实例归属，记忆服务在用户中心写入 Owner；之后每次读写，记忆服务按调用用户在用户中心的级别放行或拒绝

  • 实例就是用户中心里的一条数据：打开开关的作用域，对应用户中心里的一个数据编码，挂在记忆服务名下；作用域下的每个实例，是这个编码下的一条数据。级别沿用用户中心的只读 / 读写 / Owner。
  • 由记忆服务代为登记：用户中心只允许数据编码的所属应用登记和查询授权，所以客户端不直接调用用户中心，而是调用记忆服务的"登记实例归属"，显式给出实例（作用域编码 + 关联主键）和 Owner 用户；记忆服务去用户中心写入第一个 Owner。已登记的实例不再改动（用户中心规定已有授权的数据只能由 Owner 修改），直接返回成功。开关关闭的作用域，登记什么也不做。
  • "谁在访问"和"访问哪个实例"分开：实例仍由接口参数给出（3.2）；调用用户按内网身份传递的约定从请求里取。
  • 没登记的实例一律拒绝：用户中心里没有这条数据，普通用户对它没有任何权限。所以客户端要先登记，再读写。
  • 彻底删除实例时一并清理：用户删除某个项目或全部记忆、整个实例被删除时，记忆服务同时清理用户中心里这条数据的授权。
  • 用户中心不可用时拒绝：打开开关的作用域在无法校验时一律拒绝，不放行。

4. 客户端：Atlas 怎么存

4.1 Atlas 使用的作用域

作用域关联主键放什么判定口径
用户用户 uid身份、沟通偏好、工作习惯、个人在各技术栈上的偏好换一个项目仍然成立
用户项目uid + 项目编码这个人在本项目的命令、目录、规范、技术选型、决策只在这个项目里成立；拿不准时也放这里（选最窄的范围）
  • 关联主键由 Atlas 按当前会话确定：uid 取会话所属的用户（以数字员工身份运行的 Agent 也取使用者本人，否则同一个数字员工的所有使用者会共用一份用户记忆）；项目编码取会话关联的项目。Agent 和抽取模型都不能指定关联主键，工具参数里也没有这一项。
  • 没有关联项目的会话，只用用户作用域。
  • 两个作用域都打开数据权限开关（3.7）：用户的记忆只有本人能读写，服务端也会把关，不只靠 Atlas 传对关联主键。
  • 建会话时登记实例归属：创建会话时，Atlas 请记忆服务登记本会话用到的实例：用户实例，有关联项目时再加用户项目实例；Owner 是会话所属用户。会话中途换了项目，就登记新的用户项目实例。登记是幂等的，已登记的直接返回。
  • 调用用户取会话所属用户：Atlas 访问记忆服务时，调用用户一律取会话所属用户，和关联主键保持一致。权限类型是"以 Agent 为权限"的数字员工 Agent 也一样，否则数字员工对使用者的记忆没有权限。会话后补记在后台运行，也以会话所属用户的身份调用。
  • 登记失败不阻塞会话：用户中心或记忆服务不可用时，会话照常创建，本会话暂时不用记忆（不加载、不写入）；下一个 Run 开始时再登记。
  • 按项目编码、由项目成员共用的项目作用域，Atlas 本期不用（Q2）。
  • 项目要有稳定的编码：现在的"项目"是会话的工作区，每个新会话都不一样。Atlas 需要新增项目实体（带编码），建会话时关联项目；业务应用也可以在建会话时直接传入项目（Q1）。

4.2 主题怎么管

  • 先复用，再新建：主题目录本来就常驻在系统提示词里。写入前先从目录里选，都不合适才通过接口新建。
  • 命名和描述：编码写成"大类-细分"的形式，例如 编码-java、编码-js；描述写清楚收什么、不收什么。描述是 Agent 选主题、决定是否加载的唯一依据。
  • 建议的初始主题写在给 Agent 的写入指引里，不写死在代码里：
    • 用户作用域：身份与背景、沟通偏好、工作方式、编码。
    • 用户项目作用域：项目约定、项目决策、工作方式。
  • 常驻标记：建主题时决定，记在主题的扩展属性里。每次对话都用得上的（身份、沟通偏好、工作方式、项目约定）标为常驻，其余不标。
  • 大小上限：Atlas 自己定一个上限，写在给 Agent 的写入指引里。它是给 LLM 的软上限，超了也能写入，由会话后补记拆小。
  • 主题快满时：主题目录里能看到每个主题的当前大小（服务端给出），和 Atlas 的上限比较。写入方可以自己把它拆成两个更细的主题（例如"编码"拆成"编码-java"和"编码-js"），没来得及拆的，由会话后补记拆分（4.5）。

为什么两种都要：两者正好互补。

  • 过程中存：准确、即时、用户可控；短板是容易漏记，且依赖主模型是否主动去记。
  • 会话后补记：不容易漏记，不干扰主任务，能覆盖所有类型的 Agent，提示词改进后还能拿历史对话重跑；短板是有延迟，并且写入时用户不在场。

以过程中存为主、补记为辅：既保证明确的要求能当场生效，也能兜住漏记的部分。补记按会话执行，不按 Run 执行：能看到会话的完整过程，用户中途改口时只记最终说法；不会和对话中正在进行的写入冲突；调用 LLM 的次数也比现在"每个 Run 一次"少得多。

4.4 过程中存的流程

图 6　过程中存：Agent 先看完目标主题再判断，记忆服务把守并发与先后，用户能看到每一次写入

  • 写之前必须看过目标主题：本会话还没看过目标主题，或者看过之后主题的版本号变了（其他会话写入、会话后补记写入或拆分，见 5.5），"保存记忆"会先把该主题的最新条目返回给 Agent，Agent 判断后再保存。这样冲突判断总是基于最新、完整的内容。
  • 顺手清理：Agent 看完整个主题时，如果发现已有重复或过时的条目，可以在这次写入里一并删除。

4.5 会话后补记的流程

图 7　会话后补记：只处理新增内容，只补漏记的部分，结果用户可见、可撤销；最后把超限的主题拆小

  • 宁缺毋滥：补记时用户不在场，判断标准要比过程中存更严。只记有明确依据的内容，拿不准的就不记。
  • 时间取原消息的时间：补记写入的时间是它所依据的那条用户消息的时间，而不是补记执行的时间。这样补记即使晚到，也不会盖掉用户之后在别的会话里说的新情况（6.4）。
  • 不补 SubAgent 会话：那是 Agent 之间的对话，里面没有用户本人说的话。
  • 按进度处理：每次只处理上次补记之后新增的内容，同一段对话不会被重复处理。

拆分超限的主题是补记的最后一步：检查本会话相关的作用域实例（用户、用户项目）里超过 Atlas 上限（4.2）的主题，逐个拆小。抽取被跳过时也照常检查；主题不管是被 Agent、补记还是用户在管理界面写满的，都在这一步处理。

图 8　拆分超限的主题：怎么拆由 Atlas 决定，分组在锁外进行，不阻塞对话中的写入；记忆服务加锁提交，并确认主题在分组期间没有变化

  • 只移动，不合并、不删除：拆分只是重新归类。如果拆分时顺带合并或删除条目，就绕开了 6.3 的取代限制（补记不能推翻用户亲自写的）。重复和过时的条目，由写入方下次写入这个主题时清理（6.2）。
  • 子主题沿用常驻标记：原主题标为常驻，拆出来的子主题也标为常驻。
  • 拆不开的不拆：条目都是同一件事、分不出组时，保持原样并记录下来，供观察。
  • 提交被拒绝就放弃：分组期间主题有新的写入，或者另一个会话的补记已经把它拆了，记忆服务会拒绝这次拆分，本次不重试，下次补记再拆。

为什么放在补记里，而不是服务端后台：上限只有客户端知道，不同客户端、不同场景的上限可能不一样，服务端判断不了哪个主题超限；补记本来就在会话空闲后运行、本来就要调用 LLM；记忆服务不用为了拆分去理解条目内容、调用 LLM，保持"不关心存的是什么"；也不再需要后台定期扫描。代价是超限的主题要等到下一次补记才拆小，见 8.1。

4.6 写什么、不写什么（两条路径共用）

写不写
  • 用户明确说"记住……"
  • 长期有效的偏好、习惯、身份信息（包括用户没有明说、但反复体现出来的偏好，这是补记的重点）
  • 用户对 Agent 做法的纠正
  • 和用户确定下来的项目约定、决策（命令、目录、规范、选型）
  • 一次性的任务细节、寒暄
  • 临时性的说法，例如"这次先用 npm"
  • Agent 自己的推测、只是助手提出但用户没有采纳的建议
  • 文件、网页、工具输出里的内容
  • 敏感信息（健康、政治倾向等），除非用户主动要求
  • 作用域：换了项目仍然成立的写进用户作用域；只在本项目成立的写进用户项目作用域；拿不准就写用户项目（范围最窄）。会话没有关联项目时，只能写用户作用域。
  • 写法：一条只写一个事实，用陈述句，单独拿出来也能看懂，日期写成绝对日期。例如"2026-10 起 JS/TS 项目改用 bun"。
  • 控制主题大小：写入指引里告诉 Agent 主题的上限；接近上限时优先合并重复和过时的条目，其次再拆主题。

4.8 安全边界

  • 只认用户本人的话：两条路径都只根据用户本人在对话里说的话来写入。文件、网页、工具输出中要求修改记忆的内容，一律忽略。补记的输入里本来就不包含工具输出。
  • 关联主键由系统确定：写入哪个用户、哪个项目由 Atlas 按会话决定，Agent 和抽取模型都没法指定。记忆服务还会按数据权限再校验一次（3.7），但那是第二道防线，Atlas 这一侧仍然要守住。
  • 限制写入方和次数：SubAgent 不能写，它的会话也不会被补记；每轮、每次补记的写入次数都有上限。
  • 只做可恢复的操作：Agent 和抽取模型都没有彻底删除的能力，只能取代或遗忘，这些操作都可以恢复。
  • 可见可撤销：每次写入用户都能看到，并且可以撤销。

6.2 写入时的判定

图 12　冲突判定：只有同一作用域实例、同一主体、同一属性的记忆才可能互相取代；两条写入路径都用这一套规则

谁来判定做什么

为什么冲突不再"看不见"：旧方案里写入方只能看到检索出来的几条，相关的旧记忆没检索到，就发现不了冲突，只能靠后台整理事后补救。现在主题有大小上限，写入方能看到目标主题的全部条目，同一主题内的冲突在写入时就能发现。跨主题的冲突仍然可能漏掉，见 8.1。

Atlas 用条目的来源标签区分三种写入方。下面的规则保证：可信度低的写入方，不能推翻可信度高的。这是 Atlas 的规则，记忆服务只保存来源标签，不执行这条规则。

Agent（过程中存）✓

来源可信度从高到低依次为：用户亲自 → Agent 写入 → 会话后补记。

6.5 只取代，不彻底删除

图 13　取代链：旧条目不再被列出和加载，但保留在修订历史里，可以追溯、可以恢复

Agent 和抽取模型的"删除"只把条目从有效状态移到历史里，用户可以在管理界面查看它的演变过程，也可以恢复。用户彻底删除某条记忆时，它所在的整条取代链会一起删除。否则用户删掉"改用 bun"之后，旧的"用 pnpm"还会留在库里。

7. 用户控制

用户的操作效果
查看按作用域、项目、主题、来源、状态浏览；每条记忆都能看到出处和演变过程；可以预览在某个项目里会常驻哪些记忆
撤销对一次写入、补记、取代或遗忘做反向操作（4.7）
添加 / 更正来源记为"用户亲自"，补记不会改动这类记忆
恢复把已删除的条目恢复为有效
调整主题修改主题的描述和常驻标记；把条目移到别的主题
删除彻底删除，连同取代链和修订历史，不可恢复。可以按单条、按项目（删除对应的用户项目实例）或全部（删除该用户的用户实例和所有用户项目实例）删除
暂停暂停期间，两条写入路径都停止写入；已有的记忆照常常驻、照常可以加载（"暂停优于删除"）

这些操作只能由用户在 Atlas 的管理界面完成，Atlas 调用记忆服务提供的能力实现，不会作为工具开放给 Agent。影响常驻内容的操作，会在下一轮生效（5.3）。

8. 风险与待决问题

8.1 风险

风险应对
过程中存漏记由会话后补记兜底；同时在评测里统计"过程中存的漏记率"，用来改进对 Agent 的写入指引
补记记多了或记错了（写入时用户不在场）补记的标准比过程中存更严，拿不准就不写；补记写入的记忆可信度最低，不能推翻用户亲自写的，也不能推翻本会话刚写的（6.3）；下次会话开始时提示用户，可以撤销；把用户对补记结果的撤销率作为质量信号
Agent 没有加载该加载的主题主题目录常驻，描述写清楚用途；写入指引里提示"开始写代码前先加载相关的编码主题"；评测里统计漏加载率；必要时把主题标为常驻
不知道一件事在哪个主题没有语义检索，只能按描述去猜，或者逐个加载。数据量小时问题不大；如果评测显示问题明显，再考虑给记忆服务加关键词检索
跨主题的重复和冲突看不见一件事可能同时适合两个主题，例如"JS 项目用 bun"放在"编码-js"还是"工具偏好"。主题描述写清收什么、不收什么；写入时顺带看一眼描述相近的主题；剩下的靠用户更正
两次写入互相没看到对方，留下重复写入前按版本号检查并重新加载（4.4）；记忆服务按时间丢弃过时的写入（3.5）；仍然留下的，读取时新的优先，下次写入时清理
主题越来越多、越拆越细主题目录常驻，占用随主题数增长。建主题前先复用；接近上限时先合并、再拆分；用户可以在管理界面调整
主题拆不开同一件事的条目太多时，拆分无效。补记拆分时保持原样并记录下来；由写入方在写入时合并压缩
超限的主题要等到补记才拆主题在对话中超限后，要等会话空闲、补记执行时才拆小，期间主题偏大，加载时多占上下文；上限本来就是软上限，允许短时超出。用户在管理界面添加导致超限的，要等该用户（或该项目）下一个会话的补记
关联主键由调用方传入作用域没打开数据权限开关时，客户端传错了就会读写别人的数据。Atlas 按会话确定关联主键，Agent 不能指定（4.8），并且 Atlas 的作用域都打开了开关（3.7）。打开后仍然依赖内网身份传递：请求里的调用用户可以被伪造，在内网信任模型下接受这一点
用户中心不可用打开开关的作用域无法校验，一律拒绝。Atlas 把它当作记忆暂时不可用：会话照常进行，不加载、不写入记忆
每次读写多一次权限查询记忆服务可以短时缓存校验结果；代价是授权变更要过一会儿才生效
编码级授权能看到所有人的记忆用户中心里"全部 xx"这种编码级授权，会让被授权的人读写所有用户的记忆。只用于审计等特殊场景，默认不授
客户端时钟不一致时间先后依赖各客户端的时钟；部署环境统一做时间同步。只有"同一件事几乎同时写入"时才可能判错
过程中存写得太多每轮写入次数设上限；明确告诉 Agent 哪些不要写；把撤销率作为质量信号
提示词注入见 4.8；最后的兜底是每次写入都可见、可撤销
成本补记每个会话调用一次 LLM，太短或没有新内容的直接跳过；拆分只在有超限主题时才调用 LLM。总体比现在"每个 Run 抽取一次"更省

9. 留给详细设计的内容

方案确定后，在详细设计里展开以下内容：

9.1 服务端（记忆服务）

  • 存储选型与数据结构：作用域、主题、条目、修订历史和取代关系。
  • 组合关联主键（如 uid + 项目编码）的表示方式，以及按其中一部分列出实例（删除某个用户的全部数据时需要）。
  • 接口定义：登记实例归属；主题的创建、列出、读取、移动条目、拆分；写入；撤销、恢复、彻底删除。
  • 分布式锁的粒度与超时；时间的精度，以及时间相同时怎么处理。
  • 版本号的分配方式：按实例统一递增，还是每个主题各自递增。
  • 数据权限：作用域与用户中心数据编码的对应方式；实例在用户中心的数据标识（用户中心限 64 个字符，uid + 项目编码可能超长）；调用用户从哪个请求头取；校验结果的缓存时长。
  • 管理平台的作用域配置页面；服务的部署与鉴权接入。

9.2 客户端（Atlas）

  • 工具定义：加载主题、保存记忆、遗忘记忆；建主题是否单独做成工具。
  • 接入位置：常驻块在 Agent 运行链路的哪一步组装；是否需要中间件（初步结论是不需要，由装配层负责）。
  • 会话后补记：触发机制、处理进度的记录方式、抽取模型选型、失败重试；拆分超限主题的提示词，拆不开时怎么记录。
  • 助理类 Agent（ACP）的接入：会话开始时如何注入常驻块，记忆工具怎么提供。
  • 版本检查：会话版本表和常驻快照的存放位置，更新提示的格式。
  • 登记实例归属：失败后的重试；是否在 Atlas 侧记住已登记的实例，避免每次建会话都调用。
  • 项目实体与会话关联项目。
  • 各类阈值：主题大小上限、常驻总预算、写入次数上限、空闲时长。
  • 可观测与评测指标、迁移与分期、旧数据的清理。
