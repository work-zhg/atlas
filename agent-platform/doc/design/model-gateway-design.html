0. 方案概览

一句话：智能体和平台服务统一用 Anthropic 格式调网关的通用入口：模型的线路是哪种格式，网关就转成哪种，调用方不用按模型挑入口。另有 Anthropic、OpenAI 两个格式入口，给只会某一种格式的工具和知识库用：只走同格式的线路、原样转发、不转换，处理不了就报错。调用方只需要说明三件事：用哪个模型、要不要思考、发什么消息。至于这个模型的参数怎么写、哪个账号现在能用、失败了换哪条线路、费用怎么算，全部交给网关处理。网关不碰业务：它不写提示词，不跑智能体循环，不执行工具，也不会悄悄把一个模型换成另一个。

打个比方：网关就像公司的统一采购台。各部门只填一种标准采购单，写清要什么、要多少。采购台知道每家供应商的下单格式，也知道谁家便宜、谁家缺货；缺货时会换一家买同款，账记在提需求的部门头上。但它不会把你要的 A 牌换成 B 牌，换品牌只能由你自己决定。

图 1　智能体和平台服务只用 Anthropic 格式（通用入口），知识库和第三方工具可以用 OpenAI 格式；网关负责认 Key、整理参数、选线路、转发（格式相同就直通，只有通用入口转换）、记用量；配置来自模型平台

1. 背景与目标

现在，「模型之间有什么不同」这件事分散在每个调用方各自处理：

  • Atlas 的智能体引擎里按模型名写死了一串规则，例如：哪些模型能用自适应思考；哪个模型的思考关不掉，传「关闭」就会 400；哪些模型不接受思考力度；哪些模型一传温度就 400；思考关闭时力度不能超过多少。上下文长度这类能力，还另外存在 Atlas 自己的一张模型表里。
  • 知识库用的是另一种格式（OpenAI 格式），规则也要另写一份。
  • 新接一个模型，几个调用方都得跟着改，漏改一处就会出问题。比如会话标题在 MiniMax 上传了「关闭思考」，直接返回 400，结果所有标题都降级成了消息开头。
  • 转发交给了 LiteLLM。格式转换、换线路、限流冷却、用量怎么算，都按它的规则来。出了问题（比如思考内容、缓存标记在转换中丢了），我们只能等它修；流式回答开始后还能不能换线路、缓存命中怎么计价，这类规则我们也定不了。它只部署在集群内，个人 Key 在集群外用不了。它的配置还要由模型平台同步过去，两边各存一份。

目标

  • 调用方只说意图，不用管上游是哪种格式。模型之间的差异（参数写法、格式、能力）只在网关里处理一次。新接一个模型，调用方不用改代码。
  • 网关告诉调用方每个模型能做什么，调用方不再自己维护模型能力表。
  • 一个模型可以挂多个账号，失败时自动换，调用方感觉不到。同一个会话尽量留在同一个账号上，保住缓存命中。
  • 用量和费用按统一口径计算，可以按租户、Key、模型查询。
  • 个人 Key 能在集群外使用，比如 Claude Code、Cursor、脚本。
  • 平稳替换 LiteLLM：调用方不用换 Key，可以一个模型一个模型地切换，随时能切回去。

不做

  • 不自己发明请求格式（原因见第 2 节）。
  • 不碰业务逻辑：提示词、智能体循环、工具执行、上下文压缩、记忆、检索都留在调用方。
  • 不自动换模型：同一个模型的几条线路之间可以换，但不会换成另一个模型。
  • 不根据请求内容自动挑模型（智能路由）。
  • 不根据供应商给的「每分钟 token 数」提前排队，只在收到限流后让线路冷却一会儿。

2. 统一入口：调用方只说一种格式

调用方面对的是一套「标准接口」：一套模型名、一套参数含义、一套错误、一份能力清单。这就是网关提供的「自己的模型接口」。请求格式不重新发明，直接采用现成格式：智能体和平台服务统一用 Anthropic 格式调通用入口，知识库和第三方工具也可以用 OpenAI 格式入口。不管用哪种格式，上面这几样的含义都一样。

为什么不自己发明格式

自己发明一种格式采用现成格式
调用方的代码每种语言都要自己写客户端，流式解析也要自己写官方 SDK、LangChain 直接能用，Atlas 现有代码不用改
现成工具Claude Code、Cursor 只认现成格式，接不进来。最后还得另开一个现成格式的入口，等于维护两套直接接入
供应商出了新功能每个新功能都要先在自己的格式里设计字段格式相同的上游原样转发，新功能马上能用
能得到的好处字段完全按自己的想法定这点同样做得到：模型名、参数含义、错误、能力清单都由网关统一定义（见下表）

为什么智能体统一用 Anthropic 格式

  • 它表达得更细。一次回答由一块一块的内容组成：文字块、思考块、工具调用块。思考块带签名，内容块上可以打缓存标记。OpenAI 格式里没有这些对应的东西。从细的格式转成粗的格式，会丢掉什么是确定的，可以事先写清楚；从粗的转成细的，缺的信息补不回来（图 2）。所以需要转换时，只从它往外转，不往回转。
  • 现有调用方已经在用它。Atlas 原生智能体、Claude Code 用的都是这种格式。国内主流供应商（DeepSeek、MiniMax、Kimi、智谱）也都提供这种格式的接口，所以大部分调用可以原样转发，不用转换。
  • 但请求不必先转成它。请求和上游格式相同时，转一圈只会白白丢东西：OpenAI 格式独有的结构化输出、logprobs 这类字段，在 Anthropic 格式里没有位置。所以格式相同一律直通（第 5 节）。

图 2　转换的中转选表达更细的那一种：往粗的格式转，丢什么事先就知道；反过来，丢掉的补不回来

调用方只需要知道的几件事

统一的东西说明
模型名租户登记的名字。调用方不知道背后是哪个供应商、哪个账号
参数含义思考（开 / 关 / 自动）、思考力度（低 / 中 / 高……）、温度、最大输出，都按统一的含义传。某个模型具体怎么写，由网关决定（第 4 节）
能力清单网关列出这把 Key 能用的模型，以及每个模型的能力。调用方据此显示和挑选模型（第 4 节）
会话标识调用方带上会话标识，网关据此把同一个会话留在同一条线路上（第 6 节）。不带就按 Key 来算
错误一套错误类别，说清是谁的问题、该不该重试、对用户怎么说（第 9 节）
用量统一成四项：输入、缓存写入、缓存命中、输出（第 8 节）

入口

  • 对话 · 通用：按 Anthropic 格式传。Atlas 原生智能体、CLI 智能体和平台服务都用它，Claude Code 这类个人工具也推荐用它。账号有 Anthropic 格式的地址就直通，没有就转成它有的格式（OpenAI、Google）。调用方不用关心模型背后是哪种格式，也不用写「这个模型该走哪个入口」的判断。
  • 对话 · Anthropic 格式、OpenAI 格式：给只会某一种格式、或者要用这种格式独有字段的调用方：Cursor、OpenAI SDK、一些脚本，以及知识库（OpenAI 格式）。只走登记了同格式地址的线路，原样转发，不转换；模型没有这种格式的线路就直接报错，提示改用通用入口。认 Key、整理参数、选线路这些步骤和通用入口共用一套。知识库因此不用改格式，但它用到的模型要有 OpenAI 格式的线路。
  • 向量、重排：采用业界通用的格式。向量用 OpenAI 格式；重排用「一个问题加一组文档，返回每个文档的分数」这种通用格式。各家供应商在这里差别不大，基本原样转发。模型要标明类型（对话、向量、重排），各入口只认对应类型的模型。
  • 模型清单：列出这把 Key 能用的模型和它们的能力。

3. 一次调用怎么走

图 3　一次调用的八步：前四步任何一步不通过都直接拒绝，不会碰到供应商；第 ⑥ 步在提交点之前失败，就换下一条线路

  • 前四步只读内存里的配置和几个实例共用的状态，不查数据库，也不连供应商。网关自己增加的耗时在毫秒级。
  • 前五步只看读写器读出的共同信息，不关心请求是哪种格式，所以两个对话入口共用一套。
  • 第 ④ 步是把模型差异收进网关的地方，见第 4 节。
  • 第 ⑤ 步和第 ⑥ 步可能来回走好几次：一条线路失败，就换下一条，直到成功、线路用完，或者回答已经开始输出（第 6 节）。
  • 第 ⑧ 步在回答结束后进行，写记录不会让调用方多等。

4. 模型差异收进网关：能力与参数

模型之间的差异分成两类。一类是能做什么（能力），这是对调用方的承诺。另一类是同一件事怎么写（参数写法），这是网关自己的事，调用方不用管。

4.1 能力：对调用方的承诺

  • 每个模型都记着这几项：能不能看图；能不能思考，思考能不能关；能不能调工具；上下文多长；最多输出多少。
  • 能力从哪来：网关自带一份常见上游模型的能力和参数规则，随网关版本一起更新。登记模型时，按线路上的供应商和上游模型名自动带出，租户管理员可以修改。自部署的模型没有预置，需要手动填写。没有预置、也没人填写的能力，一律按「不支持」处理。
  • 每条线路都要做到模型承诺的能力：加线路时检查，做不到的不让加。例如，承诺能看图的模型，不能挂一条不能看图的备用线路。这样换线路时能力不会缩水。
  • 调用方从模型清单里拿能力：Atlas 编辑智能体时，按能力显示和过滤模型，比如开了浏览器的智能体只能选能看图的模型。上下文压缩何时触发，也按清单里的上下文长度来算。Atlas 不再自己存一份能力表。

4.2 参数：同一个意思，不同的写法

调用方按统一的含义传参数，网关按这个模型的规则，选择下面三种处理方式之一。改动由读写器直接做在请求原来的格式上，不需要先转换格式。

处理方式什么时候用例子
去掉不传不传也不影响回答对不对某些模型显式传温度会 400，就不传温度；不支持思考力度的模型，不传力度；思考关不掉的模型收到「关闭思考」，就不传这个参数
换一种写法这个上游有另一种写法表达同一个意思「思考：自动」在支持自适应思考的模型上传自适应，在只支持固定额度的模型上传一个固定额度；「最大输出」超过模型上限时，改成上限
拒绝去掉会让结果出错，而调用方还以为一切正常给不能看图的模型发图片、给不能调工具的模型发工具、输入超过上下文长度：直接返回 400，说清缺什么

最后一类绝不能悄悄去掉。模型看不到图片，也会照样给出回答，调用方根本发现不了问题。

图 4　同一个请求发给三个模型：能去掉的去掉，能换写法的换写法，会让结果出错的直接拒绝

思考关不掉的模型，会在模型清单里标明「思考关不掉」。会话标题这类只要很短回答的系统功能，选模型时应该避开这类模型。

4.3 历史里的思考内容

智能体每一轮都会把前面的对话再发一遍，其中也包括模型之前的思考块。各家对历史里的思考内容要求不一样：Anthropic 在工具调用过程中，要求把带签名的思考块原样带回；其他供应商有的要求带回，有的带回了反而报错（以各家文档和实测为准）。网关的规则是：

  • 网关在回答里给每个思考块留一个来源标记，记下它来自哪个上游模型。调用方原样保存、原样带回就行，不用理解这个标记。
  • 下一轮带回时，如果发给的是同一个上游模型，就按它的要求带回或者去掉；如果发给别的上游（比如换了线路），就去掉历史里的思考块。只去掉思考，正文和工具调用都保留。

5. 格式：相同就直通，只有通用入口转换

每个请求涉及两种格式：调用方用的（入口格式），和选中的账号用的（上游格式）。两者相同就直通：原样转发，只改模型名和第 4 节说的个别参数；网关不认识的字段也原样带过去，供应商出了新功能马上能用。两者不同时，只有通用入口转换。

格式入口不转换：选线路之前就只留同格式的线路，模型一条都没有就直接报错。不先试再失败，是为了不把「格式不对」当成线路故障，把好好的线路冷却掉。

入口上游格式怎么处理例子
通用Anthropic直通Atlas 调 Anthropic 官方，或 DeepSeek、MiniMax、Kimi、智谱的 Anthropic 接口
通用OpenAI转换Atlas 调自部署的 vLLM、通义千问
通用Google转换调 Gemini
Anthropic 格式Anthropic直通只想走 Anthropic 接口的脚本
OpenAI 格式OpenAI直通Cursor 调自部署的 vLLM；知识库
Anthropic 格式 / OpenAI 格式其他格式不转换，这条线路不走；一条同格式的都没有就报错Cursor 调只有 Anthropic 接口的模型

读写器和转换器

部件有几个做什么
读写器每种格式一个从请求里读出共同信息（模型名、会话标识、思考 / 温度 / 最大输出、有没有图片和工具、大致长度），按第 4 节的规则直接在原格式上改参数；从回答里读出用量、第一段内容和错误。认 Key、整理参数、选线路、记用量这些共用步骤只跟它打交道，所以只写一份
转换器Anthropic → OpenAI、Anthropic → Google 各一个，只有通用入口用账号没有 Anthropic 格式的地址时，把整个请求转过去，再把回答（包括流式回答的每一段）转回来

读写器只碰少数几个字段，比一整套转换小得多。转换器都从 Anthropic 格式往外转：从表达更细的格式出发，丢什么事先就知道（第 2 节）；不往回转，也就没有两跳。

账号可以同时登记两种格式（可选）

DeepSeek、Kimi、智谱这类供应商两种格式都提供，同一把密钥通常两种都能用。账号可以同时登记两个地址；选好线路后，网关挑和入口格式相同的那个地址，这样各个入口打到这类供应商都是直通。只登记了一种格式的账号，另一种格式入口的请求不走它；通用入口照样能用（需要时转换）。

供应商方言：同一种格式，各家写法还不一样

很多供应商说自己兼容 Anthropic 或 OpenAI 格式，但细节各有各的写法，只按格式处理会出错。这些差异叫「供应商方言」。模型之间的差异因此分三层处理：

  • 不给每个供应商写一整套适配：那样的数量是「供应商 × 格式」，大部分代码重复；方言只写和标准不一样的那几处。
  • 各家具体的写法以各家文档和实测为准，补进预置的数据和方言里。

流式回答怎么转

两种格式的流式回答，切段的方式完全不同：OpenAI 格式是一个个「增量」，每段里有什么就填什么；Anthropic 格式要求先声明「开始一个文字块」，再一段段发内容，最后「关上这个块」。转换器就像一个小记事本，记着「现在在写哪一块」。内容类型一变（比如文字写完了、开始调工具），就先把旧块关上，再开一个新块。

图 6　流式回答的转换：转换器记着「现在在写哪一块」，内容类型一变，就关上旧块、开新块；停止原因和用量在最后一段给出

OpenAI 格式的上游，有的默认不在流式回答里给用量。网关在发请求时会要求它在最后一段带上用量；直通时如果调用方自己没要，网关读完这一段的用量后不再转给调用方。

6. 选线路与换线路

6.1 按会话选线路

  • 一个模型的线路有优先级和权重。先用优先级数字小的；同一优先级有几条线路时，按权重分配。
  • 分配的单位是会话，不是单次请求。同一个会话的每一轮都落在同一条线路上，原因是缓存：智能体每一轮都会把前面几万字的对话再发一遍，供应商对重复的开头只收一成左右的钱，算得也更快。但缓存只在同一个账号内有效，如果随机分到别的账号，这部分就要按原价重算一遍（算例见第 8 节）。
  • 怎么做到：用会话标识算出一个固定的落点（加权的一致性哈希），所以不需要在任何地方记「哪个会话对应哪条线路」。增加或减少线路时，只有原来落在变动线路上的会话会挪走。
  • 不带会话标识的调用（个人工具、脚本）按 Key 来算落点。

图 7　按会话分配线路：平时同一个会话一直走同一条线路，缓存能命中；线路不可用时才挪走，先挪到同一优先级的线路，再挪到下一优先级

6.2 什么时候换线路

上游的失败先由供应商方言归成统一的种类（第 5 节），线路按种类决定，不直接看状态码：同一个状态码在不同供应商那里意思不同。

失败的种类常见的样子算谁的问题怎么办
请求有误400调用方（或网关转换出错）不换，原样返回，带上供应商的说明
限流429这条线路换下一条。这条线路冷却：供应商说了等多久就等多久，没说就等 1 分钟
过载、服务出错、连不上、等不到第一个字5xx、Anthropic 的 529、超时这条线路换下一条；这条线路冷却 1 分钟
密钥失效、余额不足401、402；OpenAI 额度用完是 429 加 insufficient_quota整个账号换下一条，并把账号标成异常，用到它的线路都跳过。平台每 5 分钟检查一次：能查余额的查余额，其余的发一个 1 token 的请求试试，恢复了就自动解除异常
  • 冷却、异常这些状态，所有网关实例共用。一个实例撞上限流，其他实例马上都知道，不会每个实例各撞一次。
  • 全部线路都在冷却时，不直接拒绝，而是试冷却最早结束的那条。全部线路都异常或停用时，直接返回「没有可用线路」，不再打到供应商。
  • 只在同一个模型的线路之间换，不会换成别的模型。
  • 重试只在网关做一层。网关换过线路仍然失败时，会在响应里告诉调用方的 SDK 不要再自动重试（官方 SDK 认这个标记）。否则 SDK 自己再重试 3 次，每次网关又换 3 条线路，一次失败就会被放大成十几次上游请求。
  • 非流式请求超时后也会换线路。但上游可能其实已经算完了，这时会付两次钱。两次尝试都会写进调用记录。

6.3 回答开始输出后就不再换（提交点）

流式回答一旦发给调用方，就收不回来了。所以网关设了一个「提交点」：在向调用方写出第一段内容之前，都可以换线路；写出之后就不再换。

  • 提交点不是「上游返回了 200」。有的供应商会先返回 200，紧接着在流里发一个「过载」错误。网关会先压住上游开头那几段不含内容的数据（比如「消息开始」），等第一段真正的内容（文字、思考或工具调用）到了才提交。在这之前收到错误，照样换线路，调用方什么也看不到。
  • 压着的这段时间里，网关给调用方发不含内容的保活注释。流式协议规定接收方会忽略这种注释，这样可以防止连接因为太久没动静，被中间的代理断开。
  • 提交之后上游出错，网关在流里发一个错误，结束这次回答，调用记录标为「中途中断」。调用方按自己的规则处理，比如 Atlas 会让这一轮失败并给出提示。

图 8　提交点是「第一段内容到了」，而不是「上游返回了 200」：之前出的错调用方看不到，之后出的错只能在流里报告

7. 流式回答与超时

  • 只有两种超时，都不限制总时长：
    • 等第一个字：从发出请求到第一段内容到达。上下文很长或者冷启动的模型，可能要好几分钟才出第一个字（实测见过近 3 分钟），所以默认值给得很长，也可以按账号单独调整。
    • 两段之间：已经开始输出后，多久没有新内容就算卡住了。
    • 不设「一次回答最多多长时间」：只要还在持续输出，就一直等下去。
  • 调用方断开时（用户点了停止，或者调用方进程退出），网关立刻断开上游，不让供应商继续生成、继续计费。
  • 回答一段一段直接转发。网关自己、以及它前面的反向代理都不攒批发送。
  • 网关发版时，旧实例先停止接收新请求，等手上的回答都结束再退出。等待时间有上限，发版不能无限期地等；超过上限的连接会被断开，调用方按「中途中断」处理。
  • 流式回答不经过任何中继：网关读一段、写一段，在同一个请求里直接转发，中间不放无限长的队列。调用方读得慢，网关写就会等，读上游也跟着慢下来，压力一路传回供应商；内存里最多只压着提交点前的那几段。中继要解决的是「产出事件的和看事件的不在同一个请求里、看的人断了还要能续看」。模型调用不是这样：一个回答只有一个调用方，调用方断了就该停，两种格式也都不支持续传。能恢复的能力放在上一层：网关报「中途中断」，由调用方（比如 Atlas）决定重跑这一轮。

8. 用量与费用

8.1 统一成四项

  • 四项是：输入（没命中缓存的部分）、缓存写入、缓存命中、输出（包含思考）。
  • 两种格式的统计口径不同，转换时最容易算错：Anthropic 格式的「输入」不包含缓存部分，缓存写入、缓存命中另外列出；OpenAI 格式的「输入」包含缓存命中的部分。
  • 同一种格式里，有的供应商还用自己的字段：比如 DeepSeek 的 OpenAI 格式接口把缓存命中放在自己的字段里（图 5），由供应商方言换算成四项。
  • 一律以供应商回答里给出的数字为准，网关不自己数 token。

图 9　算例：两种格式报上来的用量先统一成四项，再算钱；缓存没命中、或者口径弄错，费用都会差出好几倍

8.2 价格

  • 价格挂在模型上：对内统一价，人民币，按每百万 token 计。不管走哪条线路，都按这个价格算钱；不填就不计费（比如自部署的模型）。
  • 缓存写入的数量单独记录，但按输入价算钱。
  • 每条调用记录都存下当时的单价。以后改价，不影响已经记下的费用。

8.3 用量没拿全的时候

  • 调用方中途断开，或者回答中途出错时，最后一段（带用量的那一段）就收不到了。
  • Anthropic 格式的上游，在回答一开始就会给出输入用量，只需要估算输出。OpenAI 格式的上游，用量要等最后一段才给，输入和输出都得估算。估算按已经收到的内容长度来算，调用记录里标为「估算」。

8.4 Key 的限额

  • 月预算（monthly_budget）：每次调用前，先看「本月已花 < 月预算」才放行；调用结束后，再把这次的费用加上去。
  • 5 小时 / 24 小时滑动窗口费用（budget_5h / budget_24h）：统一按费用（元）计量，与月预算共用同一套模型单价折算，避免不同价位模型按 token 计数失衡；满足 budget_5h <= budget_24h。网关在 Redis 单 Hash（modelgw:spend_win:{key_uuid}）中按 5 分钟一桶（5h=60 桶、24h=288 桶、25h TTL）以整型微元（1 元=106 微元）HINCRBY 累加，消除整点固定窗口的双倍突发毛刺与浮点漂移；单条 Lua 脚本一次往返完成过期桶清理、双窗口求和，并在超限时按最老有效桶滑出窗口的时刻反算精确 Retry-After。
  • 管理员硬上限约束：客户端 Key 的所有限额仅模型管理员可配置；个人 Key 上管理员设定的 5h/24h 窗口上限同步记入 admin_budget_caps 作为硬上限，员工本人可向下收紧或在不高于管理员硬上限内调整，不能调高或清除。
  • 全部费用预算均为软上限，且先判预算再扣 RPM：并发放行的最后一批请求可能略超上限（不预占额度，防长对话锁死配额）；任何费用预算超限或本地能力校验不通过均直接拒绝，不白白消耗该 Key 的每分钟请求数（RPM）。
  • Redis 重启或首次开启自愈：月花费键缺失或滑动窗口 _init 哨兵缺失时，网关按 Key 单飞从平台库 gw_model_call（命中 ix_gw_model_call_key_time 与月分区裁剪）聚合当月花费或近 24 小时 5 分钟分桶，用 SET NX / Lua HSETNX 懒回填至 Redis。
  • 每分钟请求数（rpm）：所有网关实例共用 Redis Lua 原子计数。

9. 错误统一

网关按「是谁的问题、能不能换线路、要不要重试」把错误分成几类，用调用方入口的格式返回，并带上类别和一句能直接给用户看的话。调用方按类别处理就行，不用去认识每个供应商的报错。

类别例子换线路返回给用户的话
Key 无效不存在、已停用、已过期—401Key 失效了（附停用原因）
不能用这个模型模型不在这把 Key 里、授权已收回、模型已停用—403没有权限用这个模型 / 这个模型已停用
请求超出能力给不能看图的模型发图片、输入超过上下文—400说清缺什么，比如「这个模型不能看图」
模型没有这种格式的线路用格式入口调一个只有别的格式线路的模型—400这个接口不转换格式，请改用通用入口
请求有误上游返回 400不换400，附上游说明原样显示
Key 限额用完月预算、5h/24h 滑动窗口费用、每分钟请求数—429说明是哪个限额、预计多久后恢复（附 Retry-After）

  • 给用户的话和 Atlas 现在的规则保持一致：处理不了的只说「系统忙不过来了」；限流、余额这类问题提示换个模型。
  • 「Key 限额用完」和「模型繁忙」都返回 429，但类别不同：前者换模型也没用，后者换个模型就能用。调用方要按类别给出不同的提示。
  • 供应商返回的 402（余额不足）不原样转给调用方：充值是租户账号的事，不是调用方能解决的问题。

10. 租户与安全

  • 账号、模型、线路、Key、调用记录都属于租户。Key 属于哪个租户，就只在那个租户的模型里找；模型名也只要求在租户内不重复。这一点和多租户隔离方案一致。
  • 平台服务替租户调模型时，用该租户的服务 Key、选该租户的模型。平台服务指会话标题、判断器、记忆补记、知识库向量这类功能。
  • 网关自带的能力和参数规则属于产品知识，不归任何租户，所有租户共用。
  • Key 怎么存：个人 Key 只存摘要（哈希），原文只在创建时显示一次；客户端 Key 加密保存，因为应用需要取回原文。Key 是随机生成的长字符串，用普通摘要就够了，不需要慢哈希：每个请求都要验一次 Key，慢哈希会拖慢每一次调用。
  • 账号密钥加密保存，界面上只显示末 4 位。
  • 上游地址由租户自己填，网关替它去连接，所以要防止被利用去访问平台内部：登记时检查一次，地址不能指向平台内部；每次真正连接前，按解析出来的 IP 再检查一次，防止域名先指向外网、事后又改成指向内网。
  • 出网：海外供应商经出网代理访问，代理地址由平台统一设置。
  • 个人 Key 可以在集群外使用：网关在 Atlas 同一个域名下，只开放调用和模型清单，不开放任何管理功能。管理功能都在模型平台里，需要登录。
  • Key 停用或删除后，几秒内所有网关实例都会生效。
  • 调用记录默认不存请求和回答的内容：里面可能有敏感信息，截图也很大。记录只存第 11 节列出的那些项。

11. 调用记录

  • 每次调用写一条记录，包括：时间、租户、Key、模型、会话；走过哪些线路，每次尝试的结果和原因；最终状态和错误类别；第一个字用了多久、总共用了多久；四项用量、费用、是否估算；去掉了哪些不认识的字段。
  • 写记录不耽误回答：记录先放进内存里的队列，再批量写入。数据库暂时写不进去时先攒着；攒满了就丢掉最旧的，并记下丢了多少条。
  • 谁能看：租户管理员看本租户的记录，个人看自己 Key 的记录。运营中心只看各租户的汇总数字，看不到内容。这一点和多租户隔离方案一致。
  • 网关自身的指标：每个模型、每条线路的第一个字用时、输出速度、错误率、换线路次数、缓存命中率。线路冷却、账号异常时，通知模型管理员。
  • 自研网关全面接管前，必须先有调用记录。过渡时要靠它对比新旧两条路的结果（第 13 节）。

12. 网关自身的可靠性

  • 网关是所有模型调用的必经之路，所以要部署多个实例，实例本身不存状态。任何一个实例挂了，其他实例接着服务。
  • 配置放在内存里。网关把账号、模型、线路、Key 都放在内存里。平台每改一次配置，就把配置版本号加一；网关处理每个请求时顺手看一眼版本号（放在几个实例共用的状态里，读一次很快），变了才重新加载。这样既能做到「保存后下一次请求就生效」，平时又不用查数据库。
  • 网关自己增加的耗时很少：前四步只读内存和共用状态。回答内容也不逐段解析，只在需要的时候才看（判断提交点、取用量、做格式转换）。
出问题的依赖网关怎么办
模型平台的数据库用内存里最后一份配置继续服务；新改的配置要等数据库恢复后才生效
几个实例共用的状态冷却、异常改由每个实例自己记；每分钟请求数暂时不限，不因为计数出问题而挡住业务；月预算与 5h/24h 滑动窗口按本实例最后一次观测到的花费/分桶快照判断
调用记录的数据库先攒着，恢复后补写（第 11 节）
某个供应商换线路（第 6 节）

13. 从 LiteLLM 过渡

图 10　过渡三步：网关先接管入口，这时 LiteLLM 退成网关后面的一个账号；再逐个模型直连；最后下线 LiteLLM。每个模型随时可以把线路改回 LiteLLM

  • 第一步：网关和新的模型平台一起上线，网关接管入口。
    • 账号、模型、线路、Key 都改在模型平台上管理，不再同步给 LiteLLM。
    • 调用方的模型地址改成指向网关，由网关认 Key、记用量。已有的 Key 原样能用，调用方不用换 Key。
    • 每个已有模型先只有一条线路，指向 LiteLLM（把 LiteLLM 当成一个 Anthropic 格式的账号），所以行为和原来一样。
    • 知识库取 Key 要带租户，等它按租户改造后再切；切之前照旧直连 LiteLLM，它的 Key 在 LiteLLM 里本来就有。
    • 网关接管入口后，个人 Key 就能在集群外使用了，Anthropic 格式（比如 Claude Code）和 OpenAI 格式（比如 Cursor）都行。
  • 第二步：模型逐个切直连。逐个模型把线路换成直连供应商的账号，对比调用记录里的错误率、第一个字用时和费用。哪个模型有问题，就把它的线路改回 LiteLLM。
  • 第三步：全部模型都直连后，下线 LiteLLM。调用方去掉自己按模型写的参数规则和模型能力表，改成只传意图，能力从网关的模型清单里取。
  • 退回：平时按模型退回，把线路改回 LiteLLM。整体退回是把调用方的地址改回 LiteLLM，只对切换前就有的 Key 有效（之后新建、重置的 Key 不在 LiteLLM 里），所以只作切换当天的应急手段。
