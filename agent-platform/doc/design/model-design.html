1. 背景与目标

1.1 现状

现状带来的负担
两层网关：自研模型网关在前，按 Key 认人、按用户中心判权、计量、记访问日志；Higress 在后，转发供应商、多上游回退、协议转换每次调用多经过一个自研服务，它的可用性、性能、协议兼容都要自己保证；协议转换放在 Higress 上，已知会丢掉思考内容
判权在调用路径上：每次调用都要确认主体能用这个模型依赖用户中心实时可用，需要缓存和降级规则；用户中心出问题直接影响对话
访问日志、用量、价目、额度、告警都是自研这些能力 LiteLLM 已经现成提供
标题、记忆补记、知识库按「平台用途」放行判权规则里的特例，不按主体管
模型按智能体的权限类型判：以人为权限按使用者，以 Agent 为权限按数字员工同一个智能体换个使用者，能用的模型就不同；数字员工要在用户中心单独被授权模型

1.2 目标

  • 网关用成熟实现：LiteLLM 负责路由、协议、调用日志、计费、预算限流，不再自研。
  • 平台只管配置：有哪些模型、谁能选、每把 Key 能用哪些。平台不在调用路径上，平台故障不影响已经在进行的调用。
  • 两类 Key 覆盖两类调用方：人用用户 Key；应用里的对象（智能体）和应用自己的服务（会话标题、记忆补记、知识库）用客户端 Key，智能体的 Key 生命周期跟着智能体走。
  • 公有、私有两档：常用模型登记为公有，不用逐个授权；贵的、受限的模型登记为私有，按用户、部门授权。
  • 智能体对所有使用者一致：智能体能用哪些模型，只由它自己的 Key 决定。

1.3 非目标

  • 平台不记调用日志、不统计花费、不设额度：在 LiteLLM 里看、在 LiteLLM 里配。
  • 不做模型能力目录和能力探测：平台不区分对话、嵌入、重排，也不登记工具调用、视觉、思考等能力。
  • 不做模型别名、自动升级、跨模型回退。同一个模型名有多个部署时，部署之间的重试由 LiteLLM 负责。
  • Key 不过期，不发短期令牌。

2. 分工：模型管理平台、LiteLLM、用户中心、应用

2.1 组件分工

组件负责不负责
模型管理平台登记模型（公有 / 私有）；私有模型授权的入口；用户 Key 与客户端 Key；把模型和 Key 同步到 LiteLLM；给应用提供「取 Key 和可用模型」转发请求；调用日志；花费；预算限流
LiteLLM模型路由；OpenAI 兼容与 Anthropic Messages 两种入口；保存供应商凭据；每次调用校验 Key 未停用、模型在 Key 的可用模型里；调用日志、花费、预算限流谁能选哪些模型；Key 属于谁
用户中心组织架构；管理员角色；私有模型的数据权限（用户、部门、含下级）—
Atlas建、删智能体时创建、删除客户端 Key；编辑时取可用模型；运行时取 Key 直连 LiteLLM判断智能体能用哪些模型
知识库按部署配置取管理员事先建好的服务级客户端 Key；入库、检索时带着它直连 LiteLLM同上

2.2 为什么用 LiteLLM

  • 同时提供 OpenAI 兼容和 Anthropic Messages 两种入口，能接主流供应商和 vLLM 等自部署服务。
  • 它的 Key（虚拟 Key）自带「能用哪些模型」和停用状态，每次调用由它校验；预算、限流也挂在 Key 上。
  • 调用日志、按 Key 的花费统计、管理界面都是现成的。

2.3 平台为什么不在调用路径上

  • 校验已经在 LiteLLM：平台把「这把 Key 能用哪些模型、是否停用」算好同步过去，调用时不必再问平台。
  • 平台故障影响面小：只影响配置变更和新取 Key。Atlas 取不到时沿用上次取到的 Key（7.3），旧 Key 是否还有效由 LiteLLM 判断。
  • 代价：授权、分配的变化要同步到 LiteLLM 才生效；同步失败靠重试和定期对账补齐（第 6 章）。

2.4 LiteLLM 管理界面的边界

  • 管理员用它查调用日志、花费，按 Key 配预算和限流。
  • 模型和 Key 的新增、修改走平台。在 LiteLLM 里直接配置的模型，平台只读展示，「纳入平台」后才能放进 Key（3.3）。
  • 不在 LiteLLM 里直接建 Key：那样的 Key 不归平台管，对账时会告警（6.3）。

3. 模型

3.1 登记什么

信息存在哪说明
显示名称、描述平台给人看
供应商平台、LiteLLM决定 LiteLLM 怎么调；Atlas 也按它选协议（7.4）
模型名平台、LiteLLM供应商侧的模型名，同时就是调用时传的模型名。登记后不能改；平台内不能重名，包括 LiteLLM 里直接配置的
可见性平台公有 / 私有，登记时默认私有（3.4）
API 地址、供应商凭据只在 LiteLLM凭据由 LiteLLM 加密保存，平台不落库；编辑时留空表示不改
上下文窗口、最大输出、价格LiteLLM价格供 LiteLLM 计费
授权用户中心只有私有模型有（第 4 章）

3.2 登记流程

图 1　登记模型：先在 LiteLLM 登记，成功后再写平台记录和用户中心；后两步失败就撤回 LiteLLM 里的登记，两边不留半条

3.3 模型列表：平台登记与 LiteLLM 直配合并

平台记录和 LiteLLM 里的模型按 LiteLLM 的模型标识对应，合并成一张列表。LiteLLM 里同一个模型名的多个部署合并成一行。

情况状态能做什么
平台登记，LiteLLM 里也有可调用编辑、删除；私有的可以授权
平台登记，LiteLLM 里找不到（例如在 LiteLLM 界面里被删了）LiteLLM 中缺失不能调用，也不算进任何 Key 的有效模型。管理员可以重新登记（凭据要重新填，可见性和授权不变），或删除
LiteLLM 里有，平台没登记（直配）只读不能授权、不能放进 Key。「纳入平台」：补平台记录、在用户中心登记数据对象，不改 LiteLLM

3.4 公有与私有

  • 公有：不判权，所有人都能选进自己的用户 Key，普通用户的模型列表里都能看到。
  • 私有：授权给用户或部门后才能选、才能看到。
  • 公有只表示「谁都能选」，不会自动进入任何 Key。新登记的公有模型不会出现在已有的 Key 里。
  • 登记时默认私有：漏选可见性时，结果是「没人能用」而不是「所有人都能用」。
  • 切换可见性：公有改私有，没被授权的人的用户 Key 里这个模型随之失效；私有改公有，所有人可选，原有授权保留但不再起作用。两种切换都不影响客户端 Key。

3.5 编辑与删除

  • 编辑：显示名称、供应商、描述、可见性、地址、凭据、规格价格都能改，模型名不能改。改模型名等于换了调用方要传的名字，应当登记一个新模型。
  • 删除：LiteLLM 里的模型、平台记录、用户中心的数据对象和授权一起删除，并从所有 Key 里去掉（第 6 章）。

4. 私有模型的授权

4.1 授权怎么表达

  • 每个平台登记的模型在用户中心是一条数据（数据编码 Model），公有模型也登记，改成私有时不用补。
  • 级别只用一个：使用。授给用户或部门，部门可以选「含下级部门」。
  • 一个人能用某个私有模型 = 授给本人，或授给他所在的部门，或授给他上级部门且含下级。
  • 公有模型不写授权。

4.2 管理员

  • 能不能做管理操作由角色决定：登记、编辑、删除模型，纳入平台，设公有 / 私有，授权，给客户端 Key 分配模型。
  • 能用哪些模型由数据权限决定：管理员持有「全部模型 · Owner」这条数据编码级授权，能用、能分配、能授权全部模型；不在单个模型上写 Owner。

4.3 授权管什么、不管什么

  • 管：用户 Key 能选哪些私有模型；普通用户在模型列表里能看到哪些私有模型。
  • 不管客户端 Key：客户端 Key 由管理员直接分配模型，公有私有都行，不看智能体使用者的授权。所以，没被授权某个私有模型的人，可以通过开了这个模型的智能体用到它；给哪个智能体开哪个模型，由管理员决定。

4.4 权限矩阵

操作管理员普通用户应用（Atlas、知识库）
查看模型全部公有 + 授权给自己的私有—
登记、编辑、删除模型，纳入平台，设公有 / 私有✓✗✗
私有模型授权✓✗✗
申请、管理自己的用户 Key✓（本人）✓（本人）✗
创建、删除客户端 Key✓（事先配好的，如平台服务）✗✓（只限本应用的客户端类型）

5. API Key

5.1 两种类型

用户 Key客户端 Key
代表谁一个人应用里的一个对象，例如一个智能体
谁创建本人在页面申请应用调接口创建，例如 Atlas 新建智能体时；平台服务这类事先配好的，由管理员在页面上建
怎么识别用户客户端类型 + 客户端编码，唯一；另带一个名称，只用于展示，随对象改名同步
数量一人一把每个客户端一把；重复创建返回同一把
谁分配模型本人管理员
可选范围公有 + 授权给本人或所在部门的私有（管理员是全部）全部已登记模型
原文给谁申请、重置时显示一次给本人不在页面显示；应用经接口获取
谁删除本人应用（删除对象时）；管理员也可以在页面上删
用途Claude Code、Cursor、脚本等个人工具应用运行时调模型

客户端类型：

客户端类型所属应用客户端编码创建、删除时机
AgentAtlas智能体 id新建、删除智能体
ServiceAtlas、知识库用途，如会话标题、记忆补记、知识库的对话、嵌入、重排部署时

只有所属应用能创建、获取、删除这一类型的客户端 Key，平台按调用方应用判断。以后有新的接入方，登记一个新的客户端类型即可。

5.2 Key 的模型：只有指定模型

  • 在 Key 上逐个勾选模型。「全选」只勾当前已有的；以后登记的模型不会自动加入，需要时再来勾。
  • 实际生效的模型（有效模型）按下图计算，同步到 LiteLLM 的就是它。
  • 勾选过但已经失效的模型（授权撤销、模型删除、LiteLLM 中缺失）在页面上标出来，先保留在分配列表里；下次保存分配时移除。授权恢复的话，它重新生效。

图 2　有效模型 = 分配的 ∩ 可选范围 ∩ LiteLLM 里存在的；LiteLLM 里只放有效模型，为空就停用

5.3 生命周期

图 3　客户端 Key 的生命周期：创建后先「待分配模型」，管理员分配后才在 LiteLLM 生成 Key

  • 待分配时不生成 LiteLLM 的 Key：空的模型列表在 LiteLLM 里表示全部模型，提前生成等于先放开了全部模型。这期间应用取到的状态是「待分配」，没有 Key。
  • 停用和「无可用模型」是两回事：前者是管理员的操作，要管理员启用；后者由模型变化引起，有效模型恢复后自动解除。LiteLLM 里的停用状态 = 管理员停用，或有效模型为空。
  • 用户 Key 没有待分配状态：申请时必须勾至少一个模型，申请即生成，原文显示一次；之后同样可以改模型、重置、停用、启用，本人可以删除。

5.4 保管

  • LiteLLM 只存 Key 的哈希；平台保存一份原文，用于应用获取客户端 Key。
  • 原文的展示：用户 Key 只在申请、重置时显示一次，忘了就重置；客户端 Key 不在页面上显示。
  • 重置：生成新 Key、删除旧 Key，分配的模型和停用状态不变。正在用旧 Key 的调用会失败，应用下次获取时拿到新的。
  • 停用：LiteLLM 拒绝这把 Key 的所有调用，可以随时启用。

6. Key 与 LiteLLM 的同步

6.1 平台是事实源

平台保存每把 Key 分配的模型和管理员停用状态，并据此算出有效模型；LiteLLM 里这把 Key 的可用模型和停用状态跟随平台。LiteLLM 里另外配的预算、限流不归平台管，平台更新 Key 时不覆盖它们。

6.2 什么时候重算

事件影响的 Key
Key 的分配被修改、停用、启用这把 Key
私有模型的授权增加、撤销被影响的人的用户 Key
模型公有改私有、私有改公有用户 Key（客户端 Key 不受影响）
模型删除、LiteLLM 中缺失、重新登记分配了这个模型的 Key
员工调部门、在用户中心被停用这个人的用户 Key；被停用的人，他的用户 Key 一并停用

6.3 同步失败与对账

  • 每次重算后立即更新 LiteLLM；失败就重试。重试成功之前，LiteLLM 里的状态可能比平台多给或少给。
  • 定期对账：逐把 Key 比较平台算出的有效模型、停用状态和 LiteLLM 里的，不一致以平台为准修正。用户中心没有变更通知，调部门、员工停用这类变化靠对账发现。
  • 对账时发现 LiteLLM 里有、平台不认识的 Key（在 LiteLLM 里直接建的）就告警，不自动删除。

7. 接入：Atlas Native Agent

7.1 智能体与它的客户端 Key

图 4　Atlas 接入：建智能体时创建客户端 Key，管理员分配模型后才能用；编辑、运行时按「Agent + 智能体 id」获取，调用直连 LiteLLM

  • 新建：Atlas 调平台创建客户端 Key（类型 Agent、编码 = 智能体 id、名称 = 智能体名称）。按类型 + 编码幂等，重试不会重复创建。
  • 改名：同步名称，只影响平台页面上的展示。
  • 删除：Atlas 删除智能体是归档（之后还能恢复），归档时 Key 保留不动：恢复后照样能用，不用重新分配。
  • 新建后、分配前：编辑器里没有可选模型，智能体不能运行。平台页面上待分配的 Key 单独计数，方便管理员处理。

7.2 编辑智能体：可选模型

  • 编辑器按「Agent + 智能体 id」向平台取可用模型，也就是这把 Key 的有效模型，带显示名称、供应商、上下文窗口，填进主模型、压缩模型的下拉框。
  • Key 待分配、已停用、无可用模型时列表为空，编辑器说明原因，提示联系管理员。
  • 当前选的模型已经不在列表里（被移出 Key、被删除）时标红，提示换一个。

7.3 Run 开始

图 5　Run 开始时的检查：Key 和模型的问题在开始前报出来，不让模型调到一半才失败

  • 每轮取最新的：Key 被重置后，下一轮自动用新的；分配变了，下一轮立即按新的检查。
  • 平台不可用时沿用上次的：最终由 LiteLLM 校验，旧 Key 失效了会被拒绝，所以沿用是安全的。
  • 说清楚找谁：例如「智能体『工单助手』没有分配模型 claude-sonnet-5，请联系管理员」。

7.4 一次模型调用

  • 只经过 LiteLLM：Atlas 带着 Key 和模型名调 LiteLLM；LiteLLM 校验 Key 未停用、模型在可用模型里，转发给供应商，记录日志和花费。
  • 协议一律 Anthropic Messages：非 Anthropic 的模型由 LiteLLM 转换。Atlas 只维护一条调用路径（提示词缓存、思考都依赖它），ACP 的 Claude Code 本来也只认这一种。思考、档位、温度等参数仍只发给支持的模型。
  • 身份不进模型输入：使用者、会话、Run 等标识作为请求的元数据交给 LiteLLM，只用于日志里按人、按 Run 查，不用于判权。
  • 不设整次调用的时长上限：沿用现有规则，只按两段数据之间的静默判断卡死。

7.5 调用失败

#情况处理自动重试
①Run 开始时 Key 待分配、已停用、无可用模型，或本轮模型不在其中本轮不开始，说明原因和找谁（7.3）否
②平台暂时不可用沿用上次取到的；从没取到过的退避重试，用尽后本轮失败是（退避）
③LiteLLM 拒绝：Key 无效（本轮进行中被重置、删除）本轮停下，提示重发；重发的那一轮取新的 Key否
④LiteLLM 拒绝：Key 停用、模型被移出 Key（本轮进行中）本轮停下，说明原因；已经完成的步骤保留否
⑤连不上 LiteLLM；限流（429）、过载、5xx同一个模型名有多个部署时，LiteLLM 先在部署之间重试；仍然失败的，Atlas 退避重试，用尽后本轮失败是（退避）
⑥参数不被接受（400）本轮失败否
⑦上下文超长交给上下文压缩（现有处理）—
⑧供应商余额不足、供应商凭据失效本轮失败；对用户说「模型服务暂时不可用」，不暴露供应商细节否

对话里说清楚类别：没分配、被停用、暂时不可用、平台故障，用户分得清是「找管理员」还是「稍后再试」。

7.6 SubAgent、上下文压缩、会话标题、记忆补记

  • 内联的 SubAgent：沿用父 Run 的 Key，它用的模型同样要在这把 Key 里。
  • 委派给另一个智能体：用目标智能体自己的客户端 Key，在它的 Run 开始时检查。
  • 上下文压缩：压缩模型和主模型一样，要在智能体的 Key 里，Run 开始时一起检查。
  • 会话标题、记忆补记：不属于某个智能体，用平台服务的客户端 Key（第 9 章）。

7.7 和权限类型的关系

  • 模型跟智能体走，与权限类型无关：以人为权限（私人助理）和以 Agent 为权限的智能体，都按「Agent + 智能体 id」取模型和 Key。同一个智能体对所有使用者能用的模型相同，花费记在智能体的 Key 上。
  • 权限类型仍然决定知识库、MCP 等数据权限按谁判。

8. 接入：ACP Agent

ACP Agent 的模型客户端是会话 Pod 里的 CLI，Atlas 拦不到单次调用，LiteLLM 是唯一的治理点。

8.1 下发

图 6　ACP 下发：检查规则和 Native 相同；Pod 里只有 LiteLLM 地址、智能体的 Key 和模型名，没有供应商凭据

  • 模型从智能体配置来：编辑器只列出 CLI 能用的协议对应的模型，例如 Claude Code 用 Anthropic Messages。
  • CLI 的轻量模型：有的 CLI 会用另一个轻量模型做标题这类旁路工作，它也要在 Key 里。默认就是主模型，智能体配置里可以另选；不指定的话，CLI 会去找它默认的模型，然后被 LiteLLM 拒绝。

8.2 Key 进 Pod

Key 会进 Pod，这是有意接受的风险：

  • Key 会出现在这个智能体所有使用者的会话 Pod 里，使用者可以诱导智能体把它打印出来，然后在 Atlas 之外调用。
  • 能力不超过这把 Key 分配的模型；这些调用在 LiteLLM 的日志里，花费记在这个智能体上。
  • 发现泄露就重置。重置后已打开的会话调用都会被拒，恢复会话时重新下发新 Key。

8.3 调用失败

  • 由 CLI 自己处理，Atlas 不替它重试。LiteLLM 按调用协议的错误格式返回拒绝原因，CLI 会展示出来。
  • ACP 的调用和失败 Atlas 看不到，LiteLLM 的日志是唯一完整的记录。

9. 接入：知识库与平台服务

  • 知识库：用服务级客户端 Key，所有知识库共用，按用途分三把（客户端类型 Service）：
    用途客户端编码模型怎么定
    入库增强、查询理解knowledge-chat部署配置里写定模型，必须在这把 Key 里
    远程嵌入knowledge-embedding建库时从这把 Key 的可用模型里选
    远程重排knowledge-rerank检索设置里从这把 Key 的可用模型里选
    哪把没建或没分配模型，哪项能力就不可用：入库增强、查询理解降级为不做；远程嵌入、重排不出现在选项里，只能用本地模型。花费按这三把 Key 统计，不细分到单个知识库。
  • 平台服务：会话标题、记忆补记这类不属于某个智能体的调用。管理员事先在平台上建好客户端 Key（如客户端类型 Service、编码 session-title）、分配模型；Atlas 的平台配置里按用途记下用哪个客户端类型、客户端编码、模型，用的时候按它向平台取 Key。所有会话共用，花费单独记在这几把 Key 上，不算进任何智能体。配置时当场校验 Key 和模型可用，配错了直接报。
  • 获取和失败处理与 Atlas 相同：每次用之前取最新的，平台不可用时沿用上次的；Key 待分配或停用时，这项功能暂停并记录原因。

10. 日志、用量与成本

  • 调用日志、花费都在 LiteLLM，按 Key 统计：用户 Key 对应人，客户端 Key 对应智能体或平台服务（含知识库）。平台页面不展示花费，管理员到 LiteLLM 管理界面查看。
  • 价格：登记模型时写进 LiteLLM，LiteLLM 按它计费；自部署的模型可以不填。
  • 预算、限流：需要时在 LiteLLM 里按 Key 配置，平台不设，也不覆盖（6.1）。
  • 平台自己的操作：登记、编辑、删除模型，授权，分配模型，重置、停用 Key，都记操作日志，写明谁在什么时候做了什么。
