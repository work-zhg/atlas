0. 方案概览

图 0　方案总览：Atlas 和 Pod 里的 CLI 只连 MCP 网关；网关按 Key 认人、按用户中心判权、按复核过滤工具，再带上网关凭据转发给 Higress；Higress 只认 MCP 网关，Pod 和集群里的其他进程直连会被拒绝；工具定义由网关从 Higress 拉取存库，Atlas 从网关读

问题方案
服务怎么接入先在 Higress 上声明：业务系统的 REST 接口按模板转成 MCP，已有的远程 MCP 服务由 Higress 代理。再在 MCP 网关登记一个稳定的服务名，上游指向 Higress 上的这个服务。只接远程服务，不在平台里拉起 stdio 进程
工具定义怎么管MCP 网关是元数据的事实源：它从 Higress 拉取工具定义存进自己的库，做机械检查、人工复核、记录变化。Atlas 从网关读元数据，装配时不连网
谁能用哪个服务唯一事实源是用户中心的数据权限，数据编码属于 MCP 网关这个应用：一个 MCP 服务一条数据，"使用"级别 = 能选、能调。按这一轮的权限主体判：以人为权限的 Agent 是使用者本人，以 Agent 为权限的是它的数字员工
网关怎么认人每个主体（人或数字员工）最多一把 API Key，只表示"我是谁"，不带权限。MCP 网关按 Key 认出主体，再按用户中心判断它能不能用这个服务；Higress 不按人鉴权
谁能调 Higress只有 MCP 网关。Higress 上的每个服务只接受带网关凭据的请求，凭据只在 MCP 网关和 Higress 里，不下发给 Atlas 和 Pod；直连的请求被拒绝并告警。MCP 网关登记服务时先确认这个服务直连调不通
两道闸门Atlas 侧：选工具、保存、装配时按主体过滤（问 MCP 网关），没权限的工具模型看不到。MCP 网关：每个请求都判权、执行复核，兜住 Pod 里的 CLI 和泄露的 Key；Higress 只认 MCP 网关，这道闸门绕不过去
调用怎么走Native：Atlas 进程是 MCP client，同一个 Run 对同一个服务复用一个会话，带上主体 Key；调用前校验参数，失败转成工具结果交给模型。ACP：只把网关地址和主体 Key 交给 Pod 里的 CLI，由 CLI 自己连网关
调用失败怎么办不让整轮失败：失败转成工具结果交给模型，并说明能不能重试、要不要找人处理。Atlas 只在确定请求没到后端、原因能先修复时自动重试一次（Key 刚被重置、会话失效）；超时按"结果未知"告诉模型。ACP 由 CLI 自己处理，网关把拒绝原因写清楚（6.7、7.5）
工具多怎么办超过阈值时改为延迟加载：模型只看到名字和一句描述，用搜索工具按需加载完整定义。搜索范围只限已经过了权限和复核的工具
以后怎么替换 HigressHigress 只是 MCP 网关的一种上游。以后把 REST 转 MCP、代理、后端凭据逐步收进网关，或让服务直接挂在网关后面；Atlas、Pod、权限都不受影响
出了问题怎么止血Key 泄露：停用或重置 Key（网关立即生效）。服务有问题：在 MCP 网关停掉（对已打开的 ACP 会话也有效）。工具定义可疑：拒绝该定义（网关立即不再放行）。网关凭据泄露：轮换（MCP 网关和 Higress 一起换，不停机）

1. 背景与目标

1.1 现状

已经有的能力（已对照代码）：

  • 注册表在配置服务；服务名是工具名的前缀，模型看到的是"服务名__工具名"，不同服务的同名工具不会互相覆盖。
  • 工具目录：发现和调用分开，工具定义缓存在多副本共享的存储里，刷新失败时保留旧定义。
  • 工具定义的机械检查、人工复核；Agent 保存时记下所选工具的定义指纹，运行时比对。
  • Native：调用经过一条拦截链（身份请求头、错误转成工具结果、超时、结果截断）；MCP 工具多时自动改为延迟加载。
  • ACP：按服务把 MCP 配置随会话下发给 Pod 里的 CLI。
  • Higress：网页搜索已经改成在 Higress 上声明的 MCP 服务，后端 key 只在网关里。

存在的问题：

问题说明
谁都能用用户中心里已经登记了"MCP 服务"这个数据编码，但没有任何地方用它：任何人、任何 Agent 都能用全部已启用的服务。编辑器的工具目录也不分人
网关不认人网关上的服务没开认证，拿到网关地址就能调；网关也看不出是谁在调用
Pod 里是平台凭据ACP 会话把平台凭据的真值下发进 Pod，Pod 里的代码能调这把凭据能调的全部服务
身份请求头不可信Atlas 调 MCP 时带的身份请求头是明文的，Pod 能伪造，下游不能拿它做授权
接入方式不统一注册表接受任意地址，服务可以绕过网关直连，网关的认证、日志、下线都管不到它
每次调用 4 个请求每次工具调用都新建 MCP 会话：握手两个请求、调用一个，SDK 为校验结果再补拉一次工具列表。工具多的服务每次调用都拉一遍全量列表
参数不校验模型生成的参数只受提示词约束，Atlas 侧不按参数定义校验就直接发给服务；服务自己校不校验因服务而异
只读注解不在指纹里审批按服务声明的只读注解决定是否直接放行，但定义指纹不含注解：服务把一个工具改标为只读，不触发复核，审批却会放行它

1.2 目标

  • 收口：所有 MCP 调用都经自研 MCP 网关，它是 Atlas 和 Pod 看到的唯一入口；Higress 只接受 MCP 网关的请求，入口绕不过去。
  • 授权只有一个事实源：用户中心的数据权限；人、部门、数字员工用同一套授权。
  • 网关能认人、能限权：MCP 网关认得出每次调用是谁，只放行被授权的服务和复核通过的工具；Key 泄露也拿不到主体本来没有的权限。
  • 两类 Agent 规则一致：Native 和 ACP 按同一个主体判权、带同一把 Key。
  • 工具定义可控：第三方的工具描述在进入模型上下文前经过检查和复核；定义变了能被发现。
  • 调用稳定、开销小：会话复用；调用失败交给模型处理，不让整轮失败。
  • Higress 可替换：Higress 的能力以后逐步收进 MCP 网关；替换时 Atlas、Pod、授权、复核都不受影响。

1.3 非目标

  • 工具级授权：授权粒度到服务。同一服务内用哪些工具，由 Agent 配置和工具复核控制。
  • MCP 的 resources / prompts / sampling / elicitation：只接 tools。sampling 意味着服务反过来调用平台的模型，是另一个治理面。
  • 在平台里拉起 stdio 进程：见 3.1。
  • 限流、计费、按 Key 的配额：属于网关能力，本期不做（8.1）。
  • 在 Atlas 里做 MCP 代理：转发、鉴权是独立的 MCP 网关的事，Atlas 不进数据面。
  • 安全加固：Key 的存储加密、内网接口的访问控制、Pod 网络隔离等，后续统一设计。"只有 MCP 网关能调 Higress"不在此列，本期就做（8.3）。

3. 服务接入

3.1 接入方式

图 2　接入方式：先在 Higress 上声明服务（REST 转换或代理），再在 MCP 网关登记、上游指向 Higress；网关拉取工具定义存库，检查和复核通过后 Atlas 才能选

  • 业务系统只有 REST 接口：在 Higress 上按模板声明成 MCP 服务（工具名、参数、怎么拼请求、后端凭据），不用另写一个 MCP 服务。现在的网页搜索就是这样接的。
  • 已有远程 MCP 服务：由 Higress 代理。服务需要的后端凭据配在 Higress 上。
  • 只有 stdio 的 MCP 服务：不在平台里拉起子进程。多租户的服务进程旁边跑子进程，没有进程隔离、不能横向扩展，凭据还会落进服务进程的环境变量。由提供方部署成远程服务后按上一条接入。
  • Atlas 和 Pod 只认 MCP 网关：它们拿到的服务地址都是 MCP 网关上的地址，看不到 Higress。认证、判权、复核、访问日志、紧急下线都在 MCP 网关，对所有服务一致。
  • Higress 也只认 MCP 网关：在 Higress 上声明服务时就要求网关凭据；MCP 网关登记时先确认这个服务直连调不通（8.3）。知道了 Higress 的地址也没用。

上游是替换 Higress 的接缝。服务登记的是"上游"，而不是 Higress 本身：

4. 工具目录：元数据、检查、复核

MCP 工具和内置工具最大的不同是动态且来自第三方：连上去才知道有哪些工具、做什么，提供方还可以随时改。工具定义（名字、描述、参数说明）会原样进入模型上下文，所以它本身就是一段第三方文本。本节处理这两点带来的问题。本版起，这一节的事都由 MCP 网关负责，Atlas 只读结果。

4.1 元数据：网关拉取、存库，Atlas 读

  • MCP 网关是元数据的事实源：服务登记后，网关通过上游（Higress）拉取工具定义，连同检查结果、复核结论、指纹、变化记录一起存进自己的库。工具定义是平台级数据，不因人而异，所有人共用一份；按人过滤发生在列目录、装配和每次请求的时候（§5）。
  • 刷新：网关定期重新拉取，也可以在管理端手动立即刷新。刷新失败保留旧定义并记下原因：服务短暂宕机不该让已有的工具消失，调用时自会报错。
  • 保留上一版：定义变化时保留变化前的一版，管理端据此显示新增、删除、描述变化、参数变化。
  • Atlas 从网关读：Atlas 不再连 MCP 服务发现工具，而是从 MCP 网关读服务、工具定义和复核结论，缓存在多副本共享的存储里。装配时只读缓存、不连网；真正建连推迟到第一次调用。这样一个慢的服务不会拖慢每一轮，一个宕机的服务也不会让所有挂了它的 Agent 发不出消息。
  • 发现不需要单独的凭据：工具定义由 MCP 网关拉取，用的是它调 Higress 的网关凭据（5.6）。

4.2 机械检查

MCP 网关每次拉到新的或变化了的定义，先做机械检查，不通过的标为不可用：编辑器里灰显、不能选；已经选了它的 Agent，下一个 Run 会明确报错。

检查规则
命名模型看到的名字要符合各模型厂商工具名规则的共同子集，长度够用
描述长度工具描述、参数描述超过上限。正常的描述不需要很长，超长本身就是可疑信号
参数定义参数定义必须是对象形式
注入特征"忽略之前的指令""调用本工具前请先……"之类的句式，规则和技能扫描共用一份

机械检查有漏报，它只是兜底，主要防线是人工复核。

4.3 工具复核

图 3　工具定义的状态：只有"可用"的工具能被选、能进模型上下文；指纹覆盖名字、描述、参数定义和只读注解，任何一项变了都重新检查、重新复核

  • 复核结论按"服务 + 工具 + 定义指纹"记录：批准的是某一版定义，不是这个工具本身。指纹覆盖名字、描述、参数定义和只读注解（注解决定审批是否直接放行，6.4）：只改描述不改名字，指纹也会变，而这恰恰是注入风险最高的变化（一个审过的服务后来改了描述，是最现实的攻击路径）。
  • 复核在服务这一级做一次，覆盖所有引用它的 Agent。终端用户看到"定义变了"的提示既没有能力、也没有权限处置，所以安全闸门放在 MCP 网关的注册表，而不是放在每个 Agent 上。
  • 复核在 MCP 网关的数据面执行：未通过复核的工具从工具列表里去掉，调用直接拒绝。Native 和 ACP 都一样；Atlas 在编辑器和装配时也按复核结论过滤，是第一道。
  • 待复核和被拒绝的工具：编辑器里不能选；已经选了它的 Agent，本轮跳过这个工具并在对话里提示，Run 照常进行。
  • 不要求复核的服务：机械检查通过就可用。"可以放宽"的依据应当是代码在平台自己的评审流程里，而不是"部署在内网"。

4.4 Agent 侧的变更提示

复核解决"这版定义能不能进模型上下文"；Agent 的维护者还需要知道"我依赖的工具变了"，因为工具的行为可能随之变化：

  • Agent 保存时，记下所选每个工具当时的定义指纹。
  • 运行时比对，不一致时按 Agent 的策略处理：提示后继续用（默认），或跳过该工具并提示（对确定性要求高的 Agent）。
  • 编辑器里显示"待确认"，维护者看过后重新保存一个版本，就是确认。

ACP 按服务下发（7.1），但复核由 MCP 网关按工具执行：服务里某个工具待复核或被拒绝，只是这个工具从 CLI 拿到的工具列表里消失、调用被拒，其余工具照常可用。

5. 权限

结论先行：谁能用哪个 MCP 服务，事实源只有一个，就是用户中心的数据权限（"使用"级别），数据编码属于 MCP 网关这个应用。API Key 只是持有人在 MCP 网关上的凭据，本身不带权限。Agent 的权限类型决定这一轮的权限主体，进而决定按谁的权限选服务、带谁的 Key。鉴权只在 MCP 网关做，Higress 不按人鉴权，只认 MCP 网关这一个调用方。

5.3 服务授权：用户中心数据权限

  • MCP 网关是用户中心里的独立应用，拥有"MCP 服务"这个数据编码（编码名只表达语义，不带应用名）。用户中心规定数据编码只能由所属应用登记和查询，所以登记数据对象、查询某个主体能用哪些服务，都由 MCP 网关来做；Atlas 要知道主体能用哪些服务，问 MCP 网关，不直接查用户中心。
  • 一个 MCP 服务是用户中心里的一条数据，数据标识就是服务名（服务名不能改、不能复用，正好当稳定的业务键）。
  • 级别：使用 = 能在 Agent 里选、能经 MCP 网关调用；所有者 = 能给人、部门、数字员工授权和收回，注册人自动成为所有者。"读写"级别不用：服务定义由 MCP 管理的操作权限管，不按单条数据分。
  • 存量迁移：现在 Atlas 名下登记过"MCP 服务"的数据编码（AtlasMcpServer），但还没有地方使用它。迁移时把它的授权（含"全部 MCP 服务"这类编码级授权）按原范围迁到 MCP 网关的数据编码下，Atlas 名下的编码随后退役。

5.4 两道闸门

图 5　两道闸门：闸门一管所有经过 Atlas 代码的调用；闸门二在 MCP 网关，每个请求都认人、判权、执行复核，兜住 Pod 里的 CLI 和泄露的 Key。Higress 只认 MCP 网关，直连 Higress 的进程会被拒绝，绕不过闸门二

  • 编辑器：只列主体有权的服务里的工具（问 MCP 网关）；没权限的服务不列出，只显示个数，并说明按谁的权限列出、Key 的状态（9.2）。
  • 保存：只校验新加的服务，主体没有"使用"权限就拒绝保存。旧版本已经选了的不重判，免得授权被收回以后，连改提示词都保存不了。不校验 Key：Key 可以后发，缺 Key 由运行时跳过并提示。切换权限类型时也不重判，主体变了以后无权的服务在"身份"面板里标红。
  • 装配：每个 Run 按主体向 MCP 网关查一次可用服务。没权限、没有 Key 的服务，跳过并在对话里提示，而不是让模型调了再失败（模型看不见就不会去调）。跳过一定要提示：静默少一个工具，模型照常做事、只是做不好，用户不知道为什么。
  • 为什么还要网关这一道：闸门一只管经过 Atlas 代码的调用。ACP 会话里 CLI 直接调 MCP 网关；Key 泄露后可以在 Atlas 之外调用。这两种情况只有 MCP 网关拦得住。
  • 两道闸门的判断依据一致：Atlas 侧问的也是 MCP 网关，两边用同一份授权、同一份复核结论。只有授权刚被收回、缓存还没过期的那一小段时间里，才会出现"编辑器里还能选、调用时被拒"的情况。

5.7 下游怎么知道是谁

  • MCP 网关改写身份请求头：网关先去掉调用方自带的身份请求头，再写入它确认过的身份。权限主体来自 Key，是可信的；使用者（以 Agent 为权限时和主体不同）来自 Atlas 带的请求头，只用于审计。
  • Higress 能否把这个身份交给后端：代理的 MCP 服务一般原样转发请求头；按模板转换的 REST 服务，要看模板有没有把它带上。两种都待验证。
  • 前提：请求确实经过了 MCP 网关。Higress 只接受 MCP 网关的请求（8.3），所以经 Higress 到达后端的身份请求头都是网关写入的，Higress 这一段不再是缺口。剩下的缺口在后端自己：后端如果不要求只有 Higress 才有的后端凭据，Pod 就能绕过 MCP 网关和 Higress 直接调它，并带上任意身份请求头。所以下游要按这个身份请求头做数据隔离，前提是它只接受带后端凭据的请求；做不到的，要么自己再做一道认证，要么等用户的第三方授权方式。

6. 运行时：Native Agent

Native Agent 的 MCP client 在 Atlas 进程里：MCP 工具被装配成普通工具，调用经过 Atlas 的代码，所以能做审批、参数校验、错误转换和结果截断。engine 不认识 MCP，看到的只是普通工具。

6.1 装配

图 8　装配：权限、Key、复核导致的缺失跳过并提示（模型看不见就不会去调）；配置错误明确失败；构造工具只读缓存，不连网

  • 没引用 MCP 就不查：没用 MCP 的 Agent，不该因为 MCP 网关暂时不可用而失败。
  • 两类缺失分开处理：权限、Key、复核造成的缺失是"这个人此刻用不了"，跳过并提示，Run 照常进行；引用的服务或工具不存在、缺凭据这类配置错误，重试也不会好，明确失败并说明原因，不静默少装工具。
  • 引用的服务在 MCP 网关里没有元数据，Atlas 也没缓存过：构造不出工具，本 Run 明确失败。

6.2 一次调用

图 9　一次调用：审批和参数校验在建连之前；身份和主体 Key 由 Atlas 按这一轮的主体放进调用链，模型看不到也改不了

  • 身份和 Key 不进工具参数：它们由 Atlas 按这一轮的主体放进调用链。模型换不了身份，也就拿不到别人的 Key。Key 也不进工具目录、缓存、日志和事件。
  • 只转换传输层的错误：连接、超时、认证这类错误转成工具结果交给模型；程序错误照常抛出，不伪装成"服务不可用"让模型绕过去，否则 bug 永远不会被发现。Run 被取消时调用立即中止，不当成错误转换。

调用失败时交给模型什么、哪些情况自动重试，见 6.7。

参数校验：调用前按工具的参数定义校验参数，缺必填项、类型不对、多了定义里没有的字段，直接把错误交回模型，不发请求。

  • 为什么要做：模型生成的参数只受提示词约束，大多数时候是对的，但可能漏掉必填项、写错类型、自己编字段。服务自己校不校验因服务而异，网关从 REST 转出来的服务可能直接把错误参数传给后端。在 Atlas 侧校验，错误在发出请求之前就被拦下，报错信息也统一。
  • 不做约束解码（模型厂商的严格模式）：第三方服务给的参数定义经常不在它支持的范围内，要先改写定义，风险大。
  • 模型输出的调用本身不是合法 JSON 的情况，发生在解析阶段，不在这一层处理。

6.3 会话复用

图 10　会话复用：同一个 Run 对同一个服务复用一个会话，N 次调用的请求数从 4N 降到 N + 3；每个请求都要过一次网关认证，省下的不只是往返时间

  • 现状：每次工具调用都新建会话，先握手（两个请求）、再调用；MCP SDK 要按工具的输出定义校验结果，而新会话里还没有工具列表，于是再补拉一次。工具多的服务，每次调用都要拉一遍全量列表。
  • 方案：同一个 Run 段内，同一个服务复用一个会话。第一次调用时建会话并拉一次工具列表，之后每次调用只发 1 个请求。一个 Run 只有一个权限主体，所以会话天然按主体分开，不会跨主体复用。
  • 身份和 Key 在建会话时确定：复用会话以后，请求头只在建会话时生效。Atlas 的 MCP 客户端 10-26 换成 langchain.mcp + FastMCP 以后已经是这样：按 Run 建客户端，身份请求头写在客户端的传输层；主体 Key 也放在这里。
  • 生命周期跟 Run 段走：Run 段结束（完成、挂起、取消、被另一个实例接管）时关闭会话；恢复后重新建立，不跨进程迁移会话。
  • 会话失效（服务重启、会话过期）：重建一次再重试，仍然失败就按 6.7 处理。
  • 会话要能穿过 MCP 网关：网关转发时原样透传会话标识（8.2）。MCP 网关和 Higress 多副本时，同一个会话的请求是否必须落到同一个副本，待验证。

6.4 审批

  • 规则和内置工具相同（见 Native 审批模式）：放不放行由会话的审批模式和工具的副作用类别决定。规划模式下只读的放行、有副作用的拦下；手动模式下有副作用的都请示；自动模式下有副作用的交给判断器（判断器做出来之前一律请示）。
  • MCP 工具的副作用类别取自服务声明的只读注解：标了只读的归为"只读"，所有模式都直接放行；没标的归为"外部"，是最保守的一类。
  • 只读注解要纳入定义指纹（本方案新增）：注解是服务自报的。一个服务把会改数据的工具标成只读，它在所有模式下都会被直接放行。现在的指纹只覆盖名字、描述和参数定义，不含注解，服务把注解从"非只读"改成"只读"既不触发复核，也不触发 Agent 侧的变更提示。注解纳入指纹以后，它的变化按定义变化处理，要重新复核；复核时管理员同时确认这个工具确实只读。
  • 被审批挂起的调用不建连、不占超时。审批通过后 Run 以新的一段恢复，工具重新装配（读缓存，没有额外开销）。

6.5 工具多：延迟加载

  • 触发：一个 Agent 挂的 MCP 工具超过一定数量，或者定义总量超过一定大小时，MCP 工具全部改为延迟工具。
  • 怎么用：模型默认只看到一份"名字 + 一句描述"的清单，附在系统提示词末尾（每次都一样，不影响提示词缓存）。需要时调用搜索工具，按关键词或名字加载完整定义，之后就能直接调用；加载过的工具本会话内一直可用。已加载哪些工具从对话历史里推出来，续跑、重建历史后仍然成立。
  • 不绕过任何闸门：清单里只有本 Agent 已选、已通过权限过滤和复核的工具。加载后的执行路径和普通工具完全一样，审批、参数校验、调用链照常。搜索工具本身只读，不需要审批。
  • 代价：每加载一批新工具，下一次请求里的工具列表就变一次，提示词缓存随之失效一次。所以搜索一次应返回多个相关工具，清单里的描述要写清楚，减少反复搜索。Anthropic 的服务端工具搜索把加载的定义展开在对话里、不动前缀，因此不破坏缓存；这要模型服务端支持，Atlas 现在用的模型做不到，这是客户端实现的固有代价。

6.6 结果防护

  • 结果超长时保留头尾、中间替换为说明。截断阈值高于"大结果转存到工作区"的阈值：开了文件工具的 Agent，大结果先完整转存到工作区；没开文件工具的，靠截断兜底。
  • 工具的参数和结果不进追踪数据，和现有的追踪规则一致。

6.7 调用失败

结论先行：一次 MCP 调用失败，不让整轮失败。能让模型处理的，转成"失败的工具结果"交给模型，并告诉它能不能重试、要不要请用户找人处理，由它换个方式、稍后再试或者如实告诉用户。Atlas 只在确定请求没有到达后端、而且原因能先修复的时候自动重试一次。Run 被取消、Atlas 自身的程序错误不转换。

7. 运行时：ACP Agent

ACP Agent 的 MCP client 是会话 Pod 里的 CLI。Atlas 只在建会话时把服务的网关地址和主体 Key 交给它，之后的握手、拉工具列表、调用都由 CLI 自己完成，Atlas 拦截不到单次调用。所以对 ACP 来说，MCP 网关是唯一的治理点；好在本版起，它能对每个请求认人、判权、执行复核。

7.1 下发

图 12　ACP 下发：过滤规则和 Native 相同，按服务下发 MCP 网关上的地址；CLI 的每个请求都经过 MCP 网关认人、判权、按复核过滤

  • Agent 配置的粒度仍只能到服务：CLI 连上服务后自己拉工具列表，所以编辑器对 ACP 按服务选（显示"某服务 · 全部 N 个工具"）。但复核在 MCP 网关按工具执行：服务里某个工具待复核或被拒绝，只是这个工具从 CLI 拿到的工具列表里消失、调用被拒，其余工具照常可用。只想给 ACP 开放某个服务的部分工具，可以在网关上另登记一个只含这些工具的服务；以后让网关知道调用来自哪个 Agent，就能直接按 Agent 的配置过滤。
  • 会话级快照不再是问题：配置只在建会话、恢复会话时下发，但调用都经过 MCP 网关，收回授权（缓存时长内）、停用服务、拒绝工具定义（立即）对已打开的会话同样生效。
  • 恢复会话时下发同一份列表，由 CLI 决定是否使用。CLI 自己配置文件里的 MCP 服务，会话启动时清理掉，避免出现不在任何配置里的工具。

7.2 主体 Key 进 Pod，以及直连 Higress

Key 会进 Pod，这是有意接受的风险。Key 的能力不超出主体的授权：MCP 网关只放行主体被授权的服务，Key 泄露也拿不到主体本来没有的权限。

  • 数字员工的 Key：以 Agent 为权限时，数字员工的 Key 出现在所有使用者的会话 Pod 里。使用者可以诱导 Agent 把它打印出来，然后在 Atlas 之外按数字员工的权限调用 MCP 网关。这些调用 Atlas 看不到，但 MCP 网关的访问日志里有（主体 = 数字员工）。缓解：发现泄露就重置 Key；远期改为下发 Run 级的短期令牌。
  • 直连 Higress 行不通：Higress 只接受带网关凭据的请求，凭据只在 MCP 网关和 Higress 里，不进 Pod。Pod 里的代码就算在集群里找到了 Higress 的地址，直连也会被拒绝，并在 Higress 的拒绝记录里留下痕迹、触发告警（10）。Pod 想调 MCP 服务，只能拿主体 Key 经 MCP 网关，受判权和复核约束。

7.3 用户第三方授权方式的服务

远期方式（5.6），ACP 暂不支持。Pod 里只有主体 Key，后端凭据只在 Higress。

7.4 平台内部的 MCP 端点：知识库

  • ACP 的 CLI 通过知识库服务提供的 MCP 端点检索知识库。建会话时 Atlas 签发一个会话令牌，写明能查哪些库、按谁的权限判、谁在用；知识库服务只认这个令牌，不认任何身份请求头（Pod 里跑的是不可信代码）。
  • 它不经 MCP 网关：它的权限是"能查哪些库"，由会话令牌限定，网关的"按服务判权"表达不了；经网关只多一跳。这是"所有 MCP 都经 MCP 网关"的唯一例外。

7.5 ACP 的调用失败

  • 失败由 CLI 自己处理：Atlas 拦不到 Pod 里的单次调用，也不替它重试。网关能做的是把原因写清楚：拒绝时说明原因（8.2），CLI 再交给自己的模型。各家 CLI 拿到这些原因后怎么表现（是否交给模型、是否自动重试），待验证。
  • 授权收回、服务停用、复核拒绝：网关立即拦下，CLI 拿到的原因和 Native 相同（6.7 的 ⑤ ⑥）。
  • Key 被重置或停用：Key 是建会话时下发的，这个会话里之后的调用都会被拒，直到会话重建；恢复会话时 Atlas 重新取 Key 下发（7.1）。用户看到"API Key 已失效"，重新打开会话即可。
  • 网关不可用：这个会话里所有 MCP 调用都失败，表现取决于 CLI。
  • 记录只在网关：ACP 的失败 Atlas 看不到，网关的访问日志是唯一完整的记录（10）。

8.3 只有 MCP 网关能调 Higress

图 13　只有 MCP 网关能调 Higress：Higress 上每个服务都只认网关凭据，凭据只在 MCP 网关和 Higress 里；直连的请求被拒绝并告警；接入检查防止新服务漏开认证

  • Higress 只认一个调用方：Higress 上的每个 MCP 服务都要求网关凭据，持有它的只有 MCP 网关。这不是按人鉴权：没有按人的消费者、没有允许名单，授权变化不进 Higress；Higress 只回答"这个请求是不是 MCP 网关发来的"。
  • 凭据只在两处：MCP 网关和 Higress，不下发给 Atlas 和 Pod，不进日志和事件，和后端凭据同等对待。
  • 不停机轮换：Higress 先同时接受新旧两把，MCP 网关切到新的，确认没有旧凭据的请求后再撤掉旧的。怀疑泄露时按同样的步骤立即轮换。
  • 网关凭据不流到后端：Higress 校验后去掉它再转发。代理的第三方 MCP 服务如果拿到它，就等于拿到了绕过 MCP 网关的钥匙。
  • 接入检查：Higress 上的服务是人在控制台里声明的，难免有漏开认证的。MCP 网关登记服务时先不带凭据访问一次上游，能访问通就不允许登记；之后每次刷新元数据时复查，发现变成可以直连就告警。
  • 直连的请求要告警：正常情况下 Higress 上不会有被拒绝的请求，出现就说明有进程在尝试绕过 MCP 网关（10）。

做法好处问题
Higress 只认网关凭据（本方案）不依赖集群的网络能力，本机和 112 都能做；按服务生效，有接入检查兜住漏配；Higress 以后承担模型调用等其他流量也不受影响网关凭据是一把共享密钥，泄露了就能绕过 MCP 网关。靠"只在两处、可轮换、直连告警"控制
网络隔离：只放行 MCP 网关的 Pod 连 Higress不需要凭据，没有可泄露的东西要集群的网络插件支持（112 未验证）；内网身份传递设计里定过暂不做网络策略；Higress 以后要承担模型调用时，得按端口拆开放行；本机的 compose 环境做不到

本期只做第一种；网络隔离作为纵深防御，和 Pod 网络隔离一起放进后续统一安全设计。

Higress 保留什么：REST 接口按模板转成 MCP；代理已有的远程 MCP 服务；保管后端凭据。服务定义仍在 Higress 上维护。去掉：按人的认证、消费者、允许名单。

8.4 怎么逐步替换 Higress

  • 替换的接缝是"上游"（3.2）。按服务逐个把上游从"Higress 上的服务"换成"直连的远程 MCP 服务"或"网关内置的 REST 转 MCP"，后端凭据随之迁到 MCP 网关。
  • 换的过程中，服务名、工具名、授权、复核结论都不变，Atlas 和 Pod 无感知；可以一个服务一个服务地换、随时回退。
  • 换上游时规则不变：上游只接受 MCP 网关的请求。直连的远程 MCP 服务、网关内置的 REST 转换，都要认网关凭据（或者网络上只放行 MCP 网关），接入检查同样适用；否则换一个上游，就重新打开一个绕过网关的口子。全部换完，Higress 下线。

8.5 已知限制

限制影响应对
网关凭据是一把共享密钥泄露后，持有它的进程可以绕过 MCP 网关直接调 Higress，没有判权、复核只在 MCP 网关和 Higress 两处，不下发；不停机轮换；Higress 拒绝的请求告警（8.3）；以后叠加网络隔离
Higress 上的服务是人工声明的某个服务漏开认证，它就又能被直连接入检查：登记时不通过不允许登记，刷新时复查并告警（8.3）
MCP 网关在关键路径上网关不可用 = 所有 MCP 不可用多副本、健康检查；Atlas 把它当作服务暂时不可用，调用失败交给模型
判权结果有缓存在用户中心收回授权，要等缓存过期才生效缓存时长取短；紧急止血用停用 Key，立即生效
Higress 改服务定义后要一段时间才生效只影响新服务接入、模板修改网关刷新元数据前先确认生效

需要关注的指标：

  • MCP 网关：转发延迟、错误率、按原因统计的拒绝次数、判权缓存命中率、用户中心查询量。
  • 调用耗时和结果类别（成功、业务错误、超时、传输错误、认证失败），按服务、按工具。
  • 失败按原因的次数（6.7 的 ①–⑫）；自动重试的次数和重试后的成功率；熔断次数。
  • 元数据刷新耗时；刷新失败、仍在用旧定义的次数。后者是某个服务长期挂掉的信号。
  • 工具定义变化的次数。
  • 认证失败率：大量"有授权没 Key"或 Key 失效，说明功能等于没上线。
  • 每个服务的调用分布：长期没人调用的服务，白占复核成本。
