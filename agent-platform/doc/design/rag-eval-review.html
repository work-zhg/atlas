0. 结论

框架骨架与业界一致，部分做法更严谨；但「能证明 RAG 能力」的三个前提都还没具备。
骨架：只通过 HTTP 评测、跑题与判分分离、检索与生成分开评、出处按原文片段匹配、CRAG 三值计分、bootstrap 置信区间与配对比较 —— 这些和 RAGAS / TREC RAG / 云厂商的做法一致；其中出处匹配不依赖分段 ID，换分段方式后标注不会失效，比 Dify 内置的 golden question（按分段判定）更适合比较分段方式。
缺的三个前提：
  1. 评测集：只有 20 题自建样例集，按标题分段后检索和生成都是 100%，已饱和。按配对估算，20 题只能检出 24 个百分点以上的差距（§3.3）。
  2. 裁判可信度：裁判（deepseek-v4-pro）和生成模型（deepseek-flash）是同一家的模型，没有和人工标注做过一致性校准；RAGAS 提示词仍是英文。
  3. 评测对象：评测直接调单库的召回测试接口，生成用的是评测自己的提示词。智能体决策、多库路由、对话改写、权限、引用这些用户实际会走到的环节，都没有被评到（§3.1 图 2）。
优先级做什么解决的问题
P0补评测集：中文公开集 + 企业文档合成出题（人工审核），先做到约 500 题；裁判换另一家的模型，抽 100 题人工标注做校准；比较时按相同上下文长度对齐结论可信
P1经智能体的端到端评测；引用评测；上下文充分性判定与细粒度归因；RAG 回归门槛（含索引版本切换前对比）；权限泄漏专项测到用户实际走的链路
P2多轮、解析、文档注入专项；线上抽样评测 + 人工复核队列 + 错题回流；与 Dify / RAGFlow 横比覆盖面与持续化

1. 评测要回答的问题

不同用途需要的评测集、指标和频率都不一样。业界通常不会用一套评测回答全部问题，而是分开建。

用途要回答的问题需要的评测频率
选型与调参分段方式、向量 / 重排模型、检索方式、入库增强、查询理解，哪个更好？好多少？组件级离线评测；有标注的评测集；同等条件的配对比较做决策时
发布回归改代码、换模型、切索引版本之后，效果有没有退化？固定的回归小样本 + 门槛；结果与基线对比每次发布、每次切换索引版本
能力证明与横比Atlas 比朴素基线、比 Dify / RAGFlow 强在哪、弱在哪？公开评测集 + 官方口径；统一模型与上下文长度阶段性
线上质量真实用户的问题答得怎么样？哪些库、哪类问题差？不需要参考答案的指标；线上抽样评测 + 人工复核持续

2. 业界做法

2.1 共识：分层评测

各方（RAGAS、TREC RAG、Bedrock、Microsoft Foundry、RAGChecker）的共同做法：把链路拆成几层分别评，再加一层端到端与线上。分层评的好处是能定位问题 —— 检索没找到，生成不可能答对；检索找到了还答错，是生成的问题。

2.5 裁判

做法说明
大模型裁判为主正确性、忠实度、引用基本都由大模型判；评分标准写成结构化细则，输出 JSON，温度 0。
裁判与被测模型不同家避免裁判偏向同类回答。TREC 2025 用多个模型（GPT-4.1、Gemini 2.5 Pro、Qwen3 等）分别生成要点再合并。
与人工校准Langfuse：标注队列收集人工打分，在分数分析里和裁判对比；MLflow：align() 按人工反馈自动改写裁判，至少 10 条、建议 50–100 条。
只在配置级下结论TREC 的结论：自动评估与人工在系统排名上一致性高（nugget 自动评估与人工后编辑相比 Kendall τ 约 0.89），但单题上噪声明显大于人工。另有研究指出循环问题：被测系统用同一个大模型做重排时，自动评估的排名一致性明显下降。
小模型裁判HHEM、MiniCheck、ARES（训练轻量裁判 + 少量人工标注修正）用于线上大流量、低成本的忠实度判断。

2.6 统计

Anthropic《Adding Error Bars to Evals》给出的做法已成为常用口径：

做法说明
报告标准误 / 置信区间不只报平均分。
按簇计算标准误同一篇文档出了多道题时，题目之间不独立。按簇计算后，标准误可能比按题独立计算的大好几倍（论文里 DROP 上约 3 倍）。
重复采样降方差同一题多次生成取平均，降低生成随机性带来的波动。
配对比较两个配置在同一批题上比较时，用逐题差值算区间，比两个平均分各自算区间再比更灵敏。
功效分析定样本量先定「要检出多大的差距」，再算需要多少题。

3. Atlas 现状

3.1 评测的是哪一段

评测框架（atlas-bench）只通过知识库服务的公开接口工作：建库入库，然后对每道题调单库的召回测试接口取检索结果，用评测自己的提示词和模型统一生成回答，最后离线判分。下图对照用户实际走的链路：

图 2　评测只覆盖检索内核（绿色），其余环节没有被评到

这样设计有它的道理：先把检索内核评准，排除提示词差异，才能比较分段与检索方式。但它回答不了「用户在 Atlas 里问知识库，答得怎么样」。

平台里已有、但评测还没用上的能力：

  • 检索漏斗记录：每次检索记下各环节的候选、名次与分数，能看出某个分段是没召回、重排后被截断，还是被阈值滤掉；同一份数据也挂在 OpenTelemetry span 上，进 Langfuse。错题归因目前只看最终结果，没用到漏斗。
  • 按索引版本做召回测试：切换索引版本前可以用新版本检索对比。这正是回归评测的天然接入点。
  • 查询记录：库的检索请求有记录，可作为线上题目的来源。

3.3 已有结果与能说明什么

RAG 评测共跑过两次，都在样例集 demo-zh（3 篇虚构公司制度、20 题）上，top_k = 3，每题生成 1 次：

能说明的不能说明的
  • 流程走通了：入库、检索、生成、判分、统计、报告
  • 按标题分段比朴素分段命中率高 23.5 个百分点、CRAG 分高 0.35，配对比较显著
  • 查询理解让检索延迟从几十毫秒涨到 1–2 秒
  • 分段方式的提升有多少来自「返回更多文字」：两者 top_k 相同，但 structure 返回的字数是 naive 的 2.8 倍，没有在相同上下文长度下比较
  • 增强、查询理解、混合检索有没有用：全部 100%，评测集已饱和，比不出差别
  • 真实文档、真实问法下的能力：题是照着自己写的文档出的，问法贴近原文
样本量估算（假设：配对比较，两种配置结论不一致的题约占 15%；双侧 95% 置信、80% 功效）：最小可检出差距 ≈ 2.8 × √(0.15 / n)。
n = 20 → 约 24 个百分点；n = 100 → 约 11；n = 300 → 约 6；n = 500 → 约 5。
要分辨入库增强、查询理解这类通常只差几个百分点的改动，至少需要数百题；同一篇文档出多题时还要按簇计算，需要的题更多。

评测分层解析 / 检索 / 生成 / 端到端 / 线上只有检索与生成两层部分

5. 改进路线

原则：先让结论可信，再扩大覆盖面；能复用已有的就不新建（Agent 评测框架、检索漏斗、索引版本对比、Langfuse 都已存在）。

5.1 P0：让结论可信

做什么为什么取舍
评测集扩到约 500 题，分三块：
  • CRUD-RAG 问答子集抽样 + 干扰文档抽样（中文端到端）
  • C-MTEB 检索子集，段落不切分（向量 / 重排选型，可对照公开榜单）
  • 企业风格文档（制度、手册、带表格的 PDF）合成出题：用户画像 × 问题类别控制问法，人工审核后入库；单独补拒答题
样本量决定能检出的差距（§3.3）；中文企业文档没有合适的公开集，只能合成补CRUD-RAG 不全量入库（8 万篇成本高），按「证据文档 + N 倍干扰文档」抽样；MultiHop-RAG 等英文集放到后面
裁判换另一家的模型（与生成模型不同厂商）；抽 100 题人工标注，算裁判与人工的一致率，低了就改评分细则；RAGAS 提示词中文化并人工校对同家族裁判有偏向；没校准的裁判分数无法解释多裁判集成先不做，成本翻倍；一致率不够时再加
相同上下文长度下比较：报告增加「返回前 N 字时的召回率」，或按字数截断后再生成分段方式、父子分段、合并相邻分段都会改变返回字数，不对齐就比不出检索本身的好坏top_k 口径保留，两种都报
统计补齐：每题生成 3 次；同一文档多题时按簇计算区间；实验前按目标差距估算题量；调参只用 dev，出分只用 test与 §2.6 的口径一致生成重复 3 次，生成与裁判成本约 ×3

5.2 P1：测到用户实际走的链路

做什么为什么取舍
经智能体的端到端评测：复用 Agent 评测框架，加知识库问答任务；Agent 绑定评测库，分别跑自动注入、工具调用、ACP 三种模式；指标：答案正确率、引用正确率、整个轨迹的证据召回、检索次数当前评测绕过了智能体、真实提示词与模型；ACP 经 MCP 的检索路径还没在真实 Pod 里验证过与检索内核评测并存：内核评测用来调参，端到端评测用来回答「用户体验如何」
引用评测：引用准确率 + 覆盖率，一起报企业场景要能溯源；只看忠实度发现不了标错出处由裁判判，每题多 1–2 次调用
上下文充分性判定 + 细粒度归因：判断检索结果是否足以回答；错题归因接入检索漏斗，细分为「没召回 / 重排截断 / 阈值滤掉 / 信息不全 / 信息全但答错」现在「检索未命中」一类里混着几种原因，指不出该改哪一环；漏斗已经记录了各环节候选，只差和评测对上RAGChecker 全套陈述级指标暂不做，先用充分性 + 漏斗覆盖主要诊断需求
RAG 回归门槛：固定约 100 题回归集；发布前、切换索引版本前跑，与基线配对比较，命中率或 CRAG 分显著下降则不通过Agent 评测已有 smoke / regress，RAG 没有；索引版本切换缺一个客观依据回归集要从 test 里固定抽，不参与调参
权限泄漏专项：受限文档埋唯一标记串；用不同身份提问，检查检索结果、上下文、引用、回答里有没有标记；同时测授权用户的召回和撤权后多久生效「绑定不是授权」、按请求头身份判库级 / 文档级权限，这些改动正在上线；泄漏是企业场景的一票否决项泄漏率门槛为 0，必须和授权召回一起看

5.3 P2：覆盖面与持续化

做什么为什么
多轮：自建 50 段中文对话（指代、省略、追问、无答案），或改写 MTRAG 子集Atlas 的对话改写没被评过；多轮里的无答案题和后续轮次是公开评测里普遍表现最差的部分
解析：OmniDocBench 子集评解析器；带表格 / 版面的中文 PDF 出题评端到端PDF 版面解析、PPTX、表格摘要都没被评过
文档注入：在评测库里放带隐藏指令的文档，测攻击成功率智能体会执行工具，文档里的指令风险比纯问答高
线上评测：在 Langfuse 里对检索节点抽样跑相关性判断、对生成节点跑忠实度；人工复核队列；复核过的错题回流进评测集；聊天界面加反馈按钮离线评测集总会和真实分布有差距；链路追踪已接好，主要是配置和流程
竞品横比：Dify、RAGFlow 适配器；同语料、同向量模型、同生成模型、同上下文长度；分「开箱即用」和「各自调优」两组能力证明需要参照系

5.4 暂不建议做

事项原因
训练自己的小裁判模型需要大量人工标注；线上流量还不足以抵消成本。先用大模型裁判 + 抽样
全量导入 CRUD-RAG 8 万篇入库成本高；抽样语料足够做配置比较。规模压力测试单独做
自研一套 nugget 评估CRAG 三值 + RAGAS 事实正确性已覆盖问答题；只有汇总 / 长回答题多了以后才需要
深度依赖 RAGAS 新特性RAGAS 自 2026-01 起停止发版；保持固定版本、只用少数稳定指标，替换时只换判分这一层
