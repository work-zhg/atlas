1. 先认识几个词

词白话例子

接管 / 交接租约过期后别的实例把 run 领走叫接管；滚动部署时旧实例主动把 run 交出去叫交接滚动部署：新 Pod 起来，旧 Pod 收到停机信号，把在跑的 run 交出去
execd沙箱里负责执行命令的小服务。命令在它那里后台运行，和网络连接无关server 断开连接，命令照样在沙箱里跑

执行账本记下「哪一次工具调用对应沙箱里哪条命令」。接管的实例凭它接上原命令，不重跑调用 c1 → 沙箱 S、命令 7f3a…
取消位用户点「停止」时，在 Redis 里给这个 run 设的一个标记，所有实例都看得到取消父 run 时，子 run 也各自被设上

2. D9 + D1 + D2：取消的语义（一起修）

三个缺陷是同一件事的两面：「取消」送不到该停的地方（D9），却送到了不该停的地方（D1、D2）。一起修，规则只有一条：

中断沙箱里的命令，只在用户取消时发生。交接、租约丢失、进程停机只是「这个实例不再跟随了」，命令留在沙箱里继续跑，由接手的实例凭执行账本接上。

图 1　修复后：工具被取消时，用取消位分辨「用户要停」和「这个实例不跟了」。取消位是现成的、所有实例都看得到的「用户要停」的记录。

D9：工具执行期间收不到取消

现象

命令开始后第 10 秒取消 run，run.cancelled 要到 128 秒后才出现：那条 120 秒的命令一直跑完了才停。取消父 run 时，两个子智能体的命令和父智能体自己的命令都跑满了 120 秒。平台又不设运行上限，用户实际上没有办法停下一条长命令。

根因

用户点「停止」只是设一个取消位；执行 run 的循环在两帧之间才去查它。一条命令在跑时整个图卡在工具里，没有新帧，于是查不到。ShellSandbox 里写了「被取消就中断命令」的逻辑，但取消根本送不到它那里。

图 2　取消位什么时候被看到。

修复方案

  • 等下一帧的同时盯着取消位：执行 run 的循环不再只在两帧之间查，而是一边等下一帧、一边每秒查一次取消位。发现置位就取消正在执行的图：正在跑的工具随之收到取消，ShellSandbox 看到取消位已置位，中断命令（见 D1）。之后走现有的取消收尾：产出 run.cancelled、落终态、放会话锁、清取消位。
  • 子 run 不用特殊处理：取消父 run 时，平台已经给每个子 run 级联设了取消位，各自的循环同样在 1 秒内停下。
  • 跨实例自然成立：取消位在 Redis 里，run 在哪个实例上跑，那个实例自己看得到。不需要把取消转发到持有 run 的实例，符合「不转发、不选主」。
  • 开销：每个在跑的 run 每秒一次 Redis 查询。需要的话，一个实例可以把本实例在跑的 run 合并成一次批量查询。

不选的方案

  • 由持有实例直接取消 run 的任务：走的是交接那条中断路径，run 不进终态，要等租约过期被接管后才被发现已取消（30 秒以上）；而且又把「用户取消」和「交接」混在一起，这正是 D1 的根源。
  • 把取消位的 1 小时过期改长（取消机制的已知问题）：修好之后取消在秒级送达，过期时间不再是问题，不用单独改。

位置：引擎的 runner 主循环（只在 astream 两帧之间查 is_cancelled）。

D1：滚动部署时长命令被杀

现象

112 上跑一条 240 秒的命令，第 5 秒滚动部署 server：命令被中断（没有跑完），接手的实例读到的是被杀的输出，模型拿不到结果，也不知道为什么。L1 用例里，交接后沙箱里的命令进程以 -9 结束。

根因

停机交接时，旧实例先等「安全点」（这一批工具结果落库）；等满 60 秒还没等到，就取消 run 的任务再交出去。ShellSandbox 把所有取消都当成用户取消，顺手把沙箱里的命令中断了。

修复方案

  • ShellSandbox 被取消时，先看这个 run 的取消位：置位（用户取消）才中断命令；没置位（交接、租约丢失、进程停机）只停止跟随，执行账本原样保留。接手的实例用同一个调用重放，凭账本接上还在跑的命令（这条路径在 112 上已验证：server 崩溃、批准后崩溃、连续两次接管都能接上）。
  • 查取消位失败（Redis 不可用）时不中断：宁可让命令多跑，也不误杀。这时取消本身也送不到（D9 的检查同样依赖 Redis），行为是一致的。
  • 不需要给「取消」带上原因：asyncio 的取消原因穿过 LangGraph 的子任务时不可靠，取消位是现成的、跨实例的、可靠的判据。

位置：ShellSandbox.aexecute 的 CancelledError 分支（无条件 _interrupt_later）。

D2：假死复活的实例杀掉接管者的命令

现象

L1 用例：把 run 的租约改到别的实例名下，本实例续租时发现租约丢了，停掉本地执行，沙箱里的命令进程以 -9 结束。这时接管者已经凭执行账本接上了这条命令，结果被杀掉。

根因与修复

续租发现租约丢失后，同样是取消 run 的任务，走的是 D1 的同一个分支。D1 修好后这里自然修好：租约丢失时取消位没置位，只停跟随。

位置：执行槽的 stop_lost → task.cancel()。

3. D3：提交与记账之间崩溃会重跑

现象

L1 用例：实例在下面两个时刻死掉，接管的实例重放同一个调用，命令都又跑了一遍（副作用发生两次）。

根因

执行账本是在拿到命令 id 之后才写的。提交请求已经到了 execd、命令已经开始跑，但账本还没写，这段时间里实例一死，接管者查账本查不到这次调用，就当成没执行过，重新提交。execd 的提交接口没有客户端幂等键（命令 id 由 execd 生成），没法让它自己去重。

图 3　提交与记账的时间线。

修复方案

  • 先记后提交：提交之前先落一条记录「这次调用要在哪个沙箱执行，状态：提交中」；拿到命令 id 后补上。
  • 重放时按记录办：
    记录接管者怎么做
    有命令 id接上原命令（现有行为）
    只有「提交中」不再提交，回「结果未知」（类别 result_unknown），提示模型先检查现场再决定是否重试
    没有记录这次调用从没走到提交，正常提交
  • 记录放进库里（和检查点同一个库），不放 Redis：这条记录是防重跑的唯一依据，必须持久。每条命令多一次写库，命令本身是低频操作，代价可以忽略。顺带修好 D4 的后半（Redis 丢数据后接管会重跑）。
  • 取舍：实例死在「记了提交中、请求还没发出」的瞬间时，命令其实没跑，模型却会收到「结果未知」，要多查一次。宁可让模型多查一次，也不能跑两遍。

可选的进一步改进（暂不做）

提交时给命令包一层，开跑时先在沙箱里留一个以调用 id 命名的记号。重放时看到「提交中」，再查这个记号就能分清「没发出去」和「已经开跑」：前者可以安全重新提交。代价是用户在进程列表里看到的命令多了一层包装，实现也更复杂。等「结果未知」在实际使用中真的多起来再考虑。

位置：ShellSandbox.aexecute（先 _submit 再 ExecutionLedger.put）；执行账本现在在 Redis。

4. D5：OpenSandbox 不可达时整轮失败

现象

L1 用例：命令跟随中断过一次线（缓存的 execd 地址作废），重新取地址时 lifecycle server 恰好不可达，抛出的 LifecycleError 没被任何一层接住，直接让整轮失败，而不是变成工具错误或继续重试。

根因

跟随只接三种错误（命令不认识、沙箱没了、连不上 execd），提交只接三种（沙箱没了、连不上、被拒绝）。取地址要经过 lifecycle server，它不可达时抛的是第四种错误，没人认识。刚接管的实例没有地址缓存，第一次跟随就要取地址，所以接管期间碰上 OpenSandbox 重启也会撞上。

修复方案

  • 在执行的防腐层（取 execd 地址的那一处）翻译：lifecycle server 返回「不存在」（404）才是沙箱没了；连不上、5xx 一律算暂时连不上，和连不上 execd 同一类。
  • 于是跟随按断线重试（地址取到了就接着读），提交报「沙箱不可用」（类别 unavailable）。上层不用知道 lifecycle server 的存在。

位置：执行基座 ExecdChannel 取地址（_target → access）。

5. D7：断线放弃跟随时命令还在跑

现象

112 上断开 server 到沙箱的网络 11 分钟：约 10 分钟后平台放弃跟随，回给模型 与沙箱的连接中断且无法恢复，命令结果未知，而命令其实还在沙箱里跑。这一次模型查了进程、等它跑完，做对了；但在模型反应回放里，模型拿到这句话后 3 次都先原样重跑，其中两次重复导出后还把日志清空来掩盖。

根因

跟随断线后指数退避重连 15 次，用完就放弃。退避本身合计约 2 分钟，但断网是丢包时每次重连还要等满 30 秒的连接超时，实际能撑约 10 分钟。放弃时没有中断命令（也中断不了：连不上），提示语也没说它可能还在跑。

修复方案（推荐）

  • 重连不设次数上限：只要 lifecycle server 确认沙箱还在，就一直按同一个游标接着读，退避封顶（例如 30 秒一次）；确认沙箱没了才报「沙箱没了、结果丢失」。这样「结果未知」只剩提交途中断开一种（D3 也归到这里）。
  • 符合平台「不设运行上限、断联恢复」的原则：重连次数上限本质上是一个到点就放弃的超时。
  • 用户等不及可以取消（D9 修好后取消能送到），这时命令被中断，结果明确。

备选（如果要保留上限）

提示语改成「与沙箱的连接中断了约 N 分钟，命令可能仍在运行，结果未知。先用 ps 或检查产物确认它是否还在跑，不要直接重新执行」。改了之后用模型反应回放（PLAN-04）量化效果：现在是 1/3 通过、3/3 先原样重跑。

位置：ShellSandbox._follow 的重连（PollingPolicy.reconnects = 15）。

6. D4：Redis 丢数据后长命令可能被回收

现象（读代码发现，未实测）

闲置回收靠「这个沙箱有没有在跑的命令」来判断忙不忙，登记在 Redis 里。Redis 丢数据（重启且没持久化、被清空）后，正在跟随的长命令不会被重新登记，超过闲置时限（30 分钟）后，沙箱可能连同还在跑的命令一起被删掉。

根因

命令开始时登记一次，结束时划掉；跟随过程中读输出、问状态都不碰这本账（按设计「命令在跑本来就算忙」）。账本一丢，就没有任何东西再把它加回去。代码注释说只影响「没人跟随的长命令」，实际跟随中的也一样。

修复方案

  • 跟随时每分钟确认一次命令还在跑，就再登记一次（往集合里加同一个成员是幂等的）。只由跟随命令的一方做，不放进「查命令状态」里：会话的 bridge 这类常驻服务也会查状态，它们不能被记成在跑的命令，否则沙箱永远不闲置。
  • 执行账本随 D3 进库，Redis 丢数据不再导致接管时重跑。
  • 生产环境的 Redis 开持久化（运维项）。

位置：ActivityLedger（登记 / 划掉）；ShellSandbox._follow 定期确认。

7. D6：容器重启后没有提示

现象（读代码发现，未实测）

沙箱换了新的，下一条命令前面会加「环境已重建」的提示；但如果只是容器重启（沙箱还是同一个，比如 execd 崩了被拉起），提示不会出现，后台进程已经没了，模型却不知道。

根因

提示只比较「这个工作区上次用的是不是同一个沙箱」，容器重启时沙箱没换，比较结果相同。

修复方案

  1. 先确认：在 strict 模板下让容器重启一次，看哪些东西还在（HOME 是 emptyDir，应该还在；/tmp、已装的包、后台进程各自如何）。
  2. 跟随中撞上「execd 不认识这个命令 id」而沙箱没换时，记下「这个工作区的沙箱进程重启过」；下一条命令前加一句和实际丢失内容一致的提示（例如「沙箱进程重启过：后台进程已丢失，/workspace 与 HOME 仍在」）。提示要和实际丢失的东西一致，所以第 1 步不能跳过。

位置：ShellSandbox._notice（只比较 sandbox_uuid）。

8. D8：沙箱出站底线有缺口

现象

strict 档沙箱里实测：集群网段、K8s API 的服务地址、元数据地址都拦住了；但节点 192.168.0.112 的 22（SSH）、6443（apiserver）端口和局域网网关 192.168.0.1 都能连上。沙箱里跑的是模型写的代码，能摸到宿主机和内网。

根因

平台底线（egress sidecar 的 deny.always，优先级高于每个沙箱自己的出站策略）只写了集群 Pod 网段、Service 网段和链路本地地址，没有节点地址和局域网。

方案：放开

底线不加节点地址和局域网，只拦集群 Pod 网段、Service 网段和链路本地地址。沙箱里的命令可以访问节点和局域网，包括经节点入口（traefik）暴露的内网服务。

  • 代价：节点的 SSH、apiserver、kubelet 端口对沙箱可见，靠这些服务自身的鉴权挡住。
  • 评测 SEC-02 只判集群网段和 K8s API；节点和局域网只记录，不判定。

另外，egress-rules 脚本在 Calico 集群取错 Pod 网段的修复（11-09）还没提交，随这次一起提交。

位置：docker/egress 的 deny.always（由 deploy/local/egress-rules.sh 生成）。

9. O1：命令吃满内存，整个沙箱被杀

现象

沙箱里一条 python 命令分配 6 GiB（沙箱内存上限 4 GiB）：工具结果是「命令执行期间沙箱重启、结果丢失」，下一条命令换了一个新沙箱并带重建提示。被杀的不只是那条命令，是整个沙箱：装过的包、后台进程全部丢失。

根因（推断）

112 是 K8s 1.36、cgroup v2，kubelet 没有配置「只杀单个进程」。这种组合下，容器里任一进程触发内存超限，内核会把这个容器的所有进程一起杀掉（按组 OOM），execd 也在其中，沙箱随之不可用。

最低成本验证

再跑一次 sbf-oom，同时看沙箱 Pod 的上一次终止原因（应为 OOMKilled）和节点内核日志（按组 OOM 时，同一时刻会出现这个容器多个进程被杀的记录）。

暂不处理

接受按组 OOM：一条命令吃满内存时整个沙箱被杀、下一条命令换新沙箱并带重建提示。以后要处理时，在下面几种做法里选：

选项做法代价
Akubelet 开启「OOM 只杀单个进程」节点级设置，影响节点上所有 Pod（112 是单节点，平台服务也在上面）；某些多进程服务被杀掉一个子进程后会处于半坏状态
B接受按组 OOM，但如实告诉模型：沙箱因内存超限被重启（从 Pod 的终止原因判断），而不是笼统的「可能内存不足或被回收」，让模型知道要减小内存占用再试环境还是会丢；只改提示，改动小
C调大沙箱内存上限治标；占集群配额

位置：节点 kubelet 配置；沙箱丢失的提示在 ShellSandbox（_GONE）。
