0. 方案概览

一句话：本机 CLI 智能体也能用浏览器。浏览器跑在使用者自己的电脑上，是一个画在虚拟屏幕上的有界面 Chrome，不占用电脑的真实桌面。CLI 有两种操作方式，各配一个技能，按需选用：一种是快照，读页面清单、按元素编号点；另一种是 computer use，看截图、用系统的键盘鼠标操作。两种方式作用在同一个浏览器、同一个窗口里。computer use 不经过调试接口，网站认不出；快照暂时还用 Playwright CLI，会被 zhipin 这类网站认出（3.3）。遇到登录，智能体请人接管：这块虚拟屏幕的画面经连接器已有的那条连接传到 Atlas 网页上，人在网页里登录，然后交还。登录态留在电脑上的浏览器里，不上传平台。

打个比方：你出差在外，家里有位助理用你家书房那台电脑帮你办事。书房里专门摆了一台副显示器给他用（虚拟屏幕），你自己的主显示器他不碰。办到要输密码的地方，他通过你们一直通着的那通电话（连接器的连接）把副显示器的画面投给你，你远程把密码输进去，再把操作权交还给他。登录过的网站就留在书房那台电脑里，不寄到别处保管。

1. 背景与目标

1.1 为什么需要

  • 本机智能体要上网办事。本机 Claude Code 在电脑上写代码之外，常要操作网页：查招聘信息、在后台系统里导数据、按网页上的步骤操作。现在本机 CLI 智能体不能开浏览器，保存时直接被拒绝。
  • 电脑的网络往往更合适。沙箱浏览器从平台机房出网，很多国内网站会对机房 IP、海外 IP 多加限制。实测从大阪机房访问 zhipin，未登录时连职位列表都不给看，直接转到登录页；同一个网址在国内网络下能直接打开。电脑在家里、公司里，用的是普通宽带或公司内网，有的网站只有公司内网能访问。
  • 人不一定在电脑前。电脑可能是一台云服务器，也可能是放在家里的台式机，人在外面用别的电脑打开 Atlas 网页。要登录时，人得能从网页上看到并操作那台电脑上的浏览器。
  • 现在的自动化方式会被认出。实测 zhipin：沙箱浏览器里，模型一用 browser 命令连上，页面就跳成空白；人接管时也一样，因为同一个浏览器里一直有程序连着（3.2 的实测）。

1.2 目标

  • 本机 CLI 智能体能操作电脑上的浏览器，有两种方式可选：快照（和沙箱里的用法一样）和 computer use（看截图、用系统键鼠），在同一个浏览器里按需切换。
  • 遇到登录，人在 Atlas 网页里看到画面并操作，体验和沙箱接管一致：卡片、打开、全屏、复制粘贴、交还。
  • 电脑不开任何端口：画面只走连接器已经连着的那条连接。
  • 只共享浏览器所在的那块虚拟屏幕，不碰电脑的真实桌面。
  • 用 computer use 时，常见的自动化检测认不出来。以 zhipin 为验收：模型能打开、能读页面，人能在画面里登录。

1.3 不做什么

  • 首版只支持 Linux（包括 Windows 的 WSL）。虚拟屏幕用的是 Xvfb，macOS 上没有现成的（7 节的决策）。
  • 不用电脑主人日常用的那个 Chrome：不碰他的书签、密码、已有的登录，也不用共享真实桌面。
  • 登录态不上传平台，不进「我的登录」，和沙箱浏览器不互通（5 节）。
  • 不保证所有反爬都能过。IP 信誉、操作节奏、图形验证码，这些交给人接管处理。滑块 computer use 可以试着拖，拖不过去也交给人。
  • 不在电脑本机上另做一个看画面的入口，画面只在 Atlas 网页里看。

2. 浏览器在电脑上怎么跑

2.1 和沙箱里是同一套组件

电脑上装的浏览器组件，和平台沙箱浏览器镜像里装的是同一套：虚拟屏幕、有界面的 Chrome、每块一个画面服务、浏览器守护、browser 命令（快照和 computer use 两种操作都在这一个命令里）。屏幕按对话分块、会话各用自己的窗口、网页弹出的窗口挪回弹出它的那一块，这些做法全部沿用。只有三处不同：谁来拉起、profile 放在哪、画面从哪条路出去。

图 2　电脑上的浏览器组件：一台电脑一个 Chrome，会话各用窗口，屏幕按对话分块；所有端口只在本机

  • 一台电脑一个浏览器。这台电脑上的几个会话共用一个 Chrome，各开各的窗口，cookie 是同一份：在一个会话里登录了，别的会话也是登录状态。设备只属于一个人，所以这和沙箱里「一个人一个浏览器」是同一个意思。
  • 会话名和对话由 bridge 带上。bridge 拉起 CLI 时，把会话名和对话 id 放进 CLI 的环境里。browser 命令据此找到自己的窗口和对话那一块屏幕，模型不用管，也指定不了别人的。被委派的本机子智能体有自己的会话名，窗口放在对话那一块里。人看对话的画面时，子智能体在做什么也能看到。
  • profile 放在电脑主人的目录下，长期保留。沙箱会被回收，所以那边要把登录态存到平台。电脑上的目录不会被回收，浏览器关了再开，登录还在（5 节）。

2.2 谁来拉起、什么时候关

平台不能让电脑运行任意程序。本机 CLI 方案里平台只能告诉连接器「用哪种 CLI、在哪个目录、什么权限模式」，浏览器也照这个规矩来：

  • 模型用浏览器时：browser 命令在 CLI 的 Shell 里执行，发现守护没在跑就请连接器拉起。连接器先按本机策略核对，再拉起守护，守护再拉起虚拟屏幕、Chrome 和画面服务。
  • 人打开接管时：平台经设备网关请连接器「在这个对话那一块开接管窗口」，浏览器没在跑就先拉起。连接器只认这几件固定的事：开接管窗口、关接管窗口、接画面。
  • 闲置时关掉：一段时间没有命令、没人看画面、没有等着的接管，连接器就关掉守护和 Chrome，把内存还给电脑（一个 Chrome 约 0.5–1.5 GB）。profile 留着，下次拉起还是登录状态。闲置多久由本机策略定。

2.3 安装和开关

  • 电脑主人自己装。浏览器组件有几百 MB（Chrome 加中文字体），只有要用浏览器的人才装，用连接器的一条命令装好。两个浏览器技能（快照、computer use，教模型怎么用 browser 命令）随组件一起装进 CLI 的技能目录，版本跟着组件走。会话开始时，平台按智能体用的模型能不能看图，告诉 CLI 这次能用哪几个（3.5）。
  • 连接器上线时报告。连上平台时，连接器除了报告装了哪些 CLI，还报告装没装浏览器组件、什么版本。「我的设备」里能看到。
  • 智能体上照旧有「浏览器」开关。本机 CLI 智能体也可以打开这个开关，开了不换镜像，因为本机没有镜像。开会话时，如果电脑没装浏览器组件，一开始就提示安装命令，不等到模型第一次用浏览器才失败。

3. 两种操作方式

3.1 网站怎么认出来

程序遥控 Chrome 靠调试接口（CDP），接口按功能分「域」。Page 域管打开网址、截图，Runtime 域管在页面里执行脚本、收控制台输出。打开 Runtime 的效果，相当于替页面打开了开发者工具里的「控制台」：页面里每打印一个对象，浏览器都要把它整理好交给遥控的一方。

网站可以利用这一点埋个陷阱。常见做法是打印一个特殊对象，它只有在「有人要整理它」的时候才会被碰到。平时没人整理，它就不会被碰到；一旦被碰到，就说明有人在调试或遥控这个页面，网站随即把页面跳走。Playwright 这类工具一连上浏览器，就会给每个页面打开 Runtime，于是踩中陷阱。

图 3　同一个有界面的 Chrome，差别只在连上之后开不开 Runtime

3.2 怎么知道是这个原因：一组对照

同一台大阪的云服务器（Ubuntu，Google Chrome 157，有界面，画在虚拟屏幕上），打开 zhipin 的职位搜索页，只改「怎么连浏览器」：

组怎么连结果
A只开调试端口，没有程序连着正常（未登录，被转到登录页）
B官方 Playwright 连上（现在的 browser 命令就是这样）跳到 about:blank，读到 0 字
C直接用调试接口，只开 Page 域（在一台 Mac 上测）正常，职位列表都在
D直接用调试接口，比 C 只多开一个 Runtime 域跳到 about:blank
E修补版（patchright）连上正常，登录页能读出内容

C 和 D 只差一个 Runtime，结果一好一坏，所以原因就是它。B 是现在的做法，E 是改后的做法。A 还说明一件事：从机房 IP 访问，不登录就看不到职位，登录这一步绕不过去，所以要接管。

3.3 快照：底层暂不换

  • 快照仍用 Playwright CLI。子命令、清单格式、「按编号点」的用法和沙箱里一样，快照技能沿用沙箱浏览器的。
  • 限制：用过快照的浏览器会被认出。Playwright CLI 一连上浏览器，就给浏览器里所有页面打开 Runtime，而且一直连着，直到浏览器重新拉起。所以一台电脑的浏览器里，只要有会话用过快照，zhipin 这类网站在这个浏览器里就会被认出，跳成空白，computer use 也救不回来。
  • 应对：这类网站只用 computer use（3.5）。浏览器闲置关停后重新拉起，就恢复干净。computer use 技能里写明：页面突然变空白、跳到 about:blank，说明被认出了，停下来告诉用户，不要反复重试。
  • 以后根治：快照换成修补连接（patchright：不开 Runtime，也能拍带编号的清单，即 3.2 的 E 组）。它的版本对不上 Playwright CLI，要由浏览器守护常驻一条修补连接、browser 命令请守护代办。换了之后，两种方式在同一个浏览器里可以随便切换（3.5 末尾的算例）。这一步暂不做。

3.4 computer use：看屏幕，用系统的键盘鼠标

computer use 完全不经过调试接口：模型看的是屏幕截图，动的是系统层面的键盘鼠标，和人坐在电脑前操作一样。网页收到的就是普通的键盘鼠标事件，分不出是人还是程序。

要做的事怎么做
看截本对话那一块屏幕，包括地址栏和浏览器自己的弹窗，缩到 1280 宽交给模型。只截自己那块，看不到别的对话
点、拖、滚动、按键模型说出截图上的坐标，命令换算回屏幕坐标，用系统键鼠去做。坐标超出自己那一块就拒绝，点不到别的对话的窗口
输入文字先把文字放进剪贴板，再粘贴，中文也能输（逐个按键模拟输不了中文）

  • 守护开窗口改用只管窗口的命令。现在守护开会话窗口、接管窗口、挪窗口时，会临时用官方 Playwright 连一下浏览器，那一下也会给所有页面打开 Runtime。computer use 要干净，这几件事都改用浏览器级的调试命令：只开窗口、挪窗口，不碰页面。
  • 不连调试接口的实测（大阪 VPS，zhipin）：在地址栏里用键盘打开网址，页面正常；全选、复制拿到整页 243 字；粘贴中文进手机号输入框成功。
  • 同一台电脑只有一套键盘焦点和剪贴板。几个对话同时用 computer use 时，命令在本机排队，一次只执行一个会话的键鼠动作。每个动作都很短，排队几乎感觉不到。
  • 代价：每一步都要一张截图，比快照慢，也更费 token；要用能看图的模型。

4. 人接管：画面经连接器到网页

4.1 一次接管从头到尾

接管的登记、卡片、等待、交还，和沙箱浏览器是同一套：它是「等人决定的事」的一种，不设超时。本机这边多出来的只有两件事：「打开」和「交还」时，平台要经设备网关请连接器开、关接管窗口；画面走控制连接里的画面流。

图 5　本机接管（实线：请求；虚线：双向的画面流）。②、③、⑧、⑩ 和沙箱浏览器一样，④、⑤、⑨ 是本机多出来的

  • ① CLI 怎么请求接管。bridge 给 CLI 提供一个平台工具 request_takeover，参数只有给人看的一句话和要打开的地址，会话和对话由 bridge 带上。沙箱里的 CLI 智能体也走这一条，它现在缺的正是这条通道。用工具而不用 Shell 命令，是因为 Shell 命令有执行时限（Claude Code 的 Shell 最长 10 分钟），接管却不设期限。
  • ② CLI 怎么等。和 CLI 的权限请求一样，在线等：这一轮仍在跑，标为等人处理，bridge 和 CLI 一直在电脑上。等的时候连接断了，按本机 CLI 方案的断线恢复办：重连后会话流接回，接管还在等。连接器或电脑重启了，bridge 不在了，这一轮以失败结束，接管随之作废。
  • ④ 平台核对什么。请求者、会话创建者、设备主人必须是同一个人，和看本机文件是同一个核对。电脑不在线就直接告诉人「你的电脑不在线」，不显示「系统忙」。
  • ⑤ 连接器核对什么。本机策略允许远程查看浏览器画面；这个会话确实在这台电脑上。核对不过就拒绝，原因原样显示在卡片上。
  • ⑨ 交还时不存登录态。沙箱那边交还时要比较接管前后的 cookie，把这次登录的站点加密存到平台。电脑上的浏览器不会被回收，登录就留在它的 profile 里，这一步省掉（5 节）。

4.2 画面怎么从电脑到网页

网页是 HTTPS 页面，电脑在防火墙后面，网页既连不到、也不该直接连电脑。所以看画面的客户端（noVNC）随网页一起发布，画面数据由平台一段段转过去：网页 → server → 设备网关 → 连接器 → 电脑上这一块的画面服务。每一段只转发，不解析，不保存。

图 6　画面链路：网页和沙箱浏览器完全一样，server 按浏览器在哪选路

  • 网页这一头不变。接管卡片里的画面、对话头的「浏览器」按钮、新标签打开、全屏、复制粘贴（含中文），都和沙箱浏览器是同一个页面、同一个地址。server 按会话的浏览器在哪决定往哪转：沙箱走沙箱的画面通道，本机走设备网关。
  • 连接器只接本机浏览器的画面服务。画面流打开时只带「哪个会话」，不带端口和地址。连接器自己问守护这个对话在第几块，再接那一块的画面服务。平台借画面流连不到电脑上的其他程序。
  • 连着画面算浏览器在用。人登录可能要好几分钟，这期间没有命令在跑；不算在用的话，连接器会把浏览器当闲置关掉。

4.3 一条连接里多一路画面流

本机 CLI 方案里，一台电脑只有一条控制连接，里面分出会话流、文件流。画面流是第三种，按下面的先后顺序排队发送：

图 7　画面流排在会话流之后、文件流之前；每一路有自己的窗口，堵住只关它自己

  • 为什么排在会话流后面：画面数据比对话消息大得多（下面的算例），排在前面会让对话的过程显示变慢。
  • 为什么排在文件流前面：人在打字、点按钮，等不得；看文件慢一点没关系。
  • 互不拖累：和已有的几路一样，每一路有自己的缓冲窗口。画面这一路长时间堵住（比如网页那头网速太慢），只关这一路。网页上提示「画面断了」，人点一下就重连，对话和接管都不受影响。

算例：画面有多大、多快

项估算怎么算的
一整块屏幕的原始大小约 8 MB1920 × 1080 个像素，每个像素 4 字节
打开一个登录页（整块都变）约 100–300 KB画面服务只传变了的区域，还会压缩。网页大多是大片纯色和文字，压缩比高
输入一个字符几 KB只有输入框和光标那一小块变
一次登录（开页面、扫码或输账号密码、跳转两三次）约 1–5 MB几次整页变化，加几十次小块变化
按一个键到看见字约 0.1–0.3 秒人在国内、电脑也在国内时绕道日本服务器：网页 → 日本约 50 ms，日本 → 电脑约 50 ms，画面再原路回来。电脑就在大阪机房时，日本到电脑这一段几乎为零

对比一下，一轮对话的过程消息通常是几十到几百 KB，一次登录的画面要大一个数量级，但只在登录那几分钟里有。延迟方面，0.1–0.3 秒对打字、扫码、点按钮够用，拖滑块会觉得有点跟手慢，还能用。

5. 登录态留在电脑上

图 8　两边的登录态各管各的：沙箱的由平台保管，本机的留在电脑上

  • 不需要平台保管。沙箱会被回收，所以登录态要存到平台，下次导进新沙箱。电脑上的 profile 不会被回收，登录本来就一直在。
  • 不上传更好。电脑是使用者自己的，登录留在自己电脑上，平台少保管一份个人数据。很多网站会把登录和设备环境、IP 绑在一起，把电脑上的登录搬进机房的沙箱，或者反过来，反而容易触发风控（zhipin 这类网站尤其如此）。
  • 代价：在沙箱浏览器里登录过的网站，到电脑上还要再登录一次，反过来也一样。「我的登录」只管平台保管的那一份，页面上写清楚这一点。

6. 安全

本机 CLI 方案里，平台已经能让一台个人电脑执行命令。浏览器在这之上多给了两样东西：能看到电脑上的一块屏幕，能往里输入键鼠。下面说明这两样被限制在哪里。

问题怎么限制
谁能看画面只有本人：请求者、会话创建者、设备主人必须是同一个人，每次打开画面都核对。智能体共享给别人，别人用时浏览器跑在别人自己的电脑上
能看到什么只有浏览器所在的那块虚拟屏幕，而且只看本对话那一块。电脑的真实桌面、其他程序的窗口都不在这块屏幕上
平台能不能借画面流连别的东西不能。画面流只带会话，不带地址和端口，连接器只接到本机浏览器组件的画面服务
电脑主人能不能拒绝能。本机策略里关掉「远程查看浏览器画面」后，接管和看画面都打不开，卡片上写明原因；不装浏览器组件就根本没有浏览器
电脑上有没有对外开的口子没有。虚拟屏幕、调试接口、画面服务都只听 127.0.0.1，电脑只往外连
画面会不会留下来不会。每一段都原样转发，不落盘、不进日志
密码会不会被模型看到人输的密码、短信码只经画面进浏览器窗口，不进模型的上下文。不过 CLI 和浏览器以同一个电脑用户运行，CLI 读得到 profile 里的 cookie。这和沙箱浏览器是同一个取舍，在使用者自己的电脑上本来就是如此

7. 设计决策

决策理由
浏览器画在电脑上的虚拟屏幕里，不用电脑主人日常的 Chrome不打扰电脑主人，不碰他的书签、密码、已有登录；远程看画面只需共享这一块，不共享真实桌面。代价是和日常浏览器的登录不通，要在这里另登一次
画面经连接器已有的控制连接，不开端口、不直连电脑在路由器、防火墙后面，连不进去；复用已有的在线表和本人核对，不多一套鉴权。代价是画面要绕道平台，多几十到上百毫秒
电脑上用和沙箱同一套浏览器组件分块、窗口、弹窗、复制粘贴这些坑在沙箱上已经踩过，沿用不用重来；网页上看画面、接管的页面也就完全一样。只多出拉起方式和画面出口两处不同
加 computer use 作为第二种操作方式，和快照各配一个技能、按需选computer use 完全不经过调试接口，检测型网站认不出（3.4 实测）；画布、滑块、拖动也能做。快照点得准、省 token、纯文本模型也能用，普通网页仍以它为主
快照暂不换底层先用改动小的 computer use 覆盖检测型网站。代价是同一个浏览器里用过快照，检测型网站就会被认出，要等浏览器重新拉起（3.3）；根治办法（换修补连接）已验证可行，留到以后
守护开窗口改用只管窗口的调试命令临时连一下官方 Playwright 也会给所有页面打开 Runtime，computer use 就不干净了
文字输入走剪贴板粘贴，读文字走全选复制逐个按键模拟输不了中文；全选复制拿到的是整页纯文本，比看截图认字准，也不经过调试接口
CLI 用平台工具请求接管，不用 Shell 命令Shell 命令有执行时限，接管却不设期限；工具调用可以一直在线等，和权限请求一样。这一条通道沙箱 CLI 智能体也用，补上它的接管
浏览器由连接器拉起，闲置关停平台只能请连接器做几件固定的事，不能在电脑上跑任意程序；Chrome 吃内存，闲置就还给电脑，profile 留着所以登录不丢
登录态留在电脑上，不上传、不和沙箱互通profile 不会被回收，不需要平台保管；少一份个人数据出电脑；登录常和设备环境、IP 绑定，搬来搬去反而触发风控
画面流排在会话流之后、文件流之前画面数据大，不能挤占对话；人在操作，又比看文件急
首版只支持 Linux（含 WSL）虚拟屏幕用 Xvfb，Linux 上现成；macOS 没有，以后可以在 macOS 上用容器跑同一套组件，平台这边不用改

8. 改到的现有部分

部分改什么
智能体配置本机 CLI 智能体也能开「浏览器」（现在保存时拒绝）；开了不换镜像
连接器上线时报告浏览器组件装没装、什么版本；拉起、闲置关停浏览器守护；按平台请求开、关接管窗口；把画面流接到本机这一块的画面服务；本机策略加「远程查看浏览器画面」开关和闲置时长；一条安装浏览器组件（含浏览器技能）的命令
设备网关、设备连接控制连接里多一种通道「画面流」，优先级在会话流之后、文件流之前；转发开、关接管窗口的请求
Atlas server · 浏览器浏览器宿主多一种「设备」：接管的打开、交还经设备网关请连接器；交还时不存登录态；看画面按宿主选路（沙箱走沙箱画面通道，设备走设备网关）
bridge、CLI 运行时bridge 给 CLI 提供平台工具 request_takeover，在线等决定（沙箱 CLI 智能体同用）；拉起 CLI 时带上会话名和对话 id
浏览器守护、browser 命令加 computer use 的子命令：截本对话那一块、按坐标点击拖动滚动、粘贴输入、按键、全选复制、键盘打开网址；键鼠动作本机排队；开会话窗口、接管窗口改用只管窗口的调试命令；快照仍是 Playwright CLI；技能拆成快照、computer use 两个。沙箱的浏览器镜像加上键鼠工具后同样能用
模型平台登记模型时标注能不能看图，平台据此决定给不给 computer use 技能
网页接管卡片、画面页不变；补上电脑不在线、本机不允许查看画面时的提示；「我的设备」显示浏览器组件的状态；「我的登录」注明只含平台保管的登录态

9. 使用流程

  1. 电脑主人装浏览器组件。在电脑上用连接器的一条命令装好，连接器重连后，「我的设备」里这台电脑显示「浏览器：已安装」。
  2. 给智能体开浏览器。在智能体编辑页，给「本机 Claude Code」打开「浏览器」。
  3. 对话。比如「打开 BOSS 直聘，搜北京的 Python 职位，整理前 10 条」。Claude Code 执行 browser 命令打开网页、拍快照、读内容。对话头的「浏览器」按钮可以随时看画面，只看不操作。
  4. 需要登录。智能体发现要登录，请求接管，对话里出现卡片。人点「打开」，在新标签里全屏，用手机 App 扫码或输入账号和验证码，然后点「交还」。
  5. 接着做。智能体重新拍快照，以登录后的页面继续。
  6. 以后再用。电脑上的浏览器仍是登录状态，除非网站自己让登录过期，不用再接管。
