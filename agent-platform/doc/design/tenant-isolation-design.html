0. 方案概览

一句话：所有租户一律平等，不存在「平台租户」。智能体、知识库、技能、模型、MCP 服务这些业务资源，全部由各租户自己建、自己管，别的租户看不到。每条数据在创建时就记下属于哪个租户；所有服务的数据访问层按「这一次是替哪个租户做的」自动加上过滤条件，漏写条件的代码会直接报错，不会返回别的租户的数据。至于大家共用的设施（运行环境、容量、系统参数、系统任务），以及租户本身的开通和关闭，交给一个独立的新系统「运营中心」来管。运营人员是一个专门的「系统租户」里的人，和用别的系统一样统一登录，按模块授权；运营中心只能通过各系统专门开放的「运营接口」做事，看不到任何租户的业务内容。

打个比方：每个租户是写字楼里租了一层的公司，楼里的家具、文件和员工（智能体、知识库、模型）都归租户自己。运营中心是物业办公室：它不在任何一层楼里；物业的员工自己也租了一层（系统租户），和大家刷同一种工牌进楼，但只有这一层的人能被发物业办公室的门卡，而且按分工发——管电梯的只进得了电梯机房。物业办公室管电梯、水电、承重墙（运行环境），按合同规定每家最多能用多少电（份额），也负责办理入驻和退租；但它没有任何一层楼的门禁卡。

图 1　运营中心只通过运营接口管共用设施和租户的开通、关闭；业务资源全部在各租户里，原来的平台租户也只是一个普通租户

1. 背景与目标

用户中心已经支持多租户：一个人只属于一个租户，用户中心自己的数据也按租户自动过滤。但 Atlas 和配套服务里的数据都没有记租户，租户信息只是在调用用户中心时顺手传过去。现在看上去各租户互不相干，其实只是下面两件事顺带的效果：

  • 按人存的数据（会话、工作空间、沙箱、记忆）：一个人只在一个租户里，所以这些数据也跟着分开了。
  • 用户中心里的单条授权（比如「张三能用智能体 X」）：用户中心是按租户存的，所以这条授权只在本租户内有效。

但有三种情况会穿透这层隔离：

  • 「全部智能体 · 所有者」「全部知识库 · 所有者」这类授权，到了 Atlas 就变成「完全不过滤」。结果是，某个租户的管理员能看到所有租户的智能体和知识库。
  • 「公有」的知识库、MCP 服务、模型，是对整个平台公有，而不是只对本租户公有。
  • 模型、MCP 服务、技能、沙箱模板、运行期参数在整个平台只有一份。哪个租户的管理员拿到了对应权限，就能改所有租户都在用的那一份。

另外，平台的事现在是由「平台租户」里的管理员来做的。这让平台权限和租户权限混在同一套角色和授权里，只能靠「这个人是不是在平台租户」这个特殊判断把两者分开。

目标

  • 所有租户一律平等，不再有特殊的平台租户。
  • 一个租户的数据，别的租户看不到、改不到，运营人员也看不到。
  • 智能体、知识库、技能、模型、MCP 服务等都由租户自己建、自己管，平台不提供。
  • 平台的事交给独立的运营中心：运营权限和租户权限彻底分开，租户里的人无论怎么授权，都拿不到运营能力。
  • 运行环境由运营中心统一运营，各租户共用。按租户分份额，一个租户用满了不会影响别的租户。
  • 以后新加的代码即使漏写了租户条件，也不会串数据，而是直接报错。

不做

  • 租户之间不共享任何业务资源，包括统一提供的模型或技能。
  • 运营中心不代管租户，不能进入租户去操作。
  • 不给每个租户单独建数据库：大家共用同一套表，靠租户条件分开，和用户中心的做法一样。

2. 什么归租户，什么归运营中心

划分只看一条：带业务内容的东西归租户；不带任何租户内容、所有租户共用的东西，以及租户本身的开通和关闭，归运营中心。另外还有一类「产品自带」的东西：它们是软件的一部分，随版本发布，不属于任何人。

归谁包括谁来管
租户 智能体（含版本、数字员工）；会话、run、审批、对话里的文件；知识库、知识集；技能（上传、审核、版本）；模型和它的供应商 Key；MCP 服务和它的凭据；访问 Key（用户 Key、智能体 Key）；记忆；指令（租户指令、个人指令）；工作空间、沙箱实例、浏览器登录态、本机设备；租户设置（默认智能体、系统功能用哪个模型、每人上限等）；人、部门、角色、授权；审计记录 租户管理员，以及租户里有相应权限的人
运营中心 租户目录（建租户、停用、到期、关闭、人员名额）；应用目录（接入了哪些应用、给哪些租户开通）；运行环境（沙箱模板、可用镜像）；容量（总容量、各租户份额、用量）；系统参数（不含任何租户内容）；系统任务（巡检、兜底、清理的运行情况） 运营人员（系统租户里被授了相应模块的人）
产品自带 内置工具（读写文件、执行命令等）；和产品功能绑在一起的技能（浏览器、computer use）；记忆作用域的定义；各应用的操作码、菜单、数据编码、内置角色 随应用版本发布和登记，所有租户都一样，谁都不能改

为什么沙箱模板归运营中心

沙箱模板决定一个 Pod 能拿到多大权限，比如能不能以特权模式运行、能不能挂载宿主机目录。所有租户的沙箱都跑在同一个集群里，只要有一个租户把模板放开，它就可能通过宿主机碰到别的租户的沙箱。所以模板好比大楼的承重墙，只能由物业来管，租户只能选用。

为什么浏览器这类技能是产品自带

浏览器技能讲的是「怎么使用产品里的浏览器工具」，必须和产品版本一起升级：工具一改，技能就要跟着改。如果每个租户各存一份，产品升级后，各租户手里的旧版本就和新工具对不上了。所以它们和内置工具一样，属于软件的一部分。租户想要不同的写法，可以上传自己的技能。

运行环境共用，但彼此不通

  • 沙箱和会话 Pod 跑在同一个集群里。每个 Pod 都记着它属于哪个人、哪个租户，用来算份额和回收。
  • 不同人的沙箱之间，网络互相不通。
  • 沙箱访问不到平台内部的服务。原因是平台内部服务之间是凭请求上写的身份互相信任的，谁能直接连上它们，谁就能冒充任何租户里的任何人。

3. 运营中心

3.1 为什么单独做一个系统

  • 运营权限不进业务系统。如果平台的事散在各业务系统里，每个系统都得判断「这个人能不能做平台的事」，漏写一处，租户管理员就可能拿到平台能力。单独一个系统之后，业务系统里就只剩租户权限：运营人员虽然也在一个租户（系统租户）里，但「是不是系统租户」只有用户中心和运营中心认，业务系统里没有这个判断。
  • 没有平台租户。系统租户在业务系统里没有任何特殊能力，用户中心、Atlas 里所有和「平台租户」有关的特殊处理都可以去掉。
  • 「看不到租户内容」是靠结构保证的。运营中心只能调用运营接口，而运营接口里根本没有读取业务内容的功能（见 3.5）。

3.2 运营人员与权限

  • 运营人员在系统租户里。用户中心给租户加一个「系统租户」标记；运营人员是系统租户里的人，用用户中心的账号统一登录，登录、改密、锁定、停用都和登录别的系统一样，运营中心不再有自己的账号。
  • 只有系统租户能用运营中心。运营中心在用户中心里是一个只能开给系统租户的应用：普通租户开不了它，它的人怎么授角色都进不来。这个判断只在用户中心一处。
  • 按模块授权。运营中心按「管哪个系统」分模块：租户，以及每个接入的系统一个（用户中心的应用目录、Atlas、知识库、技能、MCP 网关、模型平台、记忆服务）。每个模块在用户中心里是一个数据编码，系统租户的管理员给人授它的级别：只读能看，读写能改，Owner 还能做不可恢复的操作（如关闭租户、补发临时密码）。同一个人可以「MCP 网关能改、模型平台只能看」。
  • 角色和别的系统一样。角色、操作码都在用户中心配；运营中心只有一个不属于任何模块的功能——看全部运营审计，放在角色里。
  • 系统租户保护自己。系统租户由用户中心部署时创建，运营中心不能停用、关闭它，免得把所有运营人员锁在门外。系统租户里只放运营团队，不放业务数据。
  • 运营中心和别的系统挂在同一个入口、经同一个网关；普通租户的人能打开页面，但进不去。

3.4 怎么连到各系统

图 2　以「给租户 A 调份额」为例：运营中心不自己存份额，而是通过 Atlas 的运营接口去改 Atlas 自己的数据

  • 数据留在用它的系统里。真正执行这些规则的是各业务系统：建沙箱时要读模板，派发 run 时要查份额。数据就放在用它的地方，这样不会出现两份数据对不上的情况。运营中心本身只是管理界面加上运营审计。
  • 运营接口比普通内部调用要求更严。它可以跨租户操作，分量更重，所以必须核对调用方确实是运营中心。
  • 两边都记审计。运营中心记录「谁在什么时候做了什么」；业务系统也记录是哪个运营人员通过运营中心改的。
  • 运营接口在「系统范围」里执行（第 6 节）。涉及某个租户时，只能做这几件事：开通时为它建配置、关闭时删它的数据、改它的份额、看它的用量。

4. 每条数据都记着租户

  • 归属在创建时就定下，之后不会改变。不支持把数据从一个租户搬到另一个租户。
  • 每张业务表都记租户，而不只是最上层的那条数据记。比如运行事件，不靠「事件 → run → 会话 → 租户」一层层往上推，而是自己就记着租户。原因有两个：自动过滤（第 6 节）只能看到当前查询的这张表；后台按 id 直接查子数据时（比如按 run 的 id 取事件），也需要受到保护。多存一列，换来的是全系统只用遵守一条规则。
  • 对象存储的第一层目录就是租户。按租户统计用量、关闭租户时删除数据，都直接按这层目录来做。
  • 向量：每个知识库各有一个向量集合。检索之前，已经按租户和权限挑出了能用的知识库，所以不会查到别的租户的集合。
  • 名字只需要在租户内唯一。智能体标识、技能名、模型名、MCP 服务名都是这样，两个租户可以各有一个叫 minimax-m3 的模型。智能体配置里照旧按名字引用，只在本租户里查找，所以现有的引用方式不用改。
  • 名字进入共用设施时要带上租户。模型网关的路由、技能文件的存放位置、集群里的标签，一律使用「租户 + 名字」。

图 3　左：数据从上到下每一层都记着租户；右：两个租户可以用同一个名字，进入共用设施时带上租户区分

5. 租户上下文：每次读写都知道替谁做

每次读写数据之前，都要先确定「这一次是替哪个租户做的」。租户上下文有五个来源，来源不同，可信程度也不同：

图 4　租户上下文的五个来源：只有网关写的租户直接采用（还要经用户中心核对），其余的都从记下的数据里取；运营中心不进入任何租户

  • 为什么用户中心核对一下就够了：用户中心只会在请求上写的那个租户里找这个人。所以不管是租户写错了，还是有人冒用别的租户，都过不了身份解析这一关。
  • 后台任务不再拿人去反查租户。run、知识库入库、记忆补记这些任务，处理的都是某一条具体数据，而这条数据本身就记着租户。
  • 服务之间调用时，原样带上租户。比如 Atlas 调知识库、MCP 网关、模型平台、记忆服务，或者业务应用（TeamFlow、评测）调 Atlas，都要带上这次调用的租户。被调用的服务按同一套规则再核对一次。
  • 没有租户上下文，说明代码有问题。这时直接报错，而不是退回成「不过滤」。

6. 自动过滤：漏写条件也不会串

业务代码不需要、也不应该自己写「且租户 = A」。这件事由每个服务的数据访问层统一来做：

  • 读、改、删：只要查询涉及租户数据，就自动加上「租户 = 当前上下文」。连表查询和子查询里涉及的也一样。
  • 新增：自动填上当前租户。如果在 A 的上下文里写入属于 B 的数据，直接拒绝。
  • 没有租户上下文：只要碰到租户数据就报错。这样漏设上下文的代码，在测试里第一次运行就会暴露出来。
  • 系统范围：需要跨租户时必须显式声明，而且只允许以下几处：系统巡检取待办、运营接口（统计用量、改份额、删除租户数据）。

这和用户中心现在用的是同一套规则。用户中心已经这样在运行了，各服务按同样的约定来做。

7. 权限：先分租户，再看授权

判断一个人能看到什么、能做什么，按固定顺序过三道关。第一道是租户：它不看任何授权，谁都绕不过去。

图 6　顺序是租户 → 数据权限 → 操作码；「全部 X」授权和「公有」都只在本租户内有效

  • 数据权限本来就是按租户存的。用户中心按租户保存授权，到了 Atlas 又先按租户过滤过一遍，所以「全部智能体 · 所有者」自然只覆盖本租户，不需要任何特殊处理。
  • 数字员工建在智能体所在的租户里。它只能拿到本租户的授权，所以以 Agent 为权限的智能体，也只能碰到本租户的资源。
  • 业务系统不知道租户状态。各系统只认角色权限和数据权限，都从用户中心取；租户停用、到期或删除后，用户中心对这个租户的人一律返回无权限。业务系统不存租户状态、不判断租户停没停用，停用、恢复时也不用通知它们。
  • 业务系统和用户中心里只有租户权限。不再有「平台级操作码」「平台级菜单」，也不再有「这个人是不是在平台租户」的判断。用户中心的超级管理员也只管本租户。平台的事只在运营中心里，按运营中心的模块授权来判断（3.2）；「是不是系统租户」只有用户中心和运营中心认。

8. 模型、MCP、技能由租户自己管

模型

租户管理员用自己的供应商账号登记模型，费用直接记在租户自己的账号上。访问 Key（用户 Key、智能体 Key）也属于租户，只能用本租户的模型。

图 7　Key 属于哪个租户，就只在那个租户的模型里查找

  • 系统功能用的模型也由租户自己选。会话标题、自动模式判断器、记忆补记、知识库的向量模型，都从本租户的模型里选。没选的话就降级：标题取消息的开头，判断器交给人来决定，记忆不补记。知识库必须先选好向量模型才能创建。
  • 新租户一开始一个模型都没有。租户管理员要先登记模型，然后才能建智能体（第 10 节）。

MCP 服务

租户自己登记 MCP 服务和它的凭据。智能体 Key 只能用本租户的服务；「公有」的服务也只对本租户公有。

技能

租户自己上传技能，由本租户的审核人审核，版本号也在各租户内各自编排。智能体只能选本租户的技能和产品自带的技能。

租户填写的地址不能指向平台内部

模型和 MCP 的上游地址是租户自己填的，平台的网关会替它去连接。平台内部服务之间是凭请求上写的身份互相信任的，如果租户能让网关去连平台内部的地址，就等于借网关冒充别人。所以登记时要检查一次地址；每次真正连接之前，还要按解析出来的 IP 再检查一次，防止域名先指向外网、事后又改成指向内网。

智能体只能引用本租户的东西

保存智能体时，会检查它引用的模型、技能、MCP 服务、知识集是否都在本租户里（技能也可以是产品自带的），沙箱模板是否是运营中心发布的。运行时也按本租户去解析这些引用。即使有人直接改配置、写进了别的租户的名字，也只会得到「找不到」。

9. 配额：运营中心管总量，按租户分份额

共用设施分三层来管：

  1. 总容量：部署了多少执行能力和集群资源，总量就是多少。运营中心显示总量和当前的占用情况。
  2. 租户份额：运营人员在运营中心给每个租户定一份；新租户先用默认份额。
  3. 每人上限：租户管理员在本租户份额以内自己设定；不设就用默认值。

按这三层管的资源有三种：同时运行的 run、同时存在的沙箱和会话 Pod、存储（工作空间文件、知识库文件）。

10. 租户的一生

图 9　开通 → 准备 → 使用中 ⇄ 停用 → 关闭；都由运营中心发起：开通、关闭要调各系统，停用、恢复只改用户中心

  • 新租户是空的。平台不提供任何模型、技能或智能体。租户管理员第一次进来时，界面引导他先登记一个模型。
  • 开通和关闭要各系统参与。运营中心先在用户中心建租户，再按登记逐个调各系统的「创建」，让它们为这个租户准备自己要用的配置（如知识库记存储份额、技能装默认技能）。各系统怎么接入由运营接口库（中间件）规定：它定好接口地址和一个要实现的类，系统只写「创建做什么、删除删什么」两段逻辑，新接入的系统照着实现即可；新登记的系统由运营中心给已有租户补建一次。
  • 停用、恢复只在用户中心。业务系统不知道租户状态（第 7 节）：停用后用户中心对这个租户的人一律返回无权限，什么新请求都做不了；到期也一样，不用另外发起停用。恢复就是用户中心放开，权限回来，数据都在。
  • 停用不会立即叫停已经在跑的后台工作。在跑的 run 等再取权限时拿不到权限，相关操作就失败；用不到权限的部分会跑到结束，沙箱等资源靠闲置回收。哪个系统需要停用即停，以后再单独加。
  • 关闭时显式删除。只能关闭已停用的租户。由运营中心依次让各系统删除这个租户的数据，最后再删除用户中心里的租户。因为每张表都记着租户，对象存储也按租户分了目录，所以能删干净，不会漏。
