运营中心设计：运营人员在系统租户里，按模块授权

一句话：运营中心不再有自己的账号。运营人员是用户中心里「系统租户」的人，和用别的系统一样统一登录、请求经 API 网关验访问 JWT；能不能进运营中心，看用户中心的授权快照（运营中心这个应用只能开给系统租户）；进来之后能做什么，按模块判——运营中心分成租户模块和每个系统一个模块，每个模块在用户中心里是一个数据编码，授「只读 / 读写 / Owner」。角色只管不属于任何模块的功能，现在只有看运营审计。

这份设计回答四个问题：运营人员是谁、怎么登录；一个人能运营哪些模块、到什么程度，在哪里授；一个请求进来后依次判什么；「系统租户」这个特殊的租户在哪里被认出来、怎么防止把自己锁在门外。运营中心怎么经运营接口开通、停用、关闭租户，见多租户隔离设计；网关怎么验 JWT、怎么路由，见API 网关设计。下面只讲原理，具体的类、表和交互见文末各图。

先认识几个词

词意思例子
系统租户用户中心里打了「系统租户」标记的租户。它在 Atlas、知识库这些业务系统里和别的租户完全一样；唯一的不同是：只有它的人能被开通运营中心。用户中心部署时用命令建，运营中心不能停用、关闭它。「平台运营」，企业代码 platform。小周、老李都是它的员工。
仅系统租户的应用用户中心应用目录里的一个标记：这个应用只能开给系统租户。运营中心就是这样一个应用（编码 opscenter）。星河科技的管理员在用户中心里找不到「开通运营中心」；就算硬建了同名角色，取授权快照也是不可访问。
运营模块运营中心按「管哪个系统」分的块：租户模块，加上每个登记的系统一个（用户中心、Atlas、知识库、技能、MCP 网关、模型平台、记忆服务）。每个模块在用户中心里是一个数据编码。MCP 网关模块的数据编码是 OpsMcp，里面是 MCP 网关的系统参数、系统任务。
模块授权在用户中心给人（或部门）授某个模块数据编码的「全部」级别：只读能看，读写能改，Owner 还能做不可恢复的操作。和给人授「全部智能体 · Owner」是同一个功能。小周：MCP 网关 · 读写，模型平台 · 只读。
ops:audit运营中心唯一的操作码：看全部模块的运营审计。放在内置角色「运营审计员」里。审计员小陈没有任何模块授权，只有这个角色：看得到谁改过什么，自己什么都改不了。
运营接口各业务系统专门开给运营中心的一组接口（/ops/v1），网关不转发，每个请求验运营中心的签名。运营中心判完模块权限，才经它去改业务系统。MCP 网关的 PUT /ops/v1/configs/{key}：改一个系统参数，请求上写明是小周改的。

原理 1　运营人员是系统租户里的人，统一登录

小周早上打开 /opscenter-ui/。运营控制台和 Atlas 控制台一样，发现没登录就跳到用户中心的统一登录页；登录之后，请求经 API 网关验访问 JWT、写上身份头，才到运营服务。运营服务再问用户中心「这个人能不能用运营中心」：

  1. 1登录页、登录接口、访问 JWT、刷新令牌都和登录 Atlas 是同一套。密码错几次锁定、首次登录改密码、停用账号，都由用户中心处理；运营中心没有自己的账号表和会话。
  2. 2运营中心和其他系统一样挂在 Atlas 站点：页面 /opscenter-ui/，接口 /opscenter/（auth 路由）。网关只验 JWT、写身份头，不知道谁是系统租户——它对运营中心没有任何特例。
  3. 3「能不能进」由用户中心一处判，运营中心照用别的系统都在用的授权快照。普通租户开不了运营中心这个应用，它的人怎么授角色都拿不到「可访问」。快照在运营服务里缓存 30 秒。

原理 2　每个模块一个数据编码，级别决定能做什么

运营的活按系统分工：管 MCP 网关的人只该碰 MCP 网关。所以运营中心分成模块，每个模块在用户中心里是一个数据编码；系统租户的管理员在用户中心的「数据权限」里给人授这个编码的「全部」级别——和给人授「全部智能体 · Owner」是同一个功能。下面是平台运营里四个人的授权：

模块只读：看读写：日常变更Owner：再加不可恢复的操作
租户租户列表、详情、操作进度开通、停用、恢复租户；给租户开通或关闭应用；给新登记的系统补建；立即重试关闭租户（删掉它在所有系统里的数据）；补发首个管理员的临时密码
用户中心应用目录接入应用、启停；维护应用的操作码、菜单、数据编码、内置角色轮换应用凭据（接入方会立刻断开）；删除应用
每个业务系统份额与用量、系统参数、系统任务、运行资源改份额和系统参数；修订、发布沙箱模板；上架、下架市场技能；改记忆作用域目前没有
  1. 1一个人在不同模块可以是不同级别，这是选数据权限而不选角色的原因：角色按人授，「MCP 能改、模型只能看」这种按模块不同的事，角色表达不了；用操作码表达「哪个模块」，又违反了「操作码只表达能不能做某类事」的约定。
  2. 2控制台只显示有级别的模块；级别不够的按钮置灰、不隐藏。小周登录后只看得到 MCP 网关、模型平台两个模块。
  3. 3授给部门也行，取本人和所在部门里最高的那个级别。收回授权、停用账号都在用户中心做，最长 30 秒后在运营中心生效。

原理 3　一个请求依次判什么

以小周改 MCP 网关的一个系统参数为例（完整交互见登录并运营一个模块）：

  1. 1每个接口都声明自己属于哪个模块、要什么级别：看要只读，改要读写，不可恢复的要 Owner。系统模块的接口是一个通用的「系统代理」，模块就是路径里那个系统的模块，GET 要只读、其余要读写。运营中心自己的路径里不出现 /ops/ 段，否则网关会当成内部端点 404。
  2. 2判权限只有一条规则：这个人在这个模块的级别 ≥ 这个动作要的级别。跨模块的功能只有查运营审计，要操作码 ops:audit。
  3. 3业务系统不再判小周的权限：它只认运营中心的签名，请求上写的运营人员只用来记日志、和运营中心的审计对上。运营中心契约里没有读租户内容的接口，判权限之前和之后都碰不到租户内容。

原理 4　系统租户只在两处被认出来

系统租户不是原来的「平台租户」：它在业务系统里没有任何跨租户的能力。认得它的只有用户中心和运营中心，各自只为一件事：

  1. 1不能停用、关闭系统租户，是为了不把自己锁在门外：运营人员都靠它登录，停了它就只能改库恢复。用户中心和运营中心各挡一次。
  2. 2别的应用的目录由运营人员在运营中心录入，代码里只留判断用的编码；运营中心自己的目录是例外，随代码同步——第一个人登录之前目录里就得有它，而且模块来自系统登记，新接入一个系统时在登记里写上它的数据编码，重启后用户中心里就多一个编码。
  3. 3系统租户的管理员是平台上权限最大的人：他能在用户中心给任何人（包括自己）授任何模块的 Owner。所以系统租户里只放运营团队，不放业务数据，也不要拿原来的平台租户改成系统租户（它有业务数据，而系统租户永远关不掉）。

设计决策

决策理由详见
运营人员是用户中心里系统租户的人；运营中心不再有自己的账号、会话和登录和其他系统一样统一登录，密码、锁定、改密、停用都在用户中心一处，少一套账号体系。代价：用户中心不可用时运营中心也登不了；原来「运营账号和任何租户都无关」的隔离，改由「只有系统租户能开通运营中心」来保证。权限与审计
系统租户只是一个标记，只有用户中心和运营中心认它业务系统不用写「是不是系统租户」的判断，系统租户在那里拿不到任何跨租户的能力；用户中心用它决定运营中心开给谁，运营中心用它保护自己。权限与审计、租户
能不能进运营中心由用户中心判：运营中心应用标「仅系统租户」判断只在用户中心一处，网关和运营中心都不判租户；普通租户怎么授角色、建同名编码都拿不到「可访问」。登录并运营一个模块
每个模块一个数据编码，授「全部」级别；级别决定能做什么和 Atlas 按智能体授只读 / 读写 / Owner 同一套，模块就是运营中心的「数据」；同一个人在不同模块可以是不同级别，角色表达不了。权限与审计
不可恢复的操作要 Owner关闭租户删掉它在所有系统里的数据，补发临时密码等于拿到一个租户的管理员，轮换凭据让接入方立刻断开；和 Atlas「只有 Owner 能删」一致，日常运营给读写就够。租户
角色只管跨模块的功能，现在只有 ops:audit操作码只表达「能不能做某类事」；看审计不属于任何模块，审计员要看全部、却不该改任何东西。权限与审计
模块 = 租户 + 每个登记的系统；数据编码写在系统登记里运营按系统分工；新接入一个系统只在登记里写上编码，运营中心不用改代码。系统接入
运营中心自己的应用目录随代码同步进用户中心（和用户中心自己的目录一样，是例外）第一个人登录之前目录里就得有它；模块来自系统登记，手工录入会对不上。只同步目录，授权始终由人在用户中心做。权限与审计
系统租户不能停用、关闭，也不能在运营中心开通运营人员都靠它登录，停了就把自己锁在门外；它由用户中心部署时的命令建。租户
运营中心挂在 Atlas 站点（/opscenter/、/opscenter-ui/），走 auth 路由；名字不叫 ops网关对它没有特例；/ops/ 是网关的禁区段，叫 ops 会整个 404，运营中心自己的路径也不含 /ops/ 段。代价：和租户业务共用站点和登录态，有模块授权的人被盗号就能进运营中心，靠只授必要的模块、不可恢复的要 Owner 收窄。网关路由表
授权按（用户，租户）缓存 30 秒每个请求都问用户中心太慢；运营权限大，收回授权最长 30 秒生效，比 Atlas 的 5 分钟短。权限与审计
