多租户隔离设计：数据只属于租户，平台的事归运营中心

一句话：每条业务数据都记着租户，各服务的数据访问层按「这一次替哪个租户做」自动过滤，漏写条件会报错而不会串数据；所有租户一律平等，没有平台租户；平台的事交给独立的运营中心，它只经各系统的运营接口做事，看不到租户的业务内容；运营人员是系统租户里的人，统一登录、按模块授权。

这份设计回答四个问题：一次读写怎么知道是哪个租户的、漏写了怎么办；租户上下文从哪来、哪些来源可信；平台的事（开通、停用、关闭租户，运行环境，容量）谁来管、怎么管才看不到租户内容；共用的设施怎么按租户分。方案正文（什么归租户、什么归运营中心，以及过渡办法）见方案设计；运营人员怎么登录、怎么按模块授权，见运营中心设计。下面只讲原理，具体的类、表和交互见文末各图。

先认识几个词

词意思例子
租户一个使用平台的组织。人和数据都只属于一个租户；所有租户地位相同。星河科技、远山律所。原来的「平台租户」现在也只是其中一个。
租户上下文「这一次读写是替哪个租户做的」，放在协程的上下文里（contextvar）：一处设定，同一个请求或 run 里开的数据库会话、发的下游请求都看得到。张三在网页上发消息：这个请求的上下文是星河科技；这条消息的 run 在后台跑时，上下文也是星河科技。
自动过滤数据访问层给每个涉及租户表的查询自动加「租户 = 当前上下文」，给新行自动填租户。业务代码不写租户条件。SELECT … FROM agent 实际执行的是 … WHERE tenant_uuid = 星河科技。
系统范围显式声明「这一次不过滤」，是唯一能跨租户的口子。只有两种用途：巡检取待办、运营接口。兜底任务找出所有该续跑的 run 和它们的租户，再一条条进入各自的租户去跑。
运营中心管平台本身的独立系统：开通、停用、关闭租户，运行环境，容量，系统参数，系统任务。运营人员是系统租户里的人，按模块授权（见运营中心设计）。运营人员小周用系统租户的账号统一登录，在 Atlas 模块里给星河科技把份额从 20 调到 40。
运营接口各业务系统专门开给运营中心的一组接口：挂在 /ops/v1，网关不转发，每个请求验运营中心的签名。地址和各系统要实现的类由运营接口库（中间件）统一定好。里面没有读租户内容的功能。知识库的 PUT /ops/v1/tenants/{id}：开通时为新租户记下存储份额。
份额一个租户最多同时占多少共用设施：同时运行的 run、同时存在的沙箱、存储。运营中心定，租户管理员在份额内再定每人上限。星河科技同时最多 20 个 run，张三最多 3 个。

原理 1　每条数据都记着租户，读写自动过滤

每张业务表（包括运行事件、分段这样的子表）都多一列租户，建的时候就填上、之后不变。各服务引用同一个租户隔离库，由它在数据访问层统一加条件，业务代码不写也不应该写租户条件：

  1. 1请求进来、后台任务开始时，先进入一个租户的上下文（从哪来见原理 2）。它放在协程的上下文里，这个请求里开的每个数据库会话、发的每个下游请求、拼的每个对象存储路径都看得到；并行的工具调用、子智能体这类子任务自动继承。
  2. 2数据访问层挂在 SQLAlchemy 的事件上：查询、ORM 更新和删除里出现的每张租户表（连表、子查询也算）都自动加上租户条件。所以「全部智能体 · 所有者」这样的授权、标成「公有」的知识库，到这一步已经只剩本租户的了，不用另外处理。
  3. 3没有上下文时碰租户表直接报错，漏设上下文的代码在测试里第一次运行就会暴露。需要跨租户必须显式进入系统范围，而且要说明原因，只有「巡检取待办」「运营接口」两种。这套规则和用户中心现在用的一样。

原理 2　租户上下文从哪来

租户上下文的来源不同，可信程度也不同。只有网关写上的租户直接采用，而且要经用户中心核对；其余的都从已经记下的数据里取，不认任何人自己报的租户：

为什么用户中心核对一下就够了：用户中心按请求上写的租户建立自己的租户上下文，只在这个租户里找人。请求上的租户写错了、或者被冒用了，在身份解析这一步就过不去。服务之间调用时原样带上租户，被调的服务按同一套规则再核对一次。

原理 3　运营中心只经运营接口做事

没有平台租户之后，平台的事由独立的运营中心来管。它碰业务系统只有一条路：各系统实现的运营接口契约。契约按能力分组，系统在登记里声明自己实现哪几组；运营中心能做的就只有这些：

  • 看不到是结构保证的，不是权限挡的。契约里根本没有读租户内容的方法，就算运营人员的账号被盗、运营中心有漏洞，也只能做这几类事。
  • 运营权限不进业务系统。运营人员是系统租户里的人，但业务系统里没有平台级的操作码，也没有「是不是系统租户」的判断：系统租户在那里就是个普通租户。能不能进运营中心、能运营哪些模块，只在用户中心授（见运营中心设计）。原来的平台管理接口（沙箱模板、配置项、定时任务、租户管理、应用接入）都移成运营接口。
  • 数据留在用它的系统里。租户名单在用户中心，份额、沙箱模板、系统参数在 Atlas 等各自的系统里；运营中心只存运营审计和租户操作的进度。
  • 业务系统不知道租户状态。契约里没有停用、恢复：停用只在用户中心挡住，这个租户的人登录不了，各系统取角色权限、数据权限时一律拿到无权限。业务系统只管权限，不存、不问租户状态；到期也一样，由用户中心算作停用。

原理 4　租户操作：拆成步骤、记进度、失败一直重试

开通和关闭要按固定顺序调好几个系统，任何一步都可能超时；停用、恢复只改用户中心一处。运营中心把一次操作记成按系统排好的步骤，由后台任务一步步推进，每做完一步记一次进度。以开通为例：

  1. 1顺序固定：开通先在用户中心建租户，再按登记逐个调各系统的创建，让它们为这个租户准备自己要用的配置（份额、默认技能等）；关闭反过来，各系统先删完自己的数据，最后才删用户中心里的租户。停用、恢复只是用户中心挡住或放开。同一个租户同一时间只能有一个进行中的操作，关闭只能对已停用的租户做。
  2. 2业务系统怎么接入，由运营接口库（中间件）定好：创建、删除两个接口地址，和一个要实现的类 TenantLifecycle。新接入的系统只写「新租户要准备什么」「删租户时数据库之外还要删什么、表按什么顺序删」，登记到运营中心后，运营中心给已有租户补建一次。
  3. 3失败不放弃：按退避一直重试，界面上标出卡住的步骤，修好后可以立即重做。各系统的创建、删除都能重做（再建一次结果一样，删除每次删剩下的），超时后重做不会出错。删除是分批的：对方说「还有剩」，这一步就马上再做一次。

原理 5　份额：运营中心管总量，按租户分

共用设施分三层管。准入点在 Atlas 自己：认领 run、登记新沙箱时，在同一个事务里先锁住这个租户的份额行，再数用量、再判，所以精确不超：

设计决策

决策理由详见
每张业务表都记租户（包括子表），读写自动过滤，没有上下文就报错自动过滤只看得到当前查的这张表；后台按 id 直接查子数据也要受保护。漏写条件报错而不是返回全部，测试第一次跑就暴露。租户隔离库
系统范围必须给原因，只有「巡检取待办」「运营接口」两种系统范围就是不过滤，是唯一跨租户的口子；收成两个有名字的用途，评审时一眼看出哪里在跨租户。租户隔离库
没有平台租户；平台的事归独立的运营中心；运营人员是系统租户里的人，按模块授权系统租户只在用户中心和运营中心被认出来，在业务系统里就是普通租户，各系统不用写特殊判断；运营人员和其他系统一样统一登录，不用另一套账号。运营中心设计、权限与审计
运营中心只经运营接口做事，契约里没有读租户内容的方法；每个系统一把运营密钥，请求签名看不到靠结构保证；运营接口能跨租户、能删数据，内部服务之间凭请求头互信那一套不够用。签名防重放，一把密钥泄露只影响一个系统。系统接入、运营接口库
数据留在用它的系统里，运营中心只存审计和操作进度执行规则的是各业务系统自己（派发 run 查份额、建沙箱读模板）；存两份就要对账。运营中心容器图
租户操作拆成步骤、存进度、后台推进；失败一直重试，不放弃关闭要删的数据可能很多、任何一步都可能超时；半开通、半删除的租户比失败更糟，修好对方后自动接着做。租户
业务系统不知道租户状态，只认角色权限和数据权限；停用、恢复只改用户中心租户归用户中心管。各系统存一份就要同步，停用还得逐个系统通知，哪个没通知到就不一致；停用、到期、删除后用户中心对这个租户的人返回无权限，一处生效。代价是在跑的后台工作不会被立即叫停，它们再取权限时失败。租户
租户接入由运营接口库规定：两个接口地址、一个要实现的类（创建、删除）新接入一个存租户数据的系统，要做什么一目了然；地址、签名、租户上下文、分批删行都在库里，各系统不会各写一套。创建、删除都能重做，不用按幂等键去重。运营接口库、系统接入
份额存在 Atlas；run 和沙箱在认领的事务里锁租户行，精确不超；满了 run 排队先数再建在并发时是软上限；锁一行让同一租户的认领串行，不同租户互不影响。run 已经提交，排队等空位最符合预期。容量
运行期参数分系统参数和租户设置；租户由调用方显式传入影响所有租户的归运营中心，只影响一个租户的归租户管理员；租户设置没改过就跟着运营中心定的系统值走。应用配置库、租户设置
模型属于租户：系统功能的模型按租户绑定，能力表按供应商模型名查、随版本发布没有平台提供的模型；租户可以随便给模型起名，按租户起的名字查能力迟早查错。模型接入

时序图

图看什么
一次请求和一个 run 怎么带上租户原理 1、2 的完整交互：网关写租户、用户中心核对（第 4 步）、自动过滤（第 8 步）、run 按会话的租户进入（第 10 步）、调知识库带上租户（第 12 步）。
run 按租户份额排队原理 5：认领事务里锁份额行、数在跑的 run；满了排队并推「排队中」；空出位置后兜底任务接走。
运营人员登录并运营一个模块统一登录、授权快照、各模块级别、按模块判权限，再经运营接口改 MCP 网关的参数。
开通租户第一步在接口里同步跑、临时密码只出现一次；之后按登记逐个调各系统的创建，知识库超时后退避再建一次。
停用租户只有一步：用户中心挡住；之后这个租户的人取权限一律无权限，业务系统不收通知。
关闭租户只能关已停用的；各系统经运营接口库的删除接口分批删（先外部资源后数据库，「还有剩」就再做一次）；最后删用户中心里的租户。
