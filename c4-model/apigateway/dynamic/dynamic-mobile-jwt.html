    全端统一 JWT 原理：同一套验签内核、载体差异最小化、安全轮换与多 kid 换钥

    一句话：Web 与 Mobile 共用同一套 Access JWT（15m Ed25519）与 Refresh Token（14d Redis 轮换），在网关侧完全走同一个 JWT 认证器 本地离线验签，唯一差别只在传输载体（Web 走 HttpOnly Cookie + CSRF，Mobile 走 Bearer 免 CSRF）。下面三张图讲清：全端统一对照、Refresh Token 轮换与 30s 弱网宽限、Ed25519 多 kid 公钥无感轮换。

    图 1　Web（Cookie）与 Mobile（Bearer）全端统一 JWT 对照

    图 2　Refresh Token 轮换与 30 秒弱网并发宽限（Web 与 Mobile 共用）

    1. 1Web 与 Mobile 客户端均在 HTTP 拦截器加单飞锁：并发请求同时遇到 401 时只发一次刷新，避免误触发并发冲突。
    2. 2服务端用 Lua 原子消费旧 RT 并写入新 RT，同时核查 PG 用户与租户状态，被停用账号在这里被彻底拒签。
    3. 3旧 RT 保留 30 秒幂等宽限，兼顾 Web 多 Tab 同时到期和手机弱网丢包重传。

    图 3　Ed25519 公私钥隔离与多 kid 无感密钥轮换

    为什么这样做

    做法为什么
    全端共享一套 JWT 签发与验签内核开发与测试量直接减半，网关不需要维护两套截然不同的会话与令牌代码，排查问题口径完全一致。
    用 Ed25519 非对称签名而非 HS256 共享密钥网关只拿公钥不碰私钥，降低密钥泄露爆炸半径，同时支持多 kid 平滑轮换。
    Access JWT 只含 sub(uid)、tid(tenant_id)、mcp保持令牌轻巧且不缓存易变权限；下游业务继续向用户中心查实时授权快照，改权限秒级生效。
    Refresh Token 存 Redis 哈希并启用轮换既支持主动登出立刻作废刷新能力、又支持 14 天长期免登录体验，同时在换票时复核账号与租户启用态。
