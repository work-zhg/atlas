    长连接与流式代理原理：零缓冲分级传输、WS 天然适配 Cookie JWT、滚动发布无感续传

    一句话：Atlas 的流量不是普通短 REST，而是短接口 + 大上传 + 超长 SSE + 双向 WebSocket混跑。网关通过分池 Transport、零缓冲 Flush、显式 WS 白名单隔离四类流量；而且 Web 端把 JWT 放在 HttpOnly Cookie 里，正好天然解决了浏览器原生 new WebSocket() 无法自定义 Authorization 头的老大难问题。下面三张图讲清：四类流量的传输分级、两类 WebSocket 差异、滚动升级排空时序。

    1. 1收到 SIGTERM 后先摘除就绪探针，留出几秒等待负载均衡刷新 Endpoints，确保不再接收新的建连请求。
    2. 2所有在途短请求（保存智能体、上传文档等）正常返回，不出现 502 截断。
    3. 3已有 SSE 流断开后，前端自动带 after_seq 连向新副本并从 Redis Stream 补发缺口（若此时 Access JWT 刚满 15m，先自动单飞刷新再续连）。

    为什么这样做

    做法为什么
    Web 端用 HttpOnly Cookie 载 JWT，直接适配 noVNC WebSocket浏览器原生 WebSocket API 不支持自定义 Authorization 头；放 Cookie 里既防 XSS，又不用把 JWT 暴露在 URL query 日志中。
    SSE 强制 FlushInterval = -1 且不设整轮硬超时模型逐字输出与工具步骤必须实时到达前端；等待审批或长任务可能跨越数十分钟，不能被网关按普通超时强杀。
    仅白名单路由允许 WebSocket Upgrade防止非预期路由被恶意升级成永不释放的长连接，耗尽文件描述符。
    将网关从 atlas-frontends 中拆出独立 2 副本部署前端打包发版不再影响网关，网关调路由/升版本也不必重启 Next.js，同时支持 RollingUpdate 零停机。
