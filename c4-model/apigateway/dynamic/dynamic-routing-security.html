    边界安全原理：先规范化、再白名单、无条件洗头、四模式分流

    一句话：Atlas 内网服务间免令牌、只信请求头，所以前置网关就是整套系统的信任边界。任何请求进门必须先过“路径严检 → 白名单匹配 → 上游路径二次断言 → 强制剥离全部内部头”四关，再按路由声明的四种模式（auth / passthrough / self-auth / public）分流；未命中白名单一律 404。下面三张图讲清：7 步入站流水线、封死 5 种路径穿越绕过、不同模式的出站头矩阵。

    图 1　入站 7 步管道与 4 类路由模式分流

    1. 1路径规范化排在路由匹配之前，所有路由共享同一道严检，避免不同服务各自手写切段校验产生口径漂移。
    2. 2白名单匹配后、在发往上游前再对改写后的 UpstreamPath 做一次禁区断言：只要含 /internal/、/ops/、/open/ 立即 404，防止配置写错把内部接口暴露出去。
    3. 3全局洗头对四种模式无一例外执行，彻底消除 Nginx 中某条 location 漏 include no-identity.inc 导致伪造头漏进内网的隐患。

    为什么这样做

    做法为什么
    领域数据面（/llm、/mcp、/device-api）统一过前置网关但不验用户 JWT统一承接 TLS、路径防穿越、伪造头清洗、限流与入口可观测，同时把专有 Key 鉴权与协议逻辑留给各自领域子网关。
    拒绝畸形编码而非宽容折叠转发不同 HTTP 框架（Go / Starlette / httpx）对 %25、#、\ 的二次解析差异是路径穿越高发根因，入口直接 400 最彻底。
    运营中心和其他系统一样走 auth 路由（/opscenter/），也受禁区段约束运营人员是系统租户的人，统一登录；运营中心的路径（含系统代理 /api/systems/<系统>/…）不含 /ops/ 段，各系统的 /ops/v1 运营接口照样只有运营中心在集群内能调。
    AUTH 路由转发下游前剥离原 JWT（Bearer 与 uc_access Cookie）下游只认 X-Uid/X-Tenant-Id，不需要看到用户原始 JWT，避免下游日志意外打印凭据。
