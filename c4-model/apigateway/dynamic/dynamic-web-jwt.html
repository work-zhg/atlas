    Web JWT 原理：JWT 直接携带 uid/租户、HttpOnly 双 Path Cookie、热路径零 Redis

    一句话：JWT 的 Payload 本身就携带 sub（uid）和 tid（租户），网关持用户中心 Ed25519 公钥在本地离线验签后即可直接写入 X-Uid 与 X-Tenant-Id——热路径零 Redis 查询、零 UserCenter 调用、无黑名单、无 Pub/Sub。Web 端为了防 XSS 不放 localStorage，而是把 Access JWT 与 Refresh Token 分装在两个不同 Path 的 HttpOnly Cookie 中。下面三张图讲清：JWT 解包到内网头、Web 双 Path Cookie 与 CSRF 防线、无 Pub/Sub 安全闭环。

    图 1　JWT 结构与网关“零 Redis”离线解包（直接取 uid 与租户）

    1. 1是的，JWT 明确包含 sub（即 uid）和 tid（租户 UUID），且受 Ed25519 非对称数字签名保护——客户端看得到但绝对改不了。
    2. 2网关收到请求后只用内存里的公钥做一次微秒级 Ed25519 验签，直接把 sub/tid 写入内网头转发，彻底告别热路径查 Redis 或调 UserCenter。
    3. 3不往 JWT 里塞细粒度权限，既避免 Header 膨胀，也保证管理员调整角色/数据权限后立即在下游生效。

    为什么这样做

    做法为什么
    Web 与 Mobile 统一用 JWT，彻底去掉服务端 Session一套签发、一套验签逻辑，网关热路径零存储访问、无滑动续期写放大，系统极简且高可用。
    Web 端用 HttpOnly Cookie 载 JWT，而非 localStorage兼得 JWT 无状态验签与 Cookie 抗 XSS 能力，前端代码无需自己拼 Authorization，多标签页自动同步。
    uc_refresh Cookie 单独限定 Path=/uc/api/v1/auth + SameSite=Strict普通业务请求、SSE、WebSocket 绝不携带长期刷新令牌，大幅收窄令牌暴露面。
    不建 JWT 黑名单、不引 Redis Pub/Sub15 分钟短有效期 + 下游用户中心实时授权快照 + Refresh 复核 PG 已形成完整闭环，避免引入脆弱广播链路。
