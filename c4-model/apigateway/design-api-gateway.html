API 网关设计：跑在 K8s 外面的 OpenResty，按服务名经内部 Ingress 找服务

一句话：服务器上只留一个对外入口——宿主机上由 systemd 管的 OpenResty，直接占 80 / 443，替代 Traefik。它终结 TLS、按域名分站点；Atlas 站点用 Nginx 原生指令做路由和转发，只在三件事上写 Lua：本地验 JWT、校 CSRF、封登录失败太多的 IP。这一期不做限流。外部路径的第一段就是内部域名的第一段：/mcp/… 是 mcp 的接口（发往 mcp.internal.techstz.com），/mcp-ui/… 是 mcp 的页面（发往 mcp-ui.internal.techstz.com），网关把域名写进 Host、发给集群里的内部 Ingress。路由表只登记名字和规则、不写地址，部署时校验后渲染成配置文件、reload 生效；网关不连 Redis，请求路径上不调用户中心。

这份设计回答七个问题：一个请求在网关里依次经过哪几步；不问用户中心怎么知道「你是谁」；网关在 K8s 外面，怎么按服务名找到里面的服务；对外暴露哪些站点和路径由谁决定；证书谁来续；改配置时长连接怎么办；有人反复试密码时怎么封 IP。它接手两样东西：服务器上 Traefik 的对外职责（80 / 443、TLS、证书、按域名分流；Traefik 留在集群里只做内部 Ingress），以及 atlas-frontends Pod 里的静态 Nginx（auth_request 到用户中心校验会话）。前端的名字一律带 -ui；前端仍在一个 Deployment 里，一个 Service 挂多条 Ingress。JWT 的签发、刷新令牌和公钥集由用户中心提供。

先认识几个词

词意思例子
OpenResty打包好的 Nginx，加上 LuaJIT 和一组 Lua 库。原来的 Nginx 配置照样能用，另外可以在处理请求的某个阶段插一段 Lua。本设计在三处插 Lua：auth 路由的 access 阶段（决定放不放行）验 JWT、校 CSRF；每个请求进 location 后查封禁表；登录接口的 log 阶段记失败。其余都是普通 Nginx。
站点一个对外域名。Atlas 站点走完整规则；Langfuse、gitea 是透传站点：它们有自己的登录，网关只清身份头就转发。atlas.techstz.com 是 Atlas 站点，运营中心也挂在这里（/opscenter-ui/、/opscenter/）；langfuse.techstz.com 是透传站点。
locationNginx 里「哪些路径怎么处理」的一段配置。缓冲、请求体上限、超时、WebSocket 升级都写在这一级。/atlas/ 开头的请求转给 Agent 服务（atlas），用默认档位。
访问 JWT用户中心用私钥签的一小段文字，15 分钟有效，写着你是谁、属于哪个租户。谁都能用公钥验它是不是用户中心签的、有没有被改过，但只有用户中心能签。浏览器的 Cookie uc_access 里就是它；手机放在 Authorization: Bearer 里。
刷新令牌14 天有效的长令牌，只用来换新的访问 JWT，只发给用户中心的刷新接口。访问 JWT 过期后，前端拿它换一个新的，用户感觉不到。
JWKS、kidJWKS 是用户中心公开的公钥集，kid 是每把钥匙的编号。换钥时 JWKS 里同时有 k-2026-10 和 k-2026-11 两把公钥。
服务名、内部域名每个对外的后端或前端有一个名字，它既是外部路径的第一段，也是内部域名的第一段。前端的名字以 -ui 结尾。/mcp/v1/servers 发往 mcp.internal.techstz.com；/mcp-ui/settings 发往 mcp-ui.internal.techstz.com，页面里调的接口是 /mcp/…。
内部 Ingress集群里的 Traefik，只在集群内：按请求的 Host 把它转给对应服务的 Service。每个服务的 Ingress 规则写在它自己的部署清单里。网关只连它一个地址（固定的 ClusterIP，宿主机经 kube-proxy 直达）。Host 是 mcp.internal.techstz.com的请求被转给 Service mcp。
认证模式、档位认证模式：auth 验 JWT 并写身份头；passthrough 原样转给用户中心（登录、刷新）；self_auth 凭证由后面的子网关自己认；public 不验。转发档位说清怎么转（默认、SSE、WebSocket、大文件、流式大报文）。atlas 的后端路由 /atlas/：auth 模式、默认转发档位。
reload让 Nginx 换用新配置而不断服务：起新 worker 接新连接，旧 worker 做完手上的请求再退出。改了路由或续了证书都 reload。
登录失败封禁登录接口回 401（账号或密码错）时，网关给这个 IP 记一次；10 分钟内满 20 次，就把这个 IP 封 30 分钟，期间它的所有请求都返回 403。只数登录接口的 401。同一个 IP 10:00 起连续登录失败，10:03:40 第 20 次 → 封到 10:33:40。

原理 1　一个请求在网关里依次经过哪几步

例子：张三在 Web 上发一条消息，浏览器发出 POST https://atlas.techstz.com/atlas/v1/threads/42/runs，自动带上 Cookie uc_access 和请求头 X-UC-CSRF。

  1. 1浏览器连到服务器的 443。网关按 SNI 和 Host 找到 Atlas 站点，用 certbot 续好的证书终结 TLS；不认识的域名在握手时就拒绝。所有站点都先清掉外部带来的 X-Uid、X-Tenant-Id、X-Auth-Uid、X-Caller-App 和运营接口的签名头——就算张三装的浏览器插件伪造了，也传不到后面。如果是 Langfuse、gitea 的域名，到这里就直接转给它们。网关是第一跳，$remote_addr 就是张三电脑的 IP。
  2. 2Atlas 站点在匹配路由之前再过一道边界：原始请求行里有双编码、反斜杠、控制字符就 400；路径里有 /internal/、/ops/、/open/ 段就 404。这两条写在 server 级，对以后新加的路由也生效。
  3. 3路径第一段是 atlas，命中服务 atlas 的后端路由：auth 模式、默认转发档位。路由表里没登记的路径落到最后一条默认路由，404。进了 location 先查一次封禁表（所有站点都查，原理 7）：张三的 IP 没被封，往下走；被封的 IP 在这里就返回 403。
  4. 4只有 auth 路由进 Lua：从 Cookie 取访问 JWT，写请求先校 CSRF，再本地验签，得到 uid = 张三、租户 = 星河科技，写进 Nginx 变量。任何一步不通过，就返回 JSON 错误并结束，不会转发。passthrough、self_auth、public 路由不进这一步，直接转发。
  5. 5转发：写 X-Uid、X-Tenant-Id、X-Caller-App: gateway，去掉 Cookie；去掉路径里的 /atlas，Host 写 atlas.internal.techstz.com，发给内部 Ingress（原理 3），它再转给 Agent 服务的 /v1/threads/42/runs。Agent 服务照旧拿这两个头去用户中心取授权快照，它不知道入口换了。

原理 2　不问用户中心，怎么知道「你是谁」

  1. 1张三登录或刷新时，用户中心用私钥签一个 15 分钟的访问 JWT。头里写算法 EdDSA 和用的哪把钥匙（kid）；载荷里只有 uid、租户、是否须先改密、签发人、接收方和有效期，不放角色和权限（会过时，也会让令牌变大）。
  2. 2网关永远拿不到私钥。公钥环每 5 分钟从用户中心拉一次 JWKS，放进共享内存，同时写一份缓存文件。宿主机重启时网关常比 K8s 里的用户中心先起来，先读缓存文件就能马上验签。换钥时用户中心先把新公钥放进 JWKS，过一个周期再用新私钥签；真碰到不认识的 kid，本次 401，后台提前拉一次。一把公钥都没有时 auth 路由返回 503，而不是 401（免得前端以为要重新登录）。
  3. 3只接受 EdDSA，kid 必须在公钥环里。这样别人没法拿 alg: none，或者拿公钥当密钥签一个 HS256 令牌来冒充。
  4. 4签名对得上，说明载荷一个字都没被改过。再看有效期——算例：张三 10:00:00 登录，exp = 10:15:00。10:15:20 的请求仍放行（允许 30 秒时钟偏差）；10:15:31 的请求返回 401 TOKEN_EXPIRED，前端用刷新令牌换一个新 JWT 再重发，张三感觉不到。
  5. 5验过就把 sub、tid 写成 X-Uid、X-Tenant-Id。全程只花几十微秒 CPU，不连 Redis、不问用户中心。代价：张三 10:05 被停用，网关要到他的 JWT 过期（10:15）才拒绝；但 10:05 之后他请求到的每个后端都会向用户中心取授权快照，拿到的已经是无权限。

原理 3　网关在 K8s 外面，怎么按服务名找到里面的服务

  1. 1外部路径的第一段就是内部域名的第一段。mcp 在路由表里登记了两条：mcp（接口，种类 api）和 mcp-ui（页面，种类 ui）。打开 /mcp-ui/ 拿到的是页面，页面里调的接口地址是 /mcp/…。
  2. 2/mcp/v1/servers 落在 /mcp/ 上：去掉 /mcp，Host 写 mcp.internal.techstz.com，mcp 服务收到的还是它自己的 /v1/servers。/mcp-ui/settings 落在 /mcp-ui/ 上：路径原样，Host 写 mcp-ui.internal.techstz.com——前端是 Next.js，basePath 就是 /mcp-ui，去掉前缀页面里的静态资源就找不到了。前后端的名字不同，不会抢同一个前缀。
  3. 3网关只连一个地址：集群里内部 Ingress 的固定 ClusterIP（kube-proxy 在宿主机上也装了转发规则，宿主机直接连得到）。内部域名只出现在 Host 头里，网关不解析它们，K8s 的 DNS 出问题也不影响。内部 Ingress 是集群里的 Traefik，只在集群内、不占宿主机端口，读超时放到 1 小时以上、不缓冲；网络策略只让宿主机连它，沙箱 Pod 连不到。
  4. 4内部 Ingress 按 Host 找 Service。后端的 Ingress 写在各服务自己的清单里；前端不拆：仍是一个 Deployment、一个 Service，mcp-ui、memory-ui、atlas-ui……每个前端一条 Ingress，都指向这个 Service（一个前端一个 Next.js 时按端口分，几个前端在同一个应用里时靠路径分）。代价是多一跳（网关 → 内部 Ingress → Service），通常不到 1 毫秒。
  5. 5不是「第一段是什么就转到哪」：只有路由表里登记过的名字才有 location，没登记的一律 404。否则集群里所有带 Ingress 的服务（包括只该内部用的）都会被暴露出去。

  1. 1加一个服务分两处：服务自己的清单里加 Ingress <名>.internal.techstz.com（有前端就在前端 Service 上再加一条 <名>-ui.internal.techstz.com）；routes.yaml 登记名字、种类、认证模式和转发档位（模式或档位不同的子路径另登记一条）。网关不写地址；禁区段、清身份头、默认拒绝、HTTPS 跳转也都不用再写。
  2. 2硬规则：名字是合法的域名标签，且不能是禁区段（internal、ops、open）——运营中心因此叫 opscenter；种类和名字一致（ui 以 -ui 结尾，api 不以 -ui 结尾）；子路径不得含 /internal/、/ops/、/open/；同一名字同一子路径只登记一次；WEBSOCKET 档位只给显式声明的路由；public 只能用在前端和预览；登录接口只能是 passthrough；每个站点都要有证书。
  3. 3渲染出站点、Atlas 路由两份文件，写到 /etc/openresty/atlas/：后端去掉 /<名>、前端原样，Host 都写 <名>.internal.techstz.com（前端的名字本身带 -ui）；同一服务里更长的子路径排在前面，最后加一条默认路由返回 404。所有 location 的上游都是内部 Ingress。
  4. 4openresty -t 检查语法、证书文件和引用；不过就停在这里，线上继续用旧配置。
  5. 5通过就 reload。CI 里也渲染一遍并跑安全回归测试（伪造的身份头会被清掉、编码变形的 /internal 路径是 400 或 404、SSE 不被缓冲、未登录是 401），这组测试和实现无关，以后换实现也照跑。

原理 5　证书谁来续

  1. 1certbot 由 systemd 定时器每天跑两次；证书还有 30 天以上就什么都不做。要续时，它向 Let's Encrypt 说要签哪个域名，拿到一个随机文件名和内容，放进 /var/www/acme。
  2. 2Let's Encrypt 从公网访问 http://域名/.well-known/acme-challenge/文件名。网关的 80 端口只对这个路径不跳 HTTPS，直接从 /var/www/acme 返回文件——证明这个域名确实指向这台机器。
  3. 3验证通过就签发 90 天证书。certbot 写到 /etc/letsencrypt，执行 deploy hook：openresty -t 通过后 reload，新连接用新证书，旧连接不受影响。从 Traefik 切过来时证书不搬，由 certbot 重新申请（同一域名每周最多签 5 张，先用 staging 环境演练）。

原理 6　改配置、换证书时长连接怎么办

  1. 1改了路由（gateway.sh）或续了证书（certbot），都执行 systemctl reload：Nginx 先检查新配置，没问题才起新 worker，新 worker 立刻接所有新连接。配置有错就不切，继续用旧的。
  2. 2旧 worker 不再接新连接，把手上的请求做完——普通接口几秒内就结束。
  3. 3SSE 事件流和浏览器画面的 WebSocket 可能一直不结束：30 秒后旧 worker 主动关掉它们，然后退出。
  4. 4前端 SSE 断开后立刻重连，带着已经收到的最后一条序号；新连接落到新 worker，后端从下一条接着推，一条不丢。WebSocket 画面断了前端重新打开。只有升级 OpenResty 本身要 restart（中断约 1 秒），放在低峰做；systemd 设了 Restart=always，进程意外退出会被拉起来。

原理 7　有人反复试密码时，怎么封 IP

例子：攻击者在 203.0.113.7 上拿一个常用密码，轮着试 200 个账号。同时，张三在公司里正常用 Atlas。

  1. 1路由表里有两条标了「登录接口」：Web 登录 /uc/api/v1/auth/login 和手机令牌登录 /uc/api/v1/auth/token。账号或密码不对时，用户中心一律回 401：账号不存在、密码错误都是 401，触发账号锁定的那一次也是。网关在 log 阶段看状态码，这时响应已经发给浏览器了，不拖慢登录。是 401，就给这个 IP 记一次。
  2. 2计数从这个 IP 第一次失败算起，10 分钟后自动清掉。算例：攻击者每个账号只试一次，用户中心的账号锁定（同一账号错 5 次）一个都碰不到。10:00:00 开始试，10:03:40 第 20 次失败。登录成功不清零计数，否则攻击者夹一次正确的登录就能从头再来。
  3. 3满 20 次就封，封到 10:33:40，同时清掉计数，并打一行告警日志（IP、次数、到期时间）。30 分钟后自动解封。误封时，运维在服务器上通过本机端口 127.0.0.1:8081 查看封禁表、提前解封。
  4. 4封禁期间，这个 IP 的每个请求进 location 后都先查一次封禁表（读一次共享内存，微秒级）。命中就返回 403 IP_BLOCKED，消息里写「还剩 N 分钟」。不用 429，是因为前端把 429 当成「模型忙，换个模型」。
  5. 5别的 401 一律不数。张三的访问令牌 15 分钟过期，业务接口回 401 TOKEN_EXPIRED，前端靠它去刷新，这是正常流程。公司几百人共用一个出口 IP 时，这种 401 一小时就有上千次，数进去整个公司都会被封。刷新接口回的 401 也不数。
  6. 6白名单网段（公司出口 IP、监控探针）不计数也不封。阈值 20 次比账号锁定的 5 次宽，也是为了同一出口 IP 后面有人偶尔输错时，不至于连累别人。这一招只挡单个 IP 的反复尝试，攻击者不停换 IP 就挡不住。

限流没有。这一期也不做。
防撞库只有用户中心的账号锁定（同一账号错 5 次）。账号锁定照旧；网关再按 IP 数登录失败，10 分钟 20 次就封 30 分钟。
真实 IP经 Traefik 转一手，要从 X-Forwarded-For 里取。网关就是第一跳，$remote_addr 就是客户端 IP；转给后端时照样写 X-Forwarded-For。

设计决策

决策理由详见
网关接手 Traefik 的对外职责；Traefik 留在集群里只做内部 IngressTLS、证书、域名分流和 Atlas 的安全规则都在一处，拿到的就是真实客户端 IP；集群内部按 Host 分流仍交给 K8s 原生的 Ingress。Langfuse、gitea 有自己的登录，只清身份头，不套 Atlas 的规则。站点、路由表与边界防护
运营中心和其他系统一样挂在 Atlas 站点、走 auth 路由，名字叫 opscenter；清头逐个列出头名，不用通配符运营人员是用户中心里系统租户的人，和别的系统一样统一登录、凭访问 JWT 访问（运营中心的登录与权限见运营中心设计）。网关不为它开特例，也不需要知道谁是系统租户：能不能进运营中心由用户中心的授权快照判。名字不能叫 ops：/ops/ 是禁区段，整个服务都会被 404；运营中心自己的路径也不含 /ops/ 段，CSRF 用网关统一的那套。清头对所有站点生效，只列运营接口的签名头，不用 X-Ops-* 通配符误伤以后合法的同前缀头。代价：运营中心和租户业务共用一个站点和登录态，系统租户里有模块授权的人被盗号，攻击者也能进运营中心；靠只授必要的模块、不可恢复的操作要 Owner 来收窄。站点、路由表与边界防护
网关跑在宿主机上，systemd 管，不进 K8s入口不跟着集群一起起停：集群升级、控制面出问题时，网关照常终结 TLS、回错误页，恢复后自动接上。代价：不是 K8s 的声明式管理，安装、配置、升级靠 gateway.sh 和固定版本的官方 OpenResty 镜像（systemd 管 docker run，host 网络；Debian 13 的 apt 拒收官方源 SHA1 绑定的签名密钥）保证一致；每台机器一个实例，没有副本。容器图
按服务名拼内部域名，经内部 Ingress 找服务；网关只写 Host、不解析服务在集群里怎么被找到由它自己的 Ingress 负责，网关只管「对外叫什么、怎么认证」；加服务不用改网关的上游。网关只连内部 Ingress 一个固定地址，不依赖 DNS。代价：多一跳，内部 Ingress 的超时、缓冲要按长连接配。站点、路由表与边界防护
前端的名字带 -ui，外部路径也带：/mcp-ui/ 是页面，/mcp/ 是接口；前端不去前缀路径第一段和内部域名第一段完全一致，一条规则看出请求去哪，前后端不抢前缀。Next.js 的 basePath 就是 /<名>-ui，去掉前缀静态资源会 404；后端去掉 /<名>，服务自己的路径不用变。流式转发
外部路径统一成 /<名>/…，旧路径过渡期保留别名；前端不拆部署一眼看出请求去哪个服务；但页面地址（/atlas → /atlas-ui）、接口地址都变了，书签、手机 App、已配对的本机连接器都记着旧路径，网关先把旧路径转到新目标，客户端都换完再删。前端保持一个 Deployment、一个 Service，靠多条 Ingress 区分，不增加部署单元。站点、路由表与边界防护
仍然是白名单，不按第一段自动转发自动转发会把集群里所有带 Ingress 的服务都暴露出去；只有登记过的名字才有 location。边界防护时序
用 OpenResty：原生指令做转发，Lua 只做认证、CSRF 和登录失败封禁转发、流式、WebSocket、大文件、证书是 Nginx 最成熟的部分；开源 Nginx 缺的是 JWT 验签和按登录结果封 IP，用 Lua 写一两百行就够。仓库里没有 Go，自研网关要多一套语言并重写 Nginx 已经做好的边角。网关组件图
路由表 routes.yaml 是唯一来源，渲染成静态配置缓冲、请求体上限、WebSocket 升级只能按 location 设；静态配置能被 openresty -t 和测试一次校验完。站点、路由表与边界防护
网关本地验 Ed25519 JWT，不在请求里调用户中心热路径只花 CPU，用户中心短暂不可用时已登录的人照常用。代价是登出、停用最多晚 15 分钟在网关生效，期间下游取授权快照已经会拒绝。访问阶段、JWT 认证与登录失败封禁
公钥放共享内存并落盘；一把都没有时返回 503没有 K8s 就绪探针替网关摘流；宿主机重启时网关常比用户中心先起来，读缓存文件就能马上验签。访问阶段、JWT 认证与登录失败封禁
证书交给 certbot，续期后 reloadNginx 本身不会申请证书；certbot 是最常用的现成工具，网关只需在 80 端口提供验证文件。容器图
改配置、换证书用 reload单实例没法轮流换；reload 是 Nginx 自带的无损切换，长连接最多拖 30 秒，前端带游标重连。升级 OpenResty 本身才 restart。流式转发
这一期不做限流先把入口、认证和路由做稳。代价：单个用户或租户的失控脚本能打满共享的控制面；登录防撞库靠下一条的按 IP 封禁。以后要做时，在 access 阶段加一个 Lua 模块、路由表加档位即可，现有结构不用动。访问阶段、JWT 认证与登录失败封禁
登录失败按 IP 封禁：只数登录接口的 401，10 分钟 20 次封 30 分钟撞库、密码喷洒每个账号只试一两次，绕得过账号锁定；按 IP 数，就挡得住单个 IP 的反复尝试。令牌过期的 401 是正常刷新流程，公司共用出口 IP，数进去会把整个办公室封掉，所以只数登录接口的。计数放共享内存、在 log 阶段记：单实例计数准确，不连 Redis，也不拖慢登录。被封返回 403，因为前端把 429 当「换个模型」。代价：换 IP 的攻击挡不住；同一出口 IP 里有人反复输错会连累别人，靠宽阈值、白名单和手动解封兜底；restart 会清空封禁表。访问阶段、JWT 认证与登录失败封禁
一组和实现无关的安全回归测试伪造身份头、编码变形的内部路径、SSE 缓冲、未登录这些行为写成测试，CI 里对着真网关跑；以后换实现，用同一组测试验收。边界防护时序
