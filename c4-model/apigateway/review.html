2. /uc/api/v1/auth/ 整段设为 passthrough 吞掉认证接口 + 强制改密 15 分钟死锁

  • 吞掉需认证接口：design-api-gateway.html 路由表将整个子路径 /api/v1/auth/ 标为 passthrough（不验 JWT、不写 X-Uid/X-Tenant-Id、不校 CSRF）。对照源码 usercenter/services/usercenter/src/atlas_usercenter/api/auth.py:121-160，GET /api/v1/auth/me 与 POST /api/v1/auth/password 均在 /api/v1/auth/ 下，且正是需要 AUTH + pending_password_ok: true 的接口。按 Nginx 最长前缀匹配，它们会被 passthrough 吞掉，永远拿不到网关身份头。
  • mcp: true 强制改密后的 15 分钟死锁：用户使用临时密码登录后拿到 15 分钟有效、载荷带 mcp: true 的 Access JWT。通过 pending_password_ok 路由调用 POST /uc/api/v1/auth/password 改密成功后，网关无状态本地验签看到的仍是旧 JWT 里的 mcp: true，接下来最多 15 分钟内访问所有业务路由都会持续 403 PASSWORD_CHANGE_REQUIRED。
  • passthrough 写接口的 CSRF 真空：POST /uc/api/v1/auth/refresh 与 POST /uc/api/v1/auth/logout 走 passthrough，不进网关 Lua CsrfCheck。dynamic-web-jwt.html 写了 refresh 带 X-UC-CSRF，但设计未明确「这两条接口的 Origin + uc_csrf == X-UC-CSRF 校验由用户中心自行负责」，易造成两不管真空。
  • 用户中心侧前置改造契约缺失：现网 deploy/local/15-usercenter.yaml 与 usercenter/.../settings.py 尚未接入 Redis（需规划独立 Redis DB 编号，避开已用的 0/3/5），且 usercenter/.../api/deps.py:76-101 的 current_principal 仍直读 uc_session Cookie 而非 X-Uid/X-Tenant-Id；另 change_password 目前依赖 keep_session=principal.session_row.uuid，切无状态 JWT 后需明确改密时如何吊销其余设备的 Refresh Token，以及 Ed25519 私钥的 Secret 注入与多 kid 轮换运维方式。

  • 「死锁」说重了：403 不会触发刷新，但旧令牌最多 15 分钟就过期，刷新后拿到的就是 mcp: false 的新令牌。

3. OpenResty / Nginx 配置生成的 4 个高危实现陷阱

  1. map $request_uri 误杀合法 Query String，且禁区正则存在漏网变体：code-routing.html 用 map $request_uri $gw_malformed 拒 %25、%5C、\。但 $request_uri 包含 ? 后的查询串——知识库搜索 ?q=100%25、登录回跳 ?next=%2Fatlas-ui%3Fq%3D100%2525 等正常请求均会被 400 误杀。必须只校验 ? 之前的原始路径段（~*^[^?]*...），大小写不敏感，并补全 %2e（编码点号）与 %2f（编码斜杠）检查；禁区段正则需覆盖无尾斜杠情况 ~*(^|/)(internal|ops|open)(/|$)（否则 /atlas/internal 漏放）。
  2. location 优先级冲突与正则内 proxy_pass 报错：design-api-gateway.html 中的 /v1/threads/*/events、/v1/threads/*/browser/view 含通配符，只能渲染为正则 location ~。若父路由 /atlas/ 用了 location ^~ /atlas/，Nginx 会直接跳过外层正则 location（必须嵌套在 ^~ 内或放弃 ^~ 并严格控制正则顺序）。此外，正则 location 内禁止 proxy_pass http://internal_ingress/; 带 URI（openresty -t 直接失败），必须改用 rewrite ^/<名>(/.*)$ $1 break; proxy_pass http://internal_ingress;。
  3. WebSocket 握手缺少 Origin 校验（CSWSH 风险）：code-auth.html 对所有 GET 跳过 CsrfCheck，但 WebSocket Upgrade 握手本身是 GET 且同源自动带 uc_access Cookie。对 WEBSOCKET + COOKIE 路由必须在握手阶段强制校验 Origin 精确等于本站。
  4. upstream keepalive 与 Connection 头冲突 + 无尾斜杠 UI 404：code-proxy.html 配了 keepalive 64，需保证 common.conf 与 websocket.conf 统一通过 map $http_upgrade $connection_upgrade（非 WS 路由固定写 ""）设置 Connection，不重复声明 proxy_set_header。另仅生成 location /atlas-ui/ 会导致直接访问 /atlas-ui（无尾斜杠）落入默认路由 404，需补 location = /<名>-ui 跳转或 ~ ^/<名>-ui(/|$)。
核对（11-26）：部分成立。
  1. 成立：$request_uri 含查询串，?q=100%25 会被 400。补 %2e、%2f 只算加固：禁区段查的是 Nginx 解码、规范化后的 $uri。
  2. 规则说得对，但不是设计缺陷：现网 40-frontends.yaml:142-159 已经是「^~ 里嵌正则 + rewrite」的写法，实现时照搬即可。
  3. 成立：SameSite=Lax 挡不住同站兄弟子域（如 langfuse.techstz.com）发起的握手。
  4. keepalive 与 Connection 头的写法属实现细节。「无尾斜杠 404」的机理不对：以 / 结尾、带 proxy_pass 的前缀 location，Nginx 会自动 301 补上斜杠。沿用现网的 ~ ^/<名>(/|$) 写法即可。
建议级别：① 保持 P0（正常请求会被误杀），③ 降为 P1，②④ 实现时注意即可。处理：已在网关代码里处理（11-26，infra-platform/gateway），都有安全回归测试。
  1. 畸形路径只看 $request_uri 的路径部分，不看查询串；另补了 %2e。
  2. 前缀 location 不加 ^~，正则 location 用 rewrite 去前缀、proxy_pass 不带 URI；正则按字面前缀从长到短排。
  3. Cookie 载体的 WebSocket 握手校 Origin（跨站 403）。

7. 内部 Ingress（第二跳 Traefik）的 4 个隐蔽风险

  2. Traefik 默认超时与滚动更新策略：Traefik entryPoint 默认 respondingTimeouts.readTimeout=60s、idleTimeout=180s，必须显式调大至 >1h 并确认非 SSE 流（如 devicegw relay）的 flushInterval；同时 cluster-setup.sh:168-169 原因 hostPort 限制设的 maxSurge: 0, maxUnavailable: 1 必须改为 maxSurge: 1, maxUnavailable: 0 + preStop，否则升级 Traefik 仍会全站中断。
