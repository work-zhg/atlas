Diagram key

    原理：TeamFlow 和 Agent 平台怎么配合

    一句话：节点页的对话组件直连 Agent 平台，看对话、回答、接管浏览器、停止都不经 TeamFlow，Agent 平台只看「这个人对这个数字员工有没有使用权」；只有开新 run 经 TeamFlow，它记下每个 run 属于哪个节点，停下节点时取消它。挂起和恢复完全是 Agent 平台自己的事，TeamFlow 不跟随事件，也不知道数字员工在等人。

    场景同上面的时序图。Agent 平台内部怎么挂起、续跑，见 挂起与审批；取消见 取消；浏览器接管见 人接管登录；使用权在什么时候授，见 发起流程。

    先认识几个词

    词意思例子
    会话、run、段一个节点一个会话（thread）；每开一次 run，数字员工就做一轮；run 被挂起时切成几段，续跑是新的一段。「编码」的会话里，李工发的那条消息是一个 run，中间挂起过一次，所以有两段。
    使用权用户中心里「这个人能不能用这个数字员工」的数据权限（AtlasAgent 的「使用」级别）。Agent 平台判对话能不能看、能不能答，只看它。李工、周工对「开发工程师」有使用权。
    接入人把数字员工接入团队的人，必须是这个数字员工的 Owner；TeamFlow 以他的身份给流程里的人授使用权。研发一部的「开发工程师」由李工接入。
    事项数字员工要人决定的一件事，Agent 平台在库里记一行，状态从「在等」变成「允许 / 拒绝 / 作废」。三种：提问、工具或计划审批、浏览器接管。「幂等键要不要带商户号？」是一个提问事项。
    挂起、续跑原生智能体等人时，这一段结束、进程走掉，run 状态是 suspended；事项都有结果后，Agent 平台把 run 放回排队，任何一个实例抢到就从库里还原接着跑。CLI 智能体是 bridge 在线等，run 不挂起，但事件一样。李工下午才回答，数字员工中午挂起，中间没有进程在等。
    三种「接管」浏览器接管：数字员工请人操作浏览器，是 Agent 平台的一种事项。节点接管：执行人主动停下数字员工、自己改流程空间里的文件，是 TeamFlow 的操作。实例接手：Agent 平台某个实例挂了，别的实例接着跑同一个 run。本页的「接管」不加说明时指节点接管。

    图 1　节点页上的三条线

    1. 1对话区就是 Agent 平台控制台的对话组件，同一份代码，直连 Agent 平台：读会话、订阅事件流、回答提问和审批、浏览器接管和实时画面、停止。TeamFlow 不转发这些请求，也不认识这些接口；Agent 平台加了新卡片、新事件，TeamFlow 重新构建就有。
    2. 2只有开新 run 经 TeamFlow：对话框里发的消息由对话组件的 submitRun 交给节点对话接口，核对后由节点协作开 run、记下 run 号。系统指令（开工、下一轮、交还）也由节点协作开。
    3. 3节点状态、会话号、能不能发消息这些流程上的事，从 TeamFlow 的流程接口取。

    对话组件是一个通用组件，接入方用参数决定它连哪里、开 run 交给谁、能不能写，组件里不写任何一个应用的接口：

    参数作用TeamFlow 传什么
    apiBase接口根：读会话、消息、事件流、事项、浏览器都调它Agent 平台的接口（经 API 网关），和 Agent 平台控制台一样
    submitRun开新 run 交给宿主：对话框发消息、重新生成都走它；不给就直接调 Agent 平台调 TeamFlow 的 …/nodes/{节点}/messages
    readOnly只读：输入框和卡片按钮都不显示，只看不是执行人，或者节点不在人机协同中、被冻结、被接管

    一个会话里有系统指令和好几个执行人在说话，对话组件要显示每条用户消息是谁发的（「李工」「TeamFlow · 开工指令」），这要 Agent 平台给用户消息带上发送方：人发的记作者（开 run 时的 X-Uid），应用发的系统指令标明来源。

    图 2　谁能看、谁能答：只看数据权限

    1. 1发起流程时，TeamFlow 算出流程里的人（各节点执行、评审角色当前分配的成员）和流程里的数字员工（各节点执行角色配的）。项目后来改了分配，给新加的人补授。
    2. 2经 Agent 平台的共享接口给这些人授「使用」。用户中心规定：数字员工的授权只能由 Agent 平台写，已经有授权的数据再授要操作人是 Owner。所以接入数字员工的人必须是它的 Owner，TeamFlow 以接入人的身份授；已经有的不重复授，也不自动收回（同一个人可能在好几条流程里用它）。
    3. 3之后每个直连请求，Agent 平台只看会话属于哪个数字员工、这个人对它有没有使用权：有就能看、能答、能接管浏览器、能停止，不要求是会话主人；没有就 404。只读成员没被授，看不到节点对话。
    4. 4唯一的例外是开新 run：会话是 teamflow 建的，就只接受 teamflow 发来的；人在 Agent 平台控制台里直接发消息会被拒，要回到 TeamFlow 里发。

    注意：使用权是对数字员工的，不是对某条流程的。被授了权的人在 Agent 平台控制台里也能直接用这个数字员工开自己的会话。

    图 3　开 run 都经 TeamFlow：记下 run 和节点的对应

    1. 1系统指令先排进队列，和改流程状态在同一个事务里；事务提交后，锁到这个节点会话行的副本去投递（多副本不会同时投同一个节点）。
    2. 2人发的消息不排队：节点对话接口核对执行人、节点在人机协同中、没冻结、没被接管后，当场以作者的身份开 run。
    3. 3Agent 平台一个会话同时只有一个没结束的 run。系统指令只在节点刚开工、刚取消之后发，撞上还在收尾的 run（409）就过几秒再投；人发的撞上了，原样告诉对话组件「数字员工正在运行」。
    4. 4TeamFlow 记的只有这些：指令表一行（种类、作者、第几轮、run 号），节点会话上的「最后开的 run」。它不记 run 后来怎么样了。

    图 4　挂起和恢复：四条线上各发生了什么

    横着看是时间，竖着看是同一时刻四个地方各是什么状态（橙色是挂起那一刻，灰色是不参与）。

    1. 1数字员工调 ask_user_question，工具行显示「在提问」。
    2. 2Agent 平台先在库里登记事项，再发 approval.required：事件到的时候库里一定已经有这一行。原生智能体随后这一段结束（run.suspended）；CLI 智能体是 bridge 在线等，不发 run.suspended，别的都一样。
    3. 3挂起期间没有进程在跑，也没有超时，等几天都行。卡片就是提醒：刷新页面后，对话组件用待决事项接口把卡片找回来。
    4. 4李工在卡片里直接向 Agent 平台提交，Agent 平台按使用权放行。
    5. 5回答本身就是唤醒：Agent 平台把 run 放回排队、续跑，谁都不用发「继续」。
    6. 6这一轮结束。整个过程 TeamFlow 只在开 run 时出现过一次。

    图 5　恢复：回答直连 Agent 平台

    1. 1李工在卡片里提交，请求直接到 Agent 平台。
    2. 2Agent 平台按使用权判，只改还在等的那一行，记下谁答的。
    3. 3一个 run 可能同时等好几项（一批调了两个要审批的工具）：全部有结果才续跑，只答了一项就接着挂。
    4. 4放回排队后，接到这次请求的实例就地抢锁续跑，没空槽就由兜底任务几秒内抢走。历史、等待、答案都从库里还原，和挂起前是哪个实例跑的无关。
    5. 5两个执行人同时答：只有一个成功，另一个回 409，对话组件重新查待决事项，卡片显示「已被处理」。

    挂起期间对话框不能发新消息：Agent 平台一个会话同一时刻只能有一个没结束的 run，挂起的也算。要往下走，只能在卡片里答、拒，或者点「停止」。

    图 6　TeamFlow 停下节点时，挂起的会话怎么收尾

    1. 1TeamFlow 自己的「停」只有一种做法：在改流程状态的同一个事务里把节点会话标成冻结、接管或停下（挡住开新 run），记「要取消」；提交后取消「最后开的 run」。它不知道这个 run 是在跑、在挂起还是已经结束，也不需要知道。
    2. 2挂起中的 run 没有进程在跑，Agent 平台接到取消就当场收尾；已经结束的，取消没有副作用。
    3. 3它名下还在等的事项随之作废，卡片不能再答。
    TeamFlow 的操作挂起中的事项之后这个会话里
    提交评审（冻结）作废评审期间不能发消息；驳回后，下一轮指令在同一个会话里发
    节点接管作废交还时发一条指令（带人写的说明），新的 run 接着原来的上下文
    打回、连带打回作废被打回的节点发下一轮指令；被连带打回的，等上游重新准出后重新走准入
    终止流程作废不再开 run，流程空间转只读

    数字员工还在等回答时，执行人点「提交评审」或「接管」，页面先提示「开发工程师还在等你回答，继续会取消这次运行」。页面从对话组件知道还有没有卡片在等，不用问 TeamFlow。

    图 7　断了怎么接上：重投不会多一条

    投递分两步：先向 Agent 平台开 run，再在 TeamFlow 的库里记「已发」和 run 号。两步之间副本挂了，指令在库里还是「排着」；别的副本扫描到后用同一个幂等键（指令号）再开一次，Agent 平台认出是同一个请求，返回同一个 run。

    断的是什么怎么接上
    李工刷新页面、网络断了对话组件直连 Agent 平台重连，带 Last-Event-ID 从断的地方接着收；没有游标时回放最近 500 条。卡片还在不在等，以待决事项接口查到的为准。TeamFlow 不参与
    TeamFlow 投递到一半，副本挂了指令还是「排着」，别的副本扫描时用同一个幂等键再开一次，Agent 平台返回同一个 run（图 7）
    TeamFlow 取消没发出去节点会话上留着「要取消」，扫描时再取消；在这之前开新 run 已经被挡住了
    跑这个 run 的 Agent 平台实例挂了Agent 平台自己接手：别的实例接着跑同一个 run，发 run.resumed；对话组件丢掉重做的那段正文。TeamFlow 不知道，也不需要知道

    设计决策

    决策理由
    开新 run 只经 TeamFlow，其余直连 Agent 平台TeamFlow 只需要知道「哪个 run 属于哪个节点」，停下时才知道取消哪一个；看对话、回答、接管浏览器、停止都是 Agent 平台自己的事，TeamFlow 不认识这些接口，也不转发事件流和实时画面。
    Agent 平台只看数据权限谁能看、谁能答只看「对这个数字员工有没有使用权」，和别的接入方式一样，Agent 平台不知道流程、执行人、评审这些概念。流程状态由 TeamFlow 管：开新 run 要经它，停下时它取消 run。
    发起流程时给流程里的人授使用权，以接入人的身份用户中心规定数字员工的授权只能由 Agent 平台写、操作人必须是 Owner；接入数字员工时由 Owner 接入，等于把「给流程里的人授使用权」交给 TeamFlow。项目改分配时给新加的人补授。
    开新 run 只认建会话的应用沿用 Agent 平台现在「应用建的会话只能回应用里继续」的规则，收窄到只管开 run：否则有使用权的人能在 Agent 平台控制台给评审中的节点发消息，评审看到的就不是提交时的内容。
    TeamFlow 不跟随会话事件少了每个节点一条常驻连接，也不用解析 Agent 平台的执行事件；数字员工在等人时，节点页对话里的卡片就是提醒。
    停下一律取消「最后开的 run」TeamFlow 不知道 run 现在是在跑、在挂起还是已经结束，也不需要知道：取消已结束的 run 没有副作用，挂起中的会当场收尾、作废事项。
    投递以指令号作幂等键副本在「开了 run」和「记下 run 号」之间挂掉时，重投拿到同一个 run，会话里不会多一条消息。
    对话组件用参数接入接口根、开 run 交给谁、只读都是参数；TeamFlow 和以后别的应用各传各的，组件里不写任何一个应用的接口。
