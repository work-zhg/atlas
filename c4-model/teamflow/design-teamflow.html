AI TeamFlow 设计：数字员工按团队的流程干活

一句话：团队把「先做什么、再做什么、谁来把关」写成流程模板；项目绑定模板、给每个角色配成员和数字员工；发起一条流程，TeamFlow 先向 Agent 平台申请一个流程空间，之后每个节点是一个挂着这个空间的数字员工会话。数字员工干活、人在会话里指点，交东西时执行人从空间里勾文件提交评审；上游准出后由下游审它交的东西（准入），通过了下游才开工。产出物都在流程空间里，TeamFlow 只记「第几轮交了哪些文件」和评审意见。

这份设计按原型 agent-platform/doc/prototype/teamflow.html（第三版）画成目标模型，回答六个问题：一条流程长什么样、怎么往下走；产出物放在哪；数字员工怎么在节点里干活、人怎么插手；评审和打回怎么改变流程；模板从哪来；谁能做什么。类、表和每一步交互在各张图里，见文末的图索引。

先认识几个词

词意思例子
流程模板团队定的「流程长什么样」：顺序步骤加并行组，每个节点写工作说明、执行角色、准入和准出评审。发布出来的每个版本都不再改。研发一部的「软件研发（标准）」v3：需求澄清 → PRD → 技术方案 → 编码与测试用例并行 → 测试执行。
流程市场产品自带的流程模板，不属于任何租户，由运营管理员维护；团队管理员拷到自己团队后就是团队的模板。市场里的「软件研发」「缺陷修复」「内容生产」「合同与合规审查」。
模板角色模板自己的概念，定义在模板的角色表里，和用户中心的系统角色（团队管理员、团队成员）没有关系。每个节点的执行绑一个模板角色，准入、准出评审也按模板角色配。用角色而不直接配人，是因为几个节点可以共用一个角色，配一次人就够。「软件研发（标准）」里需求澄清、PRD 都由「产品」执行。
项目项目绑定一个或多个模板，按模板把每个模板角色分配给团队里的成员（可以多个）和一个数字员工。支付中台：开发 = 李工、周工 + 开发工程师。
数字员工Agent 平台里以数字员工为权限的智能体（只按数字员工的权限判，谁来用结果都一样）；TeamFlow 只引用、不创建，也只接这一类，接入的人要是它的 Owner。它的技能决定交出来的东西长什么样。「开发工程师」：CLI 智能体，技能「编码」「单元测试」。
流程、节点按模板发起的一次流程，编号在租户内递增；模板里的每个节点在流程里有自己的状态和轮次。F-1025 支付回调幂等，「编码」节点第 1 轮。
执行人执行角色里配的成员：在节点里给数字员工下指令、回答它的提问、必要时接管、提交评审。「编码」的执行人是李工、周工。
流程空间一条流程一个共享目录：Agent 平台的应用工作空间 teamflow/{空间编号}/，不属于任何人或数字员工；所有节点的会话都把它当工作目录，人也能往里传文件。F-1025 的空间里有 技术方案/技术方案.md、代码/pay-core/、编码/变更.patch。
提交、产出物执行人提交评审时从空间里勾的文件；TeamFlow 只记路径，不存内容。编码第 1 轮提交：编码/变更.patch、编码/变更说明.md。
准出评审本节点交出去之前，由准出角色的人审；规则是「任一同意」或「全部同意」。测试执行要测试和产品都同意。
准入评审下游开工之前，由下游的准入角色审上游交的东西；通过就开工，不通过就打回上游。编码的准入评审人审 技术方案.md。
驳回、打回准出不通过叫驳回：本节点下一轮；准入不通过叫打回：上游下一轮。都必须写意见，意见就是下一轮的指令。周工打回技术方案：「导出分页上限没有区分租户」。
团队级别用户中心里「团队」数据权限的级别：Owner（团队管理员）、读写、只读。李工是研发一部的 Owner，何总是只读。

原理 1　一条流程长什么样

流程只有两种积木：一个节点，或者一个并行组（几条轨道同时走）。下面是研发一部的「软件研发（标准）」。每个节点写着谁执行、谁在准入和准出时把关。这里的「谁」是模板角色（产品、架构、开发……），和用户中心的系统角色无关；用角色而不直接写人，是因为几个节点可以共用一个角色（需求澄清和 PRD 都由「产品」执行），项目里给角色配一次人就够。节点之间谁等谁不用画，由步骤推出来：编码、测试用例都等技术方案，测试执行等编码和测试用例都完。

不做任意连线和条件分支：推进只有一条规则（上游都准出了就轮到我），状态机可以一步一步串着推；真要分支就拆成两个模板。节点也不配「产出物」或文件模板：交什么由执行人提交时从流程空间里选，格式由数字员工的技能约定（例如「PRD 撰写」技能写好了 PRD 的章节和自查规则），工作说明里可以点名要用的技能。

原理 2　节点的七种状态，怎么往下走

每次有人提交、投票、打回，流程运行先锁住这条流程，改完状态，再在同一个事务里看「还有谁该动了」。推进不靠定时器，并行轨道也不用特殊处理。

  1. 1准入是「下阶段准入」：上游准出后还不算完，下游配了准入，就由下游的准入评审人审上游交的东西，通过了下游才开工。第一个节点发起后停在待开始，执行人往流程空间传好资料、点「开始」才开工；其他没配准入的节点，上游都准出就直接开工。
  2. 2上游准出后是「待下游准入」，等它的全部下游都开工了才算「已通过」；最后一个节点准出，流程完成。这样任何一个下游打回它都还来得及。
  3. 3某个节点被打回时，它已开工的后代都标「已打回」、停下数字员工；被打回的节点重新准出后，这些后代重新走准入。

原理 3　产出物放在流程空间里

每条流程一个流程空间。发起时 TeamFlow 先向 Agent 平台申请一个应用工作空间，目录 teamflow/{空间编号}/，不属于任何人或数字员工，归 TeamFlow 这个应用和租户；之后这条流程所有节点的会话都把它当工作目录：上游写的文件下游直接读，不拷贝。

  1. 1空间里按节点名分目录：开工指令里约定产出写在「{节点名}/」下、不改上游提交的文件（有问题就提，或者打回）。人可以传资料和代码副本，编码节点就改空间里的代码副本、产出补丁和变更说明。
  2. 2每个节点的数字员工会话以空间为工作目录。数字员工类型的会话在 Agent 平台里一个会话一个沙箱，建沙箱时把空间挂到 /space（数字员工自己的文件挂在 /data）；原生智能体和 CLI 智能体都一样。并行的节点各有沙箱、同时挂着这个空间，各写各的「节点名/」目录，不会互相覆盖。
  3. 3TeamFlow 不存文件内容，也不做版本：没有快照、没有内容哈希。评审人和下游看的是这些文件的当前内容；为了让评审看到的就是提交的内容，评审期间这个节点的会话不再写入（原理 4）。

空间的一生：

  1. 1TeamFlow 自己生成空间编号，先登记再申请。申请是跨系统调用，可能 Atlas 建好了 TeamFlow 却没收到回复；先登记就知道 Atlas 那边可能留着哪些空间。
  2. 2同一个编号重复申请得到同一个空间，重试不会多出一个。申请失败就不发起流程。
  3. 3申请成功后才在一个事务里建流程，同时绑定空间。申请成功但建流程失败的，空间不回收（很少发生），删租户时一起释放。
  4. 4流程完成或终止后空间转只读：不再投递指令、不再放行上传，文件都留着。
  5. 5关闭租户时先释放本租户的全部空间，再删表。

原理 4　一个节点就是一个数字员工会话

节点第一次开工时，TeamFlow 在 Agent 平台给它建一个会话（数字员工是项目给执行角色配的那个，第一次开工时锁定），工作目录指定为流程空间，之后每一轮都在这个会话里接着做，上下文连续。会话的文件主体是数字员工：它的技能、CLI 的会话记录在数字员工自己的目录里。节点页左边的对话就是 Agent 平台的对话组件，直连 Agent 平台；只有开新 run 经 TeamFlow。

  1. 1开工指令由系统写：工作说明、上游最近一次提交的文件路径、约定，下一轮还带上驳回或打回的意见。不拷上游的文件，也不带上游的对话。
  2. 2指令先排进队列，和改状态在同一个事务里：要么一起成功，要么一起回滚。人在对话框里发的消息不排队：节点对话接口核对执行人、节点在协同中、没冻结、没被接管后当场开 run。两种都记进指令表。
  3. 3事务提交后唤醒；多副本里锁到这个节点会话行的那个去投递，以指令号作幂等键开 run，记下 run 号（重投拿到同一个 run）。Agent 平台一个会话同时只有一个没结束的 run，撞上还在收尾的就过几秒再投。TeamFlow 记 run 号只为一件事：停下节点（提交评审、接管、打回、终止）时取消最后开的那个。
  4. 4节点页的对话组件直连 Agent 平台：看过程、回答提问和审批、接管浏览器、停止都不经 TeamFlow，Agent 平台只看这个人对这个数字员工有没有使用权（原理 8）。TeamFlow 不跟随会话事件，不知道数字员工在跑还是在等人；在等人时，对话里的卡片就是提醒。一步一步怎么走，见 节点会话与 Agent 平台。

F-1025「编码」第 1 轮的开工指令大致是这样：

按技术方案实现支付回调幂等：以「渠道 + 渠道流水号」为唯一键，重复回调直接返回上次的处理结果；补单元测试。
上游提交的文件：技术方案/技术方案.md（技术方案）、PRD/PRD.md（PRD）
改流程空间里 代码/pay-core/ 的代码，在「编码/」下产出 变更.patch 和 变更说明.md。上游提交的文件不要改，有问题就提出来。

人也可以主动接管：数字员工停下，执行人直接改空间里的文件；交还时写一句改了什么，作为下一条指令发回去，数字员工从人改过的地方接着做。

原理 5　提交只记路径，轮次只记「交了什么、怎么评的」

执行人点「提交评审」，从流程空间里勾这一轮的产出物（至少一个）。TeamFlow 查这些文件都在，记下「第几轮、哪些路径」，按项目当前的分配锁定评审人名单，开准出评审，同时冻结这个节点的会话：不再开 run，取消最后开的 run（数字员工在跑、在等回答都停下），对话框里也不能再发消息。

两轮的路径一样，内容已经改过了；TeamFlow 不知道第 1 轮的内容是什么样，这就是「不做版本」。任何一人驳回本轮即结束，不用等其他人；驳回必须写意见。评审人名单在开评审时锁定，评审到一半改项目配置不会改变谁能投票。

原理 6　打回沿后代传播

F-1022 里，编码的准入评审人周工看了技术方案，觉得「导出分页上限没有区分租户，失败重试和断点续传没写」，点了「打回上游」。技术方案回到人机协同中（第 2 轮，意见放进指令，在原来的会话里接着改）；技术方案的后代里已经开工的测试用例也被标「已打回」、数字员工停下，因为它是照着旧方案写的。

技术方案第 2 轮准出后，编码和测试用例的上游又都准出了，各自重新走准入。准出评审也可以把节点打回到更早的祖先节点，传播规则一样。

原理 7　模板从哪来，到发起时锁定

  1. 1流程市场由运营管理员维护：系统租户里有「流程市场」读写权限的人。他们在 TeamFlow 里用和团队同一个编排器编辑、发布、上下架。
  2. 2团队管理员把市场模板拷到自己团队：拷的是当时最新的一版，记下来源；之后市场发新版、下架都不影响它。团队自己改、校验、发布。
  3. 3项目绑定模板（跟随最新发布版），按模板给角色配成员和数字员工。执行角色要有人和数字员工，只评审的角色要有人；配不齐就不能用这个模板发起。
  4. 4发起只选模板、写标题：锁定当时最新发布的版本，之后模板再发版也不影响这条流程。数字员工在节点第一次开工时锁定，评审人在开评审时锁定，执行人一直按项目当前的分配。

原理 8　谁能做什么

每个请求要过三道关。前两道由入口问访问控制：系统角色（用户中心里给人授的，带操作码，如「团队管理员」「团队成员」）决定能做哪类事，团队级别（用户中心里「团队」数据权限）决定对哪个团队做；第三道是模板角色：这个人现在是不是这个节点的执行或评审角色（项目里分配的），由流程运行判。系统角色和模板角色是两回事：前者在用户中心，后者只在模板和项目里。

系统角色（用户中心）团队级别能做什么
团队管理员团队管理员团队 Owner（自己建的团队自动是）新建团队；成员、数字员工、团队设置；流程模板（含从市场拷贝）、项目和项目配置
成员团队成员团队 读写看项目和流程、发起流程、按项目配置的角色执行和评审、往流程空间上传
只读成员团队成员团队 只读看流程、流程空间和追溯；不发起、不担任角色，看不到节点对话
管本租户全部团队团队管理员「全部团队」Owner（编码级授权）和每个团队的 Owner 一样
运营管理员不加角色（系统租户里的人）「流程市场」读写（编码级授权）在流程市场新建、编辑、发布、上下架；要两条都满足：在系统租户里，且有读写

节点对话还要过 Agent 平台这一关，那边只看数据权限：对这个数字员工有「使用」权限，就能看它的会话、回答提问和审批、接管浏览器、停止。所以发起流程时，TeamFlow 给流程里的人（这个模板各角色当前的成员）授流程里各数字员工的使用权，项目改分配时给新加的人补授，不自动收回。用户中心规定数字员工的授权只能由 Agent 平台写、操作人要是它的 Owner，所以接入数字员工的人必须是它的 Owner，TeamFlow 以接入人的身份授。使用权是对数字员工的，不是对某条流程的：被授了权的人在 Agent 平台里也能直接用这个数字员工。

团队成员和级别都存在用户中心，TeamFlow 不存：加人、改级别是以当前用户的身份写用户中心。所有业务数据按租户隔离；流程市场不属于任何租户。TeamFlow 不知道租户状态，租户停用后用户中心在授权上返回无权限。

对 Agent 平台的要求

Agent 平台那边的设计见 按权限主体分的工作空间与沙箱；会话按数据权限判、开新 run 只认建会话的应用、浏览器接管按权限类型判，画在 Agent 平台的 会话、对话、审批、浏览器接管、登录态 几张代码图里。

能力为什么要
应用工作空间：按编号申请、释放；归申请的应用和租户，不属于任何人或数字员工；同一个编号重复申请返回同一个流程空间（原理 3）；编号是幂等键，TeamFlow 先登记再申请
应用工作空间的文件接口：以空间为根列、读、写、查流程空间页、上传、提交前查文件在不在
建会话时把应用工作空间指定为工作目录：只给以数字员工为权限的智能体，会话一个沙箱、建时挂到 /space一个节点一个会话、所有节点读写同一个空间（原理 4）
会话接口：建会话、开一次 run（带幂等键）、取消 run；取消挂起中的 run 时当场收尾、作废它的事项投递指令、冻结、接管、打回（原理 4、5、6）
以数字员工为权限的会话只按数据权限判：对这个数字员工有使用权就能看、能答、能接管浏览器、能停止，不要求是会话主人；应用建的会话，开新 run 只认这个应用节点页直连 Agent 平台（原理 4、8）；开新 run 要经 TeamFlow，它要记 run 属于哪个节点
对话组件用参数接入：接口根、开新 run 交给宿主、只读（输入框和卡片都只读）；用户消息显示发送方（人发的记作者，应用发的系统指令标明来源）节点页嵌对话组件，组件里不写 TeamFlow 的接口；一个会话里有系统指令和好几个执行人在说话
智能体共享接口：以 Owner 的身份给一批人授使用权，已经有的不重复授发起流程、改项目分配时给流程里的人授使用权（原理 8）
智能体目录：本租户里这个人看得到的、以数字员工为权限的智能体和它的技能团队接入数字员工、项目配置里显示数字员工的技能

设计决策

决策理由
产出物不在 TeamFlow，不做版本，不接 git产出物在流程空间里，数字员工、人都直接读写；TeamFlow 只记路径和评审意见，少一套存储和版本规则。代码类的产出先放代码副本、交补丁，以后再集成代码仓库。
流程运行不认识 Atlas流程运行只说「开工、冻结、停下」（扩展点 NodeWork），节点协作去和 Atlas 打交道；状态机和慢的外部调用分开，Atlas 慢或断线都不占流程锁。
节点对话直连 Agent 平台，只有开 run 经 TeamFlowTeamFlow 只需要知道哪个 run 属于哪个节点，停下时才知道取消哪一个；看对话、回答、接管浏览器都是 Agent 平台的事，按数据权限判。TeamFlow 不转发对话、不跟随事件，和 Agent 平台之间只剩建会话、开 run、取消、授使用权、流程空间这几类调用。
同一条流程串行推进，节点按会话行投递状态迁移锁流程行；投递锁节点会话行，指令号作幂等键；多副本、重启都能接上。
事件和状态同一个事务写追溯不会漏记；「等你」和通知按事件往后读，不另接消息队列。
没有超时协同和评审可能持续几天，到点结束会丢掉做了一半的工作；评审靠「等你」和通知提醒，数字员工的提问靠对话里的卡片。
