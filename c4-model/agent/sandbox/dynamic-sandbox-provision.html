Diagram key

    OpenSandbox 原理：一个沙箱就是一个 BatchSandbox 和它的一个 Pod

    一句话：OpenSandbox 把「建一个沙箱」翻译成 Kubernetes 的对象。Lifecycle Server 收下请求，组装好 Pod、和本档模板合并，建一个 BatchSandbox（自定义资源）；控制器照着它建 Pod、汇总状态；kubelet 挂卷、起容器。沙箱镜像里不用预装任何东西：init 容器把 execd 拷进来，execd 作 PID 1 常驻，命令和文件都由它执行。建、查、删走 Lifecycle Server；执行命令、读写文件直连 execd。下面五张图，场景同上面的时序图。

    图 1　谁管什么：控制面一路往下，数据面直连 execd

    1. 1Atlas 的沙箱组件决定建不建、建什么：镜像、新生成的 execd 令牌、资源限额、metadata、挂载都由它填；找回、配额、闲置回收、删除也是它的事，OpenSandbox 只管照做。
    2. 2Lifecycle Server 每档一个（strict 的 sbx、CLI 的 acp、评测的 bench），各有自己的模板和 API key。它把请求组装成 Pod、和模板合并，建 BatchSandbox，然后 watch 它，等到 Running 才返回。
    3. 3控制器全集群一个，服务所有档的 BatchSandbox：按模板建 Pod，Pod 没了就再建一个；把 Pod IP 写进 endpoints 注解，数 allocated、ready，算出 phase；设了 expireTime 的到点就删。
    4. 4Kubernetes 做剩下的：调度器选节点，kubelet 让 CSI 插件挂卷、建 Pod 沙箱分 IP、跑 init 容器和主容器。
    5. 5Pod 里只有 execd 在干活：它作 PID 1，监听 44772，凭令牌执行命令、读写文件。Atlas 拿到 Pod IP 后直连它，不再经过 Lifecycle Server。

    图 2　沙箱 Pod 长什么样：三方各拼一部分

    1. 1init 容器 execd-installer 先跑：它用 server 配置的 execd 镜像，把 execd 和 bootstrap.sh 拷进一个 emptyDir（/opt/opensandbox）。所以任何镜像都能当沙箱，execd 升级只改 server 配置。
    2. 2主容器的命令是 bootstrap.sh 加上请求的 entrypoint。bootstrap.sh 让 execd --init 作 PID 1：回收僵尸进程、转发信号，再把 entrypoint（tail -f /dev/null）拉起来常驻。每条命令都是 execd 的子进程。
    3. 3挂载：/data 是整桶 PVC 的 subPath {user}，经 s3fs 读写这个人在对象存储里的全部文件；/tmp、/home/agent、/repos 是模板加的 emptyDir，本地盘，快，Pod 重建后清空。不挂 ServiceAccount 令牌，Pod 里没有 K8s 凭据。
    4. 4三方各拼一部分：Atlas 的请求给镜像、env、资源、metadata、挂载；server 加沙箱 id、init 容器、bootstrap 和几个变量；本档模板深度合并进来，只能加东西、收紧权限（UID 1000、根只读、drop ALL），不能加 sidecar。

    图 3　什么时候算建好：Pod Ready 了 create 才返回，execd 还要再等一下

    1. 1Pod IP 在挂好卷、建 Pod 沙箱时就分配了，比任何容器启动都早。控制器这时把 IP 写进 endpoints 注解、allocated=1，但 phase 仍是 Pending。
    2. 2主容器一启动，Pod 就是 Ready：沙箱容器没有就绪探针。控制器看到 ready=1，把 phase 改成 Succeed；有 Pod 失败就改成 Failed。
    3. 3server 以 phase 为准：Pending 对外是 Pending，Succeed 对外是 Running。create 一直 watch 着，见到 Running 才返回，最多等 180 秒；Atlas 这边最多等 200 秒，盖过 server 的。
    4. 4Running 只说明容器起来了，execd 开始监听还要一小会。Atlas 解析端点后轮询 /ping，通了才写路由表：此后这个人的文件读写也走沙箱。

    图 4　文件怎么进 Pod：整桶一个卷，按 subPath 分人

    1. 1K8s 对象一条线：一个静态 PV 挂整个桶，一个 PVC 绑到它，atlas-sbx 里所有沙箱共用这个 PVC；每个 Pod 一个卷，按 subPath {user} 绑到 /data，子目录不存在时 kubelet 先建。
    2. 2数据经 s3fs 走：s3fs 进程跑在 CSI 节点插件的容器里，把桶挂到节点上的目录，kubelet 再把其中的子目录绑进容器。容器里的命令读写 /data，就是在读写对象存储。
    3. 3S3 凭据只在 Secret 和 CSI 插件里：kubelet 读到后只交给插件，不进 Pod spec，也不进容器环境，沙箱里的命令拿不到。缓存开得很短：别处改了文件，挂载里最多 1 秒后看到。
    4. 4写穿：flush / close 时同步上传，命令退出时它写的文件已经在对象存储里，界面和文件工具直接读得到。subPath 就是对象存储的 key 前缀，所以挂载里看到的和对象存储里的是同一批文件。

    图 5　怎么用、怎么收：控制面、数据面和回收

    1. 1控制面走 Lifecycle Server，请求头带 API key：建、按 metadata 找回和数配额、取端点、删。server 不回传 env，所以 execd 令牌由 Atlas 生成、自己存着。
    2. 2数据面直连 execd，请求头带令牌：/ping 探测就绪；命令后台执行，从 SSE 的 init 事件拿命令 id，再按游标轮询日志和状态；文件 API 读写 /data 下的文件。长命令和大文件都不经过 server。
    3. 3回收：Atlas 调 DELETE，server 删 BatchSandbox，垃圾回收顺着 ownerReference 删掉 Pod，kubelet 停容器、卸载卷。对象存储里的文件还在，本地盘随 Pod 清空。
    4. 4Atlas 建沙箱时 timeout 传 null：BatchSandbox 不设 expireTime，打上 manual-cleanup 标签，OpenSandbox 不会到点删除，回收全由 Atlas 按闲置做。设了 timeout 的沙箱由控制器在到期时删掉。

    为什么这样做

    做法为什么
    一个沙箱是一个 BatchSandbox（一个副本），不直接建 Pod控制器负责建 Pod、汇总状态、到期删除，Pod 没了还会再建；server 只读 BatchSandbox 的状态，不用自己盯 Pod。
    execd 由 init 容器注入，不进沙箱镜像任何镜像都能当沙箱；execd 升级只改 server 配置，不用重做镜像。
    execd 作 PID 1，主进程只是 tail -f /dev/null容器只负责常驻，命令都是 execd 的子进程：某条命令退出不影响 Pod，僵尸进程有人回收，信号有人转发。
    命令和文件直连 execd，不经 Lifecycle Server控制面只管建和删；长时间跑的命令、大文件走 Pod IP，不压在 server 上，server 重启也不打断在跑的命令。
    令牌由 Atlas 生成，自己存着server 不回传 env；令牌在 Atlas 手里，它才能直连 execd，别的沙箱也拿不到这一个的令牌。
    模板只能加东西、收紧权限每档一份模板定安全基线（UID、只读根、能力），运行时的值覆盖不了这些限制，请求再怎么写也放不宽。
    create 等到 Ready 才返回，Atlas 再轮询 /pingReady 只表示容器起来了，execd 开始监听还要一小会；ping 通才写路由表，之后的读写才走沙箱，不会撞上还没监听的 execd。
    整桶一个 PV、一个 PVC，按 subPath 分人静态 PV 不用为每个沙箱建卷；subPath 就是对象存储的 key 前缀，挂载里看到的就是对象存储里同一批文件，直连和经沙箱读写的是同一个东西。
    S3 凭据只交给 CSI 插件不进 Pod spec，也不进容器环境：沙箱里的命令拿不到对象存储的凭据，只能读写挂进来的那个前缀。
    s3fs 的缓存开得很短，写穿直连对象存储写入的文件（比如新技能版本的拷贝）在挂载里最多 1 秒就能看到；命令退出时文件已经上传，界面马上读得到。
    timeout 传 null，回收由 Atlas 做Atlas 知道这个人还有没有会话在用，OpenSandbox 不知道；运行和等待都不设上限，到点删除会打断还在用的沙箱。
