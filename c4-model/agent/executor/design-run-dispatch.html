Run 派发设计：一个 run 由哪个实例来跑

一句话：run 跟着请求走，异常归兜底任务。请求经负载均衡落到哪个实例，run 就在哪个实例上抢锁、开跑。本实例满了、发版、崩溃这些情况，run 会留在库里没人管，由每个实例都跑的兜底任务处理：每 10 秒从库里分页拉候选，每页 10 条，逐个抢锁，抢到就在本实例跑，抢不到看下一个。锁就是 run 记录上的租约，一个 run 同一时刻只会被一个实例拿到。

Agent 服务会起好几个实例，前面有负载均衡。一个 run 可能跑几秒，也可能跑几小时；实例随时可能因为发版被替换，或者崩溃。这份设计回答三个问题：一个 run（准确地说是它的每一段）由哪个实例来跑；跑它的实例没了怎么办；怎么保证不会有两个实例同时跑同一个 run。一段里面怎么跑、事件怎么推给浏览器、审批怎么判，不在这里，见文末各图。

先认识几个词

词意思例子
实例Agent 服务的一个进程，在 K8s 里就是一个 Pod。部署 3 个副本，就是实例 A、B、C。
run、一段用户发一条消息，就是一个 run（一轮）。一轮中途可能挂起（等审批、等子智能体），挂起前后各算一段。每一段都要有一个实例来跑。模型要删文件，等你点「允许」：点之前是第 1 段，点之后是第 2 段，两段可以在不同的实例上跑。
执行槽、并发上限一个实例同时最多跑多少段（默认 32）；跑一段占一个槽，挂起的不占。A 上有 32 段在跑，第 33 个就没有槽了。
锁（租约）run 记录上的两项：谁拿着它（owner），拿到什么时候（到期时刻）。拿着的实例要不断往后续；不续了，过期就说明它多半死了，别人可以来抢。它是「进程还活着」的心跳，不是工作时长上限。A 在 10:00:00 抢到，锁到 10:00:30；10:00:10 续一次，到 10:00:40……一直续，就一直归 A。
抢锁（CAS）一条带条件的修改：「这个 run 如果没人拿着，就把它记成归我」。条件成立才改，几个实例同时抢同一个 run，只有一个改得成。B 和 C 同时抢 R7，B 改成了，C 改了 0 行，C 就去看下一个。
围栏每次写 run 的进度都带上「锁还在我手里」这个条件。锁被别人抢走后，旧实例的写全部失败。A 卡了一分钟，R 已被 B 抢走；A 醒来要写检查点，被拒。
兜底任务定时任务库（atlas_jobs）里的一个实例任务，每个实例都跑一份、逻辑完全一样：每 10 秒从库里拉「没人拿着、该有人跑」的 run，逐个抢锁，抢到就在本实例跑。实例 A 崩溃，它手上 20 个 run 的锁过期；B、C 的兜底任务各抢到一部分，接着跑。

原理 1　run 跟着请求走

前面已经有负载均衡把请求分到各实例，run 就在接请求的那个实例上抢锁、开跑，不再另建排队领取的机制。会让一段开始跑的请求，都按这个规则落地：

  1. 1负载均衡按请求把提交分到各实例。3 个实例收 30 条提交，大约各 10 条，各自当场抢锁、开跑。不用广播「有活了」，也不用每个实例定时去库里领活。
  2. 2父 run 派子智能体时，子 run 就在父 run 所在的实例上起；子 run 都结束后，父 run 在最后一个结束的子 run 所在的实例上续（它刚空出一个槽）。
  3. 3挂起的 run 续跑时，由触发它的那一方就地抢锁：审批决定的请求落在 C，第 2 段就在 C 跑。和第 1 段在哪个实例跑过无关，段与段之间只靠库里的记录交接。
情况多常见在哪个实例跑
提交一轮常态接到提交请求的实例
审批、提问有了决定后续跑常态接到决定请求的实例
派子智能体常态父 run 所在的实例
子 run 都结束后父 run 续跑常态最后一个结束的子 run 所在的实例
上面任何一种，本实例没有空槽偶尔留在库里，由兜底任务处理（原理 2）
发版时交出在跑的 run每次发版停机的实例放锁，兜底任务处理（原理 4）
实例崩溃、续跑信号丢失少见兜底任务处理（原理 2、3）

原理 2　兜底任务：每个实例都跑，逐个抢锁

后三种情况的共同点是「该有人接手的那一刻没人接」，run 留在了库里。不给每种情况各做一条路，统一交给兜底任务。它是定时任务库里的实例任务：每个实例都跑一份、逻辑完全一样，执行器只写下面这段抢 run 的逻辑，循环、抖动、出错隔离、停机都由库负责。

  1. 1候选是「没人拿着、该有人跑」的 run，分四种，见下表。每页最多 10 条：页小，抢锁冲突时白看的也少。
  2. 2先看本实例有没有空槽：抢到的 run 要在本实例跑，会占一个槽。没有空槽就停，剩下的留给闲的实例。所以闲的多抢、忙的少抢，异常留下的 run 自然分到各实例。
  3. 3抢锁是一条带条件的修改，条件是「还没人拿着」。几个实例同时扫到同一个 run，只有一个抢得到；其余的改了 0 行，接着看下一条。抢到后起一个执行槽就继续，不等这个 run 跑完。
  4. 4按 id 往后翻页，一轮里每条只看一次，抢不到的不会被反复拉到；翻到拉不出数据，这一轮就结束，10 秒后再来。
候选怎么来的抢到后
排队超过 5 秒接请求的实例没有空槽直接开跑。不碰刚排队的：请求那条路从建 run 到本实例抢锁只有几毫秒，5 秒还在排队，才说明它确实没被接下
在跑，但没人拿着锁发版时交出来的（原理 4）先收拾现场，再从检查点接着跑
在跑，但锁过期了实例崩溃（原理 3）先收拾现场，再从检查点接着跑，最多重做一个工具轮次
挂起，但等的事看起来都有结果了续跑信号丢了（比如子 run 收尾时进程被杀）逐个确认续跑条件，成立就放回排队再抢锁。等人批的挂起 run 可能很多，所以先在库里滤掉还有待决审批、还有没结束子 run 的，剩下的通常是零个

算例。实例 A 崩溃，留下 20 个锁过期的 run；B 有 12 个空槽、C 有 30 个。B、C 的兜底任务各自翻页抢：两边都扫到 R1，B 抢到，C 改了 0 行，去看 R2……B 抢满 12 个就停，剩下 8 个都归 C。整个过程没有选主、没有转发，也没有哪个 run 被两个实例拿到。

原理 3　锁就是租约：同一个 run 只有一个实例在跑

抢到锁，就是在 run 记录上写下「归我，到 30 秒后」。之后本进程里的一个后台任务每 10 秒用一条 SQL，把本实例全部 run 的锁往后续 30 秒。不另外用 Redis 锁：写进度时本来就要靠它挡住旧实例（围栏），再加一把锁会有两个说法，Redis 重启还会丢。下面是实例 A 崩溃的时间线：

  1. 1A 在 10:00:00 抢到 R，锁到 :30。续锁在 A 进程里的一个后台任务做，不放进 run 自己的流程：run 大部分时间在等模型和工具，一个工具可能跑几十分钟，那段时间续不上。
  2. 2A 在 :25 崩溃。最后一次续是 :20，锁到 :50；之后没人续，到 :50 过期。
  3. 3B 的兜底任务每 10 秒一轮，:52 那一轮扫到「在跑但锁过期」的 R，抢锁成功（C 同时扫到也只会改 0 行）。从崩溃到被抢走用了 27 秒；最坏情况约 40 秒：崩溃正好在一次续锁之后，锁 30 秒，再加一轮扫描 10 秒。
  4. 4B 先在一个事务里收拾 A 留下的现场（补归档事件、续序号、处理发出去还没结果的工具调用），再从最近的检查点接着跑，最多重做一个工具轮次。

如果 A 只是卡住而没死：它醒来续锁时会发现 R 已经不归它，立即停下；万一停下前还要写检查点，围栏让这次写整个回滚。所以任何时刻只有一个实例能写这个 run。锁只证明「进程还活着」，不限制工作时长：只要 A 活着、一直在续，R 跑几小时都行。挂起时放掉锁，等人可以等到第二天，不占实例。

原理 4　发版：在安全点停下、放锁，交给兜底任务

滚动发布每次都会替换实例。停机的实例不用把 run 交给谁，只要在安全点停下、把锁放掉，别的实例的兜底任务就会抢走，不用等 30 秒过期：

  1. 1K8s 先把 A 从 Service 的后端摘掉，再发 SIGTERM。之后新的请求不会再落到 A；A 关掉准入，它的兜底任务看到「停机中」也不再抢 run。续租照常进行，要一直续到交接完，所以 A 先交接完、再停定时任务库。
  2. 2原生智能体的 run 走到安全点再停：模型这一轮说完、这批工具都有结果、都已落库。这样交出去不丢工作。停下时状态不变，对用户来说这一轮没有停。
  3. 3停下的 run 放掉锁，A 退出。它们成了「在跑但没人拿着锁」的候选，别的实例的兜底任务下一轮就抢走（新实例空槽最多，多半落在新实例上），收拾现场后接着跑。浏览器的事件流断开后自动重连到别的实例，从断开的位置接着收。

设计决策

决策理由
run 跟着请求走，不建排队领取负载均衡已经在分请求，run 在接请求的实例上跑就分摊开了，不用广播唤醒，也不用每个实例为常态的 run 定时扫库。
满了、发版、崩溃、续跑信号丢失都算异常，统一交给兜底任务它们的共同点是「该接手的那一刻没人接」，run 留在了库里。一套逻辑处理：拉出来、抢锁、跑。不给「满了」单独做实例间转发，也不给「发版」单独做交接通道。
兜底任务是定时任务库的实例任务，每个实例都跑，抢到的自己跑执行器只写 execute，循环、抖动、停机由库负责；不能做成全集群一份的集群任务，否则崩溃留下的 run 会全压到一个实例上。不用选主：抢锁本身保证一个 run 只被一个实例拿到。抢一个占一个槽，没空槽就停，异常留下的 run 自然分到闲的实例上。
锁就是 run 记录上的租约，不另用 Redis 锁抢锁是一条带条件的修改。写进度时本来就要按租约做围栏；再加一把 Redis 锁，两处说法可能不一致，Redis 重启还会丢。
按 id 分页，每页 10 条，没有空槽就停按 id 往后翻，一轮里每条只看一次，抢不到的不会被反复拉到；页小，抢锁冲突时白看的少；没有空槽还抢，就会接下跑不动的 run。
排队中的只取排队超过 5 秒的；挂起的先在库里过滤前者让常态的 run 确实留在接请求的实例上，兜底任务不和请求那条路抢；后者避免每 10 秒逐个检查成百上千个等人批的挂起 run。
锁是心跳，不是工作时长上限；续租是定时任务库的实例任务，一条 SQL 续全部运行不设到点结束的上限。锁短（30 秒）是为了进程死后尽快被兜底；放进每个 run 自己的流程里续，run 在等模型、等工具的时候续不上；逐个续，几十个 run 就是几十条 SQL。
发版时在安全点停下、放锁，不做转发；交接完再停定时任务库放锁后别的实例最多 10 秒内抢走，比等锁过期少等 30 秒，也不用实例之间互相调用；等不到安全点就中止，最多重做一轮。交接期间续租要一直续，所以定时任务库最后才停。
