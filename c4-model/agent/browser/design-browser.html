沙箱浏览器设计：智能体操作网页，人接管登录

一句话：开了浏览器能力的智能体，在自己的沙箱里用一个常驻的 Chromium 浏览网页；遇到要输密码、短信码的地方就停下，请人在对话里的实时画面中自己登录，登录完交还；人登录过的网站，登录态由平台加密保管，下次换了沙箱也不用再登录。打个比方：像请一位助理用你的电脑办事——平时他自己点；到了要输密码的时候，他把键盘递给你，你输完还给他；你登录过的网站，他下次直接就能用，但他从来没见过你的密码。

这份设计回答四个问题：模型怎么操作网页；浏览器跑在哪、怎么起来；遇到登录怎么交给人、人怎么看到画面；登录态存在哪、什么时候存、什么时候恢复。原生智能体和 CLI 智能体（Claude Code 等）都适用。以后可能做的「占位符代填」只留了扩展点，不在这里展开。本机 CLI 智能体用自己电脑上的浏览器、看截图点坐标（computer use），见本机浏览器设计。

原理 1　模型怎么操作网页：拍快照、按编号点

模型不看图，看的是一份文字清单：浏览器把页面整理成无障碍树，每个能点、能填的元素一行，前面带一个编号。模型说「在 e7 里填 3021」「点 e8」，程序就去点。DeepSeek 这类不能看图的模型也能用；能看图的模型还可以截一张图，用读文件的工具直接看。

  1. 1模型执行 browser snapshot。浏览器把当前页面整理成无障碍树，每行带一个编号，写进会话工作目录的隐藏目录，命令输出里只给文件路径和页面标题。
  2. 2模型用 Shell 读这个文件。快照写文件、按需读，而不是每次都塞进对话：一页的清单可能有几千字，模型只在需要时读一次。
  3. 3模型按编号操作：填写、点击、选择、按键。它说的是「e8」，不是坐标，所以不会点偏。
  4. 4页面变了，编号就作废，模型再拍一次快照，循环下去。canvas、图形验证码这类清单里写不出来的，能看图的模型可以 browser screenshot 截图再读图；不能看图的就请人接管。

为什么用命令行而不是 MCP 工具：原生智能体和 CLI 智能体都有 Shell，命令行工具不用时几乎不占上下文，快照放在文件里按需读；MCP 每次请求都带着一大段工具定义，快照还会进对话历史。实测同一个任务，MCP 方式的 token 是命令行的四倍左右。代价是页面变了要自己记得重新拍快照，这条写在浏览器技能里。

原理 2　浏览器在哪：一个人一个浏览器，会话各用各的窗口

沙箱本来就按人共享：同一个人、同一个镜像的会话共用一个沙箱。浏览器跟着沙箱走，所以一个人一个常驻的 Chromium，这个人的各个会话各开各的窗口，cookie 是同一份——在一个会话里登录了，别的会话也是登录状态。

  1. 1每条 browser 命令都带着这个会话的会话名（平台给每条命令加的环境变量，等于会话的 id）。browser 把它交给 Playwright CLI，第一次用时经 CDP 连上这个 Chromium、开一个自己的窗口，之后各用各的窗口，互不打断。子智能体有自己的会话，也就有自己的窗口，可以和父会话并行操作。为什么是窗口而不是同一个窗口里的标签页：后台标签页里 Chromium 不刷新画面，模型点击前的「稳定」检查就一直等到超时；每个会话的页面都是自己窗口里的前台页，才都点得动。
  2. 2人接管时，守护单独开一个接管窗口打开模型给的地址，不碰模型正在用的标签页：平台分不清哪个标签页属于哪个会话，人在专用窗口里操作也不会打乱模型的页面。登录写进的是整个浏览器共用的 cookie，模型的页面刷新一下就是登录状态。
  3. 3profile 放在沙箱的本地盘上，不放 /data：Chromium 的 profile 是 SQLite，放不了对象存储挂载；/data 还是这个人所有智能体的 Shell 都能读的地方。本地盘随沙箱存活，守护或 Chromium 挂了重启，登录还在；沙箱回收前，平台把登录态导出存好（原理 5）。
  4. 4Chromium 用有界面模式，画在虚拟屏幕上：人接管时要看到并操作同一个浏览器，无界面模式没有屏幕可以转出去。虚拟屏幕不需要显卡，CPU 就能跑。

屏幕按对话分块：各看各的画面

几个对话的窗口要是叠在同一块屏幕上，谁最后被激活谁就盖在最上面，看画面的人看到的就是别人的窗口——你在一个对话里登录，另一个对话的智能体一开窗口，你的画面就跳走了。所以虚拟屏幕横着分成几块，每个对话一块：对话的窗口、它的子智能体的窗口、它的接管窗口、网页自己弹出的窗口，都放进这一块；画面也按块出，看哪个对话就只看哪一块。

  1. 1块按对话分（根会话），不按会话：子智能体的窗口和接管窗口跟着对话走，人看对话 A 的画面时，A 派出去的子智能体在做什么也看得到。守护记着哪个对话用哪一块；对话第一次用浏览器、或第一次接管时分一块，新窗口一开出来就在自己那块里。块数有上限，满了把最久没用的那块让给新对话。
  2. 2网页用 window.open 弹出的窗口（比如第三方登录），Chromium 会放在屏幕左上角，也就是第 0 块。守护一直看着新开的窗口：是谁弹出来的，就挪到谁那一块。网页里打开的新标签页本来就在原窗口里，不用挪。
  3. 3每块一个画面服务，只截自己那块；Agent 转发画面前先问守护「这个对话在第几块」，只连那一块。所以别的对话怎么开窗口、怎么切换，都不影响你看到的画面；窗口互不重叠，模型在后面操作也不受遮挡。

代价：同一个人的几个会话同时在同一个网站上操作时，可能互相影响（比如一个会话退出了登录）。每个人一个浏览器、约 0.5–1.5 GB 内存，这个人没开浏览器的智能体不受影响（用的是普通沙箱）。屏幕上只有一个鼠标和一个键盘焦点：两个对话同时都有人上手操作，会互相抢（一个人同一时间只会操作一个，影响小）；剪贴板也是整块屏幕共用的。

原理 3　怎么起来：按智能体开，换镜像，沙箱建好时拉起

浏览器能力按智能体开关。开了，就换一个带浏览器的镜像；沙箱建好时，平台把这个人的登录态导进去，再拉起浏览器。模型不用管这些，它只管执行 browser 命令。

几点说明：

  1. 1为什么换镜像，而不是装进默认镜像。Chromium 加中文字体有几百 MB，大多数智能体用不上；strict 档沙箱的根目录只读，浏览器只能在构建镜像时装好。换了镜像，沙箱按（模板，镜像）共享的规则自然把带浏览器的沙箱和普通沙箱分开。浏览器技能（教模型怎么用 browser 命令）随开关自动带上。
  2. 2为什么由平台拉起，而不是模型第一次用时自己拉起。登录态要在打开第一个网页之前导进去，而沙箱里拿不到登录态（没有凭据去平台取，也不该有）。所以在沙箱建好的那一刻，由平台带着登录态把浏览器拉起来。
  3. 3沙箱组件不认识浏览器。沙箱组件只提供一个「附加件」扩展点：建好后、退役前按顺序回调登记过的附加件；浏览器的附加件看请求上有没有「带浏览器」这个属性，决定管不管。这样依赖只有浏览器 → 沙箱一个方向。

原理 4　人接管：停下、打开、登录、交还

模型遇到登录、短信码、图形验证码，就调 request_takeover，写一句给人看的话和要打开的地址，然后停下。接管是「等人决定的事」的第四种，和工具确认、计划审批、提问共用一张表、一张卡片、一套作废和唤醒。不设超时：人可以第二天再来处理。

  1. 1模型调 request_takeover，参数只有给人看的一句话和要打开的地址。参数里没有会话和窗口，这些由平台带上，模型指定不了别人的会话。
  2. 2平台登记一件「接管」事项，对话里出现接管卡片。原生智能体的这一段随即挂起，不占进程；CLI 智能体停在这次工具调用里在线等，和它的权限请求一样。
  3. 3人点「打开」：平台先确认他是沙箱的主人，再确保浏览器在——沙箱被闲置回收了就重建并导入登录态；然后让守护记下此刻的 cookie（「接管前的样子」），开一个接管窗口打开模型给的地址，同时把实时画面接到卡片上（原理 6）。
  4. 4人在画面里输账号、密码、短信码。这些输入从人的键盘经画面直达浏览器窗口，不进模型的上下文，也不进日志。
  5. 5人点「交还」：平台让守护关掉接管窗口、比较接管前后的 cookie，找出这次登录的站点（原理 5 的算例），把这些站点的登录态加密存好，然后才记下决定、唤醒 run。先存再唤醒：续跑可能落在一个新沙箱上，存好了才导得进去。
  6. 6模型拿到的工具结果是「用户已操作完并交还，页面可能变了，先重新拍快照」，加上人写的说明。人点「不处理」时，结果是「用户没有接管」和原因，模型不该为同一件事再请求。

原理 5　登录态：存在哪、存哪些、什么时候存和恢复

登录态由平台加密保管在 Atlas 的库里，按人、按站点一行。它不放在 /data：/data 是对象存储挂载，这个人所有的智能体（包括没开浏览器的）的 Shell 都能读，放在那里，「按智能体开浏览器」就形同虚设。

  1. 1只有交还时会新增站点。平台只存人确实登录过的站点；模型自己逛过的网站、广告和统计的 cookie 一律不存。怎么知道这次登录了哪些站点，见下面的算例。
  2. 2段末、轮末刷新。网站会不时换发新的 cookie（续期），所以每次模型用完浏览器，平台就在后台把已存站点的最新登录态导出来，不拖慢这一轮。沙箱可能突然没了（节点重启），勤刷新才不会丢太多。
  3. 3退役前再刷一次。闲置回收、删除会话都会让沙箱退役，退役前平台再导出一次。导出失败不拦退役，只少一次刷新。
  4. 4新沙箱整份导入。同一个人的原生智能体和 CLI 智能体用的是两个不同的沙箱，但登录态来自同一个地方，在哪边登录过，另一边下次新建时都能用。
  5. 5按站点看、按站点删。删除只影响以后：库里删掉，正在跑的浏览器里也尽力清掉。

为什么只用更新的覆盖。两个沙箱可能前后导出同一个站点，后台刷新也可能比交还时的保存晚到。每行记着「从浏览器里导出的时间」，写入时只有比库里新才覆盖，旧的不会盖掉新的，不用加锁。

为什么存 cookie 和本地存储，不存整个 profile。profile 有几百 MB、和 Chromium 版本绑在一起；cookie 和本地存储导出成一个 JSON，换镜像版本也能导入。代价是少数把登录放在别处（如 IndexedDB）的网站，换了沙箱要重新登录。

算例：交还时怎么找出「这次登录的站点」

打开接管时，守护先记下浏览器里全部 cookie；交还时再取一次，按（域名，名字，值）比较。新增或值变了的 cookie，它所在的可注册域名就是这次登录的站点；只删不增的（比如退出登录）不算。

原理 6　画面怎么到人眼前

控制台是 HTTPS 页面，沙箱的画面服务在集群里、是明文的，浏览器不允许在 HTTPS 页面里直接连它；沙箱里跑的东西模型也能改，不该把它的网页嵌进控制台。所以看画面的客户端（noVNC）随控制台一起发布，沙箱只出一条画面数据流，由 Agent 服务在中间转发。

  1. 1接管卡片里的画面、会话里的「浏览器」按钮都连同一个地址，走同一个源，网关照常校验登录。不接管时默认只看、不操作，免得打乱模型；接管时可以操作。手机 App 不显示画面，只提示「请在电脑上处理」。
  2. 2Agent 服务只让会话的创建人看：画面里是他登录后的网页，接管时还在输他的密码。浏览器必须已经在跑——看画面不会为此新建沙箱，要建是接管「打开」做的事。再问守护这个对话在屏幕的第几块，只转那一块（原理 2）；对话还没用过浏览器就没有块，告诉人「还没用过浏览器」。连着画面的这段时间算沙箱的活动：人登录可能要好几分钟，这期间沙箱里没有命令在跑，不算活动就会被闲置回收。
  3. 3画面通道是沙箱组件的通用能力，和执行命令、读写文件一样只收 sandbox_uuid：沙箱的地址和令牌不出沙箱组件。
  4. 4画面口令由部署密钥和 sandbox_uuid 算出来，不存：拉起守护时算一次带进去，转发时落在哪个实例都能再算出来；沙箱重建，口令跟着换。

原理 7　边界：什么不经过模型，什么模型碰得到

接管保证的是密码和验证码不经过模型，不是「模型碰不到登录态」：浏览器和模型的 Shell 在同一个沙箱、同一个身份下，模型能读 profile，也能经调试接口读出 cookie。这是选定的取舍（浏览器和 Shell 不拆成两个容器），用下面几条把影响收在开了浏览器的智能体里。

设计决策

决策理由
模型按无障碍树和元素编号操作，用 Playwright CLI，不用 MCP纯文本模型也能用、点得准；原生和 CLI 智能体都有 Shell，命令行不用时几乎不占上下文，快照写文件按需读。看截图点坐标只作为能看图的模型的补充。
开浏览器 = 换一个带浏览器的镜像大多数智能体用不上浏览器，不该背着几百 MB；运行时现装太慢，构建时装好。换镜像后，沙箱按（模板，镜像）共享的规则自动把浏览器沙箱分开。
一个人一个常驻浏览器，会话各用自己的会话名沙箱本来按人共享，登录态也属于人：登录一次，这个人的会话都能用。代价是同一个人的几个会话同时操作同一个网站时可能互相影响。
屏幕按对话分块，画面按块出几个对话的窗口叠在一块屏幕上，看到的是最后被激活的那个，人看着看着就跳到别的对话。按标签页推流（CDP 截屏）也能隔开，但看不到地址栏、下拉框、浏览器自己的弹窗，登录时常要用到；每个对话一个 Chromium 又分不了登录态。分块只多几个截屏进程，地址栏、弹窗、复制粘贴都照旧。
沙箱建好时由平台拉起浏览器，经通用供给的附加件扩展点登录态要在打开第一个网页前导入，而沙箱里拿不到登录态；扩展点让沙箱组件不认识浏览器，依赖只有一个方向。
接管是审批的第四种，不设超时登记、等人、做决定、唤醒、run 结束时作废，审批都已经有了，前端卡片也是同一套；平台原则是等人不设期限。
接管开专用窗口，不碰模型的标签页平台分不清标签页属于哪个会话；人在专用窗口里登录，cookie 全浏览器共用，模型刷新页面即可。代价是表单填到一半的验证码，要在新窗口里重走到那一步。
交还时先存登录态，再唤醒 run续跑可能落在新沙箱上，先存好才导得进去；反过来，模型可能在存好之前就去开网页。
画面客户端随控制台发布，经 Agent 服务同源转发，只给沙箱主人不把沙箱里的网页嵌进控制台；HTTPS 页面连不了集群里的明文地址；身份在一处核对。画面里是这个人的登录和密码输入。
连着画面算沙箱的活动人登录要几分钟，期间没有命令在跑；不算活动，闲置回收会把正在登录的浏览器收走。
登录态按人、按站点加密存在 Atlas 的库里，不放 /data/data 是这个人所有智能体都能读的地方，profile 的 SQLite 也放不了对象存储挂载；按站点存，人看得清、删得掉，并发导出按站点比新旧。
只存人登录过的站点，以接管前后 cookie 的变化为准少存一份个人数据：模型逛过的网站、广告和统计的 cookie 不进库；单点登录跳到别的域名也能比出来。
浏览器和模型的 Shell 在同一个沙箱，按智能体开关把浏览器拆到另一个容器、只给受限接口能让模型碰不到 cookie，但要多一层浏览器服务、改动大。智能体本来就代表这个人做事，先接受这个取舍，把影响收在开了浏览器的智能体里。
