    上下文管理原理：放得下，又不把缓存搞失效

    一句话：上下文管理让一段对话在有限的窗口里一直跑得下去。每次调模型前后，它按占用的档位做几件事：大结果外置进文件、旧工具结果换成占位、超过压缩档就把早期回合压成摘要；摘要和覆盖边界存进会话的上下文状态，下一轮重建历史时，边界之前的消息由摘要代替。所有改写只作用于模型看到的 state，消息表从不改写。系统提示词按固定顺序分层、一轮内不变，提醒只追加在这一次请求的最后，提示词缓存的前缀因此稳定。下面五张图，场景同上面的时序图。

    图 1　流水线：一次模型调用前后做什么

    1. 1调模型前的几步改的是 state，本段后面的调用都看得到：先写回上一次强制压缩的结果，再外置、清理，最后看要不要压缩。只改模型看到的消息，消息表不动。
    2. 2提醒追加在最后一条消息之后，只进这一次请求，不落库、不进历史。来源有三个：记忆的更新提示（记忆组件现取）、待办提醒、到了提醒档时的用量提醒；总量有预算，是有效窗口的 10%。
    3. 3失败恢复各只试一次：模型说上下文过长，就强制压缩后重试；回复被输出上限截断，就调高上限重试（图 5）。
    4. 4每次调用后发一个 context.usage 事件：系统提示词、工具定义、摘要、对话、工具结果、提醒各占多少 token，现在在哪一档，有没有熔断。控制台的上下文面板据此显示。
    5. 5每次工具调用后检查这条结果，太大就外置（图 4）。
    6. 6智能体关了自动压缩，或者查不到模型的窗口：没有预算，按档位的清理、压缩、用量提醒和过长恢复都不做，只留外置和提醒。外置保护的是单次调用不被一条超大结果撑爆，提醒传的是记忆和待办，都不是压缩。

    图 2　预算和档位：按有效窗口的比例算

    1. 1有效窗口 = 窗口 − min(最大输出, 20k)，给回复和压缩时的摘要输出留位置。窗口和最大输出取模型平台里登记的规格，没登记就查模型目录；都查不到时不猜，不按档位清理和压缩。
    2. 2三档都是有效窗口的比例，智能体可以配：清理 60%、压缩 80%、提醒 90%。压缩档是「超过」，另两档是「达到」。提醒档在压缩档上面：正常情况下压缩会先把占用压下去，到了提醒档说明没压下来（熔断了，或者没什么可压）。
    3. 3占用优先用模型返回的实际用量：以上一次调用的输入加输出为基线，再加之后新增消息的估算，工具调用的入参也算。新会话的第一次调用、从库里重建的历史都没有基线，这时整体估算，再加上系统提示词和工具定义的开销。

    图 3　压缩：在哪切、摘要什么、留下什么

    1. 1保留最近 3 个回合（可配），想切在倒数第 3 个回合的开头。一个回合从一条真实的用户输入开始；工具结果虽然也走 user 角色，但不算新回合。切点必须是安全边界：前面发出的每个 tool_use 都已经有结果，不是就往前退，宁可少压一点也不拆散一对。
    2. 2切出的部分交给摘要器：思考块先丢掉，单条消息截到 2000 字；旧摘要也在里面，一并压进新摘要。默认用智能体自己的模型，同一个端点。摘要分八段：原始目标与约束、带来源的关键事实、做过的决定和已排除的方案、涉及的文件和命令、错误与用户的纠正、全部用户消息、未完成的事、当前在做什么和下一步。
    3. 3清空 state 后按序重写：新摘要在最前，后面附上重新读取的工作集（切掉的部分里最近用过的文件和技能，读当前版本），再接保留的回合。只删压缩区再追加摘要的话，摘要会被追加到最后，下一次调用就成了对摘要的续写。
    4. 4摘要和覆盖边界存进会话的上下文状态，边界是摘要覆盖到的最后一条消息；压缩次数加一，失败计数清零。下一轮重建历史时，摘要放最前，后面只接边界之后的消息，压一次管到下次再压。
    5. 5只有一个回合时（一条用户消息、几十次工具调用），按回合切不动，就在回合内切，保留最近 3 轮工具调用，补一句「接着做」的衔接。这份摘要不存：本轮的完整过程结束时照常落库，存了的话下一轮会「摘要 + 原文」重复。

    图 4　外置和清理：不压缩也能省出位置

    1. 1三种情况外置：单条工具结果超过 32k token（每次工具调用后）；最后一批结果合计超过 80k（调模型前，从最大的挑，挑到不超为止）；用户一次贴进来超过 80k。三处用同一套规则。
    2. 2全文写进本会话在工作区里的隐藏目录 .atlas/{会话}/，消息里换成头尾各 5 行的预览和路径。模型先看预览判断要不要读全文，要读就用 read_file 分页读回来。read_file 自带分页，写类工具的结果本来就短，这两类不外置。
    3. 3没勾文件工具（模型读不回来），或者写失败：只能截断，留头 70%、尾 30%，并说明全文没有保存。用户的原话例外：写不进去就原样交给模型，不截断。
    4. 4清理的时机：占用到了清理档；或者距上次回复已经超过提示词缓存的有效期，这时缓存反正已经失效，本段第一次调模型前顺手清一次。
    5. 5只清可再生的工具，也就是同样的调用能把结果再拿回来的那些；最近 5 条和最后一批从不清。tool_search 不清：已加载的延迟工具是从它的结果里推出来的。清掉的结果按 id 原地换成一句占位，不改消息顺序。

    图 5　失败恢复与熔断：各只试一次

    1. 1模型说上下文过长（各家网关措辞不同，按关键词认，只认 4xx）：不看档位、也不看熔断，强制压缩后用压缩过的消息重试一次；压缩结果在下一次调模型前写进 state。还不行就报错。
    2. 2回复被输出上限截断：把输出上限翻倍（至少 8k，不超过模型的上限）重试一次；已经在上限了就不试。
    3. 3摘要器失败：这一段里早期对话换成「早期对话已省略：摘要生成失败」，这份不存；失败计数加一，存进上下文状态，跨轮累计。连续 3 次就熔断，不再自动压缩，照常对话；压缩成功一次（包括用户手动压缩）就清零。
    4. 4连最近 3 轮工具调用本身都装不下，切不动：报上下文溢出，不无限压缩。

    为什么这样做

    做法为什么
    所有改写只作用于模型看到的 state，消息表不动用户看到的历史、审计和评测都以消息表为准；清理、外置、压缩只是为了让模型放得下，不能把原始记录改掉。
    摘要和覆盖边界存在会话的上下文状态里没有 checkpointer，历史每轮从消息表重建。不存的话每轮都要重压一次：摘要的 token 重复付，提示词缓存每轮击穿。
    只在完整回合的边界上切assistant 消息里的每个 tool_use 都必须紧跟着它的 tool_result，切在两者之间，请求会被拒。
    回合内也能切智能体最常见的形态就是一条用户消息、几十次工具调用；只按回合切的话，单轮长任务一超阈值就只能报溢出。
    摘要单列「已排除的方案」和「全部用户消息」已排除的方案最容易丢，丢了模型会兜回去重试已经否决的路；用户消息是意图的变化轨迹，最容易被摘要抹平。用户对提问的回答也算用户消息。
    压缩后重读最近用过的文件和技能摘要只记得改过哪个文件，记不住内容；重读当前版本，模型不用自己再读一遍，也不会拿旧内容当真。
    系统提示词分层，顺序固定，一轮内不变提示词缓存的前缀因此稳定；持久指令和记忆的修改从下一轮生效。
    提醒追加在最后，只进这一次请求提醒每次都可能变；放进系统提示词或写进历史，提示词缓存的前缀每次都会失效。
    缓存过期了就先清一次旧结果缓存反正失效了，这时清理不多花钱；缓存还热时清理会让前缀失效，所以平时等到清理档再清。
    外置，而不是截断截掉的内容就永远没了；外置后模型能按需读回来，预览让它先判断要不要读。
    外置只有一处单条、整批、超长输入用同一套规则：预览格式、写到哪、写不进去怎么办都一样。
    关了自动压缩，只留外置和提醒关压缩是不想要摘要，不是不要大结果保护和记忆提醒。
    查不到窗口就不按档位做猜大了压缩永远不触发，猜小了每轮都压；宁可不压，让模型的上限兜底。
    连续失败就熔断，失败恢复只试一次摘要器坏了时，每次调模型前都重压一遍只会持续烧钱；在同一个错误上反复重试没有意义。
