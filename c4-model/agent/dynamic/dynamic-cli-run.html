Diagram key

    TraceEvent 原理：原生和 CLI 智能体翻成同一套事件

    一句话：前端只认 TraceEvent，不认识 LangGraph，也不认识 ACP。原生智能体由 runner 把 LangGraph 的流翻成事件，CLI 智能体由 bridge 把 CLI 的 session/update 原样转交、CLI 运行时翻成事件；两边交给同一个 EventFactory 盖号，data 的形状逐字段一致，之后执行器一视同仁地发布和落库。所以换内核、加一种执行形态，web 一行都不用改。契约只有三条：todos.updated 是全量快照；seq 在一个 run 内从 1 严格递增、没有空洞；data 只增字段，删字段或改语义必须用新的事件类型。交出之后的会话序号、发布和归档，见「一个 Run」的事件中继原理。

    图 1　两条来路，一个出口

    1. 1原生：runner 驱动 LangGraph 图，用 astream 同时订四种流——messages（模型逐 token 的输出）、updates（每个节点跑完后的更新：模型发出的工具调用、工具结果、待办）、custom（中间件够不到事件工厂，审批、上下文用量、文件写入这类事件经这条通道送出来）、values（只为取挂起时的 waiting_on）。
    2. 2映射集中在 translator.py：取可见文本（思考块不算）、工具调用和结果、规整用量。runner 不直接碰 LangChain 的数据结构，内核换了只改这一层。
    3. 3CLI：CLI 经 ACP 发 session/update，bridge 一字不改地包成 agent.update 转交，给每条通知编上 bridge seq，并标明它属于哪一轮（origin、turnId）。bridge 不理解内容，所以 CLI 和适配器升级不用改它。
    4. 4CLI 运行时按 bridge seq 去重，只收本轮的；会话恢复时重放的历史、不属于任何一轮的都不进事件流。AcpV1Translator 是 server 里唯一理解 ACP 内容的地方：一条 session/update 翻成零到多条（类型，data）意图，data 的形状和原生逐字段一致。不认识的类型丢掉、记日志，不报错。
    5. 5两边都交给同一个 EventFactory 盖 run 内的 seq、depth 和时间。翻译层只交意图、拿不到工厂，所以破坏不了「严格递增、没有空洞」。每个事件再过一遍 SkillLoadTracker：读了某个技能钉死版本的 SKILL.md，就补一条 skill.loaded，两边同一份规则。
    6. 6执行器只看 TraceEvent：盖会话序号、发布到会话流、按检查点落库、收尾时先落库再发布终止事件。前端的 reducer 按字段名取值，不分来源。

    图 2　正文分段：调工具就是这一段说完了

    1. 1模型一轮里往往说好几段：先说一句再调工具，拿到结果再说结论。每条 message.delta 带上段号（block），前端边流边分段，不用等最后。
    2. 2段的边界是工具调用，不是换行：一出现 tool.started，当前这一段就封口，下一条 delta 另起一段。当前段是空的（连着调两个工具）就不另起，免得插进空段。两边用同一条判据。
    3. 3Answer 两边共用一个类：原生在 runner 里、CLI 在翻译器里各持一个，记下这一轮说过的每一段。
    4. 4message.completed 的 content 就是这几段 text block，空段丢掉，一段都没有时给一个空 block。原生在一段跑完时发；CLI 不发「说完了」的信号，在一轮结束时由 Answer 拼出来。落库的 assistant 消息就是它，刷新后照样分得开。

    图 3　三个序号：各管一段路

    1. 1bridge seq 只在 CLI 这条路上有，管的是 bridge 和 CLI 运行时之间的通道：编号、去重、ack，重连时从确认点补发；确认到哪写进 cli_session，换实例接管时接回事件流，工具不会重跑。它不进 TraceEvent。
    2. 2run seq 由 EventFactory 盖，两边一样：一个 run 内从 1 严格递增、没有空洞，跨段接着数（续跑、接管的那一段从 run.last_seq 开始）。一个 run 同一时刻只有一个工厂。
    3. 3thread_seq 在发布时盖：根会话的所有 run 共用一个 Redis 计数器，父 run 和并发的子 run 交错着取号，它是前端订阅会话流的游标。depth 是这个 run 在委派树里的层数，由工厂叠加到每个事件上，前端据此把子 run 的事件渲染进子智能体卡片。

    图 4　交出之后还剩的差别：都在事件之外

    1. 1原生的工具调用发生在平台进程里，执行器能拼出完整的消息序列落库，下一轮从消息表重建上下文；CLI 的工具调用发生在 Pod 里，平台只落最终正文，上下文靠 CLI 自己的会话恢复。
    2. 2这些差别决定了执行器怎么落库、怎么等人、怎么取消，但都不改变事件本身：同一种事件在两边的类型和 data 形状一致。

    为什么这样做

    做法为什么
    前端只认 TraceEvent，不认 LangGraph 和 ACP内核换了、加一种执行形态，只要还能翻出这套事件，web 一行不用改。
    翻译层只交（类型，data）意图，事件工厂独占 seq前端靠 seq 去重、补齐；翻译层拿不到工厂，就不可能让序号重号或断档。
    一个 run 同一时刻只有一个工厂，跨段接着数两个工厂各数各的，断线重连拿到的历史就是错乱的；挂起、接管之后从 1 重来也一样。
    data 形状逐字段对齐前端的 reducer 按字段名取值，少一个字段就要加分支。所以参数摘要（preview_args）、正文分段（Answer）、用量的键名两边共用一份。
    bridge 原样转交，翻译只在 server 一处bridge 不理解 ACP 内容，CLI 和适配器升级不用改它；ACP 的理解集中在 AcpV1Translator，改一处就够。
    不认识的 ACP 类型丢掉、记日志，不报错CLI 或适配器升一次版，不该让所有在跑的会话报错。
    思考走 thinking.delta，不混进 message.delta混进去会被拼进最终消息，用户看到一段和回答不连贯的自言自语。
    工具中间态丢掉，参数补全保留工具行已由 tool_call 建好，中间态只会让它闪烁；参数补全不能丢，否则工具行永远只显示「Edit{}」，看不出改的是哪个文件。
    用量换成同一口径：输入含缓存两种智能体的 input_tokens 才能放在一起比、一起计费；遥测按约定再减一次缓存时也不会得到负数。
    撞上限是 run.finished 加 stop_reason，不是 run.failed「做完了但被截断」和「真的出错了」在前端不该长得一样。
    会话没恢复、权限模式被降级、技能没装上，都必须是事件静默的失败最难发现：用户以为接着上次，CLI 其实从零开始；以为是自动模式，其实每条命令都在请示。
