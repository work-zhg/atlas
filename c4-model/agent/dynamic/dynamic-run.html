    事件中继原理

    一句话：写的一方给每个事件盖上会话序号（thread_seq），写进根会话的那一条 Redis 流；看的一方连在任何实例上，先读数据库里的归档段，再接上 Redis 段，两段只认 thread_seq 这一个游标；断线后带着最后的 thread_seq 重连。所以「在哪个实例上跑」和「在哪个实例上看」无关。Redis 里只放丢了也能恢复的东西。上面时序图里「订阅会话流」「事件盖序号后发布」「检查点」「收尾先落库再发布」这几步，靠的就是这些机制。下面五张图的场景比时序图多一个并行委派的子 run，用来说明多个生产者：会话 T，父 run R 跑在实例 A，子 run S1 跑在实例 C，用户的浏览器连在实例 B。

    图 1　写在哪、读在哪都无关：一个根会话一条流

    1. 1盖号：每发一个事件，先在 thread:seq:{T} 上取下一个会话序号。R 和 S1 在不同实例上同时写，号只能在 Redis 里统一分（图 2）。
    2. 2发布：带着会话序号 XADD 进根会话的那一条流。不管是哪个实例、哪个 run（包括子孙 run 的过程和审批弹窗），同一个会话的事件都在这一条里，不用把子 run 的事件「冒泡」转发到父流。
    3. 3归档：执行器在每个检查点、每段收尾时把这一批事件按 thread_seq 落进 run_event。所以归档总比 Redis 晚一截（图 4、图 5）。
    4. 4读归档段：用户的事件流连在哪个实例都行。会话管理先读 run_event 里游标之后的事件，读完立刻还掉数据库连接。
    5. 5读 Redis 段：再从这条流按 thread_seq 接着读，读完已有的就阻塞等新的（图 3）。
    6. 6推给浏览器：SSE 帧的 id 就是 thread_seq。断线后浏览器自动带 Last-Event-ID 重连，连到哪个实例，都从这个号之后接着读。

    图 2　会话序号：多个生产者共用一个计数器

    1. 1R 和 S1 在不同实例上同时发事件，写的是同一条流，所以号不能在各自进程里数，只能在 Redis 里统一分（反例 1）。
    2. 2「键不在就用水位初始化」和「递增」放在同一段 Lua 里，中间没有窗口：不会出现两个调用方都看到键不在、各自初始化的情况。
    3. 3水位来自 SeqWatermark，由 Run 执行器的事件归档实现。键丢了就从水位接着数，前端已经收到的号不会再出现（反例 2）。计数器每次分配都续期 30 天，活跃会话只有 Redis 重建时才会用到水位。

    图 3　读一条会话流：归档段 + Redis 段，按 thread_seq 接上

    1. 1归档段：读 run_event 里 thread_seq > 游标 的事件，一次读完，随后立刻还掉数据库连接，之后几个小时只占一个 Redis 连接。游标推进到读到的最大号。首连（没有 Last-Event-ID）只回放最近 500 条，免得打开老会话时灌进几万个事件；重连补的是断线那段缺口，不截断。
    2. 2Redis 段：从流头 XRANGE 读完已有的，再 XREAD 阻塞等新的，全按 thread_seq 过滤，不认 Redis 的条目 id。和归档重叠的部分自然被跳过；归档读完到开始读 Redis 之间新发布的事件也不会丢，因为 XRANGE 是从流头读起的。

    两段缺一不可：Redis 只留最近约 1 万条，老游标（老标签页、长时间断线）之前的事件只在归档里；归档又比 Redis 晚一个检查点，最新的那一截只在 Redis 里。流不因 run.finished 结束，一轮完了还有下一轮，中间还夹着挂起等待。只有两种情况会结束：客户端断开；本实例停机，这时在下一帧后发 retry: 1000 结束，浏览器一秒后带游标重连到别的实例。

    图 4　收尾事件：先盖号，再落库，最后发布

    1. 1普通事件盖号后立刻发布，前端马上能看到。
    2. 2归档跟着检查点走（模型说完一轮、或一批工具结果收齐），和那批消息在同一个事务里。
    3. 3收尾事件（终态、挂起）先只盖号：归档按 thread_seq 落库（它是主键的一半），这个号必须在落库事务之前定下来。
    4. 4收尾事务一起写：剩下的消息、run 的终态和用量、事件归档（包括这条收尾事件）。
    5. 5落库之后才发布。
    6. 6前端收到 run.finished。
    7. 7前端收到就去取最终用量。因为第 5 步在第 4 步之后，「看到终态」就说明「库里已是终态」，不会读到 running、tokens=0。挂起同理：看到 run.suspended，库里已经是 suspended。

    图 5　接管：发布了、还没归档的那一截从 Redis 找回来

    整条流扫一遍有 MAXLEN 封顶，而且只在接管时发生，不在热路径上。不补的话，这一截事件用户实时看到过，刷新后却从历史里消失（后面的事件归档了，游标越过了它们）；run 内序号也会从 31 重新数，和已经发出的 31…34 撞号。

    Redis 是易失的：每样东西丢了靠什么兜底

    Redis 里的丢了 / 过期会怎样兜底
    会话流 thread:events:{T}Redis 段读不到归档里都有（delta 除外，回放正文看 message.completed）；读取本来就先读归档
    会话序号 thread:seq:{T}从 1 重来，新事件被前端静默丢弃键不在就用归档水位初始化，和递增在同一段 Lua 里（图 2）
    会话锁 run:lock:{会话}同时进来的两个请求可能都占到串行的权威在数据库：会话里有没结束的 run 就不让起新的
    取消标记 run:cancel:{run}这次停止没生效运行时查不到按未取消处理，不让 run 因 Redis 抖动挂掉；挂起中的 run 由执行器当场收尾，不靠它
    唤醒频道 run:wake执行器晚一点才领到定时领取扫描：排队的真相在数据库
