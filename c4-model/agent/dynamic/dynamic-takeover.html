    接管原理：租约过期，别的实例收拾现场接着跑

    一句话：接管就是一个实例不再续租（崩溃、卡死，或者停机时主动交出）之后，别的实例把它手里的 run 领走：先在一个事务里收拾上一个实例留下的现场，再从最近的检查点接着跑这一段。租约是心跳，不是工作时长上限；所有写都带租约围栏，同一时刻只有一个实例能写这个 run。最多重做一个工具轮次。CLI 智能体的 run 不重做：那一轮一直在 Pod 里跑，接手的实例接回事件流就行。下面两张图，场景同上面的时序图：实例 A 刚发出一条 execute 就崩溃，实例 B 接管。橙色是这个场景实际走的路，灰色虚线是没走的分支。

    图 1　租约：心跳停了，别的实例才接手

    1. 1A 在跑：每 10 秒用一条 SQL 续本实例手里全部 run 的租约；每个工具轮次写一个检查点（消息、事件归档、序号水位）。事件实时发进 Redis，归档是批量的。A 发出 execute 后崩溃；命令在沙箱 Pod 里照常跑，不随 server 进程一起死。
    2. 2没人续租，租约最多 30 秒就过期。租约短，是为了尽快发现死掉的实例；长任务只要还在续，就一直跑。
    3. 3B 定时扫描，领到状态是 running、租约已过期的 run（同一个事务里 SELECT … FOR UPDATE SKIP LOCKED 再 UPDATE，多个实例同时扫也不会领到同一行），写上自己的租约，先收拾现场（图 2），再从检查点接着跑。停机交接走同一条路：A 在安全点停下、清掉租约并广播唤醒，B 立刻领走，不用等过期。
    4. 4A 若只是卡住了：醒来续租时，返回的「仍由自己持有的 run」里已经没有这一个，立即停掉它的执行槽。万一停下之前还要写检查点，第一条写就是围栏，整个回滚。

    图 2　收拾现场：一个事务里的四件事

    1. 1围栏：收拾现场的第一条写先校验这个 run 的 owner 还是 B。收拾到一半租约又被别人领走，整个事务回滚，不会两个实例各补一半。
    2. 2补归档：A 发进 Redis、还没批量落库的那一截（检查点之后的 13–15），从会话流里取回来写进事件归档。
    3. 3续序号：run 的序号水位改成 A 实际发到的 15，B 产出的事件从 16 接着数。前端按序号去重、补齐，不会重号或断档。
    4. 4悬空调用：可接续的工具用同一个调用 id 重放。execute 可以：沙箱按（run，调用）记了执行账本，命令还在跑就接上等结果，已经跑完就直接取结果，命令只跑一遍。副作用无法确认的工具记「中断，结果未知」，交给模型去确认。
    5. 5发布 run.resumed，带上要丢掉的字数：A 最后一次模型调用已经流到前端、没进检查点的正文，B 会重做这次调用，前端先删掉，同一段话不会出现两遍。会话锁的持有者仍是这个 run，跟着 B 的租约续。

    为什么这样做

    做法为什么
    租约是心跳，不是工作时长上限短租约（30 秒）让死掉的实例尽快被发现；长任务只要还在续，就一直跑，运行不设到点结束的上限。挂起时清掉租约，等人不占实例。
    一条 SQL 续本实例的全部租约，续不上就立即停逐个续，几十个 run 就是几十条 SQL。续不上说明 run 已被别的实例接走，继续跑就是两个实例写同一个 run。
    所有写都带租约围栏停下之前可能还有一次写在路上；围栏让它整个回滚，同一个 run 只有一个写入方。
    收拾现场和第一个检查点在同一个事务里补归档、续序号、补工具结果要么一起生效、要么一起不生效；收拾到一半被别人接走，也不会留下半套现场。
    领取用 SKIP LOCKED，在同一个事务里领多个实例并发扫描互不阻塞，也不会领到同一行。
    可接续的工具重放，其余记「结果未知」都记「结果未知」的话，模型多半会再发一次，命令就跑了两遍；而 execute 的命令在 Pod 里不随 server 死，执行账本能接上。副作用无法确认的工具如实说未知，模型才会先去确认状态。
    告诉前端丢掉没落库的正文接手的实例会重做最后一次模型调用；不丢的话，同一段话会出现两遍。
    停机交接走同一条路，只是不等过期滚动发布时实例会被替换：在安全点清掉租约并广播唤醒，别的实例立刻领走；等不到安全点就中止，最多重做一个工具轮次。
    CLI 智能体的 run 接管时不重做那一轮在 Pod 里一直在跑，工具也在 Pod 里；接手的实例按记下的 bridge 实例号和确认点接回事件流，补发之后的部分。bridge 重启过，这一轮才以失败结束。
