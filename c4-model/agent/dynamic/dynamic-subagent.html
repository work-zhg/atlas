    委派原理：派完就挂起，子 run 都跑完了再叫醒父 run

    一句话：派一个子智能体，就是在它自己的会话上起一个子 run。父 run 不等，拿到子 run 的 id 就把这次 task 调用登记成一项等待、挂起；子 run 和普通 run 走同一条执行链路，可能在任何实例上跑；它跑完时去叫醒父 run，父 run 续跑时把结论作为 task 的结果交给模型，在同一轮里接着做。这和审批是同一种挂起（waiting_on），只是等的东西不同。子智能体还能再派，每一层都是同一件事。下面四张图，场景同上面的时序图。

    图 1　一次 task 调用：派出去，立刻挂起

    1. 1task 工具只有 schema 和描述，函数体永远不执行：起子 run、登记等待、续跑时填结论，全在 SubAgentMiddleware 里，和审批接管高风险工具是同一个做法。它排在审批之后：task 要请示时先过审批，起子 run 永远是最后一步，不会重复起，也不会绕过审批。
    2. 2名字不在名录里当场拒。持久的子智能体持有会话，同一批里第二个同名的 task 直接拒；检查和占位之间没有 await，并发的两个调用不会都通过。一次性的不受这条限制。
    3. 3准入两道闸：全平台排队和在跑的子 run 不超过 3 个（挂起的不算，它不占进程）；这一轮整棵 run 树累计派出的不超过 6 个，含子智能体再派的。
    4. 4找或建子会话：持久的按（父会话，名字）找，找到就复用，这就是「它记得上次」；fresh=true 时归档旧的、新建一个。一次性的每次新建。新建时把子智能体的技能投送好。
    5. 5子会话空闲才建子 run：库里没有它未结束的 run，会话锁也占得到，否则拒。子 run 记下 parent、root、depth；发起人和按谁判权限沿用父 run；审批模式取父 run 此刻的模式。任务书写成子会话里的一条 user 消息，然后入队，任何实例都能领走。
    6. 6中间件拿到子 run id，在 waiting_on 里登记这一项，不写结果，让这个调用悬空。同一批的其他调用照常执行，可以同时派好几个。
    7. 7下一次调模型之前，SuspensionMiddleware 看到有还没结果的等待项：不调模型，本段结束，产出 run.suspended。段收尾把 waiting_on 落库、清租约；会话锁不放，这一轮没结束，用户这时发不了第二句。

    图 2　子会话和子 run：会话一棵树，run 一棵树

    1. 1子智能体的会话是一行 thread，挂在派出它的那一层下面，会话随 run 一起长成一棵树。子会话不进会话列表，只在父会话详情页的分支上出现。
    2. 2持久的子会话有记忆：它的历史是之前派给它的任务书和它的回答，再派时任务书只需补新的；同名必须串行。一次性的零上下文，可以在同一批里并行（「同时调研五个选项」）。两种都看不到父会话的对话：任务书是它唯一的输入。
    3. 3一次 task 是子会话上的一个 run：parent 指回派出它的 run，root 指向用户输入的那个 run。子 run 走和普通 run 完全同一条执行链路：历史重建、压缩、审批、取消、接管都复用；它有自己的 run id、事件、审批和取消位。
    4. 4原生子智能体带着同一份名录，可以继续派，层数不设上限；跑飞的递归靠整棵树的累计上限兜住。CLI 子智能体的工具由 CLI 自带，不能再派。子智能体都不能向用户提问：用户看到的会是一个没有上下文的问题，该问的由主智能体在派活前问清，缺信息写在结论里。
    5. 5所有 run 的事件都发到根会话的流，用 depth 区分层级。用户只订阅根会话：子 run 里的审批弹窗也在根会话里出现，挂在子会话自己的流上就没人看得见。

    图 3　叫醒：子 run 都终态了，父 run 才续跑

    1. 1父 run 挂起后没有进程在等。它等的是独立可寻址的子 run，不是某个进程里的 await，所以中途重启、换实例都不丢。
    2. 2A 收尾时去叫父 run。判据是「父 run 还有没有未结束的子 run」：B 还在跑，不续。
    3. 3B 也终态了，判据满足：CAS 把父 run 从挂起改成排队，几个子 run 同时结束也只有一个抢得到，之后任何实例都能领走它。B 中途挂起等审批不影响这条路：它没有终态，父就一直等。
    4. 4叫醒有三个入口：① 子 run 收尾时叫父 run，是正常路径。② 父挂起落库后自己再查一次：子 run 秒回时，它叫父的那一刻父还在 running，CAS 失败，唤醒就丢了。③ 每 60 秒补扫挂起的 run：子 run 收尾时进程正好被杀，叫醒信号就没了，补扫是唯一的出路。补扫不判超时，子 run 跑多久都等。
    5. 5三个入口共用一套判据，按等待项的原因分：子智能体看子 run 是否终态，审批看有没有决定。一批里同时有 task 和要审批的工具，两样都齐了才续。
    6. 6续跑时按 waiting_on 逐项取子 run 的结论，放进 decisions 交给图。图看到有结论，不调模型，先去执行工具：SubAgentMiddleware 把结论作为 task 的结果交出、删掉那一项；同一批里已有结果的调用原样返回，不重跑。然后才调模型，同一轮接着做。等待期间被取消的，不续跑，当场收尾（见「取消原理」）。

    图 4　结论怎么交回：三种结局都不能被读成「没有发现」

    1. 1成功、有结论：取子 run 最后一条回答的原文。
    2. 2成功、没给文字结论：明说「这不等于没有发现」和怎么补救，父模型不能把空结果读成没找到。
    3. 3失败或被停止：照实写状态和原因；有输出就附上最后一段（最多 4000 字），并标明可能不完整。
    4. 4末尾一行统计：状态、会话类型、token、工具调用数、时长。父模型据此判断值不值得再派；持久的还提示它下次只补新信息。结论不直接给用户看，由父智能体转述。

    为什么这样做

    做法为什么
    父 run 不等，派完就挂起子 run 可能跑一小时。在进程里等，会一直占着执行槽和租约，进程重启就丢了。挂起后没有进程在等，谁都能接着做；和审批走同一条路，不用另一套机制。
    子智能体的会话是一行 thread，一次 task 是它上面的一个 run子 run 因此和普通 run 走完全同一条执行链路，历史、压缩、审批、取消、接管一行新代码都不用写；在图里跑子图的话，这些都要再装一套，两份语义迟早漂移。
    派不出去时回失败的工具结果，不抛异常、不等锁撞上限、同批同名、会话被占都是局部问题，模型可以改派、合并任务或自己动手。抛异常会让整个 run 失败；等锁的表现是「卡住直到超时」，模型既不知道原因也拿不到替代方案。
    准入按整棵树累计数层数不设上限，挂起中的子 run 又不占并发名额：只按父 run 数的话，「A 派 A 再派 A」每层只派一个，永远撞不上限。
    在跑的子 run 有全局上限CLI 子智能体各占一个 Pod：按 run 各自限流的话，并发会话数一乘就爆。
    持久的复用会话，一次性的每次新建持久的记得之前派给它的事，任务书只需补新的，代价是同名必须串行。一次性的零上下文，换来可以并行。
    事件进根会话的流用户只订阅根会话。子 run 的事件留在子会话的流上，就是一条没人订阅的流，审批弹窗会在子智能体挂起时消失。
    叫醒有三个入口、一套判据漏掉任何一个入口，run 都会永久停在挂起：没有报错、没有事件，只是一个一直转圈的界面。判据按原因分：用子智能体的判据去判审批会立刻满足，续跑、又挂起，死循环。
    子智能体不能向用户提问用户看到的会是一个没有上下文的问题；任务书本该完整，缺信息写在结论里，由主智能体决定问不问用户。
    审批模式取派活那一刻父 run 的计划获批后父 run 的模式可能已经变了。CLI 子智能体与它自己的 permission_mode 取更严的。

    工作区与沙箱原理：一个人一个沙箱，父子、多会话共用

    一句话：对象存储按人分前缀：根会话一个 workspace，这个人所有会话共用一份 skills 和一份 home/.claude；沙箱按人要，整个 /{user}/ 挂到 /data，这个人的新会话随时加入，不用改 Pod。父、子、孙智能体都以根会话的 workspace 为 cwd，技能从共用的目录里取各自智能体绑定的那几个版本；CLI 智能体也在同一个沙箱里跑，会话记录写进 /data/home/.claude，沙箱重建后接着原来的会话。下面的场景：用户 u 的根会话 P（原生智能体）派子会话 C，C 再派孙会话 G；u 同时开着另一个根会话 Q，是 CLI 智能体（Claude Code）。{user} 是会话的创建人。

    图 1　对象存储：按人分前缀，根会话一个 workspace，一个人一份 skills 和 .claude

    1. 1桶里按人分前缀。会话目录下只有 workspace，目录名就是会话 id：/{user}/{会话}/workspace。技能和 CLI 的会话记录不按会话分，一个人一份。
    2. 2工作区只有根会话有。子、孙会话不建 workspace，读写根会话的（取 root_thread_uuid，不是父会话，所以 G 也落到 P）。委派常常就是「帮我处理这批文件」，产物要互相看得见。
    3. 3压缩归档、外置的大结果放进所用工作区下的隐藏目录 .atlas/{本会话}/：跟着工作区走，各会话分开。文件工具列目录、搜索时默认跳过它，模型不会被它们淹没。
    4. 4技能一个人一个目录 /{user}/skills，所有会话共用，按技能、版本分子目录 {slug}/{版本}/。会话创建时按智能体绑定的版本逐个看，缺了才从源仓库 _skills/{slug}/{版本}/ 拷进来，已经有就直接用；同一技能的不同版本并排放，绑不同版本的智能体互不覆盖。每个会话的提示词只列出自己智能体绑定的技能和路径，目录里别的技能不会出现。
    5. 5home/.claude 一个人一份，不属于任何会话：放 CLI 智能体的会话记录和配置，沙箱重建后据此恢复（图 3）。别的 CLI 同理，放 home/ 下自己的目录。

    图 2　一个人一个沙箱：整个 /{user}/ 挂到 /data，新会话加入不用改 Pod

    1. 1沙箱按人要，键是（人，模板）。u 的会话第一次执行命令时找这个人的沙箱，没有就建；建在锁里，同一时刻只建一个。一个人默认只用一个模板（镜像同时装好 CLI），所以就是一个沙箱。
    2. 2只有一个读写挂载：s3fs 把 {user}/ 整个挂到 /data。Pod 的卷在创建时就定死了，挂父前缀是会话后加入也能看到自己目录的唯一办法：新会话的目录一建好，Pod 里就看得见。
    3. 3每条命令带上本会话的 cwd：P、C、G 都是 /data/{P}/workspace；技能在 /data/skills/{slug}/{版本}，提示词里给的就是这个路径。文件工具和 Shell 用同一套路径（沙箱里的真实路径），模型看到的路径只有一种。
    4. 4CLI 会话 Q 在同一个 Pod 里起自己的 bridge 和 Claude Code，cwd 是 /data/{Q}/workspace。再开一个 CLI 会话就再起一对，端口按会话分配。
    5. 5本地盘是 emptyDir：HOME、/repos、装的包都在这里，快，但沙箱重建后清空。只把 ~/.claude 指到 /data/home/.claude（软链，或设 CLAUDE_CONFIG_DIR）。整个 HOME 放 s3fs 上，装包、缓存都会很慢。

    图 3　CLI 智能体：沙箱重建后接着原来的会话

    1. 1Claude Code 新建会话，拿到自己的会话 id（sid）；bridge 报给平台，平台记进 cli_session（agent_session_id，一个会话一行）。
    2. 2Claude Code 边对话边把会话记录追加到 ~/.claude/projects/<cwd 编码>/<sid>.jsonl，目录名是把 cwd 里的 / 换成 -。~/.claude 在 /data 上，记录落进对象存储。
    3. 3沙箱被回收（闲置、节点故障、换镜像），本地盘清空；/data 下的东西都在，平台记下的 sid 也在。
    4. 4下一轮来时新建沙箱，bridge 按 CLI 的能力位选 session/load 或 session/resume，带上记下的 sid。Claude Code 用同一个 cwd 找到同一个目录，读回记录，上下文还在。恢复失败才新建会话，并如实报告 resumed=false。
    5. 5前提是 cwd 重建前后一样：路径里只有会话 id 和固定的挂载点 /data，不含 Pod 名、不含随机目录。CLI 子会话的 cwd 是根会话的 workspace，记录落进同一个 projects 目录，按 sid 分文件。

    图 4　只有一个写入方：这个人的沙箱在跑时，文件读写都经它

    1. 1选路看这个人的沙箱，不看本会话、也不看本智能体有没有勾 Shell。s3fs 有目录和属性缓存：沙箱在跑时，文件工具要是绕过它直写对象存储，Pod 里的进程可能好一阵都看不到，同一个文件还会有两个写入方互相覆盖。
    2. 2沙箱 READY 时经 execd 读写，路径原样传。经沙箱失败时，先确认沙箱确实不在了才改回直连；问不到就报错，不悄悄换写入方。
    3. 3没有沙箱时直连对象存储：/data/… 换成 {user}/…，一一对应，不用查表。
    4. 4例外是技能缺的版本的拷贝：源仓库不在沙箱里，只能在对象存储里服务端复制；目标目录刚确认过不存在，不会和 Pod 里的缓存冲突。拷完最后写一个完成标记，没有标记的目录当作没拷完，下次重拷。界面上传和文件工具同一个规则。

    为什么这样做

    做法为什么
    整个 /{user}/ 挂一个点Pod 的卷在创建时就定死了。按会话挂 subPath，后加入的会话（子会话、这个人新开的会话）挂不上自己的目录。挂父前缀，新目录一建好就看得见。
    子、孙会话用根会话的 workspace委派常常就是处理同一批文件，产物要互相看得见。子会话另建 workspace 的话，父会话还得再把结果拷一遍。
    技能一个人一份，按技能、版本分子目录同一版技能只拷一次，新会话、子会话大多不用再拷；沙箱里也只有一个技能目录。不同智能体可能绑同一技能的不同版本，按版本分开才不会互相覆盖。
    提示词只列本智能体绑定的技能共用目录里有这个人所有智能体的技能；技能清单本来就来自智能体的配置（先有清单、再有文件），不扫描目录，所以别的技能不会混进来。
    压缩归档、外置结果放进 workspace 下的 .atlas/{会话}/会话目录只有 workspace，不用再多一个系统区；归档跟着工作区走，删根会话时子孙会话的归档一起清掉。
    HOME 放本地盘，只把 .claude 放 /dataHOME 里多是可以再生的缓存和装的包，放 s3fs 上很慢，重建后重装就行；要跨重建留下的只有 CLI 的会话记录和配置。
    .claude 一个人一份，不按会话分会话记录本来就按 sid 分文件，放一起不冲突；登录状态、设置也只需要一份。
    路径里只用会话 id 和固定挂载点CLI 按 cwd 找会话目录，cwd 一变，旧记录就找不到了。
    文件工具和 Shell 用同一套路径挂父前缀之后 Shell 看到的是 /data/…，文件工具跟着用，模型不用在两套路径之间换算。
