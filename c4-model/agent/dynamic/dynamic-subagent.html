Diagram key

    工作区与沙箱原理：一个人一个沙箱，父子、多会话共用

    一句话：对象存储按人分前缀，每个会话一个目录（workspace、skills），一个人一份 home/.claude；沙箱按人要，整个 /{user}/ 挂到 /data，这个人的新会话随时加入，不用改 Pod。父、子、孙智能体都以根会话的 workspace 为 cwd，技能用各自的；CLI 智能体也在同一个沙箱里跑，会话记录写进 /data/home/.claude，沙箱重建后接着原来的会话。下面的场景：用户 u 的根会话 P（原生智能体）派子会话 C，C 再派孙会话 G；u 同时开着另一个根会话 Q，是 CLI 智能体（Claude Code）。{user} 是会话的创建人。讲的是目标设计，和现在代码不一样的地方列在最后。

    图 1　对象存储：按人分前缀，每个会话一个目录，一个人一份 .claude

    1. 1桶里按人分前缀，每个会话一个目录，目录名就是会话 id：/{user}/{会话}/workspace、/{user}/{会话}/skills。原来的系统区（system）去掉。
    2. 2工作区只有根会话有。子、孙会话不建 workspace，读写根会话的（取 root_thread_uuid，不是父会话，所以 G 也落到 P）。委派常常就是「帮我处理这批文件」，产物要互相看得见。
    3. 3压缩归档、外置的大结果放进所用工作区下的隐藏目录 .atlas/{本会话}/：跟着工作区走，各会话分开。文件工具列目录、搜索时默认跳过它，模型不会被它们淹没。
    4. 4技能按会话各一份：会话创建时，按各自智能体的版本从源仓库 _skills/{slug}/{版本}/ 拷进 {本会话}/skills。会话里改了技能只影响这个会话，不影响父会话和兄弟会话。
    5. 5home/.claude 一个人一份，不属于任何会话：放 CLI 智能体的会话记录和配置，沙箱重建后据此恢复（图 3）。别的 CLI 同理，放 home/ 下自己的目录。

    图 2　一个人一个沙箱：整个 /{user}/ 挂到 /data，新会话加入不用改 Pod

    1. 1沙箱按人要，键是（人，模板）。u 的会话第一次执行命令时找这个人的沙箱，没有就建；建在锁里，同一时刻只建一个。一个人默认只用一个模板（镜像同时装好 CLI），所以就是一个沙箱。
    2. 2只有一个读写挂载：s3fs 把 {user}/ 整个挂到 /data。Pod 的卷在创建时就定死了，挂父前缀是会话后加入也能看到自己目录的唯一办法：新会话的目录一建好，Pod 里就看得见。
    3. 3每条命令带上本会话的 cwd：P、C、G 都是 /data/{P}/workspace；技能在 /data/{本会话}/skills。文件工具和 Shell 用同一套路径（沙箱里的真实路径），模型看到的路径只有一种。
    4. 4CLI 会话 Q 在同一个 Pod 里起自己的 bridge 和 Claude Code，cwd 是 /data/{Q}/workspace。再开一个 CLI 会话就再起一对，端口按会话分配。
    5. 5本地盘是 emptyDir：HOME、/repos、装的包都在这里，快，但沙箱重建后清空。只把 ~/.claude 指到 /data/home/.claude（软链，或设 CLAUDE_CONFIG_DIR）。整个 HOME 放 s3fs 上，装包、缓存都会很慢。

    图 3　CLI 智能体：沙箱重建后接着原来的会话

    1. 1Claude Code 新建会话，拿到自己的会话 id（sid）；bridge 报给平台，平台记进 cli_session（agent_session_id，一个会话一行）。
    2. 2Claude Code 边对话边把会话记录追加到 ~/.claude/projects/<cwd 编码>/<sid>.jsonl，目录名是把 cwd 里的 / 换成 -。~/.claude 在 /data 上，记录落进对象存储。
    3. 3沙箱被回收（闲置、节点故障、换镜像），本地盘清空；/data 下的东西都在，平台记下的 sid 也在。
    4. 4下一轮来时新建沙箱，bridge 按 CLI 的能力位选 session/load 或 session/resume，带上记下的 sid。Claude Code 用同一个 cwd 找到同一个目录，读回记录，上下文还在。恢复失败才新建会话，并如实报告 resumed=false。
    5. 5前提是 cwd 重建前后一样：路径里只有会话 id 和固定的挂载点 /data，不含 Pod 名、不含随机目录。CLI 子会话的 cwd 是根会话的 workspace，记录落进同一个 projects 目录，按 sid 分文件。

    图 4　只有一个写入方：这个人的沙箱在跑时，文件读写都经它

    1. 1选路看这个人的沙箱，不看本会话、也不看本智能体有没有勾 Shell。s3fs 有目录和属性缓存：沙箱在跑时，文件工具要是绕过它直写对象存储，Pod 里的进程可能好一阵都看不到，同一个文件还会有两个写入方互相覆盖。
    2. 2沙箱 READY 时经 execd 读写，路径原样传。经沙箱失败时，先确认沙箱确实不在了才改回直连；问不到就报错，不悄悄换写入方。
    3. 3没有沙箱时直连对象存储：/data/… 换成 {user}/…，一一对应，不用查表。
    4. 4例外是新会话的技能拷贝：源仓库不在沙箱里，只能在对象存储里服务端复制；目标目录是新建的，不会和 Pod 里的缓存冲突。界面上传和文件工具同一个规则。

    为什么这样做

    做法为什么
    整个 /{user}/ 挂一个点Pod 的卷在创建时就定死了。按会话挂 subPath，后加入的会话（子会话、这个人新开的会话）挂不上自己的目录，原来子会话的 /skills 挂不上就是这个原因。挂父前缀，新目录一建好就看得见。
    子、孙会话用根会话的 workspace委派常常就是处理同一批文件，产物要互相看得见。子会话另建 workspace 的话，父会话还得再把结果拷一遍。
    技能按会话各一份技能按智能体的版本投送，子智能体可能是另一个智能体、另一个版本；会话里改技能不该影响别的会话。
    去掉系统区，放进 workspace 下的 .atlas/{会话}/一个会话只剩 workspace、skills 两个目录；归档跟着工作区走，删根会话时子孙会话的归档一起清掉。
    HOME 放本地盘，只把 .claude 放 /dataHOME 里多是可以再生的缓存和装的包，放 s3fs 上很慢，重建后重装就行；要跨重建留下的只有 CLI 的会话记录和配置。
    .claude 一个人一份，不按会话分会话记录本来就按 sid 分文件，放一起不冲突；登录状态、设置也只需要一份。
    路径里只用会话 id 和固定挂载点CLI 按 cwd 找会话目录，cwd 一变，旧记录就找不到了。
    文件工具和 Shell 用同一套路径原来文件工具看到 /workspace，Shell 在 Pod 里看到的也是 /workspace；挂父前缀之后 Shell 只能看到 /data/…，文件工具跟着用，模型不用在两套路径之间换算。

    共享的代价与还没定的问题

    问题说明
    会话之间不隔离同一个人的会话在一个 Pod、一个挂载里，Shell 能读写这个人别的会话的目录和 .claude。文件工具可以按会话限定路径（本会话的 workspace 和 skills），Shell 限不住。要隔离只能用 execd 的隔离会话（bwrap），它要 CAP_SYS_ADMIN，和 strict 档冲突。
    凭据跨会话可用Credential Vault 绑在沙箱上：一个会话配的 git 凭据，这个人别的会话（可能是别的智能体）也能用。
    .claude 在 s3fs 上的写入会话记录是边写边追加的 jsonl，s3fs 每次落盘都重传整个对象，长会话越写越慢；多个 CLI 进程同时改共享文件（.claude.json、history.jsonl）时，后写的覆盖先写的。备选：.claude 放本地盘，每轮结束、Pod 排空时由 bridge 同步到 /data；代价是 Pod 被直接杀掉时丢最后一轮。
    bridge 要能一个 Pod 起多个现在 bridge 是 Pod 的入口进程，绑定一个会话（ATLAS_BRIDGE_SESSION_ID），端口固定。要改成按会话经 execd 起进程、端口按会话分配，平台在 cli_session 里记下连哪个（已有 bridge_instance）。
    一个镜像要装下所有东西原生智能体和 CLI 共用模板：镜像要同时装好 CLI；出网策略和 MITM 要按最宽的会话配。模板不同的会话仍然分开（键里有模板）。
    一个 Pod 扛这个人的所有会话资源配额要按并发会话数留余量；闲置回收要等这个人所有会话都闲下来。
    删会话删根会话：删它的目录（含子孙会话的 .atlas）。删子会话：只删它的 skills 和 .atlas/{子会话}。.claude 里的记录要按 cli_session 的 sid 找到再删。

    现在的代码和上面设计的差别

    地方现在
    布局{user}/{会话}/workspace | skills | system：还有系统区，压缩归档、外置结果、CLI 的 HOME 都在里面。
    原生智能体的沙箱按工作区（根会话）要，挂 subPath：/workspace 读写，/skills 只读且挂的是根会话的。子、孙会话的 /skills 挂不上。
    CLI 智能体一个会话一个 Pod，bridge 是入口进程；HOME=/state 整个挂在 {user}/{会话}/system/cli-home 上，按会话一份。重建后已经能恢复，只是 HOME 在 s3fs 上。
    路径文件工具和 Shell 都用 /workspace、/skills 两个固定根。
    界面上传一律直连对象存储，沙箱在跑时有互相覆盖的风险。
