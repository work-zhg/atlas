    记忆的读写原理

    一句话：读分两条路：每次都要用的记忆放进系统提示词里的常驻块，其余的由模型看主题目录、按需整块加载，不做语义检索。常驻块按会话存成快照，只在缓存本来就会失效、或用户明确操作过时才重建，保住前缀缓存。写也分两条路：对话中由模型调 save_memory，当轮生效、当场可撤销；漏记的由会话后补记补上。两条路都遵守同一条规则：写之前必须看过目标主题的最新版本。读和写靠同一张版本表串起来：Atlas 为每个会话记下模型在上下文里看到的各主题是哪个版本，只和记忆服务给的版本号比，不比内容。下面五张图按时间顺序，场景同上面的时序图（本轮 08:15，上一次回复在 08:13）。橙色是这次实际走的路，灰色虚线是没走的分支。记忆服务内部怎么判定一次写入，见 c4-model/memory/dynamic/dynamic-write.html 的「记忆原理」。

    图 1　记忆进上下文的三个位置，和 Atlas 记着的状态

    1. 1常驻块在系统提示词里，排在持久指令之后，原样取自快照（snapshot.block），不放时间、计数这类每轮都变的东西。系统提示词一变，后面整段对话历史的前缀缓存就全部失效，所以它只在该刷新时才变（图 2）。可写的主会话在它后面再接一段写入指引。
    2. 2按需加载和写入的结果是普通的工具结果，留在对话历史里，随消息落库；会话压缩后就没了，需要时重新加载。
    3. 3更新提示附在请求末尾，每次调模型前现取，只列主题不带内容，只有几十个 token，不影响前面的缓存。
    4. 4thread_memory 随会话存库、不放进程内存：run 挂起后在另一个实例续跑、被接管，快照和已知版本都接得上。known 记的是模型在上下文里看到的各主题版本：常驻块里的，加上历史里加载、写入的结果。本例中「编码-java」是本会话早先加载过的。
    5. 5memory_user_setting 是用户级的：暂停只停写入，已有的记忆照常常驻、照常加载；用户在记忆页里撤销、更正、删除、恢复、改主题，epoch 都会加一，让各会话的常驻块在下一轮刷新。

    图 2　读 · Run 开始：常驻块沿用快照还是重建

    1. 1每一段 run 开始时组装一次（续跑段也是）：读会话的记忆状态和用户设置。会话还没登记过实例（建会话时登记失败），就在这里补登记。
    2. 2列主题目录，拿到每个主题的当前版本、大小、是否常驻。这一步失败（记忆服务不可用、被拒），本轮就不用记忆：不加载、不写入，对话照常——记忆不能成为会话的硬依赖。目录同时留作「本轮的服务端版本」，更新提示和加载都拿它比；Run 进行中不再列。
    3. 3判据都是「缓存本来就会失效」或「用户明确操作过」的时机，在这些时候重建不额外丢缓存。缓存有效期取 prompt_cache_ttl（默认 5 分钟）。Agent 在本会话里自己写入不触发重建：写入结果已经在对话历史里。
    4. 4重建也不全量重拉：版本号和快照里一样的常驻主题，直接沿用快照里的条目。单个主题有上限不代表常驻总量有上限，所以还有一个常驻总预算（memory_resident_budget_chars，6000 字）。

    图 3　读 · 版本表：模型看到的是不是最新

    1. 1Atlas 不比内容，只比记忆服务给的版本号：版本号在实例锁里分配、只增不减，列一次目录就知道哪些主题变了。本轮开始时：「沟通偏好」一致；「工具链」本会话没看过，但它在常驻快照的目录里，模型知道有这个主题，不提示；「编码-java」本会话早先加载过 15，之后在别的会话里被写成 17。
    2. 2于是请求末尾附一行「有更新」，要不要重新加载由模型决定；常驻块不动，保住缓存。模型重新加载过、或常驻块重建之后，提示里就不再列它。
    3. 3load_memory：「工具链」没看过 → 返回全部 3 条，已知记成 40 并存库。之后再加载一次、版本没变，就只回一句「已在上下文中，没有变化」，不重复占上下文。
    4. 4save_memory：写前一律先加载，已知和当前一致才写。这样冲突判断总是基于目标主题最新、完整的内容；没看过就先把内容交给模型，这一次不写。
    5. 5写入之后按返回的 changed 推进：写入前的版本等于已知，说明中间没人写过，上下文里的内容加上这次写入就是最新，推进到 41；不等就不动，下一次就会被当作「有更新」。

    图 4　写 · 对话中存：save_memory

    1. 1只有可写的主会话才挂 save_memory、forget_memory：智能体勾了「记忆」工具，而且不是子会话（子智能体只读，有常驻块和 load_memory）。守卫：用户暂停了写入、或本轮已写满 memory_max_writes_per_run（8）次，就不写；同一轮的写入在一把进程内的锁里排队。
    2. 2写前必看（图 3）：先加载，已知版本和当前版本一致才写；不一致就把最新条目交给模型，这一次不写。新建的主题是空的，直接算看过。
    3. 3关联主键由会话决定，不在工具参数里；调用记忆服务的用户也一律是会话所属用户，数字员工代用户跑时也一样。时间取本轮用户发话的时间，不取调用的时间。幂等键由 run、作用域、主题、内容、删除的编号算出：网络重试、run 被接管后重放同一个调用，服务端只写一次。
    4. 4作废：要取代的条目在服务端已有更晚的信息（比如用户刚在别的会话里改过）。不写任何东西，已知版本里去掉这个主题，让模型先重新加载再判断。
    5. 5写成了：按 changed 推进已知版本；工具结果告诉模型「已记住 #31，取代了 #12」，主题超过约 2000 字（memory_topic_max_chars）时再提示它合并重复条目或拆成更细的主题。结果带一张卡片，控制台据此显示「已记住 #31［撤销］」；撤销后 epoch 加一，下一轮刷新常驻块。forget_memory 是只删除、不新增的写入，走同一条路。

    图 5　写 · 会话后补记：补上漏记的，拆小超限的主题

    1. 1维护者每 60 秒（memory_backfill_scan_s）扫一批到期的会话：开着记忆的主会话（子智能体的会话不补，里面没有用户本人说的话），空闲超过 30 分钟或已归档，上次补记之后有变化，而且没有在跑的 run。补记按会话做、不按 run 做：能看到完整过程，用户中途改口只记最终说法，也不会和对话中正在进行的写入撞上。
    2. 2只取上次补记之后新增的用户、助手正文，不含工具调用和工具结果（文件、网页里要求改记忆的话也就进不来）；太长只留最近的部分。没有用户的话、或总共不到 12 个字，就跳过抽取。
    3. 3一次 LLM 调用，用平台服务模型「记忆补记」。输入里有现有记忆（展开到 16000 字为止，没展开的主题不往里写）和本会话已经写入的记忆，所以只补缺的部分。宁缺毋滥：用户不在场，拿不准就不记。
    4. 4来源可信度从高到低是用户亲自 → Agent 写入 → 会话后补记，取代限制在代码里执行、不只靠提示词：用户亲自写的、本会话 Agent 刚写的不能取代，和它们冲突的那一条整条放弃（只做新增会留下两条矛盾的记忆）。写入时间取所依据的那条用户消息的时间，补记晚到也不会盖掉用户之后在别的会话里说的新情况；作废就放弃这一条。每次最多写 8 条。
    5. 5最后一步拆分超过约 2000 字的主题，抽取被跳过时也照常检查，不管主题是谁写满的。每个主题一次 LLM 分组，分组在锁外进行，不挡对话中的写入；提交时带上分组时看到的版本号，记忆服务确认没变才拆。拆分只移动条目，不合并、不删除，子主题沿用常驻标记。
    6. 6推进进度。写了或拆了东西就留一条补记结果，用户下次打开会话时提示「补记了 N 条」，每条都能查看、撤销。补记写入的东西，要等这些会话下一次刷新常驻块，或者 Run 开始时的更新提示，才会进到上下文里。

    为什么这样做

    做法为什么
    常驻 + 按需整块加载，不做语义检索偏好类记忆和用户的提问在语义上并不接近，靠检索召回不到，但每次对话都要用；主题有上限，可以整块放进上下文、整块加载。代价是模型可能漏加载。
    常驻块按会话存快照，只在缓存本来就会失效、或用户明确操作过时重建常驻块在系统提示词里，内容一变，后面整段对话的前缀缓存就全部失效。
    别处的更新只附提示，不改常驻块提示只有几十个 token，附在请求末尾，不影响前缀缓存；要不要重新加载由模型决定。
    比版本号，不比内容版本号在记忆服务的实例锁里分配、只增不减，一次列目录就知道哪些主题变了；条目的时间是客户端给的，看不出主题变没变。
    写前必看写入方看到目标主题的全部条目，冲突判断才不会因为「没看到」而漏掉。服务端不知道客户端看过什么，所以这条由 Atlas 执行。
    关联主键和调用用户都取会话所属用户，不进工具参数一旦可以由模型指定，提示词注入就能读写别人的记忆；数字员工代用户跑时也取使用者本人，否则同一个数字员工的所有使用者会共用一份记忆。记忆服务还会按数据权限再校验一次。
    快照、已知版本随会话存库挂起后续跑、被接管的 run 可能落在另一个实例上。
    记忆失败不让对话失败记忆是增强，不是会话的硬依赖：登记、列目录失败时本轮不用记忆，下一轮再试。
    两条写入路径：过程中存为主，补记为辅用户明确要求的当轮生效、当场可撤销；主模型漏记的、不会主动调工具的智能体，由补记兜住。两条路径共用作用域、主题、取代限制、来源标记和撤销。
    补记的时间取原消息的时间补记晚到，记忆服务按时间晚的为准，不会盖掉用户之后在别的会话里说的新情况。
    拆分放在补记里，分组在锁外上限只有客户端知道；补记本来就在会话空闲后跑、本来就要调 LLM。调 LLM 期间不挡对话中的写入，提交时靠版本号确认主题没变。
