    挂起与续跑原理

    一句话：挂起就是图在 before_model 直接跳到 END，把「在等什么」（waiting_on）和消息在同一个事务里落库，进程里什么都不留；续跑就是新建一张图，把消息、waiting_on 和审批结果一起交回，before_model 直接跳到 tools，把当初拦下的那个调用执行掉。下面四张图按时间顺序，场景同上面的时序图：手动模式下模型要删 tmp/（调用 id 记作 call_1，审批 id 记作 A）。橙色是这一段实际走的路，灰色虚线是这一段没走的边。

    图 1　段 1：图内走到 END（挂起）

    1. 1正常进图：没有悬空调用，waiting_on 为空 → 调模型。模型返回 AIMessage，tool_calls = [call_1: delete_file]。
    2. 2工具节点执行 call_1，先经过 PermissionMiddleware：手动模式 × write → 请示。ApprovalGate.check 登记审批 A = uuid5(run_uuid, call_1)（pending），发 approval.required；然后只返回 Command(update={"waiting_on": {"call_1": {"reason": "approval", "token": "A"}}})。不执行工具、不写 ToolMessage，call_1 在消息里悬空。
    3. 3工具节点的出边回到 before_model。SuspensionMiddleware 看到 waiting_on 非空、A 不在 decisions 里 → jump_to: "end"。不跳出的话，模型会拿到悬空的 tool_call，provider 直接 400。
    4. 4图正常跑完：不是异常，也不是 interrupt。runner 从 values 流的最后一帧取出 waiting_on，产出 run.suspended；执行器先落库（图 2）再发布，看到 run.suspended 就说明库里已经是 suspended。

    图 2　挂起期间的全部现场：库里三行数据，进程里什么都没有

    只看消息，只能看出 call_1 还没有结果，看不出它是「在等」还是「被放弃」（比如进程在工具执行到一半时被杀）；这件事只记在 run.waiting_on 里，所以两样必须一起落库、续跑时一起交回。

    图 3　人工审批之后：怎么被唤醒

    1. 1提交决定只改 approval 行，它是决定的唯一记录；图不在运行，没有东西要「通知到图里」。改 run 的状态是执行器的事，经 DecisionListener 通知。
    2. 2barrier 按 reason 分派：approval 看审批行已不是 pending，subagent 看子 run 已到终态。waiting_on 里每一项都有结果才续；同一批里有两个请示时，批了一个不会续。
    3. 3续跑 = 先放回排队，再抢锁。UPDATE run SET status='queued' WHERE status='suspended'：三个入口撞在一起时只有一个能改成，只有它去抢锁。做决定的请求落在哪个实例，就在哪个实例抢；那里没有空槽，run 就留在排队里，由某个实例的兜底任务抢走；兜底任务补查到的，由补查的实例自己抢。

    图 4　段 2：新建一张图，before_model 直接跳到 tools

    1. 1图入口的 PatchToolCalls：call_1 没有结果，但在 waiting_on 里，说明是「在等」，不补 cancelled。只有不在 waiting_on 里的悬空调用才补。
    2. 2before_model：A 已在 decisions 里 → jump_to: "tools"，不先调模型。
    3. 3工具节点重新执行最后一条 AIMessage 的调用。PermissionMiddleware 认出 call_1 登记过等待、结果是 approved → 真正执行 delete_file；release_wait 把工具结果和「删掉 waiting_on.call_1」放进同一个更新。同一批里已有结果的兄弟调用由 SuspensionMiddleware 原样返回，不重跑。被拒绝时回一条失败的工具结果（带理由），模型换个方案继续，run 不终止。
    4. 4回到 before_model：waiting_on 已空 → 调模型。模型看到 delete_file 的结果，接着这一轮。
    5. 5之后照常：没有 tool_calls 就结束，发 run.finished，释放会话锁；又遇到要请示的工具，就再挂起一次（回到图 1），一个 run 可以分很多段。

    为什么这样做

    做法为什么
    跳到 END，不用 interrupt() + checkpointer图的 state 只有消息和 waiting_on，事实源分别是 message 表和 run 行。checkpointer 会多出第二个状态源，还要求续跑回到存了快照的地方。续跑只需要知道「这一段从哪个节点开始」，before_model 的 jump_to 已经能做到。
    判断放在 before_modelmiddleware 没有 after_tools 钩子。工具节点的出边指向 before_model，那里是「整批工具执行完、下次调模型之前」，是唯一既能看到整批结果、又来得及不调模型的位置。
    被拦下的调用不写占位结果写了的话，续跑执行后同一个调用就有两条结果，下一次模型调用会被拒（每个 tool_use 恰好一条 tool_result）。悬空调用是「在等」还是「被放弃」，靠 waiting_on 区分。
    waiting_on 和消息同一个事务落库漏了 waiting_on，续跑时 Patch 会把 call_1 当成被放弃、补一句 cancelled，模型照着回答，批准了的工具永远不执行。
    barrier 按 reason 分派审批挂起时没有子 run，按子 run 判会立刻满足 → 续跑、又挂起、再续跑，死循环。
    结果和删除等待项放进同一个更新等待项留着的话，回到 before_model 时它的 token 仍在 decisions 里，于是又跳 tools，来回跳到 GraphRecursionError。
