    取消原理

    一句话：取消就是在 Redis 里写一个键 run:cancel:{run}。谁在跑这个 run，谁就在自己的安全点看见它、自己收尾；挂起中的 run 没有进程在跑，由接到请求的执行器当场收尾。取消是协作式的：不硬打断正在执行的工具，在帧与帧之间停下。下面四张图，场景同上面的时序图：父 run 在跑，它派出的子 run 挂起等审批，用户点「停止」。橙色是这个场景实际走的路，灰色虚线是没走的分支。讲的是现在代码里的做法，和上面时序图（目标模型）不一样的地方列在最后。

    图 1　一次取消分几条路：看 run 此刻在哪

    1. 1执行器写取消位：一个 Redis 键，1 小时过期。重复写没有副作用，所以级联时对在跑的父 run 再写一遍也无妨。
    2. 2RunService.cancel 写完这个 run，再逐层找还没结束的子孙 run（unfinished_children_of），每个都走一遍同样的流程。父 run 已经结束也要做：页面上的「停止」针对的是父 run，直接回 409 的话，还在跑的子 run 永远停不掉；一个子孙都没有才回 409。
    3. 3执行器只在 run 挂起中时当场收尾。在跑的交给跑它的那个实例自己看见，那个实例不一定是接到请求的这个；排队中的什么都不做。场景里父 run 走第一条（原生、在跑），子 run 走第三条（挂起中）。

    图 2　原生智能体：只在图吐出帧时检查

    1. 1runner 每收到一帧（模型的 token、状态更新、审批这类自定义事件），先经注入的取消令牌查一次取消位；引擎只认令牌，不认识 Redis。Redis 查不到时按未取消处理，下一帧再查。
    2. 2工具在执行时点「停止」，图里没有帧，也就没有检查点：要等这个工具返回、图吐出下一帧才停。Shell 命令、MCP 调用、读写文件都一样；并行的一批工具里，先返回的那个会带来一帧。
    3. 3看见之后：先补记这一段已经花掉的 token（usage.updated），再产出 run.cancelled（带已经吐出的字数），然后 return。
    4. 4退出 astream 循环，图里还没完成的节点随之被取消：模型的流式请求断开；同一批里还在跑的工具收到 CancelledError，Shell 工具据此到沙箱里中断那条命令（execd interrupt），不会留一个没人管的进程。段内复用的 MCP 会话在收尾时关掉，收尾本身屏蔽了取消。

    图 3　收尾：两条路写下同样的终态

    1. 1在跑的 run：段收尾把还没落检查点的消息落库，发出了、没拿到结果的调用补一条「中断，结果未知」——不删那个调用，删了等于告诉模型「没发生过」，它会原样再做一遍。run 行写成 cancelled，先落库、再发布 run.cancelled，最后清取消位、放会话锁。
    2. 2挂起中的 run：settle_cancelled 不装图、不跑任何东西，造一个 run.cancelled，和 run 行的终态同一个事务落库，再发布、清取消位、放会话锁。不当场收的话，run 一直躺在挂起状态，会话锁也一直不放，用户连下一句都发不出。
    3. 3挂起中被取消的 run，waiting_on 里的调用在消息里仍然没有结果。下一轮进图时它们已经不在新 run 的 waiting_on 里，PatchToolCallsMiddleware 补一条「was cancelled」，模型看到的历史始终合法（每个 tool_use 恰好一条结果）。

    图 4　CLI 智能体：取消在 Pod 里走完

    1. 1CLI 运行时的循环每次最多等 0.5 秒取一条 bridge 发来的消息，只有一条都没取到时才查取消位。
    2. 2看见取消就发 turn.cancel（只发一次），然后照常收消息，等 bridge 宣告这一轮结束。
    3. 3bridge 的 Turn 进入取消：挂起的权限询问全部回 cancelled 并向平台撤回，给 CLI 发 ACP 的 session/cancel，同时开始 15 秒宽限。
    4. 4CLI 停下，session/prompt 以 stopReason = cancelled 返回 → turn.ended → CLI 运行时翻成 run.cancelled，和原生一样走段收尾。取消期间 CLI 若以别的原因正常结束，以它的实际结果为准（completed）。
    5. 5宽限到点还没结果：判定 agent 坏了，bridge 重启 CLI 进程、恢复同一个会话，这一轮记为失败。断线期间收到取消则不再重连，直接以取消收尾。

    为什么这样做

    做法为什么
    取消位是 Redis 里的一个键，不是去 cancel 那个 asyncio.Task跑这个 run 的可能是任何一个实例，接到请求的进程不一定持有它；续跑、接管之后还会换实例。一个键谁都能写、谁都能读，进程重启也不丢；而且天然幂等，级联时重复写无害。
    协作式：在帧之间停，不硬打断正在执行的工具硬打断会留下半截副作用（写了一半的文件、发出去一半的请求），而且结果未知。在帧之间停下，已经完成的模型发言和工具结果都能完整落库。代价是长工具执行期间看不见取消（图 2 的盲区）。
    挂起中的由执行器当场收尾没有进程会读到取消位。不当场收，run 会一直躺在挂起状态，直到某个子 run 恰好跑完来唤醒它，而子 run 可能要跑一小时。不等子 run：它已经被级联取消，会自己收尾。
    逐层级联，父已结束也要做子智能体能再派子智能体，只取消直接子 run 的话，孙 run 还在跑，跑完还会去叫醒一个已经被取消的父 run。
    被中断的调用补「结果未知」，不删那个 tool_use删掉等于告诉模型这次调用没发生过，它会原样再做一遍，而中断的工具可能已经产生了副作用；如实说「中断，结果未知」，它才有机会先去确认状态。
    先落库再发布 run.cancelled前端看到 run.cancelled 时库里已经是 cancelled，不会出现「停了，刷新后却读到还在跑」。
    查取消位失败按未取消处理Redis 抖一下不该让在跑的 run 失败；代价只是那一帧没看见，下一帧再查。
    CLI 的取消交给 bridge 去走平台看不到 CLI 内部的工具调用，只能请 bridge 转告 CLI；权限询问、宽限、重启都在 Pod 里处理，平台只等「这一轮结束了」。

    现在的代码和上面时序图的差别

    地方现在
    挂起中的 run 挂着的审批没有作废（时序图第 9 步的 expire_run 还没有）：审批行仍是 pending，刷新页面后列表里还会出现，点「允许」能成功，只是不再续跑。
    CLI 运行时查取消位的时机只在 0.5 秒内没取到消息时才查，收到事件、通知都直接进下一轮循环：CLI 连续输出时，取消要等出现空档。
    取消位的过期时间1 小时。运行本身不设时长上限，一个工具执行超过 1 小时，取消位会在它返回前过期，这次取消就丢了。
    排队中的 run领取时不查取消位：等被领走、装配完（模型、知识库、MCP），跑到第一帧才停，白装配一次。
    当场收尾和唤醒撞在一起执行器读到 suspended 之后，若审批决定或子 run 结束恰好把它改成 queued、又看到取消位，两边会各收一次尾、发两个 run.cancelled：settle_cancelled 写终态时不看当前状态。
