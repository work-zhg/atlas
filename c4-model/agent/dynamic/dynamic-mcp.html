    MCP 原理（Agent 一侧）

    一句话：Atlas 只连 MCP 网关、只做远程。服务和工具定义从网关读，调用经网关、带这个智能体的 Key，上游凭据只在网关。原生智能体每段装配时只读缓存、过三道闸门，不连 MCP 服务；第一次调用时才建会话，同一段里同一个服务复用一个会话，段结束就关。每次调用都经过一层护栏：参数校验、超时、按网关给的原因分类失败、能先修复的重试一次、结论在本段记住。失败转成给模型的工具结果，不让整轮失败。CLI 智能体的 MCP 客户端在 Pod 里，Atlas 只在开会话时交给它服务级的网关地址和 Key。下面五张图，场景同上面的时序图：原生智能体勾了 mcp:serpapi:google_search，在这一段里调了两次。橙色是这次实际走的路，灰色虚线是没走的分支。讲的是现在的代码，和代码图（目标模型）不一样的地方列在最后。

    图 1　只连网关：原生和 CLI 两条路，Key 和凭据在哪

    1. 1只经网关、只做远程：服务和工具定义从网关的内部接口读，Atlas 不自己发现工具，也不在平台里拉起 stdio 进程。装配时读的只有元数据和 Key，两样都有缓存，不连 MCP 服务（图 2）。
    2. 2原生智能体的调用由工具接入里的 MCP 客户端发出：每个服务一个客户端，智能体的 Key 和身份请求头写在传输层，模型看不到、改不了；每次调用都经过护栏（图 3）。
    3. 3CLI 智能体的 MCP 客户端在 Pod 里：Atlas 只在开会话时把服务级的网关地址和 Key 交给它，之后握手、拉工具列表、调用都是 CLI 自己做（图 5）。
    4. 4网关是唯一的治理点：每个请求认 Key、判权到工具，原生和 CLI 走的是同一条路；上游凭据只在网关。

    图 2　装配：读缓存、过三道闸门，不连 MCP 服务

    1. 1元数据（服务、工具定义）进程内缓存 60 秒；过期了问网关，问不到就用上一份，进程里没有就读 Redis 里的副本（7 天）。
    2. 2智能体的 Key 和它此刻能用什么，是网关算好的（公开的服务 + 授给这把 Key 的），和网关数据面判权是同一份。缓存 30 秒；网关上还没有这把 Key 就补申请；网关不可用时沿用这个进程上次取到的。每个智能体一把 Key，和智能体的权限类型无关。
    3. 3三道闸门，跳过一定要提示：静默少一个工具，模型照常做事、只是做不好，用户不知道为什么。闸门三里的复核状态现在恒为通过（网关已不做人工复核），真正起作用的是指纹：它覆盖名字、描述、参数定义和注解，因为只改描述、不改名字是注入风险最高的变更。
    4. 4每个服务一个 MCP 客户端，每个工具包一层护栏（图 3）。只读注解（readOnlyHint）平铺进工具的元数据，审批按它判副作用类别；没声明只读的一律按 EXTERNAL，最保守。
    5. 5工具数量或定义总量超过阈值时，全部改为延迟工具：定义不常驻上下文，模型用 tool_search 按需加载。

    图 3　调用：每次都经护栏

    1. 1本段里已经记住「用不了」的（整段、这个服务或这个工具），直接交回同样的说明，不再打扰网关。
    2. 2按工具的参数定义校验参数，错了直接交回模型改正。要在 Atlas 这边做，是因为服务自己校不校验因服务而异，网关从 REST 转出来的服务可能把错参数直接传给后端。
    3. 3同一段里同一个服务复用一个会话：第一次调用时建（initialize、initialized、tools/list），之后每次只发一个 tools/call。建会话也算在这次调用的超时里。
    4. 4失败按网关给的原因分类（下表）。能先修复的修好后重试一次；不能的，按原因在本段记住到相应范围，然后转成给模型的工具结果。一个外部服务出问题，模型可以换方法、告诉用户找谁；整轮失败的话用户什么都拿不到。
    5. 5成功：超过 10 万字符的文本块留头 70%、尾 30%。这个阈值高于上下文管理的外置阈值，一般大小的结果交给上下文管理去外置，这里只拦返回几 MB 的。

    图 4　一段之内：会话和 Key 的一生

    失败怎么分类（providers/mcp/native.py 的 _classify、_gateway_failure）：

    情况给模型的说明自动重试本段记住
    key_missing、key_invalid智能体的 Key 已失效或停用，告知用户联系 MCP 管理员；不要重试重取 Key，取到新的就重试一次取不到或仍被拒：整段
    forbidden没被授权使用这个服务，联系服务所有者或 MCP 管理员；不要重试否这个服务
    service_disabled、service_not_found服务不存在或已停用，联系 MCP 管理员；不要重试否这个服务
    tool_unknown、invalid_params工具暂时不可用（带网关的说明）；不要重试否这个工具
    authz_unavailable服务暂时不可用，可以稍后重试否不记住
    upstream_error、upstream_unavailable，以及以后新增的原因服务返回了错误 / 暂时不可用，可稍后重试或换一种方式否不记住
    会话失效（带会话标识的请求回 404）会话已失效，可稍后重试重建会话，重试一次不记住
    认证被拒、没有网关的原因（401 / 403）网关前面的一层拒绝了认证，联系管理员检查凭据；不要重试否不记住
    超时只读工具：可以稍后重试；有副作用的：结果未知，可能已经执行，重试前先确认否不记住
    上游返回的业务错误（isError）原样交给模型（同样截断）否不记住
    取消、编程错误不归这里，照旧抛出——

    图 5　CLI 智能体：开会话时下发服务级的网关地址和 Key

    1. 1CLI 只能按服务下发：它自己 tools/list，看得到服务的全部工具。Key 停用、服务没授权的不下发并提示；block 策略下有一个工具的定义变了，整个服务这一轮不下发。
    2. 2下发的是网关上的地址和这个智能体的 Key（ACP 的请求头是数组），外加使用者 X-Uid（只作审计，权限主体由网关按 Key 写入）。CLI 运行时每轮都解析一次，但只在 session.open 时用得上：CLI 进程启动时读这些配置，中途换不了。
    3. 3Key 进 Pod 是有意接受的风险：它的能力不超出授给它的权限，工具级的授权和停用由网关在每个请求上执行。原生智能体那层护栏 CLI 没有，失败怎么处理由 CLI 自己决定。

    为什么这样做

    做法为什么
    只连 MCP 网关，只做远程服务注册、工具定义、授权、上游凭据都在网关，Atlas 不自己发现工具、不持有上游凭据，也不在平台里拉起 stdio 进程。网关是唯一的治理点，原生和 CLI 都经它。
    装配时只读缓存，建连推迟到第一次调用一个慢的服务不该拖慢每一轮，一个宕机的服务也不该让所有挂了它的智能体发不出消息；元数据在进程内和 Redis 各有一份，网关短暂不可用时照样装配。
    跳过必须提示静默少一个工具，模型照常做事、只是做不好，用户不知道为什么。
    Key 写在传输层，每个请求现取模型看不到、改不了；Key 在网关被重置后，被拒的那次请求重新取一次就能接着用，已打开的会话不用重建。
    身份闭包捕获，不进工具参数身份能由模型指定，就是冒用他人身份的口子；身份写成请求头只作审计，网关会改写成它确认过的身份。
    一段之内复用会话，段结束就关每次都新建会话要 4 个请求，复用后 N 次调用 N + 3 个。会话不跨段、不跨进程：挂起可能等很久，接管的实例重新建就好。
    只有能先修复的失败才自动重试，而且只一次Key 刚被重置、会话失效时，请求确定没到后端，修好重试是安全的；超时、后端出错时结果未知，有副作用的工具执行两次就是两张工单、两封邮件。
    失败转成给模型的工具结果，不让整轮失败模型可以换方法、告诉用户找谁；确定用不了的在本段内记住，模型再调直接给同样的说明，不再打扰网关。
    Atlas 侧校验参数服务自己校不校验因服务而异，网关从 REST 转出来的服务可能把错参数直接传给后端；LangChain 和 langchain.mcp 都不做这个校验。
    CLI 拿服务级的网关地址和 KeyCLI 的 MCP 客户端在 Pod 里，Atlas 拦截不到单次调用，只能在开会话时下发；工具级的授权和停用由网关在每个请求上执行。

    装配收进 McpToolset，原生和 CLI 各调一个入口原生的装配在 executor/tool_surface.py（取目录、取 Key、建 McpSessions、Key 重取）和 providers/mcp/native.py；CLI 的下发在 CLI 运行时和 providers/mcp/acp.py（refactor/track-a 上已改名 providers/mcp/cli.py）。

    去掉复核review.py 还在；网关的 review_required 恒为假，闸门三里的复核判断走不到。
