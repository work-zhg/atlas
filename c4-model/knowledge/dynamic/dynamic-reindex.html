    换向量模型原理：新旧两套并存，建好了再切换

    一句话：换了向量模型，库里所有文字都要用新模型重新算一遍向量；新旧模型算出来的数字串长度和含义都不一样，不能混在一起比。所以不是原地改，而是另起一套：新建一个索引版本，对应向量库里一个新的 collection，后台用新模型把库里的分段重算一遍写进去；这期间检索照常用旧的那套，新上传的文档两套都写；全部建好后，改一个开关切到新的。旧的那套留着，新模型效果不好可以随时切回来。下面先解释几个词，再用六张图走一遍：图 1 讲为什么不能原地换，图 2 是版本的几种状态，图 3 到图 6 依次是新建、重建、构建期间的双写、切换与回滚。场景同上面的时序图：库的所有者把库 A 的向量模型从 bge-small-zh 换成 bge-m3。橙色是这个场景实际走的路，灰色虚线是没走的分支。

    先认识几个词

    词意思
    向量模型把一段文字变成一串数字（向量）的模型。不同模型算出来的数字串长度（维度）不同，含义也不同：bge-small-zh 是 512 个数，bge-m3 是 1024 个数。
    索引版本一个库用某个向量模型建出来的一整套向量。一个库可以有好几个版本，但同一时刻只有一个在用。版本号从 1 往上加。
    collection向量库里的一张「表」，一个索引版本对应一个，名字是 kb_{库}_v{版本号}（库的 uuid 去掉连字符）。
    当前版本（active）检索时用的那个版本。每个库恰好一个。
    写入目标写向量时要写进哪些版本：当前版本，加上还没删掉的其他版本（构建中的、待切换的、退役的）。
    双写一份新内容同时写进几个版本，每个版本用自己的模型各算一遍向量。
    重建后台把库里已经入库完的文档，用新模型重新算向量，写进新的 collection。分段的文字不变，不重新解析、不重新切。
    切换、回滚切换：把当前版本从旧的改成新的。回滚：再切回旧的。都只改一处，在一个数据库事务里完成。
    召回测试在控制台输入一个问题，看库会搜出哪几段。可以指定版本，用来比较新旧模型的效果。

    图 1　为什么不能原地换：同一段文字，新旧模型算出两套向量

    1. 1分段的文字只在数据库里存一份。向量库里存的是它算出来的向量；用哪个模型算的，记在索引版本上。
    2. 2旧模型（例：bge-small-zh）把它算成 512 个数，放在 v1 的 collection 里。
    3. 3新模型（例：bge-m3）要把同样的文字重新算一遍，得到 1024 个数，放进另一个 collection（v2）。
    4. 4为什么不能原地覆盖：检索时问题也要用同一个模型算向量，才能和库里的向量比。新旧模型的数字串长度不同（512 对 1024），根本没法比；就算长度一样，两个模型对「意思」的编码方式也不同，比出来没有意义。原地一条条改的话，改到一半时库里新旧混杂，检索结果全乱。所以另起一套，全部算完再切过去。

    图 2　一个索引版本的状态怎么变

    1. 1building（构建中）：刚建好记录，后台正在用新模型重算。同一个库同一时刻只能有一个构建中的版本。出错就变成 failed，记下原因；要重来就删掉它，再建一个。
    2. 2ready（待切换）：全部算完了。可以先用召回测试对比两个版本的效果，满意了再手动切换。建版本时勾了「建完自动切换」，就跳过这一步直接切换；在库设置里直接改向量模型，就相当于勾了它。
    3. 3active（当前版本）：检索用的就是它。每个库恰好一个，不能删。
    4. 4retired（已退役）：被新版本换下来的旧版本。collection 留着，新内容照样写进去，随时可以切回来（回滚）。
    5. 5deleted（已删除）：手动删掉一个不在用的版本，它的 collection 一起删掉，从此不再往里写。删掉一个构建中的版本，后台重建会在做完当前这份文档后停下。

    图 3　新建版本：探维度、写记录，提交之后再投递重建

    1. 1库的所有者在库的设置里选新模型。可选的模型 = 镜像里自带的本地模型 + 模型平台分配给知识库的远程模型。
    2. 2换模型属于「管理」，要 Owner 权限（包括「全部知识库 · Owner」的授权）。
    3. 3同一时刻只能有一个构建中的版本：两个同时重建会互相抢 worker 和模型调用额度，最后切到哪一个也说不清。
    4. 4先把新模型加载一次，算一段测试文字，看它输出多少个数（维度），记在版本上；建 collection 时要按这个长度建向量字段。
    5. 5写一行版本记录：版本号 = 上一个 + 1，状态 building，collection 名 kb_{库}_v{版本号}，然后提交。
    6. 6提交之后再投递重建任务，worker 才看得到这个版本。从提交这一刻起，写入目标里就多了 v2：新上传的文档、人工编辑的分段，写向量时 v1、v2 都写；删除、开关、改文档属性，两边一起改。检索照旧只用 v1。

    图 4　重建：把已入库的文档用新模型再算一遍

    1. 1重建任务先拿这个版本的重建锁，并按文档记进度。进程死了，锁过期后巡检会把它重新投递，从记下的进度接着做，不会一直卡在构建中。
    2. 2在向量库里建新 collection：向量字段的长度按新模型的维度；同时建好所有筛选字段的索引（包括库里定义的每个元数据字段），否则切过去以后按元数据筛选会变成全表扫描。建好后加载，召回测试就能指定这个还在构建中的版本试效果。
    3. 3列出这个库里已经入库完成的文档。还在入库的不在这里做，它们自己会双写（图 5）。
    4. 4一个一个文档做：读出它的分段（文字不变，不重新解析、不重新切），用新模型算向量，写进新 collection，再记一次进度（例：已完成 120 / 300 份）。文档向量的缓存是按模型分开存的，换了模型就用不上，都要重算；远程模型经模型平台调用。
    5. 5补扫：做完一轮再查一次，有没有这期间新入库完成的文档，有就接着做，直到没有为止。
    6. 6重写「早开始」的文档：版本建立之前就已经开始写向量的文档，前几批只写进了 v1（图 5 的文档 Y）。等它们入库完成，把整篇再写一遍进 v2，补上缺的那几批。
    7. 7清孤儿：构建期间被删掉的分段、文档，可能在新 collection 里留下记录。拿新 collection 里的主键和数据库里现有的分段对一遍，多出来的删掉。
    8. 8全部做完，版本改成 ready；勾了「建完自动切换」的，在同一个事务里直接切成当前版本（图 6）。

    图 5　构建期间：三种文档怎么进到新版本里

    1. 1文档 Z 在 v2 建立之前就入库完了，它的向量只在 v1 里。重建任务会把它写进 v2（图 4 的 ④）。
    2. 2文档 Y 在 v2 建立之前就开始入库：前两批写的时候还没有 v2，只写进了 v1；入库每一批开始前都会重新读一次写入目标，所以 v2 建立后，第 3 批起两边都写。它完成之后，重建任务把整篇再写一遍进 v2，补上前两批（图 4 的 ⑥）。
    3. 3文档 X 在 v2 建立之后才上传，每一批都两边写，v2 里一开始就是全的。
    4. 4检索在切换之前一直用 v1，切换之后用 v2。重建要跑几个小时也没关系：期间检索照常可用，新文档也照常入库。

    图 6　切换与回滚：只改「当前版本」这一处

    1. 1切换前：v1 是当前版本，v2 已经建好（ready）。可以先在召回测试里分别用 v1、v2 搜几个问题，对比效果。
    2. 2切换是一个数据库事务：v2 改成 active，v1 改成 retired。检索每次都先读「当前是哪个版本」，所以一次检索要么全用 v1，要么全用 v2，不会一半一半；问题的向量也跟着改用 v2 的模型算。
    3. 3v1 退役后 collection 不删，继续双写，也保持加载（开 mmap，主要占磁盘而不是内存）：新内容照样写进去，回滚时数据是全的，切过去马上能查。
    4. 4回滚就是再切换一次：觉得新模型效果不好，把 v1 切回当前版本。确定不要的版本可以手动删掉，从此不再双写；正在用的版本不能删。

    为什么这样做

    做法为什么
    换模型不原地改，另建一套重算可能要几个小时，原地改的话，这期间库里一部分是新向量、一部分是旧向量，检索结果全乱；另建一套，旧的照常用。
    同一时刻只有一个构建中的版本两个同时建会互相抢 worker 和模型调用额度，最后切到哪一个也说不清。
    新内容同时写进所有还在的版本（双写）重建期间库还在用，新上传、编辑的内容如果只进旧版本，切过去以后就少了这一部分。
    写入目标每一批都重新读版本是在某个文档入库到一半时建立的，下一批就能写进去，不用等这个文档重新入库。
    重建完再补扫，并重写「早开始」的文档版本建立前就在写的文档，前几批只进了旧版本；不补的话，新版本里这些文档会缺几段。
    重建可以续跑，按文档记进度几千份文档要跑很久，进程随时可能被重启；每次从头再来，既慢又费模型调用。
    新 collection 建好全部筛选索引否则切过去以后，按元数据筛选会变成全表扫描，检索突然变慢。
    切换只改「当前版本」一处，在一个事务里检索看到的要么是旧版本、要么是新版本，不会一半一半。
    旧版本保留、继续双写、保持加载新模型效果不好时能马上切回去，而且回滚后的数据是全的；代价是多写一份、多占一份存储，直到手动删除。
    「当前用哪个版本」只记在索引版本上知识库本身不再另记模型和 collection；只记一处，切换时不会两边对不上。
