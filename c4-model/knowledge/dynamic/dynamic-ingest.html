Diagram key

    入库原理：一个文档一个任务，按阶段落库，停得下、续得上

    一句话：入库就是一个文档一个任务：worker 拿到任务先抢这个文档的入库锁，然后按阶段跑——解析、分段与增强、写分段、分批向量化、完成——每个阶段一个短事务，状态立刻看得到。分段写进库就是续跑点：之后再中断，只把还没向量化的分段接着做，不重新解析；每一批先写向量库、再把这批分段标成完成，重跑就是按主键覆盖。暂停和删除靠 Redis 里的一个标记，任务在每个阶段、每一批之前看；进程死了，锁一分钟内过期，接口进程的巡检把停在中间状态的文档重新投递。下面九张图：图 1 是总览，图 2 到图 7 逐个讲每个阶段怎么做，图 8、图 9 讲暂停、失败和中断。场景同上面的时序图，橙色是这个场景实际走的路，灰色虚线是没走的分支。

    图 1　一个文档走一遍：阶段、状态和落下的东西

    1. 1上传在接口进程里：校验、存原文件、建文档行（waiting），提交之后才给每个文档投递一条入库任务（图 2）。
    2. 2解析：原文件 → DocIR，DocIR 和图片存回 OSS；解析质量差的文档先进待审核（图 3）。
    3. 3分段与增强：DocIR 切成父分段和子块，按库开关补上下文、写表格摘要；这一步的结果只在内存里（图 4）。
    4. 4写分段：一个事务整篇替换这个文档的分段，记下 splitting_completed_at。这是入库唯一的续跑点（图 5）。
    5. 5分批向量化：每批 64 个还没 completed 的分段，先写向量库、再在一个事务里标 completed（图 6）。
    6. 6完成：再同步一次文档级字段，带 supersedes 的新版本取代旧版本（图 7）。

    图 2　上传：校验、存原文件、建文档，提交之后再投递

    1. 1控制台经网关上传一个或多个文件，带上处理规则（切法、长度、解析器）和文档属性（元数据、ACL、生效区间、supersedes）。接口先确认调用者能写这个库：库级权限问用户中心。
    2. 2校验：格式在支持列表里、单个文件不超过 50 MB、单库最多 5000 份文档；同一个库的文档必须用同一种分段结构；元数据按库定义的字段校验，ACL 规范化；上传新版本时一次只能传一个文件。
    3. 3处理规则存一份，这一批文档都引用它；库记下最近一次用的规则，下次上传默认沿用。
    4. 4原文件写进 OSS，key 是 {前缀}/{库}/{文档}/{文件名}。之后的 DocIR 和图片也放在这个前缀下，删文档时一起清掉。
    5. 5建文档行：waiting、同一个批次号、库里的位置。要求审核的库，新文档先待审核（照常入库，审核通过前不参与检索）；带 supersedes 的加入旧文档的版本组，入库完成时才取代它（图 7）。
    6. 6提交之后才投递：每个文档一条 indexing_task 进 Redis 队列 dataset，各 worker 并发领取。先提交是因为 worker 可能比提交更早读库，读不到文档就直接退出。接口立刻返回批次和文档，控制台按批次轮询进度。

    图 3　解析：原文件 → DocIR，顺带出一份质量报告

    1. 1worker 从 OSS 取原文件，按扩展名选解析器；不支持的格式报错并列出支持的格式。解析是纯计算、不碰 IO，读写 OSS 都由入库编排做。
    2. 2PDF 用字符坐标做版面分析，CPU 就能跑，不用版面模型：词拼成行（双栏时同一高度拆开）；剔除跨页重复的页眉页脚和页码；双栏页先左后右；行按行距、缩进、字号合并成段落；标题优先用书签，没有书签按字号、加粗、编号打分；只认有框线的表格，跨页续表合并；图片按坐标裁下来，关联「图 X」图注。DOCX 按样式还原标题和列表，PPTX 一页一个小节；表格类文件一个工作表一张表；纯文本类整段原文一块，结构留给分段识别。
    3. 3处理规则可以指定 parser = text：每页一块纯文本、保留页码，分段时再识别结构。个别文档版面分析出错时，换它重新入库。
    4. 4DocIR 是解析和分段之间唯一的契约：带类型、层级、页码和坐标的块序列。分段直接按块组装，不再从纯文本里猜标题和表格；页码和坐标一路带到分段上，用于引用定位。
    5. 5DocIR 存成 docir.json，图片写到 assets/，都在原文件的前缀下。解析预览、换分段规则时直接读它，不用重新解析。
    6. 6解析报告记页数、扫描页、空页、双栏页、乱码比例和标题、表格、图片数。缺文字（扫描件）或乱码多时 needs_review：文档先进待审核，照常入库，人看过解析预览再放行，或换解析器重来。不做 OCR。

    图 4　分段与增强：DocIR → 父分段和子块，再按库开关补上下文、写表格摘要

    1. 1默认按结构切：维护一个标题栈，一个小节一个父分段，标题层级默认到三级；同一上级下相邻的短小节可以合并，超长的按单元边界拆（父分段默认上限 3000 字，通用模式一段默认 800 字，因为它要整体进向量模型）。没有标题的文档自然退回按段落打包。可选语义分段：相邻句向量相似度骤降处断开。
    2. 2按规则切：先按分隔符切，超长的按换行、句号、空格依次递归细分，相邻小块合并到上限内、按重叠拼接；也可以整篇一个父分段。切之前先清洗：去控制字符，按规则压空白、去 URL 和邮箱。
    3. 3父子模式下，父分段是返回给模型的上下文，子块是它里面的结构单元、是检索入口：太短的并入下一个，太长的按句切（子块默认上限 300 字）。通用模式下分段自己就是检索入口。
    4. 4正文存原文；标题路径、引用定位（页、框、图片）单独存。建向量时在前面拼上前缀：标题路径，表格行再加表头。表格是原子块，放得下就不拆。分段和子块的 uuid 在这里生成，之后就是向量库的主键。
    5. 5上下文补全（库开了才做）：给每个父分段生成一句「这一段在全文中讲什么」，拼进向量化前缀。文档正文放在提示词前面作固定前缀（最多 3 万字，超长改用邻近内容），同一文档的调用前缀相同，能命中模型网关的前缀缓存。
    6. 6大表摘要（库开了才做）：行数达到阈值（默认 8 行）的表格生成一段摘要（主题、维度、关键数字），作为 summary 子块挂到包含它单元格最多的分段上。「哪种假期最长」这类汇总问题匹配不到任何单行时，靠它召回。表格从 DocIR 取，不从分段里找：一张表可能被切进好几段。
    7. 7增强结果按模型、提示词版本、文档哈希、分段哈希缓存在 Redis 30 天，重跑不用再调模型；最多 4 个并发。单个调用失败只是那一段少了增强，失败数写进解析报告。

    图 5　写分段：一个事务整篇替换，记下续跑点

    1. 1切出来的父分段和子块此时只在内存里，uuid 已经生成好。
    2. 2先删向量库里这个文档的旧 entity，所有 collection 还在的索引版本都删。重新入库时新分段的 uuid 是新的，旧的不删就成了孤儿：搜得到，却回不到任何分段，白白占掉候选名额。向量库不在数据库事务里，所以放在事务前面；删完之后事务失败也没关系，重跑会重新写。
    3. 3一个事务里删旧分段和子块、写新分段（status = waiting）和子块：正文、标题路径、引用定位、向量化前缀都在这里落库。
    4. 4同一个事务里记下 splitting_completed_at：入库唯一的续跑点。
    5. 5提交之前中断，续跑点为空，重跑从解析开始（原文件还在 OSS）；提交之后中断，续跑点有值，重跑跳过解析和分段，只把还没 completed 的分段接着向量化（图 9）。

    图 6　分批向量化：先写向量库，再在一个事务里标完成

    1. 1每一批之前先看暂停标记，再取最多 64 个还没 completed 的分段（父子模式下写进向量库的是它们的子块）。
    2. 2写入目标每批重新读一次：active 版本，加上 collection 还在的其他版本（构建中、待切换、已退役）。换向量模型时新建的版本，从下一批起就会被写到。
    3. 3每个目标用它自己的向量模型向量化。文档向量先查 kb_embedding_cache（模型 + 文本哈希），只算没缓存的；远程模型经模型平台调用。
    4. 4upsert 进这个版本的 collection：主键是分段或子块的 uuid，dense 是刚算的向量，检索文本交给 Milvus 生成 BM25 稀疏向量，标量字段带上文档级字段。
    5. 5所有目标都写完，才在一个事务里把这批分段标成 completed 并提交。
    6. 6写进向量库之后、提交之前进程死了：这批在库里还没 completed，重跑时整批再写一遍；主键相同、upsert 覆盖，结果和只写一次一样。

    图 7　完成：同步文档级字段，新版本取代旧版本

    1. 1汇总这个文档所有分段的字数，记下耗时，文档改成 completed、记完成时间。
    2. 2按文档把文档级字段（启用、审核、元数据、ACL、时效）再同步一次到向量库：按 document_uuid 查出主键，分批 partial upsert。入库中途有人改过 ACL、元数据时，正在写的那一批可能带着旧值；完成时整体覆盖一次就收敛了。
    3. 3上传时带了 supersedes 的新版本，入库完成这一刻才取代旧版本：同组其他当前版本 is_current = false，有效期截止到切换时刻；新版本从切换时刻起生效。切换时刻是新版本的生效时间，没写就是现在。新旧两版的文档级字段都同步到向量库。
    4. 4默认检索只要当前版本；按时间点检索时，时间点落在哪个版本的有效期里就返回哪个版本。新版本入库完成之前，检索一直看到旧版本，不会出现「新的还没好、旧的已下线」的空窗。

    图 8　状态与控制：暂停、恢复、重试、删除

    1. 1暂停：接口在 Redis 里设 kb:doc:{uuid}:paused。正在跑的任务在下一个检查点看到，停下并把文档改成 paused；还在排队的文档直接改成 paused。已经写进库和向量库的部分都留着。
    2. 2失败：任何阶段抛异常，文档改成 error、记下错误信息，锁随任务结束释放。
    3. 3恢复和重试是同一个动作：清掉暂停标记、改回 waiting、重新投递。只有 paused 能恢复，只有 error 能重试。重跑时按 splitting_completed_at 决定从哪开始（图 5）。
    4. 4进程死了（部署、OOM、节点故障）：文档停在 parsing / splitting / indexing，锁过期后没人持有。巡检把它重新投递，状态不变，接着做（图 9）。重复投递是无害的：多出来的任务拿不到锁就跳过，已经 completed 的直接返回。
    5. 5删除：先设暂停标记（1 小时过期），再删向量、分段、文档行和原文件前缀。正在跑的任务要么在下一个检查点停下，要么发现文档已经不在、直接退出。

    图 9　中断以后：锁过期、巡检重投、从没做完的分段接着做

    1. 1A 拿到锁 kb:doc:{uuid}:indexing（TTL 60 秒）开始跑，看门狗每 20 秒续一次。TTL 不是工作时长上限：进程活着，跑多久都行。第 3 批写到一半，进程被杀。
    2. 2没人续，锁最多 60 秒过期。文档的状态还是 indexing：只有持锁的任务会写 parsing / splitting / indexing，所以「处在这三个状态之一、却没有锁」就说明那个任务已经死了。
    3. 3接口进程里的巡检每 60 秒扫一次（每个副本各一份），把这种文档重新投递。不看 waiting：排队中的文档本来就没有锁，它的消息还在队列里。
    4. 4B 拿到锁，看到 splitting_completed_at 有值，跳过解析、分段、写分段，直接进入分批向量化。
    5. 5B 只取 status ≠ completed 的分段。第 3 批有一部分已经写进向量库，但没提交 completed，所以整批重写：主键是分段或子块的 uuid，upsert 是覆盖，不会多出重复的向量。

    为什么这样做

    做法为什么
    一个文档一个入库任务各文档能分散到多个 worker；Pod 被杀时只有正在跑的那一个停在中间状态。一批文档串在一个任务里的话，还没轮到的会一直停在 waiting，巡检也不看 waiting。
    提交之后才投递worker 可能比提交更早读库，读不到文档就直接退出，文档永远停在 waiting。
    每个阶段一个短事务大文件解析、向量化可能跑很久：状态要让控制台立刻看到，也不能长时间占着数据库连接。
    解析和分段之间只隔一个 DocIR，DocIR 存进 OSS分段直接按块组装，不再从纯文本里猜结构，页码和坐标能带到引用定位；预览、换分段规则时不用重新解析，换解析器也不影响分段。
    扫描件不做 OCR，只标记、进待审核OCR 要额外的模型和算力，结果也要人核对；先把问题暴露在解析报告里，不让一堆空分段悄悄进库。
    正文存原文，标题路径和前缀单独存建向量时拼上标题路径、表头和上下文能明显提升召回；但返回给模型和用户看的、人工编辑的都应该是原文，混在一起改一次就乱了。
    增强失败只是少了增强增强靠 LLM，会限流、超时；不能因为一句上下文生成失败就让整篇入库失败。失败数写进解析报告，看得到。
    「写完分段」是唯一的续跑点解析和分段的中间结果不落库，它们之前中断了从头再来最简单；分段落库以后，向量化按段记完成，中断只补没做完的，大文件不用重新解析。
    先写向量库、再标 completed，主键用 uuid向量库和数据库不在一个事务里。顺序反过来的话，死在中间会留下「标了完成却没有向量」的分段，永远搜不到；现在的顺序最坏是重写一遍，覆盖无害。
    新版本入库完成才取代旧版本新版本还在解析、向量化时，旧版本照常可检索；切换只发生在完成那一刻，不会有空窗。
    锁：短 TTL + 看门狗续租，拿不到就跳过TTL 只决定进程死后锁空悬多久，不限制工作时长；重复投递的任务拿不到锁就退出，同一个文档不会有两个任务同时写。放锁时校验持有者，不会删掉别人后来拿到的锁。
    恢复靠巡检，不靠 Celery 重新投递acks_late 下整个 Pod 被杀，消息要等 visibility_timeout（7 天）才回到队列；它又不能设短，到期会重复投递。看「中间状态且没锁」，进程死后一两分钟就续上。
    暂停是一个 Redis 标记，在检查点停不硬杀正在跑的任务：做完的阶段和批次都留着，恢复时从续跑点接着做。删除也借这个标记让正在跑的任务停下。
    不设到点结束的超时慢就慢，用暂停、删除控制；锁的 TTL 不是工作时长上限。
    完成时按文档再同步一次文档级字段入库中途改 ACL、元数据，和正在写的那一批会竞态，个别 entity 留着旧值；完成时按文档整体覆盖一次就收敛了。
