    记忆原理

    一句话：记忆服务只管「一个实例里一串带编号的条目」。一次写入 = 删除若干旧条目 + 至多新增一条，在实例行锁里串行、一个事务提交；删掉的条目不消失，只记下「被谁取代」，后到的写入沿取代关系找到现状，按客户端给的时间以晚的为准；主题每变一次，就从实例计数器拿一个新版本号。Atlas 一侧只多一条规则：写之前必须看过目标主题的最新版本。它为每个会话记一张版本表，对不上就先把最新条目交给模型，这次不写。下面五张图按时间顺序，场景同上面的时序图：用户说「以后前端项目都用 bun」，模型要用一条新记忆取代 #12「前端项目用 pnpm」（本轮用户发话的时间记作 08:15）。橙色是这次实际走的路，灰色虚线是没走的分支。

    图 1　写入之前的现场：记忆服务存什么，Atlas 记着什么

    1. 1作用域 → 实例 → 主题 → 条目。作用域由管理员配置；「作用域编码 + 关联主键」定位一个实例，第一次登记或写入时建行。Atlas 本期只用作用域 user，关联主键是会话所属用户的 uid，由 Atlas 按会话填，模型的工具参数里没有这一项。主题、条目都是 Atlas 写进来的，服务端不解释内容，「常驻」只是主题扩展属性里的一个标记。
    2. 2实例行上有两个计数器，只在实例锁里递增：条目编号（#31 这样的号，实例内唯一，移动、拆分都不变）和版本号（主题每变一次就取一个新值，整个实例共用一个序列）。服务端只报告主题的大小（条数、字数），不按大小拒绝写入。
    3. 3Atlas 为每个会话存一行 thread_memory：snapshot 是常驻块的快照，known 是模型看到的各主题版本。本例中模型前面已经 load_memory 过「工具链」，所以 known 里是 40，和服务端一致。

    图 2　写之前（Atlas）：没看过最新内容就不写

    1. 1守卫：用户在记忆页暂停了写入，或本轮已写满 memory_max_writes_per_run（8）次，就不写，工具结果里说明原因。同一轮的 save_memory、forget_memory 在一把进程内的锁里排队，计数不会算错。
    2. 2不管模型看没看过，都先加载一次目标主题，拿到服务端当前的版本号和全部有效条目。主题不存在时：给了 topic_description 就新建（attrs.resident 按参数定），新建的主题是空的，版本直接记入已知，接着写。
    3. 3比的是版本号，不是内容。版本表里没有这个主题（本会话没看过），或者有但和当前版本不同（之后被别的会话、补记、拆分或记忆页改过），这次就不写入：把最新条目作为工具结果交回，同时把已知版本记成当前版本。模型看完重新判断，再调一次就能写。这样冲突判断总是基于目标主题最新、完整的内容。
    4. 4一致就发写入（时序图消息 1）。replaces 原样作为 remove；时间取本轮用户发话的时间（补记取它依据的那条用户消息的时间）；幂等键由 run、作用域、主题、内容、删除的编号算出，网络重试、run 被接管后重放同一个调用，算出来都一样。

    图 3　服务端一次写入：锁内判定，时间晚的为准

    1. 1访问控制在锁外定位实例、查数据权限（时序图消息 2–5），然后锁实例行（不存在先建）。从这里起，同一实例的写入和拆分的提交一个一个来，锁随事务提交释放。加锁后重新读实例行：查权限时读进来的计数器可能已经被别的事务推进过，以锁里读到的为准。
    2. 2先按幂等键查修订：这个键写过，就原样返回第一次存下的结果（replayed: true），后面都不做。
    3. 3对要删的每一条找「现状」：还有效就是它；被取代过（deleted 且有 superseded_by），就沿取代关系往后走，找到现在有效的那条；被遗忘过（deleted 且没有后继），就取那次遗忘的时间。本例 #12 还有效。目标主题已被拆分时报 TOPIC_GONE，带上拆成了哪些。
    4. 4时间晚的为准：只要有一条的现状晚于本次写入的时间，就整次作废（outcome: discarded，带上冲突条目），什么都不写。遗忘早于本次的，只做新增（skipped）；时间相同的，后到的为准。
    5. 5执行：实例的条目编号 +1，得到 #31。#12 不真删，只改状态，记下 superseded_by=31、retired_at（本次的时间）和删除它的那次修订。
    6. 6实例的 version_seq +1，得到 41，写给这次受影响的每个主题（同一次操作共用一个值），顺带重算条数和字数。最后记一条修订（kind=write、removed [12]、added [31]、结果副本、幂等键），然后提交。

    图 4　写入之后的现场：旧条目挂在取代链上，版本号前进

    1. 1#12 没有被删掉：status=deleted、superseded_by=31、retired_at=08:15。只有 active 的条目会被列出和加载；删除的留在库里，可以撤销这次写入（恢复 #12、删掉 #31），也可以单独恢复。用户在记忆页彻底删除 #31 时，整条取代链（含 #12）一起删，不会删了「改用 bun」还留着「用 pnpm」。
    2. 2实例的两个计数器各进一格。受影响的只有「工具链」，版本 40 → 41；「沟通偏好」不动。版本号不依赖任何时钟、只增不减；整个实例共用一个序列，主题拆掉后再建同名主题，也不会撞上客户端记着的旧值。
    3. 3修订记下这次删了哪些、加了哪条，还原样留一份返回给客户端的结果：同一个幂等键再来，就照它返回。撤销就是按修订反向执行。
    4. 4Atlas 拿 changed 推进版本表。写入前的版本等于已知版本，说明中间没人写过，上下文里的内容加上这次写入就是最新，已知推进到 41；不相等就保持原值，下次加载会重新返回全部条目，调模型时也会附一条「有更新」的提示。

    图 5　后到的旧信息：沿取代链找现状，比时间

    1. 1补记在会话空闲后才跑，写入时间取它依据的那条用户消息的时间（07:50），不取执行的时间（08:50）。如果按到达顺序处理，晚到的补记就会盖掉用户 08:15 在另一个会话里说的新情况。
    2. 2服务端找 #12 的现状：它已被取代，沿 superseded_by 走到 #31。#31 的时间 08:15 晚于 07:50，于是整次作废，什么都不写，返回 conflicts。
    3. 3作废之后，补记直接放弃这一条；对话里的 save_memory 收到作废，会把这个主题从版本表里去掉，让模型先 load_memory 重新查看再判断。
    4. 4如果 #31 后来被遗忘了，就和遗忘的时间比。服务端只管「针对同一批旧条目」的先后：两次写入如果互相没看到对方、又都只做新增，两条会同时存在。读的时候以日期新的为准，下一次写入这个主题的客户端看完整个主题后再清理。

    为什么这样做

    做法为什么
    实例锁用数据库行锁（SELECT … FOR UPDATE），不用 Redis 锁锁和事务同生共死：多副本部署同样有效，没有「锁过期了，事务还在写」的窗口；条目编号、版本号也就能直接在实例行上递增。
    以客户端给的时间为准，不按到达顺序补记晚到、重试晚到都很常见（图 5）。客户端时间表示「这条信息成立的时间」，这要求各客户端的时钟基本一致。
    删除只改状态，记下被谁取代删错了能撤销、能恢复；后到的写入能沿取代链找到现状再比时间；用户彻底删除时能连整条链一起删。
    有冲突就整次作废，不部分执行一次写入表达的是一条记忆（「把 pnpm 改成 bun」）。只执行新增的话，新旧两条会同时有效。
    主题变没变看版本号，不看更新时间，也不比内容条目时间是客户端给的，补记的时间还可能早于已有条目，看不出主题变没变；多副本的时钟也不严格一致。版本号在实例锁里分配，只增不减。
    「写前必看」由 Atlas 判断，服务端不管服务端不知道客户端看过什么，它只保证并发和先后。Atlas 只比版本号，加载一次就能判断。
    幂等键由 run、作用域、主题、内容、删除的编号算出网络重试、run 被接管后重放同一个工具调用时，算出的键是同一个。服务端照修订上存的结果返回，不会写出两条。
    Agent 自己写入不重建常驻块常驻块在系统提示词里，一变，整段对话的前缀缓存就失效。写入结果已经在对话历史里，模型已经知道。
    服务端不按主题大小拒绝写入合适的上限因客户端、场景而异，所以上限由客户端自己定（Atlas 约 2000 字，超了提示模型合并或拆分）；服务端只报告条数和字数。
