Redis 中间件设计：连接按用途隔离，横切治理收进拦截链，高频模式做成标准原语

一句话：各业务服务不再裸调 redis.asyncio.from_url，而是统一接入嵌入式公共库 atlas_redis——底层按「短命令 / 阻塞流 / 单连接 PubSub」三路舱壁隔离，中层经可插拔拦截器链统一做护栏、命名空间、可观测与分级熔断，上层提供经验证的高阶并发原语（事件流、单连接订阅、脚本注册、原子限流、单飞缓存、分布式锁）。

这份设计回答五个问题：为什么选进程内客户端中间件而不是独立 Proxy；三类连接为什么要物理拆池并配不同超时；拦截器链怎么在不侵入业务的前提下统一做大 Key 护栏、OTel 观测和分级容灾；PubSub 多路复用如何用 1 条连接替代 N 条长连接；以及 5 个现有服务（Agent、模型网关、设备网关、知识库、TeamFlow）如何零破坏分阶段迁入。类结构与职责见代码图，运行时协作见动态图。

先认识几个词

词意思Atlas 里的例子
客户端中间件嵌入每个服务进程的统一数据访问底座（参考 Go go-redis Hook 链、Java Lettuce / Redisson），区别于独立部署的网络 Proxy（Twemproxy / Predixy）。infra-platform/libs/redis（包名 atlas_redis），与 atlas_tenancy、atlas_jobs 同级。
舱壁隔离把短命令、阻塞读（XREAD BLOCK）、长订阅（SUBSCRIBE）拆进互不干扰的连接资源，一类慢或满不会拖垮另一类。短命令池设 socket_timeout=2s；阻塞流池配独立上限；PubSub 只占 1 条专用连接。
拦截器链命令执行前后的洋葱模型（Guard → Telemetry → Resilience），横切关注点插拔组合，业务代码只写逻辑。拦截 KEYS/超大 value、自动打 OTel Span 与慢日志、连续超时触发软状态熔断。
PubSub 多路复用进程内只维护 1 条带自动重连的订阅连接，按 channel 路由分发到协程队列；重连后投递哨兵通知业务回库补查。500 个等审批的 CLI 协程共用 1 条连接，不再各自占 1 条短命令池连接。
ScriptRegistry集中管理 Lua 脚本，自动走 EVALSHA（遇到 NOSCRIPT 重灌 EVAL），消除每次传输完整 Lua 源码的开销。序号分配、INCR+EXPIRE 原子限流、设备在线续期、分布式锁续租。
分级容灾按原语一致性要求明确区分 Fail-Closed（出错必拒）与 Fail-Open（出错降级放行或读旧缓存）。锁与序号必须 Fail-Closed；限流、缓存、失效通知可 Fail-Open + 熔断快返。
Singleflight缓存过期瞬间只放行 1 个协程回源查库，同键并发请求共享同一个 Future；回源失败时在宽限期内返回旧值。模型网关 TenantGate 每 5 秒过期不再产生 DB 惊群，DB 闪断也不再 500。

现状痛点与架构选型

业界 Redis 中间件分「独立代理层 Proxy」和「进程内客户端中间件」两条路线。Atlas 当前单集群下瓶颈不在数万客户端连接或分片路由透明化，而在 5 个 Python 服务各自裸调 from_url 带来的治理碎片化与线上隐患：

服务当前用法暴露出的问题
atlas_agent自建 redisx.py 双池、relay.py 事件流、approval/channel.py 审批订阅、redislock短命令池被迫 socket_timeout=None；CLI 审批 pubsub.subscribe() 长占短命令池；tail_thread 末尾重连仍扫全流；EVAL 未走 EVALSHA。
atlas_modelgateway裸 from_url + QuotaGuard 限流与预算 + TenantGate 查 PGincr 与 expire 分两次调用非原子泄漏；TenantGate 5 秒过期击穿且 DB 闪断直接 500；多副本缺少租户停用即时广播。
atlas_devicegw裸 from_url + store.py 手写 eval Lua无连接池上限、无超时治理、每次 eval 传完整 Lua 源码、无 OTel/慢日志。
atlas_teamflow裸 from_url + process/bus.py 自写 PubSub 与 Lua 锁与 atlas_redislock 重复造轮子；缺少连接池治理与指标监控。
atlas_knowledge裸 from_url + RedisLock + Celery broker无统一超时与观测；键前缀未标准化，与其它服务共享 Redis 实例时难排查大 Key。

原理 1　三类连接舱壁隔离，超时各归其位

redis-py 8 默认 socket_timeout=5s 会误杀 15 秒的 XREAD BLOCK，但为了兼容阻塞读把所有连接都改成 socket_timeout=None，又会让短命令在半开 TCP 僵死时挂满 30 秒才被健康检查发现。解法是按工作负载把连接拆成三路，各自配置独立的池上限与超时：

  1. 1短命令池不再迁就阻塞读，恢复严格的 socket_timeout=2s 与 connect_timeout=3s，配合 BlockingConnectionPool 在瞬间突发时短暂排队而不是立刻报错。
  2. 2阻塞流池专供 SSE XREAD BLOCK，连接上限由宿主的 StreamGate 协同封顶，即使挂满 200 条长 SSE 也不影响任何一次锁、序号或缓存读写。
  3. 3PubSub 彻底移出短命令池：无论进程内有多少协程在等审批或听失效广播，对外永远只消耗 1 条 TCP 连接。

原理 2　可插拔拦截器链与分级容灾

借鉴 go-redis Hook 链模式，RedisClient 将每次单命令、Pipeline 与 Lua 脚本调用封装为 CommandContext，依次穿过可插拔中间件栈，再交给底层 redis-py 执行：

  1. 1键空间规范（KeySpace）：所有新 Key 经 KeySpace(service, domain) 生成，统一形状 atlas:{service}:{scope}:{domain}:{id}；多 Key 原子脚本显式使用 {hash_tag}（如 atlas:agent:{t:<thread_id>}:seq 与 :events），提前兼容 Redis Cluster 同槽约束。
  2. 2可观测脱敏：TelemetryMiddleware 只记录脱敏后的键模式（如 atlas:agent:thread:*:events），不记真实 value 与 UUID，防止 OTel / Prometheus 指标基数爆炸与凭据泄露。
  3. 3写命令绝不盲目重试：ResilienceMiddleware 仅对幂等读命令（GET/MGET/EXISTS）在瞬时断连时重试 1 次；INCR/XADD 等写命令失败直接上报，避免重复扣费或重复事件。

原理 3　单连接多路复用 PubSubHub 与断线自愈

审批通知、权限失效、租户停用广播有一个共同特点：信号只是「去回库看一眼」的提示，真相永远在数据库里。PubSubHub 把进程内所有订阅收口到 1 条后台连接，彻底消除连接数随等待协程线性增长的问题：

关键设计点：Redis PubSub 断线期间不留离线消息，因此 PubSubHub 在每次重连重订阅成功后，向所有在听队列投递一个 Resubscribed 哨兵对象——业务监听方（如 DecisionChannel、TenantGate）收到哨兵即立刻回库查一次最新状态，关闭断线期间漏信号窗口。

原理 4　标准高阶原语与各服务痛点对应

原语解决的核心机制直接替换 / 修复的现状问题
ScriptRegistry集中登记 Lua 脚本，首次编译缓存 SHA1，调用走 EVALSHA，遇 NOSCRIPT 自动回退 EVAL。收编 relay.py、devicegw/store.py、teamflow/bus.py、redislock 全部散落 Lua。
StreamChannel支持 EVALSHA 序号+写入；tail(after_seq) 先 XREVRANGE COUNT 1 快判流尾（命中直接 XREAD，O(1) 跳过 1 万条扫描），分页回放并跳过单条坏 JSON。修复 atlas_agent/stream/relay.py 末尾重连扫全流与单条坏数据掐断 SSE 的问题。
AtomicQuota单条 Lua 原子执行 INCR + if 1 then EXPIRE 与浮点/整数额度累加，默认 fail_open=True。修复 atlas_modelgateway/gateway/admission.py 中 incr/expire 非原子永久 key 泄漏。
CoalescedCache内存 L1 + Singleflight 单飞锁防击穿 + stale_ttl_s 异常降级读旧值 + 可选接 PubSubHub 收跨副本失效广播。修复 modelgateway 数据面 TenantGate 每 5 秒缓存击穿、DB 闪断 500 及停用 5 秒延迟。
PubSubHub单连接多路复用 + 自动重连重订阅 + Resubscribed 哨兵。替换 agent/approval/channel.py（释放短命令池）、agent/auth/service.py、teamflow/process/bus.py。
DistributedLock复用现有 atlas_redislock（Lua 原子续租/释放 + 单调时钟 + Python 3.13 uncancel()），由 RedisRuntime 注入 commands 客户端与脚本表。保持 atlas_redislock 为独立叶子包，零破坏复用并删掉 teamflow 重复锁实现。

架构边界与依赖方向

边界约束约定与 import-linter 守卫
纯基础设施叶子包atlas_redis 只依赖 redis、opentelemetry-api（可选）与 atlas_redislock，不依赖任何业务服务包，也不依赖 atlas_tenancy（保持与 atlas_appconfig / atlas_jobs 一致的独立性；租户标识由宿主在构键时经 KeySpace.tenant(uid) 显式传入或注册 getter 回调）。
单向依赖与防绕过所有业务服务只经 atlas_redis 构造和使用 Redis；Phase 3 迁完后在 pyproject.toml 新增 import-linter 规则：禁止业务服务直接调用 redis.asyncio.from_url（除 Celery 配置 URL 外）。
测试友好内置 IsolatedPrefix（每个用例随机前缀 + 结束自动清理）与内存替身，单测可脱离 Redis 或安全共用同一测试实例不互相污染。

渐进式三阶段迁移路线

  1. 1Phase 1（建库 + 止血高危问题）：新建 infra-platform/libs/redis，落地 RedisRuntime、拦截器链、ScriptRegistry、PubSubHub、CoalescedCache、AtomicQuota、StreamChannel；优先接入 atlas_agent（释放 CLI 审批短命令池 + 流尾快跳）与 atlas_modelgateway（修复 TenantGate 击穿/DB 降级 + QuotaGuard 原子化）。
  2. 2Phase 2（全服务收编）：将 atlas_devicegw、atlas_knowledge、atlas_teamflow 迁入 atlas_redis，删除 teamflow/process/bus.py 重复锁与手写 PubSub，删除 atlas_agent/redisx.py 重复建池逻辑。
  3. 3Phase 3（护栏固化）：接入 import-linter 禁止业务服务绕过 atlas_redis 建连；统一开启 OTel Redis 延迟、连接池水位与大 Key 告警。
