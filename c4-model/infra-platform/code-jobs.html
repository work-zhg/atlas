    原理

    一句话：应用只写 execute，调度、线程、停机都交给库。任务分两种作用域：集群任务在代码里注册「能做什么」，在库里存「什么时候、用什么参数做」，每个进程的调度协程每秒去库里抢到期的定义，抢到的进程执行、续租、跑完结算；实例任务连周期一起写在代码里，每个进程各跑一份。下面图 1～3 讲集群任务的两层结构、一次触发的全过程、进程和线程怎么规划，图 4 讲两种作用域的区别。

    管理页面的原型见 ui-jobs.html：列表、详情、新建编辑、立即触发，以及只读用户看到的样子。

    图 1　两层：代码里的任务类型，库里的任务定义

    1. 1任务类型写在代码里，随发版变：类型名全局唯一、带应用前缀；Params 是参数的 pydantic 模型；execute 写成 async def 或 def。只有注册过的类型才能被执行，库里不存可以任意导入的函数路径。
    2. 2任务定义存在库里，运行时增删改，不用发版。同一个类型可以有多条定义：图里两条清理定义，周期和参数各不相同。参数存成 JSON，存的时候按类型的 schema 校验，填错当场报错，不会等到半夜触发才失败。
    3. 3到点时，抢到这一行的进程按类型名找到任务类，把 JSON 参数解析成 Params，调用 execute。执行前再校验一次：发版改了 schema、库里的旧参数已经不合法时，这一轮记失败，不带着坏参数跑。
    @jobs.register
class CleanupRuns:
    type = "agent.cleanup_runs"

    class Params(BaseModel):
        keep_days: int = 7

    async def execute(self, ctx: JobContext, params: Params) -> None:
        ...   # 删掉 keep_days 天前的记录；进程死了这一轮会被重跑，写法要幂等

    图 2　一次触发：抢行、执行、续租、结算；进程死了别人重跑

    1. 103:00:00 这条定义到期。各进程的调度协程每秒查一次，A 先抢到：同一个事务里用 SKIP LOCKED 锁住这一行，写上 owner 和租约，记一条执行记录（running）。别的进程同时查到也抢不到。
    2. 2A 执行期间，每 10 秒续一次租约。03:00:25 A 崩溃，不再续，租约在 03:00:50 过期。这期间 next_fire_at 一直是今天 03:00，没有往后推。
    3. 3B 在 03:00:51 那一轮查到这一行「已到期、没人拿着」，抢到，把 A 那条执行记录记成 lost，用同样的参数重跑（ctx.retried = true）。所以任务必须幂等。如果在抢到时就把下一次时间推到明天，A 一死，今天这一轮就要等到明天才会再跑。
    4. 4B 跑完结算：记成功，从今天 03:00 往后找第一个晚于现在的 cron 时刻（明天 03:00）写回，清掉租约。要是这一轮跑了两天，中间错过的那次不补跑，合并成这一次。

    图 3　进程与线程：默认嵌在 Web 进程里，重的拆出去

    1. 1集群调度协程、实例任务的循环和 async 任务都跑在宿主的事件循环上：集群调度只是每秒一条走索引的查询，实例任务的循环只是睡眠和计时，都很轻。async 任务里不能有阻塞调用，否则同进程的请求和 SSE 一起卡住，用 ruff 的 ASYNC 规则检查。
    2. 2同步任务进库自己的线程池，大小等于 max_concurrent；不用 AnyIO 的默认线程池，那 40 个线程是给宿主同步接口用的，任务一占，请求就排队。每个进程同时跑的集群任务（async 加同步）不超过 max_concurrent，默认 4，相当于 Quartz 的 threadCount；实例任务数量固定、各自不重叠，不占这些槽。数据库连接池要给任务预留这么多个连接，再加抢行、续租用的 1 到 2 个。
    3. 3重的任务拆出去：同一个镜像另起一组 Pod 只跑任务，并发调大；Web Pod 关掉，或者只跑轻量类型。两组都连同一张表，靠抢行互斥，不需要额外的协调。

    图 4　两种作用域：集群任务全集群一份，实例任务每个进程一份

    1. 1集群任务「每天清理旧 run」只有一条定义。三个实例的集群调度协程都去抢，A 抢到就 A 跑，B、C 这一轮什么都不做。定义存在 app_job 里，可以在管理接口里改 cron、改参数、暂停。适合运维类任务：清理、回收、对账、告警。
    2. 2实例任务「兜底 run」「续租 run」写在代码里，三个实例各跑一份、互不相干：A 兜底抢到的 run 在 A 上跑，B 抢到的在 B 上跑。它们不进库、不抢行、不写执行记录，只出指标；上一轮没跑完，下一轮跳过。它们关系到宿主能不能正常运行，管理接口里只能看，不能暂停、不能改。

    两种任务的业务代码写法完全一样，都是实现 Job 的 execute，区别只在注册时声明的作用域：

    @jobs.register(scope="instance", every=10, jitter=3)
class RecoverRuns:
    type = "agent.recover_runs"

    async def execute(self, ctx: JobContext, params) -> None:
        if worker.draining or not worker.free_slots():
            return            # 停机中或者没空槽：这一轮什么都不做
        ...                   # 翻页拉候选、逐个抢锁

    停机顺序由宿主决定：宿主先做完自己的收尾（比如 Run 执行器先把在跑的 run 交接完，期间「续租 run」这个实例任务还要一直跑），再调 stop()。库按「停止抢新的集群任务 → 等在跑的结束 → 停实例任务」的顺序停。像兜底这种停机时不该继续的实例任务，在 execute 开头自己判断「停机中」就返回。

    三种部署形态下各有几个集群调度协程

    宿主怎么部署调度协程说明
    每个 Pod 1 个进程，3 个副本（Atlas 现在）3 个每秒 3 条查询；同一条定义只有一个进程抢得到
    gunicorn 4 个 worker，2 个 Pod（aiassistant 那种）8 个每秒 8 条查询，仍然很轻；任务多是同步写法，全部进库的线程池
    进程有几十个几十个把查询间隔调大；只用 PostgreSQL 的话可以改用 LISTEN/NOTIFY 通知，不用每秒去查
