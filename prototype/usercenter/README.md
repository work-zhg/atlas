# 用户中心 — 用户与组织管理（可点击原型）

> 独立的用户中心系统：自建账号，统一维护用户与组织架构；AI TeamFlow、Atlas 等内部系统在服务端用 App Key / Secret 调用开放接口获取用户、组织与权限，按部门控制可访问范围。统一登录（SSO）本期不做，以后用 Keycloak。

纯静态单页应用，无外部依赖。双击 `index.html` 即可打开。数据为内存态 Mock，刷新后重置。

## 权限模型（RBAC）

```
操作（应用登记的操作码，如 user:create、process:start）
  └─ 角色（属于一个应用，包含该应用的若干操作）
       └─ 岗位（默认角色）
授权：岗位 / 角色 → 用户 / 组织（部门，可选含下级部门）
用户有效授权 = 授予本人 + 授予所在部门 + 授予上级部门且含下级
用户有效操作 = 授予的角色 ∪ 所授岗位的默认角色 → 各角色操作的并集
```

- **前端控制**：登录后拿到本应用的操作码列表，`can(op)` 为假时菜单与按钮不显示；原型中用户中心自身也按此控制（侧边栏、页面入口、每个按钮）。
- **应用获取**：应用后端调用开放接口 `GET /open/v1/users/{id}/authz` 取得 `can_access`、`permissions`、`menus`，只含该应用自己的内容；建议缓存不超过 5 分钟。
- **后端仍需校验**：前端控制只负责「看不到」，接口按同一操作码鉴权。
- **不在本期**：数据范围权限（如「只能管理本部门用户」），后续可在角色上增加数据范围。

## 菜单权限

```
应用 → 菜单树（目录 / 菜单，菜单可设为「公共」）
角色 → 绑定本应用的菜单
用户在应用中可见的菜单 = 其角色绑定的菜单 ∪ 公共菜单（目录只在有可见子菜单时显示）
```

- 菜单决定「看得到哪些页面」（导航 + 路由守卫），操作码决定「页面里能做什么」（按钮 + 接口）。
- 应用从开放接口返回的 `menus` 取得可见菜单树渲染导航。
- 用户中心自己的侧边栏也按这套规则生成：「权限管理」是公共菜单（人人有数据授权），其余菜单按角色绑定。

## 数据权限

```
数据编码（如 Agent，属于某个应用，在应用详情中登记）
  └─ 数据（数据 Id，如 agt_7f3a21）
       └─ 授权：只读 < 读写 < Owner → 用户 / 组织（可含下级部门）
用户对一条数据的权限 = 命中授权（本人 / 所在部门 / 上级部门含下级）中的最高级别
```

- 应用创建数据时调用 `POST /api/v1/data-permissions` 写入创建人的 Owner；打开数据前用 `check` 校验，列表用 `accessible` 过滤，删除数据时 `DELETE` 清理。
- **只有 Owner 能修改这条数据的授权**，管理员（`data:view`）只能查看；至少保留一名可用的 Owner（移除、降级、改范围时校验，不满足则回滚）。
- 「只读 / 读写」在数据上具体能做什么由应用解释；用户中心只负责记录和计算级别。

用户中心的操作：

| 模块 | 操作码 |
| --- | --- |
| 组织架构 | `org:view` `org:manage` |
| 用户 | `user:view` `user:create` `user:edit` `user:disable` `user:reset_pwd` |
| 权限 | `role:view` `role:manage` `position:view` `position:manage` `grant:view` `grant:manage` |
| 数据权限 | `data:view` |
| 系统 | `app:manage` `security:manage` `audit:view` |

保护规则：不能停用自己；至少保留一名可用的超级管理员（撤销授权、改授权范围、改岗位默认角色时校验，不满足则回滚）；删除部门时一并撤销其授权；内置角色的操作不可修改；角色编码、岗位编码创建后不可修改。
