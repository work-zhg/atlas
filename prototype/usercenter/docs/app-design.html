User Center · Detailed Design

应用接入模块

用户中心是用户、组织与权限的主数据来源。内部系统（AI TeamFlow、Atlas 等）在服务端用 App Key / Secret 调用用户中心的开放接口，获取用户、部门以及本应用的授权（能否访问、角色、操作码、菜单、数据权限）。应用接入模块管理每个应用的接入配置（应用凭据、可访问范围），以及属于应用的权限元数据：操作目录、菜单、角色、数据编码。

统一登录（SSO / OIDC）本期不做：应用自行处理登录，按账号与用户中心对齐身份；以后需要时引入 Keycloak 等成熟方案，用户中心继续作为数据源（第 15 节）。

服务端开放接口App Secret 只显示一次可访问范围按部门角色 / 菜单 / 操作 / 数据编码属于应用用户中心是内置应用只停用不删除SSO 后续用 Keycloak

01定位与范围

本模块负责

  • 应用登记：名称、图标、说明；启用 / 停用
  • 应用凭据：App Key、App Secret（生成、轮换）
  • 可访问范围（全员 / 指定部门含下级）
  • 应用的操作目录、菜单树、角色（角色绑定操作与菜单）、数据编码
  • 开放接口的接入规范：鉴权、用户与部门查询、授权快照、实时校验、变更通知

不在本模块

  • 把角色 / 岗位授予用户或部门、数据授权 → 权限管理
  • 部门树 → 组织管理；账号 → 用户管理
  • 统一登录（SSO / OIDC）：本期不做；后续用 Keycloak（第 15 节）
  • 应用自身的登录与业务鉴权（应用按开放接口返回的结果自行控制）
用户中心管理台自身的登录用户中心自己的管理台仍使用账号密码登录（密码策略、锁定、首次登录改密），属于「认证与安全策略」模块，只服务于用户中心自身，不对外提供单点登录。

02术语

术语含义
应用接入用户中心的内部系统，用 App Key / Secret 调用开放接口。
内置应用用户中心自身。它的操作和菜单随版本发布（只读），角色可在界面维护；没有应用凭据与数据编码。
App Key / App Secret应用调用开放接口的凭据。Secret 只在生成时显示一次，服务端只存哈希；只能保存在应用后端。
开放接口用户中心对接入应用提供的服务端接口（/open/v1），每次调用都限定在调用方应用的范围内。
授权快照某用户在某应用中的 can_access、角色、操作码、可见菜单，应用登录后取一次并缓存。
可访问范围哪些人可以使用该应用：全员，或指定部门（含下级部门）。本期由应用根据 can_access 执行。
操作 / 操作码应用内可被授权的动作，格式 资源:动作（如 process:start）。前端用它控制按钮，后端用它鉴权。
菜单应用的导航结构，分目录（分组）与菜单（对应页面路由）；菜单可设为公共（人人可见）。
角色属于某个应用的一组操作 + 菜单。授予用户 / 部门 / 岗位后生效（在权限管理中进行）。
数据编码应用登记的数据类型标识（如 Atlas 的 Agent）。数据权限按「数据编码 + 数据 Id」记录。

05领域模型

应用
  • 名称、图标、说明、状态
  • App Key、Secret 哈希
  • Webhook 地址（P1）
  • 可访问范围：全员 或 部门（0..n）
1 : n
操作
  • 模块、操作码、名称
菜单
  • 目录 / 菜单树，路由，公共

  • n:n 操作、n:n 菜单（只能是本应用的）
数据编码
  • 数据类型标识
角色、数据编码被权限管理引用：角色授予用户 / 部门 / 岗位；数据权限记录「数据编码 + 数据 Id + 级别 + 授权对象」。
对象唯一性可修改
应用名称全局唯一；App Key 全局唯一名称、图标、说明；App Key 不可改
操作操作码在应用内唯一名称、模块；操作码不可改
菜单编码在应用内唯一；路由在应用内唯一名称、图标、上级、路由、公共、排序；编码与类型不可改
角色角色编码全局唯一；名称在应用内唯一名称、说明、操作、菜单（内置角色锁定）；编码与所属应用不可改
数据编码编码全局唯一名称、说明；编码不可改
编码一律不可改操作码、菜单编码、角色编码、数据编码都被应用代码引用，修改等于在应用中改代码；需要更名时新建 + 迁移授权 + 删除旧的。

06应用生命周期

状态行为
启用可获取接口令牌、调用开放接口
停用不能再获取接口令牌；已签发的接口令牌立即失效（每次调用校验应用状态）；推送 app.disabled（P1）。角色、菜单、授权、数据权限全部保留，启用即恢复。
  • 本期不删除应用：角色授权、数据权限、审计都引用它；与用户「只停用不删除」一致。
  • 内置应用（用户中心）不能停用。
  • 应用停用后用户能否继续使用该应用，取决于应用自身：应用拿不到用户与权限数据，应拒绝登录（接入规范要求）。

07应用凭据

项规则
App Key系统生成：ap_ + 16 位小写十六进制；全局唯一；不可修改
App SecretCSPRNG 生成 32 字节，Base64URL 编码（43 字符）；只在接入成功 / 轮换时显示一次；服务端存 SHA-256 哈希（Secret 本身高熵，无需慢哈希）与末 4 位用于界面识别
使用只在应用后端使用，换取接口令牌；禁止下发到浏览器或客户端
接口令牌不透明串，有效期 2 小时，服务端存储（Redis）；每次调用校验应用状态，应用停用或 Secret 轮换后立即失效
轮换P0：生成新 Secret，旧 Secret 与其签发的接口令牌立即失效，确认弹窗提示「应用在更新配置前无法调用开放接口」。P1：平滑轮换，旧 Secret 保留 24 小时
校验常量时间比较；按 App Key 与来源 IP 限流，连续失败告警；可选 IP 白名单 P1

08可访问范围

  • 两种：全员；指定部门（选中部门含其全部下级部门，可多选）。新接入的应用默认指定部门且为空，即无人可访问，避免误开放；界面提示「未设置（无人可访问）」。
  • 判定：用户未停用，且（全员 或 用户部门链与所选部门有交集）。
  • 执行点（本期）：开放接口在授权快照中返回 can_access；接入规范要求应用在用户登录时检查，为 false 时拒绝登录，提示「你没有访问该应用的权限，请联系管理员」。不在范围内的用户，授权快照中的角色、操作码、菜单均为空。接入 Keycloak 后改为在登录时由 Keycloak 执行。
  • 修改范围后，界面显示「当前 N 人可访问」；被移出范围的人在应用下次获取授权快照（或收到变更通知，P1）时失去访问。
  • 部门被删除时，从范围中移除（组织模块回调）；若某应用因此变为空范围，删除确认中提示。
  • 可访问范围决定能不能登录；登录后能看到哪些菜单、能做哪些操作，由角色授予决定。

09操作目录

  • 字段：模块（分组名）、名称、操作码。操作码格式 ^[a-z][a-z0-9_]*:[a-z][a-z0-9_]*$，应用内唯一。
  • 删除：预览「被哪些角色使用」，确认后从这些角色中移除；应用前端对应的按钮将对所有人隐藏。
  • 界面同时给出前端控制示例：can(op) = permissions.includes(op)，并提示后端接口按同一操作码鉴权。
  • 内置应用（用户中心）的操作随版本发布，界面只读。
  • P1：应用通过元数据接口上报操作（按操作码 upsert，界面标记「由应用上报」）。

10菜单

字段规则
类型目录（只用来分组，无路由）/ 菜单（对应一个页面）；创建后不可改
编码^[a-z][a-z0-9_]{1,31}$，应用内唯一，不可改
上级只能是本应用的目录；最多 3 级
路由菜单必填，以 / 开头，应用内唯一
公共仅菜单可设；所有能登录该应用的人都可见，无需角色绑定
排序同级内上移 / 下移

可见菜单的计算

visibleMenus(user, app):
  bound = ∪ 用户在该应用的全部角色绑定的菜单        // 角色来源：直接授予、部门继承、岗位默认角色（权限管理计算）
  leaves = { m | m.type = menu 且 (m.public 或 m ∈ bound) }
  return leaves ∪ leaves 的全部上级目录            // 目录只在有可见子菜单时出现
  • 删除：目录下有子菜单时拒绝；删除菜单同时解除所有角色的绑定（确认中列出角色）。
  • 菜单预览：选择一个用户，按应用样式渲染其可见导航，并显示开放接口返回的 menus JSON；悬停显示每个菜单的来源角色。
  • 内置应用的菜单只读，用户中心自己的侧边栏就是按这棵树和登录人的角色生成的；其中「权限管理」为公共菜单（人人都有「数据授权」）。
菜单与操作码的分工菜单决定「看得到哪些页面」（导航 + 路由守卫）；操作码决定「页面里能做什么」（按钮 + 接口）。两者在角色上分别勾选。

11角色

项规则
归属在应用详情「角色」分页中维护，只属于一个应用，不可更改
编码^[A-Z][A-Z0-9_]{1,31}$，全局唯一（便于在授权、日志中无歧义识别），不可改
名称应用内唯一
操作权限按模块勾选本应用的操作，支持整组全选
菜单权限树形勾选本应用的菜单；勾目录即勾其下全部菜单；公共菜单默认勾选且不可改
内置角色如「超级管理员」：不可删除，操作与菜单锁定
复制复制操作与菜单，不复制授权
删除预览：将撤销的授权数、作为默认角色的岗位、当前拥有人数；确认后由权限管理撤销授权并从岗位默认角色中移除
  • 角色详情还有「授权」「拥有者」两个分页，数据来自权限管理：授予了哪些用户 / 部门、哪些岗位带有该角色、实际拥有的人及来源。
  • 修改角色的操作或菜单后，所有拥有者的权限随之变化：用户中心内实时生效；应用在下次获取授权快照（或收到变更通知，P1）时生效。
  • 超级管理员保护：任何导致「没有可用的超级管理员」的变更都被拒绝（由权限管理校验）。

12数据编码

  • 字段：编码 ^[A-Z][A-Za-z0-9]{1,31}$（全局唯一，不可改）、名称、说明。
  • 应用只能读写自己登记的数据编码的数据权限（接口令牌所属应用必须与数据编码的所属应用一致）。
  • 删除：还有数据使用该编码时拒绝，提示应用先删除数据并调用清理接口。
  • 权限级别「只读 / 读写 / Owner」在数据上的具体含义由应用解释；用户中心只记录与计算级别（详见权限管理 · 数据授权）。
  • 数据编码分页内附应用调用的接口说明：写入 Owner、校验权限、列出可访问数据、删除清理。

13接入方式（本期）

接入步骤

  1. 管理员在「应用接入」中接入应用，保存 App Key / Secret（配置到应用后端）。
  2. 设置可访问范围。
  3. 登记操作目录、菜单、数据编码；建角色并勾选操作与菜单。
  4. 在权限管理中把角色授予用户 / 部门 / 岗位。
  5. 应用按下面的时序对接开放接口。

运行时序

#时机应用做什么
1应用启动 / 令牌到期前用 App Key / Secret 换取接口令牌并缓存
2用户在应用中登录（应用自己的登录）按账号查询用户：不存在或 status = disabled → 拒绝登录
3登录成功后取授权快照：can_access = false → 拒绝登录；否则把角色、操作码、菜单存入应用会话
4渲染页面按 menus 渲染导航、做路由守卫；按 permissions 控制按钮
5后端处理请求按会话中的 permissions 鉴权；敏感操作调用实时校验接口
6会话期间授权快照缓存不超过 5 分钟，到期重新获取；P1 起收到变更通知立即刷新或踢出
身份对齐本期不提供登录服务，应用的登录账号须与用户中心的账号一致（或在应用侧维护映射到用户 uuid）。应用内部应保存用户中心的 uuid 作为关联键，不要用账号做外键。如何让应用验证用户密码见「待确认」。

14开放接口

前缀 https://uc.xinghai.com/open/v1；除获取令牌外都需 Authorization: Bearer <接口令牌>；所有结果都限定在调用方应用的范围内。路径与报文中的 id 为用户 / 部门的 uuid。

接口说明
POST /auth/token{app_key, app_secret} → {access_token, expires_in: 7200}
GET /users/by-account/{account} · GET /users/{id}用户信息：uuid、账号、姓名、邮箱、状态、部门（uuid、路径）、直属上级
GET /users?q=&dept_id=&include_sub=选人用的用户列表，只返回本应用可访问范围内的未停用用户；分页
GET /depts/tree部门树（uuid、名称、上级、负责人）
GET /users/{id}/authz授权快照：can_access、角色编码、操作码、可见菜单树（只含本应用）
POST /authz/check{user_id, permission} → {allowed, roles[]}，实时计算
/data-permissions（4 个接口）写入 Owner、校验、列出可访问数据、删除清理（见权限管理 · 数据授权）
PUT /metadata P1应用上报操作与菜单（按编码 upsert）

变更通知（Webhook） P1

  • 应用在接入配置中登记 Webhook 地址；用户中心用该应用的签名密钥做 HMAC-SHA256 签名（请求头 X-UC-Signature、X-UC-Timestamp），应用验签并拒绝 5 分钟外的请求。
  • 事件：user.disabled、user.enabled、user.updated（含调部门）、authz.changed（该应用的角色定义或授权变化，附受影响用户 uuid 列表，过多时只给「全量刷新」标记）、app.disabled。
  • 至少一次投递：失败按 1 分钟、5 分钟、30 分钟、2 小时重试；应用按事件 id 去重。
  • 签名密钥需要可还原，加密存储（KMS / 主密钥），与 App Secret 分开。

15后续统一登录（Keycloak）

需要统一登录时，不自建 OIDC，引入 Keycloak 作为身份提供方。用户中心继续作为用户、组织、权限的唯一数据源，Keycloak 只负责登录协议与会话。

方案做法评价
A. 用户联邦（推荐）开发 Keycloak User Storage SPI：按账号 / 邮箱从用户中心查用户，密码交给用户中心校验；must_change_password 映射为 Keycloak 的「更新密码」必需动作用户数据只有一份；用户中心的密码策略、锁定、临时密码继续有效
B. 单向同步用户中心把用户推送到 Keycloak，密码由 Keycloak 管理实现简单，但密码相关功能要迁到 Keycloak，两边状态需对账
  • 每个接入应用对应一个 Keycloak Client；回调地址、PKCE 等协议配置在 Keycloak 中维护。用户中心的「应用」与 Keycloak Client 通过 App Key 关联。
  • 可访问范围：在 Keycloak 登录流程中加一个自定义认证步骤调用用户中心 can_access，或继续由应用检查。
  • 令牌中只放身份（sub = 用户 uuid、账号、姓名）；角色、操作码、菜单仍由应用调用开放接口获取，避免令牌过大、避免权限只在登录时刷新。
  • 用户中心管理台自身也改为通过 Keycloak 登录，原登录页下线。
本期为此预留用户 uuid 作为全系统稳定标识；账号全局唯一且不可改；密码用 argon2id 存储并提供内部校验能力；用户状态、可访问范围都可通过接口查询。接入 Keycloak 时无需迁移业务数据。

22非功能

安全

  • App Secret 只显示一次、只存哈希；响应 no-store
  • 开放接口只走 HTTPS；接口令牌 2 小时，服务端可随时作废
  • 每次调用限定在调用方应用：只能看到本应用的授权、可访问范围内的用户、本应用的数据编码
  • 按 App Key 与 IP 限流；可选 IP 白名单（P1）
  • Webhook 签名 + 时间戳防重放

性能与可用性

  • 应用配置、操作、菜单、角色定义常驻内存缓存，变更时按应用失效
  • 授权快照 p95 < 50ms；实时校验 p95 < 20ms
  • 开放接口可用性 99.9%；应用侧以快照缓存兜底短时故障

24测试要点

  • 接入应用：Secret 只返回一次；App Key 唯一；名称重复。
  • 轮换 Secret：旧 Secret 与其接口令牌立即失效；新 Secret 可换令牌。
  • 停用应用：换令牌、已有令牌调用全部拒绝；启用后恢复；内置应用不可停用。
  • 可访问范围：全员；指定部门含下级；空范围；用户调部门后进 / 出范围；部门删除后范围更新；范围外用户的快照角色 / 操作码 / 菜单为空。
  • 开放接口隔离：A 应用看不到 B 应用的角色 / 菜单 / 数据编码；用户列表只含本应用范围内的人。
  • 操作：格式、重复、删除后从角色移除、内置应用只读。
  • 菜单：类型不可改、编码 / 路由重复、3 级上限、删除有子菜单的目录、公共菜单可见性、目录随子菜单显示、预览结果与开放接口返回一致。
  • 角色：编码全局唯一、名称应用内唯一、跨应用勾选被拒、复制不带授权、删除撤销授权与岗位默认角色、内置角色锁定。
  • 数据编码：格式、全局唯一、有数据时不可删、应用只能操作自己的编码。
  • 实时校验与快照一致；授权变更后快照与实时校验立即反映。
  • Webhook（P1）：签名、重放、重试、去重。
  • 权限：各分页与按钮在缺少操作码时隐藏、接口 403。
