User Center · Detailed Design

组织管理模块

组织管理维护公司的部门树、各部门的负责人和部门成员。它是其他模块的基础：用户必须属于一个部门；直属上级按部门负责人实时计算；权限可以授予部门并向下继承；应用的可访问范围、数据权限都可以按部门设置。

唯一根部门每个部门一名负责人负责人须在本部门或下级部门直属上级实时计算有子部门或成员不可删除移动部门连同子树

01定位与范围

本模块负责

  • 部门树：新建、改名、移动（连同子部门与成员）、删除
  • 部门负责人：设置、清空、约束校验、自动清空
  • 直属上级计算 managerOf（供用户详情、开放接口、接入应用使用）
  • 部门成员视图：直属成员 / 含子部门成员；调入成员；在部门下新建用户
  • 向其他模块提供部门路径、子树、成员范围等查询

不在本模块

  • 用户档案与账号状态 → 用户管理（调入成员调用其服务改 dept_uuid）
  • 授予部门的岗位 / 角色 / 数据权限 → 权限管理（部门页只提供「授权」入口）
  • 应用可访问范围的配置 → 应用接入
  • 本期不做：HR 系统同步、批量导入部门、兼职多部门、副负责人

02术语

术语含义
根部门部门树的顶点，代表公司（如「星海科技」）。系统初始化时创建，唯一，不可删除、不可移动，可改名、设负责人。
部门路径从根到该部门的名称序列，展示为「星海科技 / 研发中心 / 交易中台」；对外（开放接口）通常省略根部门。
子树某部门及其全部下级部门。
直属成员dept_uuid 等于该部门的用户。
含子部门成员dept_uuid 在该部门子树内的用户。
负责人部门的唯一负责人 leader_uuid，必须是该部门子树内未停用的用户。一个人可以同时负责多个部门。
直属上级不存储。从用户所在部门向上，取第一个「不是本人、未停用」的负责人（第 08 节）。

05领域模型

属性规则
名称 name必填，1–50 字符，去首尾空白；不允许包含 /（部门路径的分隔符）；同一上级下不能重名，不同上级可以重名
上级 parent_uuid根部门为空，其他必填；不能是自己或自己的下级
负责人 leader_uuid选填；必须是本部门子树内未停用的用户（第 07 节）
排序 sort同级部门的显示顺序，新建时排在最后 P1
层级 depth根部门为 1，最多 10 级
路径 path由各级部门 uuid 组成的物化路径（第 15 节），系统维护，用于子树查询

06部门树规则

  • 唯一根部门：初始化时创建；不可删除、不可移动；可改名（公司更名）、可设负责人（通常是 CEO）。
  • 层级上限 10 级：新建与移动都校验，移动时校验「目标层级 + 被移动子树的高度」。
  • 同级不重名：新建、改名、移动时校验目标上级下是否已有同名部门。
  • 不能移动到自己的子树下：上级下拉中直接排除自己及全部下级。
  • 删除只删空部门：有子部门或直属成员时拒绝，提示先移走或删除。删除不级联删除用户或子部门。
  • 树结构变更（新建、移动、删除）低频，服务端串行执行，避免并发移动形成环（第 15 节）。

07部门负责人

约束

  • 每个部门最多一名负责人，可以不设。
  • 负责人必须是该部门子树内的用户（可以是直属成员，也可以在下级部门，例如李工属于「交易中台」，同时负责「研发中心」）。
  • 设置时必须是未停用的用户。
  • 一个人可以同时负责多个部门。
为什么要求负责人在子树内直属上级按负责人计算，负责人在子树内才能保证「上级部门的人管下级部门」的方向不乱；同时一个部门只有一名负责人，计算结果唯一。

设置入口

入口说明
编辑部门弹窗负责人下拉只列本部门子树内未停用的成员；可选「不设置」清空
成员列表「设为负责人」对列表中未停用、且不是当前负责人的成员显示；勾选「包含子部门」时下级部门的成员也可设
新建部门不设负责人：新部门还没有成员，调入成员后再设置

自动清空

以下变更导致负责人不再位于部门子树内时，系统清空该部门的负责人（审计操作人为 system，说明原因）：

触发示例
用户调整部门（编辑用户 / 调入成员）李工从「交易中台」调到「产品部」→ 「研发中心」「交易中台」的负责人都被清空
移动部门「技术中心」移出「研发中心」，若研发中心的负责人属于技术中心 → 研发中心负责人被清空

提交前先用 dry_run 计算将被清空的部门，界面确认后再执行（P1；P0 在执行后提示）。

负责人被停用

  • 不自动清空：停用可逆，启用后恢复原状。
  • 计算直属上级时跳过该负责人，继续向上找。
  • 部门详情在负责人旁显示「负责人已停用，请更换」，引导管理员处理。

08直属上级计算

managerOf(user):
  d = dept(user.dept_uuid)
  while d is not null:
    leader = d.leader
    if leader is not null and leader != user and leader.status != disabled:
      return leader
    d = parent(d)                // 本人是负责人 / 部门无负责人 / 负责人已停用 → 向上一级
  return null                    // 根部门负责人没有直属上级
用户所在部门直属上级说明
何超研发中心 / 交易中台李工本部门负责人
陈运研发中心 / 技术中心（本人负责）李工上级部门「研发中心」负责人
李工研发中心 / 交易中台（本人负责，同时负责研发中心）林远连续跳过本人
高峰研发中心 / 技术中心（负责人陈运已停用）李工跳过已停用负责人
林远星海科技（本人负责）—根部门负责人
  • 返回值附带来源：own_dept（所在部门负责人）或 ancestor（上级部门负责人），用户详情据此注明。
  • 部门树（含负责人 id）常驻内存缓存，计算为 O(层级)，不查库；负责人状态从用户缓存取。
  • 不落库，因此部门换负责人后所有相关人员的直属上级立即变化，用户表无任何写入。

09新建部门

  • 入口：选中部门 →「＋ 新建子部门」。上级固定为当前部门。
  • 只填名称；校验名称格式、同级不重名、层级上限。
  • 创建后自动展开上级并选中新部门。
  • 新部门没有成员、没有负责人，不继承任何授权以外的东西（上级部门「含下级」的授权自动覆盖新部门，见权限模块）。

10编辑与移动部门

字段规则影响
名称格式、同级不重名部门路径变化；开放接口实时返回新路径
负责人第 07 节约束相关人员直属上级立即变化
上级（移动）非根部门；不能是自己或下级；目标下不重名；层级不超限连同子部门与成员一起移动；见下

移动的影响

  • 子树内所有成员的部门路径变化。
  • 从旧上级「含下级」继承的授权失去，从新上级「含下级」继承的授权获得（权限模块实时计算，无需迁移数据）。
  • 应用可访问范围按部门链计算，可能变化（例如移出「研发中心」后不再能访问只开放给研发中心的 Atlas）。
  • 子树成员的直属上级可能变化（子树外的上级部门负责人不同了）。
  • 旧上级链中负责人属于被移动子树的部门，负责人被自动清空。
提示移动部门影响面大，确认弹窗列出：子树部门数、成员数、将被清空负责人的部门；并提示「授权与应用访问将按新位置重新计算；接入应用在刷新授权快照（或收到变更通知）后生效」。

11删除部门

  1. 前置校验：不是根部门；没有子部门；没有直属成员。不满足时提示「部门下还有 N 个子部门、M 名成员，请先移走或删除」。
  2. 影响预览（dry_run）：该部门出现在哪些应用的可访问范围中、有多少条授予该部门的授权与数据权限。
  3. 确认后在一个事务内：删除部门；通知应用接入、权限管理、数据权限清理对该部门的引用；写审计（含被清理引用的快照）。

物理删除。审计中保留部门名称与路径快照，历史记录仍能看到「当时是哪个部门」。

12部门成员

  • 默认显示含子部门成员（上级部门往往没有直属成员），可切换为只看直属成员。
  • 列：成员（姓名、账号、负责人徽标）、所在部门、岗位（权限模块计算结果）、状态；整行点击进入用户详情。
  • 调入成员：从其他部门选择未停用的用户，调入后其 dept_uuid 变为当前部门（调用用户管理服务，逐人写审计「调整部门」）；会触发负责人自动清空检查。
  • ＋ 新建用户：打开用户管理的新建表单，部门预填为当前部门。
  • 设为负责人：见第 07 节。
  • 成员超过 100 人时分页，支持按姓名 / 账号搜索 P1。

14数据模型

主键约定（全部表通用） id bigint 自增主键，只在库内使用（聚簇、分页游标），不对外暴露、不用于任何关联； uuid uuid 逻辑主键（UUIDv7，按时间有序、对索引友好，由应用生成），表间关联、外键、API、开放接口、审计对象都使用它。 关联字段统一命名为 xxx_uuid，外键引用对方表的 uuid；API 中的 id / xxx_id 取值即对应的 uuid。
-- 部门
CREATE TABLE uc_dept (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- 自增主键，仅库内使用
  uuid         uuid        NOT NULL,                              -- 逻辑主键（UUIDv7）
  parent_uuid  uuid        REFERENCES uc_dept(uuid),             -- 根部门为空
  name         varchar(50) NOT NULL,
  leader_uuid  uuid        REFERENCES uc_user(uuid),
  sort         int         NOT NULL DEFAULT 0,
  path         varchar(400) NOT NULL,     -- '/{root_uuid}/{rd_uuid}/{trade_uuid}/'，10 级 × 37 字符
  depth        smallint    NOT NULL,      -- 根 = 1
  created_at   timestamptz NOT NULL DEFAULT now(),
  created_by   uuid,
  updated_at   timestamptz NOT NULL DEFAULT now(),
  updated_by   uuid,
  version      int NOT NULL DEFAULT 1,
  CONSTRAINT uk_dept_uuid         UNIQUE (uuid),
  CONSTRAINT uk_dept_sibling_name UNIQUE (parent_uuid, name),
  CONSTRAINT ck_dept_name  CHECK (position('/' in name) = 0),
  CONSTRAINT ck_dept_depth CHECK (depth BETWEEN 1 AND 10)
);
CREATE UNIQUE INDEX uk_dept_single_root ON uc_dept ((parent_uuid IS NULL)) WHERE parent_uuid IS NULL;
CREATE INDEX ix_dept_parent ON uc_dept (parent_uuid, sort);
CREATE INDEX ix_dept_path   ON uc_dept (path varchar_pattern_ops);
CREATE INDEX ix_dept_leader ON uc_dept (leader_uuid);

uc_dept.leader_uuid → uc_user.uuid 与 uc_user.dept_uuid → uc_dept.uuid 互相引用：建表时先建两表，再用 ALTER TABLE ... ADD CONSTRAINT 补外键；初始化根部门与首个管理员时在同一事务内插入，leader_uuid 后更新。

「负责人在子树内」涉及用户表，无法用数据库约束表达，由服务层在设置负责人、用户调部门、移动部门时校验与修正。

15树的存储与查询

操作实现
子树查询WHERE path LIKE '/{root_uuid}/{rd_uuid}/%'（前缀索引）；含子部门成员：uc_user.dept_uuid IN (子树 uuid)
部门路径按 path 中的 uuid 依次取名称（内存缓存）
移动一条 UPDATE 改写子树的 path 前缀与 depth：path = :new || substr(path, length(:old)+1)，depth = depth + :delta
人数统计按 dept_uuid 分组得到直属人数，在内存树上自底向上累加得到含子部门人数
并发控制新建 / 移动 / 删除在事务内取 pg_advisory_xact_lock('uc_dept_tree') 串行化；改名、改负责人用乐观锁 version
缓存整棵树（uuid、parent_uuid、name、leader_uuid、sort、depth）常驻各实例内存；树版本号存 Redis，变更后 +1，各实例发现版本变化即重载

18页面设计

以原型为准（prototype/usercenter/index.html → 组织架构）。左右两栏：

左：部门树

  • 根部门 🏢，其余 📁；节点右侧显示含子部门人数
  • 有子部门的节点可展开 / 收起；选中时自动展开上级
  • 顶部部门搜索 P1

右上：部门信息

  • 部门路径、名称；按钮：授权 / ＋ 新建子部门 / 编辑 / 删除（根部门无删除）
  • 负责人（已停用时橙色提示；未设置时提示「成员的直属上级取上级部门负责人」）
  • 直属成员 / 含子部门人数；子部门标签（点击跳转）

右下：成员

  • 「包含子部门」开关、调入成员、＋ 新建用户
  • 表格：成员（负责人徽标）、所在部门、岗位、状态、设为负责人

弹窗

  • 新建子部门：名称；提示调入成员后再设负责人
  • 编辑部门：名称、上级（根部门无）、负责人（子树内未停用成员）
  • 删除：不满足条件时只给「知道了」；满足时列出将清理的引用
  • 调入成员：可搜索的多选列表，提示「主部门将变更为当前部门」

20异常与边界

场景处理
两人同时把 A 移到 B 下、把 B 移到 A 下树结构变更串行化，后执行者校验发现会形成环，返回 MOVE_INTO_SUBTREE
设置负责人时，该用户刚被调出子树服务端按最新数据校验，返回 LEADER_NOT_IN_DEPT
负责人被停用保留；直属上级计算跳过；部门页提示更换
负责人被启用重新作为直属上级生效，无需操作
部门没有负责人成员的直属上级取上级部门负责人
删除部门时它正被应用的可访问范围使用允许删除，从范围中移除；若某应用的范围因此为空，提示「该应用将无人可访问」
根部门只有一个人（初始化）初始化脚本创建根部门与第一个超级管理员，并将其设为根部门负责人
移动后层级超限DEPTH_EXCEEDED，提示被移动子树的层数

21非功能

容量与性能

  • 按 5000 个部门、5 万用户设计
  • 部门树接口 p95 < 200ms（内存缓存）
  • managerOf 单次 < 1ms（内存，O(层级)）
  • 移动 1000 个部门的子树 < 1s（一条 UPDATE）

一致性

  • 树结构变更串行化，杜绝环
  • 负责人约束在每个可能破坏它的写操作里校验 / 修正，并在同一事务内完成
  • 缓存以版本号失效，写后读不到旧树

22与原型的差异

原型已按本设计同步：负责人只能选子树内成员、新建部门不设负责人、根部门可改名与设负责人、调出负责人自动清空、停用负责人有提示。剩余差异：

项原型详细设计
自动清空负责人执行后提示P1 起执行前 dry_run 确认
同级排序无P1 支持
部门搜索、成员分页无P1 支持
名称格式只校验非空、同级不重名增加长度上限、禁止 /、层级上限 10
删除影响中「应用范围为空」无额外提示

23测试要点

  • 名称：空、50 / 51 字符、含 /、同级重名、不同上级同名。
  • 根部门：不能删除、不能移动；可改名、可设负责人；唯一性（不能再建第二个根）。
  • 移动：到自己、到下级、到同级、到根；层级 10 / 11；并发互相移动。
  • 删除：有子部门、有直属成员、有含下级成员但无直属成员（子部门存在则拒绝）、空部门；清理应用范围 / 授权 / 数据权限。
  • 负责人：直属成员、下级部门成员、子树外用户（拒绝）、已停用用户（拒绝）、同一人负责多个部门。
  • 自动清空：用户调出子树、调到子树内另一部门（不清空）、移动部门导致上级负责人脱离子树。
  • 直属上级：第 08 节示例全部；换负责人后立即变化且用户表无写入。
  • 缓存：A 实例改树，B 实例下一次读取即为新树。
  • 权限：缺少 org:manage 时所有写按钮隐藏、接口 403。

25待确认

  1. 负责人约束：本设计采用「每个部门一名负责人，且必须在本部门子树内」。是否认可？如需副负责人，后续以单独字段加入，不参与直属上级计算。
  2. 负责人停用：当前为保留并提示更换。是否改为停用时自动清空？
  3. 层级上限 10 级是否足够？
  4. 部门编码：是否需要业务编码（如财务成本中心编号）供外部系统对接？
  5. 部门类型：是否需要区分公司 / 事业部 / 部门 / 小组？
  6. 删除恢复：删除是否需要回收站（软删除可恢复）？当前为物理删除 + 审计快照。
