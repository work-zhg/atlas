User Center · Tenant Design

用户中心 · 租户详细设计

在用户中心引入租户：每个用户、每个部门都属于且只属于一个租户；组织、授权、数据权限在租户之间完全隔离。接入应用（Atlas、AI TeamFlow）在平台上登记一次，按租户开通。现有数据迁移为一个租户，单租户部署的行为不变。

2026-10-16 · 设计稿，待评审共享表 + tenant_uuid + 复合外键令牌绑定租户平台租户 / 客户租户
总体设计 用户管理 组织管理 应用接入 权限管理
结论先行
  1. 共享表 + 每张租户表一列 tenant_uuid，并用复合外键 (tenant_uuid, xxx_uuid) 让「跨租户引用」在数据库层面不可能写入（部门挂到别的租户、给别的租户的人授权……）。应用层再用统一的租户过滤兜底，查询漏写过滤条件也取不到别的租户的数据。
  2. 应用、操作、菜单、数据编码属于平台（应用方定义一次）；组织、用户、岗位、授权、数据对象与数据授权属于租户。角色两级：应用内置角色是平台级只读模板，租户可以建自己的角色。
  3. 开放接口令牌绑定 (应用, 租户)：应用换令牌时声明租户，之后每个请求自动限定在该租户内，接口参数里不出现租户，所以不可能被参数带到别的租户。
  4. 平台运营方也是一个租户（kind = platform，全局唯一）：「每个用户都属于某个租户」没有例外；平台级操作（建租户、维护应用目录）只对平台租户内的人生效。存量数据迁移成这个平台租户，单租户部署零感知。

01背景与目标

用户中心现在默认「一套部署 = 一个组织」：唯一根部门、账号与邮箱全局唯一、应用的可访问范围直接挂部门。要让同一套用户中心（以及其上的 Atlas、AI TeamFlow）服务多家子公司或外部客户，就需要在组织之上加一层「租户」。

目标

  • 用户、部门属于且只属于一个租户；每个租户一棵独立的部门树
  • 租户之间完全隔离：管理台、开放接口、权限计算、数据权限都看不到别的租户
  • 应用在平台登记一次，按租户开通，并由租户自己设可访问范围
  • 账号在租户内唯一，不同租户可以有同名账号
  • 存量平滑迁移；单租户部署的使用方式不变

非目标（本期）

  • 同一个人跨租户共用身份：本期在两个租户就是两个账号；以后由 Keycloak 关联（P3）
  • 按租户独立数据库 / 独立部署（大客户专属，P3 再评估）
  • 租户自定义安全策略（密码规则、会话时长）：P2
  • 租户私有应用（只在本租户接入的应用）：P2
  • 计费：只记录归属与配额，不定价

02核心概念

概念说明
租户一个相互隔离的组织空间：自己的部门树、用户、岗位、角色授权、数据权限。有企业代码（code，登录时用）、名称、状态、配额
平台租户kind = platform，全局唯一。运营方自己的人在这里；只有平台租户内的人能持有平台级操作（建租户、维护应用目录）
客户租户kind = customer。不能持有任何平台级操作，只能管理自己
应用（目录）平台级：凭据、操作、菜单、数据编码、内置角色由应用方定义一次，所有租户看到的是同一份
租户开通应用某租户能用某应用：开通状态 + 本租户内的可访问范围（全员 / 指定部门含下级）。can_access = 开通 ∧ 在范围内
角色（两级）应用内置角色：平台级，所有开通租户可授、不可改；租户自定义角色：只属于本租户
租户上下文每个请求的「当前租户」：管理台取自登录用户所属租户，开放接口取自令牌。永远不从请求参数读取（登录时的企业代码除外）

03隔离方案选型

方案优点代价结论
共享表 + tenant_uuid一套表、一套迁移；平台级统计与运维简单；用户规模（每租户数百到数万）完全够隔离靠约束与代码纪律，漏写过滤就是越权 —— 用复合外键 + 统一过滤器 + （P2）行级安全三层兜住采用
每租户一个 schema隔离天然；按租户备份恢复方便迁移要对 N 个 schema 各跑一遍；连接要切 search_path；平台级查询要 UNION；租户数一多运维成本线性增长不采用
每租户一个数据库隔离最强，可按客户独立部署资源与运维成本最高；平台级能力（应用目录）要另建一个库同步P3：只为有合规要求的大客户评估

04归属划分：哪些表属于租户

表归属变化
uc_tenant平台新 租户本身
uc_dept租户加 tenant_uuid；「唯一根部门」改为每租户唯一根；同级重名约束不变（parent 已隐含租户）
uc_user租户加 tenant_uuid；账号、邮箱唯一性改为租户内唯一
uc_user_credential · uc_session随用户不加列（经用户确定租户）
uc_login_log租户加 tenant_uuid（登录失败时用户可能不存在，按企业代码记）
uc_app · uc_operation · uc_menu · uc_data_type平台不变：应用目录全局一份
uc_tenant_app租户新 租户开通应用：状态、是否全员、开通人 / 时间
uc_app_scope_dept租户加 tenant_uuid：可访问范围是「某租户开通某应用」的属性，不再挂在应用上
uc_app_token(应用, 租户)加 tenant_uuid：令牌绑定租户
uc_role · uc_role_operation · uc_role_menu两级加 tenant_uuid（可空）：空 = 应用内置角色；非空 = 租户自定义。编码唯一改为 (租户, 编码)
uc_position · uc_position_role租户加 tenant_uuid；岗位编码 / 名称租户内唯一
uc_grant租户加 tenant_uuid；主体（用户 / 部门）与岗位必须同租户；角色必须是内置或本租户的
uc_data_object租户加 tenant_uuid；唯一键改为 (租户, 数据编码, data_id) —— 两个租户的同一个 data_id 互不相干
uc_data_acl · uc_data_type_acl租户加 tenant_uuid。「全部数据授权」只覆盖本租户的全部数据（「全部智能体 · Owner」不会跨租户）
uc_audit_event租户 / 平台加 tenant_uuid（可空：平台级操作为空）
uc_config平台本期不变（全局密码与登录保护）；P2 增加租户覆盖

05数据模型

5.1 租户与开通

CREATE TABLE uc_tenant (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  uuid          uuid NOT NULL UNIQUE,
  code          varchar(32)  NOT NULL UNIQUE,   -- 企业代码：小写字母开头，字母数字与 -，创建后不可改
  name          varchar(64)  NOT NULL,
  kind          varchar(16)  NOT NULL DEFAULT 'customer',   -- platform | customer
  status        varchar(16)  NOT NULL DEFAULT 'active',     -- active | suspended | closed
  max_users     integer,                        -- 配额；空 = 不限
  expires_at    timestamptz,                    -- 到期后视同 suspended
  created_at …, created_by …, updated_at …, updated_by …, version …,
  CHECK (kind IN ('platform','customer')),
  CHECK (status IN ('active','suspended','closed'))
);
CREATE UNIQUE INDEX uq_uc_tenant_platform ON uc_tenant ((kind)) WHERE kind = 'platform';  -- 平台租户只有一个

CREATE TABLE uc_tenant_app (
  id, uuid,
  tenant_uuid   uuid NOT NULL REFERENCES uc_tenant(uuid),
  app_uuid      uuid NOT NULL REFERENCES uc_app(uuid),
  status        varchar(16) NOT NULL DEFAULT 'active',      -- active | disabled（租户侧停用该应用）
  scope_all     boolean NOT NULL DEFAULT false,             -- 全员可访问；否则看 uc_app_scope_dept
  enabled_by    uuid, enabled_at timestamptz NOT NULL,
  UNIQUE (tenant_uuid, app_uuid)
);

5.2 租户表的通用改造

项规则
租户列每张租户表 tenant_uuid uuid NOT NULL；索引一律以 tenant_uuid 打头（列表、搜索都先按租户收窄）
复合唯一被引用的租户表加 UNIQUE (tenant_uuid, uuid)，给复合外键用
复合外键租户表之间的引用改为 (tenant_uuid, xxx_uuid) → 对方 (tenant_uuid, uuid)：
uc_user(tenant_uuid, dept_uuid) → uc_dept、uc_dept(tenant_uuid, parent_uuid / leader_uuid)、uc_grant(tenant_uuid, user_uuid / dept_uuid / position_uuid)、uc_data_acl(tenant_uuid, data_object_uuid / user_uuid / dept_uuid)、uc_data_type_acl、uc_position_role(tenant_uuid, position_uuid)、uc_app_scope_dept(tenant_uuid, dept_uuid)
★ 这是隔离的硬保证：哪怕代码 bug 把别的租户的部门 id 传进来，数据库也拒绝写入
唯一性改写uc_user：(tenant, account)、(tenant, email)；uc_dept：每租户一个根 UNIQUE (tenant_uuid) WHERE parent_uuid IS NULL；uc_role：UNIQUE (coalesce(tenant_uuid, 零值), code) 且租户角色编码不得与内置角色同名；uc_position：(tenant, code)、(tenant, name)；uc_data_object：(tenant, data_type, data_id)
授权引用角色uc_grant.role_uuid 指向的角色必须 tenant_uuid IS NULL OR = 授权的租户（触发器或服务层校验 —— 可空租户列无法用复合外键表达）

06隔离的实现

层做法防的是什么
① 数据库约束复合外键与复合唯一（5.2）跨租户写入（把 A 租户的人加进 B 租户的授权）
② 统一过滤请求开始时建立 TenantContext（管理台：会话用户的租户；开放接口：令牌的租户）。SQLAlchemy 会话上注册 with_loader_criteria，对所有带 tenant_uuid 的模型自动追加 tenant_uuid = 当前租户。平台级操作显式声明 platform_scope() 才能跨租户跨租户读取：某个查询忘了写租户条件
③ 行级安全（P2）PostgreSQL RLS：每个事务 SET LOCAL app.tenant = …，策略 tenant_uuid = current_setting('app.tenant')::uuid；平台操作用单独的数据库角色绕过 ORM 的原生 SQL；纵深防御
④ 测试守卫每个管理 API / 开放接口的契约测试都在两个租户里各造一份数据，断言 A 的凭据访问 B 的 id 一律 404回归
跨租户一律 404按 id 访问别的租户的用户、部门、角色、数据对象，返回「不存在」而不是「无权限」—— 不泄露别的租户里有什么。

07平台与租户的管理

7.1 两类管理员

平台管理员租户超级管理员
在哪平台租户内的用户每个租户内（含平台租户自己）
能做建 / 停用 / 注销租户、设配额与到期；接入应用（凭据、操作、菜单、数据编码、内置角色）；给租户开通应用本租户的组织、用户、岗位、角色授权、自定义角色、数据授权；本租户已开通应用的可访问范围
不能做默认看不到客户租户内的人员与授权；排障需要「代管」显式进入（限时、强制审计，P2）任何平台级操作；看到别的租户
保护平台租户至少一名平台管理员每个租户至少一名可用的超级管理员（现有超级管理员保护按租户进行）

7.2 用户中心内置操作码拆分

级别操作码说明
平台（只对平台租户内的人生效）tenant:view · tenant:manage 新、app:manage（含义收窄为应用目录）建租户、开通应用、接入应用
租户tenant_app:manage 新、org:*、user:*、grant:*、position:*、role:*（仅本租户自定义角色）、data:view、data:type_grant原有操作码的含义不变，只是范围限定在本租户

判定：has(op) 之外再看操作码的级别 —— 平台级操作码对客户租户的人即使被授予也不生效（防止误把平台角色授进客户租户）。内置角色随之拆成「平台管理员」（平台租户专用）与现有的「超级管理员 / 用户管理员 / 审计员」（每个租户都有）。

与「角色归角色、数据权限归数据权限」一致：租户只是两个领域共同的边界，不引入新的「管理全部租户数据」操作码；平台管理员默认不对任何客户租户的数据有权限。

08登录与租户识别

入口P1P2
用户中心管理台登录页三项：企业代码 + 账号 + 密码。浏览器记住上次的企业代码；只有一个租户时（单租户部署）隐藏企业代码子域名 {code}.uc.example.com 自动带出企业代码
接入应用的登录（Atlas、TeamFlow）应用以自己的租户令牌调 verify-password，在该租户内校验（单租户部署：应用配置固定租户）多租户应用：登录页带企业代码，应用按企业代码取对应租户的令牌
以后的 SSO（Keycloak）一个租户对应一个 Keycloak realm（或 organization）；只替换「校验密码」这一步，租户模型不变

失败提示不区分「企业代码不存在」与「账号或密码错误」，统一为「企业代码、账号或密码错误」—— 不让人枚举租户。租户 suspended / closed / 已到期：登录返回「企业账号已停用，请联系管理员」。

09开放接口

接口变化
POST /open/v1/auth/token请求加 tenant_code：令牌绑定 (应用, 租户)。租户未开通该应用 → 403 APP_NOT_ENABLED；租户停用 / 到期 → 403 TENANT_DISABLED。兼容期缺省 = 平台租户（即存量的默认租户），之后必填
GET /open/v1/tenants 新用 App Key / Secret 直接调（不需要租户令牌）：列出已开通本应用的租户 {id, code, name, status} —— 多租户应用据此为每个租户取令牌
其余全部接口请求不变，自动限定在令牌的租户内：/users 只列本租户、/users/{id} 别的租户的 id → 404、/depts/tree 是本租户的树、数据权限只读写本租户的数据对象
返回体用户、部门、授权快照里加 tenant: {id, code}，便于应用自检
Webhook（P1 规划中）事件体加 tenant_id；租户级事件 tenant.suspended、tenant.app_disabled
限流由按 App Key 改为按 (App Key, 租户)：一个租户的流量不挤占别的租户

10权限计算的变化

结果计算
命中的授权不变（授予本人 ∪ 所在部门 ∪ 上级部门含下级），天然只在本租户内（授权、部门都是租户表）
有效角色命中的角色 —— 应用内置角色或本租户自定义角色
can_access(app)租户 active 且未到期 ∧ 租户开通了该应用（uc_tenant_app.status = active）∧ 用户未停用 ∧ 在本租户为该应用设的范围内
操作码 / 菜单不变；平台级操作码只对平台租户内的人计入（7.2）
数据级别max(本租户该数据的授权, 本租户该编码的全部数据授权)
数字员工与人一样属于一个租户 —— 即创建它的应用调用时令牌所属的租户；绑定的 Agent 也在这个租户（见数字员工设计）

11关键流程

① 开通新租户

#动作谁
1新建租户：企业代码、名称、配额、到期 → 同一事务内建根部门（名称 = 租户名）与首个租户超级管理员（临时密码只显示一次）平台管理员
2为租户开通应用（Atlas、TeamFlow…）平台管理员
3租户超级管理员首次登录（企业代码 + 账号 + 临时密码）→ 改密 → 建部门、建用户、设各应用的可访问范围、授角色租户超级管理员

② 接入一个新应用

平台管理员接入一次（凭据、操作、菜单、数据编码、内置角色），再按租户开通。应用侧 register-uc 这类目录同步脚本只写平台级的应用目录，不碰任何租户数据。

③ 租户停用 / 到期 / 注销

状态效果
suspended（或已到期）管理台与应用登录拒绝；该租户的接口令牌全部作废，换令牌 403；数据完整保留，恢复即可用
closed（注销）同 suspended，且进入保留期（默认 30 天）；到期后由 Worker 清除该租户全部数据（P2，需平台管理员二次确认，清除前导出可选）

④ 租户侧停用某应用

租户超级管理员把 uc_tenant_app.status 置为 disabled：该租户的人对该应用 can_access = false，应用的该租户令牌作废；数据权限保留。

12对接入应用的影响

阶段Atlas / AI TeamFlow 要做的
P1 单租户绑定配置项 UC_TENANT_CODE（缺省 = 平台租户）；换令牌时带上；用户投影（Atlas app_user、TeamFlow tf_user）加 tenant_id 记录来源。行为完全不变 —— 一个部署服务一个租户
P2 应用多租户应用自己的业务数据按租户隔离：Atlas 的 agent / thread / run / 知识库 / 记忆、对象存储前缀、会话 Pod 标签与配额、Redis 键、向量库过滤条件；TeamFlow 的团队、项目、流程。这是每个应用独立的改造项目，用户中心只提供租户身份
数据权限调用不用改：令牌绑定租户后，data_id 只在本租户内有意义；同一个 Agent id 不会在两个租户里撞
缓存应用侧授权快照等缓存的键加上租户（P2 多租户时必需；P1 单租户无影响）

13存量迁移

#迁移步骤（一个 Alembic 版本，单事务）
1建 uc_tenant，插入一个平台租户：code = default、名称取根部门名、kind = platform。存量就是这个租户 —— 现有超级管理员同时是平台管理员，单租户部署的管理方式不变
2所有租户表加 tenant_uuid（先可空）→ 回填为平台租户 → 改 NOT NULL
3为每个存量应用建 uc_tenant_app（平台租户，开通；scope_all 取原 uc_app.scope_all），uc_app_scope_dept 回填租户
4删除旧的全局唯一约束，建租户内唯一与复合外键
5作废全部接口令牌（应用下次调用自动重新换取，兼容期缺省租户 = default）
6uc_app.scope_all 保留到兼容期结束后删除

以后要做 SaaS：新建客户租户即可，平台租户保持为运营方自己。若要把运营方与原业务组织拆开，另起一次「租户拆分」操作（P2），不在本次迁移里。

14缓存、审计与安全

项设计
缓存部门树、有效角色缓存的键加租户；授权版本号按租户（一个租户的授权变更不让全部租户的缓存失效）；应用目录缓存仍全局
