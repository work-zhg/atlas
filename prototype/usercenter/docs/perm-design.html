User Center · Detailed Design

权限管理模块

权限管理回答两个问题：谁能用应用的哪些功能（角色授权），谁能动哪一条数据（数据授权）。角色、操作、菜单、数据编码的定义属于应用（应用接入模块）；本模块负责把岗位和角色授予用户或组织、维护岗位、按「数据编码 + 数据 Id」做数据授权，并计算每个人的有效权限，通过开放接口提供给接入应用。

岗位 / 角色 → 用户 / 部门部门授权可含下级有效权限 = 并集，实时计算数据权限：只读 < 读写 < Owner只有 Owner 能改数据授权至少一名超级管理员 / Owner

01定位与范围

本模块负责

  • 角色授权：把岗位、角色授予用户或部门（部门可含下级）；撤销；调整范围
  • 岗位管理：岗位及其默认角色
  • 数据授权：数据登记、只读 / 读写 / Owner 授权，Owner 维护
  • 有效权限计算：角色、操作码、菜单、数据权限级别及来源
  • 保护规则：至少一名可用的超级管理员；每条数据至少一名可用的 Owner
  • 开放接口中的授权快照、实时校验、数据权限接口

不在本模块

  • 角色、操作、菜单、数据编码的定义 → 应用接入
  • 用户、部门本身 → 用户管理、组织管理
  • 应用内「只读 / 读写」具体能做什么 → 由各应用解释
  • 登录（SSO）→ 本期不做，以后用 Keycloak
  • 本期不做：拒绝授权（deny）、管理数据范围（只管本部门）、授权有效期 / 临时授权、授权审批

02术语

术语含义
授权对象用户，或部门。授予部门时可选「含下级部门」。
角色授权一条记录：把一个岗位或角色授予一个授权对象。
岗位全局维护的职位（如「后端工程师」），可关联多个默认角色（可跨应用）；获得岗位即获得其默认角色。
直接授权 / 继承授予用户本人的是直接授权；授予其所在部门、或授予上级部门且含下级的，是继承。继承来的授权只能在来源处修改。
有效角色用户命中的全部角色授权 ∪ 命中岗位的默认角色，去重并记录每个来源。
数据对象应用中的一条数据，用「数据编码 + 数据 Id」标识（如 Agent + agt_7f3a21）。
数据权限级别只读（1）< 读写（2）< Owner（3）。高级别包含低级别；Owner 还能管理这条数据的授权。
授权快照某用户在某应用的 can_access、角色、操作码、菜单，由开放接口返回，应用缓存使用。

05授权模型

角色授权（功能权限）

岗位
  • 全局维护
  • 默认角色 0..n
默认角色
角色
  • 属于某应用
  • = 操作 + 菜单
授权记录：岗位 或 角色 → 用户 / 部门（可含下级）

数据授权（数据权限）

数据编码
  • 属于某应用
  • 如 Agent
1 : n
数据对象
  • 数据 Id
  • 如 agt_7f3a21
授权记录：只读 / 读写 / Owner → 用户 / 部门（可含下级）
  • 两套授权相互独立：有某应用的角色不代表能看到它的某条数据，反之亦然；应用通常两者都检查（先看操作码，再看数据级别）。
  • 两套授权的授权对象规则一致：用户、部门（含下级可选），继承方式相同。
  • 只有授予，没有拒绝；有效结果是所有来源的并集（数据权限取最高级别）。

06有效权限的计算

命中的授权

matchedGrants(user):                      // 角色授权与数据授权使用同一规则
  chain = 用户所在部门及其全部上级部门
  return grants where
       (subject = user)                                   // 直接授权
    or (subject = 用户所在部门)                            // 所在部门（不论是否含下级）
    or (subject ∈ chain 的上级部门 and include_sub = true)  // 上级部门且含下级

有效角色、操作码、菜单

effectiveRoles(user):
  if user.status = disabled: return ∅
  roles = {}
  for g in matchedGrants(user) where g.kind = role:     roles[g.role] += 来源(g)
  for g in matchedGrants(user) where g.kind = position:
    for r in g.position.default_roles:                  roles[r] += "岗位：" + g.position.name
  return roles                                          // 角色 → 来源列表

permissions(user, app) = ∪ { r.operations | r ∈ effectiveRoles(user), r.app = app }
menus(user, app)       = 公共菜单 ∪ 角色绑定的菜单，补上级目录（见应用接入 · 菜单）
canAccess(user, app)   = user 未停用 且 在 app 的可访问范围内
// 不在可访问范围内时，授权快照中的角色 / 操作码 / 菜单一律返回空

示例（原型数据：陈运，技术中心）

命中的授权来源带来的角色
岗位「SRE 负责人」授予陈运直接授权流程成员（TeamFlow）、Agent 管理员（Atlas）
角色「流程成员」授予研发中心（含下级）部门：研发中心（含下级）流程成员
角色「Agent 管理员」授予技术中心部门：技术中心Agent 管理员

结果：流程成员（来源：岗位 SRE 负责人、部门 研发中心（含下级））；Agent 管理员（来源：岗位 SRE 负责人、部门 技术中心）。撤销其中一个来源，角色仍然保留。

数据权限级别

levelOf(user, data) = max{ a.level | a ∈ data.acl, a 命中 user }    // 无命中 = 无权限；已停用用户 = 无权限

07角色授权

规则说明
唯一同一（岗位或角色，授权对象）只有一条记录；重复授予时：部门授权按本次选择更新「含下级」，用户授权跳过
含下级只对部门有效；界面默认勾选（上级部门往往没有直属成员）；可随时切换
继承只读在子部门或用户上看到的继承授权不能直接撤销，显示「继承自 研发中心（含下级）」并可跳转到来源
已停用用户不能新授予；已有授权保留（启用后恢复），停用期间不生效
可访问范围允许授予范围外的用户，但不生效；P1 在授予时提示
撤销确认弹窗显示覆盖人数，提示「没有其他来源的人将失去对应权限」
保护任何撤销、范围调整都经过超级管理员保护（第 09 节）

三个入口

入口操作
权限管理 → 按对象授权选部门或用户 →「授予岗位」「授予角色」（多选，部门可选含下级）
岗位管理 →「授权」选多个部门（含下级可选）和多个用户，一次授予该岗位
应用接入 → 角色 →「授权」分页同上，授予该角色；同时列出哪些岗位带有该角色

08岗位管理

字段规则
名称必填，全局唯一，1–32 字符
编码^[A-Z][A-Z0-9_]{1,31}$，全局唯一，创建后不可改
默认角色0..n 个，可来自不同应用；按应用分组勾选
排序列表显示顺序 P1
  • 修改默认角色立即影响所有获得该岗位的人（含经部门获得的）；经过超级管理员保护。
  • 删除：岗位还有授权时拒绝，提示「请先在角色授权中撤销 N 条授权」。
  • 列表显示：名称、编码、默认角色、授权对象（前 3 个 + 总数）、人数（实际获得该岗位的人）、操作（授权 / 编辑 / 删除）。
  • 用户的「岗位」展示 = 其命中的全部岗位授权（可多个），不再是用户表上的字段。

09超级管理员保护

规则：任何时候至少有一名未停用、且有效角色包含内置角色「超级管理员」（UC_SUPER）的用户。否则没人能再管理用户中心。

可能破坏规则的写操作所在模块
撤销授权、把部门授权改为仅本部门本模块
修改岗位默认角色本模块
停用用户用户管理
用户调整部门、移动部门（继承关系改变）用户管理、组织管理

实现

  • 上述操作在事务内先取 pg_advisory_xact_lock('uc_super_guard') 串行化，再执行变更，再计算是否仍有可用超级管理员；没有则回滚并返回 LAST_SUPER_ADMIN。串行化避免「两个管理员同时撤销两位超级管理员，各自检查都通过」。
  • 计算：取所有 UC_SUPER 授权与带有它的岗位授权 → 展开为用户（部门授权按含下级展开）→ 过滤未停用 → 找到一个即可返回。
  • 超级管理员是内置角色：不可删除，操作与菜单锁定。

10数据授权

数据对象

  • 由应用在创建数据时调用开放接口登记（首次写入 Owner 时自动创建数据对象），记录数据编码、数据 Id、名称（展示用）、所属应用。
  • 数据 Id 是应用自己的 Id（≤ 64 字符），在同一数据编码下唯一。
  • 应用删除数据时调用清理接口，删除数据对象及其全部授权。

授权规则

规则说明
级别只读 < 读写 < Owner；同一对象对同一条数据只有一条授权，再次授予即更新级别（与部门范围）
授权对象用户、部门（可含下级）；继承规则同角色授权
谁能修改只有对该数据有效级别为 Owner 的人（直接或经部门获得）。管理员（data:view）只能查看
Owner 保护任何添加 / 改级别 / 改范围 / 移除后，这条数据至少还有一名未停用的用户是 Owner，否则回滚（LAST_DATA_OWNER）
授予 Owner被授予者也能管理这条数据的授权（包括移除原 Owner）
来源记录「接口写入（应用名）」或「某某授权」

无可用 Owner

Owner 离职被停用、或调出了作为 Owner 的部门时，数据可能变成「无可用 Owner」。本期不阻止停用 / 调部门（否则会卡住人事操作）：

  • 「全部数据」列表中标红「无可用 Owner」，可按此筛选。
  • Owner 被启用后自动恢复。
  • P1：超级管理员「移交 Owner」，写审计（需确认是否允许，见待确认）。

界面分组

分组内容谁能看到
我管理的我的有效级别为 Owner 的数据所有登录用户
我可访问的我的有效级别为只读 / 读写的数据所有登录用户
全部数据全部数据对象（只读）data:view

数据详情：我的级别及来源；授权列表（Owner 可在表格中直接改级别、切换含下级、移除，以及添加授权）；实际可访问的人（有效级别及来源）。

11数据授权的接口写入

#场景调用
1用户在 Atlas 创建 AgentAtlas 后端：POST /open/v1/data-permissions，permission=OWNER，subject=创建人；数据对象不存在时自动创建
2用户打开 / 编辑 / 删除 AgentGET /open/v1/data-permissions/check，按返回级别决定
3Agent 列表页GET /open/v1/data-permissions/accessible?min=READ 过滤
4Owner 在 Atlas 内「分享」给组织 P1POST /open/v1/data-permissions 带 operator_id：用户中心校验 operator 对该数据为 Owner
5删除 AgentDELETE /open/v1/data-permissions?data_code=Agent&data_id=…
接口侧的 Owner 规则 应用以自身身份（不带 operator）只能做两件事：为不存在授权的数据写入第一个 Owner（创建场景）、清理整条数据（删除场景）。其他修改必须带 operator_id 且该用户是 Owner。这样应用无法绕过「只有 Owner 能改授权」。

12变更的生效

变更受影响的人
授予 / 撤销给用户该用户
授予 / 撤销给部门该部门成员（含下级时为子树成员）
修改岗位默认角色所有获得该岗位的人
修改角色的操作 / 菜单（应用接入）该角色的全部拥有者
用户调部门 / 移动部门（组织）相关成员的继承授权变化
  • 用户中心内（用户详情、侧边栏、按钮、实时校验接口、数据权限接口）都是实时计算，变更立即生效。
  • 接入应用缓存的授权快照最长 5 分钟后刷新；P1 起推送 authz.changed（附受影响用户 uuid，超过 1000 人时只给「全量刷新」标记），应用立即刷新。
  • 数据权限接口本身不缓存，应用每次 check 即为最新结果。

13数据模型

主键约定（全部表通用） id bigint 自增主键，只在库内使用，不对外暴露、不用于任何关联； uuid uuid 逻辑主键（UUIDv7），表间关联、外键、API 都使用它。关联字段命名为 xxx_uuid，外键引用对方表的 uuid；API 中的 id / xxx_id 取值即对应的 uuid。
-- 岗位
CREATE TABLE uc_position (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  uuid        uuid        NOT NULL UNIQUE,
  code        varchar(32) NOT NULL UNIQUE,
  name        varchar(32) NOT NULL UNIQUE,
  sort        int NOT NULL DEFAULT 0,
  created_at timestamptz NOT NULL DEFAULT now(), created_by uuid,
  updated_at timestamptz NOT NULL DEFAULT now(), updated_by uuid,
  version     int NOT NULL DEFAULT 1
);

-- 岗位默认角色
CREATE TABLE uc_position_role (
  id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  uuid           uuid NOT NULL UNIQUE,
  position_uuid  uuid NOT NULL REFERENCES uc_position(uuid) ON DELETE CASCADE,
  role_uuid      uuid NOT NULL REFERENCES uc_role(uuid) ON DELETE CASCADE,
  CONSTRAINT uk_position_role UNIQUE (position_uuid, role_uuid)
);

-- 角色授权：岗位 或 角色 → 用户 或 部门
CREATE TABLE uc_grant (
  id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  uuid           uuid NOT NULL UNIQUE,
  kind           varchar(8)  NOT NULL,             -- position | role
  position_uuid  uuid REFERENCES uc_position(uuid),
  role_uuid      uuid REFERENCES uc_role(uuid) ON DELETE CASCADE,
  subject_type   varchar(8)  NOT NULL,             -- user | dept
  user_uuid      uuid REFERENCES uc_user(uuid),
  dept_uuid      uuid REFERENCES uc_dept(uuid) ON DELETE CASCADE,
  include_sub    boolean NOT NULL DEFAULT false,
  granted_by     uuid NOT NULL,
  granted_at     timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_grant_kind CHECK ((kind = 'position') = (position_uuid IS NOT NULL)
                              AND (kind = 'role')     = (role_uuid IS NOT NULL)),
  CONSTRAINT ck_grant_subject CHECK ((subject_type = 'user') = (user_uuid IS NOT NULL)
                                 AND (subject_type = 'dept') = (dept_uuid IS NOT NULL)),
  CONSTRAINT ck_grant_sub CHECK (subject_type = 'dept' OR NOT include_sub)
);
CREATE UNIQUE INDEX uk_grant ON uc_grant (kind, coalesce(position_uuid, role_uuid), coalesce(user_uuid, dept_uuid));
CREATE INDEX ix_grant_user ON uc_grant (user_uuid) WHERE user_uuid IS NOT NULL;
CREATE INDEX ix_grant_dept ON uc_grant (dept_uuid) WHERE dept_uuid IS NOT NULL;
CREATE INDEX ix_grant_role ON uc_grant (role_uuid) WHERE role_uuid IS NOT NULL;
CREATE INDEX ix_grant_pos  ON uc_grant (position_uuid) WHERE position_uuid IS NOT NULL;

-- 数据对象
CREATE TABLE uc_data_object (
  id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  uuid            uuid NOT NULL UNIQUE,
  data_type_uuid  uuid NOT NULL REFERENCES uc_data_type(uuid),
  data_id         varchar(64)  NOT NULL,           -- 应用自己的数据 Id
  data_name       varchar(100),
  created_at      timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT uk_data_object UNIQUE (data_type_uuid, data_id)
);

-- 数据授权
CREATE TABLE uc_data_acl (
  id                bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  uuid              uuid NOT NULL UNIQUE,
  data_object_uuid  uuid NOT NULL REFERENCES uc_data_object(uuid) ON DELETE CASCADE,
  level             smallint NOT NULL,             -- 1 只读 | 2 读写 | 3 Owner
  subject_type      varchar(8) NOT NULL,           -- user | dept
  user_uuid         uuid REFERENCES uc_user(uuid),
  dept_uuid         uuid REFERENCES uc_dept(uuid) ON DELETE CASCADE,
  include_sub       boolean NOT NULL DEFAULT false,
  source            varchar(8) NOT NULL,           -- api | manual
  granted_by        uuid,                          -- manual 时为操作人；api 时为空
  granted_app_uuid  uuid,                          -- api 时为调用应用
  granted_at        timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT ck_acl_level   CHECK (level IN (1, 2, 3)),
  CONSTRAINT ck_acl_subject CHECK ((subject_type = 'user') = (user_uuid IS NOT NULL)
                               AND (subject_type = 'dept') = (dept_uuid IS NOT NULL)),
  CONSTRAINT ck_acl_sub     CHECK (subject_type = 'dept' OR NOT include_sub)
);
CREATE UNIQUE INDEX uk_data_acl ON uc_data_acl (data_object_uuid, coalesce(user_uuid, dept_uuid));
CREATE INDEX ix_acl_user ON uc_data_acl (user_uuid) WHERE user_uuid IS NOT NULL;
CREATE INDEX ix_acl_dept ON uc_data_acl (dept_uuid) WHERE dept_uuid IS NOT NULL;
  • 级别存数字（1 / 2 / 3），取最高级别用 max(level)；对外显示为 READ / WRITE / OWNER。
  • 授予部门的授权随部门删除级联删除（组织模块删除前已提示数量并写审计）；删除角色级联删除其授权。
  • 岗位不级联：有授权的岗位不能删除。

14计算与查询实现

用户命中的授权

-- :user 用户 uuid；:dept 用户所在部门；:ancestors 其全部上级部门（由部门树缓存得到）
SELECT * FROM uc_grant
WHERE  user_uuid = :user
   OR  dept_uuid = :dept
   OR (include_sub AND dept_uuid = ANY(:ancestors));

用户可访问的数据（列表过滤）

SELECT o.data_id, max(a.level) AS level
FROM   uc_data_object o
JOIN   uc_data_acl a ON a.data_object_uuid = o.uuid
WHERE  o.data_type_uuid = :type
  AND (a.user_uuid = :user OR a.dept_uuid = :dept OR (a.include_sub AND a.dept_uuid = ANY(:ancestors)))
GROUP  BY o.data_id
HAVING max(a.level) >= :min_level
ORDER  BY o.data_id
LIMIT  :size OFFSET :offset;

缓存

  • 维护全局授权版本号（Redis）：任何授权、岗位、角色定义、用户部门 / 状态、部门结构变更后 +1。
  • 每个用户的有效角色（含来源）按 (user, 版本号) 缓存；版本号变化即失效重算。写操作低频，全局版本号足够且不易出错。
  • 角色定义（操作、菜单）、部门树在各实例内存中，按各自版本号失效。
  • 数据权限不缓存，直接走上面的 SQL（命中索引）。

并发

  • 可能减少超级管理员的写操作：事务内 pg_advisory_xact_lock('uc_super_guard')。
  • 数据授权的写操作：事务内 SELECT … FROM uc_data_object WHERE uuid = :obj FOR UPDATE 锁住该数据，再做 Owner 校验，避免两名 Owner 同时互相移除。

20异常与边界

场景处理
同一角色经多个来源获得，撤销其一角色仍在，来源减少
部门授权改为仅本部门下级部门成员失去继承；经超级管理员保护
两个管理员同时撤销两位超级管理员串行化执行，后者 LAST_SUPER_ADMIN
两名 Owner 同时互相移除数据行加锁，后者 LAST_DATA_OWNER
Owner 全部被停用不阻止停用；数据标「无可用 Owner」；启用后恢复；P1 移交
授予的用户不在应用可访问范围授权保存但不生效；P1 授予时提示
角色被删除授权级联删除，并从岗位默认角色移除（删除前在应用接入中预览）
部门被删除授予该部门的角色授权、数据授权级联删除（组织模块删除前提示数量）
应用对已存在授权的数据再次写入 Owner（不带 operator）OWNER_REQUIRED，防止应用绕过 Owner 规则
用户对某数据既有直接只读又有部门读写有效级别为读写；详情中列出两个来源

21非功能

性能

  • 按 5 万用户、10 万条角色授权、100 万条数据授权设计
  • 授权快照 p95 < 50ms（有效角色缓存命中 < 5ms）
  • 数据权限 check p95 < 20ms；accessible 分页 p95 < 100ms
  • 覆盖人数、拥有者列表按需计算，列表页分页

正确性

  • 保护规则与变更在同一事务，失败整体回滚
  • 缓存以全局授权版本号失效，不会读到过期的有效权限
  • 开放接口按调用方应用隔离：只能看到本应用的角色 / 菜单 / 数据编码

23测试要点

  • 继承：直接、所在部门（含 / 不含下级都命中）、上级部门含下级命中、上级部门不含下级不命中、多级继承。
  • 有效角色：岗位默认角色、多来源去重、撤销一个来源角色仍在、已停用用户为空、范围外用户快照为空。
  • 授权唯一：重复授予用户跳过；重复授予部门更新含下级。
  • 岗位：编码格式 / 唯一、名称唯一、删除有授权的岗位被拒、修改默认角色立即影响拥有者。
  • 超级管理员保护：撤销、改范围、改岗位默认角色、停用、调部门、移动部门；并发撤销两位只能成功一个。
  • 数据授权：级别取最高；非 Owner 修改被拒；Owner 互相移除并发；最后一名 Owner 移除 / 降级被拒；经部门获得 Owner 后可降级本人。
  • 接口：写入首个 Owner 自动建数据对象；已存在授权时不带 operator 被拒；跨应用数据编码被拒；accessible 分页与 min 过滤；清理接口。
  • 级联：删除部门、删除角色后授权与数据授权被清理。
  • 缓存：任意授权变更后快照与 check 立即反映新结果。
  • 权限：各分页在缺少操作码时隐藏、接口 403；普通用户只有数据授权分页。
