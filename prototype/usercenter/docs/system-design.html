User Center · System Design

用户中心 · 总体详细设计

用户中心是公司内部系统共用的用户、组织与权限的唯一数据源：自建账号、维护部门树与负责人、登记接入应用及其权限元数据（操作、菜单、角色、数据编码）、把岗位 / 角色 / 数据权限授予人和组织，并通过服务端开放接口把这些结果提供给 AI TeamFlow、Atlas 等应用。本文给出整体架构、模块边界、跨模块流程与通用约定；各模块细节见对应的模块详细设计。

用户 · 组织 · 应用接入 · 权限开放接口（服务端）模块化单体PostgreSQL + Redis自增 id + uuid 逻辑主键SSO 以后用 Keycloak
用户管理 组织管理 应用接入 权限管理 安全策略（后续）审计日志（后续）

01背景与目标

公司内部系统各自维护账号、组织和权限，导致人员变动要在多处修改、权限口径不一致、离职回收不及时。用户中心把这三类数据收拢到一处：

目标

  • 一处维护：账号、部门、负责人只在用户中心维护
  • 统一口径：功能权限（角色 → 操作码 / 菜单）与数据权限（只读 / 读写 / Owner）有同一套授权模型
  • 按组织授权：授予部门（可含下级），人员调动后权限自动跟随
  • 易接入：应用只需调开放接口，不必自建权限体系
  • 离职即生效：停用后各应用立即查到已停用

非目标（本期）

  • 统一登录（SSO / OIDC）：以后用 Keycloak，不自建
  • 安全策略、审计日志两个模块的页面与详细设计
  • HR 系统同步；批量导入 / 导出 / 批量操作
  • 兼职多部门、副负责人；拒绝授权、授权有效期、授权审批
  • 应用内业务鉴权的具体实现（由各应用按返回结果控制）

07领域模型

组织
  • 部门（树）
  • 负责人 → 用户
用户
  • 属于一个部门
  • 凭据（密码哈希、锁定）
应用
  • 可访问范围 → 部门
  • 操作、菜单、角色（操作 + 菜单）、数据编码
授权
  • 岗位（默认角色）
  • 角色授权：岗位 / 角色 → 用户 / 部门
  • 数据对象、数据授权 → 用户 / 部门
关系基数说明
部门 — 部门1 : n父子；唯一根
用户 — 部门n : 1必填
部门 — 负责人n : 0..1负责人须在部门子树内；一人可负责多个部门
应用 — 操作 / 菜单 / 角色 / 数据编码1 : n都属于应用，编码不可改
角色 — 操作、角色 — 菜单n : n只能是同一应用的
岗位 — 角色n : n默认角色，可跨应用
角色授权（岗位 | 角色）× （用户 | 部门）同一组合唯一；部门可含下级
数据编码 — 数据对象 — 数据授权1 : n : n同一对象对同一数据唯一；级别取最高

08关键流程

① 新员工入职

#动作模块
1管理员在部门下新建用户 → 生成临时密码（只显示一次），状态「未激活」用户
2用户自动继承所在部门（及上级含下级）的岗位、角色、数据授权；如需个人授权，在权限管理中授予岗位 / 角色权限
3用户首次登录用户中心管理台并修改密码 → 激活用户 / 管理台认证
4用户登录 TeamFlow（应用自身的登录）→ TeamFlow 按账号查询用户、取授权快照 → can_access 为真则进入，并按菜单 / 操作码渲染开放接口

② 新应用接入

#动作模块
1接入应用 → App Key / Secret（只显示一次）；设置可访问范围应用接入
2登记操作、菜单、数据编码；建角色并勾选操作与菜单应用接入
3把角色授予部门 / 用户，或加入岗位的默认角色权限
4应用后端按接入规范对接开放接口应用

③ Atlas 创建 Agent 并分享

#动作模块
1张明在 Atlas 创建 Agent → Atlas 后端调 POST /open/v1/data-permissions 写入张明为 Owner（自动登记数据对象）权限
2张明在用户中心「权限管理 → 数据授权 → 我管理的」中把只读授予「研发中心（含下级）」、读写授予陈运（P1 起也可在 Atlas 内带 operator 完成）权限
3陈运打开 Agent → Atlas 调 check → 读写（直接授权）与只读（部门）取最高 = 读写权限

④ 组织调整

动作连锁影响（全部自动、实时）
部门换负责人部门成员的直属上级立即变化，用户表无写入
员工调部门直属上级、部门继承的授权、应用可访问范围、部门数据权限按新部门计算；若其是原部门负责人且调出子树，负责人自动清空；经过超级管理员保护
移动部门子树成员的继承授权、范围、直属上级重算；旧上级链中负责人脱离子树的被清空
删除空部门从应用范围中移除；授予该部门的角色授权、数据授权被撤销

⑤ 员工离职

#动作
1管理员停用用户（不能停用唯一的超级管理员）→ 管理台会话注销
2开放接口立即返回 status = disabled、can_access = false、有效权限为空；应用最长 5 分钟内刷新快照后终止其会话（P1 收到 user.disabled 立即踢出）
3授权、数据权限保留（可启用恢复）；其作为负责人的部门提示更换；其为唯一 Owner 的数据标「无可用 Owner」

09权限计算总览

结果计算计算位置 / 缓存
命中的授权授予本人 ∪ 授予所在部门 ∪ 授予上级部门且含下级权限；按用户 + 授权版本号缓存
有效角色命中的角色授权 ∪ 命中岗位的默认角色（记录来源）；已停用用户为空同上
can_access(app)未停用且在应用可访问范围内应用接入
操作码 (app)有效角色中属于该应用的角色的操作并集；范围外为空权限 + 应用接入
菜单 (app)公共菜单 ∪ 角色绑定菜单，补上级目录；范围外为空同上
数据级别该数据上命中的数据授权的最高级别；已停用为无权限；不缓存，SQL 索引
直属上级部门链上第一个不是本人、未停用的负责人组织；部门树内存缓存
用户中心自己也用这套规则用户中心是内置应用：它的侧边栏 = 内置菜单树按登录人角色计算的结果（「权限管理」为公共菜单）；页面按钮 = 操作码（如 user:create、grant:manage）。内置角色：超级管理员（全部，锁定）、用户管理员、审计员。

10开放接口总览

接口说明模块
POST /open/v1/auth/tokenApp Key / Secret → 接口令牌（2 小时）应用接入
GET /users/by-account/{account} · /users/{id}用户信息（含部门路径、直属上级、状态）用户 / 组织
GET /users选人：只含本应用可访问范围内的未停用用户用户
GET /depts/tree部门树组织
GET /users/{id}/authz授权快照权限
POST /authz/check实时校验操作码权限
/data-permissions（写入 / check / accessible / 清理）数据权限；只限本应用数据编码权限
PUT /metadata P1应用上报操作与菜单应用接入
Webhook P1user.*、authz.changed、app.disabled，HMAC 签名各模块
  • 隔离：每个请求都限定在接口令牌所属应用——只能看到本应用的角色 / 菜单 / 数据编码、本应用范围内的用户。
  • 版本：路径带 v1；只做向后兼容的新增，破坏性变更走 v2 并行一段时间。
  • 限流：按 App Key，默认 50 次 / 秒，可按应用调整。
  • 错误格式：{ "code": "...", "message": "...", "details": {...} }，与管理 API 一致。

11数据设计约定

约定规则
主键id bigint 自增主键，仅库内使用，不对外、不做关联；uuid 逻辑主键（UUIDv7，应用生成）用于全部关联、外键、API、审计对象
命名表名 uc_ 前缀、单数；关联字段 xxx_uuid；时间 xxx_at（timestamptz）；操作人 xxx_by（用户 uuid）
公共列可编辑的主体表带 created_at/by、updated_at/by、version（乐观锁，接口用 If-Match）
删除策略用户、应用只停用不删除；部门、岗位、角色、操作、菜单、数据编码物理删除（有引用时拒绝或按规则级联），审计保留快照
编码账号、角色编码、操作码、菜单编码、数据编码、岗位编码一律创建后不可改
枚举varchar + CHECK 约束（如 status IN ('active','disabled')）；数据权限级别用 smallint 1 / 2 / 3
迁移Alembic 版本化迁移；内置应用、内置角色、内置菜单、根部门与首个超级管理员由初始化迁移写入

12一致性与并发

风险手段
并发移动部门形成环树结构变更取 pg_advisory_xact_lock('uc_dept_tree') 串行化
并发操作导致没有超级管理员可能减少超级管理员的操作（撤销授权、改岗位默认角色、停用、调部门、移动部门）取 pg_advisory_xact_lock('uc_super_guard')，变更后校验，失败回滚
两名 Owner 互相移除数据对象行 SELECT … FOR UPDATE，变更后校验至少一名可用 Owner
两人同时编辑同一对象version 乐观锁，后到者 VERSION_CONFLICT
唯一性竞争（账号、编码）数据库唯一约束兜底
负责人约束被破坏设置负责人、用户调部门、移动部门时在同一事务内校验 / 自动清空
对外通知与数据不一致（P1）事务内写 outbox 表，提交后由 Worker 投递 Webhook（至少一次，应用按事件 id 去重）

13缓存

内容位置失效
部门树（含负责人）各实例内存树版本号（Redis）变化时重载
应用配置、操作、菜单、角色定义各实例内存按应用的版本号
用户有效角色（含来源）Redis，键 = 用户 + 授权版本号授权版本号：任何授权、岗位、角色定义、用户状态 / 部门、部门结构变更 +1
管理台会话、接口令牌Redis到期 / 停用 / 轮换时删除
数据权限不缓存—
应用侧授权快照应用自己最长 5 分钟；P1 Webhook 触发

写操作低频，使用粗粒度的全局版本号：实现简单、不会读到过期结果，代价只是变更后短时间内缓存命中率下降。

14安全

管理台登录（本期）

  • 账号密码登录；密码 argon2id；临时密码 CSPRNG，只显示一次
  • 首次登录 / 临时密码 / 过期必须改密
  • 连续失败锁定；会话 Cookie：HttpOnly、Secure、SameSite=Lax；CSRF 令牌
  • 固定值（uc_config）：密码至少 8 位含大写与数字、有效期 90 天、5 次失败锁定 15 分钟、会话 12 小时；以后由安全策略模块提供配置界面

接口与数据

  • App Secret 只显示一次、只存哈希；接口令牌 2 小时可随时作废
  • 开放接口按应用隔离；按 App Key / IP 限流
  • 审计不含密码与 Secret，邮箱 / 手机脱敏
  • 全站 HTTPS；含密码 / Secret 的响应 no-store
  • 前端隐藏只负责「看不到」，所有接口服务端按操作码 / Owner 再鉴权
统一登录本期不提供 SSO，应用自行登录并按账号对齐身份。以后引入 Keycloak（推荐用户联邦：Keycloak 从用户中心读用户、由用户中心校验密码），用户中心仍是唯一数据源，管理台也改由 Keycloak 登录。详见应用接入 · 后续统一登录。
