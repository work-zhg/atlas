AI TeamFlow · Detailed Design

流程运行模块（含 Agent 适配层、产物与仓库）

成员按项目绑定的模板发起流程；节点由人与 AI Agent 协同产出一份产物（Markdown，存 Git），经准出 / 准入评审后通过，依赖都通过的下游节点自动开工。定义可以随时改，进行中的工作在关键时刻锁定定义而不被打乱。本文是 整体系统设计 §8–§12 的展开，与实现（teamflow/src/atlas_teamflow/process、agents）一致。

状态机 + 流程级锁一个节点一个 Atlas 会话一次提交 = 一个版本事件表 = 审计 + 实时无超时

01定位与范围

在范围内发起流程（锁模板版本）；节点状态机与自动流转（顺序、并行开工、汇合）；人机协同（指令排队投递给 Agent、Agent 输出实时显示）；产物版本（Agent 交付或人工提交，均为 Git 提交）；准出 / 准入评审（任一人 / 所有人）；驳回（本节点修改）与打回（到更早节点）；终止；流程事件（审计 + 实时）；待我处理。
不在范围内（P2）AI 自动准出、评审转交、版本对比（diff 页面）、IM / 邮件通知、度量、Git 远端推送（GitLab / Gitea）、产物白名单 Markdown 渲染（首版按纯文本显示）。

02节点状态机

待开始 ──依赖全部通过──▶ 人机协同中 ──提交准出──▶ 待准出 ──规则满足──▶ 待准入 ──规则满足──▶ 已通过 ▲ 驳回 │ │ └────────────────────────┴─────────────────────┘ 已通过 / 协同中 / 评审中 ──（上游被打回）──▶ 已打回 ──上游重新通过──▶ 人机协同中（第 n+1 轮）
状态编码说明
待开始pending依赖尚未全部通过
人机协同中working人下指令、Agent 产出；可手工提交产物；有本轮产物后可提交准出
待准出 / 待准入exit_review / admit_review有一个打开的评审轮次；未配置准入时准出通过即「已通过」
已通过passed触发调度；全部节点通过 → 流程完成
已打回returned上游被打回修改；等上游重新通过后按依赖重新开工

轮次：每次回到人机协同（首次开工、驳回、打回重开）轮次 +1。提交准出要求当前产物属于本轮 —— 驳回后必须有新版本（内容不变可人工重新提交一次）。流程状态：running / completed / terminated。

03锁定规则

锁定什么何时存在哪之后定义变化
流程模板版本发起时tf_process.template_version_uuid模板再发布不影响该流程
文件模板版本节点首次开工tf_process_node.file_template_version_uuid驳回、打回重开都不重新锁定
执行 Agent节点首次开工tf_process_node.agent_uuid / atlas_agent_id项目改分配不影响该节点
评审人名单每次进入待准出 / 待准入tf_review_round.reviewers本轮人数不变；驳回重提后用新名单

执行人不锁定：谁能在节点上协同按项目当前分配判断（换人立即生效）。

04调度与流转

  1. 依赖由模板结构推导（structure.derive_deps）：单节点依赖上一步全部出口；并行组每条轨道的首节点依赖上一步全部出口；轨道内顺序依赖。
  2. _advance：在流程锁内，把所有「待开始 / 已打回」且依赖全部通过的节点开工；全部通过则流程完成。发起时与每个节点通过时调用。
  3. 开工：首次 → 锁文件模板版本与执行 Agent，排一条开工上下文（§7.2）；重开 → 排一条「上游已更新」指令（带新的上游产物）。
  4. 没有分配 Agent 或 Agent 不可用：节点照常进入协同中并给出提示，由人直接提交产物。

05评审：准出与准入

规则说明
打开轮次执行人「提交准出评审」→ 新建轮次：阶段、角色、规则、锁定的名单、针对的产物版本
投票名单中的人逐个「同意 / 驳回」，每人每轮一票；驳回必须写意见
通过任一人：第一张同意即通过；所有人：同意数 = 名单人数。准出通过且配置了准入 → 打开准入轮次；否则节点通过
驳回任一人驳回即驳回本轮（两种规则相同）
名单为空评审角色没有分配人：轮次照开并提示；分配后由执行人「重新提交评审」刷新名单

06驳回与打回

情形效果
驳回 · 本节点修改轮次 → 驳回；节点回到协同中（轮次 +1）；驳回意见作为指令排队发给 Agent
驳回 · 打回到上游节点只能选本节点的祖先。目标节点回到协同中（轮次 +1，沿用原锁定，意见发给其 Agent）；目标的所有下游里非「待开始」的节点 → 已打回（取消其打开的轮次）。目标重新通过后，下游按依赖重新开工

07Agent 适配层

7.1 映射

TeamFlowAtlas说明
节点会话thread首次投递时创建（标题「[TeamFlow] 流程 · 节点」），驳回 / 打回在同一会话继续
一条指令（人 / 系统）runPOST /v1/threads/{id}/runs，幂等键 = 消息 uuid，重启后重发不会变成两条
Agent 输出会话事件流GET /v1/threads/{id}/events?after_seq=游标；游标（thread_seq）存在节点上，断线 / 重启续传
服务身份X-User-Id固定 UUID（ATLAS_TF_ATLAS_USER_ID），TeamFlow 建的会话都归在它下面

7.2 开工上下文

你是流程「{流程名}」中节点「{节点名}」的执行者，需要产出「{产物名}」。
需求：{发起时的需求}
<file-template name="…" version="n"> 原文 </file-template>
<input name="{上游产物名}" version="n"> 内容 </input>（每个上游一段）
请先澄清不清楚的地方，再按文件模板产出，并对照模板自查。
★ 交付产物时，把产物全文放在 <artifact> 与 </artifact> 之间，每次修改都输出完整全文。

7.3 投递与跟随（监督器）

  1. 状态迁移只把指令写入 tf_node_message（status = queued），事务提交后唤醒监督器 —— 慢的 Atlas 调用不在流程锁里。
  2. 同一节点串行：没有运行中的 run 时取最早一条排队指令 → 建会话（如无）→ 建 run → 记 atlas_run_id，并插入一条 streaming 的 Agent 消息。
  3. 跟随事件流：message.delta 经广播推给页面（不落库）；message.completed 取正文；approval.required 提示去 Atlas 处理；终态（finished / failed / cancelled）→ 在流程锁内落库回复、清 run、存游标。
  4. 回复里有 <artifact> 且节点仍在协同中 → 提交产物版本（同一轮内容相同不重复提交）。
  5. 启动时续接：有运行中 run 的节点、有排队指令的节点。
无超时Agent 运行可能持续数十分钟：不设等待上限，断线只续传不判失败；连接错误时节点显示「正在重试」并按间隔重试。

08产物与仓库

gitee.com/{命名空间}/teamflow-{项目 uuid} ← 每个项目一个私有仓库（Gitee API 提交） 0001-支持手机号登录/ 01-需求分析/需求文档.md 02-架构设计/设计文档.md
规则说明
一次提交 = 一个版本Agent 交付或人工提交都 commit（Gitee contents 接口：新文件 POST、已有文件带 blob sha PUT；内容不变也产生 commit）
两种后端gitee（多实例必须，实例本地不存仓库）；local（本机 git CLI，单实例开发 / 测试）。接口相同：commit / read / web_url
凭据token 只放 .env（ATLAS_TF_GITEE_TOKEN），放在 Authorization 头而不是 URL；写入失败（网络、5xx、并发冲突）重试 3 次
提交信息标题「流程 · 节点 · 产物 vN」+ 说明 + 结尾 Process / Node / Round / By 四行，便于 git log 追溯
写入身份只有 TeamFlow（token 所属账号）写仓库，Agent 不持有凭据
库内缓存tf_artifact_version.content 缓存内容：预览、作为下游输入都不读 Git
路径用 uuid 而不是团队 / 项目名：改名不影响历史；流程、节点名经安全化（去路径分隔符）

09实时推送

GET /api/v1/processes/{id}/stream?after=游标（SSE）。先按游标回放 tf_process_event，再等进程内广播：

帧来源前端处理
event: process（带 id = seq）事件表；事务提交后 nudge 订阅方去库里取刷新流程与对应节点；断线浏览器带 Last-Event-ID 续传
event: delta监督器转发的 Agent 增量拼到「正在输出」
: ping15 秒心跳—

鉴权后立刻归还请求级数据库连接，之后每次取事件用短会话（SSE 可以挂很久）。

10待我处理

两类，查询得出（不另建索引表）：① 进行中流程里「协同中」的节点，且我在其执行角色的当前分配中；② 打开的评审轮次，我在锁定名单里（JSONB @>）且还没投票。结果按我仍可见的团队过滤。

11数据模型

表要点
tf_process项目内编号 no（项目行锁内分配）、标题、需求、锁定的模板版本、状态、发起人、event_seq（事件游标）
tf_process_nodenode_id、名称、冗余 exec_role、状态、轮次、锁定的文件模板版本与 Agent、Atlas 会话 / 运行 / 游标、提示、当前产物
tf_node_messagerole = user / agent / system；status = queued / streaming / done / failed；对应 run
tf_artifact_version节点内版本号、轮次、路径、commit、内容缓存、来源（agent / user）、提交人
tf_review_round阶段、轮次、角色、规则、锁定名单（JSON）、针对的产物、状态（open / passed / rejected / cancelled）
tf_vote每人每轮唯一；决定、意见、打回目标
tf_process_event(流程, seq) 唯一；类型、节点、操作人、数据 —— 只追加

主键约定同其它模块：自增 id + uuid 逻辑主键，关联一律用 uuid。

14并发与一致性

  • 所有改变流程状态的操作先 SELECT … FOR UPDATE 锁流程行；监督器落库 Agent 回复也拿同一把锁 —— 同一流程的推进串行。
  • 投票唯一约束 (轮次, 人)；重复投票返回 ALREADY_VOTED。
  • 事件 seq 在流程锁内递增；通知订阅方在事务提交后（SQLAlchemy after_commit），避免读到未提交数据。
  • Atlas run 用消息 uuid 做幂等键：建 run 后、记录 run id 前崩溃，重启重发返回同一个 run。

15异常与边界

情形处理
执行 Agent 未分配 / 不可用节点照常开工并提示；人可直接提交产物；不能下指令（NO_AGENT）
Atlas 运行失败 / 取消Agent 消息标失败，节点提示；人再发一条指令即重试
Atlas 暂不可用、事件流断开提示「正在重试」，按间隔重试；续传不判失败
Agent 在 Atlas 等待操作确认节点提示去 Atlas 会话处理（TeamFlow 不代批）
流程终止时 Agent 还在跑run 结束后回复照常落库，但不再提交产物、不再投递排队指令
评审期间 Agent 又交付了产物只在协同中提交产物；评审中的回复只记消息

16首版取舍

系统设计首版原因 / 以后
Redis 任务队列不用队列：指令在数据库排队；唤醒经 Redis 广播；节点租约锁 + 定期扫描保证只处理一次、崩溃可接管数据库是排队的唯一真相，少一层状态
GitLab / GiteaGitee API按要求使用 gitee.com
待办索引按条件查询数据量下足够；需要通知时再落索引
产物白名单 Markdown 渲染纯文本显示不执行任何内容，安全优先；P2 换渲染库
移除成员的阻塞项（锁定名单中未投票等）未检查后续补到团队成员移除流程

17测试要点

  • 端到端：发起 → Agent 交付（Git 有提交）→ 下指令修订 → 准出驳回（意见发给 Agent，新轮次）→ 准出通过 → 准入「所有人同意」→ 并行开工 → 汇合（两个上游作为输入）→ 打回到上游（下游已打回、旁路节点不受影响）→ 上游重新通过 → 下游重开 → 完成。
  • 权限：非执行人不能下指令、非名单不能投票、重复投票、非成员看不到、终止只限发起人 / Owner。
  • 异常：无 Agent 时人工提交；Agent 失败提示与恢复；流程终止后不能投票。
  • 并发：重复打开、同时投票由流程锁串行。
  • 真实环境：对 Atlas 实测 Agent 按 <artifact> 交付；重启后续接排队指令。

18多实例部署

进程说明
API（可多个）python -m atlas_teamflow serve；ATLAS_TF_EMBEDDED_WORKER 决定进程内是否也跑监督器（开着也安全）
Worker（可多个）python -m atlas_teamflow worker：只跑监督器，不接 HTTP
问题机制
同一节点被两个实例同时处理节点租约锁：SET {前缀}node-lock:{节点} token NX PX 30000；持有者每 10 秒续租（Lua 校验 token）；续不上（已被别人拿走）立即停止本实例的处理
唤醒只到达一个实例唤醒经 Redis 频道广播给全部实例，谁拿到租约谁干活；另有定期扫描（默认 15 秒）补漏
实例崩溃不再续租 → 租约 30 秒后过期 → 其他实例扫描时接手，从节点上存的游标续传 Atlas 事件流；Atlas run 带幂等键，不会重复下指令
页面连在 A，Agent 在 B 上跑事件通知与逐段输出都经 Redis 发布 / 订阅，每个 API 实例把收到的推给自己的 SSE 连接
团队级别缓存本实例立即失效，并广播给其他实例
租约不是超时租约只用来判断「处理者还活着」：持有者活着就一直续租，Agent 运行多久都可以。
