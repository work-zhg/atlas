AI TeamFlow · Detailed Design

产物仓库与 Agent 提交

产物由 Agent 自己提交到 Gitee：TeamFlow 不再写仓库，只负责建仓库、把仓库信息交给 Agent、在提交评审时锁定 commit（平时不跟踪仓库）。Agent 在 Atlas 会话 Pod 里用 git CLI clone / commit / push，凭据由 Atlas 的git 凭据档案以只读文件挂进 Pod，TeamFlow 与 Agent 上下文里都没有凭据；团队成员用自己的 Gitee 账号在本地 clone 查看，权限由 TeamFlow 按团队成员身份同步。本文替代 流程运行设计 §8「产物与仓库」 与 §7.3 中「提取 <artifact> 并提交」的部分。

Agent 提交，TeamFlow 不写仓库Pod 内 git CLI凭据档案挂载一个节点一个产物路径评审针对 commit成员用自己的 Gitee 账号

01背景与变化

现状：Agent 在 Atlas 会话里工作，可能把产物写进会话工作区（MinIO）；TeamFlow 另外从 Agent 的回复文本里提取 <artifact>…</artifact>，由 TeamFlow 提交到 Gitee。两条路互不知晓，会出现「工作区有、Gitee 没有」「两边内容不一致」「人工修订只进 Gitee、Agent 下一轮基于旧文件改」等问题（实测 7 个有产物的节点中只有 1 个在工作区有对应文件）。

项现状改为
谁提交产物TeamFlow（从回复文本提取后用自己的 token 提交）Agent（在会话 Pod 里 git commit / push）
产物的唯一来源两份：工作区文件 / Gitee 提交一份：Gitee 仓库里该节点的产物路径；工作区只是 Agent 的草稿区
TeamFlow 怎么知道有新版本自己提交的，当然知道不跟踪：平时看目录预览（仓库实时内容）；执行人提交准出评审时，锁定产物路径当时的最新提交为本次评审的版本
下游拿到的输入上游产物全文拼进开工上下文仓库 + 路径 + commit，Agent 用 git show 按需读取（顺带解决上下文过长）
人工修订TeamFlow 页面「手工提交产物」给 Agent 下指令修改（默认）；需要时团队管理员可用自己的 Gitee 账号提交，下次提交评审时一样会被锁定（§9.3）

02目标与范围

目标
  1. 产物只有一份，在 Gitee；每一次修改都是 Agent（或被授权的人）的一个 commit，可追溯到流程、节点、轮次、下指令的人。
  2. 凭据不进 Agent 上下文、不进 Atlas / TeamFlow 的库与配置；只有被授权的会话 Pod 以只读文件挂载，写入账号只能写 TeamFlow 的产物仓库（取舍见 §6.5）。
  3. 团队成员在本地用标准 git 工具查看产物，权限随团队成员身份自动增减。
  4. TeamFlow 的评审、驳回、打回、下游输入照常工作，评审针对的是确定的 commit。
不在范围代码类产物（编码节点改代码仓库、提 PR）—— 另行设计，本期编码节点仍产出 Markdown 交付说明；Gitee 企业版的组织 / 权限体系；GitLab / GitHub 适配（接口按「Git 托管平台」抽象，本期只实现 Gitee）。

03职责划分

TeamFlow

  • 项目创建时建产物仓库（或绑定已有仓库）
  • 节点开工时把仓库信息、产物路径、提交规范交给 Agent
  • 提供流程目录预览
  • 提交评审时锁定 commit、登记版本
  • 按团队成员同步仓库协作者
  • 不写仓库

Agent（Atlas）

  • 按指令读输入、写产物
  • 在会话 Pod 的 /repos 下 clone，git commit / push
  • 在回复里报告 commit
  • 工作区只作草稿

Atlas 平台

  • 会话记住 git 凭据档案（子会话继承）
  • atlas-cluster 校验档案授权
  • 把档案 Secret 只读挂进 Pod
  • 镜像内置 git

Gitee

  • 产物仓库（每项目一个，私有）
  • 机器人账号：仓库管理 + 写入
  • 成员：协作者（只读 / 可写）
  • OAuth：绑定成员账号

团队成员

  • 在 TeamFlow 绑定 Gitee 账号
  • 本地 clone / pull 查看
  • 在 TeamFlow 里给 Agent 下指令、评审

04总体方案

  1. TeamFlow项目创建：用机器人账号在 Gitee 建私有仓库 {命名空间}/teamflow-{项目}，把团队成员同步为协作者（§9）。
  2. TeamFlow节点开工：以 git 凭据档案 teamflow-gitee 建 Atlas 会话；开工上下文给出 <repository>（仓库、分支、本节点产物路径、上游产物的路径与 commit）、提交说明模板与 git 操作步骤，并检查执行 Agent 能否执行命令（§6.3、§7）。
  3. Atlas为会话建 Pod 时校验档案授权，把档案 Secret 只读挂到 /run/secrets/git，设置 GIT_CONFIG_GLOBAL（§6.2）。
  4. Agent在 Pod 里 git clone 到 /repos/…，用 git show 读上游产物，写本节点产物文件，git commit -F -（按模板，带 TeamFlow-Node 尾注）后 git push，回复中报告 commit。
  5. TeamFlowrun 结束只落库 Agent 回复，不访问仓库；成员在节点页的目录预览里看本流程目录的实时内容（§8.3）。
  6. 执行人提交准出评审：TeamFlow 读产物路径的最新 commit 与内容，登记为产物版本并锁定，评审与下游输入都指向它（§8.2）。
  7. 成员在 TeamFlow 评审（针对登记的 commit）；或在本地 git pull 查看历史与差异（§9）。
一句话改产物的只有 Agent（在 Pod 里用 git，凭据由平台挂载）；TeamFlow 只在提交评审时读一次仓库。产物的唯一事实来源是 Gitee 上该节点的产物路径。

4.1 一轮对话的时序

一轮 = 一条指令驱动一次 Atlas run。指令有两个来源：执行人在对话区发言（经代理直接发给 Atlas），或系统指令（开工、驳回意见、上游更新，先在 TeamFlow 库里排队，由监督器投递）。之后两条路相同：监督器跟随事件流到终态 → 收尾落库。run 过程中和结束时都不访问 Gitee；产物版本在执行人提交准出评审时才锁定（图末 ref 段）。

要点说明
一次只跑一个 run节点已有 atlas_run_id 时，执行人再发言返回 409 run_in_progress；系统指令排队，等前一个 run 结束再投递
谁跟随不论指令来源，都由监督器跟随到终态。多实例下靠节点租约锁保证一个节点只有一个实例在处理，实例挂掉后租约过期由其他实例接手
断线按 thread_seq 游标续传，不判失败（无超时原则）
产物从哪来只看 Gitee 提交，不解析回复文本：回复里贴了全文但没有 push，提交评审时会被拒绝（产物路径没有提交）
何时访问 Gitee只在提交准出评审时（锁外读最新提交与内容，再加锁登记），以及成员打开目录预览时
人工修订成员在本地推送后，下次提交评审锁定的就是他的提交（来源 user）；需要 Agent 基于它继续改时，由执行人在对话里告诉 Agent 先 git pull
Pod 冷启动会话的第一次 run 要等 atlas-cluster 建 Pod；档案未授权时 403，run 失败，节点上提示

05仓库模型

5.1 仓库与目录

项规则原因
仓库每个项目一个私有仓库：{命名空间}/teamflow-{项目 uuid}；仓库描述写「团队 / 项目」可读名称项目是产物归属的单位；用 uuid 命名，团队 / 项目改名不影响历史与链接
命名空间专用 Gitee 组织（推荐）或机器人账号个人空间，配置项 ATLAS_TF_GITEE_NAMESPACE组织便于统一管理协作者、转交所有权；写入账号只加入这个命名空间
分支只用默认分支 master每个节点写自己的路径，不会互相覆盖；文档类产物不需要分支合并
流程目录{流程编号 4 位}-{流程名}/浏览仓库时按流程聚合
产物路径{流程目录}/{节点序号 2 位}-{节点名}/{产物名}.md，由 TeamFlow 计算并下发，Agent 不自行决定一个节点一个路径：提交评审时锁定的就是这个路径的最新提交
附属文件同一节点目录下可写附属文件（图、附录），但产物以产物路径那一个文件为准评审与下游输入只看产物文件，附属文件随目录浏览
teamflow-01a11f87…/ ← 项目「账号体系升级」 0002-登录失败锁定提示/ 01-需求分析/需求文档.md 02-架构设计/设计文档.md 02-架构设计/时序图.png ← 附属文件 03-测试方案/测试方案.md 04-编码实现/代码.md

5.2 提交规范

TeamFlow 在开工上下文里下发提交说明模板，Agent 用 git commit -F - 按模板提交：

{流程名} · {节点名} · 第 {轮次} 轮

<一句话说明本次修改>   # Agent 填写

TeamFlow-Process: {流程 uuid}
TeamFlow-Node: {节点 id}
TeamFlow-Round: {轮次}
Agent: {Agent 名称}

结尾的 TeamFlow-* 是 git trailer，git log --format='%(trailers)' 可直接检索。提交评审时锁定的是产物路径上最新的提交（不看时间）；来源按尾注判定（带本节点 TeamFlow-Node → Agent）。

06Agent 访问 Gitee

6.1 方案对比

方案做法结论
C · Pod 内 git CLI（采用）会话 Pod 镜像内置 git；Atlas 按会话的 git 凭据档案把凭据以只读文件挂进 Pod，Agent 直接 clone / commit / push✅ 后续编码节点要在 Pod 里改项目代码、开分支、提 PR，git CLI 无法回避，产物提交与之共用一套机制；git 原生的历史、diff、rebase 都可用
A · 网关上的 Gitee 工具Higress 上定义 MCP 服务（REST → MCP）调 contents 接口，token 只在网关⏸ 凭据隔离最好，但只能整文件读写、要自己管 blob sha，改代码仓库时无法替代 git；不再作为主路径
B · Gitee 官方 MCP部署官方 mcp-gitee❌ 没有写文件 / 提交工具
D · TeamFlow Git 代理TeamFlow 代理 git smart HTTP 并注入 token⏸ TeamFlow 重新进入 Git 数据面，与「TeamFlow 不写仓库」相反；作为 §6.5 P2 的备选

6.2 凭据链路：git 凭据档案

  1. TeamFlow为节点建 Atlas 会话时带 git_profile=teamflow-gitee（配置项 ATLAS_TF_ATLAS_GIT_PROFILE）。TeamFlow 只知道档案名字，不持有写入凭据。
  2. Atlas会话记住 git_profile；子智能体会话（委派给 ACP CLI）继承父会话的档案。
  3. atlas-cluster建 Pod 前校验：档案存在于 ATLAS_CLUSTER_GIT_PROFILES，且会话所属用户在档案的 allowed_users 里（只允许 TeamFlow 的服务身份）；否则 403，不建 Pod。
  4. atlas-cluster把档案对应的 K8s Secret 只读挂到 /run/secrets/git（文件 0444），设置 GIT_CONFIG_GLOBAL=/run/secrets/git/gitconfig、GIT_TERMINAL_PROMPT=0；每个 Pod 另有 /repos 本地盘（emptyDir，有大小上限）放 clone。
# Secret teamflow-gitee-git（命名空间 atlas-sessions）
gitconfig:   [user] name = TeamFlow Agent / email = …
             [credential "https://gitee.com"] helper = "!f() { echo username=$(cat /run/secrets/git/username); echo password=$(cat /run/secrets/git/token); }; f"
username:    tf-writer
token:       ********
# atlas-cluster 配置
ATLAS_CLUSTER_GIT_PROFILES={"teamflow-gitee": {"secret": "teamflow-gitee-git", "allowed_users": ["{TeamFlow 服务身份 uuid}"]}}
  • 凭据不进环境变量（不会出现在进程环境、ACP 下发参数、日志里），也不进工作区（/workspace、/state 是对象存储挂载，会被预览 / 下载）。
  • clone 放 /repos（Pod 本地盘）而不是工作区：避免把 .git 同步到对象存储，Pod 回收即清理。

6.3 哪些 Agent 能提交

Agent 类型能否用 git说明
ACP 类 Agent（Pod 里的 CLI）✅直接在 Pod 里执行 git
原生 Agent + ACP 子智能体（如「开发协调者（委派 CLI）」）✅原生 Agent 把 git 操作委派给 ACP 子智能体；子会话继承档案
纯原生 Agent❌没有 shell。节点照常开工但提示「执行 Agent 不能执行命令…请更换分配」
前提检查TeamFlow 在节点开工时读取执行 Agent（Atlas GET /v1/agents/{id}）：kind=acp 或有 kind=acp 的子智能体才算能提交，否则在节点上提示。Agent 回复里贴了全文但没有提交 → 没有新版本，不能提交准出。

6.4 Pod 内的操作步骤（随开工上下文下发）

1. git clone {clone_url} /repos/{仓库名}      # 已 clone 过：cd … && git pull --rebase
2. git show {commit}:{path}                   # 读上游输入
3. 把产物全文写入 {产物路径}；只改本节点目录
4. git add -- '{节点目录}' && git commit -F - <<'EOF' … EOF   # 提交说明见 §5.2
   git push origin HEAD:master                # 被拒绝：先 git pull --rebase 再推
5. 回复中给出 commit 号与修改说明
※ 不要询问、打印或保存任何密码 / 令牌

并行节点写不同目录，pull --rebase 不会冲突；同一节点只有一个执行 Agent。

6.5 安全取舍

风险说明缓解
Agent 能读到令牌挂载的文件对 Pod 内进程可读，被提示注入的 Agent 可以 cat 出来（方案 A 没有这个问题，这是选 C 的代价）专用写入账号只加入产物仓库命名空间；档案只授权给 TeamFlow 服务身份的会话；指令要求不打印凭据；令牌定期轮换，泄露时吊销即全部下线
写到本项目其他节点 / 其他仓库同一账号对命名空间内的产物仓库都可写评审人在目录预览里能看到整个流程目录；Gitee 提交历史可追溯；默认分支开启保护（禁止强推）。自动拦截为 P2
其他用户的会话借用档案任何人建会话都可以填 git_profileatlas-cluster 按 allowed_users 校验，不在名单 → 403

P2：Atlas 为每个会话签发短期、限定仓库的令牌（或经网关换证 / TeamFlow Git 代理按节点限定路径），替代长期令牌文件。

07开工上下文里的仓库信息

TeamFlow 不再把上游产物全文和文件模板原文拼进上下文，改为给出位置，由 Agent 按需读取：

你是流程「登录失败锁定提示」中节点「架构设计」的执行者，需要产出「设计文档」。

<repository provider="gitee" clone="https://gitee.com/{ns}/teamflow-01a11f87….git" branch="master"
            web="https://gitee.com/{ns}/teamflow-01a11f87…">
  <output path="0002-登录失败锁定提示/02-架构设计/设计文档.md" />
  <input name="需求文档" path="0002-登录失败锁定提示/01-需求分析/需求文档.md" commit="7a742ff8af…" />
</repository>
<file-template name="设计文档模板" version="3"> …模板原文… </file-template>

以上游产物为输入；执行人可能在对话中补充要求，以执行人的说明为准。先澄清不清楚的地方，再按文件模板产出，并对照模板自查。
（没有上游的节点：开工时不投递；执行人第一次说明时，这段上下文与说明合成一条发出）

在命令行里操作产物仓库（git 凭据已由平台配置好，直接用 git；不要询问、打印或保存任何密码 / 令牌）：
{§6.4 的步骤，含本节点的提交说明}
如果你不能执行命令，请直接说明，不要只在回复里贴产物全文 —— 没有提交就没有产物。
场景下发内容
首次开工如上，输入按上游当前锁定版本的 commit 固定；没有上游的节点不立即投递，等执行人第一次说明时合成一条（不空跑）
驳回（本节点修改）驳回意见 + 新一轮的 git 步骤与提交说明（轮次 +1）
被打回 / 上游更新后重开新的 <input> commit + 「上游已更新，请基于新输入修订」+ git 步骤
文件模板仍内联原文（模板在 TeamFlow 里管理，不在产物仓库；≤ 100 KB）

08TeamFlow 如何看到产物

8.1 不跟踪提交

TeamFlow 不观察仓库：run 结束、运行过程中都不访问 Gitee，也不接收 WebHook、不定时扫描。原因：按时间窗查提交依赖客户端时钟（提交时间 ≠ 推送时间，rebase / 延迟推送会漏），而按 trace 解析 git 输出既不可信也不稳定；产物是否就绪由执行人判断，他看的是目录预览。

8.2 提交准出评审时锁定版本

  1. 执行人在目录预览里确认产物后，点「提交准出评审」。
  2. TeamFlow（不持有流程锁）读产物路径上的最新提交 commits?path=…&per_page=1，再读该提交里的产物全文。路径上没有提交 → NO_ARTIFACT。
  3. TeamFlow加流程锁：这个提交之前已经锁定过（驳回 / 打回后没有新提交）→ ARTIFACT_NOT_REVISED；否则登记产物版本（commit、作者、提交说明、内容快照），开评审轮次。
  • 一个产物版本 = 一次提交评审锁定的 commit；评审页、下游输入（<input commit=…>）、审计都指向它。评审期间仓库再有提交不影响本轮评审。
  • 来源：提交说明带本节点 TeamFlow-Node 尾注 → agent；作者是已绑定成员的 Gitee 账号 → user（记到对应成员）；其他 → unknown，标出提交人。
  • 内容快照存在 TeamFlow 库里，供离线查看与审计；以 Gitee 为准。

8.3 流程目录预览

  • 节点页「产物」页签：本流程目录（{流程编号}-{流程名}/）的文件树 + 文件预览，默认打开本节点产物。
  • 可切换查看「仓库最新（master）」或某次评审锁定的 commit。
  • 经 TeamFlow 后端用管理令牌读取：成员不必绑定 Gitee 账号；只开放本流程目录（路径不在流程目录下 → PATH_OUT_OF_PROCESS）。

09团队成员本地访问

9.1 绑定 Gitee 账号

  1. 成员在 TeamFlow 左下角「Gitee 账号」（/account）点「绑定」。
  2. TeamFlow生成一次性 state（HttpOnly Cookie，10 分钟），跳转 Gitee OAuth 授权页（scope 仅 user_info）。授权后 Gitee 回到前端页 /account/gitee，前端把 code / state 交给后端；后端校验 state、用授权码换取用户信息，得到 Gitee 用户名与 id（后端不需要知道自己的对外地址）。
  3. TeamFlow保存「用户中心用户 ↔ Gitee 账号」绑定（一对一），丢弃 OAuth 令牌，只为证明账号归属；随后按 §9.2 同步该成员在各项目仓库的协作者权限。

用 OAuth 而不是手填用户名：手填可以填别人的账号，等于把仓库访问权给了别人。OAuth 回调是浏览器跳转，本地部署（localhost）同样可用。

10权限与安全

10.1 凭据

凭据持有者权限用途
写入账号令牌K8s Secret（atlas-sessions 命名空间），经 git 凭据档案只读挂进被授权的会话 Pod写入账号仅是 TeamFlow 命名空间产物仓库的成员（可写）Agent 在 Pod 里 git push（§6.2）
仓库管理令牌只在 TeamFlow 后端（.env / Secret 的 ATLAS_TF_GITEE_TOKEN）命名空间管理员：建仓库、管理协作者、读提交§5 建仓库、§8 锁定版本与目录预览、§9 同步协作者；TeamFlow 不用它写文件（代码层面不提供写接口）
Gitee OAuth 应用TeamFlow 后端user_info§9.1 绑定账号；拿到的用户令牌立即丢弃
成员个人令牌 / SSH 密钥成员本人按协作者权限本地 clone / pull

Gitee 的个人访问令牌按账号授权、不能限定到单个仓库，所以「最小权限」靠：专用写入账号只加入产物仓库命名空间 + 档案只授权给 TeamFlow 的会话 + 事后核对（10.3）+ 分支保护。

10.2 威胁与对策

威胁对策
Agent 被提示注入，读出写入令牌可能（选 C 的代价，§6.5）：令牌只能写产物仓库；不进环境变量 / 工作区 / 日志；轮换与吊销；P2 换成会话级短期令牌
其他用户的 Atlas 会话使用 TeamFlow 的档案atlas-cluster 按档案的 allowed_users 拒绝（403）
Agent 写别人的仓库 / 非产物仓库写入账号不是其他仓库的成员
Agent 写本项目其他节点的产物（越界）P1 不自动核对（TeamFlow 不跟踪提交）：评审人在目录预览里能看到整个流程目录，Gitee 历史可追溯；P2：会话级令牌 / 代理按节点目录限定，或评审前核对锁定 commit 的改动范围
Agent 改写历史默认分支开启保护（禁止强推）；TeamFlow 已登记的版本有内容快照
成员离开团队仍可访问移出团队即删协作者；每日对账兜底
冒用他人 Gitee 账号绑定OAuth 证明归属（state 防 CSRF）；一个 Gitee 账号只能绑定一个用户

10.3 越界写入（已知取舍）

TeamFlow 不跟踪提交，因此不会自动发现 Agent 改了本节点目录以外的文件。依靠：写入账号只能写产物仓库、评审人在目录预览里看到整个流程目录、Gitee 历史可追溯、分支保护。需要自动拦截时做 P2（会话级限定令牌，或提交评审时核对锁定 commit 与上次版本之间的改动路径）。
