AI TeamFlow · System Design

AI TeamFlow 整体系统设计

让 AI Agent 作为团队成员，和人一起按规范流程把工作做完。团队把工作流程配置成模板；每个节点由人与 AI Agent 协同完成 —— 人下达指令、审核成果、必要时介入，Agent 执行并产出；审核通过自动流转到下一节点。所有产物以 Git 版本化留痕，从最初的需求到最终交付全程可追溯。

独立系统唯一外部依赖：Atlas AI Agent模块化单体 + Worker产物存 Git版本锁定保证在途稳定

01背景与目标

现状问题
网页聊天、Claude Code、Codex 等 AI 工具产出方便、有人把关，但过程无从追溯：指令怎么下的、依据什么产出、谁审过、改过几轮，都散落在个人会话里
Jira 等协同工具有流程、无执行：每一步的活仍然要人来干

AI TeamFlow 把两者合一：

按规范推进

团队把流程配置成模板：有哪些环节、谁负责、谁审核、产物长什么样。

每一步由 AI 执行

节点由人与 AI Agent 协同完成，Agent 以上游产物为输入继续工作。

人在关键节点把关

准出（产出方）与准入（下游）两道评审，支持「任一人 / 所有人同意」，可驳回、可打回。

全过程可审计

指令、Agent 产出、每个版本、每次评审都留痕，产物以 Git 管理。

02范围

本期（P1）团队管理（人、AI Agent、项目、角色分配）；流程模板（结构编辑、节点配置、版本）；文件模板（Markdown 规则文件）；流程运行（发起、人机协同、准出 / 准入评审、驳回 / 打回、自动流转）；产物 Git 管理与预览；审计；站内实时更新。
后续（P2+）AI 自动准出（按文件模板规则判定）；度量（环节耗时、返工率、AI 一次通过率）与工作台；IM / 邮件通知；评审转交；版本对比；团队自建模板。
不做Agent 的创建与配置（由 Atlas 负责）；通用项目管理（任务看板、工时）；代码托管平台本身（使用现有 Git 服务）。

概念含义详细设计

07领域模型

【组织】 Team ├─ TeamMember │ User + team_role ├─ TeamAgent │ atlas_agent_id └─ Project flow_template_id → 定义 └─ RoleAssignment role → User / TeamAgent
【定义】 FlowTemplate └─ FlowTemplateVersion definition：flow + nodes 节点的文件模板 id → FileTemplate FileTemplate └─ FileTemplateVersion Markdown 内容
【运行】 Process 锁定 FlowTemplateVersion └─ ProcessNode 状态、锁定的文件模板版本、 执行 Agent、评审人名单 ├─ AgentSession │ atlas_thread_id │ └─ Message ├─ ArtifactVersion │ git commit └─ ReviewRound └─ Vote

三类「定义」（流程模板、文件模板、角色分配）都可以随时修改；三类「运行」（流程、节点、评审轮次）在关键时刻锁定定义（§12），保证进行中的工作不被打乱。

08关键流程

8.1 配置：从团队到可发起流程

#谁做什么
1平台管理员维护流程模板与文件模板（或直接使用内置模板）
2平台管理员新建团队，指定团队管理员（写入团队 Owner）
3团队管理员添加成员（个人或部门，成员默认读写、团队管理员为 Owner，存于用户中心）；从 Atlas 已启用的 Agent 中接入团队 Agent
4团队管理员新建项目、绑定流程模板；在项目设置中为每个角色分配人和 Agent

8.2 运行：一个节点从开工到流转

#参与方动作
1成员在项目首页「发起流程」，填写一句话需求 → 流程运行模块锁定模板版本，起始节点开工
2流程运行节点开工：锁定文件模板版本与执行 Agent；Agent 适配层创建 Atlas 会话，发送开工上下文（节点指令 + 文件模板原文 + 上游产物 + 需求）
3人 ⇄ Agent在「人机协同」区对话：Agent 澄清问题、人回答与下达指令；Agent 的输出经事件流实时显示
4Agent / 人Agent 产出产物 → 产物模块提交到 Git（一个 commit = 一个版本）→ 人点击「提交准出评审」
5准出评审人锁定评审人名单；逐人「同意 / 驳回」。规则满足（任一人 / 所有人）→ 进入准入；任一人驳回 → 回到第 3 步，批注作为下一轮指令发给 Agent（或打回到更早节点）
6准入评审人同上；未配置准入时跳过
7流程运行节点「已通过」；所有依赖都已通过的下游节点自动开工（回到第 2 步），上游产物作为其输入；全部节点通过后流程完成

8.3 驳回与打回

情形效果
驳回 · 本节点修改节点回到人机协同中；本阶段同意记录清空；驳回批注作为指令发给 Agent；修改后重新提交准出（重新锁定评审人名单）
驳回 · 打回到更早节点本节点标记「已打回」；目标节点回到人机协同中（沿用其原锁定的模板版本）；目标节点重新通过后，依赖它的节点按依赖关系重新开工

09流程运行

流程运行模块是系统核心，下面给出边界与关键规则，细节在其详细设计中展开。

9.1 节点状态机

待开始 ──依赖全部通过──▶ 人机协同中 ──提交准出──▶ 待准出 ──规则满足──▶ 待准入 ──规则满足──▶ 已通过 ▲ │ 驳回 │ 驳回 └───────────────────────┴─────────────────────┘ （或打回到更早节点：本节点 → 已打回）

9.2 关键规则

规则说明
依赖与流转依赖由模板结构推导（顺序、并行开工、汇合）；节点通过时计算所有依赖已满足的下游节点并开工
并发控制同一流程的状态推进串行化（流程级锁）；投票等操作带乐观锁，重复提交幂等
待办索引维护「谁在等待处理什么」的索引（评审待投、协同中），支撑项目首页的「待我处理」与通知，不现场遍历流程
事件每次状态变化写入流程事件表（审计 + 实时推送的共同来源）
无超时人机协同与评审都没有等待上限，不会到点自动通过或驳回

10Agent 接入（Atlas）

Atlas 是 TeamFlow 唯一的外部能力依赖，只使用其 AI Agent 能力。所有交互经过 Agent 适配层，业务模块不直接调用 Atlas。

TeamFlowAtlas说明
团队 AgentAgent（id）团队接入时只保存 Atlas Agent id 与快照；定期同步可用状态
节点会话会话（thread）节点开工时创建，一个节点一个会话；驳回后在同一会话中继续，保留上下文
人的一条指令一次运行（run）人在人机协同区发送消息 → 在该会话上发起运行
Agent 输出 / 进度事件流Worker 订阅事件流，落库为消息并经 SSE 推给页面；断线按游标续传

10.1 开工上下文

# Agent 适配层组装的首条消息（示意）
你是流程「{流程名}」中节点「{节点名}」的执行者，需要产出「{产物名}」。
需求：{发起时的一句话需求}
<file-template name="{文件模板名}" version="{n}"> {Markdown 原文} </file-template>
<input name="{上游产物名}" version="{commit}"> {上游产物内容} </input>   （每个上游一段）
请先澄清不清楚的地方，再按文件模板产出，并对照模板自查。
规则说明
驳回后把驳回批注作为新一条指令发到同一会话
产物提取约定 Agent 用固定标记输出产物全文（或调用「提交产物」工具，视 Atlas 能力而定），适配层识别后交给产物模块提交 Git
失败与断线Atlas 运行失败时，节点停在人机协同中并提示；事件流断线由 Worker 按游标续传，不判失败
Agent 不可用节点开工时执行 Agent 不可用 → 节点停在人机协同中，提示团队管理员更换分配

11产物与 Git

仓库：{team-slug}/{project-slug} （每个项目一个仓库） {process-id}-{流程名}/ 01-需求澄清/需求澄清纪要.md 02-PRD/PRD.md 03-技术方案/技术方案.md ...
规则说明
一次提交 = 一个版本Agent 每次产出（含驳回后的修改）提交一个 commit；commit 信息包含流程、节点、轮次、提交人 / Agent
格式产物统一为 Markdown（与文件模板一致），便于预览、对比与作为下游输入
评审关联每轮评审记录其针对的 commit；批注与投票存于数据库，并以 git note 或审计记录关联到该 commit
写入方式只有 TeamFlow（服务账号）写仓库；Git 服务不可用时提交进入 Worker 重试队列，节点暂不能提交准出
读取产物列表、版本、内容与差异由产物模块从 Git 读取并缓存

12版本与锁定

「定义可以随时改，进行中的工作不被打乱」是贯穿全系统的规则：

锁定什么何时锁定之后定义变化的影响
流程模板版本流程发起时模板再发布不影响该流程
文件模板版本节点开工时模板再上传不影响该节点（驳回修改、被打回也不重新锁定）
执行 Agent节点开工时项目改分配不影响该节点
评审人名单节点进入待准出 / 待准入时本轮评审人数不变；驳回重提后用新名单

13实时与通知

能力设计
流程详情实时更新页面订阅流程事件的 SSE：Agent 输出逐段显示、投票与状态变化即时刷新；带游标续传，刷新页面不丢事件
多实例推送事件写库后经 Redis 广播到各 API 实例，再推给各自的 SSE 连接
待我处理由待办索引驱动；项目首页与流程卡片显示标记
通知（P2）待办产生时推送 IM / 邮件，带直达流程的链接

14安全与权限

项设计
认证账号来自用户中心：本期 TeamFlow 自行登录并按账号与用户中心对齐，登录后取授权快照；以后统一由 Keycloak 登录。TeamFlow 不保存密码
授权三个角色（平台管理员管模板、团队管理员配置团队项目、团队成员处理流程）+ 团队数据权限（每个团队一条：成员读写、团队管理员 Owner）+ 流程角色分配（决定能否协同与评审）。详见权限设计
数据隔离团队是数据边界：对团队没有权限的人看不到其项目、流程与产物；接口按用户中心返回的团队级别过滤
服务凭据访问 Atlas 与 Git 使用服务账号；凭据存于密钥管理，不进代码与配置文件
内容安全产物与模板一律按纯文本 / 白名单 Markdown 渲染，不执行脚本、不加载外链资源
Agent 边界Agent 只能读到开工上下文与会话内容；写 Git 只经 TeamFlow，Agent 不直接持有仓库凭据

15审计与追溯

「过程可追溯」是产品的核心价值之一。任何一份产物都能回答：

问题来源
依据哪版流程与规则产出？流程锁定的模板版本、节点锁定的文件模板版本
指令怎么下的、Agent 怎么回应？节点会话的消息记录（人机协同全文）
改过几轮、每轮改了什么？Git commit 历史与差异
谁审过、意见是什么？评审轮次与投票、批注（关联到 commit）
配置被谁改过？模板、项目、角色分配的审计日志

审计日志与业务写入同一事务；只追加、不修改；保留期按企业合规要求配置（默认 3 年）。

16非功能

项目标
规模团队数百、成员数千、并发进行中的流程数千、单项目流程数万
性能普通页面接口 P95 < 300 ms；项目首页首屏 P95 < 500 ms；Agent 输出到页面的延迟 < 1 s（不含 Agent 自身耗时）
可用性99.9%（工作时间）；Atlas 或 Git 短时不可用时，查看与评审不受影响，开工 / 提交排队重试
长任务Agent 运行可能持续数十分钟：运行状态与事件全部持久化，服务重启后由 Worker 续接，不判失败
可观测结构化日志 + 链路追踪（请求 → 流程 → Atlas 调用）；关键指标：进行中节点数、Atlas 调用耗时与失败率、Git 提交队列长度、待办积压
