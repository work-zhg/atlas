AI TeamFlow · Detailed Design

流程上下文与 Agent 记忆

一个流程有一些每个节点都需要知道的固定内容（这个流程要做什么、项目的约定、过程中定下的决策），而每个节点的 Agent 可以不同、会话互不相通。本文规划 TeamFlow 调用 Atlas 时的记忆：流程上下文由 TeamFlow 持有（可审阅、有版本、与哪个 Agent 无关），每次向节点投递时按需带上；Atlas 的用户记忆对 TeamFlow 会话关闭（它按人划分、自动抽取，放在共享服务身份下会跨团队串味）；长期由 Atlas 提供会话固定上下文承载，不占对话历史、不怕压缩。

上下文归 TeamFlow与 Agent 无关不空跑有版本、可审阅关闭 Atlas 用户记忆

01问题与现状

现状问题
一个节点一个 Atlas 会话；不同节点可以分配不同的 Agent会话之间没有共享的上下文：n2 的 Agent 不知道 n1 的执行人最初说了什么，也不知道评审时定下的约束
节点之间只靠产物交接（仓库路径 + commit）产物是结论，不是全部：「为什么这么定」「哪些是硬约束」常常只在对话或评审意见里
发起流程只填名称（流程运行 §7.2），要做什么在第一个节点的对话里说流程的发起意图只存在于第一个节点的会话里，下游看不到
项目级的约定（技术栈、规范、术语）没有地方放每个节点的执行人都要重复交代，或者 Agent 各自猜
Atlas 开着用户记忆（Mem0，MEMORY_ENABLED=true）；TeamFlow 所有会话都用同一个服务身份（ATLAS_TF_ATLAS_USER_ID）跨团队 / 跨项目串味：记忆只按用户划分，检索只按 user_id 过滤（memory/client.py）。A 团队会话里抽取的「事实」会被注入或检索到 B 团队的节点里（§6）
长会话会被压缩（Atlas 发出 context.compacted；ACP CLI 也会自行压缩）开工时给的上下文可能被摘要掉，Agent 后面「忘了」项目约定

02目标与范围

目标
  1. 流程级的固定内容只维护一份，每个节点（不论哪个 Agent）都能拿到同一版本。
  2. 内容由人维护、可审阅、有版本和来源，不靠模型自动抽取。
  3. 内容变化后，进行中的节点在下一次投递时拿到更新 —— 不为了同步上下文单独启动 Agent（不空跑）。
  4. 会话压缩后能补回，不会「忘了」。
  5. TeamFlow 的会话之间不通过 Atlas 用户记忆互相影响。
不在范围跨项目的组织知识库（RAG）；Agent 自主写记忆；把对话自动提炼成流程上下文（P2 以后再评估）。

04流程上下文的内容

流程概况 自动

流程名称、模板版本、流程结构、本节点位置与上下游、各节点执行角色。TeamFlow 生成，不可编辑。

项目上下文 项目级

项目背景、技术栈、规范、术语。团队管理员在项目设置维护，所有流程共享。

流程说明 流程级

这个流程要做什么（发起意图）。默认取第一个节点执行人的第一条说明，可修改。

流程备忘 流程级

过程中定下、后续节点必须遵守的决策与约束；每条带来源节点与作者。
块谁写何时产生 / 变化例子
流程概况TeamFlow每次投递时按当前状态生成「n1 需求分析 → (n2 架构设计 ∥ n3 测试方案) → n4 编码实现；你在 n2，上游 n1，下游 n4」
项目上下文团队管理员项目设置里编辑；对进行中的流程，下次投递时生效「后端 Java 17 + Spring Boot；接口遵循《开放接口规范 v2》；手机号统一 E.164」
流程说明第一个节点执行人（第一条说明时勾选「同时作为流程说明」，默认勾选）；发起人、团队管理员可改第一条说明时写入；之后人工修改「同一手机号 1 分钟最多 1 次验证码，1 小时最多 5 次，超限提示等待时间」
流程备忘任一节点执行人；评审人投票时勾选「写入流程备忘」；团队管理员随时追加；作者或团队管理员可删除「[n1 评审 · 李工] 采用滑动窗口、拒绝不计次」
不放进流程上下文产物全文（走仓库输入，避免两份不一致）；对话细节；凭据与令牌（保存时提示）。

05注入方式（P1：只改 TeamFlow）

5.1 格式

<process-context version="p3.f5">
<overview>流程「登录验证码限流」（标准研发流程 v1.0）
n1 需求分析 → (n2 架构设计 ∥ n3 测试方案) → n4 编码实现；你在 n2（执行角色：架构师），上游 n1，下游 n4</overview>
<project version="3">后端 Java 17 + Spring Boot；接口遵循《开放接口规范 v2》……</project>
<brief>同一手机号 1 分钟最多 1 次验证码……</brief>
<notes>
- [n1 评审 · 李工] 采用滑动窗口、拒绝不计次
- [n2 · 何超] 计数存 Redis，key 前缀 login:otp:
</notes>
</process-context>
以上是团队维护的流程上下文，所有节点共享。冲突时：执行人在本节点的最新说明 > 流程备忘 > 流程说明 > 项目上下文。

version = 项目上下文版本 + 流程上下文版本（流程说明或备忘任何变化都 +1）。

5.2 何时带上

时机带什么说明
节点第一次投递（开工上下文；没有上游的节点是与执行人第一条说明合成的那条）全文放在开工上下文最前面
上下文版本变化后，该节点的下一次投递「流程上下文已更新（p3.f4 → p3.f5）」+ 全文前置在那条指令前；不为同步上下文单独发起 run（不空跑）
该节点会话收到 context.compacted 后的下一次投递全文压缩可能把早先的上下文摘要掉；监督器跟随事件流时打标记
其他投递不带上下文已经在会话里，重复只浪费 token
  1. TeamFlow任一来源排队给节点的消息（执行人指令、驳回 / 打回、上游更新）在入队时检查：节点已发送的版本 ≠ 当前版本，或节点被标记「已压缩」→ 前置上下文。
  2. TeamFlow入队成功后记下 context_sent = 当前版本、清除压缩标记（与消息同一事务）。
  3. 监督器跟随会话事件流时遇到 context.compacted → 节点 context_stale = true。

5.3 为什么与「哪个 Agent」无关

  • 内容存在 TeamFlow，每个节点会话从同一份内容开始；Agent 是谁、是原生还是 ACP、换没换模型，都不影响。
  • 节点的执行 Agent 在首次开工时锁定（流程运行 §3）；节点内不会中途换 Agent，所以「本节点会话里已经有上下文」是成立的。
  • 纯文本注入对原生 Agent 和 ACP CLI 都适用，不依赖任何一方的私有记忆机制。

5.4 大小预算

块上限超限时
项目上下文4,000 字保存时拒绝，提示精简或改为放进仓库文档后引用路径
流程说明4,000 字同上
流程备忘单条 500 字，合计 6,000 字拒绝追加，提示整理（合并 / 删除过时条目）

上限保证每次全文注入的成本可控（约 1 万字以内），也逼着内容保持「必须遵守的要点」，长文档放仓库。

06Atlas 用户记忆的处理（P0）

6.1 现状风险

环节行为（代码事实）对 TeamFlow 的后果
写入每个 run 完成后，从会话消息抽取，user_id = 会话所有者，metadata 记 workspace（父会话 id）所有团队、所有项目的节点对话都抽取进同一个用户（TeamFlow 服务身份）的记忆
读取检索只按 user_id 过滤（memory/client.py 的 search）；原生 Agent 挂 search_memory 工具A 团队会话里抽出的「事实」会被 B 团队节点检索到、当作背景使用
性质自动抽取、模型判断「值得记」不权威、不可审阅，与流程上下文「人写、有版本」的要求相反

6.2 方案：TeamFlow 会话关闭用户记忆

  1. AtlasPOST /v1/threads 新增 memory: "off"（默认 "on"，保存在会话上，子会话继承）。关闭时：不抽取、不注入、不挂检索工具。
  2. TeamFlow建节点会话时传 memory: "off"（与 git_profile 同一处）。
  3. 运维清理已经在 TeamFlow 服务身份下抽取的记忆（按用户批量删除，记忆管理 §10 的 bulk-delete）。
备选结论
按团队 / 流程设 workspace，检索时加 workspace 过滤❌ 能止住串味，但仍是自动抽取、不可审阅；且需要改 Atlas 检索逻辑。流程上下文已经覆盖了需求
每个团队一个 Atlas 服务身份❌ 身份管理复杂（会话归属、配额、Pod 授权都要跟着变），收益只是记忆隔离
用 Atlas 记忆承载流程上下文❌ 按人划分、自动抽取、ACP 只能按需检索，不满足「每个节点都拿到同一版本」

07会话固定上下文（P2：Atlas 能力）

P1 的注入是「消息里带上」：会占对话历史，压缩后要补发。更好的载体是 Atlas 提供会话级的固定上下文：

项原生 AgentACP CLI
设置POST /v1/threads 带 pinned_context；PATCH /v1/threads/{id} 更新（带版本号，只增不减地记录历史）
怎么生效每轮拼在系统提示词之后（模型请求层，不进 Message、不参与压缩），始终最新首轮前置；同时写入会话工作区的说明文件（如 AGENTS.md / CLAUDE.md），CLI 压缩后会自动重读
更新后下一轮自动是新内容下一轮前置一段「固定上下文已更新」+ 重写说明文件

有了它，TeamFlow 把 §5 的「前置拼接」换成 PATCH 会话的固定上下文：内容变化时更新所有进行中节点的会话即可，不再关心压缩与投递时机。P1 的数据与界面不变。

依赖需要 Atlas 增加会话固定上下文与工作区写文件能力（当前只有列出 / 预览 / 下载）。在 Atlas 侧单独设计，本文只定接口形态。

08界面

位置内容
流程页 ·「流程上下文」页签当前版本的全文预览（与注入给 Agent 的一致）；编辑流程说明；追加 / 删除备忘；版本历史（谁、何时、改了什么）
节点页 · 侧边卡片本节点已拿到的上下文版本；落后于当前版本时提示「下次给 Agent 发指令时会带上新内容」
第一个节点 · 第一次说明的输入框勾选「同时作为流程说明（所有节点可见）」，默认勾选
评审投票勾选「写入流程备忘」：把意见作为一条备忘（来源 = 节点 + 评审轮次）
项目设置 ·「项目上下文」卡片团队管理员编辑；显示版本与最近修改人

09权限

操作谁可以
查看流程上下文团队成员（与查看流程相同）
编辑流程说明发起人、团队管理员、第一个节点的执行人；流程进行中
追加备忘任一节点的执行人；评审人（投票时）；团队管理员；流程进行中

所有修改记审计。流程上下文由团队成员写入，信任级别等同执行人的指令（不是外部不可信文本），但 Agent 仍须遵守平台的安全约束。

10数据模型

表字段
tf_project新增 context（项目上下文正文）、context_version
tf_process新增 brief（流程说明）、context_version（说明或备忘变化 +1）
tf_process_note（新）process_uuid、content、source_node、source（manual / review）、review_uuid、author_uuid、created_at、deleted_at（软删，保留历史）
tf_context_revision（新）每次修改一行：范围（project / process）、对象 uuid、新版本号、变更类型（brief / note_add / note_delete / project）、前后内容摘要、操作人、时间 —— 版本历史与审计用

12异常与边界

情形处理
节点经人机协同代理（对话组件）直接发指令代理在转发前同样检查版本，必要时把上下文前置到这条消息（与排队路径一致）
上下文更新时 Agent 正在运行不打断；本轮结束后下一次投递带上
项目上下文在流程进行中被修改进行中节点下一次投递时更新；已完成的节点不受影响（历史投递保留当时版本）
打回重开 / 上游更新重开重开指令按当前版本判断，落后则前置
流程已完成 / 终止上下文只读
内容里出现疑似令牌 / 密码保存前提示（与 Gitee 令牌同类正则），不阻止
备忘与执行人最新说明冲突按 §5.1 的优先级；执行人可删除过时备忘或追加新的
