1. 要解决什么问题

原生智能体勾了「Shell」之后多一个 execute 工具：模型给一行命令，平台在隔离环境里跑完，把输出交回去。 这件事放进真实环境，要同时满足：

要求意思
和工作区是同一份数据文件工具写的，命令读得到；命令写的，文件工具读得到。工作区在对象存储上，不在某台机器的磁盘上
按需、会话级多数会话用不到 Shell，不能一建会话就起 Pod；一个会话（连同它的子智能体）共用一个环境，装的依赖、起的服务下一条命令还在
不设时长上限编译、测试、数据处理常常跑几十分钟。只要还在干活就不中断，只处理真正卡死的
断联不丢不重server 发布、崩溃、网络抖一下，命令照跑；接回来的输出不丢也不重复，命令也不能被再跑一遍（副作用会发生两次）
默认安全server 没有 K8s 权限；命令所在的容器里没有任何凭据；Pod 的接口要令牌
失败可恢复Pod 起不来、配额满、执行中途 Pod 没了 —— 模型要看到原因并能换个办法，而不是整轮失败

做法：每个会话一个 Pod，第一次 execute 时才建；Pod 里跑平台自己的守护进程 sandboxd，server 经 HTTP 让它执行命令， 事件按序号流回来。命令属于 sandboxd、不属于那条连接，所以断线、server 崩溃都只是「接上」；只有 Pod 本身没了才算丢失。

run用户说演示什么

③ 三个标识

标识是什么用来干什么
exec_id{run_id}:{tool_call_id}，如 r2:c7幂等键：同一个 id 再来一次是「接上」，不是「再跑一遍」
seq每条命令内从 1 递增的事件序号游标：重连带 after = 见过的最后一个 seq，接着给，不丢不重
boot_idsandboxd 启动时随机生成变了 = Pod 重建过：重连时 expect_boot_id 对不上就 409；工具结果前提示「环境已重建」

④ 屏障：文件和命令之间的两个缓存窗口

文件工具经对象存储 API 读写，命令经 rclone FUSE 挂载读写同一个前缀。挂载器有缓存： 读方向有 dir-cache-time（5 秒；设计文档 §7.1 实测窗口内读到的是「新内容按旧长度截断」的错数据）， 写方向有 --vfs-write-back（1 秒 + 上传耗时）。sandboxd 在每条命令的边界上收口：

时机做什么保证什么
执行前经 barrier 调 rclone 的 vfs/forget文件工具刚写的，命令看得到
执行后经 barrier 轮询 vfs/queue 直到为空，才发 exited{flushed: true}命令刚写的，文件工具读得到

3. 核心思路：一句话 + 四个要点

一句话：模型的 execute 经 PodSandbox 变成一次 POST /v1/execs（exec_id = run_id:tool_call_id）， Pod 里的 sandboxd 用 bash 在独立进程组里执行，把事件按 seq 流回来。命令的生命周期属于 sandboxd，不属于连接： 断线、server 崩溃都只是带着 exec_id 和游标「接上」；只有 Pod 本身没了（boot_id 变了）才算丢失，而那也只是一个工具错误。

要点 1：命令属于 sandboxd，不属于连接

K8s exec API 把命令绑在那条连接上，连接断了命令就没了。sandboxd 把命令登记在自己的表里（按 exec_id），事件按 seq 存下来， 连接只是一个「订阅」：断了可以再订，换个 server 实例也可以订。r2 网络断了一下、r6 server 崩溃，命令都只跑了一次（ran.log 5 行、pack.log 6 行）。

要点 2：文件与命令走两条路，在执行边界上对齐

文件工具不经过沙箱（没有沙箱的会话照样能用，读个文件也不必起 Pod）。代价是两条路之间有缓存窗口，所以屏障放在每条命令的开始和结束： r1 里 c3/c4 用文件工具写 count.py，c5 执行前 forget 让命令看得到；c5 写的 top.txt 等写回之后，c6 的 read_file 才读得到。

要点 3：不设时长上限，但每一种「停」都有明确的主人

谁什么时候停demo 里
模型自己给了 timeout：sandboxd 内部计时，到点结束进程组r2:c10 死循环一直有输出，1 秒到点结束（exit 143，timed_out）
sandboxd静默卡死：连续 N 秒既没有输出、进程组的 CPU 时间也没涨r2:c9 sleep 30 0.6 秒判卡死；r2:c8 安静地算 1 秒，CPU 在涨，不算
用户取消这一轮：server 通知 sandboxd 结束这条命令的进程组r3:c13 编译中取消，shell 和它起的子进程一个不剩
cluster闲置回收：没有命令在跑且闲置超过阈值r3 编译中「有 1 条命令在跑 → 不回收」；r3 之后回收

要点 4：沙箱的任何故障都是工具错误，不是整轮失败

故障模型看到的
配额满（实验 9）Error: Sandbox unavailable. 沙箱启动失败：该用户已有 N 个会话 Pod（上限 N）…
执行中 Pod 没了（r5:c15）Error: Sandbox unavailable. 沙箱在命令执行期间重启（可能内存不足或被回收），命令已中断、结果丢失；/workspace 内已写入的文件仍在
Pod 在两条命令之间重建过（r4:c14、r5:c16）结果前多一行 [沙箱环境已重建：/workspace 内的文件仍在；装进 HOME 的依赖、后台进程已丢失]
命令自己失败 / 被结束输出 + [Command failed with exit code 143] + 原因（卡死 / 超时 / 已取消）

6. 一条命令的一生、一个 Pod 的一生

6.1 r2:c7 的事件流：网络在 seq 3 之后断了一下

seq事件第一条连接重连（after=3）
1started {pid, boot_id}收到；记下 boot_id—
2output "case 1 ok"收到—
3output "case 2 ok"收到，随后连接断开（RemoteProtocolError）—
PodSandbox：退避 → 重新 ensure → POST {exec_id: r2:c7, after: 3, expect_boot_id}；sandboxd：「已存在（running）→ 接上，不重跑」
4–6output "case 3/4/5 ok"、"ran.log 共 5 行"收到，从 4 开始，不重复
7…flushing {pending: 1}收到（ran.log 在写回队列里；队列长度每变一次发一条，所以有一到两条）
最后exited {exit_code: 0, flushed: true}收到 → 工具结果

交给模型的输出不是把 output 事件拼起来，而是 exited.output：sandboxd 自己攒的头尾各一半（demo 4000 字节，Atlas 100 KB），中间写明省略了多少、完整输出在哪个日志文件里（r2:c11 的 seq 1 30000 输出 168894 字节）。 output 事件只用来显示进度，所以游标断了最多影响进度条，不影响结果。

7. 几个「为什么」

7.1 为什么不用 K8s exec API，而在 Pod 里跑自己的守护进程？

K8s exec APIsandboxd（设计 D2）
权限server 要有 pods/exec 权限server 不碰 K8s，只拿 cluster 交出的「地址 + per-Pod 令牌」
连接断了命令跟着那条连接没了命令照跑，按 exec_id + after 接上
幂等做不到：每次 exec 都是新进程同一个 exec_id 再来是接上
进程管理自己拼 timeout、setsid进程组、卡死判定、截断、日志、并发上限都在守护进程里
镜像—init 容器把自带解释器的 sandboxd 拷进共享盘，主容器可以是任意 glibc 镜像（评测用题目自带的镜像）

7.2 为什么 Pod 按需建、ensure 还要串行？

  • 按需：多数会话用不到 Shell。r1 前两批之前没有任何 Pod，模型只是第一次 execute 慢了冷启动那么久。
  • 幂等：名字由 workspace_thread_id 派生，Pod 在就复用。复用时令牌从 Secret 读回，不重签：Pod 里注入的是 Secret 里那份，换一个就对不上。
  • 串行：一批并行的 execute 在 Pod 还不存在时同时到达。实验 3 去掉锁：两个 ensure 各签一个令牌、先后覆盖写同一个 Secret，只有一个建出 Pod， 而 Pod 启动时读到的是后写的那份 —— 建 Pod 的 c1 手里的令牌反而对不上，固定 401。这是 2026-10-13 评测真实撞到的问题。
  • 等就绪才返回：Pod 还在 ContainerCreating 时就交出地址，第一次连接必然失败，而且看起来像网络问题。

7.3 为什么文件工具不经过沙箱？屏障又是为了什么？

文件工具直连对象存储（契约拆分：沙箱只管执行）。好处是没有沙箱的会话照样能读写文件，也不用为读一个文件起 Pod；代价是两条路之间有缓存窗口，后果很隐蔽：

实验去掉什么结果
1执行前的 forgetc5 python3: can't open file '…/count.py'，exit 2。文件工具明明刚写过
2执行后的等写回c5 正常输出了统计结果，紧接着 c6 read_file top.txt：「文件不存在」。命令成功了，产物却读不到

真实情况比实验 1 更糟：rclone 过了 dir-cache-time 会自己去看，窗口内读到的是「新内容按旧长度截断」—— 不报错，只是跑了半截旧代码，最难排查。 屏障只覆盖「文件工具 ↔ 命令」之间；后台进程在命令结束之后写的文件，按 rclone 自己的窗口最终一致。

7.4 为什么 rclone 的远程控制口令不能给 sandboxd？

forget 和查写回队列都要调 rclone 的远程控制（rc）。但 rc 还能调 operations/*、config/*，等于挂载器手里的整桶凭据。 sandboxd 和命令是同一个用户、同一个容器，sandboxd 能读到的文件命令都能读到 —— 容器边界是唯一可靠的隔离。所以： 口令只注入挂载器和 barrier 两个 sidecar；barrier 对外只有 forget 和 queue 两个无害操作；sandboxd 只认 barrier。 demo 里「容器边界」就是对象引用：ExecManager 手里只有 Barrier，没有 FuseMount，也没有口令。

7.5 为什么 exec_id = run_id:tool_call_id，重连还是 POST 同一个 id？

  • 不需要单独的 attach 接口：首发和重连是同一个请求。客户端不用判断「上次发出去没有」—— 没开始就开始，开始了就接上。
  • tool_call_id 是天然的幂等键：同一个调用不管被谁、被重放几次，都对应同一条命令。前面加 run_id，因为 tool_call_id 只在一个会话里唯一，regenerate 产生的新 run 应该重新执行。
  • after 是游标：r2:c7 重连带 after=3，从 #4 接着给，输出不丢不重；ran.log 5 行说明命令只跑了一次。

7.6 server 崩溃后的重放：前提是什么？

r6 里实例 A 在 c17 执行中崩溃。实例 B 接管、重放这一轮，模型发出的还是 c17，exec_id 还是 r6:c17，于是 sandboxd「已存在 → 接上」，从 #1 回放，pack.log 6 行。

前提：重放的必须是同一个 tool_call。demo 的假模型是确定性的，同样的历史给出同样的 id，相当于「那条 ai 消息在执行工具之前已经落库」。 真实模型重新调用一次，tool_call id 一定是新的。实验 4 模拟这一点：B 发出的 c17-5889 ≠ A 的 c17-b9c6，sandboxd 当成新命令， 两条同时在跑，pack.log 12 行。而 Atlas 水平扩展设计 §5.1 写的恰恰是「工具执行中被接管：这一轮的 tool_use 没有落库，整轮作废，重新调用模型」—— 和沙箱设计 §11「server 重启 → 重放同一个 tool_call → 接上」的前提冲突。详见 §11。

demo 怎么模拟崩溃：InstanceCrashed 继承 BaseException，在 A 读流的下一个数据块处抛出。任何 except Exception（PodSandbox 的重连、中间件的错误转换）都接不住它， 取消路径也不会走（所以不会发 kill）；只有 async with 的收尾会跑 —— 相当于操作系统替死掉的进程关掉连接。sandboxd 那边只看到「事件流断开（对端不在了）→ 命令照跑」。

7.7 为什么重连要带 expect_boot_id？

r5:c15 执行到一半 Pod 被删，PodSandbox 重连时 ensure 已经建好了新 Pod。新的 sandboxd 不认识 r5:c15 —— 如果它照「没开始就开始」处理，命令会在新 Pod 上从头再跑一遍。 带上见过的 boot_id，sandboxd 发现「对端见过 boot X，我是 Y，也不认识这条命令」，回 409；PodSandbox 转成工具错误，让模型决定要不要重跑（r5:c16）。

实验 5 去掉它：命令在新 Pod 上悄悄又跑了一遍，模型读到的是「环境已重建 + 成功」，完全不知道跑了两遍。还有一个连带问题：客户端带着旧命令的游标 after=4 去读新命令的流，新命令的 #1–#10 全被跳过，进度一条都看不到。 boot_id 同时用于提示：PodSandbox 在进程内记住每个工作区最近见到的 boot_id，变了就在结果前加「环境已重建」，r4:c14、r5:c16 都有。

7.8 为什么不设时长上限？卡死为什么要同时看输出和 CPU？

「只要在干活就不中断」是平台原则：编译、测试常常几十分钟，任何固定上限都会误杀。真正要处理的是卡死（等网络、等锁、死等输入），它的特征是既没有输出、进程组的 CPU 时间也不涨：

命令输出CPU结果
r2:c8 安静地算 1 秒没有涨（心跳里约 0.2 → 0.4 → 0.6 秒）跑完，exit 0
r2:c9 sleep 30没有不涨0.6 秒判卡死，exit 143
r2:c10 死循环 + timeout=1一直有—卡死判定管不了它；模型给了 timeout，1 秒到点结束

实验 6 只看输出：c8 在 0.6 秒被判卡死杀掉，心跳里 CPU 明明在涨。timeout 必须在 sandboxd 内部计时、由它结束进程组：只在客户端放弃的话，命令会在 Pod 里一直跑下去。 PodSandbox 的读超时（demo 1 秒，Atlas 60 秒）大于心跳间隔，它只用来发现「连接死了」，不是命令时长上限。

7.9 为什么以 shell 退出为「命令结束」，而不是读到 EOF？

r3:c12 是 (sleep 1; echo …) & echo "watcher 已在后台启动"：shell 立刻退出，但后台进程继承了 stdout，管道要 1 秒后才关。sandboxd 等 shell 退出、再给读线程一小会儿收尾，就交出结果； 之后后台进程的输出只进日志文件（剧本最后从 r3_c12.log 里读到了「watcher：后台进程的输出」）。

实验 7 改成等 EOF：命令一直「在跑」，没有输出、CPU 也不涨，0.6 秒后被判卡死 —— 连后台进程一起杀掉，那行输出永远不会出现。 换成真实场景就是：模型起一个后台服务再去测试，这条命令要挂到卡死阈值（Atlas 600 秒），然后服务被一起杀掉。

7.10 为什么要杀整个进程组？取消是怎么传到沙箱的？

  • 每条命令以 start_new_session=True（setsid）启动，自成一个进程组，pgid = shell 的 pid。结束时 killpg 先 SIGTERM，宽限之后还在就 SIGKILL。
  • 取消的路径：用户点停止 → run 的任务被 cancel → CancelledError 到达 PodSandbox 正在 await 的地方 → 它发出 POST /v1/execs/{id}/kill（发出去就走，不等）后继续往上抛。r3:c13 的进程组随即清空。
  • 实验 8 只杀 shell（os.kill）：shell 死了，sh -c 'sleep 30' 和 sleep 30 还在原来的进程组里，ps 能看到，30 秒后才自己退出。在 Pod 里它们会一直占着 CPU、内存和端口。
  • 取消只结束这一条命令；之前命令起的后台进程（r3:c12 的 watcher）在另一个进程组，不受影响 —— 这是设计 §11 的语义。
  • stdin 接 /dev/null 是同一类考虑：等输入的命令（apt 的确认、git 的口令提示）立即失败，而不是永远挂着、最后只能靠卡死判定或用户取消。

7.11 为什么沙箱的任何故障都是工具错误？

PodSandbox 把所有失败（建不出 Pod、连不上、409）都抛成 SandboxUnavailable，execute 把它转成 status="error" 的工具结果。 模型通常能换个办法（r5 里重跑了一遍），或者明确告诉用户做不了 —— 都比一个技术错误强。实验 9 配额设为 0：c1、c2、c5 都回成「沙箱启动失败：该用户已有 0 个会话 Pod」，文件工具照常，模型走完这一轮。 实验 10 不转换：r5:c15 的 409 一路抛出图，r5 整轮失败，模型没有机会重跑。 只有「平台根本没开沙箱」不走这条路：那是装配期的错误（SandboxNotEnabled），勾了 Shell 的智能体直接建不出来。

7.12 闲置回收为什么要问 sandboxd？

cluster 不认识 run，也不知道命令在不在跑；「闲置」只能由 sandboxd 回答。GET /v1/info 返回 running 和 idle_s， 有命令在跑时 idle_s 恒为 0 —— 这是「不设运行上限」在回收这一侧的体现：r3 编译中回收一次，「有 1 条命令在跑 → 不回收」。 回收是无损的：工作区在对象存储上，下一次 execute 重新 ensure，代价是冷启动和 HOME 里的东西（r4 里「HOME 里装过的依赖没了」）。 真实 cluster 的闲置回收还没实现（设计 §9，P2）；demo 由剧本手动调。

7.13 为什么命令的环境里没有凭据？

r1:c2 打印的是命令能看到的全部环境变量名：HOME LANG PATH PWD SHLVL TMPDIR _。主容器的环境由 cluster 的模板决定，本来就只有 HOME 和 sandboxd 自己的几个配置； sandboxd 再去掉 SANDBOXD_*（令牌文件路径、会话 id）。模型凭据在 server，对象存储凭据只在挂载器 sidecar，rc 口令只在挂载器和 barrier。 默认可以出网（装依赖、拉代码是最常见的用途），所以控制点放在「凭据不进容器、按需挂载」上（设计 D9）。

11. 顺带发现的问题

问题 1（设计冲突）：server 崩溃后的「接上原命令」，在现有的接管方式下不成立

文档怎么说
沙箱设计 §8 / §11exec_id = {run_id}:{tool_call_id}；「server 重启：run 恢复执行时重放同一个 tool_call → 同一 exec_id → 接上原命令（依赖 run 的恢复机制）」
水平扩展设计 §5.1「工具执行中（已拿到部分结果）：这一轮的 tool_use 没有落库，整轮作废，重新调用模型 —— 模型通常会再发起同样的调用」

重新调用模型得到的是新的 tool_call id → 新的 exec_id → sandboxd 当成新命令。结果不是「接上」，而是同一个 Pod 里两条命令同时在跑（实验 4：pack.log 12 行）； 原来那条还没人管，它跑完的结果也没人取。水平扩展设计 §13 提到的缓解「执行前写意图」，在 services/agent 里目前没有找到对应实现。

方案做法权衡
A（推荐）执行有副作用的工具之前，先把这一轮的 ai 消息（tool_use）落库；接管时从工具节点重跑，tool_call id 不变与沙箱设计的前提一致，ACP 之外的副作用工具也受益；多一次写库（只在有副作用的工具前）
B接管时先调 POST /v1/execs/kill?run_id=（sandboxd 已有）结束这个 run 遗留的命令，再重新调用模型改动最小；但已经跑了一半的副作用照样会再来一遍，长命令白跑
Cexec_id 改用不依赖 tool_call id 的键（如 run_id + 工具轮次 + 批内序号）重新调用的模型不一定发出同样的命令，按位置对上可能把不同的命令接到旧结果上，更危险

问题 2（小）：真实 sandboxd 的 exited 事件有一个竞态

execs.py 的 _finish 先在一把锁里把状态改成 exited，再在另一次加锁里 emit exited 事件。读流的线程如果恰好在两次之间检查， 会看到「已结束、但没有 exited 事件」，于是正常结束这条流；PodSandbox 把「流在 exited 之前结束」当成断线，退避 1 秒后重连才拿到结果。 结果不会错，只是偶尔慢 1 秒、多一次重连。demo 的 Exec.emit(…, final=True) 把两件事放在同一把锁里。

问题 3（小）：server 重启后，第一次 execute 发现不了 Pod 已重建

「环境已重建」靠 PodSandbox 进程内的 _BOOTS 比较前后 boot_id。server 重启（或请求落到另一个实例）后这个字典是空的，Pod 在此期间被回收重建的话， 第一次 execute 不会提示 —— 模型以为之前装的依赖还在。多副本部署后这会变得常见。可以把最近一次的 boot_id 记在会话上（数据库），或由 cluster 在 ensure 的返回里带上「是否新建」。
