1. 要解决什么问题

用 LangChain 的 create_agent() 建出来的智能体，默认只认一样东西：消息列表（messages）。 调用时传 {"messages": [...]}，返回的也是 {"messages": [...]}。

可实际开发中总会有一些「不是对话、但智能体运行时要用」的数据：

数据例子谁给 / 谁用
调用方的偏好温度单位用摄氏还是华氏调用方传入，工具读取，结果里也想带回去
调试开关打开后打印更多日志调用方传入，只在内部用，不需要返回
运行记录这次查过哪些城市工具一边跑一边记，最后交给调用方；调用方不该能伪造
内部计数模型被调了几次只在图内部用，既不让外面传、也不往外露

如果直接往 invoke 里多塞一个键，比如 {"messages": [...], "unit": "C"}，它会被悄无声息地丢掉：不报错，图里也读不到。

state_schema 就是用来解决这个问题的：先声明有哪些字段、每个字段的规则（能不能传入、会不会返回、多次写入怎么合并）， 框架再按声明去收、去存、去交出。这个 demo 用一个「查北京、上海天气」的场景，把四种典型字段各演示一遍。

2. 先分清三样东西：messages、state、context

LangGraph 把智能体表示成一张图（模型节点、工具节点……来回流转，详见姊妹篇 §2）。 图在运行时手里拿着三类数据，它们的定位完全不同：

messagesstate 的其它字段context
是什么对话历史图运行过程中要用的其它数据这次调用的「环境信息」：是谁、在哪个租户……
怎么声明AgentState 自带继承 AgentState，挂到中间件的 state_schema 上create_agent(context_schema=…)
怎么传入invoke({"messages": …})invoke({"messages": …, "unit": …})invoke(…, context={…})
图里能改吗能能不能（设计上只读）
会出现在返回值里吗会看标注（§4）不会
模型看得到吗看得到（这就是给模型的输入）看不到，除非中间件把它写进提示词或消息看不到
demo 里的例子用户提问、工具结果unit / debug / visited / model_callsuser_id
一句话区分：context 是「谁在调」，state 是「在干什么」。用户 ID、租户这类调用期间不会变、也不该被图改掉的东西放 context； 会在运行中被读写、累积的东西放 state。

3. state_schema 是怎么生效的

3.1 写法：继承 AgentState，挂到中间件上

class WeatherState(AgentState):          # AgentState 自带 messages 等字段
    unit: NotRequired[str]                # 加你自己的字段

class WeatherMiddleware(AgentMiddleware):
    state_schema = WeatherState           # 就这一行

agent = create_agent(model=…, tools=[…], middleware=[WeatherMiddleware()])

AgentState 是一个 TypedDict，所以 WeatherState 也是。TypedDict 只是给类型检查器和框架看的「说明书」，运行时 state 就是一个普通 dict， 因此取值写 state["unit"] 或 state.get("unit")，而不是 state.unit。

也可以不经过中间件，直接 create_agent(state_schema=WeatherState)。官方建议优先挂在中间件上： 字段跟着用它的那段逻辑走，换掉中间件时字段也一起走，不会留下没人用的字段。

3.2 合并：多份声明 → 一份完整 state → 再派生出入参和返回值

右侧三个框里的字段是 demo 实际打印出来的（agent.get_input_jsonschema() / get_output_jsonschema()）。

这个过程在 langchain/agents/factory.py 的 _resolve_schemas 里，做三件事：

  1. 收集：所有中间件的 state_schema（按注册顺序），最后加上 create_agent(state_schema=…)，没传就用 AgentState。
  2. 合并：把所有字段放进一个新的 TypedDict。同名字段后者覆盖前者。
    实验验证：两个中间件都声明了字段 f，一个带 reducer、一个不带，谁注册在后面就听谁的，且不会有任何提示。
  3. 派生：从合并结果里按字段标注过滤，生成 InputSchema 和 OutputSchema，分别决定 invoke 收什么、交出什么。
合并后所有字段是全局共享的。某个中间件声明的字段，其它中间件和所有工具都能读写，并不存在「只属于某个中间件」的字段。 字段名起得具体一些（比如 weather_visited 而不是 visited），可以避免不同中间件撞名后被静默覆盖。

4. 字段标注详解

一个字段的完整写法可以叠好几层，每一层管一件事：

visited: NotRequired[Annotated[list[str], OmitFromInput, operator.add]]
#        └─ ①必填性   └─ ②附加信息  └─ 类型    └─ ③可见性     └─ ④reducer（必须放最后）
层写法管什么谁在看
① 必填性NotRequired[…] / Required[…]这个键在 dict 里是不是一定存在类型检查器（运行时不检查）
② 附加信息Annotated[类型, 元数据1, 元数据2, …]Python 标准语法：给类型挂上额外信息，本身不改变类型—
③ 可见性OmitFromInput / OmitFromOutput / PrivateStateAttr能不能从 invoke 传入、会不会出现在返回值里LangChain（create_agent）
④ reducer一个 (旧值, 新值) → 合并后的值 函数，如 operator.add多次写入怎么合并LangGraph（图引擎）

4.1 必填性：一律用 NotRequired，读的时候用 .get()

TypedDict 的字段默认是 Required（必须有）。但框架在运行时并不检查：实验中把字段声明为 unit: str（Required）， 调用时不传，before_model 里 "unit" in state 是 False，没有任何报错。

所以 Required 只会让类型检查器误以为这个键一定存在。老老实实写 NotRequired，读取时用 state.get("unit", 默认值)， 类型提示和真实行为才一致。

例外是带 reducer 的字段（§4.3）：它从一开始就有初始值。demo 里 visited 在第一次进 before_model 时就是 []（实测）， 而普通字段在没被写过之前是根本不存在的，比如 model_calls 第一次不在 state 的键里。

4.2 可见性：三种标注，其实是一个开关矩阵

三种标注在源码里是同一个类的三个实例（langchain/agents/middleware/types.py）：

@dataclass
class OmitFromSchema:
    input: bool = True     # True = 从 InputSchema 里去掉（不许从 invoke 传入）
    output: bool = True    # True = 从 OutputSchema 里去掉（不出现在返回值里）

OmitFromInput    = OmitFromSchema(input=True,  output=False)
OmitFromOutput   = OmitFromSchema(input=False, output=True)
PrivateStateAttr = OmitFromSchema(input=True,  output=True)
标注invoke 能传入图内能读写出现在返回值典型用途demo 字段
（不加）✓✓✓调用方给的参数，结果里也要带回unit
OmitFromOutput✓✓✗开关、配置类输入，不需要返回debug
OmitFromInput✗✓✓由图产出的结果，不许调用方伪造visited
PrivateStateAttr✗✓✗纯内部的计数器、缓存model_calls

几个容易误会的地方：

  • 传了不许传入的字段，不会报错，只会被丢掉。demo 故意传了 visited=["伪造的城市"] 和 model_calls=99，图里完全看不到这两个值。
  • 「图内能读写」对所有人都成立。PrivateStateAttr 的源码注释写的是 “purely internal for a given middleware”， 但实验显示：中间件 A 声明并写入的私有字段，另一个没声明任何 schema 的中间件 B 也能读到。它只是对 invoke 的调用方隐藏，不是对其它中间件隐藏。
  • 可见性只影响 invoke 的边界。图内部的读写不受这些标注影响。

4.3 reducer：同一个字段被写多次时怎么办

图是一步一步执行的。每个节点执行完返回「要更新哪些字段」，图引擎再把更新合并进 state。默认规则是新值覆盖旧值。 问题出在同一步里有多个写入的时候，最典型的就是模型一次发起多个工具调用、多个工具并行执行：

字段写法两个工具在同一步都写了 visited
visited: NotRequired[list[str]]（无 reducer） 报错 InvalidUpdateError: At key 'visited': Can receive only one value per step. Use an Annotated key to handle multiple values.
（覆盖规则下，两个值谁覆盖谁没有定义，引擎干脆拒绝）
visited: NotRequired[Annotated[list[str], operator.add]] 合并 [] + ["北京"] + ["上海"] = ["北京", "上海"]

reducer 就是一个接收两个参数的函数：(当前值, 本次写入的值) → 新值。常见写法：

reducer效果
operator.add列表拼接、数字相加、字符串连接
自定义函数，如 lambda a, b: {**a, **b}字典合并
add_messagesmessages 字段自带的 reducer：追加新消息、同 id 替换、遇到 RemoveMessage 就删除（姊妹篇的 Patch 中间件用 RemoveMessage(id=REMOVE_ALL_MESSAGES) 整体替换消息列表）
reducer 必须是 Annotated 的最后一个元数据。LangGraph 判断 reducer 时只看最后一个 （langgraph/graph/state.py 的 _is_field_binop：callable(meta[-1])）。
写成 Annotated[list[str], operator.add, OmitFromInput] 时，最后一个元数据是 OmitFromInput，它不是函数， 于是 reducer 被静默忽略，并行写入时报上面那个 InvalidUpdateError。正确写法是： Annotated[list[str], OmitFromInput, operator.add]。
可见性标注就没有这个限制：LangChain 会遍历所有元数据去找 OmitFromSchema，放在哪个位置都行。

4.4 AgentState 自带的三个字段

理解了上面的标注，再回头看 AgentState 的定义就很清楚了：

class AgentState(TypedDict, Generic[ResponseT]):
    messages: Required[Annotated[list[AnyMessage], add_messages]]
    jump_to: NotRequired[Annotated[JumpTo | None, EphemeralValue, PrivateStateAttr]]
    structured_response: NotRequired[Annotated[ResponseT, OmitFromInput]]
字段标注解读
messagesreducer 是 add_messages；没有可见性标注 → 能传入、会返回
jump_toPrivateStateAttr → 不能传入、不会返回；EphemeralValue → 只活一步，用完就清空。 中间件返回 {"jump_to": "end"} 就是写这个字段（姊妹篇的核心机制）
structured_responseOmitFromInput → 由图产出、会返回，调用方不能传。只有配置了 response_format 才有值， 所以 demo 的 OutputSchema 里有它，但返回值里没有

8. 静默失败清单

state_schema 最大的坑是：大部分错误都不报错，只是数据悄悄没了。下面每一条都实际跑过：

#做了什么结果怎么防
1invoke 时传了没声明的字段静默丢弃先声明再用；在入口处打印 agent.get_input_jsonschema() 核对
2传了被 OmitFromInput / PrivateStateAttr 标注的字段静默丢弃这是预期行为，确认标注符合意图
3中间件钩子返回了没声明的字段静默丢弃同 1
4工具 Command(update=…) 写了没声明的字段静默丢弃（实验 2）同 1
5删掉中间件的 state_schema = …整个程序照常跑完，所有自定义字段都读不到、写不进（实验 2）为关键字段写测试：断言返回值里有它
6reducer 没写在 Annotated 的最后reducer 被忽略；并行写入时才报 InvalidUpdateError，串行时直接覆盖、不报错永远把 reducer 写在最后
7两个中间件声明了同名字段、标注不同后注册的覆盖先注册的，无提示字段名加前缀
8传入值类型和声明不符（unit=123）原样接收，不校验（实验 4）在用到它的地方自己校验
9字段声明为 Required，但调用时没传不报错，键不存在用 NotRequired + .get()
10以为 state 在两次 invoke 之间会保留不会。没有 checkpointer 时，每次 invoke 都从入参重新开始需要跨次保留的数据，从返回值取出来自己存、下次再传入

9. 动手实验

每个实验只改一处，结果都是实际运行得到的。

#改动观察到的现象说明了什么
1 visited 的标注改成 Annotated[list[str], operator.add, OmitFromInput]（reducer 挪到前面） 两个工具执行完后报 InvalidUpdateError: At key 'visited': Can receive only one value per step reducer 必须放在最后（§4.3）
2 删掉 WeatherMiddleware 里的 state_schema = WeatherState 不报错；没有 [before_model] 的打印（debug 被丢了）；after_agent 打印 model_calls=None visited=None；返回值只剩 messages 没声明就等于不存在，而且全程静默
3 main() 里 "unit": "C" 改成 "F" 工具结果变成 北京 64°F、上海 72°F 工具通过 runtime.state 读到了调用方传入的字段
4 "unit": "C" 改成 123 照常运行，工具打印 unit=123，返回值 unit: 123 TypedDict 的类型声明在运行时不校验

10. 扩展：放 state、context 还是 messages？

10.1 选择依据

问自己是 → 放哪
模型需要看到它吗？messages（或由中间件写进提示词）
调用期间不会变、图也不该改它（用户、租户、权限）？context
运行中会被读写、累积，或者需要作为结果交出去？state 字段，用标注控制进出

按这个标准，「租户」更适合放 context 而不是 state：它是调用方的身份信息，不该被图里任何一段代码改掉。 demo 里的 user_id 就放在 context 里。

10.2 回到挂起 demo：等待信息放在 state 里

姊妹篇的挂起 demo 把「在等什么」放在一个 state 字段里：审批中间件在 wrap_tool_call 里拦下工具时，不执行、也不写 tool 消息，只返回 

Command(update={"waiting_on": {call_id: {"reason": "approval", "token": f"ap-{call_id}"}}})

用到了本篇的三样东西，也要看清它的代价：

本篇的知识在挂起 demo 里的用法
自定义 reducerwaiting_on 按 tool_call_id 合并，值为 None 表示删除：多个调用同时挂起要合并，审批通过后要删掉这一项
OmitFromOutputdecisions（审批结果）只进不出：续跑时交进来，不需要再带回去
工具包装钩子返回 Command拦下工具时只更新 waiting_on；放行后同时写工具结果和 {call_id: None}
代价：state 只活一次 invoke要从返回值取出 waiting_on、和消息一起落库、续跑时再传入。消息和 waiting_on 两份都是依据，漏传一份就出错
