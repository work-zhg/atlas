Demo：MCP 方案主流程 · Atlas / Pod → 自研 MCP 网关 → Higress → 业务系统

按 MCP 方案设计 第二版（10-26，只有 MCP 网关能调 Higress）写的最小主流程，用来对照各模块的职责划分。一个模块一个文件，模块之间按真实边界走 HTTP；数据库都是内存里的字典，模型是 engine 里的 mock。依赖方向：server → engine → langchain / langgraph，server 不依赖 langchain（§2）。用仓库的 .venv（langchain 1.4.7 + FastMCP 4 + mcp 2.3），不需要模型 key、不需要真的 Higress，约 3 秒跑完。

2. 依赖方向：server → engine → langchain / langgraph

atlas_server ──▶ atlas_engine ──▶ langchain · langgraph
     │                 ▲
     │                 └─ 契约（contracts.py，只有标准库类型）：ToolSpec · ToolResult · ModelSpec · TurnResult
     └──▶ fastmcp · mcp · httpx      MCP 协议、传输、凭据、会话都在 server
契约谁给谁内容
ToolSpecserver → engine模型看到的名字、描述、参数定义（JSON Schema）、副作用类别、call(arguments) → ToolResult。call 是 server 的代码：持有会话 → tools/call → MCP 结果转成 ToolResult
ToolResultserver → engine文本 + is_error。is_error 时 engine 把它变成失败的工具结果交给模型，不打断这一轮
ModelSpecserver → engine用哪个模型。模型客户端由 engine 建（真实环境里按 provider 建 Anthropic / OpenAI 客户端），server 不碰 LangChain 的模型类
TurnResultengine → server最终回复 + 消息摘要。不把 LangChain 的消息对象交出去

check_layers.py 看 import 语句静态检查依赖方向（故意在 server 里加一行 import langchain_core 试过，会报 ✗、退出码 1）：

✓ atlas_server 不依赖 langchain / langgraph（3 个文件）
✓ atlas_engine 不认识 MCP、不依赖 server（5 个文件）
✓ atlas_engine/contracts.py 只用标准库（1 个文件）
✓ 网关、Higress 等外围模块不依赖 Atlas（9 个文件）

为什么不再用 langchain.mcp：它把"MCP 协议"和"转成 LangChain 工具"做在一起。放在 server 违反"server 不依赖 langchain"；放进 engine 又违反设计稿 2.2 的"engine 不认识 MCP、不知道凭据"。所以拆成两半：协议用 FastMCP 的 client 放在 server，转换写成通用的 ToolSpec → LangChain 工具放在 engine。

做法serverengine问题
A（本例）FastMCP client 直接调；交 ToolSpecToolSpec → LangChain 工具MCP 结果转 ToolResult 要自己写（本例只取文本）
B交连接信息（地址、请求头）+ 工具定义用 langchain.mcp 建客户端和工具engine 拿到主体 Key、要管会话，等于认识了 MCP
C建好 FastMCP client，连同工具定义交给 engine用 langchain.mcp 转换server 的会话池、错误转换要插进 engine 执行工具的过程，得给 engine 开钩子

3. 三种凭据、两种身份

凭据 / 身份谁持有从哪到哪demo 里在哪
主体 KeyMCP 网关（原文存库）；Atlas 运行时取；ACP 会话的 PodAtlas / Pod 里的 CLI → MCP 网关atlas_server/mcp_tools.py 写进传输层；gateway_proxy.py 认人后换掉
网关凭据只有 MCP 网关和 HigressMCP 网关 → Higress（转发调用、拉工具定义）main.py 只交给 Gateway 和 higress.app

X-Uid（使用者）调用方自带，网关照转Atlas / Pod → … → 业务系统只作审计（场景 ④ 里是 bob，主体是数字员工）

5. 时序图：Native（场景 ③）

一个 Run 只问网关一次（可用服务 + Key），装配不连 MCP；每个 MCP 请求都经过网关的认人、判权，tools/call 再加复核；网关把主体 Key 换成网关凭据，Higress 再换成后端凭据。

6. 时序图：ACP 与绕过（场景 ⑤）

Atlas 拦不到 Pod 里的单次调用，网关是唯一的治理点：工具级复核、身份改写对 CLI 一样生效；Pod 只有主体 Key，没有网关凭据，直连 Higress 调不通。

7. 写 demo 时发现的、可能要改的设计

这几条是写和跑 demo 的过程中冒出来的，设计稿里还没写或写得不够准。都没有改进设计稿，等你看完再定。

#发现设计稿现在怎么写建议
F1接入检查会触发“直连告警”：网关登记服务时发的那个不带凭据的请求，在 Higress 看来就是一个“想绕过网关”的请求（输出 ②、⑦）8.3、10：“正常情况下 Higress 上不会有被拒绝的请求，出现即告警”告警规则改为“被拒且来源不是 MCP 网关”；接入检查本身由网关记录
F2tools/call 只能按工具名判复核：tools/list 的返回带着定义，能按实时指纹去掉被改过的；tools/call 只带名字，网关只能查库里的结论。上游改了定义、网关还没刷新时，知道名字的 CLI 仍能调到新定义8.1 只写了“工具列表里去掉、调用直接拒绝”，没说按什么判数据面在 tools/list 里发现指纹对不上时，立即在网关库里把这个工具标为“定义已变、待复核”，之后的 tools/call 一并拒绝（数据面要写控制面的库）。demo 没实现这一条
F3tools/list 要读完整返回再改写：过滤工具必须拿到整个列表；上游如果回的是 SSE，还要先解析事件流8.2：“流式转发、不缓冲”改成“tools/call 等流式转发、不缓冲；tools/list 读完整返回、改写后再回”（列表一般不大）
F4拒绝必须带 JSON-RPC 错误体：mcp 2.x 客户端遇到只有状态码的 4xx，只会报 Server returned an error response，看不到原因。demo 的网关回了错误体，Pod CLI 才拿到“没有通过复核”6.2 按“Key 无效 / 无权 / …”给模型不同的提示，但没说网关怎么把原因带回来8.2 加一条：拒绝时回 JSON-RPC 错误体（原因 + 区分得开的错误码），Atlas 按错误码转成 6.2 的提示
F5Atlas 每个 Run 问网关两次：主体能用哪些服务、主体的 Key。两者总是一起用6.1：“向 MCP 网关查可用服务，同时取主体 Key”合成一个内部接口，一次返回；ACP 建会话同样只问一次
