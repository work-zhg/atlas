—贯穿全部文档的三条主线

主线 01 · 角色分工

上下文由谁持有。native 在服务端每轮重建，acp 在 CLI 进程内。这条分界线推导出了全部不对称 —— 能力矩阵、审批回路、状态机、持久化策略。它不是策略选择，是机制事实；把它当实现细节抹平，会得到一个两边都不好用的抽象。

主线 02 · 单一真相源

Message 是会话内容的唯一真相，Event 只是它的产生过程。顾问因此不存 checkpoint —— 没有第二份真相，也就没有跨源对齐规则，而那类规则对不上时是静默降级，是最难排查的一类缺陷。代价是 Run 中断后整轮重来。助理侧同理：Message 一律由 ACP session/update 固化而来，云上与本地走同一条路径，不解析 CLI 的内部文件格式。

主线 03 · 能力显式化

差异不可抹平，只能显式暴露。capabilities 归 Agent 所有，随会话快照投影下发；前端只读 capability 决定按钮的显示与禁用。一旦出现第一个按 agent.type 分支的前端组件，后面就收不住了。

—术语速查

对象作用域一句话
Agent全局配置智能体定义，capabilities 的所有者。type 取 native 或 acp
Session—一个会话，引用一个 Agent 版本
RunSession会话里的一条对话，session 内串行
MessageSession会话内容账本，永久保留
EventRunchunk 转成的过程流，只留最后一个 Run

设计阶段文档，随讨论持续变更。本期范围内不做顾问与助理的任务移交，一个 Session 只绑定一个 Agent（见系统架构 §09）。链路实现前需先完成的验证项见运行时链路 §12。
