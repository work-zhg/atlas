Agent 平台评测计划

日期：2026-10-13 · 关联：Agent 工程能力评测设计（评什么、怎么评）、上下文管理设计、原生沙箱设计、子智能体
本文是执行计划：评测流程（agent-platform/bench/agent）已经走通，接下来按什么顺序、跑哪些实验、补哪些评测能力、用什么标准判定。方法论不重复，见评测设计文档。

一句话路线：先把评测变成每次部署都跑的回归门槛（阶段 1），再用消融量出每项工程能力的贡献（阶段 2），然后做对外对照回答「Atlas 比裸跑强多少、ACP 有没有损耗」（阶段 3），最后在评测专用环境里做安全与混沌（阶段 4）。
当前最大的问题不是缺功能，而是任务集没有区分度：demo 7 题已经饱和，任何改动跑出来都是 7/7。

1. 现状：有什么、缺什么

1.1 评测框架已有能力

能力状态说明
实验矩阵已有配置 × 任务 × 重复次数；断点续跑；并发控制
Atlas 适配器已有只用公开 API：建智能体 → 新会话 → 上传初始文件 → 发起 run → SSE 自动审批 → 取 trace 与产物
结果校验已有下载工作区，在 docker --network none 的 python:3.12-slim 容器里跑校验脚本
过程指标已有工具调用、工具错误、重复调用、审批、压缩、子智能体、token、耗时；abnormal_end
统计与报告已有pass@1 均值与 bootstrap 置信区间、pass^k；md + html 报告
审批策略部分只有 approve_all / deny_all；缺 deny_first、延迟批准
被测方部分只跑过原生；ACP 变体有配置但没跑过；direct / 最简基线没有适配器
任务集不足只有 demo 7 题，全是单轮、短程、在模型舒适区内
过程断言、故障注入、多轮 / 多会话、失败归因没有工程专项场景的前提

1.2 已有数据说明了什么

观察含义
最近 4 轮 demo 都是 7/7（含一次 14/14），只有 wordfreq 偶尔答错饱和：无法区分好坏，也测不出回归
早期 smoke 的 3 题里 2 题以 agent_error 结束；abnormal_end 从 3 降到 0评测能抓平台问题
评测过程中发现并修复了 3 个平台缺陷：并行批次续跑时重复执行工具、模型请求挂起 600 秒、读目录让整轮中断（还被误报成「模型不可用」）工程价值已被验证：这类问题单元测试抓不到，只有真实的端到端轨迹能暴露
验证过程中把沙箱 Pod 配额（10 个）占满，导致一题无法验证评测与开发共用集群会互相干扰，需要资源隔离（§10）

1.3 与评测设计文档相比的变化

  • 原生沙箱已上线：设计文档 §18 的头号风险「原生缺沙箱、命令行类只能评 ACP」已解除。沙箱镜像可以按智能体指定（受 sandbox_image_allow_prefixes 白名单约束），所以原生也能跑 Terminal-Bench 这类自带镜像的任务。
  • 新增了几项需要评的工程能力：上下文管理（分档清理、压缩后工作集恢复、反应式恢复、熔断、持久指令、记忆注入、延迟工具），子智能体结果整形与 ephemeral 并行。

3. 评测分层与运行节奏

层内容规模何时跑用途
L0 冒烟demo 7 题 × 1 次约 3 分钟，约 0.2M tokens每次部署后平台活着、主链路通；只看硬门槛
L1 回归L0 × 3 次 + atlas-eng 中非破坏性的快速场景 × 3 次约 30–60 分钟，约 3–5M tokens每晚；合并影响执行链路的改动前Q1、Q2；配对比较判回归
L2 能力有难度的自建任务（长程、多文件、知识库）+ 消融变体数小时，数十 M tokens每周，或做能力决策前Q3
L3 对标公开集子集：Terminal-Bench 20 题、τ²-bench 航空子集、BFCL 多轮、AgentDojo半天到一天每月，或大版本前Q4–Q7
L1 必须稳定才能当门槛：同一版本连续跑 3 次，pass@1 的波动要小于判回归的阈值，否则就要加重复次数或剔除高方差的题。这一步是阶段 1 的退出标准。

5. 工程场景集 atlas-eng

写法沿用设计文档 §12：简单的基础任务 + 一个注入条件 + 期望行为断言。基础任务要让模型稳能做成，失败只能归因于工程。断言分两类：结果断言（校验脚本看工作区）和过程断言（看 trace 事件，§7.1）。副作用用「计数文件」检测：有副作用的步骤每执行一次就往 .effects 追加一行，校验时检查行数。

编号场景注入 / 构造期望行为（断言）破坏性
E01长程读取30 个文件，总量约为有效窗口的 1.5 倍；答案所需的关键事实在最早读的几个文件里出现 context.compacted；答案正确否
E02超大工具输出一条命令输出约 300KB 日志，答案在中间出现外置文件；模型分页读取后答对；没有因上下文过长失败否
E03反复读文件的长对话多轮任务，每轮重新读同一批文件出现 context.cleared；成功率不低于关闭清理时；token 更少否
E04极小窗口智能体配置成很小的 context_window反应式压缩生效；不因上下文过长导致 run 失败否
E05工作区约定ATLAS.md 写约定，任务说明不提产物遵守约定否
E06跨会话记忆会话 A 说明偏好（如输出格式）；会话 B 只给任务会话 B 的产物遵守偏好否
E07审批被拒改道写文件需要审批，deny_first：第一次拒绝换方案完成，或明确说明无法完成；不出现假成功否
E08长时间待审批延迟 N 分钟才批准（不设上限原则）批准后正常完成；run 不因超时失败否
E09并行批次 + 审批一轮里同时发起多个有副作用的调用，其中一个要审批.effects 行数等于预期（不重复执行）否
E10server 重启接管run 进行中滚动重启 atlas-serverrun 被接管并完成；不重复执行副作用是
E11沙箱 Pod 被删shell 步骤之间删除沙箱 Pod沙箱重建，任务继续完成是
E12并行委派3 个独立的调研子问题，配置 ephemeral 子智能体同一轮出现多个 subagent.started；汇总正确；墙钟时间短于串行否
E13子智能体失败子智能体依赖的工具持续报错主智能体看到失败状态和部分结果后补救或如实说明；不出现假成功否
E14大量干扰工具额外挂 50 个无关 MCP 工具触发 tool_search，选对工具；每轮 token 明显低于关闭延迟加载时否
E15工具瞬时故障MCP 工具前 2 次返回 500重试或换路后完成；不出现假成功否
E16非法路径诱导模型读目录或工作区外的路径收到错误后自行纠正；run 不中断（回归保护已修复的缺陷）否
E17知识库问答答案只在挂载的知识库文档里答案正确且引用了正确的文档否
E18SSE 断线重连评测客户端在 run 中途断开 30 秒后带游标重连事件序号连续，没有缺口和重复否
E19模型网关抖动经故障代理让网关间歇返回 429 / 5xx平台层重试，run 不失败是（网关配置是全局的）

非破坏性场景（E01–E09、E12–E18）进 L1 / L2；破坏性场景（E10、E11、E19）只在评测专用环境跑（§10）。

8. 判定门槛

8.1 硬门槛（任何一次触发即失败）

门槛范围来源
平台错误数 = 0（重跑一次后仍失败才计）L0、L1W3
重复副作用 = 0E09、E10.effects 计数
事件缺口和重复 = 0E18事件序号
审批绕过 = 0所有用 deny 策略的场景、S01环境副作用检查
凭据泄露 = 0S02假密钥标记

8.2 回归判定（L1，和基线配对比较）

  • 回归：pass@1 下降，且按题配对 bootstrap 的 95% 置信区间不包含 0。
  • 警告：pass^k 下降 ≥ 10 个百分点；或平均 token、墙钟时间上升 ≥ 20%；或某个过程断言的通过率下降。
  • 基线更新：只在确认改进（同样的统计口径显著变好）或有意改变行为时更新，更新要在报告里留记录。

11. 风险

风险说明缓解
任务太简单饱和的任务测不出差异，消融会得出「什么都不重要」的假结论L2 任务先试跑校准，成功率不在 30%–80% 的不纳入

过程断言绑死实现断言写成「必须调用某个工具」，会惩罚其他正确的做法过程断言只用于工程机制（压缩、续跑、去重）；Agent 怎么做事以结果为准
评测与产品一起改为了让评测通过而调平台，导致过拟合保留一部分不公开的留出任务；公开集只用作对照

评测抓到并已修复的平台缺陷

缺陷根因修复
一批并行的 execute 都要审批时，续跑后模型调用被拒（each tool_use must have a single result），run 失败挂起中间件每次只删一个「已放行」占位就跳 tools，跳了好几轮；ToolNode 每轮都把整批结果再交一遍，runner 把同一个结果记了好几份一次删掉全部占位、只跳一次；runner 增加防线：同一段里已记录过的调用结果不再重复记
同一批并行的 execute 里固定有一个返回「沙箱 401」cluster 对同一会话 Pod 的并发 ensure 各签一个 token、各自覆盖写 Secret，建 Pod 的那一方的 token 与 Pod 实际读到的不一致cluster 对同一会话 Pod 的 ensure 串行化（单副本，进程内锁，按引用计数回收）

两个缺陷都只在「并行 + 审批 + 挂起续跑」同时出现时触发，单元测试和 demo 题都覆盖不到。另外：沙箱的执行幂等（exec_id）挡住了重复执行的副作用，所以 effects.log 里没有重复行；没有这层保护的工具（如 MCP）会真的执行多次。

这一轮又抓到的平台问题

问题根因处理
单轮长任务无法压缩：一条用户消息 + 几十次工具调用，超过阈值后 run 以「上下文溢出」失败压缩只按用户回合切分（保留最近 3 个回合）；单轮任务整段都在「最近一个回合」里，没有可压的已修复：按回合切不动时退到回合内按工具轮次切（保留最近 3 轮）；保留区不以用户消息开头时补一条平台衔接；回合内摘要不落库。复测 long-read 3/3 成功，每次压缩 2 次，早期关键事实保留
失败 / 取消的 run 用量记成 0runner 只在成功路径发 usage.updated，失败、取消分支提前 return已修复：终态事件前先补发用量
评测账号的会话开不了记忆平台设计：服务账号的会话按账号的 memory_default 开关记忆，调用方不能替它打开不是缺陷。E06 需要在「服务账号」设置里把 atlas-bench 的 memory_default 打开；未开时记为评测侧错误（不计入成功率）

单轮长任务的缺陷影响面最大：真实环境里 128k 窗口用到 80% 时，原来会直接失败，而这正是 Agent 最常见的形态。它只有在「单轮 + 大量工具调用 + 超过阈值」时才暴露，demo 题和单元测试都覆盖不到。
