Agent 平台横向扩展设计

日期：2026-10-15 · 关联：执行设计、会话与事件流、原生智能体沙箱、长期记忆
范围：atlas-server（API 与 run 执行）、atlas-cluster、atlas-config、atlas-knowledge 的多副本部署、滚动发布与故障接管。
不在本期：PostgreSQL / Redis 自身的高可用（主从、Sentinel / Cluster）、多地域部署、多租户隔离。

结论先行：事件流（Redis Stream + 归档）、取消位、挂起 run 的认领（CAS）、MCP 目录、知识库（API + Celery）已经是多副本友好的；真正阻碍横向扩展的是 run 的执行绑在进程里：
  1. run 由进程内的 asyncio 任务执行，一段（segment）的消息与事件只在段结束时落库，进程退出即丢失这一段的工作，run 停在 running；
  2. 会话锁的 TTL 是 max(timeout, 24h) + 120s，持锁进程死掉后，会话最长被锁 24 小时；
  3. ACP run 与 bridge 的 WebSocket 连接只能由发起它的进程重连，换个实例接不上；
  4. 启动时的 Pod 回收、记忆抽取队列、授权缓存失效、cluster 的会话锁都假设「只有一个进程」。
方案的核心是把 run 从「某个进程的任务」变成「数据库里可被任何实例领取、续跑的工作」：租约（lease）领取 + 每个工具轮次落检查点 + 过期接管 + 优雅停机交接。这与挂起 / 续跑已经在用的「消息表是唯一事实源、run 由多段组成」完全同构，不引入 checkpointer，也不引入第二个状态源。

1. 目标与原则

目标衡量
任意服务都能跑多个副本，加副本即加容量server / config / knowledge 副本数 ≥ 2，压测吞吐随副本数近线性增长
滚动发布不打断进行中的 run发布期间 run 不失败、不重复执行已完成的工具调用；前端只看到短暂的「重新连接」
实例故障（OOM、节点宕机）后 run 自动接管接管延迟 ≤ 一个租约周期（默认 30 秒）；丢失的工作 ≤ 一个工具轮次
按负载自动扩缩API 按连接与 CPU、执行器按排队 run 数扩缩

原则（沿用平台既有约定）：

  • 不设到点结束的超时：租约是「进程还活着」的心跳，不是工作时长上限；Agent 跑多久、审批等多久都可以。
  • 消息表是唯一事实源：不引入 LangGraph checkpointer；检查点就是「把已完成的消息按轮次落库」。
  • 断联恢复，而不是判失败：进程退出、连接断开都按「可续上」处理，只有续不上时才给出明确的失败原因。
  • 数据库是排队的唯一真相，Redis 只做唤醒与加速：Redis 丢消息时由定期扫描兜底，不会丢 run。

3. 总体架构

浏览器 / 业务系统 / TeamFlow │ HTTP · SSE ┌──────▼──────┐ │ 负载均衡 │ 无会话粘滞：任何请求可落在任何实例 └──────┬──────┘ ┌────────────┼────────────┐ ┌────▼────┐ ┌────▼────┐ ┌────▼────┐ │ api #1 │ │ api #2 │ │ api #N │ atlas-server --role api └────┬────┘ └────┬────┘ └────┬────┘ 建 run（status=queued）、读写会话、SSE 订阅 │ 写库 + 唤醒 │ │ ▼ ▼ ▼ ┌──────────────────────────────────────┐ │ PostgreSQL：run（排队、租约、检查点） │◀──── 唯一真相 │ Redis：唤醒广播 · 事件流 · 取消位 · 锁 │◀──── 唤醒与加速 └──────────────────────────────────────┘ ▲ 领取 / 续租 / 落检查点 / 发事件 ┌────┴─────┐ ┌──────────┐ ┌──────────┐ │ runner #1│ │ runner #2│ │ runner #M│ atlas-server --role runner └────┬─────┘ └────┬─────┘ └────┬─────┘ 执行 run（native 在进程内，acp 连 Pod 内 bridge） │ │ │ ▼ ▼ ▼ 模型网关 · MCP · atlas-cluster（会话 Pod） · atlas-knowledge · mem0

拆分 API 与执行器（runner）：同一镜像、同一代码，启动参数选择角色；小规模部署可以 --role all 合在一个进程（即现在的形态）。拆开的理由：

  • 负载形态不同：API 是大量长连接（SSE）与短请求，执行器是模型流式调用、工具执行与上下文压缩，CPU 与内存特征完全不同，各自独立扩缩更划算；
  • 发布互不影响：发 API 不碰正在跑的 run；发执行器时 run 走交接（§6），用户的 SSE 连接不断；
  • 故障隔离：执行器 OOM（例如超长上下文）不会带走所有用户的 SSE 连接。

API 与执行器之间不直接调用：API 只写库并发唤醒，执行器只从库里领取。两者都可以任意加副本，彼此不需要知道对方有几个。

4. run 的调度：领取与租约

4.1 生命周期

POST /runs ──▶ queued ──领取（CAS + 租约）──▶ running ──段结束──▶ suspended / 终态 ▲ │ 续租（每 lease/3） │ │ ├──── 交接（优雅停机，§6）◀─────┤ └──── 租约过期被扫描接管（§5）◀─┘ 接管次数记入 run.takeovers

4.2 领取

  • 入队：API 在同一事务里创建 run（queued）并占会话锁，事务提交后向 Redis 发唤醒（run:wake，发布 / 订阅）。唤醒只是「有新活了」，丢了也没关系。
  • 领取：执行器收到唤醒或定期扫描（默认 5 秒）时，用一条 CAS 抢 run： 
    UPDATE run SET status = 'running', owner = :instance, lease_until = now() + :lease,
               claimed_at = now()
 WHERE id = (SELECT id FROM run
              WHERE status = 'queued' OR (status = 'running' AND lease_until < now())
              ORDER BY created_at
              FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING id
    SKIP LOCKED 让多个执行器并发领取互不阻塞；第二个条件就是接管（§5）。
  • 本地并发上限：每个执行器有 max_concurrent_runs（按内存估算，默认 32），满了就不再领取，自然形成背压，排队的 run 由其他实例或新扩出来的实例领走。
  • 委派的子 run：同样只入队不直接执行；父 run 的原地短暂等待改为订阅子 run 的终止事件（事件流本来就在 Redis 里），等待窗口内拿到结论就继续，超过窗口就挂起——与现在的语义一致，只是子 run 可能在别的实例上跑。

4.3 租约

  • 持有者每 lease / 3（默认 10 秒）续租一次：UPDATE run SET lease_until = now() + :lease WHERE id = :run AND owner = :me，返回 0 行说明已被别人接管，立即停止本地执行（防止「假死后复活」的双写）。
  • 租约是心跳，不是时长上限：只要进程活着就一直续，run 跑一小时也不会被抢。
  • 续租批量进行（一个执行器一条 SQL 续自己持有的全部 run），租约数量对数据库的压力与 run 数无关。

4.4 会话锁跟随租约

会话锁仍然保证「一个会话同时只有一个活跃 run」，但不再用 24 小时的长 TTL：锁的 owner 仍是 run，TTL 改为与租约同长，由持租约的执行器一并续期。持有者死掉后，锁在一个租约周期内过期；接管者领取 run 时重新占锁（owner 不变，仍是同一个 run），用户在此期间发新消息会看到「上一轮仍在进行」，而不是被锁 24 小时。挂起中的 run 不持有执行器，会话锁由「run 处于 suspended」这个库内状态表达，不依赖 Redis 键的存活。

5. 断点续跑：检查点与接管

接管的前提是「接手的实例知道做到了哪」。native 与 acp 的事实源不同，分开处理。

5.1 native：每个工具轮次落一次检查点

现在一段的消息在段结束时才落库。改为以工具轮次为单位增量落库：模型输出 tool_use、全部工具结果返回后，把这一轮的 assistant 消息与 tool 消息、这一轮的事件归档、累计用量在一个事务里写入，并推进 run.checkpoint_seq。段结束时只补写收尾。

一段 = [模型调用 → 工具执行]* → 段结束 └─ 每轮结束：消息 + 事件归档 + 用量 一个事务落库（检查点） 接管：从消息表重建历史（与挂起续跑同一条路径）→ 从下一次模型调用继续
中断时刻接管后的处理丢失的工作
模型流式输出中从上一个检查点重建历史，重新调用模型；向前端发 run.resumed，前端丢掉未完成的那段文本一次模型调用（重新计费）
工具执行中（已拿到部分结果）这一轮的 tool_use 没有落库，整轮作废，重新调用模型——模型通常会再发起同样的调用本轮已执行的工具；有副作用的工具可能被再执行一次（见下）
两轮之间直接从下一次模型调用继续无
压缩（摘要生成）中摘要未落库，重新判断是否需要压缩一次摘要调用

副作用工具的去重：对写文件、执行命令、调外部系统这类工具，在执行前先落一条「意图」记录（tool_call_id、工具名、参数哈希），执行完再落结果。接管时发现有意图、没结果的调用，不盲目重放，而是补一条工具结果「执行被中断，结果未知，请先检查当前状态再决定是否重试」交给模型——与 PatchToolCallsMiddleware 处理悬空调用的方式一致。工具也可以声明 idempotent=true（如读文件、检索），这类直接重放。

5.2 acp：bridge 是持久的一方，接管 = 重新 attach

ACP run 真正的执行在会话 Pod 里：Claude Code 不因 server 实例退出而停止，bridge 的 outbox 保存未确认的事件。现在 turn id 与已确认的序号只在执行进程的内存里，改为写入 run 行（acp_turn_id、acp_acked_seq，确认后随租约续期一并更新）。接管实例：

  1. 经 atlas-cluster 取得 Pod 地址，重连 bridge；
  2. 以 acp_turn_id 调用 attach，从 acp_acked_seq 之后重放 outbox，翻译成平台事件继续发布——同进程断线重连已经走这条路，只是参数改从库里读；
  3. 如果这一轮在断开期间已经结束，outbox 里有收尾事件，按正常收尾落库；如果 Pod 已不存在，以「执行环境已回收」失败收尾。

acp 不会重复执行工具：工具在 Pod 里只执行一次，接管只是把事件流接回来。

5.3 事件序号与前端

  • 会话序号（thread_seq）已在 Redis 分配并以库内水位兜底，接管后继续分配，不重号；检查点之后发布到 Redis、但未归档的事件，接管时从 Redis 流补归档（流里有、库里没有的序号）。
  • 前端 SSE 断开后带游标重连（已有能力），落到哪个 API 实例都一样；新增的 run.resumed 事件让对话区把正在流式输出的消息复位，并提示「已在其他节点继续」。

6. 优雅停机与滚动发布

滚动发布时让 run「主动交接」，而不是等租约过期被动接管——交接零等待，且 native 不丢工作。

步骤API 实例执行器实例
收到 SIGTERMreadiness 置为失败，负载均衡摘掉流量停止领取新 run
处理在途工作向每个 SSE 连接发 retry 提示后关闭，前端带游标重连到其他实例；短请求正常处理完native：在下一个安全点（当前工具轮次结束、检查点落库之后）停下，run 置回 queued（handoff），释放租约，立即被其他实例领取；
acp：直接断开 bridge 连接、写回已确认序号并置回 queued，Pod 里的那一轮照常进行
收尾退出全部交接后退出；terminationGracePeriodSeconds 内没等到安全点的（例如一个工具执行了很久），进程被强杀后走租约过期接管，最多丢这一轮
宽限期不是 run 的超时：宽限期限制的是「进程多久必须退出」，不是 run 能跑多久。超过宽限期的 run 不会失败，只是从「主动交接」退化为「过期接管」。建议宽限期设为 60–120 秒，覆盖绝大多数工具调用。

7. 单例任务与跨实例状态

7.1 单例任务：租约选主

Pod 孤儿回收、记忆死信重试这类「全局只需要一个人做」的任务，从 lifespan 里移出，交给维护者（maintainer）：每个执行器都参与竞选，用 Redis SET maintainer NX PX 加续租选出一个，持有者定期执行，进程退出后其他实例接任。挂起 run 的周期扫描本身靠 CAS 已幂等，保留在每个执行器上（多扫几遍只是多几次查询）。

任务现在改为
Pod 孤儿回收每个副本启动时调一次维护者每 10 分钟一次；只回收「会话已删除且超过保留期」的 Pod，避免与正在建 Pod 的会话竞态
挂起 run 补唤醒每个实例周期扫描不变（CAS 幂等）
租约过期接管无每个执行器的领取扫描自带（§4.2）
记忆死信重试无维护者定期把死信按退避重新入队

7.2 记忆抽取队列：可靠消费

BRPOP 改为 BLMOVE queue → processing:{instance}：取出时原子地放进本实例的处理中列表，处理完再删除。实例退出后，维护者把「所属实例已不在」的处理中列表搬回主队列。抽取本身按 run 去重（同一 run 只抽一次），重复投递无害。

7.3 进程内缓存的失效

缓存问题做法
授权快照（server）撤销用户只清本进程撤销时经 Redis 发布 authz:invalidate {user}，各实例订阅后清本地；TTL 仍保留作为兜底
introspect 结果（config / knowledge）同上订阅同一频道
主体展开（knowledge）部门 / 角色变化后最长 60 秒生效可接受，不改

8. 其他服务

服务做法
atlas-cluster 会话 Pod 的 ensure 串行从进程内锁改为 Redis 锁（pod:ensure:{thread}:{kind}，带续租），多副本时同一会话仍串行；Secret 写入加 resourceVersion 乐观并发，二次防线。
cluster 的 QPS 很低，本期目标是 2 副本做高可用而不是扩容量；K8s 写权限仍只在这一个服务里。
atlas-config已无状态，直接多副本；只需订阅授权失效频道（§7.3）。
atlas-knowledgeAPI 与 worker 已拆分，直接加副本；索引版本重建是 Celery 任务，acks_late 保证 worker 被杀时重新投递（重建是幂等覆盖写）。
前端（frontends）静态资源与 Next 服务端无状态，直接多副本。
Pod 内 bridge不变：它是 ACP 的持久方，接管能力依赖它的 outbox 与 attach（§5.2）。

8.1 数据库连接

副本数上来以后，「副本数 × 连接池大小」很快超过 PostgreSQL 的连接上限。在服务与数据库之间加 PgBouncer（transaction 模式），各进程的池调小（API 10、执行器 20）。注意 transaction 模式下不能用会话级特性：本平台没有用 LISTEN/NOTIFY 与会话级 advisory lock，SELECT … FOR UPDATE SKIP LOCKED 在事务内，兼容。

容量估算的单位是「并发 run」而不是 QPS：一个 native run 常驻的是上下文（几十 KB 到几 MB 的消息）与流式连接，主要耗内存与模型网关并发；acp run 在执行器里只是一条 WebSocket 与事件翻译，开销很小，真正的资源在会话 Pod。max_concurrent_runs 按 native 估，acp 单独计数、上限放宽。

10. 可观测性

  • run 根 span 增加 atlas.instance、atlas.takeovers；每次接管或交接开一个新段，span 上记 resumed_from（交接 / 过期接管）与丢弃的工作量（重放的模型调用数）。
  • 指标：排队 run 数与最长排队时间、领取延迟、租约续期失败次数、接管次数（按原因）、交接耗时、检查点落库耗时、各实例运行中 run 数。
  • 告警：接管次数突增（实例频繁崩溃）、排队时间持续上升（执行器不足）、租约续期失败（数据库抖动）。

11. 数据模型与接口变更

表 / 接口变更
run新增 owner（实例 id）、lease_until、claimed_at、takeovers、checkpoint_seq、acp_turn_id、acp_acked_seq；索引 (status, lease_until)、(status, created_at)
tool_intent（新表）run_id、tool_call_id、工具名、参数哈希、状态（started / done）；副作用工具执行前写入
事件新增 run.resumed（data：原因、丢弃的模型调用数）；run.handoff 只进归档、不推前端
工具声明新增 idempotent 属性（默认 false），内置的只读工具标为 true
启动参数--role api | runner | all；执行器配置 lease_s、max_concurrent_runs、claim_scan_s
RunExecutor 协议submit 改为「入队 + 唤醒」；新增 Runner（领取、续租、交接），现有 InProcessExecutor 的执行循环原样搬入 Runner——HookAssembly 与 AgentRuntime 不改

12. 分期

阶段内容退出标准
P1 可接管run 租约与领取（仍 --role all）；会话锁跟随租约；native 按工具轮次落检查点；acp 持久化 turn 与确认序号、跨实例 attach；优雅停机交接；维护者选主（Pod 回收移出 lifespan）；记忆队列可靠消费；授权缓存失效广播；server 2 副本评测集 L1 在「执行中随机杀实例」与「滚动发布」两种扰动下成功率不下降、平台错误为 0；副作用工具不出现重复执行
P2 可扩容API / 执行器拆分部署；KEDA 按排队数扩缩执行器；HPA 扩 API；PgBouncer；cluster Redis 锁与 2 副本；config / knowledge 多副本压测：并发 run 随执行器副本数近线性增长；扩缩容过程中 run 零失败
P3 深化副作用工具意图记录覆盖全部内置工具与 MCP 工具（按工具声明）；按租户或 Agent 的执行器分组与配额；Redis Sentinel、PostgreSQL 主从切换演练故障演练（Redis 主从切换、数据库切换）中 run 不丢

P1 的验证直接复用 Agent 评测体系：在 make regress 的场景集上加两种扰动（运行中随机删除 server Pod、执行 kubectl rollout restart），对比无扰动基线，判定条件就是成功率与平台错误数。

13. 风险与限制

风险缓解
native 中断时副作用工具被重复执行执行前写意图、接管时不盲目重放（§5.1）；只读工具声明幂等直接重放
假死后复活的实例与接管者双写续租返回 0 行即停止本地执行；落检查点时校验 owner = 本实例，不是自己的 run 不写
接管时重新调用模型的成本检查点粒度是工具轮次，最多重放一次模型调用；交接走安全点，正常发布零重放
每轮落检查点增加数据库写入一轮一个事务，批量写消息与事件；相比模型调用的耗时可以忽略，落库耗时进指标
Redis 不可用时唤醒与事件流中断领取靠定期扫描兜底（数据库为真相）；事件流中断期间前端退化为轮询会话状态（P3）
ACP Pod 在 server 断开期间被回收Pod 回收只针对已删除会话（§7.1）；会话 Pod 的空闲回收以「最近活动」为准，run 进行中的 Pod 持续有活动
