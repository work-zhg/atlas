Skill Management

技能管理设计

技能的增删改查、版本化，以及与 Agent 的关联。核心判断只有一条：技能是可执行的内容，不是配置 —— 它包含给模型的指令，也包含真正会跑的脚本，所以审查按代码审查来做。

版本不可变安全审查Agent 关联渐进披露

01定位与边界

技能是给 Agent 的可复用工作方法：怎么做代码评审、怎么写 API 文档、怎么排查某类故障。它不是知识（那是 RAG），也不是工具（那是可调用的函数），而是一段在特定场景下该如何行动的指引。

技能是可执行的内容，不是配置

一个技能包里有两样东西会真正「运行」：

  • SKILL.md 的正文 —— 进入模型上下文，被当作要遵循的指令
  • scripts/ 里的脚本 —— 模型可以真的去执行它们

所以一个恶意或错误的技能能做的事，和一段恶意代码差不多：指示模型执行危险命令、用指令覆盖系统提示里的约束、把用户的上下文发到外部地址。技能审查 ≈ 代码审查，不是文档审查。

不在本文范围

  • 技能内容本身怎么写才好 —— 那是技能作者的事，本文管的是流程与机制
  • 哪个 Agent 该挂哪些技能的产品判断 —— 见Agent 管理
  • 技能在 Pod 内的挂载细节 —— 见运行时链路 §08
  • 跨用户的领域知识 —— 那是 RAG，见记忆 §01

02技能的结构

沿用 Claude Code 的技能格式，这样平台技能与 CLI 原生技能可以互通（实测自一个真实技能包）：

my-skill/
├── SKILL.md            必需
│   ├── frontmatter     name + description  → 进索引，始终可见
│   └── 正文             → 命中后才加载
├── references/         按需读取的参考文档
├── scripts/            可执行脚本
└── data/               数据文件
---
name: ui-ux-pro-max
description: "UI/UX design intelligence for web, mobile, and desktop.
  This skill should be used when designing, building, reviewing…
  Skip it for pure backend logic, API/database design…"
---

# UI/UX Pro Max
…正文…

渐进式披露决定了容量上限

实测一个技能包可以到 3.8MB，显然不可能全部塞进上下文。所以只有 frontmatter 进索引，正文与资源在技能被选中后才加载。

真正的容量瓶颈是索引，不是技能包大小

技能包再大也只在被用到时才付出代价，但每个技能的 description 都常驻上下文。挂 50 个技能，就是 50 段描述常驻 —— 它们挤占的是每一轮对话的预算。

所以「一个 Agent 挂多少技能合适」的约束来自索引膨胀，而不是存储。这也让 description 的简洁与准确同时成为硬指标（§08）。

03数据模型

CREATE TABLE skills (
  skill_id     TEXT        NOT NULL,
  version      INT         NOT NULL,
  status       TEXT        NOT NULL,   -- draft | published | disabled

  -- 来自 SKILL.md frontmatter，解析时提取
  name         TEXT        NOT NULL,
  description  TEXT        NOT NULL,

  -- 内容
  content_uri  TEXT        NOT NULL,   -- 技能包存储位置
  content_hash TEXT        NOT NULL,   -- 完整性校验
  size_bytes   BIGINT      NOT NULL,
  has_scripts  BOOLEAN     NOT NULL,   -- 含可执行内容，审查等级更高

  -- 来源与审查
  source       TEXT        NOT NULL,   -- builtin | tenant | imported
  scan_result  JSONB,                  -- 各层扫描的结论
  scan_at      TIMESTAMPTZ,
  reviewed_by  TEXT,                   -- 人工审查者

  created_by   TEXT        NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL,
  published_at TIMESTAMPTZ,

  PRIMARY KEY (skill_id, version)
);

-- 一个技能同时只能有一个 draft
CREATE UNIQUE INDEX uq_skill_draft ON skills (skill_id)
  WHERE status = 'draft';
版本不可变，与 Agent 同一套规矩

published 的版本永不修改 —— 因为 Agent 版本可能固定引用了它（§06），改了等于绕过 Agent 的版本不可变承诺。

更新技能 = 发布新版本。draft 可反复改，但不能被任何已发布的 Agent 版本引用。

has_scripts 单独立一个字段，是因为它直接决定审查等级：只有 Markdown 的技能和带 Python 脚本的技能，风险不在一个量级（§05）。

04生命周期

各阶段做什么

阶段动作
上传接收目录或 zip；大小上限；条目数上限
解析SKILL.md 存在性、frontmatter 合法性、name 唯一性、提取 description、统计 has_scripts
自动扫描四层检查，见 §05。有 blocker 直接拒绝
人工审查has_scripts 或 source != builtin 时必经
发布冻结为不可变版本，计算 content_hash，可被 Agent 引用

05安全审查

分四层，从机械到智能，前三层自动、第四层人工。前面的层拦不住的才交给后面，但后面的层不应该被用来兜前面的底。

层检查拦什么
1归档安全 解压路径穿越（../）、符号链接逃逸、二进制可执行文件、解压后总大小与条目数炸弹。这层是纯机械判断，有命中一律拒绝
2结构与元数据 缺 SKILL.md、frontmatter 不合法、name 冲突、description 过长或缺失、单文件超限
3内容模式扫描 密钥与凭证模式、可疑外部地址、危险命令模式（curl … | sh）、提示词注入特征（「忽略之前的指令」「你现在是…」）
4人工审查 意图层面的问题：这个技能想让模型做的事合理吗？脚本做的事和它声称的一致吗？
含脚本的技能必须人工审查，没有例外

模式扫描能发现curl | sh 这种明显的东西，但发现不了一段逻辑正确、意图不良的代码。而脚本是真的会执行的 —— 在 Pod 里是我们的算力与凭证，在本地部署里是用户自己的机器（本地部署 §05）。

把「自动扫描通过」当作可以跳过人工的理由，是这套流程里最容易出的错。自动扫描的作用是省掉明显不合格的，不是替代判断。

提示词注入是技能特有的攻击面

SKILL.md 的正文会进入模型上下文并被当作指令。这意味着一个技能可以尝试覆盖系统提示里的约束 —— 比如让模型跳过审批、或者把上下文内容发到某个地址。

对 native 类型，我们构造提示词时可以把技能内容放进明确标记的边界里，并声明它的优先级低于系统约束。对 acp 类型，这取决于 CLI 怎么处理，我们无法保证 —— 又一处只能靠发布前审查的地方。

扫描结果要留存

scan_result 记下每层的结论与命中项。用途有二：出问题时回溯「当时扫描说了什么」，以及扫描规则升级后重扫存量技能 —— 新规则往往能发现老技能里被漏掉的问题。

06Agent 关联与版本引用

Agent 定义里的 skills 字段决定它挂哪些技能。引用方式有两种，可以混用：

agents.skills = [
  "code-review",        // 引用名：自动跟随最新发布版本
  "api-docs@3"          // 引用版本：固定在 v3，技能更新不影响
]
引用名（宽松）引用版本（严格）
技能更新后自动生效不受影响
Agent 版本决定行为否是
技能迭代成本低要逐个 Agent 发版
适用多数场景对确定性要求高的 Agent
引用名会让「版本不可变」出现缺口

Agent 管理 §03 承诺「同一个 Agent 版本行为一致」。引用名的技能会打破这个承诺 —— 技能更新后，同一个 Agent 版本的实际行为变了。

这是个有意接受的取舍：强制逐个发版会让技能迭代寸步难行。但它必须被写下来，别让人以为「版本号一样行为就一样」。对确定性要求高的场景，用 @version 固定。

发布时校验引用

for ref in agent.skills:
    skill = resolve(ref)                       # name 或 name@version
    if skill is None:
        raise PublishRejected(f"技能不存在：{ref}")
    if skill.status != "published":
        raise PublishRejected(f"技能未发布：{ref}")

# 索引预算
total = sum(len(s.description) for s in resolved)
if total > INDEX_BUDGET:
    raise PublishRejected(f"技能索引超预算：{total}")   # §02

反向查询同样重要

管理界面必须能回答「这个技能被哪些 Agent 引用了」。它是停用前的必查项（§09），也是评估技能改动影响面的唯一依据 —— 改一个被十个 Agent 引用的技能，和改一个没人用的，风险完全不同。

07两类 Agent 的下发差异

nativeacp
下发方式双路：正文进提示词，scripts/ 等挂进 Sandbox Pod整包挂载到 CLI 的技能目录
解析方我们自己CLI
能否裁剪/防护能不能
生效时机下一轮Pod / 进程启动时
在途会话不受影响 —— Agent 版本已钉住
native 不是「只进提示词」—— 脚本要能跑

技能的 SKILL.md 里可能直接指示模型执行脚本（实测一个真实技能就写着 python …/scripts/search.py）。所以 native 的技能必须双路下发：正文进提示词，scripts/ / references/ / data/ 挂进 Sandbox Pod。

而且提示词里声明的路径必须与 Pod 内的实际挂载点一致，否则模型照着提示词执行就会找不到文件。详见 native Agent §05。

acp 的挂载方式

见 运行时链路 §08：只读卷挂到 ~/.claude/skills，或用 --plugin-dir 按会话指定。

按 Agent 下发不同技能集，别在一个大卷里挑

用 subPath 从共享卷里挑技能，会让「这个 Agent 能看到哪些技能」散落在部署模板里，和 agents.skills 这份配置产生两个真相源。

能力边界应当是可查询的配置，不是挂载表的副产品。要么按 Agent 准备独立的卷，要么用 --plugin-dir 显式指定。

本地部署：不要动用户的技能目录

用户机器上的 ~/.claude/skills 是他自己的

平台下发技能时，不能直接往用户的技能目录里写文件 —— 那会和他自己安装的技能混在一起，卸载时也分不清哪些是平台放的。

应当用会话级的机制（如 --plugin-dir 指向一个平台管理的独立目录），并纳入 本地部署 §07 的授权范围。静默修改用户的配置目录，无论意图多好都是越界。

08描述质量决定选择质量

description 是模型判断「该不该用这个技能」的唯一依据

渐进式披露意味着模型在选择时只看得到 description，看不到正文。写得含糊，技能就选不中；写得宽泛，就到处乱选。

所以它不是附属说明，而是技能质量的核心指标。一个正文写得再好的技能，description 不行就等于没有。

好的 description 包含三件事

1. 这个技能做什么
2. 什么时候该用      ← 触发条件，越具体越好
3. 什么时候不该用    ← 常被忽略，但它能显著减少误选

实测的一个例子就明确写了「Skip it for pure backend logic, API/database design…」—— 排除条件和触发条件一样重要。

技能之间的描述冲突

两个技能的 description 高度相似时，模型会选错或随机选。发布时应当做相似度检测，命中就提示作者澄清边界，而不是等上线后靠用户反馈发现。

选中率是必须监测的指标

长期零命中是静默失效

一个技能挂上去但从来没被选中，不会报任何错 —— 它只是白白占着索引预算。这和 记忆 §11 里「检索命中率为零」是同一类问题：功能等于没有，但没有任何信号。

按技能统计选中次数与选中后的完成情况，接入可观测性（§07）。长期为零就该复查 description 或直接下掉。

09停用与删除

draft ──发布──→ published ──发新版──→ published(v+1)
                    │
                    ↓ 停用
                 disabled  ← 不能被新的 Agent 版本引用
                    │        已引用它的 Agent 版本继续可用
                    ↓ 引用归零且会话全部结束
                  可清理
有 Agent 版本引用就不能删

和 Agent 管理 §09 的 deprecated 同理：只要还有 Agent 版本引用某个技能版本，它的内容就必须保留 —— 否则那个 Agent 版本无法装配，存量会话无法恢复，审计也回溯不了「当时它挂的技能是什么」。

停用是「不再可被新引用」，不是「删掉」。真正的清理要等引用归零、且引用它的会话全部结束，那通常是很久以后。

紧急下架

发现技能有安全问题时，「停用」不够 —— 它只挡住新引用，已引用的 Agent 照常装配。需要一个紧急下架动作：

  • 标记为 revoked，所有引用它的 Agent 装配时跳过该技能并记录告警
  • 已在运行的会话：native 下一轮即生效；acp 需要重启 Pod 才能生效 —— 要如实告知影响范围与生效时间
  • 列出受影响的 Agent 与活跃会话，供运维决定是否强制中止

这和 记忆 §10 的删除生效时机是同一类问题：在 acp 一侧，我们的撤销总是慢一拍，这一点不能对用户隐瞒。

10来源与权限

来源谁能上传审查要求
builtin平台管理员随平台发布，走代码评审流程
tenant租户管理员全部四层；含脚本必经人工
imported平台管理员第三方来源，一律人工审查，且需记录来源出处
租户技能只对本租户可见

租户上传的技能不得出现在其他租户的 Agent 里。这条听起来显然，但因为技能是按 name 引用的，命名空间必须按租户隔离 —— 否则两个租户各有一个叫 code-review 的技能，解析时就会撞车。

本期建议：先不开放租户自建

和 Agent 管理 §10 同样的理由：一旦开放，安全审查就从「管理员的一道流程」变成「必须防住不可信输入的边界」，而技能里可以放可执行脚本，攻击面比 Agent 定义大得多。

先把平台内置技能跑稳，把 §05 的四层扫描在真实技能上验证过，再考虑开放。

11待验证清单

#验证项影响
1 技能索引的实际预算 —— 挂多少个技能后 description 开始明显挤占上下文、影响回答质量 决定 §06 的索引上限取值，以及单个 Agent 挂技能的数量建议
2 选中准确率 —— 用真实任务样本测试模型是否选对技能，以及 description 改写对它的影响 决定 §08 的描述规范要写到多细
3 CLI 对技能目录的实际解析行为 —— 是否有大小/数量限制、格式容错度、加载时机 决定 §07 的挂载方式与技能包体积上限
4 提示词注入的实际防护效果 —— 构造带注入意图的测试技能，验证 native 侧的边界标记是否有效 决定 §05 第三层扫描的必要强度
5 --plugin-dir 在目标 adapter 上是否可用（按会话指定技能集） 决定 acp 侧能否避免动用户的技能目录（§07）

建议的实现顺序

  1. 先做 CRUD + 版本 + 引用校验 —— 内置技能先跑通，来源可控，审查压力最小。
  2. 再做自动扫描的前两层 —— 归档安全与结构校验是纯机械判断，见效快且不会误伤。
  3. 然后是选中率监测 —— 它决定后续所有质量优化的方向，越早有数据越好。
  4. 内容扫描与人工审查流程最后 —— 在开放租户自建之前必须完成，之前可以从简。
