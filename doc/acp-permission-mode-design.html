0. 第 0 期验证结果（2026-10-03）

方法：临时镜像 atlas-acp-bridge:0.3.0-rc，只把 adapter 换成 @agentclientprotocol/claude-agent-acp@0.85.1。① 在容器里用 bridge 自带的 AcpClient 直连 adapter；② 走平台完整链路（server → cluster → Pod → bridge）。CLI 模型都是 deepseek-chat。

验证项结果对设计的影响
新 adapter 和现有 bridge 能否配合 通过 全链路四轮全部成功：写文件 + 执行命令（审批走平台）、同一 Pod 上第二轮、删掉 Pod 后跨 Pod 恢复会话（不读文件，凭记忆答出之前创建的文件名）、取消 第 1 期（只升级镜像）可以直接做
DeepSeek 下 auto 是否可用 可用，没有降级 set_mode(auto) 生效，实际模式就是 auto。adapter 拿不到 deepseek 的模型信息（models.current 为空），所以不会触发"模型不支持就降级"的检查。判断器的请求发给配置好的 DeepSeek 接口（CLI 的提示原文是 “auto mode keeps working, and its classifier requests are billed as before … go through api.deepseek.com”） 修正第 7 节：原来"DeepSeek 大概率会被降级成 acceptEdits"的推断不成立。降级的显示逻辑仍然保留（以后换模型可能会触发）
auto 的判断器有没有真的在拦截 在拦截 rm -rf /state/*（删除工作区以外的目录）被判断器拒绝，原因为 [Unverifiable Deletion Target]。写文件、ls、date、rm 工作区内的文件都直接放行 auto 确实是"有判断的放行"，不等于 bypass
auto 下有风险的操作是"请示"还是"拒绝" 是拒绝 所有 auto 测试里请示次数都是 0。被拦的操作以工具失败结束，失败信息里带着原因，模型收到后会自己调整做法或停下来说明 新增决策 D8（见下）：在 auto 下，审批卡片基本不会出现；被拦的操作以失败的工具行呈现，用户没有地方批准它
default 模式（基线） 写文件请示，rm 请示，只读命令（ls、date）不请示 与预期一致
协议细节变化 权限选项的 id 从 allow 变成了 allow-once；adapter 入口变成 …/@agentclientprotocol/claude-agent-acp/dist/index.js；能力位新增 fork、list、delete、subagents server 按选项的 kind（allow_once）选择，不受 id 变化影响。入口路径变了，第 1 期必须保留旧路径的软链接
D8：auto 拒绝的操作，用户怎么处理？——已选 A（2026-10-04）。 现在的设计里，被 auto 拒绝的操作只会表现为一个失败的工具行，用户无法批准它；"用户在会话里临时切换模式"又已经决定不做。可选的做法：
A. 接受这个行为：失败的工具行上显示拒绝原因；确实需要做的事，由作者把智能体的模式改成 manual。
B. 被拒绝时，在对话里给出一张"此操作被自动模式拦截"的卡片，提供"本轮改用手动模式重试"的按钮。这实际上就是有限范围的用户覆盖。
建议先做 A，并且在界面上把"被自动模式拦截"和普通的工具失败区分开显示。

1. 现状与关键事实

1.1 Adapter：auto 只在新包里

包版本Claude Agent SDK可用模式状态
@zed-industries/claude-code-acp（镜像当前在用）0.16.20.2.44 default · acceptEdits · plan · dontAsk · bypassPermissions无 auto，已停更
@agentclientprotocol/claude-agent-acp（迁移后的新包）0.85.10.3.286 default（Manual）· acceptEdits · plan · auto · bypassPermissions有 auto

新包里 auto 的定义是 “Claude handles permission decisions”：由 Claude Code 自己判断哪些操作可以直接执行。它没法自己判断的，仍然会走 session/request_permission 来请示（acp-agent.js 的 canUseTool 注释写明：能走到这个回调的请求，模式不会自动放行）。

1.2 模式在每次打开会话时都会重置

  • 旧包：newSession、loadSession、resumeSession 都写死 permissionMode = "default"（acp-agent.js:768），通过 _meta 也覆盖不了。
  • 新包：初始模式取自 Pod 里 settings.json 的 permissions.defaultMode，没有就是 default。
  • 两个版本都支持协议的标准方法 session/set_mode，新包另外也支持 session/set_config_option（configId = "mode"）。
直接后果：模式不能"设置一次就一直有效"。下面这些时刻，CLI 都会回到默认模式：bridge 新建或恢复会话、CLI 崩溃后被 bridge 重启并恢复会话、Pod 重建。重新应用模式只能由 bridge 负责，因为只有它知道 CLI 什么时候重启过。

1.3 auto 依赖模型能力

CLI 实际用的模型：不是子智能体 spec 里的 model，而是 cluster 的全局配置 ATLAS_CLUSTER_MODEL_NAME=deepseek-chat、MODEL_BASE_URL=https://api.deepseek.com/anthropic，生成 Pod 时注入为 ANTHROPIC_MODEL 和 ANTHROPIC_BASE_URL（cluster/template.py:344-356）。所有会话 Pod 共用这一个模型，子智能体 spec 里的 model 对 CLI 不起作用。

新包在 session-mode.js 里检查 ModelInfo.supportsAutoMode：模型不支持时，auto 会被自动降级为 acceptEdits，并发出一条 “Auto mode unavailable” 提示。CLI 现在用的是 deepseek-chat（直连 DeepSeek 的 Anthropic 兼容接口），大概率不支持，需要实测确认（见第 7 节）。

1.4 平台这边的现状

层现状
SpecCliSpec 只有 cli_type、adapter、image 三个字段，没有模式
上游协议 atlas.host.v1session.open 和 turn.start 都没有模式参数
bridgeAcpClient.new_session 只取 sessionId，丢弃了响应里的 modes；从不调用 session/set_mode
审批CLI 每次请求权限，都会变成对话里的一张审批卡片，没有等待上限（上一轮刚改的）。默认模式下，写文件、执行命令都要人点

2. 目标与非目标

目标非目标
  • 智能体作者可以给 ACP 子智能体（以及直接对话的 ACP 智能体）配置权限模式，其中包括 auto
  • 这个模式在会话的整个生命周期里始终生效：新建、恢复、CLI 崩溃重启、Pod 重建之后都一样
  • 用户看得到实际生效的模式；降级了（比如 auto → acceptEdits）也要明确提示
  • auto 下仍然需要请示的操作，照常走对话里的审批卡片
  • 不让模型通过 task 工具自己选择权限模式，防止模型给自己提权
  • 不在平台侧自己实现一套"自动审批"分类器，判断交给 CLI
  • 不改 Native 智能体自己的审批机制（require_approval_for）
  • 不做"会话中途由用户临时切换模式"（2026-10-03 决定）
  • 不做 bypassPermissions（2026-10-03 决定）

3. 关键决策

#决策备选方案取舍理由
D1 模式由 CLI 原生实现：升级 adapter，并用 ACP 的 session/set_mode 设置 A. 平台自己做自动审批：server 收到 permission.ask 后直接按允许答复
B. 往 Pod 里写 settings.json，设置 defaultMode 		A 违反 bridge "绝不自动批准"的原则，而且平台不知道哪些操作安全，相当于全部放行。B 是 Pod 级别的配置，同一 Pod 里没法按每一轮切换，而且模式失效后（比如降级）平台无法感知。set_mode 是协议标准方法，新旧两个包都支持
D2 模式配置在 spec 上：CliSpec.permission_mode，由智能体作者设置，随智能体版本快照 A. 作为 task 工具的参数，由父模型每次委派时选择
B. 由用户在会话里设置 		A 等于让模型给自己提权，被提示注入时风险最大。B 不做（2026-10-03 决定）。放在 CliSpec 上，直接对话的 ACP 智能体和作为子智能体的 ACP 智能体都能复用
D3 模式随 turn.start 下发，bridge 在发出 prompt 之前，按需调用 session/set_mode 放在 session.open 的 defaults 里 会话已经打开时（attach、ALREADY_OPEN）不会走 open，智能体换版本后模式也就不会更新。放在每一轮的开头，会话的任何状态都能覆盖到，而且 turn.start 本身是幂等的。bridge 会记住"期望的模式"，CLI 崩溃并恢复会话后自动重新应用
D4 设置失败不让这一轮失败：回退到当前实际生效的模式继续执行，并发出 mode_degraded 提示 直接让这一轮失败 模式只影响"要不要问人"。降级到更保守的模式，最坏的结果是多弹几张审批卡片，不会造成误操作；而让这一轮失败，用户就得重试。唯一的例外：要求更保守的模式（比如 plan）但没能设置成功时，这一轮失败，避免以比预期更宽松的权限执行
D5 不提供 bypassPermissions（2026-10-03 决定） 由管理员开关控制是否开放 它会跳过所有检查，而工作区是父会话共享的，Pod 里还有模型凭据。没有明确需求，就不引入这个风险面。spec 校验只接受下表里的四个值
D6 上报实际生效的模式：turn.state(running) 带上 mode 字段，server 转成事件，前端在委派卡片上显示 只记日志 auto 会被模型能力悄悄降级。不显示出来的话，用户会以为是 auto，实际却是 acceptEdits，命令还是要一个个点
D7 默认值为 auto（2026-10-03 决定），包括已有的 ACP 智能体：spec 里没有这个字段时也按 auto 处理 默认 manual，保持现有行为 减少长任务里的打扰。代价：已有智能体的行为会变，从"每次都请示"变成"文件编辑自动通过"。在 DeepSeek 上执行命令仍然要请示（见第 7 节），所以变化主要在文件编辑上。上线说明里要写明这一点

支持的模式（平台对外的取值）

平台取值ACP modeId行为适用场景开放范围
manualdefault编辑文件、执行命令都要请示敏感工作区所有人
accept_editsacceptEdits文件编辑自动通过，命令仍要请示写代码为主所有人
auto（默认）auto由 Claude 判断；它判断不了的仍要请示。模型不支持时降级为 accept_edits希望少打扰的长任务所有人（需要升级 adapter）
planplan只规划，不执行工具只想要方案所有人

不对外提供 bypassPermissions（见 D5），也不对外提供 dontAsk（没有预先授权的操作一律拒绝）：它不会请示人，在平台场景下的效果只是让 CLI 默默做不成事。

5. 协议与数据改动

5.1 Spec（server）

# domain/spec.py
PermissionMode = Literal["manual", "accept_edits", "auto", "plan"]

@dataclass(frozen=True)
class CliSpec:
    cli_type: str
    adapter: str
    image: str
    #: ★ 有默认值是快照纪律：历史 agent_version.spec 里没有这个字段。
    #:   默认 auto（D7）：已有的 ACP 智能体也按 auto 运行
    permission_mode: PermissionMode = "auto"
  • 校验：只接受上面四个值，其他值以 InvalidSpec 拒绝保存。
  • schemas/agent.py 的入参与出参同步加这个字段；前端执行 gen:api 重新生成类型。

5.2 上游协议 atlas.host.v1（新增可选字段，向后兼容）

# host/messages.py
class TurnStartParams(Model):
    ...
    #: ACP 的 modeId。None = 不管，保持会话当前的模式（旧 server 的行为）
    mode: str | None = None

class ModeState(Model):
    requested: str | None      # server 要的
    effective: str             # adapter 实际生效的
    available: list[str]       # adapter 支持的
    degraded: bool = False     # requested 与 effective 不一致

class TurnStateParams(Model):
    ...
    #: 只在 state = running 时带
    mode: ModeState | None = None

class AgentRestart(Model):     # session.state 里的 agent
    ...
    mode: ModeState | None = None

兼容性：旧 server 不发 mode，新 bridge 就不调用 set_mode，行为与现在一致。新 server 连旧 bridge 时，旧 bridge 会忽略这个字段；server 从 turn.state 里收不到 mode，就认为模式"未知"，前端不显示模式标签。

5.3 ACP 层（bridge ↔ adapter）

  • AcpClient.new_session、load_session、resume_session 返回值里加上 modes（SessionModeState），不再丢弃。
  • 新增 AcpClient.set_mode(session_id, mode_id)，调用 session/set_mode，走现有的 ACP 请求超时（30s）。
  • 处理 session/update 里的 current_mode_update：更新 bridge 记录的实际生效模式。adapter 自己切换模式时也会发这个通知，比如 auto 降级、或者在 plan 模式下用户同意退出规划。

7. 模型兼容与降级

更新（第 0 期实测）：DeepSeek 下 auto 可用、没有降级，判断器的请求走的就是 DeepSeek 接口，见第 0 节。下面这段是验证之前的推断，保留作为背景。
这是这个功能能否真正可用的前提。auto 的判断由 Claude 模型完成，adapter 依据 SDK 返回的 supportsAutoMode 决定能否启用。我们的 CLI 直连 DeepSeek 的 Anthropic 兼容接口使用 deepseek-chat，SDK 很可能认为它不支持，于是 auto 会一直被降级成 acceptEdits：文件编辑自动通过，执行命令仍然要请示。
情况效果平台的处理
CLI 使用的模型支持 auto（Claude 系）真正的 auto委派卡片显示 Auto
不支持（DeepSeek 等非 Claude 模型）降级为 acceptEdits委派卡片显示黄色标签 Auto → 接受编辑；编辑器保存时给出提示："当前模型可能不支持 Auto，将以'接受编辑'运行"
运行中途 CLI 切换了模型adapter 自己重新判断（reconcileForModel）通过 current_mode_update 同步给前端

第 0 期的验证项：用新 adapter 分别配 deepseek-chat 和一个 Claude 模型，各跑一次，记录 supportsAutoMode 和实际生效的模式。如果目标模型都不支持 auto，这个功能对用户的实际价值就等于 acceptEdits，需要重新评估是否值得做。

8. 安全与审计

关注点措施
模型给自己提权模式只能来自智能体作者配置的 spec。task 工具没有这个参数；子智能体的系统提示词也改变不了模式
提示注入诱导 CLI 越权auto 的判断在 CLI 内部完成；平台层的隔离不变：Pod 非 root、只能看到工作区、出网受限（cluster 模板）
bypass 的风险不提供这个模式（D5）
审计run.started 记录配置的模式，agent.mode 事件记录实际生效的模式，两者都进归档表。哪个 run 在什么模式下执行过什么，可以追溯
审批原则不变CLI 请示的操作仍然没有等待上限，只由人决定。平台不会因为配置了 auto 就自动替用户批准
