三条已定的原则（2026-10-16 拍板）
  1. 内网免令牌：链路是 前端 → 网关（只在这里校验令牌）→ 内网应用。用户中心、Atlas、TeamFlow、知识库之间互相调用不带令牌，uid 等身份参数放在请求头里逐跳传递。
  2. 授权看 X-Auth-Uid：请求头分两个字段。X-Uid 是「谁在用」（人），X-Auth-Uid 是「按谁的权限判」。Agent 干活时 X-Auth-Uid 就是这个 Agent 的数字员工。Agent 能读哪些知识库、能用多少 Pod 配额，都是 Agent（数字员工）自己的配置；用户 1 和用户 2 只要能用这个 Agent，就能得到同样的结果。
  3. 产物跟数字员工走：每个数字员工开一个 GitLab 账号，Agent 提交代码用它自己的账号，仓库权限授给这个账号。
由此：Atlas 服务账号整体下线（密钥、代表用户、页面、操作码）。知识库、TeamFlow、评测同步改造。
实现记录（2026-10-19）与设计的偏差
  1. §5 不做（决定）：NetworkPolicy 与知识库 MCP 拆端口都不做。§2 所说的风险因此是已接受的：会话 Pod 里的代码能直接带伪造的请求头访问内网服务。Pod 级令牌（bridge、sandbox、知识库 MCP）照常保留。
  2. 应用编码：用户中心原来没有「应用编码」，新增 uc_app.code（迁移 u0005，存量按名称回填 Atlas → atlas、AI TeamFlow → teamflow）。知识库、配置服务属于 Atlas 应用，调用户中心时 X-Caller-App 写 atlas。
  3. 租户缺省：开放接口的租户按 X-Tenant-Id → X-Uid 所属租户 → 唯一租户 依次推定，不是「没有就 400」（多租户且三者都没有时才 400）。后台任务（TeamFlow 监督器、Atlas 的 run）因此只需要记 uid，不必各表加租户列。
  4. git 档案：P1 还没有数字员工，allowed_users（TeamFlow 服务账号）改为 allowed_apps: ["teamflow"]，按会话的 source_app 判断（§9 的「auth-uid 是数字员工」留到 P2）。
  5. 开放接口：/open/v1/auth/verify-password 删除；/open/v1/auth/token 与应用令牌的签发保留，给以后经网关接入的外部应用（§4），但 /open/v1 的各接口只认请求头。
  6. 监督器的 X-Uid：建会话、跟事件流 = 流程发起人；投递人写的指令 = 指令作者（没有作者的系统投递才用发起人）。
  7. 业务应用的会话：source_app 非空时，同一应用来访不要求 uid = 所有者；从别处（网关）来只读，写操作 403。查看别人的会话仍只认所有者（没有加「全部智能体 · Owner 可看」）。业务应用可以显式要求打开记忆（评测的跨会话记忆用例）。
  8. 知识库 owner_kind：列先保留，sync-uc --service-owner <atlas-bench 用户> 把存量服务账号的库登记到用户中心后再删。
  9. 存量会话：迁移 0020 按服务账号名回填 source_app，不改所有者 —— TeamFlow 的节点会话经 TeamFlow 照常可用；要出现在发起人的会话列表里，跑 python -m atlas_teamflow export-thread-owners > map.json 再 python -m atlas_agent reassign-threads map.json。

3. 身份请求头规范

请求头含义谁写入缺省
X-Tenant-Id租户 uuid。用户中心的自动租户过滤以它为上下文（租户设计 §06，原来从应用令牌推出）网关（来自登录态）；内网调用原样透传没有就 400（用户中心本来就对缺上下文抛 MissingTenant）
X-Uid谁在用：真实的人。决定会话归属、记忆、审计里的「发起人」、能不能用这个 Agent网关（登录用户）；TeamFlow 监督器自动投递时写流程发起人（§10）无（必填）
X-Auth-Uid按谁的权限判：操作码、数据权限、配额、git 凭据全看它只有 Atlas 的运行时会把它设成数字员工（run 期间发出的所有调用）；其他调用方不写缺省 = X-Uid（人直接操作时，两者相同）
X-Caller-App直接调用方的应用编码：gateway、atlas、teamflow、knowledge、bench…每个内网应用在自己发出的请求上写自己的编码（覆盖上一跳的值，不透传）没有就当作 unknown，只记审计、不放行特权路径
traceparent / X-Request-Id链路追踪网关生成，逐跳透传—

3.1 规则

  • 网关先剥后写：外部请求带进来的身份头一律丢弃，以登录态为准，再写 X-Uid、X-Tenant-Id。外部永远写不进 X-Auth-Uid。
  • 透传而不是重算：内网应用调下游时，原样转发 X-Tenant-Id、X-Uid、X-Auth-Uid，只把 X-Caller-App 换成自己的编码。
  • 只有 Atlas 能「换成数字员工」：把 X-Auth-Uid 改为数字员工 uid 的只有 Atlas 运行时这一处（它知道这一轮跑的是哪个 Agent）。TeamFlow 调 Atlas 时不写 X-Auth-Uid，由 Atlas 根据 Agent 自己决定。这条靠代码评审和审计来保证，网络层做不到（见 §16 风险 1）。
  • 不从参数读身份：uid、租户只认请求头，不接受 body 或 query 里的 user_id（沿用「service 层不自己取身份」的纪律）。
  • 每个服务各写约 30 行解析，不抽公共包。这沿用 knowledge/auth.py 里「与 atlas-config 各自实现」的先例，规则很少，抽包反而增加发版耦合。
# 各服务的依赖（示意，以知识库为例）
@dataclass(frozen=True)
class Principal:
    tenant_id: str
    uid: str                 # 谁在用
    auth_uid: str            # 按谁判（缺省 = uid）
    caller: str
    operations: frozenset[str]   # 按 auth_uid 取用户中心授权快照（进程内缓存 + authz:invalidate 广播失效）

async def current_principal(req: Request, uc: UCDep) -> Principal:
    uid = req.headers.get("x-uid") or raise_401()
    auth_uid = req.headers.get("x-auth-uid") or uid
    snap = await uc.authz(auth_uid)            # 数字员工也是用户中心用户，同一个接口
    return Principal(req.headers["x-tenant-id"], uid, auth_uid,
                     req.headers.get("x-caller-app", "unknown"), frozenset(snap["operations"]))

4. 网关

不新增组件：deploy/local/40-frontends.yaml 里的 nginx 已经是三个前端和各个 API 的唯一入口（含 /atlas-api/、/uc/api/、/teamflow/api/、/atlas-knowledge-api/），并且已经挡掉了 /internal/。把它升级为网关只需要加 auth_request。

location = /_auth {
  internal;
  proxy_pass http://atlas-usercenter.atlas-system.svc.cluster.local:8030/api/v1/auth/verify;
  proxy_pass_request_body off;
  proxy_set_header Content-Length "";
  proxy_set_header X-Original-Method $request_method;   # 写请求在 verify 里校验 CSRF
  proxy_set_header X-Original-URI    $request_uri;
}
location ^~ /atlas-api/ {
  auth_request /_auth;
  auth_request_set $uid    $upstream_http_x_uid;
  auth_request_set $tenant $upstream_http_x_tenant_id;
  proxy_set_header X-Uid        $uid;
  proxy_set_header X-Tenant-Id  $tenant;
  proxy_set_header X-Auth-Uid   "";          # 外部永远不能指定
  proxy_set_header X-Caller-App gateway;
  proxy_pass http://atlas-server.atlas-system.svc.cluster.local:8000/;
}
# 登录、静态资源、预览站点（令牌在路径里）不加 auth_request
事项设计
统一登录只保留用户中心的登录（企业代码 + 账号 + 密码，已有锁定和强制改密），Cookie uc_session 的 Path 为 /。Atlas 的 /v1/auth/login、auth_session 表和 TeamFlow 的 tf_session 下线，三个前端未登录时都跳到 /uc/login?next=…。
verify 接口用户中心新增 GET /api/v1/auth/verify：校验会话 → 200 并返回响应头 X-Uid、X-Tenant-Id；未登录返回 401（网关把 401 转给前端去跳登录）。写请求校验 CSRF 双提交（Cookie uc_csrf 对比请求头），这一步从各应用挪到这里统一做。
性能每个请求都要 verify 一次：用户中心侧做进程内会话缓存（短 TTL）；网关可以加 proxy_cache，以 Cookie 为键缓存 5–10 秒。SSE 长连接只在建连时 verify 一次。
只暴露网关atlas-server、用户中心、TeamFlow、配置服务的 Service 从 LoadBalancer 改为 ClusterIP。现在 localhost:8000/8030/8040 直连是绕过网关的后门，必须关掉。运维要直连时用 kubectl port-forward，持有 kubectl 本来就等于集群管理员，不算新增风险。
外部第三方应用如果以后有外部系统要调接口：在网关上校验应用令牌（沿用用户中心现有的 App Key / Secret 换令牌），网关写入 X-Caller-App=<应用>。内网应用不再使用这条路。
Keycloak（以后）只换 /_auth 背后的校验（JWT 验签或 introspect），内网协议不变。这与「用户中心不自建 OIDC」一致。

5. 信任边界：网络隔离（前置条件）

5.1 NetworkPolicy

策略内容
atlas-system 默认拒绝入站只放行：同命名空间的 Pod（应用之间互调）、网关 Pod → 各服务端口
atlas-sessions 默认拒绝出站只放行：知识库 MCP 专用端口（§5.2）、模型代理、对象存储、GitLab、DNS；atlas-server → Pod 的 bridge 连接属于入站方向，放行
按端口而不是按路径NetworkPolicy 是四层的，区分不了 /mcp 和 /internal，所以面向 Pod 的接口要单独开端口

5.2 知识库 MCP 拆端口

现在 /mcp 和 /api、/internal 共用 8050 端口。改为：MCP 单独监听 8051（同一进程，另起一个 ASGI 应用），Pod 只能访问 8051；8050 只对 atlas-system 开放。

5.3 为什么 Pod 级令牌要保留

这些令牌和「服务间令牌」不是一回事：会话 Pod 不可信，它们是可信区签发给不可信代码的、带范围的一次性能力（某个会话、某几个库）。去掉后 Pod 就能访问任意库。保留三种：bridge token、sandbox token、知识库 MCP 签名令牌。MCP 令牌的内容从 {"d","t","u":发起人} 改为 {"d","t","u":数字员工,"o":发起人}：检索按 u（auth-uid），审计记 o。

待验证：Docker Desktop 自带的 K8s 不一定执行 NetworkPolicy（取决于 CNI）。P0 第一步先在本地验证：从 atlas-sessions 的 Pod 里 curl atlas-knowledge.atlas-system:8050 应当失败。如果不生效，本地环境需要装 Calico，或明确记录「本地不隔离」并接受这个风险；生产集群必须生效。

6. 权限模型：uid 与 auth-uid

资源 / 判定按谁判说明
能不能用这个 Agent（列表、建会话）uid · AtlasAgent ≥ READ这是唯一按人判的数据权限闸门。谁能用 Agent，谁就间接拥有它数字员工的数据访问能力

操作码（agent:create、kb:create…）auth-uid（人直接操作时 = uid）数字员工默认不授任何角色。Agent 运行时一般用不到操作码；确实需要（例如让 Agent 建知识库）时，在用户中心给数字员工授角色
审计两个都记uid、auth_uid、caller_app、run_id
这个模型有意接受的代价（请评审确认）：原设计默认取「发起人 ∩ 数字员工」，目的是防止「代理人困惑」（confused deputy）。本设计改为只看数字员工，结果是：把一个知识库共享给某个数字员工，就等于共享给了这个 Agent 的所有使用者，其中包括本来无权看这个库的人；提示注入也可能把内容引到别处。好处是行为可预测（同一个 Agent 对谁都一样）、配置面只有一处、不需要 delegated / autonomous 两种模式和审批流程。
配套的约束：
  • 共享给数字员工时强提示：知识库共享面板选到数字员工时，显示「该 Agent 当前有 N 位使用者（含部门展开）可间接检索本库」，必须由库的 OWNER 确认。
  • Agent 共享面板反向提示：给 Agent 加使用者时，列出它的数字员工能访问的库和 MCP。
  • 编辑 Agent 要求 OWNER：谁能改提示词、加工具，谁就间接握有数字员工的全部权限。沿用原设计里「autonomous 的编辑收紧」这一条，现在对所有 Agent 生效。
  • 访问审计：每次检索记录 uid + auth_uid + 命中的库和文档，库的 OWNER 可以在库页面查看「通过哪个 Agent、谁检索了」。

与数字员工设计的差异：§7.1 的交集公式、delegated / autonomous 两种模式、identity_mode 字段、autonomous 审批全部取消；§3（用户中心的数字员工类型）、§4（开放接口，改为请求头鉴权）、§5（创建与生命周期）、§8（用户对 Agent 的数据权限）保留。

知识库挂载编辑 Agent 时「能挂哪些库」改为：数字员工对库 ≥ READ（不再看编辑者）；编辑者能看到候选库的名称，以便知道该去找谁共享
Pod 配额providers/cluster.py 传 quota_key = agent 的数字员工 uid、quota = agent.pod_quota；cluster 的 _check_quota 改为按 quota_key 计数（Pod 加标签 atlas.io/quota-key）

7.3 业务应用建的会话（TeamFlow）

现在 TeamFlow 的会话属于服务账号，TeamFlow 自己判断「谁能看节点会话」（_require_executor），Atlas 只认服务账号。去掉服务账号后：

  • thread.created_by = X-Uid（节点操作人，或监督器自动投递时的流程发起人），thread.source_app = X-Caller-App（teamflow）。
  • 访问规则：X-Caller-App == thread.source_app 时，Atlas 信任这个应用已经做过授权（TeamFlow 的执行角色校验），不再要求 uid == created_by，这样团队里其他执行人也能经 TeamFlow 代理看到会话。直接从网关来（gateway）时，仍然按「所有者或全部智能体 · Owner」判断。
  • 这些会话出现在发起人的 Atlas 会话列表里，带「来自 TeamFlow」标记，只读（不能从 Atlas 侧续聊，避免绕过 TeamFlow 的流程状态）。

9. 产物与 GitLab 账号

现状：TeamFlow 的产物由 Agent 在 Pod 里用 git CLI 提交，凭据档案 teamflow-gitee 里放的是一个共享的机器人账号，allowed_users 限定为 TeamFlow 服务账号。所有 Agent 共用这一个身份，仓库那边看不出是谁写的，也没法按 Agent 收权限。

9.1 开户与凭据

Agent 创建 → Atlas 在用户中心创建数字员工（uid） → Atlas 调 GitLab Admin API：POST /users（username = de-<uid 前 8 位>，email = <uid>@agents.<域>， skip_confirmation，外部用户 external=true） → POST /users/:id/personal_access_tokens（scopes = read_repository, write_repository；有效期 ≤ 1 年） → atlas-cluster PUT /v1/git-credentials/{数字员工 uid} ── cluster 写 K8s Secret git-cred-<uid>（atlas-sessions） （cluster 仍然是唯一持有 K8s 写权限的进程） → agent 表记 gitlab_user_id、gitlab_username（不存令牌）
事项设计
挂载cluster 建 Pod 时按 auth_uid 挂载 git-cred-<uid>（沿用现有 git 凭据文件挂载和 credential helper 的方式），并设置 user.name = Agent 名（数字员工）、user.email = <uid>@agents.<域>。git_profile 和 allowed_users 下线
提交归属author 是数字员工；提交信息末尾加 On-behalf-of: <uid 的姓名> <邮箱>，便于在仓库里追到发起人
仓库权限授给数字员工的 GitLab 账号（项目成员 Developer）。TeamFlow 的协作者对账在「团队成员」之外，再加上「项目流程模板里用到的 Agent 的数字员工」
生命周期Agent 归档 → GitLab 账号 block 并吊销令牌；恢复 → unblock 并重新签发令牌；删除 → 账号保留为 block 状态（保住提交历史的归属）
令牌轮换Atlas 维护任务每天检查，令牌到期前 30 天重签并更新 Secret；运行中的 Pod 通过已挂载的 Secret 自动拿到新值（文件挂载会更新，不用环境变量）
同一 Pod 内的子智能体共享工作区的子会话用的是同一个 Pod，所以 git 身份是根 Agent的数字员工。知识库、MCP 调用经过 atlas-server，仍按各自的数字员工判断。这一点写进限制说明
Gitee 不能这样做：Gitee 没有「管理员 API 开账号、签发令牌」的能力，现在的 TeamFlow 用的是 Gitee（ATLAS_TF_GIT_BACKEND=gitee）。按数字员工开账号的前提是迁到自建 GitLab。迁移之前沿用共享机器人账号（只把 allowed_users 的限制改为「auth-uid 是数字员工」），产物权限暂时无法按 Agent 区分。

12. 评测改动

现状：评测用专用服务账号 atlas-bench（agent:create · chat:use · kb:create），从宿主机经 localhost:8000 直连。它建的库是「仅自己可见」的 service 库（库里现有 4 个），评测留下的会话会占满 Pod 配额（见记忆 atlas-context-mgmt）。

项设计
评测身份用户中心里建一个普通用户 atlas-bench（人类型、禁止登录、随机密码），授予「评测」角色（agent:create · chat:use · kb:create）。评测发请求时 X-Uid = 该用户、X-Caller-App: bench，不写 X-Auth-Uid
访问路径内网接口不再对宿主暴露。评测脚本先 kubectl port-forward svc/atlas-server 18000:8000（知识库同理），由 smoke.sh / regress.sh 自动开启和关闭。结果仍写宿主的 var/bench/，基线比较不受影响。CI 以后可以改成集群内的 Job
配置ATLAS_BENCH_ATLAS_API_KEY 改为 ATLAS_BENCH_UID + ATLAS_BENCH_TENANT_ID；platforms/atlas.py（RAG）和 agent/platforms/atlas.py 两处客户端把 Bearer 换成请求头
Agent 评测的新步骤评测建的 Agent 会自动得到数字员工。runner 需要显式把评测知识库共享给这个数字员工（READ），否则检索为空。这一步本身就是对新模型的覆盖
清理评测结束删除 Agent，数字员工随之停用（GitLab 账号 block）。用户中心里会累积停用的数字员工：清理时调用户中心的删除接口（数字员工没有被任何授权引用时允许物理删除）
配额Pod 配额按 Agent 计，评测 Agent 设 pod_quota，不再挤占真实用户的配额
新增评测用例① 数字员工没有库权限 → Agent 检索为空，并给出提示（负例）；② 用户本人无权看某库，但经 Agent 能检索到（记录这是被接受的行为，§6）；③ 轨迹 trajectory 记录 auth_uid，report 按 auth-uid 汇总拒绝次数

16. 风险、权衡与待确认

#风险 / 权衡应对
1内网任一应用被攻破 = 可以冒充任何人，包括平台管理员（请求头没有签名）。令牌方案下，攻破一个应用只能拿到这个应用自己的权限NetworkPolicy 收紧到「谁能调谁」（例如 TeamFlow 只能调 Atlas 和用户中心）；审计记录 caller_app；以后如果需要更强的保证，用服务网格 mTLS 在网络层证明调用方身份，应用代码不用再改
2代理人困惑（§6）：经 Agent 能读到自己无权看的库已接受；靠强提示、编辑权限收紧到 OWNER、访问审计来控制
3Pod 配额按 Agent 计：某个人可能把一个热门 Agent 的配额占满，其他人用不了P2 可选：在 Agent 配额内再加单人上限（pod_quota_per_user），默认不启用，待确认
4Docker Desktop 可能不执行 NetworkPolicyP0 第一步实测（§5.3）
5网关每个请求都调 verify，用户中心成为关键路径短 TTL 缓存；用户中心多副本（它是无状态的）
6GitLab 账号数量随 Agent 增长；令牌有效期最长 1 年外部用户不占许可证（视 GitLab 版本而定，待确认）；每日轮换任务
7port-forward 是一条绕过网关的路径只有持有 kubectl 的人能用，本来就等于集群管理员；在文档里写明

待确认

  • 监督器自动投递时 X-Uid 取流程发起人 started_by（另一个选项是节点执行角色里的第一个人）。
  • 评测身份用「禁止登录的普通用户 atlas-bench」，而不是数字员工（数字员工不能做 Agent 的创建者和 OWNER）。
  • 数字员工默认不授任何角色（操作码），有需要时在用户中心单独授予。
  • 外部第三方应用的令牌由网关校验，是否在 P0 就做，还是等有实际需求再做（建议后者）。
  • TeamFlow 建的会话在 Atlas 侧只读（§7.3）。
