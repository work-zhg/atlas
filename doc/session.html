Session Management

会话管理设计

Session / Run / Message / Event 四个对象，一套状态机，两类 Agent。顾问出谋划策，助理实际干活 —— 它们共享对象模型，但能力边界必须显式暴露而非抹平。

AgentSessionRunMessageEvent

01角色分工：顾问与助理

顾问

type = native · Server 进程内 · 上下文在服务端

  • 分析、方案、评审、答疑
  • 工具集限只读
  • 产出即 Message 本身
  • 无 checkpoint，Message 是唯一事实源
  • 重跑安全

助理

type = acp · Pod 内经 ACP · 上下文在 CLI 进程

  • 写代码、改文件、跑命令
  • 工具集完整，含写操作
  • 产出是 OSS 文件 + Message 摘要
  • 上下文在 CLI 进程内
  • 重跑危险，每个危险动作需审批
一条分界线推导出全部不对称

上下文由谁持有。本文后面每一处两类 Agent 不一致的地方，都能回溯到这一条：

  • 顾问可以 regenerate / 编辑历史 —— 因为输入是我们每轮重建的，截断改写即可
  • 顾问不需要 Run 内挂起 —— 因为无 checkpoint，interrupt() 用不了
  • 顾问可以不存 checkpoint —— 因为不需要精确恢复到中断点
  • 助理的上下文动不了 —— 因为它在别人的进程里
配置顾问工具时要考虑重跑语义

顾问支持 regenerate 与编辑历史，意味着同一轮可能被重跑多次，该轮的工具调用会重新执行。给它配工具时要清楚这一点 —— 前端那个重试按钮在用户看来是无害的。

02术语与对象模型

对象作用域定义生命周期
Agent全局配置智能体定义。type 取 native（进程内）或 acp（经 ACP 驱动 CLI）。capabilities 的所有者。配置态 · 带版本
Session—一个会话。引用一个 Agent 版本，持有工作区、模型配置、认证上下文，以及对 acp 类型而言的 Pod 健康状态（state）。不存 capabilities。永久
RunSession会话里的一条对话：一次用户提交 → Agent 干完活 → 停下来。Session 内串行，同时只允许一个活跃 Run。永久（元数据）
MessageSession会话内容账本。user / assistant / tool / system。展示的唯一真相，对顾问而言也是执行的唯一输入源。永久
EventRun由 chunk 转成的过程流：增量文本、思考、工具中间态、审批请求。只保留最后一个 Run 的。随下一个 Run 开始而清理
核心分层

Message 是「会话内容」，Event 是「它怎么产生的」。Run 结束后 Message 即为真相，Event 可以丢弃 —— 前提是所有需要保留的语义都已固化进 Message 或 Run 元数据（见 §11）。

03对象层次与作用域

04能力矩阵

前端只读 capability 决定按钮的显示与禁用，禁止出现 if (agent.type === 'assistant')。「实现机制」一列说明能力从何而来 —— 顾问的编辑类能力不再来自 checkpoint 回放，而来自重构输入。

能力顾问助理实现机制
multi_turn✓✓顾问每轮重传完整 Message 列表；助理靠 CLI 自身上下文
stream✓✓两者都投影成同一套 Event
cancel✓✓顾问中止 astream；助理发 session/cancel
rollback_on_cancel✓✗顾问删除本轮 Message 即可；助理的已执行动作与半截上下文都留着
regenerate✓✗截断 Message 重构输入 —— 上下文本就是我们每轮重建的
edit_history✓✗改 Message 表后重构输入
branch✓✗复制 Message 子集到新 Session
compact✓✗服务端压缩 Message 列表；助理的压缩由 CLI 自管
in_run_input✗✓Run 内挂起等待输入。顾问无 checkpoint 故不可用，见 §05
resume_mid_run✗✗两者都不支持：顾问无 checkpoint，助理状态在进程内
resume_session✓native ｜ replay ｜ none顾问的 Message 在库里，进程重启无影响；助理取决于 loadSession

上线前必须先验证

对每个要接入的 CLI，实测 initialize 返回的 agentCapabilities.loadSession。这一个布尔值决定助理的整套恢复策略：为 true 走原生续接；为 false 只能重放（有损、重复计费、可能重复执行已做过的动作）或直接放弃上下文。

capabilities 的所有权与投影

  • agents 表持有 capabilities，Session 不复制一份，只存 agent_id + agent_version。
  • 会话快照 GET /sessions/{sid} 里投影出 capabilities —— 为前端省一次往返的传输优化，不是所有权转移。
  • Agent 定义变更会改变 capabilities；存量会话通过 agent_version 钉住快照时那一版，避免会话中途能力集漂移。
助理的 capabilities 有两层

顾问的 capabilities 是纯静态声明。但助理的部分字段只有握手后才知道 —— resume_session 取决于 initialize 响应，要真正连上 CLI 才读得到，且随 Pod 上的 CLI 版本变化。

所以 Agent 上分开存 declared（配置里写的）与 probed（首次握手探测到的，带时间戳）。probed 覆盖 declared；尚未探测时下发保守值（resume_session: "none"），而不是乐观假设 —— 猜错的代价是用户以为上下文还在。

05顾问的执行

用 LangChain 的 create_agent 构造，不传 checkpointer。每轮从 Message 表读取完整历史作为输入，跑完把新增部分固化回 Message 表。

构造

from langchain.agents import create_agent

advisor = create_agent(
    model=model,
    tools=tools,                   # 注意重跑语义：regenerate 会再执行一遍
    system_prompt=ADVISOR_PROMPT,
    middleware=[...],
    name="advisor",
    # checkpointer 省略 → 无状态图
    # Message 表是唯一事实源，不需要第二份
)

执行一轮

# 1. 从 Message 表构造输入 —— 这是唯一的上下文来源
history = await messages.load(session_id)
history.append(HumanMessage(content=user_input))

# 2. 流式执行，chunk 转成 Event 推 SSE
async for mode, chunk in advisor.astream(
    {"messages": history},
    stream_mode=["messages", "updates"],
):
    await events.publish(run_id, translate(mode, chunk))

# 3. 固化：超出输入长度的部分即本轮新增
await messages.append(session_id, run_id, final_state["messages"][len(history):])

注意不传 thread_id —— 无 checkpointer 时它没有意义。run_id 通过 config 传递，仅用于 OTel 关联，不用于状态寻址。

为什么这样更好

checkpoint 方案Message 方案
真相源两份（checkpoint + Message），需对齐规则一份
对齐失败表现静默降级，不报错不存在该失败模式
regenerate回放到某个 checkpoint 再分叉截断列表重新调用
编辑历史需要改写检查点谱系改一行记录
Run 中断续跑支持不支持，整轮重来

把编辑类能力建立在「重构输入」而非「checkpoint 回放」之上，实现更简单也更可控 —— checkpoint 的谱系、分叉与增量重放本身就是一类难对付的 bug 来源。实质损失只有中断续跑一项。

连带后果：顾问不能在 Run 内挂起

LangGraph 的 interrupt() 明确要求 checkpointer —— 它靠持久化图状态来实现恢复。不存 checkpoint 就无法用 interrupt 做追问。

因此顾问的追问必须是 「结束本轮 + 开新轮」：Agent 提出问题作为本轮最终输出，stop_reason = need_clarification，Run 正常 completed；用户的回答作为下一轮的 human message。而助理的审批是 Run 内挂起（waiting_input），因为 CLI 进程还活着在等。

这个不对称由 in_run_input capability 暴露给前端。它恰好和产品语义自洽：顾问的追问本就该长得像「它问了我一个问题」（一条消息），助理的审批本就该长得像「它要做一件事，请批准」（一张操作卡片）。这两者在 UI 上本来就不该一样。

成本：上下文随轮次线性增长

每轮重传完整历史，token 成本随会话长度增长。这一点 checkpoint 方案并不更优（LangGraph 的 checkpoint 同样保存完整消息列表），所以不算本方案的额外代价 —— 但仍然必须实现 compact：服务端压缩 Message 列表并写入一条 system 摘要消息，后续轮次从摘要点之后重构输入。

可选优化：把中断损失降到轮内

一轮内如果 Agent 调了多个工具后崩溃，默认整轮重来。若把工具调用与结果实时固化成 Message（而非等 Run 结束批量写），重来时它们作为已有上下文传入，模型通常会跳过已完成的步骤。

这是启发式而非保证

它依赖模型「看到自己已经调过这些工具」后的行为，不是机制保证 —— 模型完全可能重新调用一遍。对只读工具而言重复调用无害，所以对顾问可以接受；但不要把它当作 resume_mid_run 对外宣称，能力矩阵里这一项仍然是 ✗。

06助理的执行

Server 经 WebSocket 把 prompt 下发给 Pod 内的 Bridge，Bridge 作为 ACP client 驱动 CLI，并把 session/update 分流成两条线：实时推 Event，Run 结束时固化 Message。

ACP session/updateEventMessage 固化
agent_message_chunkmessage.deltaassistant Message —— 必须
agent_thought_chunkthought.delta—
tool_calltool_call.startedtool Message —— 必须
tool_call_updatetool_call.updated/ended
planplan.updated可选
session/request_permissionrequest.pendingsystem Message（审计）
session/prompt 返回 stopReasonrun.endedRun 元数据
不要把 CLI 的输出全当 trace

agent_message_chunk 必须走 Message 固化路径。若助理的所有输出都只当作过程 trace，历史记录里这类会话会是空白的，只剩用户发的问题。

Pod 即会话

  • 不需要 sticky 路由 —— 会话与 Pod 一一对应，Server 维护 session_id → pod 映射并直连该 Pod 的 WebSocket 端点。Server 自身因此可无状态扩容。
  • idle 缩容 —— 无活动超时后销毁 Pod，会话置 cold；下次提交时重新调度。
  • OSS 让重建对文件无损 —— 但上下文不在 OSS 上，它随 Pod 消失。能否恢复只取决于 loadSession。别把「文件还在」误当成「上下文还在」。
  • 凭证隔离天然成立 —— Pod 边界即隔离边界。
  • 会话 ID 分层 —— 客户端只见持久的 session_id；bridge_ref = {pod, acp_session_id} 易失，随 Pod 重建更换。

会话健康状态必须可见

state含义前端表现
activePod 存活，上下文完整正常
coldPod 已回收，下次提交时重建resume_session=native 时无感；replay 时提示有损
lost无法恢复，上下文已丢消息流中插入分隔线：「会话已重启，此前上下文未保留」

不要让它静默。用户最恨的是「我明明刚说过」而 Agent 完全不记得。

07数据模型

-- 智能体定义。capabilities 的唯一所有者，按版本不可变
CREATE TABLE agents (
  agent_id         TEXT        NOT NULL,
  version          INT         NOT NULL,
  type             TEXT        NOT NULL,   -- native | acp
  launch           JSONB,                  -- acp: 镜像 / command / args / env
  caps_declared    JSONB       NOT NULL,
  caps_probed      JSONB,                  -- acp: initialize 握手探测，覆盖 declared
  probed_at        TIMESTAMPTZ,
  PRIMARY KEY (agent_id, version)
);

-- 会话。只引用 Agent 版本，不复制 capabilities
CREATE TABLE sessions (
  session_id     TEXT        PRIMARY KEY,
  agent_id       TEXT        NOT NULL,
  agent_version  INT         NOT NULL,   -- 钉住，避免能力集中途漂移
  state          TEXT        NOT NULL,   -- active | cold | lost
  workspace_uri  TEXT,                   -- acp: OSS 前缀
  model          TEXT,
  bridge_ref     JSONB,                  -- {pod, acp_session_id} 易失，可为空
  next_seq       BIGINT      NOT NULL DEFAULT 1,
  created_at     TIMESTAMPTZ NOT NULL,
  FOREIGN KEY (agent_id, agent_version) REFERENCES agents (agent_id, version)
);

-- 一条对话。session 内串行；run_id 由客户端生成，天然幂等键
CREATE TABLE runs (
  run_id          TEXT        PRIMARY KEY,
  session_id      TEXT        NOT NULL REFERENCES sessions,
  idx             INT         NOT NULL,
  status          TEXT        NOT NULL,   -- queued|running|waiting_input|…
  stop_reason     TEXT,                   -- end_turn | need_clarification | error | …
  usage           JSONB,
  tool_call_count INT         NOT NULL DEFAULT 0,
  first_seq       BIGINT,
  last_seq        BIGINT,
  started_at      TIMESTAMPTZ,
  ended_at        TIMESTAMPTZ
);
-- session 内同时只允许一个活跃 Run
CREATE UNIQUE INDEX uq_run_active ON runs (session_id)
  WHERE status IN ('queued', 'running', 'waiting_input');

-- 会话内容账本。展示的唯一真相，也是 native 类型执行的唯一输入源
CREATE TABLE messages (
  session_id TEXT        NOT NULL,
  seq        BIGINT      NOT NULL,   -- session 内单调，全局排序真相
  run_id     TEXT        NULL,       -- system 类消息不隶属任何 Run
  role       TEXT        NOT NULL,
  kind       TEXT,                      -- session_restarted / permission_decision / compaction …
  content    JSONB       NOT NULL,
  created_at TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (session_id, seq)
);

-- 过程流。与 messages 共用 session 级 seq；随下一个 Run 开始被清理
CREATE TABLE events (
  session_id TEXT        NOT NULL,
  seq        BIGINT      NOT NULL,
  run_id     TEXT        NOT NULL,
  type       TEXT        NOT NULL,
  payload    JSONB       NOT NULL,
  created_at TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (session_id, seq)
);
CREATE INDEX ix_events_run ON events (session_id, run_id, seq);
序列分配

messages 与 events 共用同一条 session 级 seq，由 sessions.next_seq 串行分配。前端把两者混流按 seq 追加即得正确顺序，无需任何客户端合并逻辑。uq_run_active 保证写入天然串行，seq 分配不需要额外的跨 Run 并发控制 —— 两个约束互相支撑。

08Message / Event 保留策略

历史 Run 的降级渲染

Event 被清理后，历史 Run 不该退化成一堆裸消息。runs 表的元数据足够渲染有意义的摘要：

Run #6  ·  调用 12 个工具  ·  耗时 3m21s  ·  12.9k in / 881 out  ·  end_turn
        └─ 展开 → 固化下来的 tool Message 列表（名称 · 参数摘要 · 结果摘要 · 审批决定）

09Run 状态机

10传输层与接口契约

选型：SSE 下行 + REST 上行

审批看似需要双向连接，实际是「事件下行 + REST 上行」：服务端推 request.pending，前端用一个普通 POST 回复。审批频率是分钟级的，不值得为它引入 WebSocket 的连接管理、重连、心跳以及代理层的麻烦。用 POST + fetch 流式读取，而非 EventSource（后者既不能带自定义 header 也不能带 body）。

端点

POST/sessions创建会话，指定 agent_ref；返回 capabilities
GET/sessions/{sid}元数据 · capabilities · state · active_run · pending_requests[]
DEL/sessions/{sid}关闭会话；助理须一路传到调度层销毁 Pod
GET/sessions/{sid}/messages?before_seq=&limit=会话内容分页，向前翻历史
POST/sessions/{sid}/runs提交并开流（SSE）。body 含客户端生成的 run_id
GET/sessions/{sid}/runs/{rid}/join重连观察（SSE）。只读，断开不得触发取消
GET/sessions/{sid}/runs/{rid}/events?after_seq=断线补洞 / 冷启动回放
POST/sessions/{sid}/runs/{rid}/cancel返回实际发生了什么，见下
POST/sessions/{sid}/requests/{qid}/respond审批应答（仅助理）。幂等
POST/sessions/{sid}/compact压缩 Message 列表（仅顾问）

会话快照：重连的关键

GET /sessions/sess_01H8Z…
{
  "session_id": "sess_01H8Z…",
  "agent_ref": { "id": "claude_code", "version": 3, "type": "acp" },
  "state": "active",          // 会话自身的动态状态

  // ↓ 投影自 agents(claude_code, v3)，不存在 sessions 表里。
  //   放在这里只为省一次往返；所有权仍归 Agent。
  "capabilities": {
    "cancel": true,  "regenerate": false, "edit_history": false,
    "branch": false, "compact": false,   "rollback_on_cancel": false,
    "in_run_input": true,  "needs_approval": true,
    "resume_mid_run": false, "resume_session": "replay"
  },
  "active_run": { "run_id": "run_8", "status": "waiting_input", "last_seq": 166 },
  "pending_requests": [ { "request_id": "req_abc", "kind": "permission", … } ],
  "last_seq": 166
}
最常见的漏

pending_requests[] 必须出现在会话快照里。否则用户刷新页面后审批弹窗消失，CLI 进程仍在阻塞等待，会话永久卡死且无法自愈。

提交一个 Run

POST /sessions/{sid}/runs
{ "run_id": "run_01J…",          // 客户端生成 = 幂等键
  "content": [ { "type": "text", "text": "…" } ] }

// 200 → text/event-stream
// 409 → { error: "run_active", active_run_id: "run_8" }   前端据此禁用输入框

客户端生成 run_id，网络超时重发时服务端按同一 ID 返回既有 Run 而非新建一轮。对助理尤其重要 —— 重复提交意味着 CLI 真的会把活干两遍，可能是两次文件写入。

取消：返回实际发生了什么

POST /sessions/{sid}/runs/{rid}/cancel
// 顾问  → { "cancelled": true, "rolled_back": true,  "side_effects_retained": false }
// 助理  → { "cancelled": true, "rolled_back": false, "side_effects_retained": true }

前端据此决定是把这一轮从流里抹掉，还是保留并标记为「已中断」。

SSE 帧格式

event: message.delta
data: {"seq":141,"run_id":"run_8","payload":{"role":"assistant","text":"正在读取 "}}

event: request.pending
data: {"seq":142,"run_id":"run_8","payload":{"request_id":"req_abc",…}}

event: run.ended
data: {"seq":167,"run_id":"run_8","payload":{"stop_reason":"end_turn","usage":{…}}}

11Event 目录与固化清单

固化规则

Event 可以被清理，当且仅当它承载的语义已经固化进 Message 或 Run 元数据。这条规则漏掉不会报错，只会在三个月后有人问「为什么看不到上次的操作记录」时才暴露。把清单做成集中定义的显式契约并用测试卡住，不要散落在各个 handler 里。

message.delta✓✓assistant Message —— 必须
thought.delta✓✓— 可丢
tool_call.started✓✓tool Message
名称 · 参数摘要 · 状态 · 结果摘要
tool_call.updated✓✓

最容易漏的两项

  • 工具调用 —— 用户回溯时最想知道的就是「上次助理到底改了哪些文件」。这个信息若只在 Event 里，一个新 Run 就冲掉了。
  • 审批记录 —— 「谁在什么时候批准了写入 src/main.py」是审计信息，不是过程信息。合规场景下绝不能随 Event 蒸发。

审批回路的四条硬约束（仅助理）

  1. 幂等 —— 同一 request_id 重复应答返回第一次的结果，不报错。用户双击、网络重试都会撞上。
  2. 超时兜底 —— CLI 进程正阻塞等待，无人应答就永久挂住并占用 Pod。到期按 default_on_timeout（默认拒绝）自动处理并发 request.resolved。
  3. 多端竞争 —— 先应答者赢，其余客户端收到 request.resolved 自动关闭弹窗。
  4. 重连可见 —— 见 §10 的 pending_requests[]。

allow_always 的作用域要注意：ACP 会话级的「总是允许」随会话消失，而用户的心理预期通常是持久的。建议由服务端自己存这个偏好（per session 或 per user × tool），下次自动应答，而不是透传给 CLI。

12交互时序

重连的三步

1.  GET  /sessions/{sid}                    → capabilities · state · active_run · pending_requests
2.  GET  /sessions/{sid}/messages?before_seq=…   → 渲染历史（含已清理 Event 的 Run）
3.  active_run 存在？
    ├─ 是 → GET /runs/{rid}/events?after_seq={本地 last_seq}   补洞
    │        GET /runs/{rid}/join                                 续订
    └─ 否 → 结束，仅渲染 Message

13关键约束与陷阱

约束 01

Message 表是展示的唯一真相，对顾问而言也是执行的唯一输入源。不存 checkpoint 就不存在第二份真相，也就不需要任何跨源对齐规则 —— 那类规则一旦对不上是静默降级而非报错，是最难排查的一类缺陷。代价是顾问的 Run 中断后只能整轮重来。

约束 02

Session 内同时只允许一个活跃 Run。ACP 的一个 session 同一时刻只能有一个活跃 prompt，顾问也应施加同样约束。提交时若已有活跃 Run，返回 409 + 当前 run_id，前端禁用输入框。不要做排队 —— 用户排队时看到的上下文，与 Agent 真正处理到那一轮时的上下文可能已经不同。

陷阱 01 · 顾问专属

顾问的同一轮可能被重跑多次。regenerate 与编辑历史都会重新执行该轮的工具调用 —— 配置工具时要考虑这一点，前端那个重试按钮在用户看来是无害的。

陷阱 02 · 助理专属

Message 表 ≠ CLI 的上下文。Message 表是「你观察到的记录」，CLI 内部状态是「它真正记得的」。两者会漂移：CLI 自己做了 compaction、loadSession 失败重建、它自己写了持久化记忆文件。对助理而言 Message 表是展示账本，不是可以拿来重建上下文的真相 —— 除非明确走 replay 路径并接受有损。顾问恰好相反：Message 表就是全部。

陷阱 03

Event 清理必须晚于「下一个 Run 开始」，且留宽限期。即时删除会在多端场景下让正在查看上一个 Run 详情的用户页面内容凭空消失。用 TTL + 保留最近 N 个 Run，异步清理。固化清单必须先于清理逻辑上线 —— 顺序反了就会丢数据，而且丢得无声无息。

陷阱 04

删除会话要真正回收 Pod。DELETE /sessions/{sid} 必须一路传到调度层销毁 Pod，而不只是关掉 WebSocket。同时服务端要有定时任务兜底回收 idle 会话 —— 否则幽灵会话会一直占着 Pod 配额烧钱。OSS 上的工作区文件是否随会话删除一并清理，是独立的保留策略决定，须显式定义而非默认继承 Pod 的生命周期。

落地优先级

  1. 先实测 loadSession —— 一个布尔值决定助理的恢复策略，别在不确定的前提上设计。
  2. 先把顾问跑通 —— 无 checkpoint、无 Pod、无审批，是整套抽象最小可验证的切片；它跑对了，对象模型与事件流就立住了。
  3. 固化清单先于清理逻辑上线 —— 顺序反了会丢数据。
  4. capability flags 而非统一接口 —— 一旦出现第一个按 agent.type 分支的前端组件，后面就收不住了。
  5. 接受助理是有状态的 —— Pod 生命周期、idle 回收、重启断上下文，提前设计进去。
