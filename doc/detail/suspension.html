Detailed Design · Suspension

挂起与恢复

一次委派可以跑一小时。父 run 在进程里等那么久的代价是明确的：部署一次、OOM 一次，父 run 就没了，连带丢掉子 run 已经干完的活。这份设计把「等」从 asyncio.Task 移到数据库 —— 并且发现委派挂起与审批挂起是同一件事。

一个 run，多段执行thread 级事件流不引入 checkpointer审批可以等一天

01问题：一次委派可以跑一小时

native Agent 通过 task 委派给 acp Agent（一个 CLI 助理）时，子任务的真实时长可以是分钟到小时级。原先的链路是父 run 同步等到子 run 终态（SubagentService._await_result 轮询），这在秒级委派下没有问题，在小时级下有三重代价：

代价具体表现
撑不到中断父 limits.timeout_s 默认 300s，_await_result 的 deadline 也是它 —— 一小时的委派在第 5 分钟就被判超时并取消
重启即全丢父子 run 都是同进程的 asyncio.Task。滚动部署时两者一起死，而 Pod 里的 CLI 还在跑 —— 一小时的产出无人认领
锁的承诺破了会话串行锁 TTL 按 max(timeout_s, approval_timeout_s)+120 算。等待期间无人续租，锁静默过期，第二个 run 能进来交错写同一个 thread
真正值钱的资产不在父 run 上

父 run 的状态小到不值得持久化 —— 它就是「一次 task tool call 在等返回」，历史全在 message 表里，重建成本是一次模型调用。子 run 那一小时才是不可重建的。

所以问题不是「怎么把父 run 的内存状态存下来」，而是怎么让父 run 不必在线一小时。这个视角决定了后面全部的取舍。

02两种等待，一个机制

系统里原本有两处「等外部」，各自实现：

委派审批（原状）
拦截点task 工具返回值awrap_tool_call 内 await gate.request()
等待载体父 run 的轮询循环进程内 BLPOP，600s
进程占用一个 Task一个 Task
重启后全丢全丢
工具执行状态已执行完（结果在等）尚未执行
核心判断

两者都是「这一段到此为止，等一个外部事件，事件到了续跑」。差异只有最后一行：审批挂起时工具还没跑。所以不该给审批单独造一套挂起，而应把 suspension 抽象出来，让委派与审批成为它的两个 reason。

2.1 统一模型

engine/contracts/suspension.py

SUSPENSION_MARKER = "__ATLAS_SUSPENDED__"

@dataclass(frozen=True)
class Suspension:
    reason: Literal["delegation", "approval"]
    token: str          # delegation → sub_run_id；approval → approval_id

def suspend_marker(reason, token) -> str   # "__ATLAS_SUSPENDED__:delegation:<uuid>"
def parse_suspension(text) -> Suspension | None

能力方（task 工具、审批中间件）在需要等待时返回一个 marker 字符串作为 ToolMessage 的内容。图内只有一个地方认识它：

class SuspensionMiddleware(AgentMiddleware):
    @hook_config(can_jump_to=["tools", "end"])
    def before_model(self, state, runtime):
        ...  # 三条判据，见 §6.3
★ marker 必须是返回值，不能是异常

task 工具对受理方抛出的异常一律接成错误文本回给模型（委派失败是局部问题，不该炸掉整个 run）。marker 走异常路径会被那个 except 吞掉，变成模型眼里的一句「委派失败」—— 而它其实正在跑。

2.2 为什么 marker 自带 token

续跑时要把 marker 换成真实结果，而「换哪一条」只能靠它。把关联关系放在消息序列自己身上的回报是：不需要另一张表去记 (tool_call_id → sub_run_id) —— marker 所在的那条 ToolMessage 本来就带着正确的 tool_call_id（工具节点自己生成的）。

这一条在实现时救掉了一整张表，见 §12 的修正记录 1。

03不引入 checkpointer

LangGraph 的原生答案是 checkpointer + interrupt() + Command(resume=)。这份设计明确不用，理由分两层。

3.1 它解决的不是我们的问题

checkpointer 解决什么我们的情况
恢复图的内存状态图的状态就是 messages，而 messages 的事实源是 message 表
决定从哪个节点恢复middleware 的 jump_to（图内条件边）已经提供了这个能力
记住「在等什么」run.waiting_on 一列 + Approval 表

更关键的是它会引入第二个状态源。这条约定在仓库里有四处注释守着（kernel/middleware/skills.py、services/compaction.py、迁移 0001/0005、db/models.py），middleware/approval.py 顶部那段「为什么不用 interrupt」也是同一个判断。推翻它换回来的东西，我们用一个 before_model hook 就拿到了。

3.2 实验证据

关键问题是：不用 checkpointer，能不能让图从 tools 节点开始执行？这正是审批续跑需要的 —— 挂起时工具没跑，续跑时要先把它跑掉。

构造一个只有 messages 的输入，其中有一条带 tool_calls 的 AIMessage 但没有对应的 ToolMessage（审批挂起后的形态），middleware 在 before_model 里返回 {"jump_to": "tools"}：

节点顺序: ['ResumeMiddleware.before_model', 'tools',
           'ResumeMiddleware.before_model', 'model']
工具实际执行: ['/tmp/x']

第一次 before_model 发现悬空的 tool_call → 跳 tools → 工具执行 → 再回 before_model，这次没有悬空的了 → 正常流向 model 收尾。零 checkpointer。

★ 而 jump_to 不能从图输入传进去

设计初稿写的是「续跑时 _graph_input 带 {"jump_to": "tools"}」。不可行：InputAgentState 只有 messages 一个字段，而 jump_to 标着 PrivateStateAttr = OmitFromSchema(input=True, output=True) —— 从输入 schema 排除，传进去会被直接丢弃。

正确做法是判据来自 state 本身，middleware 在图内自己决定。见 §12 的修正记录 2。

3.3 由此带来的简化

PreparedRun.resume_entry 这个字段不需要。server 侧什么都不用传 —— 三条判据全部只看 messages，SuspensionMiddleware 因此是无状态的，也不需要知道审批和委派的存在。

附带好处：这个判据是通用的 —— 任何「工具没执行完就中断」的 run 续跑时都会自愈，不只审批。

04thread 级事件流：seq 的归属

挂起暴露了事件流的一个结构性缺陷：前端只订阅父 run 那一条流，而子 run 的过程活在它自己的流上。父 run 挂起后，父流再不产出任何事件 —— 用户盯着一个不动的界面，分不清「在等」和「挂了」。审批更严重（§6.4）。

根治办法是把订阅单位从 run 换成 thread：一个会话一条流，该会话下所有 run（含子 run）的事件都进去。核心难题不是「合并两条流」，是 seq 的归属权。

4.1 契约规则 2 变更

旧：seq 在单个 run 内从 1 严格递增无空洞
新：seq 在单个 thread 内从 1 严格递增无空洞
为什么必须换归属，而不是用复合游标

前端的去重是一行 if (event.seq <= state.lastSeq) return state（run-reducer.ts），Last-Event-ID 传 String(lastSeq)。只要 seq 还是「thread 内单调的整数」，这两处一行都不用改。

复合游标 (run_id, seq) 会强迫前端为每个 run 维护一个 lastSeq，而且无法回答「两个并发 run（父 suspended + 子 running）的事件谁在前」。

4.2 分配方式：Redis INCR + DB 水位恢复

thread 级 seq 有多个并发生产者（父 run 挂起时子 run 在跑），不能由单个进程内存分配。必须是共享计数器。

为什么不用 Postgres 的 UPDATE ... RETURNING：message.delta 是 token 级事件，一次回答几千条 —— 几千次 DB 写不可接受。Redis INCR 是 O(1) 单 RTT，且事件发布不在用户等待路径上。

Redis 是易失的：key 丢了会从 1 重来 → 重复 seq → 前端把新事件全当重复丢掉（静默故障，最坏的一种）。恢复必须原子：

-- KEYS[1]=thread:seq:{id}  ARGV[1]=DB 水位  ARGV[2]=ttl
if redis.call('EXISTS', KEYS[1]) == 0 then
  redis.call('SET', KEYS[1], ARGV[1])
end
local v = redis.call('INCR', KEYS[1])
redis.call('EXPIRE', KEYS[1], ARGV[2])
return v

水位 = SELECT COALESCE(MAX(thread_seq),0) FROM run_event WHERE thread_id=?，每段执行开始时查一次（不是每事件），缓存在 EventFactory 里作为 floor。TTL 设 30 天并每次续期 —— 活跃会话不会过期，只有冷启动/Redis 重建才走恢复路径。

不做号段预分配：号段会产生空洞，而「无空洞」是契约的一部分（前端虽不依赖，但 replay(after_seq) 的可推理性依赖它）。

4.3 stream key 与归档

旧新
Redis keyrun:events:{run_id}thread:events:{thread_id}
seq key—thread:seq:{thread_id}
归档主键(run_id, seq)(thread_id, thread_seq)，run_id 降为普通列+索引
回放查询WHERE run_id=? AND seq>?WHERE thread_id=? AND thread_seq>?

run_event 加 thread_id 列而不是 JOIN run 表 —— 回放是热路径。表名保留（它仍是「某个 run 产出的事件」），只是索引口径换了。

4.4 SSE 生命周期：最大的 breaking change

旧（run 流）新（thread 流）
端点GET /v1/runs/{id}/eventsGET /v1/threads/{id}/events
何时关闭收到终态事件即关永不自动关，直到客户端断开
relay.tail 的 returntype in TERMINAL_EVENTS删掉
前端停止重连isTerminalEvent删掉；改为组件卸载时 abort
activeRunId决定订阅哪条流消失 —— 订阅只看 threadId

连带简化掉的东西：thread.active_run_id 不再为订阅服务（可留作 UI 判断「是否在跑」）；ChatWorkbench 里那段 restorable && !activeRunId 的刷新恢复逻辑消失 —— 订阅 thread 天然就是恢复；切会话时 reset() 的时序问题消失。

★ 两个必须一起处理的新问题

首连回放量。订阅一个有 500 轮历史的 thread，after_seq=0 会回放全部事件，打开老会话直接卡死。必须同时加 since 语义：默认只回放最近 N 条或「最后一个未完成 run 起」，完整历史轨迹走单独的分页端点。这一条不能延后到 D 之后做。

长连接数。一 thread 一条 SSE，多标签页放大。DB 连接已在 stream() 开头归还，但每条 SSE 占一个 Redis 连接 —— 要给池设上限并在耗尽时明确 503，而不是静默排队。

4.5 delta 进流，但归档要分流

子 run 的 message.delta 进 thread 流 —— 否则「过程可见」只到工具粒度，D 的价值减半。代价是事件量大致翻倍，两个配套措施：

措施原因
xadd(maxlen=N, approximate=True)一个 thread 一条流且永不结束，不设上限则内存随会话寿命单调增长。~ 裁剪按整块丢，O(1)
delta 不再归档delta 的价值是实时打字效果；回放历史用 message.completed 的完整 content 就够（前端读历史本来走 message 表）。能把归档量降一个数量级
前端默认折叠 depth=1 的 delta一小时的委派会产出大量 delta，全渲染会让主对话区滚动失控。折叠态显示「已输出 N 字」，展开即见

05depth 重新获得语义

现在 depth = len(ns)（LangGraph 子图命名空间深度）。而委派模式下 _build_delegating_task_tool 根本不编译子图 —— 所以 depth 恒为 0。

两条注释因此是死代码

SubAgentCard.tsx 说「子智能体内部的工具调用仍然可见 —— 它们在 Inspector 工具页里带 depth 缩进」，run-reducer.ts 说「内部工具调用在 toolCalls 里带 depth≥1」。两者都是图内子图时代的遗留：父流上不存在 depth≥1 的事件。tests/test_subagents.py 自己写着「子 run 有自己的事件流（depth=0），父只看边界事件」，并断言了 all(e.depth == 0)。

新语义：depth = run 在委派树里的深度。

EventFactory(run_id, clock, start_seq=..., base_depth=...)
    depth = base_depth + 局部子图深度

base_depth = 1 if run.parent_run_id else 0    # 委派深度封顶 1 ⇒ depth ∈ {0,1}

这一步让 D 的价值落地：前端拿到 depth=1 的事件就知道「这是子智能体内部的」，Inspector 的缩进逻辑复活，SubAgentCard 可以真的显示步骤列表 —— 那两条注释从死代码变回真的。

配套：runner._from_messages 里 if depth > 0: return [] 这个丢弃保留（它丢的是局部子图，不是子 run），但判据要明确基于局部 depth，避免把 base_depth=1 的子 run delta 误丢。

06审批走 suspension

6.1 ApprovalGate：从阻塞等待改成查询状态

#  旧
async def request(self, *, approval_id, tool_name, args) -> Decision   # 阻塞 600s

#  新
async def check(self, *, approval_id, tool_name, args) -> ApprovalState
#  ApprovalState = "pending" | "approved" | "rejected" | "expired"
gate 返回middleware 动作
pending（首次：已落库、已发事件）返回 marker ToolMessage → 本段挂起，工具不执行
approvedawait handler(request) —— 正常执行
rejected / expired返回 REJECTED_RESULT / EXPIRED_RESULT

6.2 ★ approval_id 必须可复现

这是审批挂起能否成立的关键

现在是 uuid.uuid4()。续跑时同一个 tool_call 会算出一个新的 approval_id，gate 查到 pending，于是再挂起一次 —— 死循环。

approval_id = uuid.uuid5(_NS, f"{run_id}:{tool_call_id}")

(run_id, tool_call_id) 在一个 run 内唯一且跨段稳定（tool_call_id 由工具节点生成，落在 message 表里）。顺带修掉一个既有隐患：随机 approval_id 在重试路径上会留下孤儿 Approval 行。

6.3 SuspensionMiddleware 的三条判据

悬空的 tool_call（有 tool_use 无 tool_result）  → jump_to tools
末批 ToolMessage 里有 marker                     → jump_to end
两者都没有                                        → 正常流向 model

全部只看 messages。一段里同时有两种 marker 时（模型一轮里既委派又调了高风险工具）：tools 优先 —— 先把待执行的工具跑掉，委派结论已经在历史里了，tools 跑完自然流向 model。

6.4 D 让审批的冒泡整个消失

这是选 D + 审批挂起的最大回报。原先的链路：

旧  子 run 的 approval → 父 run 的轮询循环 → get_stream_writer() → 父流
      挂起后三处同时失效：
        ① _await_result 返回 marker 后循环就结束了，没人再调 _forward_approvals
        ② 就算想调也没有出口 —— get_stream_writer() 只在图上下文里有效，图已跳出
        ③ 父流上不会再有新事件

新  子 run 的 approval → 子 run 自己的 EventFactory（base_depth=1） → thread 流
      前端订阅 thread，直接就收到了

SubagentService._forward_approvals 和它那段「实测两次委派各卡满 300s，审批最终 expired」的注释一起删除 —— 它记录的问题由架构消解了。

ApprovalRequiredData.run_id 这个字段仍然必要（决策要 POST 到对应 run 的端点），但 ApprovalModal 的 runId={pendingApproval?.runId ?? activeRunId} 可以简化成 runId={pendingApproval.runId} —— thread 流里每个事件都带 run_id，回落不再需要。

6.5 超时判定权的移交

旧新
判定者gate 内的 BLPOP 超时resume reaper：扫 suspended run 时检查 created_at + timeout < now → 标 expired → 唤醒续跑
approval_timeout_s60086400（一天）

默认值从 10 分钟提到一天，是这次改造真正解锁的东西：挂起不占用任何进程，审批因此可以等到用户第二天上班。

但仍然保留超时，不做无限等：一个永远 pending 的 approval 会让 thread 永久锁死（DB 权威锁认 suspended，见 §8）。

awaiting_approval 保留为 suspended 的细分

不合并。UI 要区分「在等机器」和「在等你」—— 前者用户只能干等，后者需要他行动。实现上两者共用 suspension 机制，只在 status 字面值上分开。

07交汇点：补齐与悬空

★ 两个机制会在这里打架

domain/messages.py 的 to_storage 有一条不变量：每个 tool_use 必有配对的 tool_result，悬空的会自动补一条 is_error 的「执行被中断」（不补则下一轮直接 400）。

而审批续跑要求 tool_call 悬空 —— 那正是 jump_to tools 的判据。补齐之后 middleware 就不跳，工具永远不执行。

正确的顺序：

阶段消息序列为什么
审批挂起落库AIMessage(tool_use) + ToolMessage(marker:approval:<id>)marker 本身就是一条合法的 tool_result，配对完整，格式合法
续跑重建历史换成「已放行」占位（__ATLAS_RELEASED__）序列保持配对 —— 否则 PatchToolCallsMiddleware 会在图入口把悬空补成「cancelled」（§12 修正 10）
before_model删掉占位 + jump_to "tools"制造悬空的时机推到 patch 之后

而 _seal_dangling_tool_calls 只在真正异常中断（没有 marker 的悬空）时起作用。两者不冲突，但这个边界必须在 _settle_pending 里写死并配一条测试 —— 否则将来有人「顺手统一」就会把审批路径压坏，而症状是「批准了但工具没跑」。

对比委派续跑的处理，差异一目了然：

delegation marker  →  换成结论（子 run 的最终文本）   → 流向 model
approval   marker  →  换成放行占位 → before_model 删它 → 跳 tools

委派挂起的实现里刻意没有建这张列（靠 marker 字符串 + parent_run_id 查 barrier 就够，见 §12 修正记录 1）。加审批之后 barrier 判据分叉了 —— 子 run 终态 vs approval 被决策 —— 把「在等什么」显式落一列比在消息序列里反复解析更清楚。

8.3 会话锁的权威源（已实现）

挂起可以持续一小时，而没有进程替它续租 Redis 锁。把 TTL 调到覆盖最长等待也不行：进程被杀时锁要空悬那么久，对应会话一直 409。

权威判据 → DB：这个 thread 上还有没有没跑完的 run（active_run_of，含 suspended）
Redis 锁 → 降为短 TTL 的抢占互斥，只防「两个请求同一瞬间都查到没有活跃 run」

这顺带修掉了「进程被杀后锁靠长 TTL 熬」这个既有问题。

11.1 不可避免的代价

不是 bug，写明以免以后当 bug 查：

  • 每次挂起必然一次 prompt cache miss。间隔一小时跨过任何档位的 cache TTL。物理限制，消不掉。
  • 失败的 run 现在也留痕。模型说过的话、调过的工具会落库。原先抹掉的代价是用户重试时模型不知道上次做到哪，把有副作用的操作又做一遍。
  • 主 agent 下一轮记得上一轮委派的结论。它以 tool_result 落进父历史（格式要求，不是污染）。原先只活在内存里 —— 那其实是个缺陷。父历史会因此变长。

11.2 与本设计正交、仍未做的

  • ACP 断连续传。Pod 里的 CLI 还在跑，但 session/prompt 的响应绑在那条断掉的 WS 上，拿不回来（bridge/ws.py 明确丢弃断连期间的 update）。本设计保住了父 run，没保住子 run 那一小时。
  • subagent_max_running=3 的配额模型。挂起让父 run 不再占进程，用户会更愿意派长任务；三个小时级委派占满后，后续委派全被拒到任务结束。且判据要从进程内计数改成 DB 查询（挂起跨进程了）。

12设计过程中的修正

按 文档约定：设计先写、实现后跑，跑通之后发现设计错了的地方回来改文档，并且写明原来错在哪。删掉修正只留最终形态，会让人以为这些结论一开始就想明白了 —— 而下一个人会在同样的地方再摔一次。

修正 1 · run_delegation 表整张不需要

设计初稿要建一张 run_delegation(run_id, tool_call_id, sub_run_id, task_hash, status, result_content)，兼做 join barrier、幂等键、结论载体，估了 8% 的工作量。实现时发现一张都不需要：

需求初稿实际用了什么
marker ↔ 子 run 关联表里存映射marker 字符串自带 token，而它所在的 ToolMessage 本来就带正确的 tool_call_id
join barrier表里数 pendingWHERE parent_run_id=? AND status NOT IN (终态) —— ix_run_parent 早就在
结论载体result_content子 run 自己的会话（last_assistant_content），续跑时现取
幂等task_hash挂起方案不重放，用不上

连带好处是没有第二个事实源：结论的权威始终在子会话里，子 run 被 fresh=true 重跑时不会出现两份分叉的结论。

（审批加入后 run.waiting_on 一列又回来了 —— 但那是一列，不是一张表，且理由不同：barrier 判据分叉了。见 §8.2。）

修正 2 · jump_to 不能从图输入传进去

初稿写「续跑时 _graph_input 带 {"jump_to": "tools"}，或用 Command(goto=)」。两条都不成立：InputAgentState 只有 messages，jump_to 标着 PrivateStateAttr = OmitFromSchema(input=True, output=True)，传进去被直接丢弃。

正确做法是 middleware 在 before_model 里从 state 自己推断（§3.2 有实验输出）。这个修正让设计变简单了：PreparedRun.resume_entry 整个字段不需要，server 侧什么都不用传。

修正 3 · 超时检查必须在轮询之前

_await_result 初版是「sleep(interval) → 查子 run 终态 → 查等待窗口是否超时」。于是 subagent_inline_wait_s=0（「不等，直接挂起」）实际上还是会等一个轮询间隔 0.5s，而子 run 在那 0.5s 里往往已经跑完 —— 配置为 0 却走了同步路径，挂起从未触发。

测试先撞上了这个：断言 run.suspended 事件存在，拿到的却是一条完整的成功事件流。把窗口检查移到 sleep 之前，「等多久」才真正由配置说了算。

修正 4 · 「never 返回的假模型」不存在

测试里想构造「子智能体永不返回」来稳定停在 suspended，用的是 TurnModel(scripts=[[AIMessageChunk(content="")]])。但空内容也是一次正常完成 —— 子 run 照样终态、照样来唤醒父 run，断言拿到的是 'queued'。

改为直接构造状态（跑完一轮再把几个列按回挂起中）。「挂起中」本来就只是几个列的值；直接摆出来，测的反而是这些测试真正关心的东西（取消怎么收尾、扫描捞不捞、孤儿回收碰不碰它）。

修正 5 · 迁移里的约束真名

op.drop_constraint("status_enum", "run", type_="check") 报「约束不存在」。naming_convention 会加一层 ck_<table>_ 前缀，而 0001 建表时传进去的名字本身已经带着一层 —— 库里实际是 ck_run_ck_run_status_enum。改用 raw SQL 写死真名，不让 convention 再插手。

修正 6 · 漏了唤醒的一整条来源

初稿把「谁来唤醒」只想了一半：委派是子 run 收尾时唤醒，而审批的决策来自 HTTP —— 那条路径压根没设计。少了它，用户点完「允许」要干等周期扫描 （默认 60s），看着像没生效。

修法是把 resume_if_ready 提升进 RunExecutor 协议， 端点在 submit_decision 之后调它。协议的 docstring 现在明写 「唤醒有两个来源，都在执行器之外」。

修正 7 · awaiting_approval 在错误的词表里

它原先在 _RUNNING（「有进程在跑」）里 —— 那时是对的： awaiting_approval 意味着一个 asyncio.Task 正阻塞在 BLPOP 上， 进程死了它确实是孤儿。

改成挂起之后它的含义变了：「挂起中，等人点头」，没有进程是正常的。 留在 _RUNNING 里意味着**每次部署都把所有等待中的审批判死**。 词表因此拆成三个：_RUNNING（有进程）/ _SUSPENDED （挂起，含 awaiting_approval）/ _UNFINISHED（两者之和）。

连带踩到的：resume_if_ready 开头写的是 status != "suspended" —— 等审批的 run 落的是 awaiting_approval，于是审批永远唤不醒。三条测试同时红才 暴露出来。这类「状态值多了一个，而某处还在用 == 比较」的 bug 要靠把词表导出成常量（SUSPENDED_STATUSES）来防。

修正 8 · 挂起检测不能依赖调用方记得传 transcript

_suspensions 只能从 transcript 看（runner 拿不到图的最终 state）。而 transcript 原先是可选参数 —— 不传时检测静默失效：图确实 因为哨兵跳出了，但 runner 当成正常结束，于是 run 落成 succeeded 而哨兵留在 历史里，下一轮模型读到一句 __ATLAS_SUSPENDED__:...。

改成 runner 内部无条件构造一份（调用方传了就共享）。让它无条件生效比依赖 每个调用方记得传更可靠。

修正 9 · 两处死机制要删掉，而不是留着

Redis 的决策队列（run:approval:{id}）在审批改成挂起后没有消费者 了，连带 submit_decision 的 redis 参数和那条论证 「用 BLPOP 而非 pub/sub」的测试一起删除。同理 gate 的 timeout_s 在超时判定移交 reaper 后是个死参数。

留着的代价不是那点开销，是误导：下一个人看到 rpush 会 以为有等待方。这与 §06 删 _forward_approvals 是同一条理由。

修正 10 · 「悬空的 tool_call」这条判据与 kernel 直接冲突

初稿的审批续跑靠「把哨兵那条 ToolMessage 删掉，让 tool_use 悬空」 来触发 jump_to "tools"。§07 还专门讨论过它与 to_storage._seal_dangling_tool_calls（我们自己那个补齐逻辑） 的交汇 —— 但漏掉了 kernel 里早就存在的另一个：

PatchToolCallsMiddleware.before_agent 在图入口给一切悬空的 tool_call 补上一句「was cancelled - another message came in before it could be completed.」。它在核心栈里、排在用户 middleware 之前，顺序无法调整。

于是续跑段的实际行为是：删出来的悬空被 patch 当场补掉 → SuspensionMiddleware 看到的序列配对完整 → 不跳 tools → 流向模型 → 模型看到「工具被取消了」就重新发一次调用 → 再挂起一次。 死循环，表现是「点了允许但 run 一动不动」，而每转一圈烧一次模型调用。

修法：续跑时把 approval 哨兵换成一条「已放行」占位 （__ATLAS_RELEASED__:<approval_id>），而不是删掉 —— 交给图的 序列因此始终配对完整，patch 不插手。制造悬空的时机推到 before_model：中间件在那里返回 {"messages": [RemoveMessage(id)], "jump_to": "tools"}，一次同时 完成「删占位」和「去执行」，而 patch 已经跑完，没有第二次机会。

这个 bug 单测抓不到

单测直接调 before_model 或用裸 create_agent 构图 —— 两种都不含 PatchToolCallsMiddleware（它是 create_deep_agent 装的）。12 条中间件测试、7 条审批端到端测试全绿，而真机第一次跑就撞上。

教训是具体的：依赖「某个中间状态」作为信号时，要先确认没有别人也在管那个状态。 显式标记（一个只有我们认识的占位）比隐式状态（悬空）稳健得多。

修正 11 · awaiting_approval 在两条路径上不是一回事

§06 把审批统一成挂起，于是 awaiting_approval 被划进 _SUSPENDED，恢复扫描照着这个词表找可续跑的 run。对 native 成立， 对 acp 不成立：

路径审批期间的真实状态
native图已跳出、进程已结束 —— 真挂起，waiting_on 有值
acpCLI 在 Pod 里发起的同步 RPC，run 还在跑 —— bridge 正等着响应，只能在线等（见 §06 末），waiting_on 是空的

扫描不区分的后果：一个正在跑的 acp 子 run 被当成可续跑并 submit 第二次， 第二个 AcpChannel 连上同一个 Pod，bridge 按 CLOSE_SUPERSEDED(4409) 关掉第一个 —— 整轮 runtime_crashed。症状是「审批批准了，子 run 却崩了」， 而崩的原因在另一个组件的关闭码里。

修法：suspended_runs() 加一条 waiting_on IS NOT NULL， _waits_are_settled() 里对「状态是 awaiting_approval 但没有 waits」直接返回 False。这一条不是优化，是正确性 —— 注释里写死了这句话， 否则下一个人会把它当成多余的过滤条件删掉。

修正 12 · 一列 varchar(128) 伪装成「子智能体不说话」

真机上 native → acp 的委派表现为：子智能体干完活但不出声，父模型连试两次， 最后向用户报告「cli-hand 的输出通道可能有问题」。父模型的推理没有错， 错的是平台喂给它的每一层信息。

根因是一行 schema：Approval.tool_name 是 String(128)。 native 往里写的是真工具名（write_todos，十几个字符），acp 写的是 CLI 给的 toolCall.title —— 而 Terminal 工具的 title 就是整条命令。 一条带几个 && 的验证命令轻松过 128， StringDataRightTruncationError。

然后它连过三道，每一道都把信息磨掉一层：

环节做了什么信息损失
gate.check()捕获一切异常，按不放行处理（§12.2 的红线，方向正确）「系统坏了」被压成「用户拒绝了」
CLI收到 reject_once 就停手，不重试不解释本轮零文本产出
translate_stopstopReason=end_turn → run.finished子 run 报 succeeded，而它什么都没做成

再加上 acp 的 tool_call_update 只带变化的字段（title 在 start 时给过就不重复， 被拒的工具也没有 output），而前端 upsertTool 是浅合并 —— 空串把 start 时记下的 工具名原地抹掉。用户在界面上看到的最终形态是 {"name": "", "result": "", "status": "error"}： 一个没有名字、没有原因的失败工具行。根因只在 Pod 日志里。

四处一起改，缺一条就还是查不出来：

改动为什么在这一层
ApprovalRepository.create 截断 tool_name约束属于存储层。只改 acp 的话，下一个长 tool_name 的来源会再撞一次
ApprovalState 加 failed「系统没工作」与「系统工作了并否决」处理相同、含义相反。压成一个值，故障在界面上完全隐形
acp 自己发一条带原因的 tool.failed原因只在平台手里 —— CLI 眼里就是「用户没批」
「有工具失败 + 零文本产出」→ run.failed两个条件缺一不可：只看前者会误伤 CLI 的正常试错，只看后者会误伤真的没什么可说的一轮
失败方向选对了，可观测性仍然可以归零

except Exception → 不放行 这条红线本身是对的，这次也确实挡住了工具。 但它沉默地挡住了 —— 而沉默的安全措施和没有安全措施，在排查时长得一模一样。 安全的失败方向不能替代说清楚为什么失败。

连带发现：test_acp_end_to_end.py 已经红了一段时间， 因为 websockets 默认要问 urllib.request.getproxies()， 而它在 macOS 上不只看环境变量、还读系统网络设置 —— 开发机配了全局 SOCKS 代理之后， 连 127.0.0.1 也被拐进代理，报一句和 WebSocket 毫无关系的 「python-socks is required」，而 env | grep -i proxy 是空的。 connect(..., proxy=None) 一行堵住。 测试红着没人管，正是上面那条「静默故障」链能活这么久的原因。
