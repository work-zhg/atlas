01WebSocket

WebSocket（RFC 6455，2011）是一个建立在 TCP 之上的全双工、长连接、面向消息的协议。它借用一次 HTTP 请求完成握手，之后这条 TCP 连接就不再说 HTTP，而是双方随时可以向对方发送「消息」。

1.1 它解决什么问题

HTTP 是请求—响应模型：只有客户端能发起，服务端只能被动回答，且一问一答。当服务端需要「主动说话」时，历史上有几种变通：

方案做法代价
短轮询客户端每隔 N 秒问一次「有新消息吗」延迟 = 轮询间隔；大量空请求
长轮询服务端把请求挂住，有消息才返回，客户端立刻再发下一个每条消息一次完整 HTTP 往返；服务端要管理挂起的请求
SSE一个不结束的 HTTP 响应，服务端持续往里写事件只能服务端 → 客户端；客户端要说话仍得另发 HTTP 请求
WebSocket握手后变成双向消息通道连接有状态、要自己管理生命周期（见 1.8 · 1.10）

WebSocket 的核心价值是两点：双方都能主动发，以及一条连接上承载任意多条消息（不必每条消息付一次握手与头部的开销）。

1.2 协议分层

应用协议 你自己定义：消息长什么样、怎么关联请求与响应、版本… ← WebSocket 不管（1.10） ──────────────────────────────────────────────────────────────── 消息 一条完整的 text（UTF-8）或 binary 数据 ← 应用看到的单位 帧 消息被切成一个或多个帧；另有控制帧 ping/pong/close ← 1.4 · 1.5 握手 一次 HTTP/1.1 GET + Upgrade，成功后协议切换 ← 1.3 ──────────────────────────────────────────────────────────────── TLS（可选） wss:// = WebSocket over TLS，与 https 同一套 TCP 可靠、有序的字节流：不丢、不乱序、不重复 —— 但只在这一条连接之内

理解分层能避免一类常见误解：WebSocket 的「可靠、有序」完全来自 TCP，因此只在一条连接的生命周期内成立。连接一断，断点前后发生了什么，协议本身一无所知。

1.3 握手

客户端 → GET /session HTTP/1.1 Host: bridge.example:8900 Upgrade: websocket Connection: Upgrade Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ== 16 字节随机数的 base64 Sec-WebSocket-Version: 13 Sec-WebSocket-Protocol: acme.v2, acme.v1 可选：应用子协议，按偏好排序 Sec-WebSocket-Extensions: permessage-deflate 可选：扩展（压缩） Authorization: Bearer <token> 普通 HTTP 头，鉴权常放这里 服务端 → HTTP/1.1 101 Switching Protocols Upgrade: websocket Connection: Upgrade Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo= Sec-WebSocket-Protocol: acme.v2 从客户端列表里选定一个回显 Sec-WebSocket-Extensions: permessage-deflate …此后这条 TCP 连接上只有 WebSocket 帧，不再有 HTTP…
头作用
Upgrade / ConnectionHTTP/1.1 的协议升级机制。中间的代理必须认识并放行它（1.12）
Sec-WebSocket-Key → AcceptAccept = base64(SHA1(Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))。不是鉴权：它只证明对面确实是一个理解 WebSocket 的服务端，而不是一个碰巧回了 200 的普通 HTTP 服务或缓存
Sec-WebSocket-Version固定 13。不匹配时服务端回 426 并告知支持的版本
Sec-WebSocket-Protocol应用层协议的版本协商。客户端报列表，服务端选一个回显；不回显 = 没有选定任何子协议。这是 WebSocket 里唯一内建的「双方确定地达成一致」的机制
Sec-WebSocket-Extensions协商扩展，最常见的是 permessage-deflate（RFC 7692，逐消息压缩）
Origin浏览器自动带上，服务端据此拒绝跨站连接（1.11）。非浏览器客户端通常不带

握手阶段仍然是 HTTP，所以可以用任何 HTTP 状态码拒绝（401、403、426…），而且拒绝时连接根本不会升级。一旦回了 101，再想拒绝就只能走 WebSocket 的关闭流程（1.7）。

1.5 消息与分片

  • 消息有边界。这是它相对裸 TCP 的一大便利：TCP 是字节流，应用得自己分包（换行符、长度前缀）；WebSocket 保证收到的就是对方发出的那一整条。
  • text 必须是合法 UTF-8，否则对端应以 1007 关闭连接。JSON 走 text；任意字节走 binary。
  • 分片：一条大消息可以拆成「首帧（opcode=text/binary，FIN=0）+ 若干续帧（opcode=0）+ 末帧（FIN=1）」。发送方可以边生成边发，不必先知道总长度。
  • 控制帧可以插在分片之间：一条 100MB 的消息正在分片传输时，ping 与 close 仍能及时送达。控制帧自身不能分片，负载 ≤ 125 字节。
  • 数据消息之间不能交错：一条消息的分片没发完，不能开始发另一条数据消息。所以一条超大消息会堵住它后面的所有消息 —— 队头阻塞在消息粒度上依然存在。

1.6 心跳：ping / pong

TCP 有一个根本局限：对端悄无声息地消失时（机器掉电、网络被切、NAT 表项过期），本端在不发数据的情况下永远察觉不到。连接会停在「看起来还开着」的状态，称为半开连接。

  • 收到 ping 必须尽快回 pong，并原样带回 ping 的负载（用来配对是哪一次 ping）。
  • 可以主动发不请自来的 pong，作为单向心跳。
  • 典型用法：每 N 秒发一次 ping，M 秒内没收到对应 pong 就判定连接已死、主动关闭。
  • 心跳还有第二个作用：让连接不空闲，避免被中间的负载均衡 / NAT 按空闲超时掐断（1.12）。
  • 浏览器的 JavaScript API 不能发 ping（只能被动回 pong），浏览器场景的应用层心跳只能用普通消息模拟。服务端之间通信没有这个限制。
心跳只证明「连接活着」，不证明「对方在干活」

pong 通常由协议库在 I/O 层自动回复。对端的业务逻辑哪怕已经卡死在一个死循环里，只要事件循环还能跑，pong 照样回来。「对方业务是否还在推进」是应用层要单独回答的问题。

1.7 关闭与状态码

A ──close(1000, "done")──▶ B A 进入 CLOSING，不再发数据帧（控制帧除外） A ◀──close(1000)──────────── B B 回一个 close，同样不再发数据 之后 TCP 关闭（通常由服务端先关，避免客户端端口进入 TIME_WAIT）

这叫关闭握手：双方都明确知道「对方不会再发数据了」。与之相对的是异常关闭 —— TCP 直接断掉，没有 close 帧，本端看到的状态码是 1006。

码名称含义
1000Normal Closure正常结束
1001Going Away一方要离开：服务端下线、页面关闭
1002Protocol Error协议错误
1003Unsupported Data收到了无法处理的数据类型（如只收 text 却来了 binary）
1005No Status Rcvd保留，不能发送：对方的 close 帧里没带状态码
1006Abnormal Closure保留，不能发送：连接没经过关闭握手就断了
1007Invalid Payload数据不合法，如 text 不是 UTF-8
1008Policy Violation违反策略（通用的「不允许」）
1009Message Too Big消息超过接收方上限
1010Mandatory Ext.客户端要求的扩展服务端没协商

close 帧可以附带一个原因字符串，但总负载 ≤ 125 字节（状态码 2 字节 + 原因 ≤ 123 字节），只够写一句话，不适合传结构化的错误信息。

1.8 连接生命周期

CONNECTING ──握手成功(101)──▶ OPEN ──一方发出或收到 close──▶ CLOSING ──TCP 关闭──▶ CLOSED │ │ └──握手失败(4xx/超时)──────────┴──TCP 直接断开（无关闭握手，code 1006）──────────────▶ CLOSED
  • 只有 OPEN 状态下能收发数据消息。
  • 一条连接只会经历一次这个过程，不能「重开」。所谓重连，就是新建一条连接，从 CONNECTING 重新开始 —— 对协议而言它和上一条毫无关系。
  • 每个阶段都应有超时：握手超时（CONNECTING 卡住）、关闭超时（对方不回 close 时，等多久后直接断 TCP）。

1.9 流控与背压

WebSocket 协议里没有任何流控机制。唯一的流控来自下层 TCP：接收方读得慢 → 接收窗口变小 → 发送方的内核发送缓冲积压 → 发送方的写操作最终阻塞。

发送方应用 ──send()──▶ [库的写缓冲] ──▶ [内核发送缓冲] ══TCP══▶ [内核接收缓冲] ──▶ [库的接收队列] ──recv()──▶ 接收方应用 write_limit max_queue 超过则 send() 等待 满了就停止从 socket 读 → TCP 窗口收缩 → 反压到发送方

三件事要分清：

  • send() 返回 ≠ 对方收到。它只表示消息已进入本端缓冲。发送方无从得知对方应用有没有处理 —— 需要确认就得在应用层设计（1.10）。
  • 反压是好事。它让「生产太快的一方」慢下来，而不是让「消费太慢的一方」内存爆掉。设计上要让反压能传到真正的源头，而不是在中间某一层用一个无界队列吞掉。
  • 单条消息大小上限（max_size）是接收方的自我保护：超过就以 1009 关闭连接。上限要与业务上可能出现的最大消息匹配，并且整条链路上各段一致。

1.10 它不提供什么

这一节决定了应用协议要设计什么。WebSocket 只是「一条能双向发消息的管子」，以下这些全都没有：

缺失的能力后果应用层的常见做法
请求—响应关联发出一条消息后，收到的下一条不一定是它的回答每条请求带 id，响应回带同一个 id（如 JSON-RPC 2.0）
送达确认不知道对方应用是否处理了某条消息显式 ack，或把「响应」当作确认
重投连接断开时缓冲里的消息直接丢失发送方保留未确认的消息，重连后重发
跨连接的顺序与去重重连前后的消息谁先谁后、有没有重复，协议不知道消息序号 + 接收方按序号去重
断线续传新连接从零开始重连时带上「最后收到的序号」，对方从那里补发
鉴权与授权握手后的每条消息都不带身份握手时鉴权，把身份绑定到连接上
消息类型 / 路由收到的只是一段 text 或 bytes消息内带类型字段
超时协议层面一条消息可以永远没有回答应用对每类请求定义超时及超时后的动作
多路复用一条连接是一条消息序列，大消息会堵住后面的（1.5）在消息里带「流 id」自己复用，或开多条连接

1.11 安全

议题要点
传输加密ws:// 明文，wss:// = TLS。掩码不是加密（1.4）
鉴权时机在握手时做，失败直接回 401/403，连接不升级 —— 攻击者连一条可用的通道都拿不到。握手成功后再在消息里鉴权，意味着任何人都能先占一条连接
凭据放哪服务端之间：Authorization 头。浏览器：JS API 不能设自定义头，常见替代是 cookie、query 参数（会进访问日志，需短期有效）或借用子协议头
跨站劫持（CSWSH）WebSocket 不受同源策略与 CORS 约束。浏览器会带上目标站点的 cookie，恶意页面因此能以用户身份建连。服务端必须校验 Origin，或不用 cookie 鉴权。只有浏览器会带来这个风险
资源耗尽限制单条消息大小、接收队列长度、每个来源的连接数；握手与关闭都要有超时，防止慢速连接占满资源
压缩permessage-deflate 省带宽，但每条连接要维护压缩上下文（内存），解压还可能被构造的「压缩炸弹」放大。内网高带宽场景常直接关掉
「在内网」不是边界同一网络里的其它工作负载一样能连上来。凭据校验不能因为「只在内网」而省略

空闲超时负载均衡、NAT、代理普遍会掐断一段时间没有流量的连接（常见默认 60 秒左右）。心跳间隔必须小于链路上最短的空闲超时

连接是有状态的一条连接钉在某个后端实例上。实例重启 = 连接全断；扩缩容与滚动发布都要考虑存量连接怎么处理
健康检查对 WebSocket 端口做 TCP 探测会建立又立刻断开连接，在服务端日志里留下噪音。更好的做法是在同一端口上对某个路径直接回 HTTP（不升级）

1.15 对 bridge 的启示

把本章的事实翻译成 bridge 设计必须回答的问题。每一条都会在后面的章节给出答案：

T1 · 可靠性只在一条连接之内（1.2 · 1.8）连接断开时，正在进行的工作怎么办？重连是「接着来」还是「重新来」？如果要接着来，序号、缓冲与补发由谁负责？
T2 · WebSocket 不带请求—响应语义（1.10）通道上跑什么应用协议？请求如何关联响应？一个可能持续很久的请求（CLI 的一整轮工作）与普通请求要不要区别对待？
T3 · 双向都能发起请求（1.1）除了 server 找 bridge，bridge 也要找 server（例如 CLI 请求权限）。反向请求没有及时应答时，谁决定超时、默认结果是什么？
T4 · 心跳只证明连接活着（1.6）「CLI 还在干活吗」由什么判定？卡死检测与「整件事最多做多久」是不是同一个计时？
T5 · 版本协商有现成机制（1.3）server 与 bridge 分开发布、在跑的 Pod 不能原地升级。用子协议协商版本，还是在应用消息里协商？
T6 · 鉴权要在握手时完成（1.3 · 1.11）凭据是什么、多久有效、如何把一条连接绑定到一个会话？同一会话来了第二条连接怎么办？
T7 · 协议没有流控，只有 TCP 反压（1.9）CLI 输出很快而 server 处理不过来时，压力传到哪里？中间有没有无界队列？单条消息上限定多少，链路各段是否一致？
T8 · 大消息会堵住后面的消息（1.5）整份文件内容这类大负载要不要走这条通道？如果走，它会不会延迟取消、权限这类紧急消息？
T9 · 关闭要有语义（1.7）哪些情况用 4000–4999 私有关闭码表达（鉴权失败、被新连接取代、会话已结束…）？结构化的错误信息放在关闭帧还是应用消息里？
T10 · 部署环境会掐连接（1.12）心跳间隔与链路上的空闲超时是否匹配？健康检查如何不污染日志？Pod 滚动或被驱逐时，存量连接如何收尾？

02ACP 协议

ACP（Agent Client Protocol）是 bridge 另一侧说的协议：CLI（或它的 adapter）只认 ACP。本章只讲协议本身。依据是官方仓库 agentclientprotocol/agent-client-protocol 的 schema-v1.23.0 标签（2026-09-18 发布）下的规范文档、meta.json 与 schema.json。v1 是稳定版，v2 仍是草案（2.0.0-alpha.5），单独放在 2.13。

2.1 是什么、为什么

编辑器想接入各种编码 agent，agent 也想被各种编辑器使用。没有标准时，这是一个 M × N 的集成问题：每一对都要写一套胶水代码。ACP 的做法与 LSP（语言服务协议）一样，定义一个中间协议，把问题变成 M + N：编辑器实现一次「ACP client」，agent 实现一次「ACP agent」。

官方架构文档列出三条设计原则：

原则含义
MCP-friendly基于 JSON-RPC，尽量复用 MCP 的数据类型（如内容块），集成方不用再维护一套表示
UX-first为「把 agent 的意图清楚地呈现给人」而设计：流式正文、思考过程、工具调用、计划、diff 都有专门的消息
Trusted假设用户在编辑器前、信任所用的模型：用户仍能审批工具调用，但编辑器会把本地文件与 MCP server 交给 agent 使用
注意「Trusted」这条前提

ACP 的默认场景是本机、有人值守：编辑器与 agent 在同一台机器上，用户就坐在屏幕前，随时能点「允许」或「取消」。这个前提决定了协议里很多东西的形态（例如权限请求可以一直等人回答）。把 ACP 搬到远端 Pod、由平台代替编辑器时，这个前提不再自动成立（2.15）。

2.2 角色与拓扑

ACP MCP Client ◀══════════════════▶ Agent ◀══════════════▶ MCP server（工具 / 数据） 编辑器、IDE、其它 UI 编码 agent（常是一个 CLI） · 拉起 agent 子进程 · 调用模型、执行工具 · 展示过程、代用户做决定 · 向 client 汇报进度、请求权限 · 把用户配置的 MCP server 告诉 agent · 自己去连 MCP server
  • Client：管理环境、与用户交互、控制资源访问。Agent：用生成式 AI 自主修改代码，通常作为 client 的子进程运行。
  • ACP 与 MCP 分工不同：ACP 是「client ⇄ agent」，MCP 是「agent ⇄ 工具」。client 在建会话时把 MCP server 的连接配置交给 agent，由 agent 自己去连。
  • 一条连接可以承载多个会话（官方架构文档原话：「Each connection can support several concurrent sessions」）。会话由 sessionId 区分。
  • 两个方向都能发请求：client 调 agent（如 session/prompt），agent 也调 client（如 session/request_permission）。

2.3 传输

规范定义的传输只有 stdio 一种；Streamable HTTP 仍是「讨论中的草案」。规范允许自定义传输，条件是保持 JSON-RPC 消息格式与 ACP 的生命周期要求，并且应当写明建连与消息交换的方式。

stdio 规则内容
进程关系client 把 agent 作为子进程拉起，并负责结束它（关闭 stdin、终止进程）
方向agent 从 stdin 读消息，向 stdout 写消息
分帧一条消息一行，以 \n 分隔，消息内部不得含换行（JSON 里的换行必须转义）
编码UTF-8
stdout 纯净agent 的 stdout 上只能出现合法的 ACP 消息；client 写进 stdin 的也只能是 ACP 消息
日志agent 可以往 stderr 写日志；client 可以收集、转发或忽略
大小上限规范没有规定单条消息的上限。一条消息可能带着整个文件的内容（diff、写入内容），实现方要自己定读缓冲的大小

2.4 消息模型

ACP 完全遵循 JSON-RPC 2.0，只有两类交互：

类型形状语义
方法（请求—响应）请求带 id + method + params；响应带同一个 id 与 result 或 error必须得到一个响应
通知只有 method + params，没有 id单向，永远不会有响应（成功失败都不回）

约定：

  • JSON 对象的键用 camelCase（如 sessionId、toolCallId）；判别字段的取值用 snake_case（如 agent_message_chunk、end_turn）。
  • 协议中出现的文件路径必须是绝对路径；行号从 1 开始。
  • 两个方向各自分配请求 id。收到一条带 id 的消息时，靠「有没有 method」区分它是对方的请求还是对自己请求的响应。

2.5 版本与能力协商

连接建立后，client 必须先调用 initialize，之后才能建会话。

client → initialize { "protocolVersion": 1, "clientCapabilities": { "fs": { "readTextFile": true, "writeTextFile": true }, "terminal": true }, "clientInfo": { "name": "my-client", "version": "1.0.0" } } agent → result { "protocolVersion": 1, "agentCapabilities": { "loadSession": true, "promptCapabilities": { "image": true, "audio": true, "embeddedContext": true }, "mcpCapabilities": { "http": true, "sse": true } }, "agentInfo": { "name": "my-agent", "version": "1.0.0" }, "authMethods": [] }
规则内容
协议版本一个整数，代表主版本，只在有破坏性变更时递增。client 报自己支持的最新版本；agent 支持就原样回，不支持就回它自己支持的最新版本；client 不接受该版本时应当关闭连接并告知用户
能力所有能力都是可选的；请求里没列出的能力一律视为不支持。新增能力不算破坏性变更 —— 协议靠能力位演进，而不是靠版本号
client 能力fs.readTextFile / fs.writeTextFile（agent 可以反过来调 client 读写文件）、terminal（agent 可以让 client 执行命令）、elicitation（向用户索取结构化信息）等
agent 能力loadSession；promptCapabilities（prompt 里能否带图片、音频、嵌入资源 —— 文本与资源链接是必须支持的基线）；mcpCapabilities（能否连 HTTP / SSE 类 MCP server —— stdio 类是必须支持的）；sessionCapabilities（resume、close、delete、list 等）
鉴权agent 在 authMethods 里声明它需要的登录方式，client 按需调用 authenticate
能力位是双向承诺

client 声明了 fs 或 terminal，就意味着 client 必须真的能替 agent 读写文件、执行命令；agent 会据此改变自己的行为（例如不再自己读文件，而是请 client 读）。能力位不是「可以试试」，而是「我保证提供」。

2.7 会话

会话是一段对话的上下文：它有自己的历史与状态，由 agent 持有。client 拿着 sessionId 与之交互。

initialize 完成 ├─ session/new { cwd, mcpServers } → { sessionId } ├─ session/load { sessionId, cwd, mcpServers } → 先以 session/update 重放全部历史，重放完才响应 └─ session/resume { sessionId, cwd, mcpServers } → 不重放，恢复上下文后直接响应 │ ▼ 可以发 session/prompt 了
参数 / 规则内容
cwd会话的主工作目录，必须是绝对路径；无论 agent 进程是在哪个目录启动的都以它为准，也是相对路径解析的基准。与 additionalDirectories（需能力）一起构成文件操作的边界
mcpServers让 agent 去连的 MCP server。v1 中这个字段在 new / load 上必须出现（可以是空数组）。三种传输：stdio（name, command, args, env，所有 agent 必须支持）、http（type:"http", name, url, headers，需 mcpCapabilities.http）、sse（已被 MCP 规范废弃）。env 与 headers 都是 [{name, value}] 数组，不是对象
load 的重放agent 必须把整段对话以 session/update 通知重放出来（用户消息、agent 回答、工具调用…），全部发完之后才响应 load 请求。重放消息的形态与实时消息相同，v1 中没有字段区分「这是重放」还是「这是实时的」
closeagent 必须像收到 session/cancel 一样取消进行中的工作，然后释放该会话的资源

是否支持 load、resume、close，全看 initialize 返回的能力位；没声明就不得调用。

2.8 一轮 prompt

一轮（prompt turn）从用户发出一条消息开始，到 agent 完成回答结束，中间可能多次调用模型与工具。在 v1 中，session/prompt 请求要等整轮结束才响应 —— 它是一个可能持续很久的请求。

  • 规范没有规定权限请求的等待上限：在有人值守的前提下（2.1），它默认可以一直等到用户回答。

2.10 取消

取消一轮：session/cancel（通知）

一方规范要求
client发出 cancel 后，应当立即把本轮未结束的工具调用标为已取消；必须对所有还挂着的 session/request_permission 回复 cancelled；应当继续接收 cancel 之后到来的工具调用更新
agent应当尽快停止所有模型请求与工具执行；把剩余的更新发完之后，必须以 stopReason:"cancelled" 正常响应原来那个 session/prompt
取消不是错误

模型 SDK 在请求被中止时通常会抛异常，这个异常很容易以 error 的形式冒到 session/prompt 的响应上。规范明确要求 agent 捕获这些异常，回一个 cancelled 结束原因 —— 否则 client 无法可靠地确认「取消已完成」，而会把一次正常的取消当成故障展示给用户。

取消单个请求：$/cancel_request（通知）

JSON-RPC 本身没有取消机制，ACP 补了一个通用的：发送方用 $/cancel_request 指明要取消的请求 id。支持它的一方可以中止该请求及其派生的活动，但必须仍给原请求一个响应：要么是有效结果（可带部分结果），要么是错误码 -32800（Request cancelled）。支持是可选的。

执行方也可以内部取消（上下文超限、内部超时、资源不足），此时应当回同样的 -32800。规范给出的级联示例是：client 取消一轮 → agent 对自己发出的挂起请求（如权限请求）发 $/cancel_request → client 以 -32800 回复这些请求 → agent 以 cancelled 响应 prompt。

机制规则

03bridge 的职责边界

3.1 两项决定

#决定要点
D1bridge 是 ACP clientbridge 自己完成 ACP 握手、建会话、发起与取消轮次、应答反向请求。server 不说 ACP 的控制语义，改说一个由平台定义的上游协议（第 4 章）
D2内容翻译在 serversession/update 的内容原样交给 server，由 server 翻译成平台事件。bridge 只读取其中用于控制的信号，不改写、不删减、不重排

D1 的依据：取消的义务（2.10）、进程生命周期（2.3）、卡死判断（T4 · T14）、断线时的默认行为（T11），都只能由贴着 agent 进程的一方可靠完成；而与 ACP 版本绑定的对端（适配器、CLI）和 bridge 在同一个镜像里一起发布，把 ACP 的控制语义放进 bridge，版本耦合就留在镜像内部。

D2 的依据：update 内容 → 平台事件的映射是平台的事件契约，前端直接依赖它；这份契约应当随 server 发布、在一处演进，不应该跟着 Pod 镜像走。

3.2 一句话定义

bridge 是 Pod 里的「会话宿主」

对下，它是一个完整的 ACP client：拉起并看管 agent 进程，按规范履行 client 的全部义务。对上，它提供一个平台定义的会话宿主接口：接受「开会话 / 提交一轮 / 取消 / 关闭」这类指令，汇报「轮次状态」，并把 agent 的输出原样转交上去。
它理解协议，不理解业务：知道一轮什么时候开始、结束、卡住，不知道输出的内容意味着什么，也不决定一个工具该不该被允许。

3.4 控制面与数据面

D1 与 D2 合起来，等于把 agent 的输出分成两个面：

包含什么bridge 怎么处理server 怎么处理
控制面会话与轮次的生命周期、轮次状态（在干活 / 在等人 / 已结束）、结束原因、错误、时限、取消、权限询问的收发拥有：由 bridge 判定、由 bridge 宣告，以上游协议里的控制消息表达消费：据此更新 run 状态、弹审批、做兜底超时
数据面session/update 的内容：正文、思考、工具调用、计划、用量……只读、原样转交。可以从中读取控制信号（见下），但不改写拥有：翻译成平台事件、落库、推给前端

bridge 从数据面里读哪些控制信号

信号用途
任意一条 update 的到达「agent 还在推进」的证据，用于卡死检测（第 6 章）
v2 的 state_update直接给出 running / requires_action / idle 与结束原因
v1 的 prompt 响应一轮结束与结束原因（v1 没有 state_update）
工具调用的 status辅助判断 agent 此刻在执行工具还是在等模型（可选）
正在进行的反向请求「在等人」的直接证据：权限请求挂起期间，轮次处于等人状态
同一条消息可能同时属于两个面

v2 的 state_update 本身就是一条 session/update：bridge 读它来推进轮次状态（控制面），同时照样原样转交给 server（数据面）。规则是：数据面永远全量、原样转交；控制面是 bridge 基于同一份输入另外发出的消息。server 不需要、也不应当自己从数据面里推断轮次状态 —— 那是 bridge 的职责，推断两次就会得出两个答案。

3.7 D2 的含义与代价

server 要能读懂两个版本的 update

内容原样转交，意味着 ACP v1 与 v2 在 update 格式上的差异（2.13：tool_call 与 tool_call_update 的合并、messageId 变为必填、整条消息的 upsert、plan 改为 plan_update……）全部由 server 的翻译层吸收。这是 D2 的主要代价，我们接受它，并用两条规则控制它：

  1. bridge 在开会话时把协商结果报上去：ACP 版本、agent 的能力位、agent 名称与版本。server 据此选择翻译规则，而不是靠猜。
  2. 控制语义不外泄：轮次状态、结束原因、取消是否完成，永远以 bridge 的控制消息为准。server 的翻译层只负责「内容 → 展示」，不从内容里推导控制结论。这样 v1/v2 差异里最麻烦的那部分（prompt 响应语义的改变）不会到达 server。

bridge 声明哪些 ACP client 能力

能力声明理由
fs.readTextFile / writeTextFile否声明就得真的替 agent 读写文件（2.5）。agent 本就在 Pod 里、能直接访问工作区，由 bridge 代理只多一跳；v2 已移除这一面
terminal否同上，命令由 agent 在 Pod 内自行执行
elicitation暂不向用户索取结构化信息需要平台侧有对应的交互形态；等有需求时再声明
其它（如布尔配置项）按需只声明 server 真能处理的

原则：bridge 只声明它自己或 server 确实能兑现的能力。多声明一项，agent 就可能改走一条我们没有实现的路径。

数据面不是「字节透传」

「原样转交」指语义不变：同一条 update 的 JSON 内容不增、不删、不改，转交顺序与 agent 发出的顺序一致。bridge 可以（也应当）给每条转交的 update 套一层上游协议的信封，写明它属于哪个会话、哪一轮、是重放还是实时、序号是多少 —— 信封是控制面的，内容是数据面的。信封的具体格式在第 4 章定义。

3.8 边界不变式

#不变式为什么需要它
B1每一轮的开始与结束都由 bridge 宣告，且各只宣告一次，并带上结束原因单一事实来源。两处都能宣告，就会有两个答案
B2bridge 转交的 update 与 agent 发出的在内容上完全相同、顺序一致D2 成立的前提：翻译只在一处发生
B3上游不可达时，bridge 的一切默认都偏向安全：永远不会因为没人应答而批准任何权限请求，超过重连窗口仍不可达则一律拒绝；进行中的一轮按时限继续或取消，不会因为没人看着就无限期运行（第 7 章修订）ACP 假设有人在场（2.1），远端 Pod 里这个前提不成立（T11）
B4bridge 不持久化业务数据。Pod 里唯一持久的会话状态，是 agent 自己保存的会话文件server 是事件与记录的唯一权威；bridge 重启不应造成数据分叉
B5策略数值来自 server，bridge 只保留安全兜底默认值同一个 agent 在不同场景下需要不同的时限与等待上限，这些属于平台配置
B6agent 的反向请求永远有回应，无论上游在不在、轮次是否已结束ACP 的义务（2.10）；不回应会让 agent 一直等下去

04上游协议

本章定义 server ⇄ bridge 之间的应用协议（下称上游协议），把第 3 章的职责边界落成具体的消息。它承载在 WebSocket 上（第 1 章），与 ACP（第 2 章）是两套独立的协议。

4.1 设计原则

#原则理由
P1server 发出的请求都是短请求一轮工作可能持续很久，不能让「一个请求」承载它（T14）。提交一轮立即返回，进展与结束靠通知汇报 —— 与 ACP v2 的做法一致，无论 agent 说哪一版，上游都只看到这一种形态
P2控制与数据走同一条有序流顺序本身就是正确性的一部分：一轮的最后几条 update 必须先于「这一轮结束」到达。分两条流就要跨流重排序（4.10）
P3数据原样装进信封第 3 章 B2：ACP update 的内容一字不改，外面套一层上游信封写明归属
P4bridge 发出的每条消息都带序号为断线续传预留（第 7 章），也让 server 能发现丢失与重复
P5方法名与 ACP 明显区分上游用点号（turn.start），ACP 用斜杠（session/prompt）。日志与代码里一眼可辨，不会把两套协议混为一谈
P6协议面尽量小server 与 Pod 分开发布，每多一个方法，两边的兼容负担就多一分。能用参数表达的，不新增方法

4.2 基本形态：JSON-RPC 2.0

消息格式采用 JSON-RPC 2.0，每条消息是一个 WebSocket text 帧。

备选结论
JSON-RPC 2.0（选定）请求—响应靠 id 关联、通知单向、双方都能发请求 —— 正好覆盖「server 下指令」「bridge 发通知」「bridge 向 server 询问权限」三种交互。团队已经熟悉它（ACP 同款），调试工具通用
自定义带类型的事件流要自己重新发明「请求与响应的关联」，收益只是少几个字段
gRPC 双向流多路复用与强类型是真优势，但需要 HTTP/2 端到端，并引入 IDL 与代码生成；第 1 章已经选定 WebSocket 作为承载

约定：JSON 键用 camelCase；判别取值用 snake_case（与 ACP 一致，降低在两套协议之间来回切换时的认知成本）；不使用 JSON-RPC 的批量发送。

4.3 连接与版本协商

  • 版本协商用 WebSocket 子协议（1.3）。server 按偏好报出列表，bridge 选一个回显。子协议名只在不兼容的变更时递增；兼容的新增（新的可选字段、新的可选方法）通过 session.open 返回的 features 声明，不改子协议名。

// bridge → server（agent 会话建好之后）

    "agentSessionId": "sess_7f3a…",
    "resumed": true,                     // 要求恢复却没恢复成（能力不支持、会话不存在）时为 false

  • 「新建还是恢复、恢复哪个」由 server 决定；「用 load 还是 resume」由 bridge 按 agent 能力位决定（3.5）。replay 表达的是 server 的需求（要不要历史），bridge 选用能满足它的 ACP 方法。
  • 要求重放时，历史以 agent.update（origin: "replay"）在 session.open 的响应之前全部送达 —— 与 ACP load「重放完才响应」的顺序一致。
  • 恢复失败不是错误：返回 resumed:false 并已经新建了会话。「上下文丢失」必须让 server 知道，由它决定怎么告诉用户。
  • session.open 是唯一可能耗时较长的请求（agent 启动 + 历史重放），它有自己的超时（第 6 章）。

session.close 与 session.ended

session.close：若有进行中的一轮，先按取消流程结束它（会收到 turn.state ended），再关闭 agent 会话，然后响应。之后 bridge 以关闭码 4410 关闭连接。

session.ended：会话在 server 没有要求的情况下结束，例如 agent 进程退出且重启失败。参数带 reason 与结构化的 error。发出后同样以 4410 关闭连接。

4.10 大消息与单连接（T8）

一条 agent.update 可能带着整个文件的内容（diff 的 newText）。WebSocket 没有多路复用，大消息会堵住它后面的消息（1.5）。三种做法：

做法评价
单连接、严格按序（选定）顺序天然正确（P2）。代价是控制消息可能排在大消息后面 —— 在集群内网里，几 MB 的消息传输只需几十毫秒，而控制消息对延迟的要求是秒级，可以接受
控制、数据各一条连接控制消息不再被大消息阻塞，但「一轮的最后几条 update 先于 ended 到达」要靠跨连接重排序来保证；还要处理「两条连接只断了一条」
单连接、控制消息插队会违反顺序：ended 可能跑到这一轮最后几条 update 前面

配套规则：

  • 单条消息上限 32 MiB，两端一致（1.9），并与 bridge 读 agent stdout 的单行上限一致。
  • 超限不静默丢弃：bridge 以一条 agent.update 代替，内容换成 {"oversize": true, "bytes": N, "sessionUpdate": "…"} 并记录告警。这是 B2（内容原样）的唯一例外，且是显式的。
  • 关闭 permessage-deflate 压缩：内网带宽充裕，压缩的 CPU 开销与每条连接的压缩上下文内存换不来什么（1.11）；跨地域部署时再评估。

什么算「进展证据」

agent 在这个会话上从 stdout 送来的任何一条消息：update 通知、它发起的请求（如权限请求）、它对 bridge 请求的响应。心跳不算（ACP 没有心跳；WebSocket 的心跳只证明连接活着，1.6）。

为什么静默要分两档

agent 执行一个长时间的命令（安装依赖、跑测试、编译）时，往往几分钟都没有任何输出：工具调用停在 in_progress，模型在等工具结果。只用一个阈值的话，要么调得很短、把正常执行的命令误判为卡死，要么调得很长、真卡死时要等很久才发现。

bridge 从数据面读取工具调用的状态（3.4），维护「进行中的工具调用」集合： tool_call / tool_call_update 的 status = in_progress → 加入集合 status = completed / failed（或 v2 的 cancelled） → 移出集合 集合为空 → 静默阈值 = idleS（默认 120 s） 在等模型：模型服务不该沉默这么久 集合非空 → 静默阈值 = toolIdleS（默认 600 s） 在执行工具：允许长时间没有输出

v2 的 terminal_output_chunk 与 tool_call_content_chunk 本身就是进展证据，长命令只要有输出就会不断重置计时。

6.3 权限等待

  • 询问的过期时刻 = min(现在 + permissionWaitS, 本轮截止时刻)。截止先到时，询问随这一轮一起结束（按取消处理，给 agent 的答复是 cancelled）。
  • 到期未答复：给 agent 选 reject_once，向 server 发 permission.withdraw（expired），轮次回到 running 并重置静默计时。agent 收到拒绝后通常会换一种做法继续。
  • 同一轮里可能有多个询问同时挂起（agent 并发调用多个工具）。只要有一个询问挂起，轮次就处于 awaiting_permission，静默计时暂停；全部答复后才恢复。

6.4 取消流程

无论取消由谁触发，bridge 都走同一条流程。触发原因：

cause触发

deadline · idle6.2 的计时到点

为什么以 agent 的实际结果为准

取消与完成可能在同一时刻发生：bridge 发出 cancel 时，agent 恰好已经答完。此时如实报告 completed，server 可以照常把这一轮的结果展示给用户；硬报 cancelled 反而会让用户以为工作没做完，而文件其实已经改了。

终止进程是最后手段

终止 agent 会丢掉它进程内的全部状态，只能靠会话文件恢复（5.6）。所以宽限期不宜太短：15 s 足够一个遵守规范的 agent 中止模型请求、收拾工具、回出 cancelled；取消后多久能收尾，不同适配器差异很大，这个值上线后要按实测调整（6.9）。

server 读取server 必须及时从连接读取；入库、翻译等慢操作不能阻塞读取本身。它自己的缓冲也要有界，满了就停止读取，让 TCP 把压力传给 bridge
bridge 发送队列按字节计的上限 64 MiB。队列满时，bridge 停止读取 agent 的 stdout
agent 的 stdoutbridge 不读，管道缓冲写满，agent 的写操作受阻 —— 压力到达源头
单条消息stdout 单行上限、WebSocket 单条上限都是 32 MiB（4.10）
背压未必能让 agent 真的慢下来

「管道满了写操作就阻塞」是同步写的行为。常见的 ACP 适配器用 Node.js 实现，而 Node 写管道时不会阻塞：写不进去的数据留在它自己的内存里继续排队。这种情况下 bridge 停止读取只是把积压从 bridge 的内存挪到了 agent 的内存 —— 保护了 bridge，却保护不了 Pod。所以背压之外还需要一条兜底规则。

兜底：发送队列持续处于满的状态超过 30 s，就判定上游不健康，主动以 1011 关闭连接，进入第 7 章的断线处理。长时间读不动，意味着 server 已经跟不上了；与其让积压一直增长直到 Pod 内存耗尽，不如把它明确地变成一次断线。

反方向不受影响

WebSocket 是全双工的：bridge → server 方向的积压不会阻塞 server → bridge 方向。只要 bridge 读取上游消息的循环与发送队列相互独立，即使在大量数据积压时，turn.cancel 仍能及时到达 bridge。这是 bridge 实现上的一条硬性要求：读上游、读 agent、写上游，三者互不阻塞。

6.7 时间的表示

  • 跨进程传递时长，不传递时刻。server 给出 deadlineS: 900，bridge 用自己的单调时钟计时。两台机器的系统时间可能相差数秒甚至更多，用绝对时刻做判断会被时钟偏差放大或缩小。
  • permission.ask 里的 expiresAt 是展示用的绝对时刻（让前端显示倒计时），同时附带 expiresInS；server 的判断应当基于后者。bridge 自己的判断始终基于单调时钟。
  • turn.state 的 stats 里给出 elapsedS、awaitingPermissionS 等耗时，server 据此向用户解释「这一轮为什么超时」（例如「共 900 秒，其中等待审批 212 秒」）。

07故障、断线与恢复

第 5 章处理了 agent 进程在 Pod 内崩溃的情形。本章处理剩下的：上游连接断开、server 重启、bridge 进程崩溃、Pod 丢失。目标只有一个 —— 无论哪一层出事，server 最终都能知道发生了什么，并把会话带回可用状态。

7.1 故障分类

故障典型原因什么还在处理
上游连接断开网络抖动、server 重启或滚动发布、背压兜底主动断开（6.6）Pod、bridge、agent、进行中的一轮重连 + session.attach + 按序号补发（7.3）
agent 进程崩溃适配器或 CLI 出错、被 OOM 终止Pod、bridge、会话文件bridge 自行恢复（5.6）

Pod 丢失节点故障、驱逐、空闲回收会话文件、工作区（都在持久存储上，M7）新建 Pod，session.open 恢复（7.7）

四种故障的共同点：持久存储上的东西都在（会话文件、工作区），丢的只是进程内的协调状态。恢复的本质就是用持久的东西重建协调状态。

7.2 断线时进行中的一轮：继续跑

bridge 拥有轮次（D1），它不依赖上游连接也能看管这一轮。所以断线不立即结束这一轮，而是给一个重连窗口：

上游断开 │ 这一轮照常进行；bridge 发出的消息全部留在补发缓冲里 │ agent 发来的权限询问：暂存，不答复（agent 在等，静默计时按 6.3 暂停） │ 截止与静默计时照常走 │ ├─ 窗口内 server 重连并 attach ──▶ 补发缓冲里的消息，暂存的询问随之送达，一切照常 │ └─ 窗口到期仍未重连 ──▶ 取消这一轮（cause: upstream_lost，6.4） 暂存的询问全部答复拒绝（取消流程里为 cancelled） 会话保持打开（READY），ended 等结果留在缓冲里，等 server 回来取
决定理由
重连窗口默认 120 s，由 server 在 session.open 的 defaults.reconnectWindowS 给出要能覆盖一次 server 的滚动发布或重启（通常几十秒）。更长的窗口意味着 agent 在无人观察的情况下继续工作，但这仍受截止时限约束
询问在窗口内暂存，而不是立即拒绝一次几秒钟的网络抖动不应该让一个本来会被批准的操作被拒绝。暂存有上限（窗口），窗口到期仍一律拒绝 —— 永远不会因为没人应答而自动批准
窗口到期后会话不关闭server 可能只是重启得慢一些。会话保持打开，结果留在缓冲里，直到 server 回来或 Pod 被回收

这一节修正了第 3 章 B3 的表述：原文「上游不可达时权限一律拒绝」改为「不会因上游不可达而自动批准；超过重连窗口仍不可达则拒绝」（第 3 章已同步修订）。

7.3 重新接上：session.attach 与补发

为什么需要确认

bridge 把消息写进连接，不代表 server 收到并处理了它（1.9）。断线时，最后若干条消息可能在 bridge 的缓冲里、在网络上、或者已被 server 读到但还没来得及入库。只有 server 能说清楚「我已经可靠地处理到了哪一条」。

两个新方法

// ① server → bridge：定期确认（通知）。bridge 据此释放补发缓冲
{ "method":"session.ack", "params": { "seq": 412 } }
  // 含义：seq ≤ 412 的消息已经处理完成（入库），而不只是收到
  // 频率：每 1 s 或每 200 条，以先到者为准

// ② server → bridge：重连后第一条请求（代替 session.open）
{ "id":1, "method":"session.attach", "params": {
    "bridgeInstance": "b-7c1e…",   // 上次见到的 bridge 实例 id（7.6）
    "lastSeq": 412                 // server 已处理完成的最后一条
} }
{ "id":1, "result": {
    "state": "in_turn",                                    // ready | in_turn | recovering | ended
    "turn": { "turnId":"run_8ab2…", "state":"awaiting_permission" },
    "resendFrom": 413,                                       // 随后补发的第一条
    "gaps": [ ]                                               // 缓冲溢出时丢掉的区间（7.4）
} }
// 响应之后，bridge 按 seq 顺序补发 413 起的全部消息，然后接着发实时消息
  • 投递语义：至少一次 + 按序号去重。补发可能与 server 已经收到的消息重复，server 按 seq 丢弃已处理过的即可。「处理完成」由 server 用同一个数据库事务记录事件与 lastSeq，于是重启后的 server 也能给出准确的 lastSeq。
  • 补发的询问沿用原来的 JSON-RPC id。server 对同一个询问的答复只会被采用一次；bridge 已经自行答复过的（例如窗口到期后拒绝），紧跟着会补发 permission.withdraw，server 据此关闭审批界面。
  • server 的判断依据是 state 与 turn，不是补发的消息。补发是为了把事件流补全；会话此刻处于什么状态，以 attach 的响应为准。

7.4 补发缓冲

第 6 章的发送队列与补发缓冲是同一个缓冲：消息发出后不删除，直到被 session.ack 确认。上限仍是 64 MiB（6.6）。

情形规则
连接正常server 每秒确认一次，缓冲里通常只有最近一两秒的消息
断线期间缓冲将满先淘汰最老的 agent.update，控制消息（turn.state、session.state、询问与撤回）永不淘汰。被淘汰的序号区间记入 gaps
控制消息本身把缓冲占满理论上不会发生（控制消息很小、很少）。万一发生，取消当前这一轮以止损

这个淘汰顺序保证了：即使补发不完整，server 对会话与轮次状态的认知永远是完整的，缺的只是一段展示内容。server 收到 gaps 后，在对应的一轮上标注「部分过程记录缺失」，而不是假装完整。

连接正常时，缓冲的上限同时起背压作用

server 如果收到消息却迟迟不确认（处理太慢），缓冲会被已发送但未确认的消息占满，bridge 随即停止读取 agent（6.6）。这正是想要的：「server 跟不上」无论表现为读不动还是确认不动，压力都会传回 agent。6.6 的「持续满 30 s 即断开」对两种情况同样适用。

7.5 重连策略（server 侧）

规则内容

7.6 bridge 进程崩溃

bridge 崩溃时，它的子进程 agent 也随之结束（bridge 作为容器的主进程运行，容器退出会带走进程组内的全部进程），进程内的协调状态全部丢失。容器被重启后，bridge 从 BOOTING 重新开始，没有任何会话。

server 怎么知道 bridge 重启过

每个 bridge 进程启动时生成一个随机的实例 id，在 session.open 与 session.attach 的响应里返回。server 把它与会话一起记下。

server 重连，发 session.attach { bridgeInstance: "b-7c1e…", lastSeq: 412 } │ ├─ 实例 id 相同、会话存在 → 正常 attach（7.3） │ └─ 实例 id 不同（bridge 重启过） → 返回 SESSION_NOT_OPEN，data: { cause: "bridge_restarted", bridgeInstance: "b-91d4…" } server 据此： · 进行中的那一轮 → 以失败结束（cause: bridge_lost） · 发 session.open，带 resume.agentSessionId 恢复上下文

实例 id 解决的是一个具体的歧义：没有它，server 分不清「会话在，但缓冲里的消息补不回来了」与「会话根本不存在了」。

7.7 Pod 丢失

server 发现 Pod 丢失的途径：执行环境的管理组件报告 Pod 已不存在，或者重连持续失败超过 6.8 的兜底时间。处理与 7.6 相同：进行中的一轮以失败结束（cause: pod_lost），新建 Pod，session.open 恢复。

工具的副作用无法撤销

一轮在中途失败时，agent 可能已经改了一些文件、执行了一些命令。这些副作用留在工作区里，恢复会话不会把它们撤回。server 在向用户报告失败时应当说明这一点，而这一轮已送达的工具调用事件（数据面）正好记录了哪些操作已经发生。gaps 非空时，这份记录本身也可能不完整，要一并说明。

8.3 把 agent 当作不可信的

操作系统层面的隔离

措施防的是什么
agent 以另一个系统用户运行（bridge 为 uid A，agent 为 uid B）不同用户的进程无法读取对方的 /proc/<pid>/environ、内存，也无法向对方发信号。token 文件只对 uid A 可读
清理传给 agent 的环境变量只传 agent 运行所需的（HOME、PATH、模型相关配置等），bridge 自己的配置一律不传
拒绝来自本 Pod 地址的连接agent 与 bridge 共享网络命名空间，agent 连 bridge 端口时源地址就是 Pod 自己的地址（或回环地址），而 server 永远来自别的 Pod。这是凭据之外的又一层
agent 只能写工作区与自己的会话目录限制 agent 能篡改的范围

以另一个用户身份拉起子进程，需要 bridge 具备 CAP_SETUID / CAP_SETGID。bridge 只保留这两项能力，其余全部丢弃。备选做法是把 agent 放进同一 Pod 的另一个容器、双方通过共享卷上的 Unix socket 通信 —— 隔离更彻底，但 ACP 的 stdio 传输就要改成自定义传输（2.3），复杂度明显上升。第一版采用前者。

协议层面的防御

规则内容
输入校验agent 的每条输出都按 ACP schema 解析；不合法的行记录并丢弃，不影响状态机
大小上限单行 32 MiB（4.10）
并发询问上限同一轮最多 8 个挂起的权限询问，超出的直接拒绝。防止 agent 用大量询问淹没用户
不认识的方法未声明能力的方法（fs/*、terminal/*）与 _ 扩展方法一律回 -32601（4.9）
agent 不能影响控制决定之外的东西agent 能决定「这一轮以什么原因结束」，但不能延长时限、不能改变审批结果、不能影响 seq

数据与日志

数据面里是用户的代码与对话，可能包含密钥。bridge 的日志默认只记元数据（方法、会话、轮次、seq、大小、耗时），不记内容。适配器的 stderr 按行截断到 2 KB 后写入 Pod 日志，因为它同样可能打印敏感内容。需要记录内容排查问题时，由 server 按会话临时开启，并自动过期。

链路追踪

server 在 turn.start 的参数里带上 W3C trace context（traceparent）。bridge 以它为父节点创建「一轮」与每个 ACP 请求的 span，并通过 ACP 请求的 _meta.traceparent 继续传给 agent —— 这是 ACP 为追踪保留的键（2.12），适配器支持的话，链路能一直延伸到模型调用。这是 bridge 在 ACP 消息里写入的唯一附加信息，而且它走的是规范认可的位置。

8.5 健康检查

探针端点判定
startup/readyz覆盖预热时间：最长等 90 s
readiness/readyz预热完成（状态不在 BOOTING），可以接受 session.open
liveness/healthzbridge 的事件循环能在 1 s 内响应。不检查 agent：agent 的问题由 bridge 自己恢复（5.6），不应该让 Kubernetes 因此重启整个容器

两个端点与 WebSocket 共用一个端口，在握手前直接回 HTTP、不升级（1.12）。这样健康检查不会在日志里留下一条条「连接建立又断开」的噪音。

8.6 部署形态

会话 Pod（一个平台会话一个，M1） └─ 容器（镜像 = bridge + ACP 适配器 + CLI，一起构建、一起发布） ├─ PID 1：轻量 init（负责信号转发与回收僵尸进程） │ └─ bridge（uid A，只保留 CAP_SETUID / CAP_SETGID） │ └─ agent（uid B，oom_score_adj 调高） ├─ /run/secrets/bridge-token 只读，仅 uid A 可读 ├─ /workspace 持久存储：工作区 ├─ /home/agent/…（会话目录） 持久存储：agent 的会话文件（M7） └─ /tmp 临时
要求理由
bridge、适配器、CLI 在同一镜像ACP 的版本耦合留在镜像内部（3.1 D1）。镜像标签写明三者的版本，session.open 如实报告
bridge 退出则容器退出保证 agent 不会在没有 bridge 看管时继续运行（7.6）
agent 的 OOM 优先级调高bridge 与 agent 共用容器的内存上限。内存不足时应当让内核先杀 agent —— bridge 还能把它恢复回来；先杀 bridge 则整个会话的协调状态都丢了
会话目录放在持久存储上否则 Pod 回收后无法恢复上下文（5.2、5.6）。具体路径取决于 CLI，需要按 CLI 确认（9.4）
内存预算bridge 自身：发送缓冲 64 MiB + 单条消息 32 MiB + 运行开销，约 256 MiB；其余留给 agent

8.7 Pod 的终止与回收（T10）

收到 SIGTERM

① 进入排空：新的 turn.start 一律拒绝（SESSION_NOT_OPEN，cause: draining） ② 有一轮在进行 → 取消（cause: pod_terminating，6.4），等它结束 ③ 对 agent 发 session/close（如果支持），让它把会话文件写完整 ④ 发 session.ended（cause: pod_terminating），以 1001 关闭上游连接 ⑤ 终止 agent，bridge 退出

terminationGracePeriodSeconds 设为 60 s：取消宽限 15 s + 终止宽限 5 s + 关闭会话与收尾，留有余量。超时后 Kubernetes 会强制终止，此时会话文件可能不完整 —— 这正是要给足时间的原因。

收到 1001 的 server 知道这是一次有序退出：这一轮已经以 pod_terminating 结束，下次使用时在新 Pod 上恢复。

空闲回收

由平台决定，不由 bridge 决定（B5）：平台发现会话闲置超过阈值（例如 30 分钟没有新的一轮），先发 session.close，再删除 Pod。bridge 不自行退出，因为它不知道用户是不是马上就会回来，也不知道平台的资源状况。
