Detailed Design · Wire

server ⇄ bridge 通道详细设计

acp 详设把这条 WebSocket 定成「透明管道 + 三件本地事务」，正常路径已经在真 CLI 上跑通。本文补的是异常路径：一轮跑多久算超时、超时之后谁收拾残局、上一轮的帧怎么不串进下一轮。核心判断：长请求不能用固定总时限，而「这一轮结束」必须是两端与 CLI 三方都知道的事实。

超时分层：静默 / 截止 / 审批超时即取消轮次 idWS 子协议协商新 server 兼容旧 Pod

02现状：一条连接上的三类消息

03事故复盘：五次委派全部 300s

04设计目标与不变式

#不变式破了会怎样
I1一轮的时限由 server 决定，bridge 执行。bridge 不写死任何「整轮」时长R1：agent 配了 900s，bridge 300s 就掐掉
I2等人的时间不算 CLI 卡死。静默计时在审批等待期间暂停用户多想一会儿，整轮就被判卡死
I3任何一方判定一轮结束，CLI 一定收到 session/cancel。结束 = 完成 / 超时 / 失败 / 取消 / 断线R2：残留轮次堵住下一轮
I4每个来自 adapter 的帧都带轮次归属。server 只按归属做取舍，不按时间先后猜R3：审批被当成重放丢弃
I5反向请求永远有回应。不属于当前轮次的审批请求要回拒绝，不能静默丢弃CLI 一直等到自己超时
I6run 终态之后，它名下没有 pending 审批，也没有还在跑的轮询任务。R4：幽灵审批 + 泄漏的任务
I7一条链路上各段的帧上限同口径。R5：WS 8MB、stdio 64KB，丢帧还连坐
I8新 server 必须能驱动旧 Pod。Pod 在跑时无法原地升级发一次 server 就得重建全部会话 Pod

05版本协商：WS 子协议

I8 要求 server 知道对面是新 bridge 还是旧 bridge。不加方法（§01），也不在第一条业务请求里试探 —— 用 WebSocket 自带的子协议协商，在握手时就定下来。

server → GET / HTTP/1.1 Upgrade: websocket Authorization: Bearer <token> X-Thread-Id: <thread> Sec-WebSocket-Protocol: atlas.acp.v2, atlas.acp.v1 新 bridge → 101 Sec-WebSocket-Protocol: atlas.acp.v2 → 本连接按 v2 行为 旧 bridge → 101 （不回该头） → server 视为 v1，走兼容路径
版本含义
v1现状：透明管道，无帧扩展，bridge 固定 300s。server 自己兜底超时与取消（§13）
v2本文：帧扩展 atlas 字段（§06）、bridge 执行静默 / 截止超时并在超时时取消（§07 §08）、帧带轮次归属（§09）
 
# acp/src/atlas_acp/wire.py
SUBPROTOCOL_V1 = "atlas.acp.v1"
SUBPROTOCOL_V2 = "atlas.acp.v2"
#: server 按偏好顺序报出；bridge 选它支持的最高版本
OFFERED = (SUBPROTOCOL_V2, SUBPROTOCOL_V1)
为什么用子协议而不是自定义头

子协议是 RFC 6455 里专门做这件事的机制：客户端报出列表，服务端选定一个回显，双方都能确定地知道结果。自定义请求头只能单向声明，旧 bridge 不认识它也不会告诉你。websockets 两端都原生支持（subprotocols=）。旧 bridge 不回该头时客户端是否照常建连，是待验证项 V1。

06帧扩展：atlas 字段

新能力都放在 JSON-RPC 帧的一个顶层扩展成员 atlas 里，不进 params。它只存在于 server⇄bridge 这一跳：bridge 转给 adapter 前剥掉，从 adapter 收到的帧由 bridge 加上。adapter 按 ACP schema 严格校验 params（踩过：缺 mcpServers 就回 -32602），往 params 里塞东西等于赌对方宽松。

server → bridge：请求上的控制参数

{ "jsonrpc": "2.0", "id": 7, "method": "session/prompt",
  "params": { "sessionId": "…", "prompt": [ … ] },          ← 原样给 adapter
  "atlas": {                                                ← bridge 读完即剥
    "turn": "8ab2836b-…",        // 轮次 id = run_id（一个 run 恰好一轮 prompt）
    "idleTimeoutS": 120,         // 静默上限（§07）
    "deadlineS": 900             // 截止：从 bridge 收到本帧起算（§07）
  } }

initialize / session/new / session/load 也可带 atlas.deadlineS（短请求只有截止、没有静默概念），缺省 60s。

bridge → server：来自 adapter 的帧上的归属

{ "jsonrpc": "2.0", "method": "session/update", "params": { … },
  "atlas": { "turn": "8ab2836b-…", "phase": "prompt" } }

// phase 取值：
//   load    session/load 进行中（ACP 规定 load 要先把历史以 update 重放一遍）
//   prompt  某一轮 prompt 进行中，turn 为该轮 id
//   orphan  该轮已被判结束（超时 / 取消），CLI 还没停下时漏出来的帧；turn 仍为那一轮
//   idle    不在任何请求期间（理论上不该有，出现即记告警）
# acp/src/atlas_acp/wire.py
class AtlasExt(BaseModel):
    model_config = ConfigDict(populate_by_name=True, extra="allow")
    turn: str | None = None
    phase: Literal["load", "prompt", "orphan", "idle"] | None = None
    idle_timeout_s: float | None = Field(default=None, alias="idleTimeoutS")
    deadline_s: float | None = Field(default=None, alias="deadlineS")
JSON-RPC 允许顶层扩展成员吗

2.0 规范只定义了 jsonrpc/method/params/id，没有禁止其它成员，但也不保证对端忽略。这里的关键是它从不离开我们控制的两端：server 与 bridge 都用 atlas_acp 的模型解析（extra="allow"），adapter 看不到。§15 有一条测试守住「bridge 转给 adapter 的帧里没有 atlas 字段」。

07超时分层

计时谁定 / 谁执行规则默认
静默server 定，bridge 执行adapter 每吐一帧（通知或反向请求）就重置；有反向请求在等 server 回话时暂停（I2）acp_prompt_idle_timeout_s = 120s（已有配置，此前从未接线）
截止server 定，bridge 执行从 bridge 收到请求起算的绝对上限，审批等待也算在内（防一轮无限期挂着占 Pod）spec.limits.timeout_s（与 native 同源）
审批server单次审批最多等多久；实际取 min(acp_approval_wait_s, 截止剩余)从 240s 提到 600s（不再受 bridge 300s 绑架）
兜底serverserver 自己的 channel.request 超时 = 截止 + 宽限（30s）。正常情况下 bridge 先报；它只在 bridge 失联时生效截止 + 30s
短请求server 定，bridge 执行initialize / session/new / session/load 只有截止60s（load 历史长时可调）

bridge 侧一轮 prompt 的计时状态机

为什么截止要把审批等待算进去

静默不算审批（I2），是为了不把「人在想」误判成「CLI 卡死」。但截止必须算：一轮占着一个 Pod 与一个会话串行锁，没有绝对上限的话，一个没人理的审批能把会话锁挂到审批超时为止。两种计时回答的是两个问题 —— 「它还活着吗」与「这一轮最多占用多久」。

事故里的数字按新规则会怎样

8f56：12 次审批共等 62s，其余是 CLI 连续写文件、每几秒就有 update —— 静默计时从不触发；截止取 agent 的 900s，整轮能做完。8ab2 若没有 R2/R3，也不会先白等四分钟。

08取消与善后

I3 与 I6 要求「一轮结束」在三方之间是同一个事实。按「谁先知道」分四种情形：

情形bridge（v2）server
bridge 判超时（静默 / 截止）发 session/cancel 给 adapter → 宽限 → 回 TURN_TIMEOUT 或重启 adapter 回 TURN_ABANDONED收到错误 → run.failed（带原因）→ 善后
用户取消同上，reason=client已有：relay.is_cancelled → 发 session/cancel（runtime.py:348）→ 等响应 → run.cancelled → 善后
server 兜底超时 / 自身异常—新增：先发 session/cancel，再关通道 → run.failed → 善后
通道断开（server 重启、网络）新增：连接关闭时若有轮次在跑，等同 reason=disconnect 的取消run.failed(runtime_unreachable) → 善后

server 侧「善后」的三件事

# server/src/atlas_server/acp/runtime.py —— run_turn 的 finally，任何终态都走
async def _settle(self, channel, run_id, session_id, *, ended_normally: bool) -> None:
    if not ended_normally:
        await channel.notify(Method.SESSION_CANCEL, {"sessionId": session_id})   # ① I3，v1 bridge 也有效
    await channel.cancel_reverse_tasks()        # ② 此前 create_task 不留引用（RUF006），审批轮询比 run 活得久
    await ApprovalRepository(session).expire_pending(run_id)   # ③ I6：本 run 名下 pending → expired
① 在 v1 下也成立，这是先落地它的理由

session/cancel 是通知，bridge 原样转给 adapter，旧 bridge 也会转。所以「server 在任何非正常结束时都发一次 cancel」不依赖 bridge 升级，就能把 R2 的主要危害（残留轮次堵住下一轮）消掉 —— 前提是旧 bridge 此时还连着，而超时路径上它确实还连着（它只是回了个错误）。

审批行的终态

expire_pending(run_id) 用一条条件更新 UPDATE approval SET status='expired' WHERE run_id=? AND status='pending'。与用户点按钮竞争时，谁先写谁赢，后写的一方拿到 0 行 —— 决策接口本来就对「已决策」回 409，前端据此关弹窗（审批弹窗修复里已处理）。

09轮次归属与过期帧

现在 server 靠「load 响应到达时队列里的都是旧的」来切边界（_drive 里的清空队列）。这个判据对通知成立，对反向请求不成立 —— 反向请求不能丢，必须回话（I5）。v2 下 server 按 atlas.phase / atlas.turn 逐帧决定：

帧归属server 的处理
session/updatephase=prompt，turn=当前翻译成事件（现状）
session/updatephase=load丢弃（它是历史重放，现状的清空队列就是在做这件事）
session/updatephase=orphan 或 turn≠当前丢弃并计数（指标 acp.frames.stale）
request_permissionphase=prompt，turn=当前走审批（现状）
request_permission其余任何归属立即回拒绝（reject_once），不建审批行、不发 approval.required；日志记 turn 与 phase

v1 连接没有归属字段，保持现在的清空队列逻辑，但修掉 R3：清空时只丢通知，队列里的内部审批帧与反向请求改为回拒绝。这一条也不依赖 bridge 升级。

为什么过期的审批回拒绝而不是转给用户

那一轮已经被判结束，它的结果没有人会用；让用户去批一个「上一次失败的任务里的写文件」，批准了反而是在不受控地改工作区。回拒绝让残留轮次尽快收尾，也是「断线时审批按拒绝」的同一条安全默认。

10断线与重连

方案做法代价
A · 一轮随连接结束（选定）一轮进行中断线，该 run 失败；bridge 把在跑的轮次当作 reason=disconnect 取消（§08）；下一个 run 靠 session/load 拿回上下文长任务一断就白跑。但断线本身稀少（同集群、有心跳），而 §07 之后长任务不再被误杀
B · 一轮之内续传bridge 给 update 编号并缓冲；server 重连时带游标补发，续上同一轮bridge 要持缓冲与游标、server 要能在 run 中途换通道 —— 等于把会话流的续传机制下推一层。不做，理由见下
选 A 的前提

A 能成立，靠的是 §08 的「断线即取消」：旧 bridge 的现状是断线后 CLI 继续跑、审批按拒绝 —— 那就是本次事故的「残留轮次」。只要断线后这一轮被干净地终止，下一轮 load 拿到的就是一个静止的会话，A 的代价只剩「重跑」。等真出现「断线频繁到重跑不可接受」的数据，再评估 B。

连接取代时的在途轮次

新连接取代旧连接（4409）时，旧连接上若有轮次在跑：不迁移到新连接，按 reason=disconnect 取消。新连接的第一个请求照常是 initialize → load。这让「一个轮次只属于一条连接」成为可依赖的性质。

16落地顺序

S1 · 只改 server（旧 Pod 立即受益）

非正常结束一律发 session/cancel；反向请求任务留引用并在通道关闭时取消；run 终态审批出列；清队列只丢通知、反向请求回拒绝；server 兜底超时改为「截止 + 宽限」。

验证：T5、T6。复现事故：在现有（v1）Pod 上让一轮超时后立刻委派下一轮，下一轮的 load 不再被堵。

S2 · bridge 小修（不改线协议）

limit=_MAX_FRAME_BYTES；/healthz 与探针；300s 改读环境变量、默认提到 1800s，并在超时时发 cancel。

验证：T8。重建 bridge 镜像；已有会话 Pod 需重建才生效（旧 Pod 继续按 v1 工作，不受影响）。

S3 · 线协议 v2

子协议协商、atlas 帧扩展、bridge 轮次状态机、归属过滤、新错误码与映射、审批等待按版本分档。

验证：T1–T4、T7、T9–T11；真 CLI 链路（test_acp_real_cli）跑一个 >300s、多次审批的任务。

S4 · 可观测性

§12 的指标与日志前缀；错误 data 进 run.failed 的附加字段。

为什么 S1 放第一

本次事故五个根因里，R2 / R3 / R4 三个的修复点在 server，而 server 是一处发布、立即覆盖全部在跑的 Pod。S1 做完，「一轮超时连带堵死后面所有委派」这个最伤人的形态就没了；剩下的 R1（300s 本身太短）在 S2 就能先用环境变量放宽。

风险

#风险缓解
K1截止从 300s 放宽到 agent 配置值后，真卡死的 CLI 占 Pod 更久静默计时专门抓卡死（120s），截止只管「正常工作但太久」

  • 加新方法 —— 全部能力走帧扩展与错误码（§01）
