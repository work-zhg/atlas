Code Design · Bridge v2

Bridge 代码设计

把 Bridge 重新设计的九章落成代码结构：分哪些包、每个包里有哪些模块、核心类各自持有什么状态、对外暴露什么方法，以及一个请求在这些类之间怎么流动。文中「§x.y」指设计文档的章节。

4 个包 + server 对接模块单事件循环状态机即类假时钟 + 假 agent 可测

00范围与约定

约定内容
语言与运行时Python 3.13，asyncio。bridge 内不使用线程，所有状态只在一个事件循环里修改（§5.5）
依赖pydantic 2（消息模型）、websockets 15（上游连接）。可观测性用 prometheus-client 与 opentelemetry-api，均为可选依赖
仓库结构沿用 uv workspace：每个包一个目录，src/ 布局，hatchling 构建
依赖方向用 import-linter 契约强制（1.3），违反即 CI 失败
命名一个模块一个主要类；状态机类以 …State 枚举 + 类方法表达状态转换，转换函数名即转换本身（如 begin_cancel）
可测性时间、进程、连接三样外部依赖都经协议注入（Clock、MessageChannel），单元测试不启动进程、不等真实时间

01包划分与依赖

1.1 四个包：职责与拆分理由

包（目录）导入名内容使用者
jsonrpc/ 新atlas_jsonrpcJSON-RPC 2.0 的帧模型、编解码、通用端点 RpcEndpoint。与 ACP、上游协议都无关bridge、server
acp/ 重构atlas_acpACP 协议模型（v1，日后 v2），由官方 schema.json 生成，外加少量手写辅助bridge（全部）；server 只用 update 相关模型（翻译）
host/ 新atlas_host上游协议：12 个方法的参数与结果模型、错误码、关闭码、子协议名（§4）bridge、server
bridge/ 重写atlas_bridgebridge 进程本身会话 Pod 镜像

server 侧新增一个模块 atlas_server.host，承担上游协议的客户端与 ACP 内容的翻译（第 11 节）。

每个包管什么、刻意不管什么

包负责刻意不管第三方依赖变化来源与节奏
atlas_jsonrpc帧的解析与编码；请求与响应按 id 关联；请求超时；通道关闭时让挂起的请求全部失败；对方请求并发处理、通知按序处理（背压）；current_request_id()传输方式（stdio、WebSocket、内存由 MessageChannel 适配）；任何方法的语义无JSON-RPC 2.0 规范，几乎不变
atlas_acp由 ACP 官方 schema.json 生成的模型（v1/_generated.py）；能力位解读 AgentCaps；从原始 update 读控制信号（update_kind、tool_status）怎么发请求；会话与轮次；任何平台概念pydanticACP 官方发版，外部、节奏不受我们控制；重新生成即可
atlas_host上游协议 12 个方法的参数与结果模型；TurnLimits、Outcome；错误码、关闭码、子协议名；两端共用的校验规则（如 outcome 只在 ended 时出现）ACP 的内容（一律是不透明的 JsonObject）；传输pydantic我们自己；改动要两端同时兼容，兼容新增走 features
atlas_bridgebridge 进程：agent 进程管理与重启节制、会话与轮次状态机、计时与取消、权限代理、Outbox 与补发、WebSocket 服务端平台概念（run、事件、审批表、用户、数据库）上面三个包 + websocketsbridge 的业务规则，改动最频繁

拆分的依据：每个包只有一个变化来源

拆包看的不是代码量，而是谁会让它改变。上表最后一列是四个互不相同的变化来源：冻结的 JSON-RPC 规范、外部的 ACP 官方、需要两端协调的上游协议、频繁迭代的 bridge 业务。变化来源不同的代码放在一起，一处变化就会连带无关代码一起改、一起评审、一起发布；按变化来源拆开，每次改动都只落在一个包里。

四个包都是仓库内的 uv workspace 成员，不单独发版到包仓库。拆包带来的是边界，而不是版本管理的负担。

好处

好处体现在哪里
两端共用一份协议定义server（atlas_server.host）与 bridge 导入的是 atlas_host 里同一组模型。字段改名、加字段只改一处，两端的测试同时覆盖。若两端各写一份，字段漂移只能靠联调发现。
D2 由规则守住，而不是靠自觉atlas_host 不得导入 atlas_acp（import-linter 契约，§1.3）。于是上游协议在类型层面就不可能理解 ACP 内容。ACP 从 v1 升到 v2 时，上游协议的类型一个都不用改（§3 D2）。
容易出错的通用逻辑只写一遍RpcEndpoint 同时服务三条链路：bridge 与 agent 之间（stdio）、server 连 bridge 的客户端（WebSocket）、测试里的 FakeAgent（内存通道）。请求关联、超时、关闭收尾这类细节只有一份实现、一份测试。
依赖面最小atlas_jsonrpc 零依赖，atlas_host 与 atlas_acp 只依赖 pydantic。会话 Pod 的镜像不会带上 server 的依赖（SQLAlchemy、LangChain…）；server 使用协议模型时，也不会被迫引入 bridge 的进程管理代码。
能独立测试每个包有自己的 tests/：jsonrpc 测帧与端点，host 测模型的校验规则，acp 测生成结果与辅助函数，bridge 测状态机与进程。前三个包的测试不需要进程、网络或数据库，毫秒级跑完。
各自演进，互不牵连ACP 的模型可以随官方 schema 整体重新生成（生成脚本可复现），不会碰到上游协议；上游协议的兼容新增走 features，也不必跟随 ACP 的节奏。
边界本身就是文档看 import 就知道谁认识谁：bridge 不认识 server，上游协议不认识 ACP。读代码的人不会在 bridge 里找平台的审批逻辑，也不会在上游协议里找 ACP 的字段。

为什么不是更少，也不是更多

替代方案问题
全部放进 atlas_bridgeserver 要用上游协议模型，就得依赖整个 bridge 包（连带 WebSocket 服务端、进程管理）；bridge 与 server 之间的边界也无法再用依赖规则约束。
上游协议并入 atlas_acp，合成一个「协议包」两种协议同处一个包，「上游协议不理解 ACP」（D2）就无法用依赖规则表达，只能靠约定；重新生成 ACP 模型时，也可能误碰上游协议的代码。
JSON-RPC 并入 atlas_hostbridge 的 ACP 客户端也需要 JSON-RPC。放进 host 的话，ACP 一侧就得依赖上游协议，依赖方向反了。
拆得更细（例如把 bridge 的 session/、upstream/ 拆成独立包）它们只被 bridge 自己使用、总是一起发布，拆开只会增加协调成本。包内用模块分层（§5）加上 import 规则就足够了。
代价

构建镜像时要把依赖的包一起打进去：docker/bridge/Dockerfile、docker/app/Dockerfile 以及各自的 .dockerignore 白名单都要列全，漏一个就会构建失败或在运行时报 ImportError。不兼容的协议改动需要 server 与 bridge 同时发布 —— 这是协议本身的性质，拆包只是把它变得显式。

02atlas_jsonrpc

jsonrpc/src/atlas_jsonrpc/ ├── frames.py Request · Notification · Response · RpcError；parse_frame(text) → Frame ├── errors.py 标准错误码常量；RpcFault（携带 code/message/data 的异常） ├── channel.py MessageChannel 协议 ├── endpoint.py RpcEndpoint：id 分配、挂起请求、分派 └── memory.py MemoryChannel：一对内存通道，测试替身（§12.1）
# channel.py —— 一条「按消息收发文本」的双向通道。stdio 与 WebSocket 都实现它
class MessageChannel(Protocol):
    async def send(self, text: str) -> None: ...
    async def receive(self) -> str | None: ...      # None = 通道已关闭

# endpoint.py
RequestHandler = Callable[[str, dict], Awaitable[Any]]      # (method, params) → result；抛 RpcFault = 错误响应
NotificationHandler = Callable[[str, dict], Awaitable[None]]

class RpcEndpoint:
    """一条通道上的 JSON-RPC 对端。双向：既能发请求，也能处理对方的请求。"""
    def __init__(self, channel: MessageChannel, *, name: str,
                 on_request: RequestHandler, on_notification: NotificationHandler) -> None
    async def run(self) -> None                   # 读循环：直到通道关闭；关闭时让所有挂起请求失败
    async def request(self, method: str, params: dict, *, timeout: float) -> Any
    async def start_request(self, method: str, params: dict) -> asyncio.Future[Any]   # 发出即返回，供长请求使用
    async def notify(self, method: str, params: dict) -> None

实现修正：初稿有一个 respond(request_id, result) 供「延后答复」（权限请求）使用。实现时发现不需要 —— 对方的每个请求本来就在独立任务里处理，处理函数等多久再返回，就是延后多久答复。改为增加 start_request：发出请求后立即返回 Future，供 session/prompt 这类可能持续很久的请求使用（§7.3）。

行为规则
对方的请求每个请求起一个任务处理，读循环从不等待处理完成（§6.6 C6：长时间的处理不能堵住读取）
对方的通知按到达顺序串行处理（顺序对 update 有意义，§4.8）
收到的响应按 id 找到挂起的请求并唤醒；找不到的记日志后丢弃
request 超时抛 TimeoutError。是否据此重启对端由调用方决定，端点本身不做判断
通道关闭所有挂起请求以 ChannelClosed 失败

它在 bridge 里只用于与 agent 的 stdio。上游方向不直接用它发消息，因为上游需要序号与补发，而 RpcEndpoint 的挂起请求表是跟着连接走的（断线即清空），不能跨连接保留（第 7 节 Outbox）。

03atlas_acp

acp/ ├── schema/v1/ 官方 schema.json 与 meta.json（schema-v1.23.0，原样收录，附来源与校验和） ├── scripts/generate_v1.py 从收录的 schema 生成下面两个文件；不联网、不写时间戳，输出可复现 └── src/atlas_acp/ ├── … 旧模块（wire / types / updates / caps），现有 bridge 与 server 仍在用，不动 └── v1/ ├── _generated.py 生成的 pydantic 模型（215 个类），禁止手改 ├── methods.py 生成的方法名常量（来自 meta.json） ├── caps.py AgentCaps：能力位解读（出现即支持；形状不对按不支持） ├── updates.py update_kind / tool_status：直接读原始 JSON 的控制信号 ├── errors.py ACP 定义的错误码（-32800 · -32000 · -32002） └── __init__.py 只重新导出实际用到的类型

实现修正：初稿把 caps.py、version.py 放在包根目录，但那里已有同名的旧模块，放进 v1/ 避免与旧代码冲突，旧模块在切换后删除。生成参数里的 --collapse-root-models 让 ToolCallId 这类简单别名直接是 str；它同时把联合类型展开，字段的类型是各个变体本身。变体的类名是生成器编号的（SessionUpdate4 之类），但每个变体都继承规范里有名字的类型（如 ToolCall、McpServerHttp）—— 判断类型时一律用有名字的类。

决定理由
模型从官方 schema 生成ACP 的类型有两百多个，手写必然漂移。生成脚本固定在一个发布标签上，升级 ACP 时换标签重新生成，差异一目了然
生成的模型允许未知字段（extra="allow"）新版本 agent 可能多带字段；透传给 server 时不能丢（§3.8 B2）
bridge 转交 update 时不经模型往返先解析成模型再序列化回去，可能改变字段顺序、省略空值，违反「原样」。bridge 只在需要读控制信号时解析（§3.4），转交的永远是收到的原始 JSON 对象
v2 放在 v2/ 子包两个版本并存（§2.13 官方建议），按协商结果选择

层职责不做什么
agent/把「一个会说 ACP 的子进程」包装成类型化的异步接口不知道轮次、会话、上游的存在
session/全部业务规则：状态机、计时、取消、权限、恢复不碰 socket、不碰进程，只调用 agent/ 与 Outbox 的接口
upstream/连接、鉴权、编解码、序号与补发不做任何业务判断，收到指令直接交给 HostSession

这个分层让 session/ 可以在没有进程、没有网络、没有真实时间的情况下完整测试 —— 而它恰恰是 bug 最集中的地方。

06运行时结构

6.1 常驻任务

①、③、④ 是三个独立任务，这就是 §6.6 C6「读上游、读 agent、写上游互不阻塞」在代码里的样子：发送积压只会让 ① 停下，③ 照常读取，turn.cancel 照样能到达。

6.2 状态修改的规则

  • 所有状态（会话状态、轮次状态、询问表、缓冲）只由事件循环里的回调与任务修改；没有锁，也不需要锁。
  • 一次状态转换在同一个同步代码段里完成「改状态 + 把对应消息放进 Outbox」，中间没有 await。于是 seq 的顺序与状态转换的顺序天然一致（§5.5）。
  • 需要等待的操作（发 ACP 请求、等宽限期）先把状态转到一个「进行中」的中间态，再 await；醒来后先检查状态是否已被别的事件改变。

6.3 启动顺序

  1. 读配置、读 token 文件、生成 bridge 实例 id
  2. 启动 UpstreamServer（此时 /readyz 返回 503）
  3. AgentSupervisor.boot()：拉起 agent、完成 initialize（§5.5 预热）
  4. HostSession 进入 IDLE，/readyz 返回 200
  5. 等待；收到 SIGTERM 时执行 drain() 后退出（§8.7）

7.1 类关系

7.2 HostSession

会话状态机（§5.5），也是上游指令的唯一入口：dispatch 把每个上游方法映射到它的一个方法上。

class SessionState(StrEnum):
    BOOTING = "booting"; IDLE = "idle"; OPENING = "opening"; READY = "ready"
    IN_TURN = "in_turn"; RECOVERING = "recovering"; CLOSING = "closing"; ENDED = "ended"

class HostSession:
    # —— 上游指令（由 dispatch 调用）——
    async def open(self, p: OpenParams) -> OpenResult             # IDLE → OPENING → READY
    def       attach(self, p: AttachParams) -> AttachResult         # 校验实例 id，交给 Outbox 计算补发
    async def close(self) -> None                                  # → CLOSING → ENDED
    def       start_turn(self, p: TurnStartParams) -> TurnStartResult  # READY → IN_TURN；同 id 查 ledger
    def       cancel_turn(self, turn_id: str) -> TurnCancelResult
    async def drain(self) -> None                                  # SIGTERM：§8.7 的五步

    # —— 来自下层的事件（由 AcpClient / AgentSupervisor 回调）——
    def       on_agent_update(self, raw: dict) -> None                 # 定 origin → Outbox；转给当前 Turn 读信号
    async def on_permission_request(self, raw: dict) -> dict        # → PermissionBroker；返回 ACP 结果
    def       on_agent_lost(self, cause: FailCause) -> None          # 当前轮 failed → RECOVERING

    # —— 状态 ——
    state: SessionState
    agent_session_id: str | None
    limits: TurnLimits                                             # open 时的 defaults
    turn: Turn | None

每个上游方法都有一张「允许的状态」表，不在表里就抛 SessionNotOpen（带 cause：recovering、draining…），由 dispatch 转成错误码 -32010（§4.11）。

    oom_score_adj: int | None = 900 # §8.6：内存不足时先杀 agent；None 或无 /proc 时跳过
    max_line_bytes: int = 32 * 2**20
    stderr_line_bytes: int = 2048

class AgentProcess(MessageChannel):
    def __init__(self, launch, *, on_oversize: Callable[[OversizeLine], None], on_stderr: Callable[[str], None])
    async def start(self) -> None
    async def send(self, text: str) -> None            # 写一行到 stdin；进程已退出 → ChannelClosed
    async def receive(self) -> str | None           # 读一行；超长行跳过并回调 on_oversize（不静默丢）
    async def terminate(self, grace: float) -> int   # 对进程组 SIGTERM → grace → SIGKILL（§6.1）
    async def wait(self) -> int                      # 退出码
实现要点原因
create_subprocess_exec(..., limit=max_line_bytes, start_new_session=True, user=, group=)读缓冲上限必须显式设置，默认只有 64 KiB（§4.10）；独立进程组让 terminate 能连带杀掉 CLI 拉起的子进程；user= 实现 §8.3 的用户隔离（可配置，本机 macOS 测试时关闭）；启动后由父进程写 /proc/<pid>/oom_score_adj（不用 preexec_fn：它在多线程进程里不安全）
超长行用 readuntil 捕获 LimitOverrunError 后逐块跳过到下一个换行，保留前 512 B 交给 on_oversizeasyncio 在超限时会清空整个缓冲区，连带丢掉后面完整的行。自己跳过只丢这一行；用回调而不是在 receive 里返回标记，MessageChannel 的契约保持为「一行文本」
stderr 由独立任务持续读取不读的话 stderr 管道写满会阻塞 agent
 
class AcpClient:
    """ACP client 的类型化包装。不知道轮次与会话，只把 agent 的输出交给回调。"""
    def __init__(self, channel: MessageChannel, *, on_update, on_permission) -> None  # 请求超时由 RpcEndpoint 负责
    async def initialize(self, *, timeout: float) -> Negotiated          # 版本 + agent 能力 + agentInfo
    async def new_session(self, cwd, mcp_servers, *, timeout) -> str
    async def load_session(self, sid, cwd, mcp_servers, *, timeout) -> None
    async def resume_session(self, sid, cwd, mcp_servers, *, timeout) -> None
    def       prompt(self, sid, prompt: list[dict], *, trace: str | None) -> asyncio.Future[PromptOutcome]
    async def cancel(self, sid) -> None                                 # session/cancel 通知
    async def close_session(self, sid, *, timeout) -> None

prompt 返回一个 Future 而不是 await 到底：一轮可能持续很久，Turn 需要同时等待它、计时器与取消事件（7.5）。它没有超时参数 —— 一轮的时限由 Turn 的计时器负责，不由请求超时负责（§6.2）。其余方法都有超时，超时抛 AcpRequestTimeout，由上层按 §6.5 C4 重启 agent。

7.5 Turn

一轮的全部规则都在这个类里：状态机（§4.6）、两种计时（§6.2）、取消流程（§6.4）、v1 / v2 的结束判定（§5.4）。

class Turn:
    turn_id: str
    state: TurnState                     # RUNNING | AWAITING_PERMISSION | CANCELLING | ENDED
    outcome: Outcome | None
    progress: ProgressTracker
    # 三个计时器：截止（不可暂停）、静默（可暂停、可重置）、取消宽限

    def start(self) -> None                       # 发 prompt；启动截止与静默；放入 turn.state(running)
    def on_update(self, raw: dict) -> None          # 进展证据；v2 的 state_update 在此推进状态
    def on_permission_pending(self, n: int) -> None  # 挂起询问数变化：0 ↔ >0 切换等人状态、暂停/恢复静默
    def begin_cancel(self, cause: CancelCause) -> None   # §6.4 ①–④；幂等
    def _on_prompt_done(self, fut) -> None       # v1：prompt 的结果或错误 → _finish
    def _on_deadline(self) -> None                # → begin_cancel(DEADLINE)
    def _on_idle(self) -> None                    # → begin_cancel(IDLE)
    def _on_cancel_grace(self) -> None            # §6.4 ⑥：通知 HostSession 终止 agent
    def _finish(self, outcome: Outcome) -> None   # 唯一写入 ENDED 的地方（B1）：停全部计时器、放入 turn.state(ended)
设计点理由
_finish 是唯一写入 ENDED 的方法，进入时若已是 ENDED 则直接返回把 B1「结束只宣告一次」变成一处代码。取消与完成同时发生时，先到的那个生效，后到的是空操作
取消期间收到非 cancelled 的结束原因 → completed§6.4「以 agent 的实际结果为准」直接体现在 _on_prompt_done 里
计时器全部经 Clock 创建测试里用假时钟推进 30 分钟只需一行代码
v1 / v2 的差异只存在于 on_update 与 _on_prompt_done§5.4 的表就是这两个方法的全部分支

7.7 PermissionBroker

class AskState(StrEnum):
    HELD = "held"            # 上游不在，暂存（§7.2）
    ASKED = "asked"          # permission.ask 已放入 Outbox
    SETTLED = "settled"      # 已有结果（server 答复 / 过期 / 取消 / 窗口到期）

class PermissionBroker:
    async def handle(self, turn: Turn, raw: dict) -> dict   # 返回 ACP 的 RequestPermissionResponse
    def on_answer(self, ask_id: int, result: dict) -> None  # 上游响应；已 SETTLED 的忽略（§4.7）
    def settle_all(self, turn_id: str, how: Settlement) -> None   # 取消时：全部回 cancelled（ACP 义务）
    def on_upstream_change(self, connected: bool) -> None   # 连上：HELD → ASKED；断开：开始窗口计时
    asks: dict[int, Ask]                                 # ask_id = 上游 JSON-RPC id，跨连接不变
规则在代码里
每个询问一个 asyncio.Futurehandle 等这个 Future；答复、过期、取消、窗口到期都只是「谁先 set_result」
server 选的 optionId 必须在 agent 的选项里否则按拒绝处理（§4.7）
拒绝 → 选 agent 的 reject_once；没有则 cancelled_reject_result(options)
并发上限 8（§8.3）超出的询问不上报，直接返回拒绝结果
绝不自动批准（B3）代码中不存在生成 allow 结果的分支，只有「采用 server 的选择」一条路径能产生允许

7.8 Outbox

bridge 发往 server 的一切都经过它：分配序号、保留到被确认、断线时保存、重连时补发、溢出时淘汰、满时产生背压。

@dataclass
class Entry:
    seq: int; kind: Literal["control", "data"]; text: str      # 已序列化的完整 JSON-RPC 帧
    sent: bool = False

class Outbox:
    def put_notification(self, method: str, params: dict, *, kind) -> int   # 返回 seq
    def put_request(self, method: str, params: dict, *, request_id: int) -> int
    def ack(self, seq: int) -> None                                    # 释放 ≤ seq 的条目
    def rewind(self, last_seq: int) -> ResendPlan                         # attach：标记 > last_seq 为未发送，算出 gaps
    def bind(self, conn: UpstreamConnection | None) -> None              # 换连接 / 断开
    async def wait_writable(self) -> None                              # 背压：未满时立即返回
    async def pump(self) -> None                                       # 常驻发送任务
    bytes_held: int; full_since: float | None; gaps: list[tuple[int, int]]
设计点理由
放入时就序列化成文本补发时发送的是完全相同的字节；也便于按字节计算缓冲占用（§6.6）
put_* 是同步方法6.2 节：状态转换与放入消息在同一个同步段里完成，seq 顺序即转换顺序
淘汰只挑 kind="data"，从最老的开始§7.4 控制消息永不淘汰；被淘汰的区间记入 gaps
full_since 超过 30 s 由 HostSession 的计时器检测，以 1011 断开连接§6.6 兜底
补发的请求（询问）沿用原 id§7.3；id 由 PermissionBroker 分配，不由连接分配

09异常约定

BridgeError                          # 所有 bridge 自定义异常的基类
├── SessionNotOpen(cause)            # → -32010；cause: not_opened | recovering | draining | bridge_restarted
├── SessionAlreadyOpen               # → -32011
├── TurnBusy / TurnNotFound          # → -32012 / -32013

├── AgentRequestFailed(acp_error)    # → -32015；agent 回了 ACP 错误，data.acp 原样带上

规则内容
错误码的映射只在一处upstream/dispatch.py 捕获 BridgeError 并转成上游错误码；session/ 里不出现任何数字错误码
未预期的异常dispatch 回 -32603，记完整堆栈；不让它终止事件循环。若异常来自状态机内部（状态可能已不一致），当前一轮以 failed 结束并重启 agent
来自 agent 的坏数据永远是 ProtocolViolation：记录、计数、丢弃，不抛到状态机外（§8.3「把 agent 当作不可信的」）
