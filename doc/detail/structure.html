Detailed Design · Structure

目录与包结构设计

系统分成两个平面：配置平面（Java）拥有技能、MCP 注册表、K8s 模板与身份体系；运行时平面（Python）拥有 session、run、事件流与执行环境。智能体配置与版本留在 Python —— 它是装配说明，不是内容资产。Python 以 API 只读消费其余配置。

基线 atlas 7b1a991Python 5 包 + Java 配置服务纯搬迁优先从零历史处开刀

01两个平面

配置平面 · Java

技能 · MCP 注册表 · K8s 模板 · 用户 / 权限 / 审计 / 配额。内容资产的所有者 —— 有独立于任何 agent 的生命周期：创作、审核、发版、下架。

运行时平面 · Python

智能体配置与版本 · session · run · message · event · 审批 · 沙箱 · 压缩 · 记忆读写。既是内容资产的消费者（按版本号只读拉取），也是装配说明的所有者。

这条线为什么成立

核心论证是技能不该归 agent 应用管：技能是有独立生命周期的资产，消费者不止一个 —— native agent 用它，acp 的 Claude Code 直接挂载它的目录，人也会直接读它。让 agent 应用当 owner 是错位。

同理成立于 MCP 注册表（多个 agent 共享、运维在管）与 K8s 模板（改一个资源限额不该触发 Python 包的构建）。

为什么运行时那一半必须留在 Python

一次 run 里 Python 要写 message / run 状态与用量 / run_event / run_file / thread.summary / thread.title / approval。这些不是"配置的副产品"，它们是运行时自己的事实。而且 atlas 有一条明确的顺序保证 —— 终止事件先落库再发布，否则客户端收到 run.finished 后立刻查会读到 status=running。跨服务之后这是个分布式协调问题；留在一侧它只是两行代码的顺序。

沿用 atlas 已经对的部分

运行时平面内部，atlas 现有的三包分层不动：依赖单向、repositories/ 是唯一接触 DB 的地方、engine 能脱离数据库单测 —— 而且不靠自觉，靠 import-linter 契约。

02边界怎么划

四类配置对运行时的耦合度不一样，不能当成一个平面统一处理。前三类拆出去，第四类留下：

资产独立性Python 的角色耦合点
技能完全独立只读消费无 —— 只认 (slug, version) 与投送路径 /skills/<slug>/
K8s 模板完全独立只读消费无 —— 只认 template id
MCP 注册表基本独立只读 + 运行时连接凭据解析必须留在 Python
Agent 配置不拆所有者模型门禁 · 工具目录 · 审批目标 · 两条真实外键（见 §03）

MCP 的那个口子：凭据

atlas 现在的纪律是：配置里只存 ${ENV} 占位符，真值在发起连接的那个进程的环境变量里。拆分后保持这条 —— Java 存的永远是占位符，解析发生在 Python。

这让隔离反而更彻底

配置服务从来看不到真凭据。它被拖库也拖不到 MCP 的 token —— 那些只存在于运行时进程的环境变量里。原本是个"口子"，实际上是这套拆分白拿的一个好处。

# 配置服务返回的 MCP server 定义（Java → Python）
{
  "name": "calc",
  "url": "https://mcp.internal/calc",
  "transport": "streamable_http",
  "headers": { "Authorization": "Bearer ${CALC_TOKEN}" }   ← 占位符,不是真值
}

Python 侧 resolve_env_refs() 原样保留：环境变量不存在时明确报错，不能当空串 —— 否则会用空 token 去连，服务端返回 401，报错指向"认证失败"而不是"你没配这个环境变量"。

03Agent 配置为什么不拆

技能、MCP、模板是内容；agent spec 是装配说明 —— 它说的是"把哪个模型、哪些工具、哪些技能、什么限额装配成一个可执行的图"。装配说明属于装配者。

决定性的理由：两条真实外键

# server/src/atlas_server/db/models.py —— 现存的引用完整性

class Thread:
    agent_id: Mapped[UUID] = mapped_column(UUIDType, ForeignKey("agent.id"), ...)

class Run:
    agent_version_id: Mapped[UUID | None] = mapped_column(
        UUIDType, ForeignKey("agent_version.id"), ...)

把 agent / agent_version 搬到另一个服务，这两条外键只有两种下场：

  • 降级成软引用 —— 于是"删掉一个 agent 会不会让历史会话变成孤儿"从数据库保证的事，变成一条要靠代码自觉维护的约定。而 atlas 全部可复现性承诺（run.agent_version_id 能回答"当时用的哪份配置"）就建立在这条引用上。
  • 保留但跨库 —— 做不到。
技能为什么不受这个约束

因为技能引用不是外键，是 spec 里的 (slug, version) 值对 —— 本来就是软引用，而且它必须是软引用：spec 是版本快照，存 id 在执行时解引用的话，技能一改所有历史 run 的含义就跟着变（这一点在 native 详设 §04 论证过）。同一个设计判断，在 agent 上给出相反的结论。

连带的三个好处

不拆之后
不需要内部 APIspec-schema / spec/validate 全部取消。校验回到 atlas 现在的样子 —— 保存时 spec.validate()，实测门禁只有一份实现且从没离开过它产生的地方
调用方向单一只剩 Python → Java 的只读拉取。没有反向同步调用，也就没有循环依赖的可能
快照纪律不跨语言「spec 新字段必须有默认值」仍由 tests/guards/test_spec_snapshots.py 一处守着，写入方与读取方是同一个进程

Java 仍然拥有它该拥有的：授权

"谁能编辑哪个 agent"是 iam 的问题，不是存储的问题。BFF 形态下 Java 先做授权判定，再把请求转给 Python 的 /v1/agents：

浏览器 → Java console
           ├─ 授权判定（iam）· 审计留痕（audit）
           └─ 代理 → Python /v1/agents/*   ← 存储与校验在这里
网络层必须配合

Python 的 /v1/agents 不能从浏览器直接可达，否则 Java 那道授权门形同虚设。运行时服务只暴露给 Java 与内部网络；对外的入口只有一个。这条是部署约束，不是代码能保证的 —— 要写进 deploy/ 的网络策略里。

一处新增的跨平面调用：保存时解析技能版本

# services/agent.py —— 保存 agent 时把 skills 里的 version=None 钉死

async def _pin_skill_versions(self, spec: AgentSpecIn) -> AgentSpecIn:
    """version=None → 配置平面当前的版本号。

    ★ 顺带做存在性校验：引用了不存在或未发布的技能，**保存时就 400**。
      配置平面不可用时保存会失败 —— 这是可接受的：无法确认技能存在
      就写进快照，等于允许一份指向空气的配置进库。
    """
    if not spec.skills:
        return spec
    resolved = await self._configplane.skills.resolve(spec.skills)
    return spec.model_copy(update={"skills": resolved})

04不可变契约与缓存

对配置平面的硬约束

已发布的 agent_version / skill_version 行，内容永不原地修改。要改就发新版本。

这不是洁癖，是 atlas 全部可复现性承诺的地基：run.agent_version_id 必须能回答"当时用的哪份配置"。如果配置服务允许编辑已发布版本，所有历史 run 的含义会静默改变 —— 而 run 行还指着同一个 id，看起来一切正常。

它顺带把硬依赖变成软依赖

版本不可变 ⇒ Python 可以按 version id 永久缓存解析结果，无需失效策略。于是：

配置服务状态运行时表现
正常一切正常
不可用命中缓存的 agent / 技能照常跑；只有首次用到的新版本会失败，错误明确指向配置平面
返回了与缓存不同的同版本内容缓存优先 + 告警 —— 这说明对方破了不可变契约，应当被发现而不是被跟随
 
# server/src/atlas_server/configplane/cache.py

class VersionCache:
    """按 (资产类型, id, version) 缓存。

    ★ 永不失效 —— 依据是配置平面的不可变契约，不是猜测。
      这一点必须在代码里写明：将来有人想加 TTL 时，他要先推翻那条契约。

    ★ 内容指纹不一致时**用缓存并告警**，不静默跟随新内容：
      跟随 = 帮对方把「破了不可变契约」这件事藏起来。
    """

    async def get(self, kind: str, id_: str, version: int, fetch) -> Any:
        ...

磁盘落地：进程重启不该让全部会话重新拉配置。缓存写到本地 var/cache/configplane/，内容寻址（key 含 digest），可以随时删。

05顶层：仓库与包

两个仓库，两种语言，没有共享数据库 atlas/ 运行时平面 · Python ├── contracts/ src/atlas_contracts/ 新增 零重依赖的执行侧契约 ├── engine/ src/atlas_engine/ 收窄 native 执行引擎（LangGraph） ├── acp/ src/atlas_acp/ 下一期 Server 侧 ACP 客户端 ├── bridge/ src/atlas_bridge/ 下一期 Pod 内守护进程 ├── server/ src/atlas_server/ 保留 编排 · 运行时持久化 · API ├── web/ 对话工作台（见 §10） ├── deploy/ 新增 └── tests/ 分组 atlas-config/ 配置平面 · Java 新仓库 ├── skill/ · mcp/ · k8stemplate/ 三个内容资产域 ├── iam/ · audit/ · quota/ 身份 · 审计 · 配额 └── console/ 管理控制台 + 智能体编辑器（代理到 Python）
配额是唯一的反向数据流，但它不该是同步调用

Java 的 quota/ 需要 run 的 token 用量。不要为此加一个 Java → Python 的查询接口 —— 那会把刚刚拿到的单向调用图破掉。用量是运营数据不是配置数据：run 收尾时投递一条用量事件（消息队列），或 Java 定时批量拉取归档。两种都不进 run 的关键路径，也不产生同步依赖。

06contracts 与跨语言契约

修正：contracts 仍然只是 Python 包

讨论时我提过"contracts 可能要双语实现"。想清楚之后不需要 —— 因为 Java 把 spec 当不透明 blob 处理，它不需要理解 LimitSpec 的任何字段。跨语言的契约是两份 OpenAPI 文档，不是一个共享的类型包。这个结论更好：少一个需要双边同步的东西。

atlas_contracts：执行侧的共享契约

纳入判据不变：native 与 acp 两条执行路径都要用，且前端也认。

contracts/ ├── pyproject.toml 依赖只有 pydantic └── src/atlas_contracts/ ├── events.py TraceEvent · EventType · TERMINAL_EVENTS · to_sse() ├── errors.py error_kind 取值集合 · retryable 语义 ├── capabilities.py Capabilities · capabilities_for() └── limits.py LimitSpec

消费方是 engine / acp / bridge / server。bridge 跑在 Pod 里和 CLI 打包在一起 —— 它不能为了一个 TraceEvent 类拖进 langgraph + langchain + langsmith。这是 contracts 独立的部署约束理由，不是整洁诉求。

跨平面契约：一份 OpenAPI

智能体配置不拆之后，跨语言的契约只剩一份、一个方向：

文档谁定义谁消费内容
config-plane.yamlJavaPython按版本读取技能内容 / MCP 定义 / K8s 模板；解析技能当前版本号
 
# atlas/contracts/openapi/config-plane.yaml
#   由 Java 侧生成后**复制**进运行时仓库。
#
# ★ 复制而不是运行时拉取：生成客户端代码需要它在构建期就存在，
#   且要能对 diff 做 review —— 配置平面改了返回结构，
#   应当在这个仓库的 PR 里被看见，而不是某天 run 起来才发现。
快照纪律仍然是单语言的

「spec 新字段必须有默认值，否则历史快照反序列化全部失败」—— 这条由 tests/guards/test_spec_snapshots.py 一处守着就够了，因为 spec 的写入方与读取方是同一个进程。这是智能体配置不拆换来的最实在的一条好处：最容易被破坏、后果最隐蔽的那条纪律，没有跨语言。

07kernel：自有代码，可裁剪

定性变了

kernel 按需裁剪与扩展、不会被整体替换 —— 那它就是自有代码。这个定性决定了怎么对待它：不需要任何"版本对账"机制，需要的是正常的代码质量要求与一条安全的裁剪路径。

因此撤销：VENDOR.md 与 drift 测试

我在上一版里设计过 kernel/VENDOR.md + test_vendor_drift.py，守的是"同步外部改动时把本地修改弄丢了"。kernel 是自有代码，这个失败模式不存在 —— 保留它只会变成一个为了显得严谨而存在的测试，以及一份没人会读的清单。撤掉。

值得保留的只有一份来源说明，几行就够：代码出自哪个项目、哪个版本、为什么 fork。它是给两年后的人看的，不是给 CI 看的。

裁剪的真实收益不是行数

26411 行、53 个模块。裁掉几千行本身不值钱，值钱的是这两样：

  • 缩小升级验证面。engine/pyproject.toml 把 langchain==1.3.* / langgraph==1.2.* 钉死了，理由写得很清楚 —— kernel 与这两个包深度同构。将来必须升的时候，kernel 里每一个贴着它们结构写的模块都是一个验证点。用不到的模块不该参与这场验证。
  • 减少读代码时的干扰。找一个中间件时，不该在四个永远不会被装配的 profile 之间翻。

别用 import 图判定死代码

__init__.py 的 barrel 导出会让一切都"可达" —— 直接跑一遍可达性分析，53 个模块里 50 个是"活的"，结论毫无用处。

判据必须是功能可达：从 create_deep_agent() 出发，沿着真正参与装配的 import 走。上表就是这么核的 —— "仅经 barrel 可达"正是死代码的特征。

安全的裁剪路径：两步走

  1. 先从 barrel 摘掉，不删文件。把模块从 middleware/__init__.py / backends/__init__.py 的导出里去掉，跑全量测试。这一步可逆，且能立刻暴露"其实有人在用"。
  2. 观察一个迭代后再删文件。没有任何东西回来找它，再物理删除并同步 profile 的 register() 调用。

profiles 的裁剪要动 profiles/_builtin_profiles.py 里的注册调用，删文件不改注册会直接 ImportError —— 这一处不能只做第一步。

质量要求逐步收紧

atlas 现在的 ruff 配置已经为此留了口子，而且注释里写明了打算：

# kernel/ 纳入检查以捕获真问题（F/B/SIM 等），
# 但不为继承来的风格大改。裁剪推进时可逐步收紧这里。
[tool.ruff.lint.per-file-ignores]
"engine/src/atlas_engine/kernel/**" = ["E501", "RUF100", "UP", "B", "SIM", "RUF012"]

# ★ formatter 没有 per-file-ignores，是全有或全无。
#   裁剪到某个模块时，可把该模块从这里移出并单独格式化。
[tool.ruff.format]

随裁剪推进，把已经改造过的子目录从这两处移出。顺序是先裁后收紧 —— 反过来做的话，格式化会先把要删的几千行重排一遍，淹没真正的改动。

configplane 与 providers 为什么不合并

两者都是"对外部说话"，看着该合并。但失败语义不同：configplane 有不可变契约撑起的缓存，所以它的不可用是可降级的；providers 大多不可缓存（沙箱要真起容器、搜索要真发请求），不可用就是硬失败。把可降级的和不可降级的混在一起，降级策略就没有统一的落点。

09配置平面（Java）

不假装了解你们的 Java 工程约定，这里只给域划分与两条必须遵守的契约，包名与框架按你们现有规范落。

atlas-config/ ├── skill/ Skill · SkillVersion · 正文 + 附件 · 审核流 │ └── ★ 已发布版本内容不可变 ├── mcp/ McpServer 注册表 · 工具目录探测与缓存 │ └── ★ headers 只存 ${ENV} 占位符,永不存真值 ├── k8stemplate/ Pod 模板 · 资源档位 · 镜像版本 ├── iam/ 用户 · 组织 · 角色 · 授权矩阵 ├── audit/ 谁在什么时候改了哪份配置 ├── quota/ 配额与计费口径 └── console/ 管理控制台前端

对配置平面的两条硬契约

  1. 已发布版本不可变。要改就发新版本。这撑起运行时的永久缓存，也撑起 run 的可复现性。
  2. 不越界管智能体配置。console/ 里的智能体编辑器是代理：授权判定与审计留痕在 Java，读写落到 Python 的 /v1/agents。不要在 Java 侧缓存或复刻 spec 的结构 —— 那会让工具列表、模型门禁出现第二份事实源。

技能审核这件事归这里

概要设计里说过：技能是可执行的内容而非配置 —— 含给模型的指令，也含真正会跑的脚本，所以审查按代码审查来做。这套审核流（提交、评审、发布、下架）天然属于资产的 owner，也就是配置平面。运行时只消费已发布的版本。

结构性的好处：运行时拿不到草稿态技能，误用不可能发生 —— 不是靠字段判断，是靠 API 根本不返回。

10web：三个方案

浏览器现在面对两个后端。这是个真实的分叉，三种解法：

方案形态代价
A · 两个前端对话工作台（Python）+ 管理控制台（Java），各自独立两套登录态、两套设计系统，用户要在两个地址间跳
B · Java 做 BFF
（推荐）		浏览器只连 Java；配置类请求本地处理，对话与 SSE 透传到 PythonSSE 透传有坑（见下）；Java 多一层路由
C · 单前端连双后端一个 SPA，按路径分别请求两个域名两套 CORS、两套鉴权头，登录态同步是自己发明的

推荐 B。它给出单一鉴权面与单一审计点 —— 而这正是把 iam / audit 放进配置平面的初衷。C 的问题在于"登录态同步"会变成一段自研逻辑，而那是最不该自研的东西。

B 方案的 SSE 透传必须做对三件事
  • 不缓冲。任何响应缓冲都会让流式输出变成"等半天一次性出现"。Spring 侧要用响应式栈或显式关闭缓冲，Nginx 那层也要 proxy_buffering off。
  • Last-Event-ID 原样转发。atlas 的断线重连靠它做游标补发。透传时丢了这个头，重连会从头开始或直接断在中间。
  • 超时要长于最长 run。审批等待可达 600s、编码委派 1800s —— 网关默认的 60s 读超时会在半途切断连接。

运行时仓库的 web/ 在 B 方案下收窄为对话工作台，管理模块迁到 Java 的 console：

web/src/ 对话工作台 ├── app/chat/[[...threadId]]/ ├── features/chat/ ChatWorkbench · MessageStream · TraceInspector … ├── api/ · components/ └── lib/ events · sse · run-reducer · http · format
lib/events.ts 的特殊地位不变

它是 TraceEvent 契约在前端的实现，native 与 acp 共用。acp 接进来后一行都不该改 —— 如果发现要为 acp 加分支，说明 acp/translate.py 没把事件翻译干净，该改的是后端。这条值得写进文件头注释。

12落地顺序

原则：从没有历史包袱的地方验证边界

技能、MCP、K8s 模板在 atlas 里根本还不存在（都是详设里的新增）。直接建在配置平面，迁移成本为零，而且它们恰好是边界最清晰的三个。智能体配置不拆之后，这套拆分不涉及任何存量数据迁移 —— 风险大幅下降。

步骤 1 · 运行时侧的纯搬迁（不涉及 Java）

建 contracts/ 包；services/ 分出 providers/；assembly.py 拆子包；tests/ 分组 + guards。四步全是移动文件 + 改 import。

验证：每一步之后 make check 绿；make test-engine 在没起 Postgres 的机器上跑通。

步骤 2 · kernel 裁剪第一轮

按 §07 的两步法：先从 barrel 摘掉 rubric / context_hub / local_shell，跑全量测试；profiles 的裁剪连同 _builtin_profiles.py 的注册一起改。写 ORIGIN.md。

验证：make test 绿；make serve 起得来且能跑通一次真实对话（profile 注册出问题只会在运行时暴露）。

可以与步骤 1 并行 —— 两者不碰同一批文件。

步骤 3 · 配置平面立项：技能优先

Java 侧实现 skill/ 域（版本不可变 + 审核流）与 config-plane.yaml。Python 侧建 configplane/（client + cache + skills + fake），AgentSpecIn.skills 与 _pin_skill_versions 接上。

验证：native agent 能用上配置平面发布的技能，双路投送（沙箱 / StateBackend）都通；停掉 Java 服务后，已跑过的会话仍能继续（永久缓存生效）。

步骤 4 · MCP 与 K8s 模板

同样直接建在配置平面。MCP 注意占位符纪律：Java 永不接触真凭据。

步骤 5 · Java console 接管入口

iam / audit 落地；智能体编辑器以代理形态接上 Python 的 /v1/agents；SSE 透传按 §10 的三条做对。网络策略收紧：运行时服务不再对浏览器直接可达。

验证：绕过 Java 直接请求 Python 的 /v1/agents 应当被网络层拒绝 —— 这是授权门是否真实存在的唯一检验。

13什么时候不该拆

想过但不做理由重新考虑的信号
把 session / run 也划进配置平面一次 run 要写 7 类数据，且有"终止事件先落库再发布"的顺序保证。跨服务之后它变成分布式协调问题永不
把 agent / agent_version 迁到配置平面thread.agent_id 与 run.agent_version_id 是真实外键。迁走只能降级成软引用，而 run 的可复现性正建立在这条引用上。且 agent spec 是装配说明不是内容资产永不
Java 重新实现模型能力门禁那是对网关的实测结论。两份实现必然漂移，表现是"编辑器让我存了，跑起来 400"永不 —— agent 不拆之后这个问题根本不出现
两个平面共享数据库迁移失去单一 owner，事务跨不过去，而且等于把接口耦合换成了 schema 耦合（更紧）永不
contracts 做成双语包Java 根本不碰 spec。跨语言契约只有一份 OpenAPI、一个方向永不
给 kernel 做版本对账机制
（VENDOR.md + drift 测试）		kernel 是自有代码，"同步时丢改动"这个失败模式不存在。保留只会变成为了显得严谨而存在的测试某天 kernel 改为跟随某个外部基线时
靠 import 图判定 kernel 死代码barrel __init__.py 让一切"可达" —— 53 个模块里 50 个是"活的"，结论没用。判据必须是从 create_deep_agent() 出发的功能可达永不
configplane 与 providers 合并失败语义不同：前者有不可变契约撑起的缓存可降级，后者不可用就是硬失败缓存策略被推翻时
server 改成域内聚拆掉技能与 MCP 之后 server 只剩 6 个域，分层样板的重复成本更划不来域数超过 10 个
repositories/ 按域分子包平铺本身是纪律的体现：想加 DB 访问只有这一个目录可去单个 repository 超 400 行
给 memory 造表以对齐其他域数据在 Mem0 里。为目录对称造数据结构是把形式放在事实之上需要本地索引"哪条记忆来自哪个 thread"时
acp 与 bridge 合成一个包两个进程、两处部署、两种镜像体积约束永不
判据

拆分要能回答两个问题才做：拆完之后哪条依赖边变短了？哪条纪律有了新的执行点？两个都答不上来的拆分，只是把同样多的代码摊进更多目录。

这套平面拆分两个都答得上：依赖边 —— 技能资产不再被 agent 应用挟持，它的消费者可以是任何人；纪律执行点 —— 「已发布版本不可变」有了明确的 owner，而它恰好是 run 可复现性的地基。

反过来，智能体配置不拆也是同一个判据的结论：拆了没有哪条依赖边变短（thread/run 仍要指着它），却会让一条 DB 保证的引用完整性降级成代码自觉。同一把尺子，两个方向的答案。
