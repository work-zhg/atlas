kernel 包分析

53 个模块、26411 行。这份分析把它拆成五层逐一说明功能与类设计，标出 Atlas 已改动的四处、实际用到的部分、休眠但有价值的能力，以及确定的死代码 —— 最后给一张可以逐行打钩的评估清单。

53 模块 / 26411 行Atlas 直接 import 4 个符号已改动 4 处建议裁剪 ~4600 行

01全景

kernel 是一个 LangChain/LangGraph 之上的 agent 组装框架。它不发明执行循环 —— 循环来自 langchain.agents；它提供的是一套可插拔的能力层，用中间件的形式叠加到那个循环上。

一句话概括各层

backends 回答"文件存在哪、命令在哪执行"；middleware 回答"模型能看到什么工具、上下文怎么管"；profiles 回答"换个模型要不要改行为"；graph.py 把三者按固定顺序装配成一张图。

02装配中心：create_deep_agent

理解 kernel 的钥匙是这个函数的中间件叠加顺序。列表顺序即包裹顺序，从外到内：

# graph.py 主 agent 栈（约 835–900 行）

deepagent_middleware = []

1  if skills:      SkillsMiddleware(backend, sources=skills)
2                  FilesystemMiddleware(backend, tools=filesystem_tools,
                                       _permissions=permissions)      ← 必备脚手架
3  if subagents:   SubAgentMiddleware(backend, subagents, state_schema)  ← 必备脚手架
4                  create_summarization_middleware(model, backend)
5                  PatchToolCallsMiddleware()
6  if async_sub:   AsyncSubAgentMiddleware(async_subagents)
   ──────────────────────────────── 以上是「核心栈」
7                  profile.materialize_extra_middleware()      ← 按模型注入
8                  append_prompt_caching_middleware(...)
9  if memory:      MemoryMiddleware(backend, sources=memory, add_cache_control=True)
10 if interrupt:   HumanInTheLoopMiddleware(interrupt_on=...)
   ──────────────────────────────── 最后按 profile 剔除被排除项
                    _apply_excluded_middleware(...)

三个顺序是有语义的，不能随手调

  • profile 中间件在 8/9 之前 —— 注释写明理由：memory 会改系统提示词，放在 prompt caching 之后才不会让 Anthropic 的缓存前缀每轮失效。
  • memory 在 prompt caching 之后 —— 同上，它是"每轮都可能变"的部分。native 详设里我把 Mem0 记忆拼在 system_prompt 末尾，理由完全一致。
  • _ToolExclusionMiddleware 最后跑 —— 所有注入工具的中间件跑完之后再剔除，否则剔不干净。

两个不可剔除的脚手架

_REQUIRED_MIDDLEWARE = (
    (FilesystemMiddleware, ()),   # 背后是全部文件工具 + permissions 安全保证
    (SubAgentMiddleware,  ()),    # 背后是 task 工具的 handler
)

HarnessProfile.excluded_middleware 试图排除它们时直接 ValueError，而不是继续跑一个悄悄退化的 agent。这条设计和 Atlas 自己的 §13.2「不静默降级」是同一条纪律。

这解释了 Atlas 的一处写法

filesystem_allowlist() 返回空表时，FilesystemMiddleware 仍然装上，只是不给模型任何文件工具。不是可以省略却没省 —— 是结构上不允许省略。

子智能体有自己的一套栈

# 每个 SubAgent 的默认栈（graph.py 约 672–690 行）
FilesystemMiddleware(backend, tools=filesystem_tools, _permissions=继承或自有)
create_summarization_middleware(subagent_model, backend)
PatchToolCallsMiddleware()
if spec["skills"]: SkillsMiddleware(backend, sources=...)
+ 子智能体自己模型的 profile 中间件
+ prompt caching

关键点：子智能体共享同一个 backend，但可以有自己的 permissions、skills、model、middleware。调用方在 spec["middleware"] 里给了自己的 FilesystemMiddleware 时会替换默认那个 —— Atlas 正是靠这个语义给子智能体单独的文件工具白名单。

SubAgent 的配置面

class SubAgent(TypedDict):
    name, description, system_prompt          # 必填
    tools, model, middleware                  # Atlas 用到
    skills: list[str]                       ← 休眠：子智能体可有独立技能集
    permissions: list[FilesystemPermission] ← 休眠：按路径的细粒度权限
    interrupt_on: dict[str, ...]            ← 休眠：子图内的 HITL
    response_format                           ← 休眠：结构化返回

class CompiledSubAgent(TypedDict):
    name, description, runnable               ← 休眠：直接塞一个编译好的图

CompiledSubAgent 值得记一笔：它接受任意 Runnable。acp 子智能体如果要做，这是接入点 —— 把 ACP 会话包成一个 Runnable 即可，不必改 kernel。

03Backend 层

一套协议，七个实现。这是 kernel 设计最干净的一层。

class BackendProtocol(abc.ABC):
    ls · read · grep · glob · write · edit · delete
    upload_files · download_files
    # 每个都有 a 前缀的异步版本，共 18 个方法

class SandboxBackendProtocol(BackendProtocol):
    id · execute · aexecute        # 多出「能跑命令」这件事
七个实现
StateBackend365 行Atlas 在用（默认）

文件存在 graph state 的 files 字典里，随 run 结束消失。没配 backend 时的默认值。

与技能投送相关：native 详设里"无沙箱时把技能塞进 invoke(files=...)"这条路，吃的就是它。

BaseSandbox1824 行Atlas 继承 · 建议改造

抽象方法只有四个：execute / id / upload_files / download_files。其余 13 个文件操作全部由它用 execute() 实现 —— read 是往沙箱里塞一段 Python 脚本跑，grep 是 grep -F，ls 是 os.scandir 脚本。

还提供 execute_with_offload()：大输出直接在沙箱内落盘，只把路径回给模型。

CompositeBackend956 行建议启用

按路径前缀把操作路由到不同 backend：

CompositeBackend(
    default=sandbox,
    routes={"/skills/": readonly_skills_backend},
)

详见 §08 —— 这正好解技能投送的一个痛点。

FilesystemBackend1542 行未用

直接读写宿主机真实盘。Atlas 走容器隔离，不用它。但别删 —— CompositeBackend 的只读路由若要挂本地目录会用到。

StoreBackend710 行未用

适配 LangGraph 的 BaseStore，跨 thread 持久。Atlas 的跨会话持久是 OSS/卷 + Mem0，两条路不冲突但也不互补。暂时留着，成本低。

ContextHubBackend706 行建议裁剪

把文件存进 LangSmith Hub 的 agent 仓库。内部实现了一套 _MutationQueue 做写入合并与持久性等待 —— 相当重的东西，绑死 LangSmith。

LangSmithSandbox353 行连带裁剪

LangSmith 托管沙箱。Atlas 用 Docker/K8s 自建。

LocalShellBackend364 行建议裁剪

FilesystemBackend + 无限制本机 shell。在一个讲究隔离的平台里，这是个反向能力 —— 留着只会成为某天有人图省事绕过沙箱的入口。

改造点：热路径全走 docker exec

Atlas 的 DockerSandbox 只覆盖了 execute / write / upload_files / download_files / id。于是 ls · read · edit · delete · grep · glob 每次调用都是一次 docker exec（代码注释自己估的是 ~50–150ms）。

单看不算贵。但两件事会放大它：① 模型读文件是高频动作，一轮里十几次很常见；② 换 K8s 之后，每次 exec 是一个带协议升级的 API 调用，代价比本机 docker exec 高一个量级。

改造方向：在 K8sSandbox 上覆盖 read / ls / grep，走一条常驻通道（agent sidecar 或长连接 exec），而不是每次新建。这不是 kernel 的问题，是实现子类的优化空间 —— 协议本身允许覆盖，正是为此留的。

04Middleware 层

FilesystemMiddleware3527 行 · 最大核心，必备脚手架

它大是因为塞了五件事：

  • 8 个文件工具：ls / read_file / write_file / edit_file / delete / glob / grep / execute，各自带 pydantic 入参 schema
  • 权限执行：FilesystemPermission 按 glob 匹配路径，过滤 ls/glob/grep 的结果，拦截 write/edit/delete
  • 大结果外置：工具结果超 20000 token、HumanMessage 超 50000 token 时写到 backend 文件，消息里只留路径
  • 多模态清洗：模型不支持的 content block 换成占位符，避免网关 400
  • 视频抽帧：read_file 对视频文件抽帧（依赖未装时该分支恒不成立）

构造参数里有几个 Atlas 没调过但值得知道的：tool_token_limit_before_evict=20000、grep_max_count=1000、max_execute_timeout=3600。

FilesystemPermission在 filesystem.py 内建议启用

声明式的路径级权限规则。配套的 _fs_interrupt.py 能把权限规则自动翻译成 HITL 配置（_build_interrupt_on_from_permissions），接到 HumanInTheLoopMiddleware。

Atlas 现在的审批是按工具名粗粒度（require_approval_for = ["execute", "coding_task"]）。kernel 这套是按路径 glob：可以做到"写 /workspace/** 免批，写 /skills/** 一律拒绝"。详见 §08。

summarization2169 行Atlas 在用（自动那半）

两个中间件：

  • _DeepAgentsSummarizationMiddleware —— 自动压缩。相比 LangChain 原版多三件事：被逐出的消息先追加到 backend 的 /conversation_history/{session}.md（原版直接丢弃，无恢复路径）；压缩前先截断老消息里的大 write_file 参数，常常就够用不必真压；provider 超预算报错时兜底压缩再重试。
  • SummarizationToolMiddleware —— 提供 compact_conversation 工具，让模型自己决定何时压缩。Atlas 未启用。
SkillsMiddleware1053 行Atlas 待接入

Agent Skills 规范的实现：从 backend 的若干 sources 路径扫 SKILL.md，解析 YAML frontmatter，把 name + description 列表注入系统提示词，正文由模型按需 read_file —— 这就是"渐进披露"。

硬上限：技能文件 10MB、名称 64 字符、描述 1024 字符、加载警告最多 20 条。后两个正是 native 详设里 Skill.description 设成 String(1024) 的来源。

多个 source 按顺序加载，同名后者覆盖前者 —— 可以做 base → user → project 的分层。

SubAgentMiddleware742 行核心，必备脚手架

提供 task 工具。每个子智能体在独立上下文里跑，只把最终结论回给主 agent。

工具描述里有 {available_agents} 占位符 —— 被替换成子智能体名称与描述列表。这是模型判断"何时委派给谁"的唯一依据，也是 Atlas 的 SubAgentSpec.description 会影响行为的原因。

AsyncSubAgentMiddleware935 行易被误认

提供 5 个工具（start / check / update / cancel / list async task）做非阻塞委派，主 agent 发起后继续干别的，稍后回来取结果。

别把它当成 ACP 的现成方案

它 from langgraph_sdk import get_client，连的是 LangGraph Platform 部署的图（认 graph_id）。文档里的 "Agent Protocol" 指的是 LangGraph 的那个，不是 ACP（Agent Client Protocol）。两者同名不同物。

acp 子智能体真要做，接入点是 CompiledSubAgent（塞一个 Runnable），不是这里。

MemoryMiddleware412 行同名陷阱

加载 AGENTS.md 规范的静态上下文文件，每轮全量进提示词，并在 Anthropic 模型上打 cache_control 断点。

与 Mem0 长期记忆不是一回事 —— 这条已经写进 native 详设 §05。两者可共存，但别复用 create_deep_agent(memory=) 这个参数。

PatchToolCallsMiddleware46 行小而关键

修补消息历史里的悬空工具调用——有 tool_call 却没有对应 ToolMessage。这种情况在取消、超时、压缩截断之后很容易出现，不补的话下一轮请求会被网关拒。

RubricMiddleware1024 行建议裁剪

自评迭代：跑一个 grader 子智能体，按结构化 rubric 打分，不达标就打回重做。

能力本身有意思，但它与 Atlas 的成本模型冲突：每次迭代多一次完整的 grader 调用，而 Atlas 的 max_total_tokens 是明确的刹车。要做质量门禁，用 Atlas 已有的审批或外部评测更可控。且它仅经 barrel __init__.py 可达，graph.py 根本不 import。

辅助模块共约 750 行保留
  • _message_eviction / _overflow_clip —— 大内容的 head+tail 预览与读侧裁剪，被 filesystem 与 summarization 共用
  • _prompt_caching —— 按 provider 追加缓存中间件
  • _tool_exclusion —— 最后一道工具过滤
  • _fs_interrupt —— 权限规则 → HITL 配置的翻译器
  • permissions.py —— 7 行，只是向后兼容的 re-export

05Profiles：两套档案

这是 kernel 里 Atlas 完全没用的一层，但它恰好是"按模型定制行为"的官方扩展点。

HarnessProfile —— 改 agent 行为

@dataclass
class HarnessProfile:
    base_system_prompt: str | None              # 替换基础提示词
    system_prompt_suffix: str | None            # 追加后缀
    tool_description_overrides: Mapping[str, str]  # 改工具描述
    excluded_tools: frozenset[str]                # 对该模型隐藏某些工具
    excluded_middleware: frozenset[...]             # 剔除中间件（脚手架除外）
    extra_middleware: Sequence | Callable            # 追加修补中间件
    general_purpose_subagent: ... | None            # 调整默认子智能体

按模型 key 注册，create_deep_agent 里用 _harness_profile_for_model(model, spec) 解析。内置档案：

档案行数内容
anthropic haiku-4-5 / sonnet-4-6 / opus-4-752–56提示词微调，各 50 来行
_nvidia_nemotron_3_ultra182611 个修补中间件：修文本形态的工具调用、清理 <think> 块、429 重试、追问纪律、实体解析守卫、最终答案守卫……
_openai_codex88Codex 适配
Nemotron 那 1826 行是这层存在的理由

它在说一件事：弱一点的模型需要大量外挂修补才能跑 agent 循环 —— 工具调用发成纯文本要解析回来、思考标签要清理、会重复追问要打回。这是很有价值的工程情报。

但对 Atlas 没用：它只面向 claude-opus-5 / sonnet-5 / fable-5 / haiku-4-5 四个模型，全部经 Anthropic 协议网关。这 1826 行是单笔最大的裁剪项。

ProviderProfile —— 改模型构造

457 行，管的是"按 provider 决定怎么构造 chat model"（额外 header、参数改名等）。Atlas 有自己的 model_factory.py + compat.py 做同一件事，且已经承载了实测门禁。两套并存但互不感知 —— 见 §08 的评估。

06Atlas 已改动的四处

全仓只有四处带 ★ Atlas 改动 标记，都集中在一个主题上：把工具门禁做实。

位置改了什么为什么
graph.py · 签名加 filesystem_tools 白名单参数，贯通主 agent / 子智能体默认栈 / general-purpose 三处原本三处都默认注册全部文件工具（含 execute），造成两个门禁缺口
graph.py · 子智能体栈默认栈的 FilesystemMiddleware 也吃白名单否则未勾 filesystem 的子智能体照样能 write_file
graph.py · general-purpose不再无条件注入 general-purpose 子智能体会让主 agent 能委派一个平台从没配置过的子智能体
middleware/filesystem.py空白名单 = 完全关闭文件工具，并连带关掉大结果外置原校验要求 read_file 恒在；零工具时外置出去的内容模型读不回来，留着是个只写不读的黑洞
这四处改动的共同点

原本的默认是「注册后运行时报错」，Atlas 改成「对模型结构性不存在」。差别在于：前者模型看得见、调用后才失败，每次尝试烧一轮 token；后者模型根本不知道有这个工具。

这个思路值得作为后续改造 kernel 的统一口径。

08评估清单

按建议动作分四组。裁剪与保留基本没有争议；启用与改造是需要你判断的部分，每条都写了收益与代价。

建议启用 · 需要判断
① CompositeBackend 做 /skills 与 /workspace 分离启用

解什么问题：native 详设里技能物化到容器 /skills/，需要 SkillMaterializer 做写入、幂等判断、以及 agent 改版后清理残留旧技能 —— 那段清理逻辑是自己写的兜底。

换成路由之后：

backend = CompositeBackend(
    default=docker_sandbox,                      # /workspace 等
    routes={"/skills/": StateBackend()},          # 技能走 state，run 级天然隔离
)

技能内容随 run 注入 state，run 结束自动消失 —— 不需要物化、不需要幂等判断、不需要清理残留。而 execute（bash）仍然作用于真实容器。

代价：技能文件对 execute 里跑的脚本不可见（它们在 state 里不在容器盘上）。而 技能管理设计明确说过技能可能含"真正会跑的脚本"（python scripts/search.py 那类）。

所以结论是二选一，取决于技能形态：纯提示词类技能 → 路由方案更干净；含可执行脚本的技能 → 仍需物化进容器。建议两条都留：按技能的 resources 是否为空自动选路。这个判断可以做在 SkillService 里，不必改 kernel。

② FilesystemPermission：路径级权限 + 自动 HITL启用

现状：Atlas 的审批粒度是工具名 —— require_approval_for = ["execute", "coding_task"]。一旦勾了 bash，每条命令都要人点头。

kernel 提供的：按路径 glob 的规则，且 _build_interrupt_on_from_permissions() 能把规则自动翻译成 HITL 配置。可以表达"写 /workspace/** 直接放行，写 /skills/** 一律拒绝，删任何东西都要批"。

收益：审批疲劳会真实降低 —— 现在的粗粒度会让用户对每条命令都点"允许"，点到最后就不看了，审批的意义也就没了。

代价：这是一个新的配置维度，要进 AgentSpec、进编辑器 UI、进 spec 快照纪律。而且 _permissions 参数本身标了私有（注释说"可能将来移到 backend 层"），接口有变动风险。

建议：值得做，但不要急 —— 先把技能与记忆落地。真要做时，把它包在 Atlas 自己的 spec 字段后面，不要让编辑器直接暴露 kernel 的 FilesystemPermission 结构。

③ execute_with_offload：大输出不进上下文启用 · 成本最低

沙箱内直接把大输出落盘，只回路径。Atlas 现在的兜底是 OUTPUT_LIMIT_BYTES = 100_000 硬截断 —— 截断是丢信息，外置是不丢。

一条 pytest 的完整输出、一次大构建的日志，截断之后模型看到的是半截，而报错往往在末尾。

代价极低：BaseSandbox 已经实现好了，Atlas 只需在 DockerSandbox 上确认 offload 路径可写。这条我建议直接做。

④ SummarizationToolMiddleware：模型主动压缩可选

给模型一个 compact_conversation 工具，让它在自己觉得该收敛时压缩。

收益有限：Atlas 的自动压缩（trigger_ratio=0.75）已经覆盖了主要场景，而模型主动压缩的时机判断未必比阈值更好。倾向不做，除非观察到"自动压缩总是太晚"的实际案例。

建议改造 · 需要判断
⑤ K8sSandbox 覆盖文件操作热路径改造

见 §03 的论证：ls/read/grep/glob 每次一个 exec，换 K8s 后代价升一个量级。

但先量一量再改 —— 一轮对话里文件操作的真实次数是多少？如果个位数，这个优化不值得先做。可观测性落地后能直接回答这个问题。建议：先埋点，后优化。

⑥ HarnessProfile vs Atlas 自有的模型适配值得收敛

现在有两套做同一件事的机制：kernel 的 HarnessProfile / ProviderProfile，与 Atlas 的 spec.py 门禁 + model_factory.py + compat.py。两者互不感知。

具体的重叠：Atlas 的 _SANDBOX_HINT（有 backend 时往 system_prompt 拼一段路径引导）其实正是 HarnessProfile.system_prompt_suffix 的用途。

两个方向，我倾向后者：

  • 用 kernel 的 —— 把 Atlas 的适配搬进 profile。顺了 kernel 的设计，但把实测门禁（Atlas 最有价值的资产之一）埋进一个继承来的框架里。
  • 裁掉 kernel 的 —— profiles 层只留 HarnessProfile 骨架（graph.py 依赖它），删掉全部内置档案注册。Atlas 的适配留在自己手里，门禁仍在 spec.py 这个显眼的地方。

理由：那些 frozenset 是对网关的实测结论，会随模型更新而变，放在一眼能找到的地方比放在框架扩展点里重要。
