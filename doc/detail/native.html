native Agent 详细设计

在 atlas 上落地。结论先说：atlas 的 native 执行内核已经对了 —— Message 为事实源、不存 checkpoint、版本快照、会话级沙箱、Run 内审批，全部与概要设计一致。缺的是它周围的四个平台域：技能、记忆、MCP 管理、身份。

01现状盘点

逐条对照概要设计。一致 表示不动，对齐 表示语义相同但要调整，新建 表示完全没有。

执行内核 —— 全部一致

概要设计atlas 现状
Message 为事实源，不存 checkpointdb/models.py 开篇即写明；InProcessExecutor._prepare 每轮从 message 表重建历史一致
Agent 配置版本化，Run 指回当时那份Agent.current_version_id + AgentVersion.spec + Run.agent_version_id一致
LangChain 组装 agent 图build_agent() → kernel 的 create_deep_agent()，中间件顺序显式分层一致
Event 属于 Run，seq 严格递增TraceEvent 契约三条规则；_EventFactory 集中管 seq一致
sandbox 按会话创建，不按 runSandboxManager.acquire(thread_id)，per-thread 懒创建幂等一致
subagent 独立上下文，深度封顶_subagent_dict() 显式传 tools=[]，结构性封顶在 1一致
Run 内审批，拒绝不终止ApprovalMiddleware + Approval 表；拒绝作为工具结果回给模型一致
上下文压缩，原文不丢CompactionMiddleware + thread.summary/summary_upto一致
这一栏的意义

这八条是概要设计里论证最久的部分。它们在 atlas 里已经成立，而且是带着理由成立的 —— 代码注释里写明了每个决定的代价。本期不要去动它们，也不要因为命名不同就重构。

平台域 —— 缺口在这里

概要设计atlas 现状

技能 CRUD、版本化、与 Agent 关联、双路投送kernel 里 SkillsMiddleware 已就绪且 create_deep_agent(skills=) 已接，但 atlas 一行都没用新建
Mem0 长期记忆，读写与用户管理没有。kernel 的 memory.py 是 AGENTS.md 静态上下文，不是同一个东西新建

最值得注意的一行

kernel 里 SkillsMiddleware 完整可用，create_deep_agent 的签名里 skills: list[str] | None 就在那儿摆着 —— atlas 的 build_agent() 从来没传过它。技能这一块不是从零写，是把已有的能力接上，工作量集中在存储、版本和投送，不在中间件。

02概念对齐与一处修正

thread 还是 session：不改

概要设计里叫 session，atlas 叫 thread。我的判断是保留 thread，把两个名字登记为同一个概念。

  • thread 是 LangGraph 生态里这个概念的标准词（thread_id 是 checkpointer 的键），atlas 的内核血统如此，改名等于跟生态拧着来。
  • 改名的收益是词汇一致，代价是 5 张表的外键、全部 API 路径、前端路由、27 个测试文件 —— 一次纯粹的重命名重构，没有任何行为改进，却有引入回归的真实风险。
  • 接 acp 时统一用 thread 即可，两类 Agent 仍然共享一套对象模型。

下文一律用 thread。概要文档里的 session 读作同一个东西。

一处概要设计的修正：needs_approval 不该由 type 推导

概要设计的 Agent 管理里写了这样一条推导：

caps.in_run_input = caps.needs_approval = not is_native

理由是"native 的上下文由服务端每轮重建，不能在 Run 内挂起等人"。atlas 证明这条是错的 —— 它的 native agent 有完整的 Run 内审批：ApprovalMiddleware 在图内 interrupt，run 停在那里等决策，拒绝作为工具结果回给模型继续跑。而且 bash 和 coding_task 是强制进审批列表的，这条写在 schema 层，绕过前端直接调 API 同样被拦。

病根

把两件不同的事塞进了一个能力位。「Run 内挂起等人」与「挂起时能接受什么」是两回事：native 挂起后接受的是结构化决策（allow_once / allow_always / reject），acp 挂起后还能接受自由文本。只有后者是 type 推导的。

修正后的推导：

# 上下文由服务端持有 ⇒ 可以重建、可以改写
regenerate = edit_history = branch = rollback_on_cancel = is_native

# 压缩要能改写「模型看到的历史」，前提同样是服务端持有上下文
compact = is_native and spec.compaction.enabled

# 自由文本插入进行中的 Run —— native 的 Run 内交互是决策不是对话
in_run_input = not is_native

★ 与 type 无关，由 spec 决定：两类 Agent 都能做 Run 内审批
needs_approval = bool(spec.limits.require_approval_for)

这个修正让能力位的来源分成两类，而不是一类：

来源能力位为什么
type 推导regenerate / edit_history / branch / compact / rollback_on_cancel / in_run_input取决于上下文由谁持有 —— 这是 type 的定义本身
spec 推导needs_approval取决于这一版配置勾了什么，与 type 正交
握手探测resume_session（仅 acp）取决于 adapter 声明的能力位

原型里 native 会话不显示审批卡片的那个演示，因此也是错的 —— 配了 require_approval_for 的 native agent 一样会挂起等确认。这一条要同步改回去。

03Agent.type 与能力推导

为什么现在就加

本期只做 native，type 的取值恒为 native —— 看起来可以等 acp 来了再加。不行，两个理由：

  • type 是不可变字段。等有了存量数据再加，要回填全部 agent 行，而且 API 契约会 breaking（AgentOut 多一个必填字段）。现在加，默认值 native，零成本。
  • capabilities 要投影到 API 给前端用。前端按能力位渲染界面这件事本期就要做（决定"重新生成"按钮显不显示），没有 type 就无从推导。

字段放 agent 行，不放 spec

# server/src/atlas_server/db/models.py — Agent 类追加

            "(type = 'native' AND cli_type IS NULL) OR "
            "(type = 'acp' AND cli_type IS NOT NULL)",

为什么不放 agent_version.spec

spec 回答的是"这一版怎么配"，type 回答的是"这个 agent 走哪条执行路径"。放 spec 里意味着可以通过发新版本把 native 改成 acp —— 同一个 agent 的历史 run 一半走 engine、一半走 bridge，agent_version_id 能指回配置却指不回执行语义，可复现性承诺当场破掉。放 agent 行上，一条 CHECK 加一句服务层拒绝就够了。

capabilities 是算出来的，不入库

新文件，放 engine 而不是 server：它是 agent 语义的一部分，server 只做投影。

# engine/src/atlas_engine/capabilities.py （新建）
"""能力位 —— 由 type 与 spec 推导，不是配置项。

★ 唯一所有者。前端渲染按钮、后端拒绝非法操作，都读这里，
  不允许任何一方自己判断 `type == "native"`。
"""
from dataclasses import dataclass

from .spec import AgentSpec

AgentType = Literal["native", "acp"]


@dataclass(frozen=True)
class Capabilities:
    regenerate: bool          # 重跑最后一轮
    edit_history: bool        # 改写历史消息后重发
    branch: bool              # 从某条消息分叉出新 thread
    compact: bool             # 上下文压缩
    rollback_on_cancel: bool  # 取消后回到 run 之前的状态
    in_run_input: bool        # run 进行中插入自由文本
    needs_approval: bool      # 这一版配置会触发 Run 内审批
    resume_session: bool      # 环境回收后能续上


def capabilities_for(agent_type: AgentType, spec: AgentSpec) -> Capabilities:
    is_native = agent_type == "native"
    return Capabilities(
        regenerate=is_native,
        edit_history=is_native,
        branch=is_native,
        compact=is_native and spec.compaction.enabled,
        rollback_on_cancel=is_native,
        in_run_input=not is_native,
        # ★ 与 type 正交（§02 的修正）
        needs_approval=bool(spec.limits.require_approval_for),
        # native 恒真：历史在 message 表，环境回收不影响续聊
        resume_session=True if is_native else False,  # acp 由握手探测覆盖
    )

04技能：本期主体

kernel 已经准备好了

create_deep_agent 的签名里就有 skills: list[str] | None，传的是源路径列表。它在三处装配 SkillsMiddleware：主 agent、每个 subagent（如果 subagent spec 里有 skills 键）、以及 general-purpose。

更关键的是 graph.py 里这一行：

backend = backend if backend is not None else StateBackend()

而它的 docstring 明确写着：With StateBackend (default), provide skill files via invoke(files={...}). With FilesystemBackend, skills are loaded [from disk].

概要设计的"双路投送"在这里落地

它不是我们要额外设计的机制，而是 kernel 里已经定义好的两种模式。我们要做的是：按 agent 有没有沙箱，决定走哪条，并保证两条路下技能内容完全一致。

两条路

agent 配置backend技能怎么到位
勾了 bashDockerSandboxrun 启动前把技能包物化进容器 /skills/<slug>/，中间件从容器文件系统读
没勾 bashStateBackend（默认）把技能文件预置进 graph 初始 state 的 files 字典

存储：技能也要版本

# server/src/atlas_server/db/models.py （新增两张表）

class Skill(Base, TimestampMixin):
    """技能定义。与 Agent 同构：行存身份与当前版本，内容在 version 表。"""
    __tablename__ = "skill"

    id: Mapped[UUID] = _uuid_pk()
    #: == SKILL.md frontmatter 的 name，也是投送路径 /skills/<slug>/
    slug: Mapped[str] = mapped_column(String(64), nullable=False, unique=True)
    display_name: Mapped[str] = mapped_column(Text, nullable=False)

    #  写得含糊，技能就等于没有。≤1024 是 Agent Skills 规范的上限。
    description: Mapped[str] = mapped_column(String(1024), nullable=False)
    status: Mapped[str] = mapped_column(String(16), server_default="draft")
    current_version_id: Mapped[UUID | None] = mapped_column(
        UUIDType, ForeignKey("skill_version.id", use_alter=True,
                             name="fk_skill_current_version"), nullable=True)
    created_by: Mapped[UUID] = mapped_column(UUIDType, ForeignKey("app_user.id"))

    __table_args__ = (
        CheckConstraint("status IN ('draft','enabled','archived')", name="status_enum"),
    )


class SkillVersion(Base):
    __tablename__ = "skill_version"

    id: Mapped[UUID] = _uuid_pk()
    skill_id: Mapped[UUID] = mapped_column(
        UUIDType, ForeignKey("skill.id", ondelete="CASCADE"), nullable=False)
    version: Mapped[int] = mapped_column(Integer, nullable=False)
    #: SKILL.md 正文（不含 frontmatter —— 它由 slug/description 渲染生成，
    #  避免正文里的 name 与 skill.slug 不一致这种双事实源问题）
    body: Mapped[str] = mapped_column(Text, nullable=False)
    #: 附属文件 {相对路径: base64}。MVP 入库，与 RunFile 同一个 >1MB 转对象存储的阈值
    resources: Mapped[dict] = mapped_column(JSONType, nullable=False, default=dict)
    #: sha256(render()) —— 沙箱物化的幂等键，也是"内容真的变了吗"的判据
    digest: Mapped[str] = mapped_column(String(64), nullable=False)
    created_by: Mapped[UUID] = mapped_column(UUIDType, ForeignKey("app_user.id"))
    created_at: Mapped[datetime] = mapped_column(UTCDateTime, server_default=func.now())

    __table_args__ = (UniqueConstraint("skill_id", "version", name="uq_skill_version"),)
为什么技能也要版本

与 agent_version 同一条理由：run 必须能回答"当时用的哪版技能"。技能是会改变模型行为的内容，甚至含可执行脚本 —— 不版本化的话，技能一改，所有历史 run 的含义跟着变，而 run.agent_version_id 仍然指着同一行配置，可复现性是假的。

关联放哪：spec 里存 (slug, version) 对

三个候选，逐个排除：

方案问题
agent_skill 关联表改技能关联不产生 agent 新版本 → 历史 run 的配置快照不完整，可复现性破了
spec.skill_slugs: list[str]活引用。技能升级后历史 run 语义静默改变 —— 和上面一个病
spec 里存技能全文像 subagent 那样物化拷贝。但 SKILL.md 可能很长且带附件，spec 会膨胀到几百 KB，且技能升级要所有 agent 重新发版

取第四个：存 (slug, version) 对，保存 agent 时把 None 解析成当时的 current 版本号写死。

# server/src/atlas_server/schemas/agent.py

class SkillRefIn(BaseModel):
    """agent 引用一个技能。

    ★ version=None 只在**请求体**里合法，表示"用当前版本"。
      服务层在保存前解析成具体版本号再落进 spec —— 于是存进
      agent_version.spec 的永远是确定版本，历史 run 可精确复现。

    ★ 快照纪律（tests/test_spec_snapshots.py）：本模型的必填集合
      是 {"slug"}，version 必须有默认值。
    """
    slug: str = Field(pattern=r"^[a-z][a-z0-9-]{0,62}$")
    version: int | None = None


class AgentSpecIn(BaseModel):
    ...
    #: 默认空列表 —— 历史快照没有这个字段，反序列化照常
    skills: list[SkillRefIn] = Field(default_factory=list, max_length=32)
# server/src/atlas_server/services/agent.py — 保存路径

async def _pin_skill_versions(self, spec: AgentSpecIn) -> AgentSpecIn:
    """把 version=None 解析成当时的 current 版本号。

    ★ 顺带做存在性校验：引用了不存在或已归档的技能，**在保存时就 400**，
      而不是等到某次 run 才在事件流里报错。与 spec.validate() 同一条纪律
      （§3 D3：能在保存时拒绝的，不留到运行时）。
    """
    if not spec.skills:
        return spec
    resolved = await SkillRepository(self._session).resolve_refs(spec.skills)
    return spec.model_copy(update={"skills": resolved})

于是"跟进技能新版本"是个显式动作：用户在编辑器里点"更新到 v5"，产生 agent 新版本。不会有技能作者一改，全平台 agent 行为悄悄变了这种事。

投送：SkillService 与 SkillMaterializer

# server/src/atlas_server/services/skill.py （新建）

@dataclass(frozen=True)
class ResolvedSkill:
    slug: str
    version: int
    description: str
    body: str
    resources: dict[str, str]
    digest: str

    def render(self) -> str:
        """拼出完整 SKILL.md。frontmatter 由字段生成，不从 body 里取。"""
        return (
            f"---\nname: {self.slug}\n"
            f"description: {self.description}\n---\n\n{self.body}"
        )


class SkillUnavailable(RuntimeError):
    """引用的技能不存在 / 版本已归档。冒泡成 run.failed。

    §13.2：勾了却静默跳过，模型会按"我没有这个技能"的行为跑完一轮，
    用户看到的是"它怎么没照技能说的做"，而不是"技能没装上"。
    """


class SkillService:
    def __init__(self, session: AsyncSession) -> None:
        self._repo = SkillRepository(session)

    async def materialize(self, refs: list[dict]) -> list[ResolvedSkill]:
        """按 spec 里钉死的 (slug, version) 精确取内容。"""
        rows = await self._repo.load_exact(
            [(r["slug"], r["version"]) for r in refs])
        if missing := {r["slug"] for r in refs} - {s.slug for s in rows}:
            raise SkillUnavailable(f"技能不可用：{sorted(missing)}")
        return rows
# server/src/atlas_server/services/skill_delivery.py （新建）

SKILLS_ROOT = "/skills"


def as_seed_files(skills: list[ResolvedSkill]) -> dict[str, str]:
    """StateBackend 路：技能 → graph 初始 state 的 files 字典。"""
    out: dict[str, str] = {}
    for s in skills:
        out[f"{SKILLS_ROOT}/{s.slug}/SKILL.md"] = s.render()
        for rel, b64 in s.resources.items():
            out[f"{SKILLS_ROOT}/{s.slug}/{rel}"] = b64decode(b64).decode("utf-8")
    return out


class SkillMaterializer:
    """沙箱路：把技能包写进容器的 /skills/。

    ★ 幂等靠 digest：容器是会话级长寿的，同一 thread 的第二个 run
      通常技能没变，不该每轮都重写一遍（docker cp 有真实开销，
      且会让容器内的 mtime 无谓地跳动）。

    ★ 先清理不在本次清单里的目录：agent 改版把某个技能去掉后，
      残留在容器里的旧技能仍会被 SkillsMiddleware 扫到并进提示词 ——
      "取消勾选了却还在生效"，比没装上更难查。
    """

    def __init__(self, backend: Any) -> None:
        self._backend = backend
        self._applied: dict[str, str] = {}   # slug → digest

    async def apply(self, skills: list[ResolvedSkill]) -> None:
        wanted = {s.slug: s for s in skills}
        for stale in set(self._applied) - set(wanted):
            await self._backend.aexecute(f"rm -rf {SKILLS_ROOT}/{stale}")
            self._applied.pop(stale)
        for slug, s in wanted.items():
            if self._applied.get(slug) == s.digest:
                continue
            await self._write_one(s)
            self._applied[slug] = s.digest

# server/src/atlas_server/services/memory.py （新建）

class MemoryService:
    """Mem0 接入。

    ★ 作用域映射（容易错配，写死在这里）：
        mem0 的 user_id  ← atlas 的 app_user.id
        mem0 的 run_id   ← atlas 的 **thread_id**（mem0 的 run 指"一段会话"）
        mem0 的 agent_id ← 本期**不用**
    """

    def __init__(self, settings: Settings) -> None:
        self._client = AsyncMemory.from_config(settings.mem0_config)
        self._top_k = settings.memory_top_k
        self._threshold = settings.memory_threshold

    async def recall(self, *, user_id: UUID, query: str) -> str | None:
        """检索并渲染成提示词片段。

        ★ 只按 user_id 检索，不带 agent_id —— 概要设计已定：把任意用户
          说的话自动变成服务所有人的知识太激进。agent 维度的知识走 RAG，
          且必须是总结提炼并事实核查过的，不走 Mem0 的自动提取。
        """
        hits = await self._client.search(
            query, user_id=str(user_id),
            top_k=self._top_k, threshold=self._threshold)
        if not hits:
            return None
        lines = "\n".join(f"- {h['memory']}" for h in hits)
        return f"## 关于这位用户已知的事实\n\n{lines}\n\n" \
               "（来自历史对话的提取，可能过时；与用户当前陈述冲突时以当前为准。）"

    async def remember(self, *, user_id: UUID, thread_id: UUID,
                       messages: list[dict]) -> None:
        await self._client.add(
            messages, user_id=str(user_id), run_id=str(thread_id),
            metadata={"thread_id": str(thread_id)})

写入时机

不能在 run 内同步做 —— Mem0 的 add 会调 LLM 做提取，几秒起步，把它挂在 run 里等于每轮对话都多等一次模型调用。

接在 _persist() 之后，与标题生成同级处理：

    #   记忆少一条不影响本轮正确性，不该让 run 变成 failed。
    #   代价写明：进程重启会丢掉排队中的提取。要可靠就进队列，

只在 succeeded 时提取

08身份贯通

atlas 的 README 明说不做鉴权。本期仍然不做权限判定，但必须做身份贯通 —— 这不是功能诉求，是记忆功能的正确性前提。

不做会怎样

identity.current_user() 缺 header 时回落到 DEFAULT_USER_ID。如果前端不传 header，所有人共用一个 user_id —— Mem0 按 user 隔离的记忆就变成全局共享：A 说的偏好会出现在 B 的对话里。这是数据泄露，不是功能缺失。

最小动作，三处：

  • 前端每个请求带 X-User-Id（已有 header 支持，只是前端没传）。
  • MemoryService.recall/remember 的 user_id 来自 current_user，不允许从别处取 —— 与 identity.py 的"唯一身份来源"纪律一致。
  • 配置加一个开关：memory.enabled 默认 false。身份没接通之前，记忆功能不该默认打开。

权限矩阵（谁能看到哪些 agent / 用哪些技能 / 调哪些 MCP）留给权限专项。本期只把身份这条线接通。

09可观测性埋点

atlas 有完整的 TraceEvent 流，但那是给用户看的执行轨迹，不是给运维看的遥测。两者受众不同、保留期不同、聚合方式不同，不要复用。

埋点位置：engine 的 runner

所有事件的必经之路就是 _EventFactory.make 与 runner.run 的主循环。在那里挂 span 即可。

分层是允许的

import-linter 的 forbidden 列表里是 fastapi / sqlalchemy / redis / uvicorn / …，没有 OTel。而且 opentelemetry-api 是无副作用的接口包 —— 没装 SDK 时它是 no-op。engine 只发 span，server 侧装配 exporter，分层依然成立。这是干净的做法，不需要为可观测性开分层的口子。

# engine/src/atlas_engine/telemetry.py （新建）
"""OpenTelemetry GenAI 语义约定的埋点。

★ 只依赖 opentelemetry-api（no-op 友好）。exporter 装配在 server。
★ 属性名一律用 _incubating 里的 GenAI 常量，不自己编 —— 编了的话
  Langfuse / 任何标准后端都认不出来，仪表盘要手写映射。
"""
from opentelemetry import trace
from opentelemetry.semconv._incubating.attributes import gen_ai_attributes as ga

_tracer = trace.get_tracer("atlas.engine")


@contextmanager
def run_span(spec: AgentSpec, run_id: UUID):
    with _tracer.start_as_current_span(
        f"invoke_agent {spec.slug}",
        attributes={
            ga.GEN_AI_OPERATION_NAME: "invoke_agent",
            ga.GEN_AI_AGENT_NAME: spec.name,
            ga.GEN_AI_REQUEST_MODEL: spec.model.model,
            "atlas.run_id": str(run_id),
        },
    ) as span:
        yield span

三条不要破的既有纪律

  • engine 不得依赖 server / DB / Web 框架 —— import-linter 守着。技能与记忆都必须以"已解析好的数据"形态经 RunHooks 注入，engine 不认识 SkillRepository，也不认识 Mem0。
  • 快照新字段必须有默认值 —— tests/test_spec_snapshots.py 守着。AgentSpecIn.skills 与 SkillRefIn.version 都遵守。
  • 不静默降级（§13.2）—— 技能解析失败、MCP 工具缺失、沙箱起不来，一律冒泡成 run.failed，不允许"少装一个就默默跑"。SkillUnavailable 是这条纪律在技能域的实例。
阶段 1 与 2 之后可以停

阶段 1+2 交付的是能用技能的 native agent，这是概要设计里 native 最核心的缺口。阶段 3（记忆）依赖阶段 8 的身份贯通才安全，阶段 4、5 是平台化与运维诉求 —— 可以按实际优先级重排，但不要把阶段 3 排在身份贯通之前。
