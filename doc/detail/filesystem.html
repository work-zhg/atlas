Detailed Design · Filesystem

文件系统与沙箱改造

把 middleware/filesystem 拆成 filesystem 与 sandbox 两个中间件，协议层同步拆成两个并列的 Protocol。更实质的变化是：文件系统的事实源从容器内盘换成 OSS，会话工作区经 FUSE 挂进沙箱的 /workspace。技能随之并入同一条投送路径 —— 会话创建时拷进与工作区平级的 skills/ 前缀，读走 filesystem，执行走 sandbox。

挂载方案 A · FUSE技能随会话拷贝移除 dry-runkernel 净减 ~8000 行

01改动的实质

现在改造后
无沙箱StateBackend —— 文件在 graph state 里，run 结束消失OssFilesystem —— 真实持久化
有沙箱DockerSandbox —— 文件工具全部委托 execute()，每次一个 docker execOssFilesystem 直连 OSS；沙箱只负责跑命令
工作区docker volume，与容器绑定OSS 前缀，容器回收后仍在
技能未接入（kernel 有能力，atlas 没用）会话创建时拷进 {user}/{thread}/skills/，与工作区平级
三个连带收益
  • 没配 bash 的 agent 也有真实文件。现在它们只有 run 级的 state 文件，跨轮都留不住。
  • docker exec 热路径消失。kernel 分析 §03 指出 ls/read/grep/glob 每次都是一个 exec，换 K8s 后代价升一个量级 —— 现在它们根本不经过容器。
  • 冷会话恢复有了地基。概要设计里「环境已回收，工作区仍在 OSS」从此是事实而非承诺。
  • 技能投送不再需要第二条路。见 §08 —— SkillMaterializer、CompositeBackend 路由、双路分叉全部不需要。

代价要说在前面

OSS 不是文件系统。edit_file 变成 read-modify-write（无法原地改），没有原子 rename，删目录要先列举再批量删，而 FUSE 挂载为了保证可见性必须关掉缓存 —— 容器内的文件读取会变慢。详见 §06。

02协议层：两个并列协议

现在是 SandboxBackendProtocol(BackendProtocol) —— 继承，所以「沙箱」在类型上必须同时是「文件系统」。拆开后并列：

# kernel/backends/filesystem_protocol.py

class FilesystemProtocol(Protocol):
    """只做 OSS 能做的事。路径一律相对会话工作区根。

    ★ 没有 grep：对象存储不支持内容检索。内容搜索归 execute。
    ★ 没有 ls/glob：统一成 search（前缀 + 可选文件名 glob）。
    """
    def read(self, path: str, offset: int = 0, limit: int = 2000) -> ReadResult: ...
    def write(self, path: str, content: str | bytes) -> WriteResult: ...
    def edit(self, path: str, old: str, new: str, *,
             replace_all: bool = False) -> EditResult: ...
    def delete(self, path: str, *, recursive: bool = False) -> DeleteResult: ...
    def search(self, prefix: str, *, pattern: str | None = None,
               max_keys: int = 1000) -> SearchResult: ...
    # 各配一个 a* 异步版，共 10 个方法


# kernel/backends/sandbox_protocol.py

class SandboxProtocol(Protocol):
    """只负责「在隔离环境里跑一条命令」。不提供任何文件操作。"""
    @property
    def id(self) -> str: ...
    def execute(self, command: str, *, timeout: int | None = None,
                cwd: str | None = None) -> ExecuteResponse: ...
    async def aexecute(self, ...) -> ExecuteResponse: ...
并列换来的最大收益

BaseSandbox 那 1824 行里，有 13 个方法是「用 execute() 实现 ls/read/write/edit/delete/grep/glob 及其异步版」的委托代码 —— read 是往沙箱塞一段 Python 脚本跑，ls 是 os.scandir 脚本。全部删掉，只剩 execute / aexecute / execute_with_offload / id。估计 1824 → 约 300 行。

结果类型跟着精简

保留   ReadResult · WriteResult · EditResult · DeleteResult · ExecuteResponse
       ExecuteArtifact · ExecuteOffloadResult
新增   SearchResult
删除   LsResult · FileInfo · GlobResult · GrepResult · GrepMatch · ContextLine
       FileData · FileUploadResponse · FileDownloadResponse *

* upload/download 不再是协议的一部分：它们存在是为了让 BaseSandbox 的
  文件操作能把内容搬进搬出容器。文件操作没了，它们也就没了消费者。
  （沙箱内的文件出入现在由 FUSE 挂载承担。）

03OssFilesystem

Key 布局

{bucket}/{user_id}/{thread_id}/workspace/   ← 工作区。★ 可被子智能体共享挂载
{bucket}/{user_id}/{thread_id}/skills/      ← 会话的技能副本。与 workspace 平级
{bucket}/{user_id}/{thread_id}/system/      ← 压缩归档、大结果外置

{bucket}/_skills/{slug}/{version}/          ← 技能源仓库（全局只读，配置平面发布）
★ 技能与工作区平级，不在 workspace 之内

因为 workspace 是共享挂载的。子智能体的 Pod 挂的是主 agent 的 workspace（见 Subagent 设计 §03）—— 技能若住在 workspace 里，子智能体挂载时会连主 agent 的技能一起带上，而它应该有自己的一套。

平级之后三件事同时成立：挂 workspace 带不上技能、各自的技能互相看不见、search("") 不用靠点前缀过滤就已经列不到技能文件。

系统区同理：压缩产生的历史归档、外置的大工具结果放在兄弟目录，模型 search 时不会被它们淹没并当成自己的产物 —— 不是靠过滤，是不在前缀内。

三个前缀，三个独立的来源

前缀thread_id 取自为什么
workspace/可配置 —— 主 agent 用自己的，子智能体用父的委派常常就是「帮我处理这批文件」，产物要能互相看见
skills/恒为自己的技能是能力配置，跟 agent 走
system/恒为自己的压缩归档属于自己的上下文历史
 
# 主 agent（thread A）
workspace → {user}/{A}/workspace     skills → {user}/{A}/skills

# 子智能体 coder（子会话 thread B，父是 A）
workspace → {user}/{A}/workspace     ← 父的
skills    → {user}/{B}/skills        ← 自己的

session_id 不进 engine

server 构造实例时闭包进去，与现有的 SandboxManager.acquire(thread_id) 同一手法。engine 只看到一个 FilesystemProtocol，不知道会话的存在 —— 分层不动，runner.run() 的签名也不动。

# server/src/atlas_server/providers/filesystem/oss.py

class OssFilesystem(FilesystemProtocol):
    def __init__(self, client: OssClient, *, root: str, session_id: UUID) -> None:
        self._client = client
        base = f"{user_id}/{thread_id}"
        #: ★ 工作区可以是**别人的** —— 子智能体挂父会话的工作区。
        ws_base = f"{user_id}/{workspace_thread_id or thread_id}"
        self._ws = f"{ws_base}/workspace"
        #: 技能与系统区恒为自己的 —— 与 workspace **平级**，不在它之内，
        #  所以挂载 workspace 带不上它们。
        self._skills = f"{base}/skills"
        self._sys = f"{base}/system"

    def _to_key(self, path: str) -> str:
        """★ 本类唯一的安全关键点：路径不得逃出所属前缀。

        规范化必须在拼前缀**之前**做 —— 先拼后归一的话，
        `../../other-thread/x` 会归一成另一个会话的真实 key。
        路径里现在有 user 段，这一条同时挡住跨用户。

        ★ `/skills/**` 路由到**自己的** skills 前缀，其余落 workspace。
          两者是平级的兄弟目录，所以这里只是一次前缀选择 ——
          不需要 CompositeBackend 那种通用路由（它已随旧协议一起删除）。
        """
        norm = posixpath.normpath(posixpath.join("/", path))
        if norm in ("/", ".") or not norm.startswith("/"):
            raise PathEscape(path)
        if norm == "/skills" or norm.startswith("/skills/"):
            return f"{self._skills}{norm[len('/skills'):]}"
        return f"{self._ws}{norm}"
这一处必须有测试

../、..%2f、/workspace/../../、符号形式的绝对路径 —— 逐个钉住。会话隔离全靠这个函数，它错了等于会话之间可以互相读写。放进 tests/guards/：它红了不是功能坏，是隔离破了。

五个操作的实现要点

操作OSS 侧注意
readGetObject + Range行分页要先取到再切；Range 是字节不是行，大文件先按字节窗口取再对齐行边界
writePutObject整对象覆盖。无追加语义
editGet → 改 → Putread-modify-write，见下方大小上限
deleteDeleteObject / 批量recursive 要先 ListObjects 再 DeleteMultiple，分批（多数实现单批上限 1000）
searchListObjectsV2见 §04
edit_file 要有大小上限

OSS 不能原地改，edit 必须把整个对象拉下来。没有上限的话，模型对一个 200MB 的文件做一次替换，会把整个对象拉进执行器内存。

建议 EDIT_MAX_BYTES = 2 * 1024 * 1024，超过时明确报错并给出替代方案：「文件超过 2MB，无法用 edit_file 修改；请用 execute 跑 sed -i」。§13.2 的纪律 —— 不静默降级，也不静默吞内存。

04search 的能力边界

@dataclass(frozen=True)
class SearchResult:
    keys: list[str]              # 命中的文件路径（已剥掉会话前缀）
    common_prefixes: list[str]   # delimiter 分组，用来模拟"子目录"
    truncated: bool              # 撞到 max_keys
调用行为
search("")列工作区根，delimiter="/" → 顶层文件 + 子目录名
search("reports/")列该前缀下一层
search("reports/", pattern="*.md")列举后在客户端做 fnmatch 过滤
search("", pattern="**/*.csv")递归列举（不带 delimiter）后过滤 —— 大前缀下会拉很多 key
工具描述里必须明说没有内容搜索

否则模型会反复用 search 找内容、拿到空结果、然后据此下结论说"没找到相关文件" —— 错得很安静。

按路径前缀与文件名查找工作区中的文件。
本工具不搜索文件内容 —— 要按内容查找，用 execute 跑 grep。

连带的能力削减：没配 sandbox 的 agent 失去内容搜索。对顾问型 agent 可以接受（它主要读自己写过的东西），但这是个要意识到的取舍 —— 如果观察到顾问 agent 频繁"找不到东西"，信号是给它配 sandbox，而不是给 filesystem 加 grep。

truncated=True 时结果里要带一句可执行的提示，而不是只标个布尔：「已达 1000 条上限，请缩小前缀范围」。

默认跳过点开头的前缀

技能与系统区已经不在 workspace 前缀内（§03），所以它们不靠这条过滤 —— 结构上就列不到。

这条留给写入隔离区：子智能体的产物落在 .agents/<name>/（Subagent 设计 §03），不过滤的话主 agent 每次 search("") 都会被子智能体的中间产物淹没。判断按段做而不是只看开头，否则 reports/.draft.md 会漏网；显式给出 search(".agents/coder/") 时仍然列得出来。

05挂载：FUSE 必须在沙箱外

直接在沙箱容器里挂 FUSE 会毁掉现有的安全姿态

atlas 的沙箱容器现在是 --read-only + --cap-drop ALL + --user 1000:1000 + --network none + --pids-limit。

而在容器内挂 FUSE 需要 --device /dev/fuse + --cap-add SYS_ADMIN。SYS_ADMIN 与 cap-drop ALL 直接冲突，而且它是容器逃逸最常用的一块跳板。

正确做法：挂载发生在沙箱容器之外

Kubernetes（目标形态）
  ┌─ Node ──────────────────────────────────────────────────┐
  │  kubelet + OSS CSI driver                                │
  │     ↓ 在节点上完成 FUSE 挂载                               │
  │  ┌─ Pod（NetworkPolicy: deny-all）──────────────────────┐ │
  │  │  sandbox 容器                                         │ │
  │  │    /workspace ← subPath {user}/{★workspace_thread}/   │ │
  │  │                        workspace                      │ │
  │  │    /skills    ← subPath {user}/{自己的 thread}/skills │ │
  │  │    /tmp       ← emptyDir(Memory)                      │ │
  │  │    cap-drop ALL · non-root · read-only                │ │
  │  └──────────────────────────────────────────────────────┘ │
  └──────────────────────────────────────────────────────────┘

★ 两个挂载点的 subPath **来自不同的 thread**：
    主 agent    workspace_thread = 自己
    子智能体     workspace_thread = **父会话** ← 所以 Pod 模板必须参数化

沙箱容器看到的是一个普通的卷，它自己不需要任何额外能力，cap-drop ALL 原样保留。

为什么是 CSI 而不是 sidecar

把 ossfs 做成 Pod 内的 sidecar 也能挂上，但同一个 Pod 共享网络命名空间 —— sidecar 要访问 OSS 端点，就必须给这个 Pod 开 egress，于是沙箱容器里的 bash 也能触达 OSS 端点。「沙箱无网络」这条保证就没了。

CSI 让挂载发生在节点层，Pod 可以保持完全的 deny-all。sidecar 只作为 CSI 不可用时的退路，且要接受这个网络面的扩大。

本地开发（Docker）

同一条原则：ossfs 跑在沙箱容器外。宿主机（或一个带 SYS_ADMIN 的辅助容器）把 OSS 前缀挂到宿主路径，沙箱容器 bind-mount 那个路径。

# 宿主侧一次性挂载（按会话）
ossfs {bucket}:/{user}/{thread}/workspace  /var/lib/atlas/{user}/{thread}/workspace \
      -o url=... -o allow_other \
      -o attr_timeout=0 -o entry_timeout=0 -o negative_timeout=0   ← 见 §06

# 沙箱容器（安全参数不变）。两个挂载源来自不同的 thread ——
# 子智能体的 WS_TID 是父会话的 id，SELF_TID 是自己的。
docker run -d --read-only --cap-drop ALL --user 1000:1000 --network none \
  -v /var/lib/atlas/{user}/${WS_TID}/workspace:/workspace \
  -v /var/lib/atlas/{user}/${SELF_TID}/skills:/skills:ro \
  --tmpfs /tmp:rw,size=64m \
  ...

本地也可以用 MinIO 顶替 OSS —— 接口是 S3 兼容的，OssFilesystem 一份实现两处都能跑。

06一致性：两个写入方

这是方案 A 最需要想清楚的地方。工作区有两条写入路径，它们不经过同一个栈：

① write_file 工具  → OssFilesystem → OSS SDK → OSS        （不经过 FUSE）
② execute 里的 bash → FUSE 挂载点 → ossfs → OSS
后果：FUSE 的缓存看不见路径 ①

模型 write_file("a.txt") 写进 OSS，紧接着 execute("cat a.txt") —— ossfs 可能命中负缓存（刚才 stat 过，那时文件不存在）而报 No such file。

这是那种"平时不出、出了极难查"的问题：它取决于两次调用的间隔与缓存 TTL。

处置：关掉 ossfs 的三层缓存

-o attr_timeout=0        # 属性缓存（大小、mtime）
-o entry_timeout=0       # 目录项缓存
-o negative_timeout=0    ★ 最关键：否则"文件不存在"会被缓存
-o max_stat_cache_size=0
（不加 kernel_cache）

代价是真实的：容器内每次 stat / open 都要打一次 OSS。反复读同一个文件的场景（编译、测试）会明显变慢。

给模型一条可执行的规避路径

把它写进 sandbox 的提示词，而不是指望模型自己想到：

需要反复读取同一批文件时（编译、跑测试），先 cp 到 /tmp 再操作：
    cp -r /workspace/src /tmp/src && cd /tmp/src && make
产物写回 /workspace。
改用方案 B 的信号

观察到 execute 里频繁出现重 IO（编译、大量小文件生成、node_modules 这类）。届时改成「启动下载 / 结束上传」，并同时把 write_file 改为经沙箱写入 —— 两件事必须一起做，否则就是 §06 开头那个两份不一致的问题。

这个信号可以量化：可观测性落地后统计 execute 的 P95 时长与命令类型分布。

并发不是问题，但要知道为什么

同一会话的 run 被 Redis 锁串行化，工具调用本身也是串行的 —— 两条写入路径不会真正同时发生。唯一的例外是 bash 起了后台进程（& 或 nohup），它可能在 execute 返回后继续写。这个风险低，但值得在容器回收前留一个短暂的静默窗口。

装配顺序：filesystem 在 sandbox 外层

# kernel/graph.py 主栈
1  if skills:    SkillsMiddleware(...)
2                FilesystemMiddleware(fs, tools=...)      ← 脚手架 · 大结果外置挂这里
3  if sandbox:   SandboxMiddleware(sandbox=...)          ← 新增

顺序是有语义的：wrap_tool_call 的大结果外置在 FilesystemMiddleware 上，而它的主要服务对象正是 execute —— TOOLS_EXCLUDED_FROM_EVICTION 把 7 个文件工具全排除了（它们自己有分页）。filesystem 必须在外层才能接住 sandbox 的大输出。

capture-at-source 的取舍

execute_with_offload 的 capture-at-source 优化（在沙箱内直接把输出重定向到文件，不经内存）要求 execute() 与 read_file 解析到同一文件系统。

在新架构下这个前提仍然成立 —— 沙箱的 /workspace 就是 OSS 工作区，read_file 读的也是它。所以 capture-at-source 可以保留：把输出写到 /workspace/.atlas/out/<tool_call_id>，模型用 read_file 分页读回。

注意那个 .atlas/ 前缀要被 search() 默认过滤掉，理由同 §03 的系统区。

依赖关系改成显式

atlas 现在的 filesystem_allowlist() 藏着一条隐式联动：勾了 bash 就自动获得全部文件工具（注释理由是"bash 写的文件 read_file 要能读到"）。拆分后改成显式校验：

# tool_registry.py
ToolDef(
    name=BASH_TOOL,
    ...
    requires=lambda spec: FILESYSTEM_TOOL in spec.tool_names,
    unmet_hint="sandbox 需要同时启用文件系统 —— "
               "否则 execute 产生的文件无法被读取或检索",
)

不满足时进 unsupported_tools() 明确报出来，而不是偷偷替用户勾上。

08技能：随会话拷贝

会话创建时把技能包拷进 {user}/{thread}/skills/：读走 filesystem（模型看到 /skills/…），执行走 sandbox（Pod 单独挂一个 /skills 挂载点）。

为什么这条路成立 —— FUSE 让可执行技能自动可用

此前需要设计两条投送路径（有沙箱物化进容器 / 无沙箱塞进 graph state），是因为假设技能区与工作区是两个地方。

但 OSS 前缀就是 Pod 的挂载源 —— 技能作为一个平级前缀单独挂到 /skills，它在容器里天然有一个真实路径，execute 直接能跑。不需要 SkillMaterializer、不需要幂等判断与残留清理。

技能的三个能力层级

层级构成需要什么真实例子
L1 纯指令只有 SKILL.md能 read_file代码规范、写作口径、评审清单
L2 指令+参考+ references/能 read_filedataviz：7 篇参考文档，88 KB / 9 文件
L3 指令+可执行+ scripts/ + data/能 execute，且脚本路径在容器内可见ui-ux-pro-max：3.8 MB / 76 文件（data 3.1M · scripts 684K）

L3 不是假设的形态。ui-ux-pro-max 的 SKILL.md 里直接写着让模型执行脚本：

python "<skill>/scripts/search.py" "<query>" --domain <domain>

指令本身没有价值，价值在那 3.1MB 的 CSV 与检索脚本里。kernel 注入的提示词也明确教模型这件事："Skills may contain Python scripts or other executable files. Always use absolute paths." —— 可执行技能是这套技能规范的既定语义，不是我们额外加的诉求。

Key 布局

# 技能源仓库 —— 全局只读，配置平面所有，按版本寻址
{bucket}/_skills/{slug}/{version}/SKILL.md
                                 /scripts/…
                                 /data/…

# 会话副本 —— 可读写，随会话生死。★ 与 workspace **平级**
{bucket}/{user_id}/{thread_id}/skills/{slug}/SKILL.md
                                            /scripts/…
技能为什么不能放进 workspace

因为 workspace 是共享挂载的。子智能体的 Pod 挂的是主 agent 的 workspace（Subagent 设计 §03）—— 技能若住在里面，子智能体挂载时会连主 agent 的技能一起带上。

早先设想过用 .skills/<agent-name>/ 分目录解决，但那只是约定：子智能体照样能读、能改别人那份。平级前缀是结构性的 —— 挂载根本带不上。

副本路径不带版本号 —— 会话内只有一份，用哪一版在拷贝那一刻就定了。模型看到的路径因此是稳定的 /skills/<slug>/（由 _to_key 路由到自己的 skills 前缀，见 §03）。

拷贝流程

# server/src/atlas_server/providers/filesystem/skill_copy.py

async def seed_session_skills(
    fs: OssFilesystem, refs: Sequence[SkillRef], *, concurrency: int = 20
) -> None:
    """把 spec 钉死的技能版本拷进会话工作区。

    ★ 时机：**会话创建**，不是首次 run —— 用户对「新建会话」的
      延迟容忍度更高，而首轮对话的等待是最刺眼的。

    ★ 用 OSS 的 CopyObject：服务端拷贝，不下载不上传。
      单对象 10–50ms，按包并发 20 的话 76 个对象 < 1s。

    ★ 失败即冒泡（§13.2）：少拷几个文件就默默开始，
      表现是模型「照技能说的做了但脚本不存在」—— 比明确报错难查得多。
    """

版本语义：拷贝替代了引用

native 详设里让 spec.skills 钉死 (slug, version)，是为了防止技能改版悄悄改变历史 run 的含义。会话副本天然做到了这一点，而且更强：

钉版本引用会话副本
技能发 v4 后，已有会话仍读 v3 —— 靠引用正确仍读自己那份 —— 物理隔离
v3 被误删 / 误改历史会话受影响不受影响
spec 里钉版本还有用吗有 —— 作用变成决定新会话拷贝哪一版
但可复现性的语义确实变了

会话可以改自己的技能副本。于是 run.agent_version_id → spec → foo@v3 这条链，回答的是「这个会话开始时拷了哪一版」，不再是「这一轮实际用的是什么」。

本期接受这个代价（不额外发 skill.modified 事件）。要还原实际内容时，会话副本本身就在 OSS 里 —— 它是自证的。

两条必须跟上的收尾

  • 会话回收要覆盖 {user}/{thread}/ 下的全部三个前缀（workspace / skills / system），而不只是用户写的文件。3.8MB × N 会话的技能副本如果不删，会变成只增不减的孤儿对象 —— 而且它们不在任何索引里，事后连查都不好查。子会话同理：它有自己的 skills 与 system 前缀，父会话删除时要连带回收。
  • 技能不在 workspace 前缀内，search("") 结构上就列不到。早先靠点前缀过滤，现在靠布局 —— 后者更硬：不是「默认不显示」，是「不在那里」。
要写清的边界：技能不再是可信输入

技能进了工作区，而工作区对 execute 完全开放 —— 模型可以改自己的技能脚本然后执行它。这在能力上是想要的，但意味着：

将来做技能审核（概要设计里说过技能是可执行内容、要按代码审查来做），审核保证的是发布时那一份，不是会话内运行的那一份。这条边界要在文档和界面上都说清楚，别让「已审核」给人虚假的安全感。

09SkillsMiddleware：从扫描到清单

现在每一轮都在重新推导已知信息

SkillsMiddleware.before_agent 扫描技能目录，结果缓存进 SkillsState.skills_metadata。但 atlas 没有 checkpointer —— 每轮 run 都是一次全新的 graph invocation，state 不跨 run 保留。

所以每一轮对话都重扫一遍：配 5 个技能的 agent，每轮在模型看到任何东西之前先做 1 次目录列举 + 5 次 SKILL.md 读取。在无缓存的 OSS/FUSE 上，这是加在每一轮上的固定延迟。

而这 6 次 IO 拿回来的东西，我们在调用之前就全知道：

信息已有来源
有哪些技能spec.skills 里钉死的 (slug, version)
name / description配置平面的 skill 表（configplane/ 有永久缓存）
path确定的：/skills/<slug>/SKILL.md
原实现为什么要扫描

在它原本的场景里，技能是人手动扔进 ~/.claude/skills/ 的，没有任何注册表 —— 文件系统就是注册表，扫描是唯一的发现途径。

我们的架构反过来：注册表先于文件存在，文件是照着注册表亲手拷贝进去的。继承这个扫描，等于假装自己不知道自己刚做了什么。

改造后的接口

@dataclass(frozen=True)
class SkillRef:
    name: str
    description: str
    path: str          # /skills/<slug>/SKILL.md


class SkillsMiddleware(AgentMiddleware):
    """把技能清单渲染进系统提示词。不做发现，不读文件。"""

    def __init__(self, *, skills: Sequence[SkillRef],
                 system_prompt: str | None = None) -> None: ...

    def wrap_model_call(self, request, handler): ...   # 唯一的钩子

不再需要 backend，不再需要 sources。1053 行 → 约 150 行，因为下面这些全部消失：

删   _load_skills_from_source（+ 异步版）与 backend.ls
删   YAML frontmatter 解析（_parse_frontmatter / _parse_allowed_tools）
删   SkillsState / SkillsStateUpdate / before_agent / abefore_agent
删   加载警告整套（MAX_SKILLS_LOAD_WARNINGS、截断、HTML 转义、
     <skill_load_warnings> 渲染）
删   多 source 覆盖逻辑与来源标注

留   SKILLS_SYSTEM_PROMPT 模板（去掉 locations / warnings 两个占位符）
留   _format_skills_list · wrap_model_call

校验从运行时移到发布时

kernel 现在在加载时校验 name ≤64、description ≤1024、文件 ≤10MB。这些搬到配置平面的发布路径 —— 技能作者提交时就被拒，而不是等某个用户跑到一半在提示词里看到一条警告。

与 atlas 已有的纪律一致：能在保存时拒绝的，不留到运行时。

frontmatter 的定位变了，但仍然保留

作者写 SKILL.md（带 frontmatter）
   ↓ 发布时解析一次
配置平面 skill 表：slug / description / body / resources / digest   ← 唯一事实源
   ↓ 会话创建时拷贝，frontmatter 由 slug + description 重新渲染
{user}/{thread}/skills/<slug>/SKILL.md

这接上了 native 详设里那个决定：SkillVersion.body 存不含 frontmatter 的正文，frontmatter 生成出来 —— 避免「正文里的 name 与 skill.slug 不一致」的双事实源。

副本里仍然写入 frontmatter，理由是可移植性：会话里的技能目录导出后仍是一个合法技能包，能给别人用或导回 Claude Code。成本为零。

不扫描会失去三样东西

失去影响判断
会话内新建的技能被发现模型在 /skills/ 下建新目录，不会出现在提示词里诉求是「改技能」不是「建技能」。而且「模型建一个技能再靠提示词发现它」是个奇怪的回路
会话内改 description 生效提示词里仍显示配置平面那份这是好事，见下
损坏的 SKILL.md 有警告副本是我们拷的，损坏只可能来自会话内改坏发布时已校验；运行时读到坏文件模型自己会报
description 始终来自配置平面，是个正确的安全姿态

技能进工作区后不再是可信输入（§08）。而 description 的职责是路由 —— 「这个任务要不要打开这个技能」。让它始终来自那份经过审核的版本，而正文可以按会话适配，这个分工比「全部可改」更稳：改不动别人对你的第一印象，但可以改自己的做法。

10提示词分工

atlas 现在的 _SANDBOX_HINT 一句话讲了两件事，要拆开，各自中间件出各自那半。

# FilesystemMiddleware
文件工具作用于会话工作区，内容持久保留，跨轮对话都在。
按内容搜索不可用 —— search 只匹配路径与文件名；
要按内容查找，用 execute 跑 grep。
# SandboxMiddleware
execute 的工作目录是 /workspace，即上述持久工作区。

- 需要保留的产物必须写在 /workspace 下。
- 临时中间产物写 /tmp —— 它更快，但容器回收后即消失。
- 需要反复读取同一批文件时（编译、跑测试），先 cp 到 /tmp
  再操作，产物写回 /workspace。
- 沙箱无网络。

技能那一段由 SkillsMiddleware 出

它是 kernel 既有的 SKILLS_SYSTEM_PROMPT（去掉来源标注与加载警告两块）—— 教模型渐进披露：看描述判断相关性、read_file(path, limit=1000) 读正文、按绝对路径执行脚本。

本次要补的只有一句，接在技能清单之后：

技能位于 /skills/，是本会话独有的副本 —— 你可以修改它们，
改动只对本会话生效。需要反复执行某个技能脚本时，先 cp -r 到 /tmp 再跑。

后半句是 §06 那个 FUSE 性能问题的逃生口：技能脚本导入兄弟模块、读数据文件，每一次都是一个 OSS 往返。

这条提示词有物理支撑

方案 A 让「/tmp 快但易失、/workspace 持久但慢」成为真实的性能与生命周期差异，而不只是一句约定。模型按提示词行事时得到的反馈是一致的 —— 这比单纯的规则更容易被遵守。

13落地顺序

步骤 1 · 移除 dry-run

独立且无依赖，先做能让后面每一步都少一个分支。迁移 + 服务层 + 前端面板 + 测试。

验证：make check 绿；grep -rn "spec_snapshot\|ephemeral" server/src 无结果。

步骤 2 · 协议拆分（不换实现）

拆 FilesystemProtocol / SandboxProtocol，BaseSandbox 删掉文件委托，DockerSandbox 只实现 sandbox 侧。此时文件工具暂时仍走 StateBackend，行为不变。

验证：现有测试全绿 —— 这一步不该有任何行为变化。

步骤 3 · 中间件拆分

middleware/filesystem.py 拆两个；ls/glob/grep 三工具合并成 search；tool_registry 改造，filesystem_allowlist() 拆掉，bash 的 requires 上线。

验证：勾 bash 不勾 filesystem 时，unsupported_tools() 明确报出，而不是自动补上。

步骤 4 · OssFilesystem + FUSE 挂载

实现 OssFilesystem（本地用 MinIO）；宿主侧 ossfs 挂载；沙箱容器改 bind-mount。路径逃逸测试进 tests/guards/。

验证：写→读往返测试 —— write_file("a.txt") 后立刻 execute("cat a.txt") 必须读到。这条是 §06 那个缓存问题的唯一防线，必须在集成测试里跑，不能只靠手测。

步骤 5 · 技能接入

SkillsMiddleware 精简成清单渲染；skill_copy 在会话创建时并发拷贝；search() 跳过点前缀；会话删除连带回收整个前缀。

验证：三个层级各跑一遍 —— L1 纯指令能被 read_file 读到；L2 的 references/ 可达；L3 的脚本能在沙箱里直接 python 跑起来（这条最能证明这套路径是通的）。再加一条：改掉会话里的 SKILL.md 正文，只影响本会话，同 agent 的新会话仍拿到原版。

步骤 6 · K8s CSI

把宿主 ossfs 换成 CSI driver，Pod 保持 deny-all。属于执行环境那一期。

步骤 1–3 之后可以停一停

前三步完成的是结构拆分，行为不变、无新依赖 —— 可以单独合入并观察一个迭代。步骤 4 起才引入 OSS 与 FUSE 这两个新的基础设施依赖，风险与验证成本都上一个台阶。
