Detailed Design · acp Agent

acp Agent 详细设计

把 执行环境概设的 Bridge/Pod 链路落到 atlas 的现有骨架上。核心判断：acp 的 run 也是普通 run —— 会话、锁、事件、审批、子会话全部复用，整个 acp 只新增一个 AgentRuntime 实现和一个 Pod 内进程。

AgentRuntime 分岔Bridge 独立部署物atlas_acp 共享线协议caps: declared → probed

01定位与范围

native 已定型（子会话、文件系统、装配收进 server），接缝不会再跟着变 —— 概设里「等 native 定型后再写」的前提现在成立了。本文把三份概设的决定翻译成代码结构：

02复用面：acp run 也是普通 run

这是整篇详设最重要的一句话。atlas 现在的执行链路是：

load_for_execution → _prepare → mark_running     ← 与 agent 类型无关
┌─────────────────────────────────────────────┐
│ assembly.build → build_graph → runner.run    │  ← 只有这一段是 native 特有的
└─────────────────────────────────────────────┘
收事件 → persist → archive → 释放会话锁          ← 与 agent 类型无关

acp 的分岔点就是中间那一段。把它抽成协议，acp 只是第二个实现：

# server/executor/runtime.py —— server 内部的缝，不进 contracts
class AgentRuntime(Protocol):
    """在一个已就绪的 run 上执行一轮，产出事件流直到终态。"""
    def run_turn(self, prepared: PreparedRun, *, run_id: UUID) -> AsyncIterator[TraceEvent]: ...

class NativeRuntime:   # 现状代码原样搬入：build_graph + runner.run
class AcpRuntime:      # 本文主角：ensure pod → ensure session → prompt → 翻译事件
这个对称性买到了什么
  • 子会话零改动 —— 委派链路（task → DelegationProtocol → 子会话 → 子 run）不感知子 run 用哪个 runtime。acp 子智能体 = 子会话的 spec.kind 是 acp，仅此而已
  • 会话串行锁、幂等、SSE 回放、孤儿回收原样生效 —— 它们都挂在 run 的生命周期上，不挂在执行方式上
  • 前端一行不改 —— 事件契约（TraceEvent）不变。包结构设计那句「acp 接进来后 web 一行都不该改，否则是 translate 没翻译干净」在这里成为验收标准

两类 run 的差异被压缩成一张表：

NativeRuntimeAcpRuntime
模型上下文在哪message 表重建，压缩归平台CLI 进程内，压缩归 CLI
历史恢复每轮从 message 表重建loadSession(external_session_id)，能力位决定
工具平台装配（filesystem/sandbox/MCP…）CLI 自带 + MCP 列表下发
审批ApprovalMiddleware 拦 require_approval_forACP request_permission 回路（§07）
执行体本进程协程Pod（Bridge + adapter + CLI）
timeout / 取消runner 的 asyncio.timeout + CancelToken同一个 CancelToken → session/cancel

03包规划

关键的结构性事实：Bridge 跑在 Pod 里，是独立部署物（进 Pod 镜像，随 Pod 生灭），它和 server 必须说同一种线协议。共享的那部分抽成零重依赖的小包，两边分别依赖：

三条包边界，各有守卫

边界规则为什么
atlas_acp零重依赖（仅 pydantic），不认识 atlas_server / atlas_enginebridge 镜像要装它 —— 拖进 sqlalchemy 就把整个 server 依赖树带进了 Pod
atlas_bridge只依赖 atlas_acp；禁止 import atlas_serverBridge 与 server 的唯一接口是 WS 上的线协议。代码级共享会让「升级 server 必须同步升级全部在跑的 Pod」
acp/translate.py进 server 纯计算层 contract（与 domain / build / runner 同列）翻译是纯函数：一条 update 进、零或多条 TraceEvent 出 —— 它必须能脱离 WS 和 DB 单测，§06 的表就是它的测试用例
为什么 Bridge 不用 Node（adapter 是 npm 包）

adapter（如 @zed-industries/claude-code-acp）确实是 Node 生态，但 Bridge 与 adapter 之间是 stdio 上的 JSON-RPC，语言无关。Bridge 用 Python 换来的是与 server 共享 atlas_acp 的类型定义 —— 线协议两端用同一份模型解析，漂移在类型层就被抓住。Pod 镜像里 Node 只为 adapter 存在。

    ...
    kind: AgentKind = "native"     # ★ 有默认值 —— 历史快照反序列化照常（快照纪律）

server 侧的类与职责

修正：Pod 生命周期是**独立服务**，不是 server 的一个包

本文初稿把它放在 server/providers/pods/。实施时提成了独立的 cluster 服务，理由是初稿自己写过的那句：模板、创建、回收、卷分配、配额这些逻辑不是 acp 独有的 —— native 的 sandbox Pod 将来要一模一样的东西。放在 server 里会让「谁拥有 Pod 生命周期」有两个答案。

还有一条初稿没写到的：cluster 是全仓唯一需要 K8s 写权限的进程。独立之后那份 RBAC 只发给它一个，而不是发给整个 API 服务。

PodManager 沿用 SandboxManager 的三条纪律

① 状态从 K8s label 派生，不建 pod 表 —— 两处真相必然漂移，label（atlas/thread-id）是唯一账本；② 闲置 TTL 停不删，下次 acquire 快速恢复；③ 启动时 reap 扫孤儿（label 存在但 thread 已删）。这三条在 DockerSandbox 上已验证过一轮。

05线协议与能力位

WS 上跑的就是 ACP 的 JSON-RPC，Bridge 对 server 是透明管道加三件本地事务（鉴权、单活跃 prompt、优雅终止）。方法面收敛为五个 + 两类通知：

方向方法用途
server → bridgeinitialize握手后第一件事。回 AgentCaps：loadSession、sessionCapabilities.resume、fs.*、terminal
server → bridgesession/new建 CLI 会话，cwd=/workspace、MCP 列表随参传入 —— 不落盘（执行环境 §07：落盘文件在 Pod 重建时产生不可复现差异）
server → bridgesession/load恢复 external_session_id。仅当 caps 允许时调用
server → bridgesession/prompt一轮。终了回 StopReason：end_turn / max_tokens / max_turn_requests / refusal / cancelled
server → bridgesession/cancel取消当前轮（notification，不等响应）
bridge → serversession/update流式通知：§06 的全部输入
bridge → serversession/request_permission审批回路（§07）。★ 这是 bridge → server 方向唯一的请求（要等响应）

caps：declared → probed，两次落库

发布时（配置平面）   caps_declared ← 按 cli_type 的经验表推导（编辑器展示用）
首次连接（运行时）   caps_probed   ← initialize 的实测响应，落 agent_version 关联表
                     ★ 两者不一致 ⇒ 显式事件 caps.mismatch —— 比如 declared 说能
                       resume、probed 说不能：这决定 §10 里 lost 的触发路径
resume 是能力位，不是假设

Claude Code 的 adapter 可能声明 loadSession，Codex 的可能不声明 —— 同为 acp 类型，一个能无损恢复，另一个每次冷启动。Subagent §04 已把降级路径定死：不支持时标 lost 再新建，绝不静默新建 —— 用户以为在继续上次，CLI 实际从零开始，是最坏的失败形态。

07审批回路

native 的审批在 ApprovalMiddleware；acp 的审批是 ACP 的一等公民 request_permission。两条路在 server 汇入同一张 Approval 表、同一个前端弹窗：

CLI 要动危险东西
  → adapter 发 session/request_permission（带 toolCall 与选项列表）
  → Bridge 原样转交（红线：默认转交，绝不自动 allow —— 执行环境 §02）
  → AcpRuntime 落 Approval 行 + 发 approval.required 事件（含「请求来自哪个 agent」）
  → 用户在前端决定 → RedisApprovalGate 唤醒 → 决定沿原路回 CLI
  → 超时 = 拒（approval_timeout_s 与 native 共用同一配置）
差异点处理
ACP 的决定是选项列表（allow_once / allow_always / reject…），平台是二元（approve/reject）v1 只映射 allow_once / reject_once。★ 不透传 allow_always —— 「永远允许」是全局策略，必须过权限管理那一篇，不能从一次弹窗里溜进来
native 由 require_approval_for 白名单触发；acp 由 CLI 自己判断触发照实展示来源差异即可。acp 的 Pod 本身是隔离的（无横向网络、只读根、前缀限定凭证），审批是第二道闸不是唯一一道

08时序：Pod 供给与配对

09时序：一轮 prompt（含审批）

10时序：恢复、lost 与取消

WS 断线 ≠ 会话丢失

断线分两种，处置完全不同：连接层断（网络抖动、server 重启）—— Pod 还在、CLI 会话还在，重连 + session/load 即可，什么都不丢；Pod 层没（节点故障、OOMKill、闲置回收后镜像升级）—— CLI 进程状态没了，但状态目录在 NAS（执行环境 §04 选 NAS 而不是「退出前 sync」的原因正是这些不给机会同步的死法），新 Pod 挂同一卷后 session/load 仍可恢复。只有 caps 不支持 resume 或状态目录真损坏时才落到 lost。

12落地顺序

步骤 1 · atlas_acp 线协议包 + translate 纯函数

不碰任何执行链路。验证：§06 的表逐行成为 translate 的单测；未知 kind 不产事件但计数。

步骤 2 · AgentRuntime 接缝 + NativeRuntime 收编

executor/runtime.py 落地，inprocess 中段改调 runtime.run_turn。纯重构，acp 还不存在。验证：全量套件基线不变 —— 这一步的回归风险最高（动执行器主路径），单独合入。

步骤 3 · Bridge + 本地假 adapter 联调

bridge 进程 + 一个脚本化假 adapter（按剧本回 update 流），不需要 K8s：docker 起 bridge，server 直连。验证：配对拒绝无 token 的握手；单活跃 prompt 第二个请求 4409；假 adapter 崩溃 → run.failed(runtime_crashed)。

步骤 4 · AcpRuntime 端到端（仍用假 adapter）

spec.kind=acp 的 agent 全链路：prompt → update 流 → SSE → 前端。验证标准就是那句话：web 一行不改。加审批回路：request_permission → 弹窗 → 决定回传。

步骤 5 · PodManager + 真 CLI

K8s 模板、配对 Secret、真 Claude Code adapter。验证：执行环境 §12 的待验证清单（resume 真实可用性、状态目录 NAS 恢复、优雅终止三步）。

网络取开放策略：不加 NetworkPolicy —— adapter 本来就要出网（拉依赖、调模型网关、访问用户给的 API），限制入口只会把一类正常需求变成难查的超时。因此入口的唯一闸门是握手上的 per-Pod token，不是网络位置：K8s 的网络是平的，"在集群里"从来不是安全边界。

修正：真集群 + 真对象存储跑通后的五处返工

本节与 §04、§08 写的 Pod 模型，在对着 k3s 与真 GCS 跑通之前有五处是错的。它们的共同点是内存后端全都测不出来 —— 那个后端只把 manifest 当字典存起来，既不校验字段，也没有"启动"这个概念。

  1. 双 subPath 挂不了 FUSE。subPath 是 kubelet 在容器启动时做的 bind mount，不跟随之后在卷里建立的 FUSE 挂载 —— 主容器看到的会一直是空目录，而且不报错。现在改成两个共享卷 + 两个挂载器 sidecar，挂载语义（workspace 挂父会话、skills 挂自己且只读）不变，只是落点从 subPath 换到了 rclone 的 remote 路径。
  2. 挂载凭据根本没传。CSI 卷只写了 bucket 与 path，没有任何 nodePublishSecretRef；也就是说这条路在任何真集群上都不可能挂成功。
  3. Pod 地址指向一个不存在的 Service。_url 返回 ws://<pod>.<ns>:8900，注释写着"由 cluster 侧的 Service 兜底"，而那个 Service 从来没有被创建过。现在直接用 Pod IP。
  4. ensure 不等 Pod 就绪。它在 Pod 还处于 ContainerCreating 时就把 URL 与 token 交给 server，而 AcpChannel 的连接超时只有 10s 且不重试 —— 每个新会话的第一轮必然失败，报的还是"连不上 bridge"，一个看起来像网络问题的调度问题。
  5. 只写 runAsNonRoot 会让 Pod 起不来。没有具体 runAsUser 时，kubelet 无法在启动前判定镜像是否 root，除非镜像自己在 USER 里写了数字 UID，否则一律 CreateContainerConfigError。这等于把"镜像必须声明数字 USER"变成一条不成文要求，而违反它的表现是 Pod 根本起不来。

另有两处只在真跑时才会暴露：rclone 默认拒绝挂到"已是挂载点"的目录上（需 --allow-non-empty，否则整个 Pod 卡在 Init:CrashLoopBackOff）；Pod 的 Ready 在没有 readinessProbe 时只代表"容器进程起来了"，而 bridge 还要拉起 adapter 才会 bind 端口 —— 那几秒是个稳定复现的竞态。

这批问题与上一轮 InMemoryBackend 掩盖三个 K8s bug、moto 掩盖 GCS 校验和 bug 是同一件事的第三次重演：模拟器测的是"我以为的协议"，真服务测的是协议本身。

接真 Claude Code CLI：又两处，其中一处是整个方案的地基

假 adapter 按剧本回话，它不调模型、不写状态、不实现 resume。换成真 @zed-industries/claude-code-acp（模型走 DeepSeek 的 Anthropic 兼容端点）之后：

  1. 模板没有 adapter 的凭据通路。它只注入 ATLAS_*，于是真 CLI 拿不到任何模型配置，session/new 直接失败。现在按 cli_type 注入（claude-code ⇒ ANTHROPIC_BASE_URL / ANTHROPIC_MODEL / ANTHROPIC_SMALL_FAST_MODEL，凭据走 Secret）。小模型也要一起指过去 —— 不指的话 CLI 会去找端点上不存在的 haiku，失败发生在生成标题这类旁路上，很难联想到模型配置。
  2. CLI 的状态目录必须持久化，否则 resume 是假的。Claude Code 把会话记录写成 ~/.claude/projects/<cwd-slug>/<sessionId>.jsonl。HOME 放 emptyDir 的话，resume 只在 Pod 活着时成立 —— 而 Pod 会被闲置回收，于是表现成悄悄失忆：恢复"成功"了，但上一轮不见了。现在多挂一个 /state（会话自己的 system/cli-home 前缀）。所幸那是纯 JSONL 而不是 SQLite，挂在对象存储上没有文件锁问题。

已验证：session/load 恢复上一轮上下文 —— 同一个 Pod 内（含另起一个 adapter 进程）CLI 确实记得上一轮的暗号。

跨 Pod 重建的 resume：通了，但踩到一条值得记住的坑

删掉 Pod、重建、session/load 同一个 sessionId —— CLI 记得上一轮的暗号，恢复的依据只可能是桶里那份 HOME。这是 §01 那句"第二次委派时 CLI 记得上次改过什么"第一次真正被证明。

但它一开始三次里挂两次，真因是：对象存在 ≠ 已经持久化。rclone 会先把一个不完整的版本传上去（实测 139 字节），随后才用完整的覆盖（2124 字节）。撞在中间那段时间重建，新 Pod 拿到的是个截断的会话记录，而 --resume 读它会让 CLI 子进程直接退出 —— adapter 报的是 Query closed before response received，一句完全看不出"文件是半截的"的话。

排查时我差点得出错误结论：在另一次运行里量到文件是完整的，就以为截断已被排除，转而去怀疑 FUSE。跨运行拼观测在这种时灵时不灵的问题上不成立 —— 每一条证据都得来自同一次失败。

镜像已构建，最后一块替身拆掉了

docker/bridge/Dockerfile 把 node、adapter 与 bridge 打进一个镜像（Python 3.14 + Node 24，同一个 Debian trixie 基础 —— 跨版本拷 node 会缺 libatomic，而它的表现是容器起来之后 adapter 才报"找不到共享库"，离根因很远）。判据是 Pod spec 里一个 hostPath 都没有：还挂着的话，跑的就仍然是宿主上那份 node 与 CLI，依赖、入口点、数字 UID 全都绕过去了。这条判据本身也有测试钉着。

构建走 make bridge-image（BuildKit 独立二进制 → OCI 归档 → ctr import）。这套环境里没有 docker 守护进程，而镜像是本地构建的、registry 上不存在，所以 Pod 必须靠 import 而不是 pull。

顺带修掉一个假阳性：判断"镜像在不在"原先用的是 crictl images -q <ref> —— 它根本不过滤，给个不存在的名字也照样列出所有镜像。拿它当判据，只要节点上有任意镜像就会判成"生产镜像已就绪"，于是测试会声称自己跑的是生产镜像、实际跑的是 hostPath 那套。这种假阳性比直接失败坏得多：它让"没验过"看起来像"验过了"。改用 crictl inspecti。

另一个已知窗口：rclone 的回写有延迟（--vfs-write-back，已从默认 5s 收到 1s）。文件关闭到真正上传之间数据只在容器本地，这期间 Pod 被突然杀掉会丢掉最后一轮的记录，而丢法是静默的。实测还看到对象会先以不完整的大小出现、随后才被完整覆盖 —— 所以"对象已存在"不能当作"已经持久化"来用。

步骤 6 · acp 子智能体

native 主 agent 委派给 kind=acp 的子智能体（「让 Claude Code 去改这三个文件」）。验证：第二次委派 CLI 记得上次改过什么；不支持 resume 的 CLI 标 lost。

修正：不是「零新增」

初稿说这一步机制上零新增。实施时发现两处必须补：

  • build_graph 只被 NativeRuntime 调用 ⇒ acp agent 永远拿不到 task 工具，它配的 subagents 会被静默忽略。现在 validate 直接拒（§13.2 不许「配了却不生效」）
  • spec_for_subagent 原先硬编码 kind=parent.kind ⇒ native 父只能产出 native 子，acp 子智能体根本造不出来。SubAgentSpec 因此加了自己的 kind / cli

补完之后委派链路本身确实一行未改 —— 子会话也是 thread，AcpRuntime 对它原样生效。§02 那条对称性成立，只是它保证的是「链路不用改」，不是「什么都不用加」。

adapter 行为漂移CLI/adapter 升级后 update 形态变化，翻译静默丢事件未知 kind 计数指标 + 告警；Pod 镜像钉版本（cli/adapter/bridge 三件套一起发版）

Pod 供给延迟首轮 prompt 等 Pod 调度 + 镜像拉取，可达分钟级会话创建即预热 Pod（与技能拷贝同时机 —— 用户对「新建会话」的等待容忍度更高）；镜像预拉节点

acp agent 用平台内置工具CLI 自带文件/命令工具，平台工具对它没有意义；能控的只有 MCP 列表与审批闸门（Agent 管理 §05）
