Detailed Design · Subagent

Subagent 重新设计

从「每次委派都从零开始」改成「子智能体持有自己的会话」。第二次委派给同一个子智能体时恢复上次的上下文，任务因此有连续性 —— 而 ACP 的 loadSession 正好需要这样一个可寻址的会话。

子会话 = thread工作区读共享 · 写隔离技能独立前缀Pod 挂载参数化

01诉求改变了什么

现在（一次性）改造后（会话级）
第二次委派从空上下文开始，只有任务书恢复上次的会话
上下文`[HumanMessage(description)]` 一条子会话的完整历史
ACP 恢复做不到 —— 没有可寻址的会话loadSession(sessionId)
技能无（kernel 支持，atlas 没接）子智能体有自己的一套
并行随便并 —— 无状态同名必须串行
这是个方向性的改变，不是加功能

「独立上下文」这四个字的含义变了：从每次都空变成与主线程分开、但自身连续。收益是不用反复交代背景，代价是上下文会增长、并行会冲突、上次的错误认知会带到下次。§11 逐条列了这些。

驱动它的是 ACP

native 子智能体干的是「读几个文件做个分析」—— 一次性完全够用。真正需要连续性的是 acp 助理：

第 1 次委派：「把 auth 模块迁到新 token 格式」
            → CLI 起来，读代码，改了 12 个文件，跑测试，3 个失败

第 2 次委派：「那三个失败的用例修一下」
            ┌ 一次性模型：CLI 重新起，空上下文 —— 它不知道「那三个」是哪三个，
            │            也不知道刚才改过什么，只能重新读一遍代码
            └ 会话级模型：loadSession → CLI 记得自己改了什么、为什么失败

一次性模型下，用户只能把上一轮的结论复制进任务书 —— 而那正是 CLI 已经知道、却被丢掉的东西。

02核心决定：子会话是 thread，不是 run

「子智能体有自己的会话」落到数据模型上有两个候选，选哪个决定了后面所有事：

候选问题
子会话 = 一串关联的 runrun 是「一轮对话」，没有跨轮的身份。要表达连续性得靠 parent_run_id 串成链，而「第二次委派恢复哪条链」没有自然的键
子会话 = thread—— 选这个

thread 本来就是「一段有历史的对话」：有 message 序列、有摘要边界、有压缩计数、有标题。子智能体需要的正是这些。

# thread 加两列
parent_thread_id: UUID | None   # NULL = 用户会话；非空 = 某个会话的子智能体会话
subagent_name:    str | None    # 与 parent 组成唯一键

# 恢复的查找键就是它
UNIQUE (parent_thread_id, subagent_name)
为什么这个键是对的

「下次再委派到这个 subagent 时恢复」—— 恢复的依据就是哪个父会话 + 哪个子智能体。不需要发明新的标识：两者都是已有的东西。

三层关系

用户会话 thread A parent_thread_id = NULL │ ├─ run #1 ─ run #2 ─ run #3 … 用户与主 agent 的对话轮次 │ ├─ 子会话 thread A/researcher parent=A, subagent_name=researcher │ └─ run ─ run … 每次委派一个 run │ └─ 子会话 thread A/coder parent=A, subagent_name=coder └─ run ─ run … ★ 子会话的 message 与主线程**完全分开** —— 这就是「独立上下文」的持久化形态。 主 agent 看到的只有每次委派的最终结论（ToolMessage）。

03三条边界

「隔离」这个词要拆开说 —— 三样东西的隔离程度不同，混为一谈会做错。

隔离程度理由
上下文完全隔离子会话有自己的 message 序列。委派的价值之一就是不让子任务的中间过程污染主对话
工作区读共享，写隔离委派常常就是「帮我处理这批文件」，产物要互相看得见；但并行的子智能体不能互相覆盖
技能完全隔离
（独立前缀）		技能是能力配置，跟 agent 走

OSS 布局：三个平级前缀

{bucket}/{user_id}/{thread_id}/workspace/    ← 可被子智能体共享挂载
{bucket}/{user_id}/{thread_id}/skills/       ← 恒为自己的
{bucket}/{user_id}/{thread_id}/system/       ← 恒为自己的（压缩归档、大结果外置）
★ 技能必须与 workspace 平级，不能放在它里面

因为 workspace 是共享挂载的。子智能体的 Pod 挂的是主 agent 的 workspace —— 技能若住在里面，挂载时会连主 agent 的技能一起带上。

早先设想用 workspace/.skills/<agent-name>/ 分目录解决，那只是约定：子智能体照样读得到、改得动别人那份。平级前缀是结构性的 —— 挂载根本带不上。

三个前缀，两种 thread 来源

# 主 agent（会话 A）
workspace → {user}/{A}/workspace      skills → {user}/{A}/skills

# 子智能体 coder（子会话 B，父是 A）
workspace → {user}/{A}/workspace      ← 父的
skills    → {user}/{B}/skills         ← 自己的
system    → {user}/{B}/system         ← 自己的
所以 Pod 的挂载必须参数化

不能由「Pod 属于哪个会话」一个参数派生全部挂载。Pod 模板要接两个 thread id：

/workspace ← subPath {user}/{workspace_thread_id}/workspace
/skills    ← subPath {user}/{thread_id}/skills

workspace_thread_id 对主 agent 等于自己，对子智能体等于父会话。这条是 文件系统改造 §05 里 Pod 模板参数化的直接来源。

写隔离：靠挂载，不靠约定

工作区共享读之后，并行的子智能体会并发写同一份数据。而 OSS 没有文件锁、写是整对象 PUT —— 后写的完整覆盖先写的，没有任何提示。

# 共享区只读挂载，自己的写入区嵌套在内层且可写
volumeMounts:
  - mountPath: /workspace
    subPath:   {user}/{workspace_thread_id}/workspace
    readOnly:  true
  - mountPath: /workspace/.agents/coder          ← 嵌套，内层可写
    subPath:   {user}/{workspace_thread_id}/workspace/.agents/coder
    readOnly:  false

挂载点彼此独立，内层可写不受外层 readOnly 影响。于是：

  • 读 —— 子智能体看得见父与兄弟的全部产物
  • 写 —— 只能写自己那块，内核层面拦住，不是提示词
  • 交付 —— 父读 .agents/coder/ 取产物；合并进主工作区由父决定，这正是委派该有的语义
native 子智能体同理，且 execute 管不住

FilesystemPermission 能对文件工具做同样的事，但对 execute 完全不生效 —— _create_execute_tool 里零个权限检查（kernel 分析 §04）。所以配了 bash 的子智能体，写入隔离只能在挂载层做。

两条路殊途同归：结构性的写隔离必须靠挂载。

.agents/ 与技能一样点开头 —— search("") 默认跳过（§04），主 agent 列工作区时不会被子智能体的中间产物淹没。

子智能体的技能从哪来

@dataclass(frozen=True)
class SubAgentSpec:
    name: str
    description: str
    system_prompt: str
    model: ModelSpec
    tool_names: tuple[str, ...] = ()
    #: ★ 新增。与主 agent 的 skills 同构：(slug, version) 钉死。
    skills: tuple[SkillRefSpec, ...] = ()

子会话创建时按自己的 thread_id 拷进 {user}/{B}/skills/。同一个技能被主 agent 和子智能体同时引用时拷两份 —— 冗余可接受，换来的是各自改动互不影响。

04恢复：两条路

子会话存在 ⇒ 恢复。但 native 与 acp 的恢复机制完全不同 —— 这正是 type 这个字段存在的意义。

native：历史从 message 表重建

# 与主 agent 完全同一条路径（inprocess.py::_prepare）
rows = await RunRepository(session).history(sub_thread.id, after=sub_thread.summary_upto)
history = [_to_lc(m) for m in rows]
if sub_thread.summary:
    history.insert(0, AIMessage(content=SUMMARY_PREFIX + sub_thread.summary))

没有新机制 —— 子会话就是个 thread，Message 为事实源这条纪律原样适用。压缩、摘要边界、标题生成全部复用。

acp：loadSession

# thread 再加一列：CLI 侧的会话标识
external_session_id: str | None

# 委派时
if sub_thread.external_session_id and caps.resume_session:
    await bridge.load_session(sub_thread.external_session_id)   # ACP loadSession
else:
    sid = await bridge.new_session(cwd="/workspace")          # ACP newSession
    sub_thread.external_session_id = sid
恢复是能力位，不是假设

loadSession 是 ACP 里 adapter 可选声明的能力。Claude Code 的 adapter 可能有，Codex 的可能没有 —— Agent 管理里 caps.resume_session 走握手探测，正是为此。

不支持时降级为新建会话，并且必须让用户看见：子会话的状态标成 lost，而不是假装恢复了。原型里那条 codex 的 lost 状态就是这个场景。

什么时候不该恢复

class TaskToolSchema(BaseModel):
    description: str
    subagent_type: str
    #: ★ 显式要一个干净的开始。默认恢复 —— 连续性是本次改造的目的。
    fresh: bool = False

用途是「上一轮把它带偏了，重来」。fresh=True 时归档旧子会话（status='archived'）并新建一个，而不是删 —— 历史不该因为一次重来就消失。

05流程时序

首次委派

只有第 5–7 步是新建路径。第二次委派时这三步被一次 SELECT 命中替代，其余完全相同 —— 这正是「子会话 = thread」带来的对称性。

第二次委派：两条恢复路径

静默新建是最坏的失败形态

用户以为「接着上次继续」，CLI 实际从零开始 —— 它会重新读一遍代码、重新问一遍已经回答过的问题，而事件流上看不出任何异常。所以 lost 必须是一个可见的状态，不是一条日志。

并行与同名冲突

这条约束不是新发明的规则：子会话也是 thread，会话串行锁原样适用。工具层的拦截只是把一个必然发生的冲突提前到调用时暴露。

06执行：子 run 与准入

子会话有了之后，「一次委派」自然就是子会话上的一个 run：

task(description, subagent_type)
   ↓ 解析/创建子会话 thread（父 + name 唯一）
   ↓ 在 run 表建行：thread_id = 子会话, parent_run_id = 发起者
   ↓ executor.submit() —— 走与普通 run **完全一样**的链路
   ↓ 父 await 它到终态
   ↓ 取最终文本作为 ToolMessage
这样白拿到四样东西
  • 事件流 —— 子 run 有自己的 run_id，前端能完整展开。现在子智能体的内部步骤是 depth=1 的受限视图
  • 审批 —— Approval 表本来就是 run 级的，子 run 的审批天然可寻址
  • 取消 —— 走已有的 RedisCancelToken，父取消时级联
  • 孤儿回收 —— reap_orphans 天然覆盖。执行体在表里可见，不是藏在内存 registry 里

父仍然等

委派的语义就是「我需要这个结论才能继续」。§11 说明了 deer-flow 在同样的问题上也是等的 —— 它那套隔离执行体买的是故障隔离，不是让模型能同时干别的。

准入控制：全局，不是每 run

# 子 run 的准入与普通 run 分开计
subagent_max_running: int = 3     # 全进程同时执行的子 run
subagent_max_per_run: int = 6     # 单个父 run 累计委派次数

第二个数防的是一种绕过：长 run 在每个规划点发起一批「合法尺寸」的委派，累计起来远超并发限制。deer-flow 用持久委派账本挡这个，我们查 run 表里 parent_run_id = 当前 run 的行数即可 —— 不用新表。

acp 子智能体吃 Pod，准入必须是全局的

Pod 是有限资源。按 run 各自限流的话，10 个并发会话每个委派 2 个 acp 子智能体 = 20 个 Pod。全进程一个闸是必须的。

三条派生规则

1  parent_thread_id IS NOT NULL ⇒ 该 thread 不出现在用户的会话列表
2  子 run 不争父会话的串行锁 —— 它是父 run 的一部分
3  子会话**内部**仍然串行 —— 见 §07

07并行的结构性约束

同一个子智能体不能并行委派

一次性模型下子智能体无状态，随便并。会话级模型下它有状态 —— 同一轮里对 researcher 发两个 task，两者都要恢复同一个子会话，写回时互相覆盖。

这条约束不用新发明：子会话也是 thread，会话串行锁原样适用。第二个并发委派会撞到 ThreadLocked。

但不能让模型撞了才知道。两层处理：

1 工具层：同一轮里出现重复的 subagent_type，第二个直接返回可操作的错误
     「researcher 已在本轮中被委派。子智能体持有会话，同名委派必须串行 ——
       把两个子任务合并成一次，或改派给不同的子智能体。」

2 提示词层：task 的工具描述写明这条，并给出可行的并行形态
     「并行委派只能给**不同的**子智能体。」

这反而让并行的语义更清楚

形态可否并行
researcher + coder + reviewer可以 —— 三个不同的子会话
researcher × 3（三个子任务）不可以 —— 同一个子会话

deer-flow 那条「可变状态重叠 ⇒ 硬否决并行」的经验规则，在这里变成了结构性约束：不是靠提示词劝阻，是锁会拦住。

08上下文增长

连续性的代价是上下文只增不减。第 10 次委派给 coder 时，它的会话里已经有 9 轮历史。

native：压缩机制原样复用

子会话是 thread，thread.summary / summary_upto / compact_count 三列都在，CompactionMiddleware 直接可用。一行新代码都不用写 —— 这是「子会话 = thread」这个选择最实在的回报。

但压缩配置该独立

子智能体的会话性质与主会话不同：它是「一个专项任务的连续记录」，而主会话是「用户与顾问的往来」。主会话的 trigger_ratio=0.75 未必适合。

建议 SubAgentSpec 加一个可选的 compaction，缺省继承主 agent 的 —— 与 model 的处理方式一致。

acp：压缩归 CLI

上下文在 CLI 进程内，Claude Code 有自己的压缩。平台侧不介入，只在 caps.compact 上标明这一点（Agent 管理的能力推导：compact = is_native and spec.compaction.enabled）。

一个必须给出的出口

会话越长，恢复越贵、越容易被旧结论带偏。fresh=True（§04）是模型可用的出口；界面上也要能看到子会话的轮次与 token 累计，让用户能主动重置。

09代码机制：hook 与 delegate

前面几节说的是「应该怎样」。这一节说代码里实际是怎么接起来的 —— 一次 task 调用从主图出发，经过哪几个对象，最后变成子会话上的一个 run。

一句话

engine 只认识一个回调，server 是它唯一的实现。engine 不知道「子会话是一行 thread」，server 不知道「图是怎么跑的」—— 这条缝就是 Delegate。

注入链路：能力从哪来，到哪去

装配曾经分两层：server 的 HookAssembly 收集能力对象装进 RunHooks，engine 的 build_agent（防腐层）再把 spec+hooks 排成中间件栈。kernel 永久内化之后防腐失去对象，两层合一：装配策略整体收进 server（build.py），engine 只剩词汇（spec/events）与执行循环（runner）。RunHooks 随之溶解 —— 能力对象直接进中间件构造，runner 只留 cancel / clock / titler 三个自己消费的注入点。

HookAssembly.build() server —— IO 的收集：连对象存储、起沙箱、建 Redis 门禁 └─ build_graph(spec, model, …) server/executor/build.py —— 装配策略与顺序的唯一住所 filesystem = OssFilesystem(…) sandbox = DockerSandbox(…) approvals = RedisApprovalGate(…) compactor = CompactionMiddleware(…) kernel/middleware —— 全部中间件的家 subagents = SubagentService(…) ★ DelegationProtocol 的实现 └─ create_deep_agent(…, subagent_delegate=…) └─ SubAgentMiddleware → task 工具 → await gateway.delegate(brief, name, fresh=…) │ ▼ runner.run(spec, run_id, graph, input, history, cancel/clock/titler) server/executor —— 执行循环与事件推导
委派是唯一形态 —— 其余三种子智能体实现已整体删除

曾经并存四种执行形态，现在只剩委派一种。删掉的三种与理由：

形态为什么删
图内 SubAgent（编译子图、主图协程里 ainvoke）每次委派从空上下文开始，且需要一套平行的治理装配（子图审批 / 子图步数刹车 / 子图白名单）—— 与子 run 天然继承的同一批守卫重复，两份语义必然漂移
CompiledSubAgent（调用方自带 runnable）同上，且状态合并的两层黑名单（_EXCLUDED_STATE_KEYS / private_state_keys）只为它存在
AsyncSubAgent（langgraph_sdk → LangSmith 部署）Atlas 不用 LangSmith。将来的远程形态是 acp 子智能体 —— 它走的正是委派这条路（子会话 + AgentRuntime），不需要第二种远程机制

连带删除：general-purpose 自动补齐、GeneralPurposeSubagentProfile 配置面、kernel 的 async_subagents 模块。SubAgentMiddleware 的 delegate 参数从可选变为必填；配了子智能体不注入受理方，engine 的 build_agent 直接 InvalidSpec。多一种执行形态就多一套要维护的治理语义 —— 而那些守卫在「子 run 是普通 run」的模型下是免费继承的。

DelegationProtocol：三个标量进，一段文本出

# 定义在 atlas_engine.contracts（架构最底层）—— kernel 与 server 都向下依赖它
class DelegationProtocol(Protocol):
    async def delegate(self, task: str, name: str, *, fresh: bool = False) -> str: ...
#                          ↑任务书      ↑子智能体名        ↑重开一轮       ↑最终文本

与 FilesystemProtocol / SandboxProtocol 并列的第三个能力协议。刻意一个对象管全部子智能体，不是每个子智能体一个 handle：准入、同轮去重、并行约束都是跨智能体的关切，拆成 per-agent 对象就没有地方放它们了；名录的权威也不在协议上 —— 有哪些子智能体由 spec（版本快照）回答，协议只负责执行。

形状是刻意压到最小的。三个参数全是标量、返回值是纯文本 —— 这意味着：

约束换来什么
不传图状态进去子会话的输入只有任务书那一段文本。「独立上下文」因此是结构性的，不靠调用方自觉过滤 —— 图内那条路要用 _EXCLUDED_STATE_KEYS + private_state_keys 两层黑名单才做到同一件事
不返回 Command子会话的状态不合并回主图。主线程只看见结论，这正是委派该有的语义（§02）
不传 DB 句柄 / thread idengine 保持对数据库无知。tests/test_engine_purity.py 那条「engine 不许 import sqlalchemy」的守卫不用开口子
注入 delegate 时，子智能体图完全不编译

这一点容易被当成性能优化，其实是正确性问题。子智能体的配置会在子 run 里重新装配一遍（下面的 spec_for_subagent）。若同时还在主图里编译一份，「这个子智能体到底用哪个模型、哪些中间件」就有了两个答案，而它们会随代码演进悄悄分叉。

所以 create_deep_agent 在委派模式下跳过整个 per-spec 装配循环，只取 name / description 去拼 task 的描述。顺带也不补 general-purpose 子智能体 —— 它在 server 的 AgentSpec 里没有对应配置，委派过去必然失败，而模型看得见它就会去试。

spec_for_subagent：对称性的来源

「子会话 = thread」这个决定的全部回报，兑现在这一个函数上：

def spec_for_subagent(parent: AgentSpec, name: str) -> AgentSpec:
    sub = parent.subagent(name)          # 找不到 ⇒ InvalidSpec，不回落
    return AgentSpec(
        slug   = f"{parent.slug}/{sub.name}",   # 日志里一眼看出是谁的哪个
        model  = sub.model,
        tool_names = sub.tool_names,
        skills = sub.skills,                     # ★ 技能跟着子智能体走
        subagents = (),                          # ★ 深度封顶，保险一
        limits = replace(parent.limits, max_subagent_depth=0),  # 保险二
        compaction = sub.compaction or parent.compaction,
    )

它返回的是一份完整的 AgentSpec，不是半个配置对象。于是执行器不需要为子 run 开任何分支 —— _prepare() 里只是换了一份 spec：

# server/executor/inprocess.py::_prepare
spec = _spec_from_version(version, slug=slug, name=name)
if thread.subagent_name:                      # ← 全部的分支就这两行
    spec = spec_for_subagent(spec, thread.subagent_name)
这两行之后的一切都是免费的

历史从 message 表重建、摘要回填、压缩中间件、步数刹车、工具并发熔断、审批门禁、取消令牌、用量入账、事件归档、孤儿回收 —— 子 run 走的是同一段代码。§02 里「子会话 = thread 而不是 run」的论证，落地之后就是这两行。

SubagentService：一次委派的完整代码路径

它是 Delegate 唯一的实现，也是整个系统里唯一知道「子会话是一行 thread」的地方。生命周期绑定一次父 run，不是进程级单例 —— 因为 _inflight 记的是「本轮已经派给谁了」，而「同一轮」正是一个 run。

async def delegate(brief, name, fresh):
    sub = spec.subagent(name)                       # ① 名字不存在 → 可操作的错误

    if persistent and name in _inflight:            # ② 同轮重名 → 拒，不等锁超时
        raise DelegationRejected(…)
    _inflight.add(name)                             #    ★ 占位必须在任何 await 之前

    await _check_admission(name)                     # ③ 全局并发 + 本 run 累计

    thread_id = await _resolve_thread(sub, fresh)   # ④ 命中已有 = 恢复；否则新建 + 投技能
    if not await relay.acquire_thread_lock(thread_id, owner=run_id):
        raise DelegationRejected(…)                 # ⑤ 子会话也是 thread，串行锁原样适用

    await runs.create(thread_id=子会话, parent_run_id=发起者)
    await threads.add_message(子会话, role="user", content=brief)   # ⑥ 任务书入 message 表
    await executor.submit(child_run_id)              # ⑦ 与用户发起的 run 同一条链路

    return await _await_result(…)                   # ⑧ 轮询终态 + 级联取消

第 ⑥ 步值得单独说：任务书写进子会话的 message 表，而不是作为参数直接丢给图。原因是 Atlas 没有 checkpointer，历史每轮从 message 表重建 —— 任务书不落表的话，第二次委派时重建出来的历史里会缺掉「上次让它干什么」，只剩它自己的回答。

两个只有跑真实链路才会暴露的坑

坑一：子 run 继承了父 run 的流式上下文

委派让 executor.submit() 第一次可能在另一个 run 的执行上下文里被调用。而 asyncio.create_task 默认拷贝当前 contextvars，langgraph 的流式输出与 langsmith 的追踪都挂在 contextvar 上。

后果：子 run 的 token 被写进父 run 的流通道，子 run 自己一个 message.delta 都不产出，落库的 assistant 消息是空的。而 run 状态一路 succeeded、模型确实被调用过、日志里毫无异常 —— 排查起来极费劲。

asyncio.create_task(self._guarded(run_id), context=contextvars.Context())

语义上这也正是对的：子 run 是独立可寻址的执行，不该继承发起者的任何环境。

坑二：同轮重名的拦截被一个 await 击穿

模型在一个 turn 里发两个 task 是并发执行的。原先的顺序是「查 _inflight → await 准入查询 → 加入 _inflight」—— 两个协程都能在对方占位前通过检查，于是同名委派照样起了两个子 run，拦截形同虚设。

修法是把占位提到任何 await 之前。单线程事件循环里，检查与占位之间没有 await 就没有交错点。这类 check-then-act 竞态在 asyncio 里格外隐蔽：代码看着是同步的。

错误怎么回到模型

DelegationRejected 的消息是给模型看的，所以每条都必须可操作 —— 说清原因，并给出下一步：

"coder 已在本轮中被委派。子智能体持有会话，同名委派必须串行 ——
 把两个子任务合并成一次，或改派给不同的子智能体。"

"当前已有 3 个子智能体在执行（上限 3）。稍后重试，或先自己处理一部分。"

kernel 侧的 task 工具把异常接成工具错误文本，不让它冒泡：

try:
    return await delegate(brief, name, fresh)
except Exception as exc:
    return f"委派给 {name} 失败：{exc}"
为什么不冒泡

撞并发上限、同轮重名都是可恢复的局部问题：主 agent 能改派、把两个子任务合并、或者干脆自己动手。让它冒泡等于把一次局部问题升级成整个 run 失败 —— 用户看到的是「这轮对话崩了」，而实际上只是委派排队了。

task 的描述也必须改

kernel 默认那份描述写着 Each invocation is stateless —— 会话级模型下这句恰好说反了。说反的代价很具体：模型会把上一轮的全部背景重新抄进任务书（白付 token），或者以为并行委派同一个子智能体是安全的（会撞会话串行锁）。所以委派模式用另一份描述，三句话是必须的：

- Each subagent remembers your previous delegations to it.
- Parallel delegation only works across different subagents.
- Pass fresh=true to discard its session and start over.

11与 deer-flow 相反的选择

deer-flow 的子智能体是严格一次性的：每个 task run 拿到一个全新的 ThreadState。这是个深思熟虑的选择，不是疏漏。所以这里要说清楚我们为什么反着来。

deer-flow（一次性）本设计（会话级）
第二次委派全新上下文恢复
并行随便并（无状态）同名串行
重试干净 —— 重试看不到上次的失败会看到上次的痕迹
污染风险无上次的错误认知会带到下次
ACP 恢复做不到这是驱动因素
分歧的根源：子智能体干的活不一样

deer-flow 的子智能体是 general-purpose / bash 这类通用执行体 —— 一次性是对的，因为每个任务彼此无关，无状态换来可并行、可重试、无污染。

我们的 acp 子智能体是带着 CLI 的助理，它在同一个代码库上连续工作。「把 auth 模块迁完」和「修那三个失败用例」是同一件事的两个阶段 —— 丢掉中间状态意味着每次重新读一遍代码。

因此保留一次性作为选项，而不是删掉它

# SubAgentSpec 加一个模式位
session_mode: Literal["persistent", "ephemeral"] = "persistent"

ephemeral 的子智能体每次新建子会话、跑完归档 —— 于是可以并行（每次一个新 thread，不撞锁）。适合「并行调研五个选项」这类任务。

两种模式共用同一套机制，差别只在「委派时查不查已有子会话」。

实施回顾：步骤 1 最终没有单独合入

原计划让它先走 —— 它不碰执行模型，纯粹是技能投送多一个维度。实际做下来它依赖步骤 2：「子智能体的技能落在不同的 thread 前缀下」这条验收标准，在子会话不存在时根本没有第二个 thread 可用。图内执行模型下只能退回成 workspace/.skills/<name>/ 这类约定，而 §03 花了整节论证约定不够。于是两步一起合。

步骤 2 确实是重心与风险所在：它同时动数据模型、kernel 的工具实现、和执行链路。两个真实的坑都在这一步（§09），且都只有跑真实链路才暴露 —— 静态检查与单测全绿。

14风险与不做的事

三个真实风险

风险表现处置
状态污染上一轮把子智能体带偏了，之后每一轮都在错误前提上继续fresh=True；界面显示子会话轮次让用户能主动重置
重试语义变了一次性模型下重试是干净的；现在重试会看到上次失败的痕迹不一定是坏事（知道试过什么），但要在文档里写明差异，别让人以为重试等于重来
删除影响面变大删一个会话会级联删掉所有子会话的 message / run / run_event删除确认要显示子会话数量与总轮次

明确不做

不做理由重新考虑的信号
非阻塞委派需要跨轮传句柄（无 checkpointer，得落表）、结果回来的通知机制、以及改会话串行锁。而委派的语义就是「我需要这个结论」量到 task 的 P95 超过 60s
子会话完全独立的工作区产物就得靠返回值搬运，而返回值是一段文本。读共享 + 写隔离（§03）比两个极端都好：读得到，写不乱永不 —— 真要更严就收紧挂载，不是切前缀
子智能体再委派深度仍然结构性封顶在 1。会话级模型下嵌套会让「哪个会话恢复哪个」变成一棵要遍历的树永不
照搬 deer-flow 的隔离事件循环它买的是故障隔离，而「子 run」已经天然具备：独立 run_id、独立取消令牌、reap_orphans 覆盖永不
验收标准与凭据核验

三条可以先摘的低成本改进

与本设计无关，来自 deer-flow 的对照，改动都很小：

  • 委派成本论证进 task 的工具描述 —— 零成本，直接减少无谓委派
  • stop_reason 用附加字段 —— 现在 subagent.finished 只有 failed 布尔，「撞上限」与「真失败」分不开
  • turn budget 按中间件链深度换算 —— StepLimitMiddleware(max_steps) 数的是步，而每个中间件钩子编译一个节点；子智能体装了三层中间件，实际可用步数比配置的少，这个偏差现在是隐性的
