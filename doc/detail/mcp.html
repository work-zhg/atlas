Detailed Design · MCP

MCP 接入详细设计

把 MCP 管理概设落到 atlas 现有代码上。核心判断：发现与调用必须分离 —— 工具定义是缓存出来的数据，调用才是网络行为。现在两者绑在装配路径上，导致慢、脆。其余改动（命名空间、acp 下发、错误语义）都建立在这一刀上。

McpCatalog 协议server__tool 命名interceptor 链acp 按 server 粒度下发

02现状盘点：六处缺口

现有实现集中在 server/src/atlas_server/services/mcp.py（约 170 行），HTTP 远程、${ENV} 占位符、mcp:<server>:<tool> 标识、MissingTool 明确失败 —— 这几条都对，保留。问题在它周围：

#缺口证据严重度
G1模型看到的工具名没有命名空间。spec 里是 mcp:local:add，模型看到的是 add。两个 server 都有 search 时互相覆盖；MCP 工具叫 read_file 时与内置工具撞名。services/mcp.py tools_for 原样返回 t.name；adapter 的 tool_name_prefix 默认 False高
G2MCP 工具无法设审批。ApprovalMiddleware 按模型侧名匹配，而 /v1/tools 给 MCP 条目的 model_tool_names 是空列表 —— 编辑器里根本选不到。kernel/middleware/approval.py 按 call["name"]；services/meta.py 未填 model_tool_names高
G3acp agent 的 MCP 从未下发。spec 允许并且只允许 mcp:*，但 session/new 与 session/load 永远传 []。配了不生效 —— 正是 §13.2 禁止的形态。acp/runtime.py _ensure_session 两处 "mcpServers": []；atlas_acp.types.McpServerSpec 只有 stdio 形状高
G4发现在热路径上。每个 run 装配都对引用到的 server 做一次 tools/list；/v1/tools 每次请求连全部 server。一个慢 server 拖慢每一轮与编辑器。assembly.py McpService(...).tools_for；meta.py list_tools中
G5调用期的传输错误会打死整个 run。adapter 只把 isError=True 转成给模型的错误；连接断开、超时属于非 ToolException，直接冒泡。一个 MCP server 抖一下，整轮失败。langchain_mcp_adapters/tools.py _handle_mcp_tool_error 注释；无调用超时配置中
G6没有版本钉。（不做，见 §09）agent_version 快照不记录所引用工具的定义；server 改了 description / 参数，已发布的 agent 行为静默变化，无人知晓。domain/spec.py 无相关字段中
一个与概设不同的事实，会改变结论

概设 §09 说「新增工具会自动出现在模型的工具集里」。在 atlas 里不成立：agent 勾选的是单个工具（mcp:github:search），不是整个 server。所以 native 侧新增工具无害，真正要钉的是已勾选工具的定义。进一步推下去，native 侧的漂移大多会自愈（§09 的撤销理由）。
但 acp 侧恰好相反 —— ACP 只能按 server 下发（§07）。

关键决策：engine 零改动

命名空间、超时、错误转换、身份注入全部在 server 侧通过 adapter 的 tool_interceptors 与 StructuredTool 的构造完成。engine 看到的依然是普通 BaseTool，审批中间件照旧按名字匹配 —— 名字对了（§04），审批就自然生效。

04三种名字

一个 MCP 工具有三个名字，现在只有前两个被区分过，第三个一直是隐含的：

名字示例谁用约束
spec 标识mcp:github:searchspec.tool_names、/v1/tools.name不变，保持现状
模型侧名github__searchLLM 工具定义、require_approval_for、tool.* 事件^[A-Za-z0-9_-]{1,64}$（Anthropic / OpenAI 共同子集）
线上名searchtools/call 发给 serverserver 自定，我们只校验
 
# providers/mcp/naming.py
SEP = "__"
_MODEL_NAME = re.compile(r"^[A-Za-z0-9_-]{1,64}$")
_SERVER_NAME = re.compile(r"^[a-z][a-z0-9-]{0,23}$")   # ★ 不含 "_"，前缀才可逆

def model_name(server: str, tool: str) -> str:
    name = f"{server}{SEP}{tool}"
    if not _MODEL_NAME.match(name):
        raise InvalidToolName(server, tool, name)   # 发现期就报，不等模型调用
    return name

为什么是 server__tool

  • 不用 adapter 自带的 tool_name_prefix=True —— 它用单下划线 server_tool，而 server 名与工具名都可能含下划线，前缀不可逆，审计时无法从模型侧名还原来源。自己构造，规则握在手里。
  • server 名禁止下划线、限 24 字符 —— 保证 __ 第一次出现的位置就是分隔点，并给工具名留出 ≥38 字符。工具名超限或含非法字符的，在发现期标记为不可用（目录里 available=false + note），不进入可选列表。
  • 与内置工具不可能撞名 —— 内置工具名都不含 __。

审批因此自然生效（修 G2）

atlas 现有约定是 require_approval_for 存模型侧名，编辑器从 ToolInfo.model_tool_names 取候选项（bash→execute、filesystem 展开成 7 个就是这么做的）。MCP 条目只需把 model_tool_names=[model_name(server, tool)] 填上，审批链路一行不改。子 run 继承 require_approval_for 的既有逻辑同样覆盖 MCP。

兼容性：历史消息里的旧名字

改名后，已有 thread 的 message 表里仍有 tool_use.name = "add" 的历史调用。按 message 重建上下文时，这些是历史块，不要求出现在本轮工具列表里，Anthropic 与 OpenAI 均接受。需要在 §14 步骤 1 用一个带旧名历史的 thread 实测确认（待验证 V3）。

05目录与缓存

协议

# providers/mcp/catalog.py

@dataclass(frozen=True)
class ToolDef:
    """一次 tools/list 里的一个工具，已规范化。可 JSON 往返，存 Redis。"""
    server: str
    name: str                    # 线上名
    description: str
    input_schema: dict
    annotations: dict | None      # readOnlyHint / destructiveHint，给审批默认值用（§15）
    digest: str                  # sha256(canonical_json(name, description, input_schema))
    issues: tuple[str, ...] = ()   # 命名非法 / 描述超长 / 注入特征（§10）；非空即不可选

@dataclass(frozen=True)
class ServerSnapshot:
    config: McpServerConfig
    tools: tuple[ToolDef, ...]
    names_hash: str              # 工具名集合 —— 结构变化
    content_hash: str            # 全部 digest —— 任何变化
    fetched_at: datetime
    error: str | None = None      # 最近一次刷新失败原因；tools 仍是上次成功的

class McpCatalog(Protocol):
    async def servers(self) -> list[McpServerConfig]: ...               # 仅 enabled
    async def snapshot(self, server: str) -> ServerSnapshot: ...          # 读缓存，缺失时单飞拉取
    async def refresh(self, server: str) -> ServerSnapshot: ...           # 强制 tools/list

缓存策略

项取值理由
位置Redis，键 atlas:mcp:snap:{server}多副本共享；进程重启不丢。atlas 已依赖 Redis，不引入新组件
过期软 TTL 10 min，硬 TTL 7 天软过期后抢到锁的那一个同步刷新，其余先用旧值；硬过期才视为缺失。实现修正：原写「后台刷新」—— Redis 客户端的生命周期属于请求 / run，后台任务会拿着一个随时被关掉的连接
刷新失败保留旧 tools，写 error，fetched_at 推到现在server 短暂宕机不该让已缓存的工具定义消失 —— 调用期自会报错
单飞SET atlas:mcp:lock:{server} NX EX 30多个 run 同时 miss 只打一次 tools/list
冷启动 miss同步拉取一次，超时 10 s唯一允许发现落在装配路径上的场景；失败即 McpUnavailable → run.failed
为什么装配期可以不连网

adapter 的 convert_mcp_tool_to_langchain_tool(session=None, tool, connection=...) 只需要工具定义 + 连接参数就能构造出 StructuredTool，真正建连推迟到 tools/call。所以把 ToolDef 还原成 mcp.types.Tool 交给它即可 —— 发现与调用在 adapter 层面本来就是可分离的，现状只是没用上。

两个实现

实现server 定义来自ToolDef 缓存在何时用
SettingsCatalogSettings.mcp_servers（.env）Redis现在
ConfigPlaneCatalog配置平面 /mcp，占位符原样配置平面（其 tools_cache），Python 侧 Redis 只做短缓存Java 上线后；换 deps.py 一处注入

不在 Python 侧建 mcp_server 表 —— 那是注定要迁走的数据（包结构 §02）。改 MCP 配置仍需改 .env 并重启，这是过渡期明确接受的代价，写进 §15。

06native：装配与调用

装配时序

HookAssembly.build(prepared) │ ├─ wanted = {parse_tool_id(n) for n in spec.tool_names if n.startswith("mcp:")} │ ├─ for server in wanted: 并发，asyncio.gather │ snap = await catalog.snapshot(server) 命中缓存 → 零网络 │ server 不在目录 / 已禁用 → McpUnavailable → run.failed │ 勾选的工具不在 snap.tools → MissingTool → run.failed (现有语义，保留) │ 工具 issues 非空 → MissingTool(原因) → run.failed │ 缺 ${ENV} → MissingCredential → run.failed │ └─ tools = NativeMcpTools.build(snaps, wanted, ctx) → extra_tools，交给 build_graph

NativeMcpTools

# providers/mcp/native.py

@dataclass(frozen=True)
class CallContext:
    """闭包捕获，不进工具参数 schema —— 与 search_memory 的 user_id 同一条纪律。"""
    run_id: UUID
    thread_id: UUID
    user_id: UUID

class NativeMcpTools:
    def build(self, snaps, wanted, ctx: CallContext) -> list[BaseTool]:
        out = []
        for server, names in wanted.items():
            snap = snaps[server]
            conn = self._connection(snap.config)        # resolve_env_refs 在这里，timeout 也在这里
            chain = [
                identity_headers(ctx),                  # ① X-Atlas-Run/Thread/User
                errors_to_result(server, timeout),      # ② 修 G5 —— 必须在超时外面
                call_timeout(timeout),                  # ③ asyncio.timeout
                clip_result(self._max_chars),           # ④ §10
            ]
            for d in snap.tools:
                if d.name not in names: continue
                t = convert_mcp_tool_to_langchain_tool(
                    None, d.to_mcp_tool(), connection=conn,
                    server_name=server, tool_interceptors=chain,
                    handle_tool_errors=True)
                out.append(t.model_copy(update={"name": model_name(server, d.name)}))
        return out

interceptor 顺序即包裹顺序（外 → 内）：身份头要最先加上；错误转换在超时外面才接得住超时；超时包住真正的网络调用；裁剪只作用于成功结果。实现修正：本节初稿把超时排在错误转换外面，那样超时会直接冒泡打死 run。指标 interceptor 未做 —— 仓库目前只有 tracing 没有 metrics 管道，调用失败先记结构化日志（§11）。

错误语义：装配期硬失败，调用期交给模型

场景时点表现理由
引用的 server / 工具不存在、工具不可用、缺凭据装配run.started → run.failed，error_kind=capability_unavailable，message 写明 server 与工具配置错误，重试不会好；§13.2 不静默降级
冷缓存 + server 连不上装配run.failed没有工具定义就构造不出 schema
调用时连接失败 / 超时 修 G5调用ToolMessage(status="error")：「MCP 服务 github 暂时不可用（超时 60s），可稍后重试或换一种方式」瞬时故障；模型可以绕路。整轮失败代价远大于一次工具错误
isError=True调用adapter 原样转给模型（现有行为）业务错误，模型需要看到内容
HTTP 401 / 403调用ToolMessage：「MCP 服务 github 拒绝了认证，请联系管理员检查凭据」+ 指标 mcp.auth.failures概设 §06：让模型能转达，而不是反复重试一个 401
取消（CancelToken）调用正常取消语义，不转换CancelledError 必须穿透，③ 只接 httpx.HTTPError / McpError / TimeoutError
③ 不能写成 except Exception

吞掉 CancelledError 会让 run 取消失效；吞掉编程错误会让 bug 伪装成「服务不可用」被模型绕过去，永远不会被发现。只转换明确属于传输层的异常，其余照旧冒泡。

实现修正：装配失败此前根本不发 run.failed

本节初稿写「装配期硬失败 → run.failed」，但实际代码里装配异常直接冒泡到执行器兜底（_guarded → _force_fail）：run 落成「执行器内部错误」，一个事件都不发。SSE 上既无开始也无结束，能指出病根的原因只留在服务端日志里。这是既有问题 —— web_search 缺 key、记忆未开启走的也是这条路。

修法：NativeRuntime.run_turn 捕获 build() 的异常，用 runner.failed_before_start() 以同一套 EventFactory 规则（接着 start_seq 数）产出 run.started → run.failed，之后照常落库。消息是否给用户看按异常类型分：

  • CapabilityUnavailable（新标记类，errors.py）—— MissingTool / McpUnavailable / MissingCredential / SearchUnavailable / MemoryUnavailable / SkillUnavailable 改为继承它（仍是 RuntimeError，既有 except 行为不变）。消息约定面向用户，原样给出
  • EngineError —— 保留自身 kind（如 invalid_spec）
  • 其余（bug）—— 细节只进日志，用户看到的仍是「执行器内部错误」

审批中的 MCP 调用

ApprovalMiddleware 在 interceptor 链之外（它包的是整个工具调用），所以被审批挂起的调用不会建连、不占超时。审批通过后 run 以新段恢复（挂起与恢复），装配重跑、工具重建 —— 缓存命中，没有额外代价。

07acp：随会话下发

粒度冲突：ACP 只能按 server 下发

ACP 的 mcpServers 传的是 server，CLI 连上后自己 tools/list，拿到的是该 server 的全部工具。spec 里勾 mcp:github:search 的意思是「只给 search」，这在 CLI 侧无法兑现。

方案做法代价
A · 按 server 粒度（推荐）acp agent 只允许 mcp:<server>:*；勾具体工具在 validate() 报 InvalidSpec无法对 acp 只开一个 server 的部分工具。但语义诚实：配置与实际一致
B · 静默放宽收集涉及的 server 整体下发否决 —— 用户以为只开了 search，CLI 实际能调 delete_repo。越权且不可见
C · 代理过滤下发的 url 指向一个过滤 tools/list 与 tools/call 的代理正确但要一个数据面组件。Higress 就绪后在网关做（V4），届时再放开工具粒度
 
# domain/spec.py · AgentSpec.validate()  —— 替换现有 acp 分支
if self.kind == "acp":
    bad = [n for n in self.tool_names if not (n.startswith("mcp:") and n.endswith(":*"))]
    if bad:
        raise InvalidSpec(
            "acp agent 只能按 server 挂 MCP（mcp:<server>:*）：CLI 会拿到该 server 的全部工具，"
            "勾单个工具在 acp 下无法兑现", tool_names=bad)

mcp:<server>:* 只对 acp 合法；native 仍要求逐个勾选（native 能兑现工具粒度，没理由放宽）。parse_tool_id 对 * 返回 (server, "*")，native 装配遇到它报 InvalidSpec。

线协议修正

atlas_acp.types.McpServerSpec 现在只有 stdio 形状，且 env 是 dict —— ACP 规范里 env 与 headers 都是 [{name, value}] 数组（概设 §05 已标注「数组，不是对象」）。拆成两个模型：

# acp/src/atlas_acp/types.py
class NameValue(BaseModel):
    name: str
    value: str

class McpServerHttp(BaseModel):
    type: Literal["http"] = "http"
    name: str
    url: str
    headers: list[NameValue] = []

class McpServerStdio(BaseModel):      # 保留类型以便解析，平台不生成（概设 §03）
    name: str
    command: str
    args: list[str] = []
    env: list[NameValue] = []

McpServerSpec = McpServerHttp | McpServerStdio

AgentCaps 增加 mcp_capabilities: McpCaps（alias mcpCapabilities，http/sse 默认 False）。与 can_resume 同样的保守默认：adapter 没声明 http，就不能下发 http server —— 此时 run.failed「该 CLI 不支持 HTTP MCP」，而不是发过去让它静默丢弃。

下发时序

AcpRuntime.run_turn ├─ caps = initialize(...) ├─ servers = await AcpMcpServers.build(spec, caps, ctx) │ for mcp:<s>:* in spec.tool_names: │ cfg = await catalog.servers() 里的 s 不在 → McpUnavailable → run.failed │ caps.mcp.http 为假 → run.failed │ McpServerHttp(name=s, url=cfg.url, headers=pod_headers(cfg, ctx)) §08 │ ├─ _ensure_session(..., servers) │ session/load {sessionId, cwd, mcpServers: servers} ★ 两处必须一致 │ session/new {cwd, mcpServers: servers} └─ ...
session/load 也要传真实列表

runtime 注释说「恢复一个已有会话时它没什么用」—— 这对 Claude Code adapter 未必成立：恢复后的会话若不重新挂 MCP，工具就没了（待验证 V5）。两处传同一份列表，由 adapter 决定是否使用，比我们猜更安全。

会话级快照的后果

acp 的 MCP 列表在建会话时固定。管理员禁用某 server 后，已存在的 CLI 会话仍可调用它直到 Pod 重建 —— 紧急下线只能在出口侧做（Higress 或 server 端吊销凭据），这一点在运维手册里要写明（概设 §05）。

08凭证与身份

实现记录：本机已经过 Higress（2026-09-29）

Higress 2.2.4 all-in-one 跑在宿主的 compose 里（--profile higress，端口 18080 / 18001），不进 k8s —— 集群内的 atlas-server 访问 pg / redis 本就走宿主局域网 IP，Higress 同理。配置由 deploy/local/higress/setup.py 经控制台 API 完成，可重复执行。首个 server 是 OPEN_API 类型（REST → MCP）的 serpapi，取代了内置 web_search：后端 key 只在网关里，Atlas 侧只有网关地址。

  • 更正：前文「Higress 就绪后只改 url，代码不动」只对平台凭据 + 纯收口成立。按用户 / 会话限流、user 作用域凭据都需要 Atlas 签发可验证的身份令牌（本期未做），明文的 X-Atlas-* 头不能当依据
  • 模板引擎是 GJSON Template：管道写法 {{ .args.q | urlquery }} 会报参数个数错，要写 {{ urlquery .args.q }}
  • serpapi 尾延迟很长：直连 2.6–7s，未命中缓存偶尔 50s+（网关日志的 upstream 耗时证实慢在上游，不在网关）。由此引出 server 级的 call_timeout_s（§12），serpapi 配 90s
  • 协议版本：Python MCP SDK 请求 2025-11-25，Higress 回落到 2025-06-18，握手正常

native：保持现状

${ENV} 占位符在 server 进程内解析，真值只存在于连接参数里，不进 spec、不进事件、不进日志（record_metrics 只记 server/tool/耗时/结果类别）。

acp：真凭据要不要进 Pod

给 CLI 下发 headers 意味着把解析后的 token 送进 Pod —— Pod 里跑的是第三方 CLI，模型可以让它读自己的进程内存吗？不能直接读，但 CLI 可能把 MCP 配置写进日志或会话文件，而会话文件在 OSS 工作区上，用户可见。

方案Pod 里有什么取舍
P1 · 显式放行（过渡期推荐）解析后的真值，但仅限 McpServerConfig.pod_exposable=True 的 server默认不放行；未放行的 server 被 acp agent 引用时 InvalidSpec。管理员要为「这把 token 可以进 Pod」签字
P2 · 网关换证（目标形态）一个 run 级短期令牌 + Higress 地址Higress 按令牌注入真凭据、解析身份。依赖 V1/V2 验证
P3 · Atlas 自建代理同 P2，但代理在 atlas server否决 —— 让 server 进入 MCP 数据面，等于在 Higress 之前再造一个网关，Higress 上线后成为要删的代码
 
# providers/mcp/acp.py
def pod_headers(cfg: McpServerConfig, ctx: CallContext) -> list[NameValue]:
    if cfg.headers and not cfg.pod_exposable:
        raise McpUnavailable(f"{cfg.name} 带凭据且未允许下发到 Pod（pod_exposable=false）")
    hs = [NameValue(name=k, value=resolve_env_refs(v)) for k, v in cfg.headers.items()]
    return hs + identity_pairs(ctx)

P1 → P2 的切换只改 pod_headers 一个函数与 server 定义里的 url。

身份头：用于审计，不用于授权

两类 agent 都附带 X-Atlas-Run / X-Atlas-Thread / X-Atlas-User。它们来自 CallContext（闭包捕获），不在工具参数 schema 里，模型无法指定。

这些头不能被下游当作身份凭据

它们是明文、未签名的 —— 在 acp 路径上甚至由 Pod 里的 CLI 发出，CLI 可以改。下游 MCP server 若按 X-Atlas-User 做数据隔离，就是概设 §06 说的越权口子。user 作用域必须等 P2：由 Higress 从签名令牌解析身份并强制覆盖。在此之前注册表只接受 credential_scope=platform，且注册审查时要确认「该 server 的数据不因用户而异」。

09变更检测（已撤销）

初稿设计了 per-agent 版本钉，实现前撤销

初稿：发布 agent 版本时把每个已勾选 MCP 工具的定义哈希（name + description + inputSchema）写进 agent_version.spec.mcp_pins；每次装配比对缓存里的当前定义，不一致时按 per-agent 策略 warn（往 SSE 发 mcp.drift 事件后继续）或 strict（run.failed）。

撤销，原因按变化类型逐一看都不成立：

  • 工具被删 —— 装配期已报 MissingTool，不需要钉
  • 参数 schema 变了 —— native 用当前缓存定义构造工具，模型看到的就是新 schema，自然按新 schema 调；缓存未刷新的 ≤10 分钟窗口里调用失败会作为工具错误交给模型。基本自愈
  • 描述正常更新 —— 模型读到更准的描述，是好事；检测它只会误报
  • 描述被注入 —— 唯一真实的风险，但版本钉防不住：warn 下模型照样读到新描述；推给用户的 mcp.drift 事件，看到的人（终端用户）既无能力也无权限处置；strict 则让对方任何一次无害升级同时打挂所有 strict agent。它发生在 server 级，正确的控制点是注册表：定义变更 → 待审 → 批准后才生效，一处审查覆盖所有 agent。归配置平面的审核流
  • 「版本可复现」 —— 钉只能发现变化，不能让 agent 回到旧定义上跑，从来给不了可复现

留下的：McpToolDef.digest 与 ServerSnapshot.content_hash 仍随缓存计算与存储 —— 成本近零，配置平面做「变更待审」时直接可用。本期不据此做任何判断、也不记日志。

结果裁剪（interceptor ④）

文件工具开着时，FilesystemMiddleware 会把大结果转存到工作区；没开文件工具的 agent 没有这层保护，一个返回 5 MB JSON 的 MCP 调用会直接撑爆上下文。④ 是最后一道：文本内容超过 mcp_max_result_chars（默认 100 000）时保留头尾、中间替换为说明。★ 阈值必须高于 FilesystemMiddleware 的转存阈值（tool_token_limit_before_evict=20000 × 4 = 80 000 字符）：interceptor 在工具内部执行、早于中间件看到结果，阈值更低的话会抢先裁掉本可完整转存到工作区的内容。
