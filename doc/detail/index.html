详细设计

概要设计说的是应该长什么样，这里说的是在现有代码上怎么落地：类怎么设计、流程怎么走、哪些文件要动、哪些是新建。载体是 /root/workspace/atlas —— 一个已经跑起来的 LangGraph 多智能体平台。

载体 atlasPython 3.13 · FastAPI · LangGraphengine / server / web 三层

00为什么先做 native

概要设计里两类 Agent 共享同一套对象模型：Agent / Session / Run / Message / Event。atlas 已经把这套模型的 native 半边实现到了可用状态 —— 有版本快照、有事件契约、有审批、有沙箱、有压缩。

所以落地顺序是清楚的：先把 native 补齐到概要设计的完整形态，再接 acp。反过来做的话，acp 会被迫在一套还没定型的抽象上对接，接缝定不住。

这份详设回答什么

atlas 现有代码里，哪些与概要设计一致（不动）、哪些命名或语义不同（对齐）、哪些完全没有（新建）。每一条都落到类、函数、迁移和文件路径。

01
native Agent 详细设计

对照 atlas 现状的落地方案。一处概要设计的自我修正（needs_approval 不该由 type 推导）、技能的双路投送、Mem0 接入点、MCP 从环境变量到数据库、执行环境的接缝抽象，以及分五阶段的改动清单。

类设计 · 流程 · 迁移 · 文件级清单
02
目录与包结构设计

系统分成配置平面（Java）与运行时平面（Python）：技能、MCP、K8s 模板是有独立生命周期的内容资产；智能体配置留在 Python —— 它是装配说明，且 thread / run 对它有真实外键。含 kernel 的裁剪清单（已做功能可达性核对，约 4600 行）。

两个平面 · 单向调用 · 不可变契约 · kernel 裁剪 · 十一处否决
03
kernel 包分析

53 模块 / 26411 行拆成五层逐一说明：装配中心的中间件叠加顺序、Backend 协议的七个实现、Middleware 的能力清单、两套 Profile 档案。标出 Atlas 已改动的四处、休眠但有价值的能力、以及 ~5000 行死代码。末尾是可逐行打钩的评估清单。

功能 · 类设计 · 启用/改造/裁剪建议
04
文件系统与沙箱改造

中间件与协议各拆成 filesystem / sandbox 两半，事实源从容器内盘换成 OSS，工作区经 FUSE 挂进沙箱。技能并入同一条路径 —— 会话创建时拷进 .skills/，读走 filesystem、执行走 sandbox，可执行技能自动成立。含一处安全关键发现：FUSE 必须挂在沙箱容器之外。

两个协议 · OSS 布局 · 技能三层级 · 一致性 · 逐文件清单
05
Subagent 重新设计

从「每次委派都从零开始」改成子智能体持有自己的会话 —— 第二次委派时恢复上下文，而 ACP 的 loadSession 正需要一个可寻址的会话。核心决定：子会话是 thread 不是 run，于是压缩、摘要、恢复全部复用。含与 deer-flow 相反选择的诚实对照。

三条边界 · 两种恢复 · hook 与 delegate · 前端展示 · 同名串行
06
acp Agent 详细设计

把执行环境概设的 Bridge/Pod 链路落到 atlas 骨架上。核心判断：acp 的 run 也是普通 run —— 分岔只在 AgentRuntime。含 atlas_acp 线协议包、Bridge 独立部署物、事件翻译表、配对/一轮 prompt/恢复三张时序图。

AgentRuntime · 线协议共享包 · 审批回路 · lost 降级 · 落地六步

待写

  • 执行环境详细设计 —— K8s 模板管理与 Pod 生命周期组件。本期只在 native 详设里定下 SandboxProvider 协议接缝，实现留到这一篇。
  • 配置平面（Java）详细设计 —— 四个资产域的表结构、审核流、不可变版本的实现。本篇只给域划分与两条硬契约。
  • 权限详细设计 —— atlas 现在明确不做鉴权。native 期只做身份贯通（记忆按人隔离的前提），权限矩阵单独成篇。
