详细设计

概要设计说的是应该长什么样，这里说的是在现有代码上怎么落地：类怎么设计、流程怎么走、哪些文件要动、哪些是新建。载体是 /root/workspace/atlas —— 一个已经跑起来的 LangGraph 多智能体平台。

载体 atlasPython 3.13 · FastAPI · LangGraphengine / server / web 三层

00为什么先做 native

概要设计里两类 Agent 共享同一套对象模型：Agent / Session / Run / Message / Event。atlas 已经把这套模型的 native 半边实现到了可用状态 —— 有版本快照、有事件契约、有审批、有沙箱、有压缩。

所以落地顺序是清楚的：先把 native 补齐到概要设计的完整形态，再接 acp。反过来做的话，acp 会被迫在一套还没定型的抽象上对接，接缝定不住。

这份详设回答什么

atlas 现有代码里，哪些与概要设计一致（不动）、哪些命名或语义不同（对齐）、哪些完全没有（新建）。每一条都落到类、函数、迁移和文件路径。

类设计 · 流程 · 迁移 · 文件级清单
02
目录与包结构设计

系统分成配置平面（Java）与运行时平面（Python）：技能、MCP、K8s 模板是有独立生命周期的内容资产；智能体配置留在 Python —— 它是装配说明，且 thread / run 对它有真实外键。含 kernel 的裁剪清单（已做功能可达性核对，约 4600 行）。

两个平面 · 单向调用 · 不可变契约 · kernel 裁剪 · 十一处否决
03
kernel 包分析

53 模块 / 26411 行拆成五层逐一说明：装配中心的中间件叠加顺序、Backend 协议的七个实现、Middleware 的能力清单、两套 Profile 档案。标出 Atlas 已改动的四处、休眠但有价值的能力、以及 ~5000 行死代码。末尾是可逐行打钩的评估清单。

功能 · 类设计 · 启用/改造/裁剪建议
04
文件系统与沙箱改造

中间件与协议各拆成 filesystem / sandbox 两半，事实源从容器内盘换成 OSS，工作区经 FUSE 挂进沙箱。技能并入同一条路径 —— 会话创建时拷进 .skills/，读走 filesystem、执行走 sandbox，可执行技能自动成立。含一处安全关键发现：FUSE 必须挂在沙箱容器之外。

两个协议 · OSS 布局 · 技能三层级 · 一致性 · 逐文件清单
05
Subagent 重新设计

从「每次委派都从零开始」改成子智能体持有自己的会话 —— 第二次委派时恢复上下文，而 ACP 的 loadSession 正需要一个可寻址的会话。核心决定：子会话是 thread 不是 run，于是压缩、摘要、恢复全部复用。含与 deer-flow 相反选择的诚实对照。

三条边界 · 两种恢复 · hook 与 delegate · 前端展示 · 同名串行
06
acp Agent 详细设计

把执行环境概设的 Bridge/Pod 链路落到 atlas 骨架上。核心判断：acp 的 run 也是普通 run —— 分岔只在 AgentRuntime。含 atlas_acp 线协议包、Bridge 独立部署物、事件翻译表、配对/一轮 prompt/恢复三张时序图。

AgentRuntime · 线协议共享包 · 审批回路 · lost 降级 · 落地六步
06
挂起与恢复

一次委派可以跑一小时，父 run 不该在进程里等那么久。核心判断：委派挂起与审批挂起是同一件事 —— 都是「这一段到此为止，等一个外部事件」。含 thread 级事件流（seq 归属从 run 移到 thread）、不引入 checkpointer 的论证与实验、以及五条设计修正记录。

一 run 多段 · thread 流 · jump_to tools · 审批可等一天
08
MCP 接入详细设计

核心判断：发现与调用必须分离 —— 工具定义走缓存，装配期零网络。含现状六处缺口（模型侧名无命名空间导致审批失效、acp 的 MCP 从未下发、传输错误打死整个 run 等）、server__tool 命名、interceptor 链，以及 acp 只能按 server 粒度下发的语义修正。per-agent 版本钉在实现前撤销，撤销理由留在 §09。

McpCatalog · 三种名字 · 错误语义 · 装配失败可见 · 凭据进 Pod
09
server ⇄ bridge 通道详细设计

WebSocket 通道的异常路径：一轮跑多久算超时、超时之后谁收拾残局、上一轮的帧怎么不串进下一轮。由一次真实事故推出 —— 五次委派全部卡在 bridge 写死的 300s，超时不取消 CLI、残留轮次堵住后续每一次委派。核心判断：长请求不能用固定总时限，「这一轮结束」必须是三方共知的事实。

超时分层 · 超时即取消 · 轮次 id · WS 子协议协商 · 兼容旧 Pod
10
Bridge 重新设计

从零设计会话 Pod 里的 bridge，不继承现有实现。自底向上推：每章先讲清事实，章末把事实翻译成设计要回答的问题。第 1 章：WebSocket —— 握手、帧、心跳、关闭码、背压、它不提供什么。第 2 章：ACP —— 依官方 schema-v1.23.0 逐项整理：传输、协商、方法全景、一轮 prompt、权限、取消义务、扩展规则，以及仍在草案中的 v2（prompt 改为「接纳即返回」+ 显式会话状态）。第 3 章：职责边界 —— bridge 是 ACP client、内容翻译在 server；控制面与数据面、职责总表、六条边界不变式。第 4 章：上游协议 —— JSON-RPC over WebSocket 的 12 个方法：提交即返回的轮次、权限往返与兜底、原样装箱的数据面、错误码与关闭码。第 5 章：会话与轮次 —— 一会话一 Pod 一进程、预热与恢复、bridge 状态机、状态归属。第 6 章：超时、取消与背压 —— 截止与静默分开计时、静默按「等模型 / 执行工具」分两档、统一取消流程、有界队列与兜底。第 7 章：故障与恢复 —— 断线后一轮继续跑、attach + 按序号补发、控制消息永不淘汰、bridge 实例 id、恢复对照表。第 8 章：安全、可观测性与部署 —— 防 agent 自我批准（独立用户、凭据隔离）、指标与追踪、终止与回收。第 9 章：收尾 —— 不变式、决定索引、协议速查、待验证、落地顺序。

从零设计 · 事实 → 启示 → 决定 · 九章完成
11
Bridge 代码设计

把 Bridge 重新设计的九章落成代码：四个包（jsonrpc · acp · host · bridge）与依赖契约、bridge 的三层模块（agent / session / upstream）、核心类的状态与方法、关键流程在类之间的走向、异常约定、测试替身与 FakeAgent 剧本、十步实施拆分。

包划分 · 类设计 · 单事件循环 · 假时钟可测
12
会话文件预览

在会话右侧直接看智能体产出的文件，不用先下载。难点是 HTML 原型：它是多个文件组成、会执行脚本的站点。核心判断：把工作区当成只读站点挂在 /v1/previews/{token}/ 下，令牌放在 URL 路径里（iframe 带不了请求头），iframe sandbox 和 CSP sandbox 两层都运行在不透明 origin。内容另有：文件类型与渲染器矩阵、Range 截断与二进制判定、按 ETag 刷新（HTML 只提示不自动刷新）、生产环境独立 origin、测试清单与未决项。

工作区 = 站点 · 预览令牌 · sandbox 不透明 origin · ETag 刷新
