01链路总览

02ACP 协议

Bridge 作为 ACP client，由 adapter 负责启动并驱动 CLI 进程。本节是这条链路的协议契约，字段与枚举均取自 agent-client-protocol 0.12.1 的 schema。

2.1 传输与连接模型

ACP 是 双向 JSON-RPC，跑在 stdio 父子管道上：client 把 agent 作为子进程拉起，双方通过它的 stdin/stdout 通信。

async def spawn_agent_process(to_client, command, *args, env, cwd, ...):
    """Spawn an ACP agent subprocess and return a ClientSideConnection to it."""
这个传输模型有三个决定性推论
  • 只有 spawn 方能通信 —— 没有监听端口，没有第三方 attach 的入口。Bridge 只能和它自己拉起的 adapter 对话。
  • 无法观察外部进程 —— 用户自己在终端起的 claude 不是 ACP agent（claude 本身不说 ACP，要靠 adapter 包一层；且交互式 TUI 占用着同一对 fd）。这条路彻底封死。
  • 进程即会话边界 —— adapter 进程退出，这条 ACP 连接上的一切随之消失；会话能否续上取决于 agent 侧的持久化与 §03 的恢复方法。

2.3 能力协商

initialize 必须最先调用，双方交换能力。agent 返回的能力位要写回 agents.caps_probed（会话管理 §04 的 declared / probed 两层）。

# Agent 声明（我们读）
AgentCapabilities:
  loadSession: bool = False          # 默认关！
  promptCapabilities / mcpCapabilities / auth
  sessionCapabilities:
    list · delete · fork · resume · additionalDirectories

# Client 声明（我们写）
ClientCapabilities:
  fs: { readTextFile: False, writeTextFile: False }
  terminal: False
  session: { configOptions } · plan · auth

2.4 会话生命周期

session/new(cwd, mcpServers[, additionalDirectories])
    → NewSessionResponse { sessionId, modes?, configOptions? }
      ↑ ID 由 agent 生成，客户端不能指定

session/resume(sessionId, cwd, mcpServers)   ← 首选：不重放
session/load  (sessionId, cwd, mcpServers)   ← 退路：重放历史，需去重
session/fork  (sessionId, cwd, mcpServers)   → ForkSessionResponse（新 ID）
session/list  ([cwd], [cursor])              → SessionInfo[] + nextCursor
session/close (sessionId)                    ← 移交/停用时让 agent 收尾
session/delete(sessionId)                    ← 删历史
恢复优先用 session/resume

我们自己持有完整的 Message 账本，不需要 agent 把历史再吐一遍。session/load 的重放带来两笔额外成本：流量与延迟，以及与已有 Message 做去重 —— 而去重逻辑正是最容易产生静默 bug 的地方。

sessionCapabilities.resume     → session/resume   首选
agentCapabilities.loadSession  → session/load     退路
两者皆无                        → session/new + 置 lost

2.5 一轮对话

Bridge → session/prompt(sessionId, prompt[])
Agent  → session/update × N        （通知，见下表）
Agent  → session/request_permission  （可能穿插，需应答）
Bridge → PromptResponse { stopReason, usage? }

session/update 的 13 种变体（sessionUpdate 字段判别）：

变体用途平台 Event
agent_message_chunk正文增量message.delta
agent_thought_chunk思考增量thought.delta
user_message_chunk回显用户消息忽略（我们已有）
tool_call工具调用开始tool_call.started
tool_call_update状态变化tool_call.updated/ended
plan · plan_update · plan_removed计划增删改plan.updated

current_mode_update运行模式变化会话状态
config_option_update配置项变化会话状态
available_commands_update可用命令变化可选
session_info_update会话元信息（标题等）会话标题

ToolCallStatus：pending / in_progress / completed / failed。

StopReason：end_turn / max_tokens / max_turn_requests / refusal / cancelled —— 直接落进 runs.stop_reason。注意 max_turn_requests 和 refusal 都不是错误，前端不该显示成失败。

2.6 审批回路

Agent  → session/request_permission(sessionId, toolCall, options[])
Bridge → 翻译成平台 request.pending 事件 → 网页端
用户   → POST /requests/{qid}/respond
Bridge → RequestPermissionResponse { outcome: selected(optionId) | cancelled }

PermissionOptionKind：allow_once / allow_always / reject_once / reject_always。

默认必须是「转交用户」

Bridge 实现 request_permission 时，默认行为是转交，不是自动选 allow。一旦为了省事在 Bridge 里写死自动批准，前端那套审批卡片就成了摆设，任意文件写入与命令执行的权限实际上交给了模型。同理，adapter 若暴露「跳过所有权限检查」的开关，不要开。

allow_always 的作用域是 agent 会话级，随会话消失，而用户的心理预期通常是持久的。建议由平台自己存这个偏好（per session 或 per user × tool）并在下次自动应答，而不是透传给 agent。

2.7 取消

session/cancel 是通知，没有响应。发出后 agent 会中止当前轮，进行中的 session/prompt 以 stopReason = cancelled 正常返回 —— 不要把它当作错误处理，也不要在收到 cancel 确认前就认为轮次已结束。

已执行的工具副作用不会回滚，这正是 会话管理 §04 里助理的 rollback_on_cancel = false 的由来。

2.8 这套选择放弃了什么

  • 不能指定 session ID —— ID 由 agent 生成并返回，见 §03。
  • 不能直接控制 CLI 启动参数 —— 模型、权限模式等是否可配，取决于 adapter 暴露的 modes 与 configOptions。
  • transcript 文件名不可预测 —— 看不到 CLI 内部的 session UUID；目录仍可预测（cwd 固定）。
  • 多一层进程与一个上游依赖 —— adapter 的成熟度成为链路可靠性的一部分。

换来的是：审批、恢复、枚举、清理都有标准语义，且换 CLI 时只要对方有合规 adapter，Bridge 以上几乎零改动。

03三层 Session 映射

ACP 不允许客户端指定 session ID

核对 schema 的结论，这一点没有回旋余地：

class NewSessionRequest:
    cwd: str                          # 必填
    mcp_servers: list[...]              # 必填
    additional_directories: list[str] | None
    field_meta: dict | None              # _meta 扩展位
    # ← 没有 sessionId 字段

class NewSessionResponse:
    session_id: str                   # ← agent 生成并返回
    modes / config_options ...

ID 由 agent 在建会话时生成，客户端只能接收并持久化。类型是裸 str，没有格式约束 —— 不要假设它是 UUID。

三层映射

层标识谁生成性质
平台会话session_id我们持久，落库，客户端唯一可见
ACP 会话acp_session_idagentagent 侧持久，我们必须存下来
CLI 会话Claude Code session UUIDadapter 内部我们不可见，由 adapter 维护与 ACP ID 的对应

第三层对我们是黑盒 —— 这是选方案 A 的直接代价，但也意味着那一层的对应关系由 adapter 负责，不是我们的问题。我们只需守住前两层的对应。

ID 必须在第一个 prompt 之前落库

1.  conn.new_session(cwd="/home/agent/workspace", mcp_servers=[...])
2.  → NewSessionResponse(session_id="…")
3.  立即持久化：sessions.bridge_ref = {pod, acp_session_id}
4.  才发第一个 conn.prompt(...)
第 2 步与第 3 步之间有个孤儿窗口

如果 Pod 在拿到 ID 之后、写库之前崩溃，agent 侧已经建了会话而我们不知道它的 ID —— 状态卷上留下一份永远认领不回来的数据。窗口很短，但会话量大了就会遇到。

靠 session/list 兜底。它支持按 cwd 过滤，返回 SessionInfo{sessionId, cwd, title, updatedAt}。因为我们固定 cwd 且一个 Pod 一个会话（§05），该 cwd 下正常最多只有一个会话 —— 于是列表结果是可判定的：

  • 列出 1 个且与库里一致 → 正常
  • 列出 1 个而库里为空 → 孤儿，认领（写回库）或 session/delete 清掉
  • 列出 0 个而库里有 ID → agent 侧状态已丢，置 lost

固定 cwd 在方案 A 下因此有了一层新价值：它不只是让 transcript 目录可预测，更是让 session/list 的结果可判定。若 cwd 随会话变化，这个对账手段就废了。

恢复：resume 优先，load 退路

# 首选 —— 不重放，我们本就持有完整 Message 账本
conn.resume_session(
    session_id=<库里存的 acp_session_id>,
    cwd="/home/agent/workspace",          # 必须与建会话时一致
    mcp_servers=[...],                    # 重新传入，可与当初不同
)

# 退路 —— 会重放历史，需与已有 Message 去重
conn.load_session(session_id=..., cwd=..., mcp_servers=[...])
两个能力位默认都是关的

AgentCapabilities.load_session 在 schema 里默认 False；sessionCapabilities.resume 默认 None（即不支持）。agent 必须显式声明。会话恢复因此是「取决于上游」的能力问题，这是选 ACP 相比自研 Bridge 最实质的损失。

所以 会话管理 §04 的 resume_session 必须走 declared / probed 两层：握手拿到能力位之前，对外一律下发保守值 none。这是上线前第一个要实测的事（§12 第 1 项）。

清理与对账

  • session/delete —— 删除平台会话时一并清掉 agent 侧状态，避免状态卷上堆积无主数据。同样是可选能力，不支持时退化为直接删卷。
  • session/list —— 除孤儿检测外，也是运维排查入口：SessionInfo.updatedAt 可用于识别长期不活跃但仍占着存储的会话。

_meta 可以带关联提示，但不能依赖

NewSessionRequest 有 _meta 扩展位，可以塞进 platform_session_id。若 adapter 在 SessionInfo._meta 里回传，孤儿对账会更直接。

但协议明文写着实现不得对这些键的值做任何假设 —— 也就是说对方完全可以忽略甚至丢弃它。把它当作锦上添花，真正的兜底仍是固定 cwd + session/list。

Run 与 prompt 的对应

一个平台 Run = 一次 session/prompt，stop_reason 取自其返回值。会话管理 §13 的「Session 内 Run 串行」在这里落地为：Bridge 同时只允许一个活跃 prompt，第二个请求直接拒绝而非排队。

04存储分层与挂盘

最容易做错的一处

不要把 Claude Code 的状态目录挂在 OSS 上。Claude Code 把会话逐条追加写入 ~/.claude/projects/<escaped-cwd>/<uuid>.jsonl。对象存储没有真正的追加语义，ossfs 这类 FUSE 的追加写实际是「下载整个对象 → 修改 → 整体上传」。一次长会话的 transcript 会长到数 MB（实测单文件 1.4MB 并持续增长），每轮对话都全量重写一次，延迟与费用都不可接受，并发写还可能丢数据。

数据存储模式理由
会话产出文件OSSrw大文件、低频写、需长期留存与外部访问
Claude Code 状态NAS / CPFS / PVCrw小文件高频追加写，需要 POSIX 语义
技能包只读卷或镜像ro全局共享、读多写零
凭证K8s Secretro不落盘到持久卷
注入配置ConfigMap / initContainerro每次启动按会话渲染

OSS 前缀与卷的划分

oss://<bucket>/tenants/<tenant_id>/sessions/<session_id>/     ← 挂到 /home/agent/workspace
nas://<fs>/tenants/<tenant_id>/sessions/<session_id>/claude/  ← 挂到 /home/agent/.claude

两者都按 tenant_id/session_id 隔离。挂载凭证只授予该前缀的权限，Pod 即使被攻破也读不到其他会话的数据 —— 这是 Pod-per-session 隔离模型的存储侧落实。

如果只想用一种存储

全部用 NAS 也是自洽的，代价是产出文件失去对象存储的成本与外部访问优势（生成预签名 URL 给前端下载会变麻烦）。反过来全用 OSS 则不可行，原因见上。若因成本必须压到一种，选 NAS。

不要用「退出前 sync 到 OSS」来省掉 NAS

看起来可以：状态目录用 emptyDir，Pod 终止前同步到 OSS。但 Pod 的终止路径不止优雅关闭一种 —— 节点故障、OOMKill、抢占式回收都不给你同步的机会，而这些恰恰是最需要恢复的场景。把持久性建立在「进程有机会执行清理代码」之上，是不可靠的。

05Pod 内目录设计

/home/agent/                              # HOME，固定
├── .claude/                              ← NAS 卷（rw，per-session）
│   ├── .credentials.json                 # Secret 投射（ro）或改用 env
│   ├── settings.json                     # ConfigMap 投射（ro）
│   ├── projects/
│   │   └── -home-agent-workspace/        # 目录可预测（cwd 固定）
│   │       └── <CLI 内部 UUID>.jsonl     # 文件名不可预测（见下）
│   ├── skills/                           ← 技能只读卷（ro，subPath 嵌套）
│   ├── plugins/
│   ├── history.jsonl
│   └── shell-snapshots/  file-history/  todos/ …
│
├── .claude.json                          # initContainer 清理残留 MCP 配置 + 预置信任标记
│
└── workspace/                            ← OSS 卷（rw，per-session）· cwd
    ├── CLAUDE.md                         # 可由 Server 注入项目级指引
    ├── .mcp.json                         # initContainer 清理，避免与 ACP 参数叠加
    └── …产出文件

cwd 必须固定

Claude Code 按工作目录组织 transcript，目录名规则是把绝对路径里的 / 全部替换成 -（已实测核对：/root/workspace/deer-flow → -root-workspace-deer-flow）。

把 cwd 固定为 /home/agent/workspace，transcript 目录就恒为：

~/.claude/projects/-home-agent-workspace/

方案 A 下我们看不到 CLI 内部的 session UUID，所以文件名不可预测。但因为一个 Pod 一个会话，这个目录下正常只有一个 .jsonl 文件 —— 目录级可预测对备份、排查、清理已经够用。

固定 cwd 在方案 A 下承担了双重作用

其一是状态位置确定：不必依赖运行时变量就能定位 transcript。

其二更关键 —— 它让 session/list(cwd=…) 的结果可判定，这是 §03 孤儿会话对账的基础。若让每个会话用不同的工作目录（比如按项目名），这个兜底手段就失效了。会话之间的隔离已经由「一个 Pod 一套卷」保证，不需要再靠目录名区分。

嵌套挂载

~/.claude 整体是可写 NAS 卷，而 ~/.claude/skills 要是只读技能卷 —— 这是在一个卷的子目录上再挂另一个卷，K8s 支持，但要注意挂载顺序：父卷先挂，子卷后挂，否则子卷会被父卷盖住。用 volumeMounts 的声明顺序控制，并在就绪探针里验证 ~/.claude/skills 非空。

06Claude Code 配置注入

方案 A 下配置分三条通道，优先级依次降低：能走 ACP 参数的最好，其次环境变量，最后才是落盘文件。ACP 参数每次建会话显式传入，行为完全确定；落盘文件是有状态的，会在 Pod 重建、版本升级、卷复用时产生难以复现的差异。

配置项通道说明
工作目录session/new → cwd固定 /home/agent/workspace
MCP 服务器session/new → mcpServers见 §07，指向 Higress
额外可访问目录session/new → additionalDirectories默认空，扩大范围需显式决策
会话标识不可指定agent 返回，见 §03
模型session/set_config_option 或 env取决于 adapter 暴露什么，待验证
权限策略session/request_permission 回调决定权在客户端，见下
认证Secret → envANTHROPIC_API_KEY 指向 Higress
Claude 设置文件 ~/.claude/settings.jsonadapter 启动的 CLI 会读，见下
技能文件 ~/.claude/skills/见 §08
权限决定权在客户端，这正是选方案 A 的主要理由

ACP 的 session/request_permission 是 agent → client 的反向请求：CLI 要做危险动作时，agent 把选项列表交给客户端，由 Bridge 决定。Bridge 把它翻译成平台的 request.pending 事件一路推到用户面前，再把用户的选择原样返回。

自研 Bridge 时这条回路的机制需要自己摸索并验证；协议里它是一等公民，语义明确。助理角色的整个安全模型建立在这条回路上（会话管理 §11），它有没有标准机制，是 A / B 之间最重要的差别。

不要让 Bridge 自动批准

Bridge 侧实现 request_permission 时，默认必须是「转交用户」而不是「自动选 allow」。一旦为了省事在 Bridge 里写死自动批准，前端那套审批卡片就成了摆设，而任意文件写入与命令执行的权限实际上交给了模型。

同理，如果 adapter 提供了「跳过所有权限检查」的开关（Claude Code 自身有 --dangerously-skip-permissions），不要开。

仍然要落盘的部分

adapter 启动的仍是标准 claude 进程，它照常读取 ~/.claude/。所以这些还是文件：

  • ~/.claude/settings.json —— 模型、主题、env 等。经 ConfigMap 只读投射。
  • ~/.claude/skills/ —— 技能，见 §08。
  • ~/.claude/projects/ —— transcript，必须持久化（§04）。
MCP 配置文件要清掉，避免与 ACP 参数打架

Claude Code 自身有 --strict-mcp-config 可以一刀切断其他 MCP 来源，但这个开关握在 adapter 手里，我们无法保证它被启用。session/new 传入的 mcpServers 究竟是替代还是叠加，是 §12 第 3 项。

因此 initContainer 应当主动清理状态卷上可能残留的 MCP 配置：~/.claude.json 里的 projects[<cwd>].mcpServers、以及 workspace 下的 .mcp.json。否则卷复用时，上一次会话遗留的服务器可能与本次 ACP 参数传入的叠加，表现为「用户看到了不该有的工具」—— 这类问题排查起来很费时间，因为配置来源不在代码里。

信任对话框

实测 claude --help 说明：「The workspace trust dialog is skipped when Claude is run in non-interactive mode (via -p, or when stdout is not a TTY)」。adapter 通过管道驱动 CLI，stdout 不是 TTY，对话框会自动跳过。

保险起见仍可在 initContainer 里预置 ~/.claude.json 的 projects["/home/agent/workspace"].hasTrustDialogAccepted = true，成本极低。若哪天 Pod 卡在启动且无任何输出，这是第一个该查的地方。

认证与多租户

  • API Key —— 经 Secret 注入 ANTHROPIC_API_KEY，指向 Higress 的 LLM 网关而非模型厂商。最简单，也让助理的模型调用纳入统一治理。
  • OAuth 凭证 —— ~/.claude/.credentials.json。注意它不应写进 per-session 的状态卷，否则凭证会随会话状态一起长期留存、备份、迁移。用 Secret 以只读方式投射到该路径。

Pod-per-session 让凭证隔离天然成立：每个 Pod 只拿到本会话该用的那一份。

信任对话框

实测 claude --help 说明：「The workspace trust dialog is skipped when Claude is run in non-interactive mode (via -p, or when stdout is not a TTY)」。Bridge 通过管道驱动 CLI，stdout 本就不是 TTY，信任对话框会自动跳过。

保险起见仍可在 ~/.claude.json 预置 projects["/home/agent/workspace"].hasTrustDialogAccepted = true，成本极低。若哪天 Pod 卡在启动且无任何输出，这是第一个该查的地方。

认证与多租户

  • API Key —— 经 Secret 注入 ANTHROPIC_API_KEY。最简单，且与 Higress 的 LLM 网关天然配合（密钥指向网关而非模型厂商）。
  • OAuth 凭证 —— ~/.claude/.credentials.json。注意它不应写进 per-session 的 NAS 卷，否则凭证会随会话状态一起长期留存、备份、迁移。用 Secret 以只读方式投射到该路径。

Pod-per-session 让凭证隔离天然成立：每个 Pod 只拿到本会话该用的那一份，不存在跨用户读取 CLI 本地状态的问题。

07MCP 配置

方案 A 下 MCP 配置随 session/new 参数传入，不落盘。ACP 支持四种传输：http、sse、acp、stdio。我们统一用 http 指向 Higress。

配置随会话传入，而不是写进文件

这是方案 A 的一项实在收益：CLI 看到的工具集由 Server 在建会话时决定，不需要渲染配置文件、不需要考虑文件何时被读取、也不会在卷复用时受上一次会话影响 —— 前提是清掉了残留的文件配置（§06）。

指向 Higress，而不是直连

注意 ACP 的 headers 是 {name, value} 对象数组，不是 JSON 对象 —— 与 Claude Code 自己的 .mcp.json 格式不同，转换时容易写错：

mcp_servers = [
  {
    "type": "http",
    "name": "github",
    "url":  "https://higress.internal/mcp/github",
    "headers": [                                  ← 数组，不是对象
      { "name": "Authorization", "value": "Bearer <session-scoped-token>" },
      { "name": "X-Session-Id",  "value": "<session_id>" }
    ]
  }
]

这样 CLI 发起的工具调用也进入网关，与顾问的调用共享同一套鉴权、限流、配额、成本核算与出站审计（系统架构 §06）。否则助理会成为一条绕过所有治理的旁路 —— 而它恰恰是副作用最大的那一类调用。

令牌随会话作用域，且要能失效

session-scoped-token 应当只对本会话有效、随会话结束失效、并带有效期。它被写进 Pod 内的 ConfigMap 文件，虽然有 Pod 隔离，但仍应按「可能泄漏」来设计生命周期 —— 长期有效的全局令牌落到几百个 Pod 的文件系统上，是个不必要的暴露面。

08技能目录挂载

Claude Code 的个人技能位于 ~/.claude/skills/<name>/SKILL.md（已实测核对该布局）。技能包的特点是全局共享、只读、体积可观、更新频率低于会话频率。

方案热更新冷启动适用
打进镜像需重建镜像最快技能稳定、随版本发布
只读卷（推荐）更新卷即可首次挂载有开销技能独立于镜像迭代
--plugin-dir按会话指定快按 Agent 下发不同技能子集

推荐只读卷挂到 ~/.claude/skills，配合 §05 的嵌套挂载。技能管理模块更新卷内容后，新起的 Pod 自动获得新版本，已运行的会话不受影响 —— 这个「不影响在途会话」的性质是对的，技能在会话中途变化会让模型行为出现无法解释的跳变。

按 Agent 下发技能子集时不要用同一个卷

如果不同 Agent 要挂不同技能集合，别在一个大卷里用 subPath 挑挑拣拣 —— 那会让「这个 Agent 到底能看到哪些技能」散落在部署模板里。改用 --plugin-dir 按会话显式指定，或为每个技能集合准备独立的卷。能力边界应该是可查询的配置，不是挂载表的副产品。

09K8s 管理

生命周期由执行环境管理组件统一拥有

本节描述 acp Pod 的 K8s 细节，但模板、创建、回收、卷分配、配额这些逻辑不是本链路独有的 —— native 的 sandbox Pod 需要一模一样的东西。它们统一归执行环境管理组件，本节只讲 acp 特有的部分。

Pod 身份

name:   agent-<session_id 短哈希>
labels: app=agent-pod
        session-id=<session_id>
        agent-id=<agent_id>
        agent-version=<n>
        tenant-id=<tenant_id>

用 label 而非 name 承载 session_id —— name 有长度与字符集限制，而 label 可被 selector 查询，运维排查时能直接按会话定位。

生命周期

阶段动作
调度Server 收到首个 Run 或会话从 cold 唤醒 → 创建 Pod，会话状态置 starting
就绪就绪探针通过（见下）→ Server 建立 WebSocket → 会话置 active
空闲无活跃 Run 且超过 idle TTL → 删除 Pod，会话置 cold；状态卷保留
删除DELETE /sessions/{sid} → 删除 Pod + 按保留策略处理卷
异常Pod 消失而会话未主动关闭 → 置 cold，下次提交时重建并 session/load

就绪探针要验到 CLI，不能只验 Bridge

探针只检查 Bridge 的 WS 端口是不可靠的 —— Bridge 起来了但 CLI 不可用（镜像缺二进制、认证失效、卷没挂上、技能目录为空）的话，Server 会把流量打进一个必然失败的 Pod，用户看到的是提交后卡住然后报错。

探针应当覆盖：CLI 二进制可执行、认证有效、~/.claude 与 workspace 卷可写、技能目录非空。宁可 Pod 起不来，也不要起来一个坏的。

接入控制：谁能连上 Pod 里的 Bridge

K8s 的默认网络是平的

集群里任何 Pod 都能连任何 Pod 的端口。Bridge 的 WS 端点如果不做认证，同集群的其他工作负载 —— 包括别的租户的会话 Pod —— 就能连上它并驱动 CLI：读该会话的工作区、用该会话的凭证执行命令。

「只有 Server 能连」必须显式实现，不能假设。「它在 Pod 网络里」不是一种安全边界。

措施做法
每 Pod 一份凭证 Server 在创建 Pod 时生成随机凭证，经 K8s Secret 注入。Bridge 在 WS 握手的 header 上校验，不通过直接拒绝握手。绝不能把凭证打进镜像 —— 那等于全集群共用一把钥匙。
NetworkPolicy 限制 ingress 只允许 Server 的 Pod 标签访问 Bridge 端口。这是纵深防御的第二层：凭证泄漏时网络层仍然挡着。
凭证随 Pod 生命周期 Pod 销毁即失效，重建换新。不需要轮换机制，因为它本来就是短命的。
会话绑定校验 Bridge 只接受针对本 Pod 所属会话的指令。即使连接通过认证，带着别的 session_id 的请求也要拒绝。

本地部署的接入控制是另一套问题 —— 连接方向相反，且需要防止服务端被冒充（后果是用户电脑上的任意命令执行），见本地部署 §03。

优雅终止

terminationGracePeriodSeconds 要留够 Bridge 做三件事：拒绝新请求、把当前 Run 标记为中断并上报、刷完 OTel span。但不要把数据持久性依赖在这段时间里（§04）—— 节点故障和抢占不会给你这个窗口。

资源与配额

CLI 进程的内存占用随上下文增长，limits.memory 设得太紧会在长会话中途 OOMKill，用户感知是「聊着聊着就断了」。建议按实测的长会话峰值设定，并把 OOMKill 作为一个明确的监控指标 —— 它与其他退出原因的处理方式不同（OOMKill 后重建并 resume 是合理的，反复 OOMKill 则说明该会话需要 compact 或更大规格）。

租户级 Pod 数量配额要有，否则一个租户的批量会话会把集群占满。

10启动与恢复时序

冷启动

 1.  Server        收到 Run 提交，会话无活跃 Pod
 2.  K8s           调度 Pod，挂载 4 类卷
 3.  initContainer 校验卷可写；清理残留 MCP 配置；预置 hasTrustDialogAccepted
 4.  Bridge        启动，监听 WS，spawn adapter 子进程
 5.  Bridge→agent  initialize(protocolVersion, clientCapabilities)
 6.  Bridge←agent  agentCapabilities —— 记下 loadSession / sessionCapabilities
 7.  Bridge        就绪自检（adapter 可用 / 认证 / 卷 / 技能目录非空）
 8.  Server        探针通过 → 建立 WebSocket → 会话置 active
 9.  Bridge→agent  session/new(cwd=/home/agent/workspace, mcpServers=[指向 Higress])
10.  Bridge←agent  sessionId
11.  Server        立即持久化 bridge_ref = {pod, acp_session_id}
12.  Bridge→agent  session/prompt(sessionId, [...])
13.  Bridge        session/update 流 → 翻译成平台 Event；
                   session/request_permission → request.pending → 用户

第 6 步拿到的 agentCapabilities 要写回 agents.caps_probed（会话管理 §04 的 declared / probed 两层）。第 11 步不能推迟到 prompt 之后，理由见 §03 的孤儿窗口。

从 cold 恢复

 1-8  同上，卷挂载到同一 NAS / OSS 前缀 → agent 侧会话状态仍在
 9.  Bridge        按能力位择路
                   ├─ sessionCapabilities.resume → session/resume(...)  首选，不重放
                   ├─ agentCapabilities.loadSession → session/load(...) 退路，需去重
                   │     两者均 → 上下文完整，不提示用户
                   └─ 皆不支持 → session/new(...)  → 新会话
                                 → 置 lost，消息流插入「会话已重启」
10.  Bridge        对账：session/list(cwd) 与库里的 ID 比对，处理孤儿
恢复无损时不要提示用户

会话管理 §06 要求 lost 必须在消息流里插入「会话已重启，此前上下文未保留」。但 session/load 成功时上下文是完整的，不应该提示 —— 没必要让用户为一次对他无影响的基础设施事件分心。cold 对用户应当完全透明，代价只是下一条消息慢几秒。

反过来，loadSession 为 false 或 session/load 失败时必须提示。这两条路径的用户感受差别很大，而分支条件是上游能力 —— 所以 §12 第 1 项的实测结论会直接决定这个功能的体验档次。

11CLI 适配层

ACP 本身就是适配层，所以这一层比自研 Bridge 时薄得多。会话语义、流式输出、审批回路、恢复与清理都由协议统一，Bridge 的核心逻辑对所有 CLI 通用。

剩下的差异只有两类：怎么把 adapter 拉起来，以及哪些东西还得靠文件系统。

interface CliProfile {
  // adapter 进程怎么起
  command: string
  args: string[]
  env(ctx: LaunchContext): Record<string, string>

  // 需要持久化的状态目录（挂 NAS）
  statePaths(): string[]

  // 启动前要清理的残留配置，避免与 ACP 参数叠加
  staleConfigPaths(): string[]

  // 技能 / 设置等仍走文件系统的部分
  fileConfig(ctx: LaunchContext): ConfigFile[]

  // 就绪自检
  healthCheck(): Promise<boolean>
}

注意这里没有 session id 派生、没有协议翻译、没有权限回调 —— 那些都归 ACP 管了。

Claude Code 的 profile

字段取值

envANTHROPIC_API_KEY（指向 Higress）、HOME=/home/agent
statePaths~/.claude/projects/（必需）、~/.claude/history.jsonl（可选）
staleConfigPaths~/.claude.json 的 projects[cwd].mcpServers、workspace/.mcp.json
fileConfig~/.claude/settings.json、~/.claude/skills/

Codex 的对应项尚未调研

协议层统一了，但上表每一行在 Codex 上仍需确认：adapter 怎么装、状态写在哪、有没有需要清理的残留配置、技能/设置机制是什么。在实际调研之前不要假设它与 Claude Code 对称。

真正需要警惕的不是这些，而是能力差异：Codex 的 adapter 是否实现 loadSession、session/list、session/delete。这些都是 ACP 的可选能力，缺任何一项都会让 §03 的恢复与对账在该 CLI 上降级。接入时第一件事是读它 initialize 返回的 agentCapabilities。

12待验证清单

下面各项决定了本文若干设计能否成立，都应当在写代码之前用一个最小实验确认，而不是在实现到一半时发现。

#验证项影响
1 adapter 的 initialize 返回什么 agentCapabilities —— 五个位全要看：loadSession、sessionCapabilities 的 resume / list / delete / fork 决定 §03 的恢复、对账、清理各自能不能做
2 session/resume 与 session/load 的实际语义差异：是否重放、Pod 重建后能否跨进程恢复、cwd 不一致时的行为 决定 §10 恢复路径的可用性与用户感受
3 session/new 传入的 mcpServers 是否完全替代了 CLI 自身的 MCP 配置，还是与之叠加 决定 §06 的残留清理是必需还是保险
4 模型、权限模式等参数能否经 session/set_config_option 或 modes 控制 决定 §06 里那几项「取决于 adapter」能否落地
5 长会话下 transcript 的增长曲线与 NAS 上的追加写延迟 校准 §04 的存储选型与 §09 的资源规格
6 技能只读卷嵌套挂载在目标 K8s 版本与 CSI 驱动上的实际表现 决定 §08 是否改用镜像内置
7 Codex adapter 在 #1–#4 上的对应情况 决定 §11 的 profile 是否够用
第 1、2 项是最该先做的实验

loadSession 在 schema 里默认为 false，agent 必须显式声明支持。它直接决定 cold → active 是「用户无感、只是慢几秒」还是「上下文全丢、要在消息流里道歉」—— 这是两个完全不同档次的产品体验，而分支条件完全在上游手里。

建议的最小实验：起 adapter，打印 initialize 的完整响应；建一个会话发两轮对话；杀掉进程重启；用存下来的 sessionId 调 session/load，看能否续上、历史是否重放、session/list 是否列得出来。半天的实验能省掉一次架构返工。

如果 loadSession 为 false

不要立刻退回自研 Bridge —— 那会连带失去 request_permission 这个标准审批回路，代价更大。可选的应对，按推荐顺序：

  1. 给 adapter 提 issue 或自己补一个 —— 底层 CLI 有 --resume，能力是在的，缺的只是 adapter 没暴露。
  2. 接受 cold 即 lost —— 把 idle TTL 调长以降低发生频率，并在 UI 上诚实提示。
  3. 混合方案 —— 审批走 ACP，恢复另想办法（例如由 Bridge 直接调用 CLI 的 resume 能力预热）。复杂度高，仅在前两条都不可行时考虑。
