2. 目标与非目标

目标非目标（不在本模块）
  • 可信身份：Python 运行时只接受经过验证的身份（G1、G7）
  • 用户投影：首次出现自动登记，资料随身份信息同步，禁用的用户立即失效（G5）
  • 资源授权：会话、run、消息、事件流、审批、记忆、文件按所有者隔离（G2、G3）；智能体按角色和创建者控制编辑（G4）
  • 可追溯：每一轮记录发起人，每个审批记录决策人（G6）
  • 开发体验不变：本机开发保留现在的"请求头 + 默认用户"模式
  • 登录界面、密码、SSO 对接、组织和角色的维护：这些属于配置平面的 iam（Java），本文只定义对接契约
  • 配置类变更的审计：属于配置平面的 audit
  • 计费和细粒度配额策略：属于配置平面的 quota；本文只规定运行时如何执行它
  • 会话共享和协作（多人一个会话）：第 3 期再做，本文预留数据结构

3. 总体架构与职责划分

职责配置平面 iam（Java）运行时 auth / authz（Python，本模块）
谁是谁（认证）权威：登录、对接 SSO、签发令牌只验证令牌，不登录、不存密码
用户资料权威：用户、组织、角色的增删改维护一份投影（id、外部 id、显示名、邮箱、组织、状态），供关联查询和展示
能不能做某类事（粗粒度）权威：角色写进令牌按令牌里的角色执行
能不能动某个具体资源（细粒度）智能体编辑：BFF 先判一次权威：会话、run、审批等运行时数据只有 Python 知道归属，必须在这里判。智能体编辑在这里再判一次（纵深防御）
配额定策略执行（Pod 配额已经由 cluster 按用户执行）
为什么运行时一定要自己做资源授权：已有规划里，对话和 SSE 由 BFF 透传给 Python。BFF 不知道某个会话属于谁（那是运行时的数据），所以"A 不能读 B 的会话"这条规则，只能由 Python 来执行。

4. 核心概念

概念定义落地
Principal（请求主体）一次请求"是谁在做"：内部用户 id、外部 id、组织、角色、显示名每个请求解析一次，经依赖注入传给接口；service 层不允许自己去取身份（沿用现有纪律）
User（用户投影）iam 用户在运行时的镜像。id 是运行时内部的 UUID，永不变；external_id 是 iam 的用户标识app_user 表
Org（组织）用户所属的组织（租户）。智能体的可见范围以组织为界先存在用户上（app_user.org_id），智能体上预留 org_id
Role（角色）member：使用已启用的智能体对话；builder：再加上创建和编辑智能体；admin：管理本组织的一切来自令牌，不存库（存了就有两份事实）
Owner（所有者）会话的所有者 = thread.created_by；会话下的一切（run、消息、事件、审批、文件、子会话、Pod）都归会话所有者归属链见 7.3 节

5. 身份认证

5.1 两种模式

模式身份来源适用
dev（默认，兼容现状）X-User-Id 请求头，缺省用 default_user_id；角色固定为 admin本机开发、单测。启动时如果检测到非本地监听地址又是 dev 模式，打印醒目的警告
jwtAuthorization: Bearer <令牌>，用 iam 的 JWKS 公钥验证签名；忽略 X-User-Id所有共享环境（测试、正式）

配置：auth_mode: dev | jwt、auth_jwks_url、auth_issuer、auth_audience、auth_leeway_s（默认 30）。

5.2 令牌契约（运行时与 iam 的接口）

{
  "iss": "https://iam.atlas.internal",        // 必须等于 auth_issuer
  "aud": "atlas-runtime",                     // 必须包含 auth_audience
  "sub": "u_8f2c…",                           // iam 的用户 id → app_user.external_id
  "exp": 1791234567, "iat": 1791230967,       // 建议有效期 ≤ 15 分钟，由 BFF 续签
  "name": "张三",                              // 显示名
  "email": "zhangsan@example.com",
  "org": "org_acme",                          // 组织
  "roles": ["member", "builder"],             // 粗粒度角色
  "active": true                              // false = 已禁用（也可以由 iam 直接不签发）
}
  • 签名算法只接受 RS256 / ES256（非对称），并且拒绝 alg: none 和 HS*：运行时只持有公钥，不持有能签发令牌的密钥。
  • JWKS 在内存里缓存（默认 10 分钟）；遇到不认识的 kid 时强制刷新一次，以支持密钥轮换；iam 不可用时继续用缓存里的公钥。
  • 短有效期加 BFF 续签，所以运行时不需要维护吊销列表。被禁用的用户最多在一个令牌有效期内（≤ 15 分钟）失效。

5.3 一次请求的认证流程

5.4 特殊通道

通道身份说明
SSE 事件流同普通请求（Bearer 头）前端已经用 fetch 读 SSE（sse.ts），可以带头，不需要把令牌放进 URL（放进 URL 会进访问日志）。长连接期间令牌过期不断开；断线重连时用新令牌
执行器后台任务不是请求，没有 Principalrun 在后台 task 里执行，身份取自会话所有者（thread.created_by）—— 现状就是这样（inprocess.py:534、assembly.py:151），保持不变
server → cluster、server → bridge服务之间的身份，不是用户保持现状（内部网络 + bridge 的会话令牌）。user_id 只作为数据参数传给 cluster，用于路径和配额
server → 外部 MCPX-Atlas-User 明文头外部服务无法验证它的真伪。第 3 期改为短期签名令牌（由 iam 签发、受众是该 MCP 服务），本期不动

6. 用户投影（app_user）

6.1 表结构

列类型说明状态
idUUID 主键运行时内部 id，永不变；所有业务表的 created_by 都指向它，对象存储路径也用它已有
external_idString(255)，唯一（非空时）iam 的 sub。投影靠它与 iam 用户对应已有
nameText显示名，随令牌同步已有
emailString(320)，可空随令牌同步；只用于展示和检索，不作为身份新增
org_idString(64)，可空组织；智能体可见范围的边界新增
statusString(16)，active / disableddisabled 的用户所有请求都返回 401；执行器也不再为他启动新的 run新增
last_seen_at时间最多每 10 分钟写一次，避免每个请求都写库新增
updated_at时间资料最后同步时间新增
created_at时间首次登记时间已有

角色不存库：它来自令牌，存一份就会出现"iam 已经收回权限，库里还写着有"的不一致。

6.2 首次出现自动登记（JIT Provisioning）

async def resolve_user(claims) -> AppUser:
    user = cache.get(claims.sub) or await repo.by_external_id(claims.sub)
    if user is None:
        # 并发首登：靠 external_id 的唯一索引兜底；冲突就重查一次
        user = await repo.insert_or_get(external_id=claims.sub, name=claims.name, email=claims.email,
                                        org_id=claims.org, status="active")
    elif user.profile_differs(claims):
        await repo.update_profile(user.id, name=..., email=..., org_id=...)   # 资料以 iam 为准
    if user.status == "disabled" or claims.active is False:
        raise Unauthorized
    await repo.touch_last_seen(user.id, at_most_every=600)
    cache.put(claims.sub, user, ttl=60)
    return user
场景处理
新用户第一次访问插入一行，生成内部 id
两个请求同时首登external_id 唯一索引保证只插入一行；插入冲突的那个请求重新查询
改名、换邮箱、调组织下一次请求时按令牌更新（以 iam 为准）
禁用首选 iam 不再签发令牌；令牌里 active=false 也会把投影标记成 disabled。iam 如果提供变更通知（webhook），可以立即标记，不必等令牌过期
删除（离职）投影不删，只标记 disabled：历史会话、审批记录还要能显示是谁。数据处置（移交或清除）是单独的流程，见第 16 节的待决问题
dev 模式X-User-Id 对应的用户不存在时，同样自动登记（名字记成 dev-xxxx），解决 G5

7.1 两层判定

  1. 角色（粗粒度，来自令牌）：这个人能不能做这一类事，比如"能不能创建智能体"。
  2. 资源归属（细粒度，运行时判定）：这个人能不能动这一个资源，比如"这个会话是不是他的"。

7.3 归属链：一切运行时数据都归到"根会话的所有者"

判定方式：从请求里的资源 id 出发，取到它所在的会话，再取 root_thread.created_by，和 Principal 比较。实现上用一条带 JOIN 的查询完成，不额外增加请求次数。子会话的 created_by 本来就继承自父会话（services/subagent.py），所以直接比较也成立。

7.4 拒绝时返回什么

  • 资源不属于你 → 返回 404，不返回 403：403 等于告诉对方"这个 id 存在"，会泄露会话的存在。
  • 角色不够 → 返回 403：比如 member 去创建智能体。这里不涉及具体资源，没有泄露问题。
  • 身份无效 → 返回 401，响应里不说明具体原因（是过期、签名错误还是用户被禁用），原因写进服务端日志。

8. 数据隔离：每一层怎么做

层现状设计
会话列表不按用户过滤（G2）WHERE created_by = :me，并补上索引 (created_by, updated_at DESC, id DESC)
按 id 访问（会话、消息、事件流、run、取消、审批）不检查归属（G2、G3）统一走 authz.owned_thread() / owned_run()，不属于你就返回 404
事件流 SSE同上建立连接时检查一次归属；Redis 的事件流键按会话命名，不需要再加用户维度
对象存储{user}/{thread}/… 已隔离不变。前提是身份可信（G1 修好之后才真正成立）
记忆按会话所有者 已隔离不变
会话 Pod按用户计配额 已有不变；被禁用的用户，由 cluster 的孤儿回收按会话清理他的 Pod
智能体全局可见（G4）第 1 期按角色和创建者控制编辑；第 2 期加 org_id 和可见范围
遥测没有用户维度根 span 带 langfuse.user.id（见 Langfuse 接入设计）

9. 数据模型变更

遵守"不建外键"的约定（迁移 0013）：引用完整性由代码保证。

# 迁移 0014_user_module（示意）
ALTER TABLE app_user ADD COLUMN email        VARCHAR(320);
ALTER TABLE app_user ADD COLUMN org_id       VARCHAR(64);
ALTER TABLE app_user ADD COLUMN status       VARCHAR(16) NOT NULL DEFAULT 'active';   -- CHECK IN ('active','disabled')
ALTER TABLE app_user ADD COLUMN last_seen_at TIMESTAMPTZ;
ALTER TABLE app_user ADD COLUMN updated_at   TIMESTAMPTZ NOT NULL DEFAULT now();
CREATE INDEX ix_app_user_org ON app_user (org_id);

ALTER TABLE run ADD COLUMN created_by UUID;            -- 发起人（G6）；存量 run 回填为会话所有者
UPDATE run SET created_by = thread.created_by FROM thread WHERE run.thread_id = thread.id;

CREATE INDEX ix_thread_owner_recent ON thread (created_by, updated_at DESC, id DESC)
  WHERE parent_thread_id IS NULL;                     -- 会话列表

-- 第 2 期
ALTER TABLE agent ADD COLUMN org_id     VARCHAR(64);
ALTER TABLE agent ADD COLUMN visibility VARCHAR(16) NOT NULL DEFAULT 'org';   -- private / org / public
变更理由
run.created_by以后会话共享时，"谁发起的这一轮"和"会话是谁的"不再是同一个人；费用归属也要靠它。子 run 的发起人填父 run 的发起人
会话列表的部分索引列表从全表扫描变成按用户查询，没有这个索引会变慢
不加 thread.org_id会话只归个人，组织维度可以通过所有者推出来，不重复存储

10. API 设计

10.1 新增

接口说明
GET /v1/me当前用户：id、name、email、org_id、roles、auth_mode，以及用量摘要（本月 token、在跑的 Pod 数 / 配额）。前端据此显示用户菜单，并按角色显示或隐藏"新建智能体"
GET /v1/users?q=（admin）本组织的用户投影列表，只读；用于展示"智能体由谁创建"等

10.2 现有接口的行为变化

接口变化
GET /v1/threads只返回自己的会话
GET/PATCH/DELETE /v1/threads/{id}、/messages、/events、POST /runs不属于自己 → 404
GET /v1/runs/{id}、/cancel、/approvals按 run 所在根会话的所有者判定 → 404
POST /v1/runs/{id}/approvals/{aid}同上；decided_by 记录真实的决策人
POST /v1/agents、PATCH、/status需要 builder / admin；编辑还要求是创建者或 admin → 403
GET /v1/agentsmember 只能看到已启用的；builder 还能看到自己的草稿
全部接口jwt 模式下没有有效令牌 → 401。X-User-Id 请求头被忽略（OpenAPI 文档里也移除这个参数）

11. 代码结构

server/src/atlas_server/
├── auth/                          ← 取代 identity.py（保留 identity.py 作为兼容的再导出，过渡期后删除）
│   ├── principal.py               Principal 数据类（user_id · external_id · org_id · roles · name）
│   ├── tokens.py                  JWT 验证 · JWKS 缓存与轮换 · 时钟偏差
│   ├── provisioning.py            resolve_user：首次登记 · 资料同步 · 禁用检查 · 进程内缓存
│   ├── dependency.py              current_principal（dev / jwt 两种模式）→ CurrentPrincipalDep
│   └── authz.py                   require_role() · owned_thread() · owned_run() · can_edit_agent()
├── deps.py                        CurrentUserDep 保留为 Principal.user_id 的别名，现有接口签名不用改
├── repositories/user.py           by_external_id · insert_or_get · update_profile · touch_last_seen
├── repositories/thread.py         list(owner=…) · get_owned(thread_id, owner) —— 带 JOIN 的归属查询
├── repositories/run.py            get_owned(run_id, owner) —— run → 会话 → 根会话所有者
└── api/v1/me.py                   GET /v1/me
  • "身份只有一个入口"这条纪律保留：current_principal 是唯一的身份来源，service 层不允许自己读请求头。
  • 归属检查放在 repository 的查询里（get_owned），不是取出来之后再在接口里比较。这样漏写检查的接口会因为拿不到数据而暴露出来，而不是悄悄放行。
  • 后台执行器继续用 thread.created_by 作为身份，不依赖请求上下文。

登录没有由 BFF 完成（OIDC 跳转），浏览器只持有 HttpOnly 的会话 Cookie，前端代码碰不到令牌
请求带 X-User-Id（来自 NEXT_PUBLIC_USER_ID）同源请求 BFF，自动带 Cookie；authHeaders() 返回空
401不会出现统一拦截，跳转到 BFF 的登录地址
用户菜单显示 dev 用户用 /v1/me 显示名字和组织，提供退出入口
按角色显示全部可见没有 builder 角色时隐藏"新建智能体"和编辑入口。这只是体验优化，真正的权限在后端判定

13. 存量数据与上线

  • 存量数据：现在所有会话、智能体都属于默认用户 00000000-…-0001。切到 jwt 模式后，这个用户不会再有人登录，数据实际上就成了无主数据。提供一个管理脚本 atlas-admin claim --from default --to <外部 id>，把它们移交给指定的真实用户。移交时对象存储的路径也要迁移，因为路径里带着用户 id，所以脚本要同时搬对象存储。
  • 上线顺序：① 部署代码（仍然是 dev 模式，行为不变）→ ② 跑迁移 0014 → ③ 配置 iam 的 JWKS、issuer、audience → ④ 切到 auth_mode=jwt → ⑤ 网络策略只允许 BFF 访问运行时（已有规划里的部署约束）。
  • 回滚：把 auth_mode 切回 dev 就行，新增的列和索引不影响旧逻辑。

14. 安全清单

威胁措施
伪造身份请求头jwt 模式下忽略 X-User-Id；dev 模式在非本地监听地址时启动告警
伪造、篡改令牌只接受非对称签名；校验 iss、aud、exp；拒绝 alg: none 和 HS*
越权访问别人的资源（IDOR）归属检查放进 repository 查询；越权一律返回 404；每个按 id 访问的接口都有越权测试
令牌泄露短有效期（≤ 15 分钟）；令牌不进 URL、不进日志；前端碰不到令牌（只有 HttpOnly Cookie）
绕过 BFF 直接访问运行时网络策略：运行时只接受 BFF 和内部服务的访问。即使被绕过，没有有效令牌也是 401
用户被禁用后仍能访问令牌短有效期加投影的 status 检查；iam 的变更通知可以做到即时失效
枚举其他用户用户列表只对本组织的 admin 开放

16. 分期、风险与待决问题

期内容解决
1 · 隔离与可信身份auth 包（dev / jwt）、用户投影和首次登记、会话 / run / 审批的归属检查、run.created_by、/v1/me、前端 401 处理G1、G2、G3、G5、G6、G7
2 · 组织与智能体权限角色判定、智能体的 org_id 和可见范围、admin 用户列表G4
3 · 共享与外部身份会话共享（多人协作）、排障审计入口、MCP 改用签名令牌、离职用户的数据处置—
风险应对
Java 配置平面还没有就绪，jwt 模式无处可接令牌契约是标准的 OIDC / JWT，任何符合标准的身份服务都能先顶上（比如 Keycloak）；在那之前继续用 dev 模式，但只限本机使用
存量数据移交时漏搬对象存储移交脚本先搬对象存储、核对数量，再改库；支持重复执行
归属检查漏掉某个接口检查放在 repository 层，再加上"每个按 id 访问的接口都有越权测试"作为门槛

待决问题

  1. 身份服务：Java 配置平面的 iam 什么时候能就绪？如果短期内没有，是否先引入一个现成的身份服务（比如 Keycloak），让 jwt 模式先用起来？
  2. 组织模型：是否有多组织（多租户）的需求？如果只有一个组织，第 2 期的 org_id 可以先不做。
  3. admin 能否查看别人的会话：本设计默认不能（对话属于个人数据），排障走单独的审计入口。是否符合你们的合规要求？
  4. 离职用户的数据：会话和工作区文件是移交给他人、保留只读，还是到期删除？
