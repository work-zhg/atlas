1. 现状与目标

部件现状
契约 SandboxProtocol（engine/contracts/sandbox.py）在 只管执行（id / execute / aexecute），不含文件操作；约定 /workspace 与文件系统是同一份数据，靠挂载保证
kernel 的 SandboxMiddleware、build_graph(sandbox=)在 装配接缝保留；assembly 恒传 None
工具目录里的 bash未实现 implemented=False，勾了会进 unsupported_tools 明确报出；schema 层强制 execute 进审批列表
Docker 沙箱已删 提交 e5cfb94：它的 /workspace 是容器本地盘，与 OSS 工作区不是同一份数据
cluster 服务（ACP Pod）已跑通 状态从 label 派生、ensure 幂等、Secret 先于 Pod、per-Pod 令牌、rclone FUSE 原生 sidecar 挂载（工作区 / 技能 / CLI 状态）、配额、按活会话回收孤儿
cluster 的闲置回收未实现 idle_ttl_s=1800 只有配置项，没有任何代码使用

目标：

  • 原生智能体勾选「Shell」后可用 execute：会话级 Pod，按需创建，/workspace 即会话工作区（文件工具写的，命令读得到；命令写的，文件工具读得到）。
  • 长命令不被时长上限误杀；server 重启 / 网络抖动后命令继续跑、结果不丢不重。
  • 默认安全：沙箱容器里默认没有任何凭据（按需挂载）、非 root、根只读、资源有上限；默认可出网（与 ACP 一致），可按智能体关闭。
  • 沙箱镜像可替换：评测（Terminal-Bench 等）能用题目自带的镜像当沙箱。

不在范围内：本地设备执行环境（本地部署）；快照回滚；GPU。

4. 关键决策

#决策备选理由
D1cluster 服务扩展 kind=sandbox，复用模板、Secret、令牌、配额、回收server 自己调 K8scluster 是全仓唯一有 K8s 写权限的进程；ACP 那套已在真集群踩过一轮坑（挂载顺序、传播、就绪竞态），重写一遍会再踩一遍
D2自有守护进程 sandboxd（HTTP + 流式响应）K8s exec APIserver 没有也不该有 K8s 权限；exec API 做不到按命令 id 幂等与断线重连（server 重启时命令会被一起带走）；进程组管理、输出截断、记账都要自己做
D3守护进程由 init 容器注入：独立可执行文件拷进共享 emptyDir，主容器用任意镜像运行它守护进程打进固定镜像沙箱镜像可替换：评测用题目镜像、团队用自己的开发镜像，都不需要预装任何东西。限制：要求 glibc 镜像（§17）
D4文件仍走对象存储 API，执行走沙箱；两者一致性靠「执行前刷新、执行后落盘」屏障（§7）沙箱存在时文件工具改走守护进程不推翻已完成的契约拆分；没有沙箱的会话（多数）不受影响；屏障把 FUSE 缓存窗口带来的不一致收在执行边界上
D5Pod 按 workspace_thread_id 建：原生子智能体共用父会话的沙箱每个子智能体一个 Pod工作区本来就是父会话的；共用一个 Pod 时子智能体装的依赖、起的进程父智能体也看得到，符合「共享工作区」的直觉；Pod 数不随委派膨胀
D6不设命令时长上限，只做静默卡死检测（无输出且无 CPU 增长）；模型可显式传 timeout默认 120 秒超时（旧 Docker）「只要在干活就不中断」原则；编译、测试、数据处理常常是分钟到小时级。只看输出会误杀安静的长任务，加上 CPU 才算真卡死
D7执行以 tool_call_id 幂等，可按 id 重新接上每次请求都新跑断联恢复：server 重启、网络抖动后接回同一个进程的输出，而不是重跑一遍（重跑会重复副作用）
D8安全档位 profile：strict（默认）与 task（root、可写根，仅评测 / 管理员）只有一档真实题目环境常需要 root 与 apt 安装；但这不能成为普通智能体的默认
D9默认出网（与 ACP 一致），智能体可设 network: none 关闭；凭据默认不给、按需挂载（git 凭据档案等，沿用 ACP 的档案机制）默认不出网（native §03 原建议）装依赖、拉代码是沙箱最常见的用途，默认断网会让多数任务先失败一次；数据外传的风险主要来自凭据，所以把控制点放在「凭据不进容器、按需挂载」上（2026-10-13 评审结论）
D10审批规则不变：勾了 Shell 仍强制 execute 进审批列表有了隔离就默认免审批先不改变安全姿态；无人值守场景（评测）由调用方的审批策略自动处理。是否按隔离程度放宽，P3 再议（§16）

在 cluster 的 template.py 里新增 sandbox_pod_manifest，与 pod_manifest 共用卷、挂载器、Secret 的渲染函数；差异如下：

metadata:

spec:

  terminationGracePeriodSeconds: 30
  restartPolicy: Always
  volumes:  workspace / skills / tmp / home / repos(emptyDir) / atlas-bin(emptyDir) / sandbox-token(Secret)
  initContainers:
    - name: sandboxd-installer                     # 普通 init：拷贝后退出
      image: atlas-sandboxd:{version}
      command: [cp, -a, /dist/., /opt/atlas/]
    - oss-workspace（原生 sidecar，同 ACP）         # 挂 {user}/{workspace_thread}/workspace，rw；加 --rc（§7）
    - oss-skills（原生 sidecar，同 ACP）            # 挂 {user}/{thread}/skills，ro
    - barrier（原生 sidecar）                       # atlas-sandboxd 镜像，持有 rc 口令，只暴露 forget / queue（§7.2）
  containers:

      command: [/opt/atlas/bin/sandboxd]
      env:  SANDBOXD_TOKEN_FILE / SANDBOXD_SESSION_ID / SANDBOXD_PORT / HOME=/home/agent

      volumeMounts: /workspace(HostToContainer) /skills(ro) /tmp /home/agent /repos /opt/atlas(ro) /run/secrets/atlas(ro)

      resources: {requests, limits}                # 来自 profile 与智能体配置（有上限）
      securityContext:                             # strict 档

6. 沙箱守护进程 sandboxd

6.1 形态

  • Python 实现（与仓库技术栈一致），新包 sandboxd/；用独立 Python 发行版（python-build-standalone）打包成自带解释器的目录，放进 atlas-sandboxd 镜像的 /dist。不依赖目标镜像里有没有 Python、是什么版本。
  • 不 import 任何 atlas 包（import-linter 合约），依赖尽量少（HTTP 服务 + 进程管理）。
  • 单进程异步；命令以子进程运行。

6.2 接口

鉴权：Authorization: Bearer {per-Pod 令牌}；X-Atlas-Sandbox: {workspace_thread_id}（会话绑定，同 bridge §4.3）

POST /v1/execs                              开始一条命令（按 exec_id 幂等）
  {exec_id: "{run_id}:{tool_call_id}", command, cwd?, env?, timeout_s?, refresh_paths?: [...]}
  → 200  application/x-ndjson 流：
     {"t":"started","pid":123,"boot_id":"…"}
     {"t":"output","seq":1,"data":"…"}          # stdout/stderr 合并，按块
     {"t":"heartbeat","cpu_s":12.3}              # 每 15s；无输出时让对端知道还活着
     {"t":"exited","exit_code":0,"signal":null,"duration_ms":5321,"truncated":false,
      "stalled":false,"flushed":true,"output_bytes":10240}
  同一 exec_id 已存在 → 不重跑，按 after 游标接上原来的流（运行中）或直接回放结果（已结束）

GET  /v1/execs/{exec_id}?after={seq}        重新接上（断线、server 重启后）
POST /v1/execs/{exec_id}/kill               结束进程组（SIGTERM，宽限后 SIGKILL）
POST /v1/execs/kill?run_id=…                结束某个 run 的全部命令（取消一轮时）
GET  /v1/info                               boot_id、镜像、profile、资源、正在运行的 exec、最近活动时间
GET  /readyz   GET /healthz

6.3 执行语义

项目做法原因
shellbash -lc（无 bash 时 sh -c）与模型的习惯一致
stdin/dev/null交互式命令（等输入的 apt、git 提示）立即失败而不是永远挂着
进程组每条命令 setsid 新会话；kill 整个进程组只杀 shell 会留下孤儿子进程
环境变量白名单（PATH、HOME、LANG、TERM、TZ）+ 调用方传入的非敏感变量守护进程自己的配置（令牌路径等）不进命令环境
输出落盘到 /tmp/.sandboxd/{exec_id}.log；返回给模型的部分做头尾截断（默认 100 KB），完整输出可经文件工具外置读取yes 不该打爆内存；大输出由 kernel 的外置机制接手
后台进程命令里 & / nohup 起的进程在命令结束后继续存在（同一 Pod 内），直到 Pod 被回收起服务再测试是常见用法；在工具描述里写明
并发同时运行上限（默认 8），超出排队并行子智能体共用一个 Pod
记录保留结束后保留 exec 记录与输出文件 1 小时（可配），供重新接上断联恢复
boot_id守护进程启动时生成server 据此发现「Pod 已重建」，提示模型环境已重置

7. 文件一致性屏障

文件工具经对象存储 API 读写，命令经 FUSE 读写同一前缀。rclone 挂载有两个窗口（ACP 模板里的参数）：

  • 读缓存 --dir-cache-time 5s：文件工具刚写的文件，命令最长 5 秒内可能看不到（或看到旧内容）。
  • 写回 --vfs-write-back 1s + 上传耗时：命令刚写的文件，文件工具可能还读不到。

典型失败：write_file("app.py") 后立刻 execute("python app.py") 跑的是旧代码——不报错，只是结果不对，最难排查。所以在每次执行的边界上加屏障：

执行前 server 记下本会话自上次执行以来文件工具写过 / 删过的路径（FilesystemMiddleware 已有 file.written 事件） → 随请求带上 refresh_paths → sandboxd 调 rclone 远程控制：vfs/forget（这些路径）+ vfs/refresh（所在目录） 路径过多（> 200）时退化为刷新整个工作区根 执行后 命令退出 → sandboxd 轮询 rclone 的写回队列（vfs/stats / vfs/queue），等到本挂载点没有待上传文件 → 再返回 exited{flushed: true}；server 收到后文件工具即可读到命令的产物
  • rclone 以 --rc --rc-addr 127.0.0.1:5572 --rc-no-auth 启动；同一 Pod 共享网络命名空间，只有 Pod 内可达（命令也能访问它，但它只暴露本会话这一个挂载的缓存控制，不含凭据读取接口之外的能力——见 §17）。
  • 执行后的等待不设上限（与「不设运行上限」一致），但会在心跳里带上待上传数量；挂载器异常（进程退出、队列长时间不减）时返回 flushed: false 并附说明，由模型和用户看到，而不是假装成功。
  • 屏障只覆盖「文件工具 ↔ 命令」之间；后台进程在命令结束后继续写的文件，按 rclone 自身窗口最终一致（工具描述里写明）。

7.1 P0 实测结论（2026-10-13，rclone 1.75.1 + MinIO）

场景结果
对象存储侧改写一个已被挂载读过的文件，立即经挂载读读到的是「新内容按旧长度截断」（如 v2-new 读成 v2-）——不是旧数据而是错数据，屏障必须有
vfs/refresh（含 recursive）无效
vfs/forget file=…，默认 --attr-timeout 1s0/6 正确：内核 FUSE 属性缓存（1 秒）仍返回旧长度
vfs/forget file=… + --attr-timeout 06/6 正确
对象存储侧新建文件forget 父目录（或文件）后可见；新建的多级目录要 forget 挂载里已存在的最近祖先目录
对象存储侧删除文件forget 父目录后消失
经挂载写 30 MB 后的写回vfs/queue 列出待上传项，约 1.2 秒清空；清空后对象存储可见完整大小。vfs/stats 的 diskCache.uploadsInProgress 可作辅助

据此确定的做法：

  • 沙箱的工作区挂载器加 --attr-timeout 0 与 --rc --rc-addr 127.0.0.1:5572 --rc-no-auth（只影响沙箱 Pod，不改 ACP）。
  • 执行前：对每个 refresh_path，vfs/forget file=路径，再对「挂载里已存在的最近祖先目录」vfs/forget dir=…（根目录时不带参数 forget 全部）。
  • 执行后：轮询 vfs/queue 直到为空（不设上限，心跳里带待上传数）。

7.2 远程控制端口的隔离

同一 Pod 的容器共享网络命名空间，127.0.0.1:5572 对沙箱里的命令同样可达；而 rclone 的远程控制能调 operations/*（以挂载器的凭据读写整桶）与 config/*。不加限制就等于把对象存储凭据交给了命令。做法：

oss-workspace（挂载器） rclone mount … --rc --rc-addr 127.0.0.1:5572 --rc-user sbx 口令经环境变量 RCLONE_RC_PASS（secretKeyRef），只在这个容器里 barrier（新 sidecar） 镜像 = atlas-sandboxd，模式 barrier；同样经 secretKeyRef 拿口令 只监听 127.0.0.1:5573，只提供两个操作： POST /forget {paths} → vfs/forget（按 §7.1 的规则） GET /queue → vfs/queue 的待上传数 sandbox（主容器） sandboxd 调 127.0.0.1:5573；容器里没有口令 命令即便直接访问 5573，也只能让缓存失效或查看队列长度 —— 无害

为什么不让 sandboxd 自己持有口令：sandboxd 与命令是同一个用户、同一个容器，它能读的文件命令都能读（strict 档不允许切换用户）。容器边界是唯一可靠的隔离，所以持有口令的一方必须在另一个容器里。

9. 生命周期与回收

会话创建 → 不建 Pod（多数原生会话用不到沙箱） 首次 execute → ensure（kind=sandbox）：Secret → Pod → 就绪 → 执行。模型看到的只是这一次调用慢几秒 会话活跃 → Pod 保持 闲置（无运行中命令，且最近活动 > idle_ttl_s）→ 删除 Pod；工作区在对象存储上，无损 再次 execute → 重新 ensure，boot_id 变化 → 提示「环境已重建」 会话删除 → release（Pod + Secret） server 启动 → reap：不在活会话名单里的 Pod 一律回收（已有机制，按 label 覆盖两种 kind）
  • 闲置回收（新增，ACP 一并受益）：cluster 起一个周期任务（默认每分钟），对 atlas/kind=sandbox 的 Pod 读 sandboxd 的 /v1/info：有运行中命令的 Pod 永远不回收（不设运行上限）；无运行中命令且最近活动超过 idle_ttl_s（默认 30 分钟）才删除。ACP Pod 的闲置判据另议（要看 bridge 的会话状态），本期只做沙箱。
  • 配额：与 ACP Pod 共用每用户上限（quota_per_user）；超额时 ensure 返回 429，execute 把原话作为工具错误返回给模型（不让整轮失败）。
  • 预热池（P3）：沙箱 Pod 高度同质，适合预热（执行环境 §07 的建议）；先测冷启动耗时再决定。

10. 子智能体与并发

场景行为
原生子智能体（persistent / ephemeral）与父会话共用同一个沙箱 Pod（键是 workspace_thread_id）；技能卷挂的是父会话的技能前缀（子智能体自己的技能仍按现有方式拷入其会话前缀，经文件工具可读）。P1 限制：子智能体的技能脚本若需要在沙箱里执行，需由文件工具读取后在 /workspace 执行（见 §17）
ACP 子智能体不变：自己的 ACP Pod，共享的是对象存储上的工作区
并行 ephemeral 子智能体同时执行命令sandboxd 并发执行（上限 8，排队）；各自的 exec_id 不冲突。它们共享文件与进程空间，互相踩踏（同时 pip install、同时改同一文件）由提示词提醒，平台不加锁

11. 长命令、取消与断联恢复

情况行为
命令运行很久不设时长上限；持续心跳（CPU 时间、输出量）；SSE 里以工具进度事件展示（P2：tool.output 增量）
静默卡死连续 tool_idle_s（沿用 acp_tool_idle_timeout_s，默认 600 秒）既无输出、进程组 CPU 时间也没有增长 → 判定卡死，结束进程组，返回已有输出与 stalled: true，工具结果写明「命令无输出且无 CPU 活动超过 N 秒，已结束」。sleep / 等网络这类「无 CPU」的命令若是有意为之，模型可显式传 timeout 或改成后台运行
模型显式 timeout守护进程内部计时并结束进程组（契约要求在沙箱内部兜一层）；这是模型自己的决定，不是平台上限
用户取消这一轮结束该 run 的全部命令；后台进程不受影响
server ↔ Pod 网络中断命令继续跑；PodSandbox 带游标重连 GET /v1/execs/{id}?after=，输出不丢不重
server 重启命令继续跑；run 恢复执行时重放同一个 tool_call → 同一 exec_id → 接上原命令（依赖 run 的恢复机制，ACP 的 re-attach 是待做项，原生同理）
Pod 中途消失（被删、节点故障、OOM）当前命令返回错误「沙箱已重启 / 被终止（原因：OOMKilled …）」；下次调用自动重建并提示环境已重置；不让整轮失败
挂载器异常就绪探针失败 → 不接新命令；屏障返回 flushed: false 并说明

12. 安全

威胁措施
命令读走凭据沙箱容器里没有模型凭据与对象存储凭据（后者只在 rclone sidecar，经 secretKeyRef，同 ACP）；令牌文件只读；enableServiceLinks: false、不挂 ServiceAccount 令牌
未授权调用守护进程per-Pod 令牌 + 会话绑定头；K8s 网络是平的，「在集群里」不是安全边界（同 bridge）
数据外传 / 横向访问默认可出网（同 ACP）；容器里默认没有凭据，凭据按需挂载（git 凭据档案经 Secret 只读挂载、GIT_CONFIG_GLOBAL 指向它，不写进 HOME）；network: none 时下发 NetworkPolicy 禁止全部出站（仅允许入站到守护进程端口）
越权与提权strict：非 root、根只读、drop ALL、禁止提权、seccomp RuntimeDefault；task 档仅允许名单可用
资源滥用CPU / 内存 limit；emptyDir sizeLimit；Pod 级 PID 上限（依赖 kubelet 的 podPidsLimit，部署时配置）；守护进程并发上限；输出截断
容器逃逸P3：为沙箱 Pod 配 RuntimeClass（gVisor / Kata），与 ACP 共用开关
对象存储前缀越界rclone 用的是整桶凭据，但凭据不在可执行命令的容器里（同 ACP 的已知短板）；前缀级临时凭据（STS）是独立的后续事项
FUSE 挂载器需要 privileged沿用 ACP 的代价；csi 模式可避免（同 ACP 的取舍）
本机注意：Docker Desktop 自带的 K8s 网络插件可能不执行 NetworkPolicy。network: none 落地前需实测；若不执行，本机的「不出网」只是声明，提示词不能对模型说「无网络」。

13. 可观测性

  • 链路：现有的工具 span 下挂 sandbox.ensure（是否新建、等待就绪耗时）与 sandbox.exec（exit_code、duration、output_bytes、truncated、stalled、flushed、屏障耗时、boot_id）；命令正文与输出按内容档位进 Langfuse（同现有规则）。
  • 事件：Pod 重建、OOMKilled、配额拒绝作为 run 事件可见（用户在对话里能看到「沙箱已重建」）。
  • 指标：冷启动耗时分布、活跃沙箱 Pod 数、闲置回收数、屏障等待时间、卡死判定次数。

17. 风险与限制

风险 / 限制说明缓解
文件一致性屏障依赖 rclone 远程控制能力（已验证）；后台进程的写入不在屏障内工具描述写明
rclone 远程控制端口同一 Pod 共享网络，命令也能访问 127.0.0.1:5572；rclone 的 rc 有 config/*、operations/*，等于把挂载器的整桶凭据交给了命令已在设计中处理（§7.2）：rc 加口令，口令只给挂载器与屏障 sidecar；命令能访问到的只有屏障 sidecar 的两个无害操作
FUSE 性能/workspace 上的大量小文件 IO（依赖安装、git）慢引导到 /repos、HOME（本地盘），产物再拷回 /workspace
环境不持久闲置回收或 Pod 重建后，安装的软件与后台进程丢失boot_id 提示模型；常用依赖放进自定义镜像（P2）
sandboxd 注入的镜像要求需要 glibc；musl 镜像需另一份构建P0 确认；镜像校验时提示
审批体验每条命令都要审批，交互式使用会很烦本期不改安全姿态；P3 单独评审放宽规则

regenerate 的副作用重跑会在已改动的环境上再执行一次沿用 native §08：UI 明确告知，不做快照回滚
默认出网命令能访问公网与集群内可达的服务容器内无凭据（按需挂载）；内部服务本就要求认证；需要隔离的智能体设 network: none
