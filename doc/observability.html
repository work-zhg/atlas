Observability

可观测性设计

按 OpenTelemetry GenAI 语义约定采集，Collector 分流到 Langfuse 与通用后端。目标是让一次 Run 在 Server、Higress、Bridge、CLI 四层上拼成同一条可追查的链路。

OTelGenAI semconvLangfuseCollector成本归因
本文的事实基础

GenAI 语义约定的属性名与指标名取自 opentelemetry-semantic-conventions 0.65b0；Claude Code 的遥测开关、环境变量与指标名取自其 2.1.220 可执行文件的实测提取。两者均已核对，未凭记忆书写。

GenAI 语义约定目前仍在 _incubating 命名空间下，属性名可能随版本变化 —— 采集侧应当把它当作可能演进的契约，见 §11。

01定位与三个信号

这套系统的可观测性要回答三类完全不同的问题，对应三种信号，不能混为一谈：

信号回答什么问题典型场景
Trace这一次为什么慢 / 为什么错用户说「刚才那次改文件卡了两分钟」，需要定位到具体哪一环
Metric整体是否健康、趋势如何审批等待时长的 P95 是否在恶化；token 成本的走势
Log / Event当时究竟发生了什么某次审批被拒的具体原因；某条记忆是怎么被提炼出来的

Langfuse 不替代通用后端

两类后端各有不可替代的用途

Langfuse 擅长 LLM 维度：按会话看提示词与回答、评估打分、按模型/用户的成本归因。但它不是 APM —— Pod 冷启动慢、NAS 写入抖动、WebSocket 断连这类问题在它那里看不出来。

所以 Collector 要分流而不是转发：LLM 相关的 span 进 Langfuse，全量 trace 进通用 trace 后端，metrics 进时序库。用一个后端硬扛两类问题，最后两类都查不好。

03语义约定

用 OTel 的 GenAI 语义约定，不自定义字段。理由在系统架构 §07说过：只有共用同一套约定，四层的 span 才能拼成一条链路，也才能被 Langfuse 这类现成后端直接识别。

核心属性（0.65b0 实测）

# 用量（注意缓存与推理 token 是独立字段）

gen_ai.usage.cache_read.input_tokens

# Agent 与工具

# 会带内容，默认不采集（§08）
gen_ai.input.messages / gen_ai.output.messages
gen_ai.prompt / gen_ai.completion

标准指标

gen_ai.client.operation.duration
gen_ai.client.token.usage

缓存 token 必须单独记

cache_read.input_tokens 与 cache_creation.input_tokens 是独立字段，计价也不同。把它们并进 input_tokens 会让成本核算（§10）系统性偏离 —— 对长会话尤其明显，缓存读取往往占输入的大头。

约定仍在 incubating

这些属性目前位于 _incubating 命名空间，属性名可能随版本调整。采集侧不要把属性名硬编码散落各处 —— 集中在一个常量模块里，升级时只改一处。Collector 也可以配 rename processor 做过渡期兼容。

04一次 Run 的 Trace

Run 是 trace 的根。不是 Session（太长，一条 trace 装不下），也不是单次模型调用（太碎，看不到因果）。

顾问

Run (root)                             invoke_agent
├─ memory.search                        retrieval        # 注入前检索
├─ llm.chat                             chat             # 经 Higress
│   └─ higress.upstream                                  # 网关侧 span
├─ tool.execute                         execute_tool
│   └─ mcp.call                                          # 经 Higress
├─ llm.chat                             chat             # 带工具结果再来一轮
└─ （Run 结束后）
    memory.extract                      独立 trace + span link

记忆抽取是 Run 结束后的异步动作（记忆 §04），不要把它挂在 Run 的 trace 下 —— 那会让 Run 的耗时统计包含一个用户根本没在等的操作。用 span link 关联，各自独立计时。

助理

Run (root, Server)                     invoke_agent
└─ bridge.prompt                        # WS 往返
    └─ acp.session.prompt               # ACP 请求
        ├─ tool_call                    execute_tool     # 由 session/update 还原
        ├─ request_permission           ← 含用户等待时长
        └─ CLI 自身的遥测（§05）
审批等待必须是独立 span

助理的一次 Run 里可能有几分钟花在等用户点「允许」上。如果这段时间混在 Run 总耗时里，所有延迟统计都会被它污染 —— 你会看到 P95 高得离谱，却分不清是系统慢还是用户在吃午饭。

把 request_permission 做成独立 span，并在指标上分开统计「系统耗时」与「等待人的耗时」。前者是工程问题，后者是产品问题，处理方式完全不同。

05助理侧：CLI 遥测接入

CLI 内部不是黑盒 —— 这推翻了早先的判断

系统架构 §07 原先写「CLI 内部的工具调用在链路上是一整段黑盒」。实测结论是：Claude Code 原生支持标准 OTel 导出，可以配置成上报到我们自己的 Collector。那段判断已更正。

开关与环境变量（2.1.220 实测）

CLAUDE_CODE_ENABLE_TELEMETRY=1
OTEL_EXPORTER_OTLP_ENDPOINT=https://collector.internal
OTEL_EXPORTER_OTLP_PROTOCOL / _HEADERS / _TIMEOUT / _COMPRESSION
OTEL_EXPORTER_OTLP_{TRACES,METRICS,LOGS}_ENDPOINT      # 可分信号分流
OTEL_METRIC_EXPORT_INTERVAL

# 关联与维度（默认关，按需开）
OTEL_RESOURCE_ATTRIBUTES=platform.session_id=…,platform.agent_id=…
OTEL_METRICS_INCLUDE_SESSION_ID
OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTES
OTEL_METRICS_INCLUDE_ENTRYPOINT / _VERSION / _ACCOUNT_UUID

# 内容采集，默认关，见 §08
OTEL_LOG_USER_PROMPTS

Bridge 在 spawn adapter 时通过环境变量注入这些值（运行时链路 §11 的 CliProfile.env），CLI 继承后即生效。

TRACEPARENT 有生命周期错配

CLI 支持读 TRACEPARENT 环境变量接续 trace context。但环境变量在 spawn 时就固定了，而 adapter 进程要服务整个会话的多个 Run —— 于是所有 Run 的 span 都会挂到第一个 Run 的 trace 上。

所以可靠的关联方式是 OTEL_RESOURCE_ATTRIBUTES 注入平台 session_id，下游按资源属性 + 时间窗做关联；TRACEPARENT 只在会话级有意义，不要指望它做 Run 级串联。

本地部署下这是用户的机器

在用户电脑上启用 CLI 遥测，等于把他本机的工具执行、命令、会话时长上报到服务端。必须纳入 本地部署 §07 的授权范围，与目录授权同一个开关，并且默认关闭。云上 Pod 无此顾虑。

06关联维度

四层 span 要拼成一条链路，靠的是同一组 ID。它们正好是会话管理里已有的对象主键，不用另造：

维度载体传播方式
session_idgen_ai.conversation.id贯穿全部四层
run_id自定义属性Server / Bridge 层；CLI 层靠时间窗归属
user_id / tenant_id资源属性成本归因与配额的维度
agent_id + versiongen_ai.agent.id区分顾问与助理、以及 Agent 版本

Trace context 的传播路径

Server → Higress      HTTP header（traceparent）        标准，可靠
Server → Bridge       WS 消息体自带 traceparent 字段      自有协议，可靠
Bridge → adapter      ACP 的 _meta 扩展位              见下
Bridge → CLI 进程     TRACEPARENT 环境变量               仅会话级（§05）
ACP 的 _meta 正是传播 trace context 的地方

ACP 的请求模型（NewSessionRequest、PromptRequest 等）都带 _meta 扩展位。协议明确说实现不得对其中的值做假设 —— 这恰好意味着放一个 traceparent 进去是安全的：对方不认识就忽略，认识就能接续。

但也因为「可以忽略」，不能依赖它必然生效。把它当作锦上添花：能接上就得到完整链路，接不上则退回按 session_id 关联。

08内容与隐私

默认不采集内容

GenAI 约定里的 gen_ai.input.messages / gen_ai.output.messages / gen_ai.prompt / gen_ai.completion，以及 CLI 的 OTEL_LOG_USER_PROMPTS，都会把对话原文送进遥测系统。

这些内容里会有：用户的私有代码、.env 里的密钥、内部文档片段。一旦进了遥测管道，它们的留存期、访问控制、备份策略就和业务数据完全脱钩了 —— 而遥测系统的访问面通常比业务库宽得多。

分档

档位采集什么适用
元数据
默认		token 数、模型、耗时、finish_reason、工具名全部环境，包括本地部署
摘要+ 截断与脱敏后的片段需要 Langfuse 做质量分析时
全文+ 完整提示词与回答仅限显式开启、限定范围、限定留存期
脱敏只在 Collector 做

把脱敏逻辑散在 Server、Bridge、CLI 三处实现，等于三份规则要维护、三处都可能漏，而且新增来源时默认是不设防的。集中在 Collector 的 processor 里：规则一份，任何新来源自动受约束。

对应地，来源侧的职责是标注而非过滤 —— 把可能含敏感内容的属性打上统一标记，由 Collector 按档位决定丢弃、截断还是放行。

本地部署额外一层：CLI 遥测涉及用户本机行为，必须纳入用户授权，默认关闭（§05）。

09告警

判断标准只有一条：响不响都不知道该做什么的，不要设成告警。那类信息属于仪表盘，不属于寻呼机。

告警级别为什么值得被叫醒
Higress 不可用P1同时掐断推理与工具两条链路（架构 §06），全平台不可用
Run 失败率突增P1用户直接感知
Pod 调度失败 / 配额耗尽P2新会话起不来，但存量不受影响
记忆检索命中率跌至零P2静默失效 —— 不报错，功能等于没有，只能靠指标发现
审批等待 P95 异常增长P2可能是通知链路坏了，用户根本没收到审批请求
OOMKill 反复发生P2长会话被截断；§09 要求它与其他退出原因分开看
token 成本突增P3可能是死循环或滥用，但不紧急
本地设备批量离线P3多半是客户端发版问题
两类「静默失效」要专门盯

记忆命中率为零和遥测断流都不会报错。前者让记忆功能形同虚设，后者让所有告警失去依据 —— 而「没有告警」很容易被误读成「一切正常」。

给 Collector 本身配一个心跳指标，长时间没有数据流入要告警。可观测系统自己的可观测性是最容易被遗漏的一环。

10成本归因

成本要能归到人、团队、Agent三个维度，否则只能看到一个总数，既无法优化也无法分摊。

三个采集点，各有盲区

采集点覆盖盲区
Higress经网关的全部模型调用绕过网关的调用看不到
Server顾问的调用、记忆抽取助理内部的调用
CLI 遥测claude_code.cost.usage需显式开启；本地部署受授权约束
本地部署是成本盲区，这是设计使然

本地部署 §08 已说明：用户机器上的 CLI 用他自己的订阅直连模型厂商，不经 Higress。所以本地会话的模型成本平台看不到也不该看到 —— 那是用户自己的额度。

这不是缺陷，但必须在口径上说清楚：平台的成本报表不包含本地会话。如果对外有用量统计或计费承诺，这块要单独说明，否则数字对不上时会很被动。

别忘了记忆抽取

每个 Run 触发一次 add(infer=True)，那是一次真实的 LLM 调用（记忆 §11）。它不在用户的对话里，容易在成本核算中被漏掉，但会话量大时占比不低。打上独立的 gen_ai.operation.name 维度，让它在报表里可见可拆。

11待验证清单

#验证项影响
1 CLI 遥测的实际产出 —— 开启后真正发出哪些指标、维度是否含可用的关联字段、OTEL_RESOURCE_ATTRIBUTES 是否透传到 metrics 决定 §05 的接入是否成立，以及助理侧可观测性的实际深度
2 ACP adapter 是否透传 _meta 里的 traceparent；CLI 是否读取 TRACEPARENT 决定链路能否真正打通，还是只能按 session_id 关联
3 Higress 的 span 是否符合 GenAI 语义约定，还是需要在 Collector 侧做属性重命名 决定 Langfuse 能否直接识别网关侧数据
4 Mem0 内部的模型调用能否产生 span 并接入链路 决定记忆抽取的成本与耗时能否精确归因
5 GenAI 约定从 _incubating 转正后的属性变更范围 决定常量集中管理的必要程度与升级成本
6 全量 trace 的存储成本与采样策略 —— 尤其长会话与高频工具调用场景 决定采样在 Collector 还是 SDK 侧做

建议的上线顺序

  1. 先打通 Server 侧的 Run trace 与基础指标 —— 一条链路端到端可见，比五个来源各有一半数据有用得多。
  2. 再接 Higress —— 成本与限流的依据都在这里。
  3. 然后是 CLI 遥测 —— 云上 Pod 先行，验证 §11 第 1 项后再考虑本地。
  4. 内容采集最后，且默认关闭 —— 先把元数据档位跑稳，确有质量分析需求时再按 §08 分档开启。
