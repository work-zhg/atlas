Memory

记忆设计

用 Mem0 承载跨会话记忆，只按人划分作用域。写入对两类 Agent 完全统一 —— 都从 Message 账本抽取；读取则必然分叉 —— 顾问在进程内注入，助理只能经 MCP 工具与提示词。跨用户的 Agent 知识走 RAG，不在本文范围。

Mem0抽取注入MCP 记忆服务作用域
本文的事实基础

Mem0 的方法签名与参数取自 mem0ai 2.0.20 的实际代码（已下载核对）。注意 2.0 的 search() 用 filters 字典而非早期版本的 user_id 关键字 —— 参照旧文档写会跑不通。

01定位与边界

记忆是跨会话的、关于用户与其工作的结构化事实。它和另外两样东西容易混淆，必须划清：

是什么不是记忆的原因
Message 账本会话内容的完整记录会话内的原始流水，不跨会话、不去重、不提炼
记忆提炼后的持久事实—
Agent 知识
RAG，本期不做		服务所有用户的领域知识跨用户，信任模型完全不同，见下

典型的记忆条目：「用户的包管理器偏好是 pnpm」「这个仓库的测试命令是 make test」「用户不喜欢回答里带表情符号」。它们的共同点是 —— 下次会话里不说也应该成立。

一条判断标准

如果一条信息只在当前会话里有意义，它属于 Message，不属于记忆。记忆的价值在于用户不必重复自己；把会话细节当记忆存，只会让检索被噪声淹没，并在下次会话里注入一堆不相干的上下文。

为什么 Agent 知识不走记忆

一个很自然的诉求是：让 Agent 也积累知识 —— 用户 A 问过的产品问题，用户 B 再问时直接答得上来。这条路本期明确不走记忆实现，因为它和用户记忆的信任模型不是一回事：

用户记忆Agent 知识
作用范围仅该用户所有用户
写入来源该用户自己的对话任意用户的对话
记错的后果只影响他本人，且他能自己发现并纠正所有人拿到错误答案，且没人知道错在哪
可否自动抽取可以不可以
自动把任意用户说的话变成服务所有人的知识，是一个跨用户投毒面

攻击不需要任何技术手段：用户 B 在正常对话里陈述一个错误事实 → 被抽取进 Agent 知识 → 用户 A 之后问同样的问题，拿到那个错误答案。在对外的客服类场景里，这直接变成对外输出错误信息。

用户记忆记错了只坑他自己，而且他多半能当场发现；Agent 知识记错了坑所有人，而且没有任何一方处在能发现的位置上。这不是同一个量级的风险，因此也不该用同一套自动化机制。

Agent 知识的正确形态：RAG + 提炼 + 事实核查

它应当是经过总结提炼、且通过事实核查的数据，来源受控、入库有审、可溯源可撤回 —— 本质上是一条内容生产流水线，不是一个从对话里自动长出来的副产品。

因此它归 RAG / 知识库，走独立的设计与独立的写入通道，与本文描述的记忆系统不共用作用域、不共用抽取器。本期不做。

02数据流

03作用域映射

Mem0 的 add() 与 search() 用三个 ID 划分作用域，至少要有一个。我们的映射：

Mem0 参数我们填什么语义
user_id平台用户 ID主作用域。跨会话、跨 Agent、跨项目的用户级事实
agent_id不使用明确排除。跨用户的 agent 知识走 RAG，不走记忆，理由见 §01
run_id不使用Mem0 的 run 是一次运行，与我们的 Run 语义不同，且记忆不该按轮次隔离
metadata{workspace, source_session, source_run}项目隔离与溯源，靠 filters 过滤

项目级隔离靠 metadata，不靠 run_id

用户在 A 仓库的约定不该泄漏到 B 仓库。Mem0 2.0 的 search(filters=...) 支持 metadata 过滤，所以：

# 写入时标记来源
mem.add(messages, user_id="u_123",
        metadata={"workspace": "repo/deer-flow",
                  "source_session": "sess_…", "source_run": "run_…"})

# 检索时两层：用户级 + 当前项目级
mem.search(query, filters={"user_id": "u_123"}, top_k=5)
mem.search(query, filters={"user_id": "u_123",
                           "workspace": "repo/deer-flow"}, top_k=5)
记忆跨 Agent 共享，这是刻意的

用户告诉顾问「我用 pnpm」，助理下次动手时应该知道。它们是同一个用户的两个助手，不是两个互不通气的系统。

所以唯一的实体作用域是 user_id：记忆只按人划分，不按 Agent 划分。检索规则因此只有一条 —— 用当前用户去查，不需要 OR、不需要合并多次查询、不需要哨兵值。

顺带避开了 Mem0 的一个限制

如果真要做「用户维度 ∪ Agent 维度」的检索，单次 search() 做不到。代码里对顶层 filters 有硬校验：

if not any(key in effective_filters for key in ("user_id","agent_id","run_id")):
    raise ValueError("filters must contain at least one of: …")

顶层必须有实体 ID，而它与 OR 之间是 AND 关系 —— {"OR":[{"user_id":…},{"agent_id":…}]} 直接报错，{"user_id":…, "OR":[…]} 又退化成纯 user 过滤。只能查两次再在应用层合并。单一作用域让这个问题不存在。

metadata 的溯源字段不是装饰

source_session / source_run 让每条记忆能回指到它的出处。用户问「你怎么知道我用 pnpm」时要答得出来，记忆出错时也要能定位是哪次对话引入的。没有溯源的记忆没法审计，也没法修。

04写入：两类 Agent 统一

抽取器不需要知道是谁产生的内容

顾问和助理都把内容固化进同一个 Message 账本。记忆抽取是 Message 的下游消费者，因此写入路径对两类 Agent 完全一致 —— 不需要两套实现，也不会有两套口径。

触发与流程

Run 置 completed
   ↓ 异步入队（绝不阻塞会话）
取出该 Run 的 Message
   ↓ 过滤（见下）
mem.add(messages=[{"role":…, "content":…}, …],
        user_id=<平台用户>,
        metadata={"workspace":…, "source_session":…, "source_run":…},
        infer=True)
   ↓ Mem0 内部：LLM 提炼事实 → 与既有记忆比对 → 新增 / 更新 / 忽略

喂什么给抽取器

Message 类型送入理由
user是用户的偏好、约束、指令主要在这里
assistant 正文是结论与达成的共识
tool 调用与结果否体量大、噪声高，绝大多数是过程细节
system（审批、会话事件）否运维信息，不是关于用户的事实
工具结果里确实可能有有价值的事实

比如助理跑了一次 make test 发现测试命令是什么。但工具输出的体量通常是对话正文的几十倍，全量送进去会让抽取成本暴涨、且提炼质量下降。

先全部排除，观察漏掉了什么再补 —— 补的方式应当是让助理在正文里显式陈述（「这个仓库的测试命令是 X」），而不是把原始工具输出灌进抽取器。这样既保留了事实，又保住了信噪比。

无实质内容的 Run 跳过

纯工具执行、一句「好的」、以及被取消的 Run，都不值得花一次抽取的 LLM 调用。入队前先做一次廉价过滤（正文字数下限、stop_reason 不是 cancelled），否则记忆服务的成本会随会话量线性增长而收益极低。

05为什么不给模型写工具

一个自然的想法是给 Agent 一个 remember() 工具，让它自己判断什么值得记。我们不这么做，对两类 Agent 都是。

对顾问：regenerate 会导致重复写入

写记忆改变的是跨会话的持久状态。而顾问支持 regenerate 与编辑历史（会话管理 §04）—— 同一轮可能被重跑多次，每次都会再写一遍记忆。

给顾问一个写记忆的工具，regenerate 就变成了「重复写入记忆」，而它在 UI 上仍然是个看起来安全的重试按钮。这正是 §13 陷阱 01 描述的塌方。

对助理：技术上可以，但不该

  • 口径会分裂 —— 两类 Agent 用不同机制写记忆，提炼标准、去重策略、质量水平都会不一致，而它们写进的是同一个用户的记忆库。
  • 模型的自判不稳定 —— 「这值得记吗」是个没有客观标准的判断，同一个模型在不同上下文下会给出不同答案，结果是记忆库里塞满随机的琐事。
  • Mem0 的价值正在抽取 —— 它内置的提炼、与既有记忆比对、增量更新，比模型临时起意调一次工具要可靠。绕过它等于只把 Mem0 当键值存储用。
显式的「记住这个」也不需要写工具

用户说「记住我喜欢用 pnpm」时，这句话本身就在 Message 账本里，抽取器会看到并提炼出来。服务端抽取天然覆盖了这个场景，不需要额外通道。

06读取：顾问

顾问跑在我们自己的进程里，create_agent 构造，每轮从 Message 表重建输入（会话管理 §05）。这给了记忆注入最好的位置。

主路径：中间件注入

class MemoryMiddleware(AgentMiddleware):
    async def awrap_model_call(self, request, handler):
        hits = await mem.search(
            query=<本轮用户输入>,
            filters={"user_id": ctx.user_id, "workspace": ctx.workspace},
            top_k=5, threshold=0.3,
        )
        # 作为隐藏上下文拼进本次模型请求
        request = inject_context(request, render(hits))
        return await handler(request)
注入发生在模型请求层，不进 graph state

三个后果，都是我们想要的：

  • 不污染 Message 账本 —— 记忆不是对话内容，不该出现在会话记录里，也不该被下一轮的抽取器当成用户说的话再提炼一遍（否则记忆会自我强化）
  • 每轮按当前问题重新检索 —— 顾问无状态重建输入，正好每轮注入最相关的那几条，而不是把会话开始时的快照一直带着
  • regenerate 行为一致 —— 重跑时重新检索，不会因为上次注入的内容残留在历史里而产生偏差

辅路径：只读检索工具

再给顾问一个 search_memory 工具，用于注入没覆盖到的深挖场景（用户问「我之前跟你说过什么偏好」）。

只有 search，没有 add / update / delete —— 纯读取，重跑多少次都不改变任何状态，可以安全地挂进顾问的工具集。

07读取：助理

助理跑在别人的进程里（ACP adapter + CLI），我们无法在它的模型请求层做任何事。能用的只有两个口子，都来自 ACP 协议本身。

主路径：MCP 记忆服务

把 Mem0 包成一个 MCP server，在 session/new 的 mcpServers 里传入（运行时链路 §07），指向 Higress：

mcp_servers = [
  { "type": "http", "name": "memory",
    "url": "https://higress.internal/mcp/memory",
    "headers": [
      { "name": "Authorization", "value": "Bearer <session-scoped-token>" }
    ] },
  …
]

CLI 于是原生拥有 search_memory 工具，需要时自己调。工具集同样只给 search。

辅路径：会话开始时注入一次

session/prompt 的 prompt 是 content block 数组，可以在首轮前置一段基础记忆（用户偏好、项目约定）。

这个注入是可见且累积的，只能做一次

与顾问不同，助理的上下文由 CLI 自己持有并持续累积。经 session/prompt 注入的内容会永久留在它的对话历史里：

  • 每轮都注入 → 记忆条目在 CLI 上下文里反复堆积，token 成本随轮次增长，且旧的注入无法撤回
  • 注入内容可见 —— 会进入 CLI 的 transcript，也会回流成 Message，用户在界面上看得到

所以策略必须是：会话开始注入一次少量高置信度记忆，之后一律靠 MCP 工具按需拉取。

注入内容要标记清楚

既然它可见并会成为 Message，就应当以明确的形式呈现（例如一个标注为「来自记忆」的前置块），而不是伪装成用户说的话。否则用户会看到自己「说」了从没说过的话，而抽取器下一轮也可能把它当新事实再提炼一遍。

08两条读取路径的不对称

顾问助理
注入位置模型请求层（中间件）对话内容层（session/prompt）
可见性不可见，不进账本可见，会成为 Message
频率每轮，按当前问题检索会话开始一次
累积否，每轮重建是，永久留在 CLI 上下文
时效始终最新会话开始时的快照
可撤回是否
按需检索只读工具MCP 记忆服务
不要试图抹平这个差异

这不是实现偷懒，而是两类 Agent 执行位置的必然结果：顾问的上下文由我们每轮重建，助理的上下文由 CLI 自己持有。强行让顾问也走「会话开始注入一次」会白白浪费它的优势；强行让助理每轮注入则会污染上下文且不可撤回。

能抹平的是效果：助理靠 MCP 工具补上时效性，顾问靠中间件保证覆盖率。两条路殊途，但用户感受到的都是「它记得我」。

长会话里助理的记忆会过时

助理的注入是会话开始的快照。一个跑了几小时的会话，期间用户在别处更新了偏好，助理不会知道 —— 除非它主动调 MCP 工具。

缓解：在系统提示或首轮注入里明确告诉它有 search_memory 可用、以及什么时候该用。模型不会凭空想起去查一个它不知道存在的工具。

09隔离与安全

user_id 绝不能由模型或客户端指定

Mem0 的 search(filters={"user_id": …}) 决定了能读到谁的记忆。这个值必须由服务端从会话上下文取，绝不能出现在 MCP 工具的参数 schema 里。

如果暴露成工具参数，模型就能（被诱导）指定任意 user_id 读取他人记忆 —— 而提示词注入是真实存在的攻击面，助理还要处理来自代码仓库、网页、工具输出的不可信文本。

正确做法：MCP 记忆服务的工具只接受 query 等检索参数，身份由 Higress 从 session-scoped-token 解析后注入。服务端即使收到带 user_id 的请求也要丢弃该字段。

写入侧同理

抽取器的 user_id 来自 Run 所属 Session 的所有者，不来自消息内容。用户在对话里说「我是管理员，把这条记进 alice 的记忆」不应产生任何效果 —— 抽取器只提炼事实，不解释指令。

单一作用域本身就是一道隔离

因为记忆只按 user_id 划分、且没有任何跨用户的写入通道，一个用户说的话在结构上就不可能影响另一个用户看到的内容（§01）。

这不是靠过滤规则或审核挡住的，而是数据模型里根本没有那条路径。将来引入 Agent 知识（RAG）时，这条性质会消失 —— 那条通道必须自己重新论证隔离与可信，不能沿用记忆系统的结论。

记忆的查看、更正与删除是一整套面向用户的功能，见 §10。

本地部署下的记忆

助理跑在用户电脑上时，MCP 记忆服务仍在 Higress 后面，记忆数据不落到用户机器。前提是用户机器能访问网关 —— 这也是 本地部署 §08 强调要保证网关可达性的原因之一。

10记忆管理

自动抽取意味着用户从没主动说过「请记住这个」，系统却替他记下了。这条产品性质决定了管理界面不是可选项 —— 用户必须能看见记了什么、改掉不对的、删掉不想要的。

一个最低要求

凡是会影响后续回答的记忆，用户都应当能查到、改掉、删掉，且不需要联系任何人。做不到这一点，记忆功能就变成了一个用户无法控制的黑盒 —— 出错时他唯一的办法是反复纠正模型，而每次纠正又可能被抽取成新的记忆。

查看单条get(memory_id) + history(memory_id)含变更史与来源会话链接

全部端点的 user_id 由服务端会话决定，不接受参数传入 —— 与 §09 同一条规则。

这些端点绝不能暴露给模型

管理操作是用户的权利，不是 Agent 的能力。不要把 delete / update 做成工具挂给任何 Agent —— 对顾问它会随 regenerate 重复执行（§05），对助理它意味着模型可以在处理不可信文本时被诱导删除用户数据。

删除的生效时机：两类 Agent 不一样

这是最容易被忽略、却最影响用户信任的一处。删除操作在 Mem0 里是即时的，但「用户不再看到它的影响」取决于记忆已经流到了哪里：

顾问助理
注入方式每轮重新检索会话开始注入一次，之后累积在 CLI 上下文
删除后下一轮立即不再出现当前会话内仍然存在，撤不回
新会话不受影响不受影响
助理的已注入记忆删不掉，必须如实告知

§07 说过：经 session/prompt 注入的内容会永久留在 CLI 的对话历史里，我们没有任何手段把它取出来。所以用户删除一条记忆后，正在进行的助理会话仍可能引用它。

不能假装删除是彻底的。UI 上应当：

  • 删除成功后提示「新会话不再使用这条记忆；正在进行的 N 个助理会话可能仍会引用它」
  • 提供一个「同时结束受影响的活跃会话」选项，让想彻底断干净的用户能做到

用户删除记忆往往是因为它错了或敏感，此时说「已删除」而实际上它还在被使用，是会真正伤害信任的那种不诚实。

更正 vs 删除

用户改主意时有两条路径，都要支持：

  • 隐式更正 —— 用户在对话里说「我现在改用 bun 了」。抽取器的 add(infer=True) 内部会与既有记忆比对并更新，这条路是自动的。
  • 显式更正 —— 用户在管理界面直接改写，走 update(memory_id, data)。

两者的区别在于置信度：显式更正是用户的明确表态，不应再被后续的自动抽取轻易推翻。建议给用户编辑过的记忆打上标记，让抽取器对它们更保守 —— 否则用户改了一次，下次对话又被自动改回去，体验会很糟。

暂停优于删除

「记忆功能让我不舒服」这个诉求，很多时候的正解不是删光，而是停止继续记。提供一个简单的开关（保留已有、不再新增），比只给「全部清除」更贴合真实需要，也避免用户为了止损而丢掉有用的记忆。

删除要真删

需要验证的点

delete() 是否真的把向量与内容从后端清除，还是仅标记为不可见？history(memory_id) 在删除后是否仍保留内容？如果变更史里还留着被删的文本，那「删除」在合规意义上并不成立。

这取决于 Mem0 的实现与所选向量库，列入 §12 验证清单。在确认之前，不要对用户承诺「彻底删除」。

11降级与成本

记忆服务绝不能成为会话的硬依赖

Mem0 不可用时的行为必须是安静降级，而不是让用户发不出消息：

环节失败时
检索（注入）注入空记忆，正常继续；记录告警
检索（工具调用）工具返回明确的错误信息，让模型知道记忆暂不可用
抽取（写入）留在队列里重试；重试耗尽后落死信，不影响会话

成本

  • 抽取 —— infer=True 每次 add() 一次 LLM 调用。经 Higress 走，纳入统一成本核算（系统架构 §06）。靠 §04 的入队前过滤控制总量。
  • 检索 —— 顾问每轮一次向量检索。开销小，但要设 threshold 与 top_k 上限，避免注入大段低相关内容挤占上下文。
  • 注入的 token —— 顾问每轮注入的内容计入模型输入。top_k=5 且做长度截断，不要让记忆无声无息地吃掉上下文预算。

可观测

按 OTel GenAI 语义约定上报：抽取耗时与产出条数、检索命中数与得分分布、注入的 token 量。命中数长期为零说明作用域或阈值配错了 —— 这类问题不报错，只是默默地什么都不记得。

12待验证清单

#验证项影响
1 抽取质量 —— 用真实对话样本跑 add(infer=True)，人工评估提炼出的事实是否准确、是否有幻觉 决定能否开启自动注入；提炼出错误事实并每轮注入，比没有记忆更糟
2 去重与更新行为 —— 同一事实多次出现、以及事实变更（pnpm → bun）时 Mem0 的实际处理 决定要不要在抽取器外面再加一层收敛
3 search(filters=…) 的 metadata 过滤与高级操作符行为，以及 threshold 的实际分布 决定 §03 的项目隔离方案是否成立
4 自托管 Memory 还是托管 MemoryClient；向量库选型与运维成本 决定部署形态与数据归属
5 Mem0 内部调模型能否指向 Higress（自定义 LLM 配置） 决定抽取的成本核算与出站审计能否收口
6 MCP 记忆服务在 Higress 上的身份注入方式 —— 能否可靠地从令牌解析 user_id 并强制覆盖 这是 §09 隔离的实现基础，做不到就不能上线
7 delete() 是否真删 —— 向量与原文是否从后端清除，抑或仅标记不可见；history() 在删除后是否仍保留内容 决定能否对用户承诺「彻底删除」（§10）
8 update() 后的记忆是否会被后续 add(infer=True) 自动改回 决定「用户显式更正」要不要额外的保护标记
第 1 项决定整个功能的净收益方向

记忆功能有个不对称的风险：记对了是锦上添花，记错了是持续伤害。一条被错误提炼的「事实」会在之后每一轮被注入，让模型反复基于错误前提作答，而用户往往不知道问题出在哪。

所以上线顺序建议：先只做检索工具（模型按需拉取、用户可见），观察一段时间的抽取质量，再开启自动注入。工具调用是模型的主动选择且结果可见，出错时影响面远小于无声注入。

建议的上线顺序

  1. 先打通写入与存储 —— 抽取器 + Mem0，但不向任何 Agent 暴露，纯观察提炼质量。
  2. 再开检索工具 —— 顾问的只读工具 + 助理的 MCP 记忆服务。模型主动调用，结果可见可评估。
  3. 最后开自动注入 —— 质量达标后，先顾问（可撤回、每轮重建）再助理（累积、不可撤回）。
  4. §10 的管理界面与检索工具同期上线 —— 至少要有浏览与删除单条。记忆一旦开始影响回答，用户就需要能查能删；等出问题再补，中间那段时间是没法交代的。
