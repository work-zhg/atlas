1. Langfuse 是什么 官方资料

Langfuse 是一个开源的 LLM 工程平台，帮团队观察、调试、评估和迭代基于大模型的应用（包括 Agent）。 核心代码以 MIT 许可开源，可以自托管，也可以使用官方云服务；少量企业功能（如 SSO 细粒度权限、审计日志）属于商业版。

一句话概括它解决的问题："模型这一次到底收到了什么、回了什么、花了多少钱、效果好不好，以及改了提示词之后有没有变好。"

典型问题Langfuse 给出的答案
用户说回答不对，当时模型看到了什么？Tracing：按会话、按用户找到那一次调用，看完整的输入输出和中间步骤
这个月模型花了多少钱，花在哪了？成本统计：按模型、用户、功能、提示词版本拆分 token 用量和费用
改了提示词，效果是变好还是变坏？提示词版本管理 + 数据集实验 + 评分，对比不同版本
线上回答质量怎么持续监控？评估：LLM 自动打分（LLM-as-a-Judge）、人工标注、用户反馈

2. 核心功能 官方资料

🔍 链路追踪 Tracing

记录一次请求里的每一步：模型调用、工具调用、检索、Agent 推理。可以看完整的输入输出、耗时、token 和费用，支持多模态内容（图片、音频）。

💬 会话与用户 Sessions / Users

把多条 trace 归到同一个会话（多轮对话）或同一个用户下，按会话回放整段对话，按用户统计用量和费用。

📝 提示词管理 Prompt Management

提示词集中存储、版本化，用标签（如 production、staging）发布；应用运行时按名称加标签拉取，改提示词不用重新发版。

⚖️ 评估 Evaluation

给 trace 或其中某一步打分（Score）：LLM-as-a-Judge 自动评估、人工标注队列、用户反馈（点赞点踩）、通过 API 写入的自定义指标。

🧪 数据集与实验 Datasets / Experiments

沉淀测试样本（可以直接从线上 trace 加入），拿不同的提示词或模型版本跑一遍，结果自动打分，横向对比。

🛝 Playground

在界面里直接调提示词、换模型、改参数，立即看效果；可以从某条 trace 一键打开，复现当时的调用。

📊 指标与看板 Dashboards

成本、延迟、token 用量、质量评分随时间的变化，可以按模型、用户、标签、提示词版本等维度切分。

🔌 开放 API 与导出

所有数据都能通过 Public API 读写，支持导出到对象存储或数据仓库做离线分析。

3. 数据模型 官方资料

理解 Langfuse，先理解它的几个核心对象：

对象含义要点
Trace一次完整请求或一次 Agent 执行所有步骤的根。挂 sessionId、userId、tags、metadata，方便检索
Observationtrace 里的一步，有父子关系，组成一棵树三种基本类型：Span（有时长的步骤）、Generation（模型调用，带模型、参数、token、费用）、Event（单点事件）
Session多条 trace 组成的一段对话不需要单独创建，trace 上带同一个 sessionId 就自动归为一组
Score对 trace 或某一步的评价来源可以是自动评估、人工标注、用户反馈或 API；可以是数值、分类或布尔值
Prompt受管理的提示词不可变的版本 + 可以移动的标签；Generation 上记录用了哪个版本，于是能按版本对比效果
Dataset测试集每个 Item 有输入和期望输出；一次 Run 是"拿某个版本跑一遍这个测试集"，每个样本对应一条 trace

4. 架构与组件（v3 自托管） 官方资料 仓库核对

v3 把系统拆成"接收请求"和"处理数据"两部分，存储也按数据特点分成了四种：

组件职责为什么这样选
langfuse-web界面和全部 API；接收上报后只做鉴权、校验、落盘、入队接收路径要快、要稳，把重活交给 worker，上报高峰不会拖慢界面
langfuse-worker消费队列：解析事件、合并同一对象的多次更新、计算 token 和费用、写入 ClickHouse；执行自动评估、批量导出等后台任务可以独立横向扩容。Atlas 部署时踩过的坑：只起 web 不起 worker 的话，上报会返回 200，但数据永远不会出现，也不报错（docker-compose.yml 的注释） 仓库核对
ClickHouse存 trace、observation、score 这类海量、只追加、以聚合查询为主的数据v2 只用 Postgres，量一大查询就慢；列式数据库适合"按时间、模型、用户聚合"这类看板查询
PostgreSQL存用户、项目、API Key、提示词、数据集配置等事务性数据量小、需要事务和强一致
Redis / Valkeyweb 和 worker 之间的任务队列，以及缓存（比如 API Key 校验、提示词）解耦接收和处理，削峰
S3 / 对象存储上报的原始事件先落这里；图片、音频等多模态内容；批量导出原始事件可以重放：处理出错或升级后能重新入库，不怕丢数据

5. 原理：一条 trace 是怎么进来的 官方资料

  1. 应用侧埋点，异步批量发送：SDK 在内存里攒事件，后台线程批量发给服务端，不阻塞业务请求。网络出错会重试；进程退出前要调用 flush()，否则缓冲里最后一批会丢失。
  2. web 接收：校验 API Key（Basic Auth，公钥 pk-lf-… 加私钥 sk-lf-…）和事件格式，然后：
    • 把原始事件写进对象存储（同一个对象的多次更新，按 id 落在同一个路径下）；
    • 往 Redis 队列里放一个"处理这个对象"的任务；
    • 立即返回。返回 2xx 只代表已收下，不代表已经能查到。
  3. worker 处理：从队列取任务，从对象存储读出这个对象的所有事件，合并成最终状态（一个 span 往往先上报开始、后上报结束和输出）；对 Generation 按模型价格表计算费用（上报里没有 token 数时，会用对应模型的分词器估算）；最后写进 ClickHouse。
  4. 查询：界面和 API 从 ClickHouse 读。从上报到能查到，通常是秒级延迟，属于最终一致。
为什么要"先落对象存储，再入队，再合并"：LLM 应用的事件天然是乱序、分多次到达的（开始、流式中间状态、结束、事后补打的评分）。先把原始事件可靠地存下来，再由 worker 按对象合并，就不用关心到达顺序，也能在出错后重放。

6. 原理：提示词管理与评估 官方资料

6.1 提示词管理

  • 版本不可变，标签可移动：每次保存都生成一个新版本；production 这样的标签指向某个版本，发布或回滚就是移动标签。
  • 客户端缓存：SDK 按"名称 + 标签"拉取提示词并缓存在本地（有过期时间），过期后在后台刷新，期间继续用旧值（stale-while-revalidate）。所以 Langfuse 短暂不可用，不会让应用拿不到提示词，拉取也不会给每次请求增加延迟。
  • 和 trace 关联：调用模型时把提示词对象传给 Generation，就能在看板里按提示词版本对比费用、延迟和评分。

6.2 评估

方式原理
LLM-as-a-Judge在界面里配置"评估器"：用哪个裁判模型、什么评分提示词、作用于哪些 trace（过滤条件 + 采样比例）。新 trace 入库后，由 worker 异步调用裁判模型打分，结果写成 Score
人工标注把 trace 放进标注队列，按预先定义好的评分维度逐条打分
用户反馈前端把用户的点赞点踩通过 SDK 或 API 写成 Score，挂到对应的 trace 上
自定义业务代码自己算指标（比如代码能不能编译通过），通过 API 写入
数据集实验拿一组固定样本跑新版本，每个样本生成一条 trace 并自动打分，和旧版本放在一起对比

7. 接入方式 官方资料

方式说明适合
原生 SDK（Python / JS·TS）用 @observe 装饰器自动记录函数的输入、输出和耗时；或者手动创建 span 和 generation。新版 SDK 基于 OpenTelemetry 构建自己写的应用，想要最完整的功能（提示词管理、评分等）
OpenAI SDK 替换把 import openai 换成 Langfuse 提供的包装模块，调用会被自动记录直接用 OpenAI SDK 的项目，改动最小
框架集成LangChain / LangGraph 的回调（CallbackHandler）、LlamaIndex、LiteLLM、Vercel AI SDK 等用了这些框架的项目
OpenTelemetry标准 OTLP/HTTP 发到 /api/public/otel；会把 OTel GenAI 语义约定（gen_ai.* 属性）映射成 Langfuse 的模型调用、token、费用已经有 OTel 埋点、或者要和 APM 共用一套埋点的项目（Atlas 用的就是这种）
Public APIREST 接口直接读写 trace、score、数据集、提示词其他语言、或者离线批量导入导出

from langfuse import observe, get_client

@observe()                      # 自动记录成一个 span（输入、输出、耗时）
def answer(question: str) -> str:
    ...                         # 里面的模型调用若用了集成，会自动成为子 Generation
    return "..."

answer("Langfuse 是什么？")

8. 与 Jaeger 等 APM 的分工 仓库核对

Atlas 的设计里，Langfuse 不替代 Jaeger，而是分流（deploy/local/otel/collector-langfuse.yaml 的注释）：

LangfuseJaeger（APM）
关注点LLM 维度：提示词、回答、token、费用、质量评分、提示词版本系统维度：服务间调用链、耗时分布、错误
擅长回答"这一轮为什么答得不好"、"哪个提示词版本更好"、"钱花在哪""为什么这么慢"、"哪一跳超时了"
看不到的Pod 冷启动慢、存储抖动、WebSocket 断连这类基础设施问题提示词内容、评估分数、按会话回放对话

结论：用一个后端去同时应付两类问题，最后两类都查不好。所以同一份埋点数据，由 Collector 同时发给两边。

9. 在 Atlas 里怎么用 仓库核对

9.1 现有接入方式

Server ──OTLP/HTTP──▶ OpenTelemetry Collector ──▶ Jaeger（全量链路）
                                            └──▶ Langfuse（LLM 维度，可选）
  • server 只发给 Collector，不直连任何后端（telemetry/__init__.py）。要不要接 Langfuse，只是换一份 Collector 配置的事，server 代码不用改。
  • 埋点遵循 OTel GenAI 语义约定（telemetry/semconv.py）：gen_ai.request.model、gen_ai.usage.input_tokens、gen_ai.conversation.id 等。Langfuse 能直接识别成模型调用、token 用量和会话。缓存 token、推理 token 都是独立字段，保证费用核算准确。
  • 一个 run 对应一棵 span 树（telemetry/run_trace.py）：根 span 是 run，下面挂模型调用和工具调用；Native 和 ACP 产出的事件形状相同，同一套代码两条路径都覆盖。
  • 会话映射：Atlas 的会话（thread）对应 gen_ai.conversation.id，在 Langfuse 里就是一个 Session。

9.2 本机启动

# 1. 起 Langfuse（挂在 profile 上，make up 不会启动它）+ 换成带 Langfuse 的 Collector 配置
OTEL_COLLECTOR_CONFIG=collector-langfuse.yaml docker compose --profile langfuse up -d

# 2. server 打开遥测（默认关闭）
OTEL_ENABLED=true              # 对应 config.py 的 otel_enabled（配置无前缀）
OTEL_ENDPOINT=http://127.0.0.1:4318

# 3. 打开 Langfuse 界面（3000 端口被前端占了，所以映射到 3001）
open http://localhost:3001
本机组件说明
langfuse-web + langfuse-worker镜像 langfuse/langfuse:3、langfuse/langfuse-worker:3，两个都必须起
ClickHouse独立容器 atlas-langfuse-ch；需要两个地址：8123（HTTP）和 9000（迁移用的原生协议）
Redis独立容器 atlas-langfuse-redis，用 REDIS_HOST/PORT/AUTH 三个变量配置，不是连接串
PostgreSQL / MinIO复用 Atlas 已有的实例：Postgres 里用独立的 langfuse 库，MinIO 用同一个桶的 langfuse-events/ 前缀
鉴权Collector 用 Basic Auth（base64(pk:sk)），还必须带 x-langfuse-ingestion-version 请求头，少了会被拒
注意：默认看不到提示词和回答的内容。Collector 配置里有一个脱敏处理器 attributes/strip-content，会删掉 gen_ai.input.messages、gen_ai.output.messages 等内容字段；server 的 otel_capture_content 也默认关闭。所以 Langfuse 里能看到调用链、token、费用、耗时，但看不到对话内容，而按会话看提示词、做内容评估恰恰是 Langfuse 最大的价值。要用这部分能力，需要同时打开 otel_capture_content，并去掉通往 Langfuse 那条管道上的脱敏处理器。这里有数据合规上的权衡，要先确认内容允许落到 Langfuse 的存储里。

9.3 能力对照：Atlas 现在用到了哪些

Langfuse 功能Atlas 现状
链路追踪、会话、token 与费用✅ 已经通过 OTel 接入（需要手动打开）
对话内容查看⚠️ 默认脱敏，见上方提示
提示词管理❌ 没用。Atlas 的系统提示词在智能体版本快照里管理，有自己的版本机制
评估、数据集、实验❌ 没用。可以作为后续引入的方向（比如对委派结果做 LLM-as-a-Judge 质检）
用户反馈打分❌ 没用。前端还没有点赞点踩

10. 优缺点与注意事项

优点代价与注意事项
  • 开源、可自托管，数据留在自己手里
  • 追踪、提示词、评估、数据集在同一个平台里打通，能形成"观察 → 评估 → 改进"的闭环
  • 支持 OTel，可以和 APM 共用一套埋点，不被厂商绑定
  • 上报是异步批量的，对业务延迟影响很小
  • 自托管的组件多：web、worker、ClickHouse、Redis、Postgres、对象存储，一共 6 个，运维成本不低
  • 最终一致：上报成功不等于马上能查到；worker 停了，数据会静默积压
  • 内容合规：完整的提示词和回答落盘后，需要考虑脱敏、保留期限和访问权限
  • 短进程要 flush：脚本、Serverless 函数退出前不 flush，最后一批事件会丢
  • 费用是估算值：依赖模型价格表，自定义模型或网关模型（比如 DeepSeek 经网关）需要自己配置价格，否则费用为空或不准
