数字员工：Agent 的身份与权限设计

日期：2026-10-15 · 状态：设计稿，待评审 · 关联：Atlas 权限与数据权限（接入用户中心）、用户中心权限设计、应用接入设计、知识库企业级设计
依据代码：usercenter/…/db/models.py（uc_user · uc_grant · uc_data_acl）、api/open.py（/open/v1）、perm/effective.py、Atlas auth/catalog.py（AtlasAgent · AtlasMcpServer）、providers/knowledge.py。
范围：用户中心新增「数字员工」用户类型与开放接口；Agent 平台创建 / 绑定数字员工，运行时按数字员工的权限执行；用户对 Agent 的数据权限。

结论先行：每个 Agent 在用户中心有一个数字员工（uc_user.user_type = 'digital'，有自己的 uid）。数字员工和人一样可以被授角色、岗位、数据权限 —— 给数字员工配了什么权限，Agent 就有什么权限。三层关系：
  1. 人 → Agent：用户对 Agent 的数据权限（AtlasAgent：使用 / 编辑 / 所有者），决定谁能用、谁能改这个 Agent（沿用现有设计）。
  2. Agent ↔ 数字员工：一对一，Agent 平台在创建 Agent 时调用户中心开放接口创建数字员工并记下 uid。
  3. 数字员工 → 资源：在用户中心给 uid 授权（角色 / 岗位 / 数据权限），知识库、MCP 服务、TeamFlow 团队等按它判定。
三条关键决策：① 数字员工不能登录、不继承部门授权（只认直接授给它的，最小权限）；② 用户与 Agent 对话时，有效权限 = 发起人 ∩ 数字员工（防止借 Agent 越权），无人发起（定时、TeamFlow 系统投递）时才只看数字员工；③ 「Agent 以自身权限服务所有使用者」是需要管理员批准的独立模式，不是默认。

1. 背景与目标

#现状（已对照代码）问题

目标非目标
  • 用户中心有「数字员工」类型的用户，有 uid，和人一样可被授权、可在选人器里被选到。
  • Agent 平台经开放接口创建、维护数字员工；Agent 与数字员工一对一。
  • 数字员工的权限 = Agent 的权限上限；在用户中心统一授权、统一审计。
  • 用户对 Agent 有数据权限（使用 / 编辑 / 所有者），且不能借 Agent 拿到自己没有的数据。

  • 多个 Agent 共用一个数字员工（P1 不做，§14 待确认）。
  • 数字员工的「记忆」：记忆仍只属于人（记忆设计 §03），不以数字员工为 user_id。

3. 用户中心：数字员工类型

3.1 与「人」的差异

方面人（human）数字员工（digital）理由
创建方管理员在管理台 / 导入接入应用经开放接口（如 Atlas）；管理台只读 + 停用数字员工的生命周期跟随 Agent，由拥有 Agent 的应用驱动，避免两边各改各的
账号人工填写自动生成 dw- + 10 位短码（如 dw-k3m9q2x7ab），不可改账号要全局唯一、稳定；不用 Agent 名（会重名、会改名）
邮箱 / 手机必填 / 选填不填不收通知，也不该占用真实邮箱的唯一约束
登录可以不可以：没有 uc_user_credential；verify-password、管理台登录直接拒绝数字员工的「行动」只能经由绑定它的应用发生，才能被归因与审计
所属部门必填必填（默认 = 负责人的部门）用于展示、应用可访问范围校验、按部门筛选；不参与权限计算（见 3.3）
负责人—必填，一个人（默认 = Agent 创建者）出了问题找谁；负责人离职要能被发现
部门授权（含下级）继承不继承见 3.3
角色 / 岗位授权可授可授（只能直接授给该 uid）与人同一套模型，用户中心统一授权、统一审计
数据权限主体可以可以（只能以「用户」主体被授权）知识库 / TeamFlow 团队的所有者可以像共享给同事一样共享给数字员工
部门负责人可以不可以（uc_dept.leader_uuid 拒绝数字员工）审批流、汇报线只属于人
超级管理员 / 用户中心管理角色可以不可以：用户中心自身（内置应用）的角色不能授给数字员工Agent 不能管理权限体系本身，否则一次提示注入就能改掉所有授权
数据编码级授权（「全部 xx」）可以不可以：授权时拒绝以数字员工为主体（含经部门授予 —— 数字员工本来就不继承部门授权）「全部智能体 · Owner」意味着能改任意 Agent 及其授权，交给 Agent 等于让 Agent 管 Agent；数字员工只按单条数据被共享

3.2 数据模型

uc_user  （新增列）
  user_type        varchar(8)  NOT NULL DEFAULT 'human'   -- human | digital
  owner_uuid       uuid NULL   FK uc_user.uuid             -- 负责人（digital 必填，必须是 human）
  source_app_uuid  uuid NULL   FK uc_app.uuid              -- 创建它的应用（digital 必填）
  external_ref     varchar(64) NULL                        -- 来源应用里的对象 id（Atlas = agent id）
  description      varchar(200) NULL
  email            改为可空

约束
  CHECK (user_type IN ('human','digital'))
  CHECK (user_type = 'digital' OR email IS NOT NULL)                       -- 人仍必须有邮箱
  CHECK ((user_type = 'digital') = (owner_uuid IS NOT NULL AND source_app_uuid IS NOT NULL))
  UNIQUE (source_app_uuid, external_ref) WHERE user_type = 'digital'       -- 幂等创建的依据
  INDEX  (user_type, status)

不新建表：数字员工就是一种用户，uc_grant、uc_data_acl、审计、选人器全部原样复用 —— 这是「和人一样被授权」最便宜、也最不会漂移的做法。只有少数地方按 user_type 分支（3.3、3.4、§4）。

3.3 权限计算：不继承部门授权

决策：数字员工的有效权限只来自直接以它为主体的授权（uc_grant.subject_type='user'、uc_data_acl.subject_type='user'）。授给部门（含下级）的角色与数据权限对数字员工不生效。
方案优点问题
不继承（采用）最小权限：数字员工拥有的每一项权限都是有人明确授给它的，可逐项追溯；放进哪个部门不改变权限常见的「全员可读」资源也要单独授一次 —— 用「数字员工通用」岗位解决（见下）
继承（与人相同）零额外配置Atlas 默认把数字员工放进负责人的部门 → Agent 自动获得整个部门（往往是根部门含下级）的全部权限。授权的人当时想的是「全员」，没想过 Agent；权限随部门调整悄悄变化，无法审计
按数字员工可选开关灵活多一个影响权限的隐藏开关，排查「它为什么能读到」时又多一个分支；P1 不做，留作待确认

落点：perm/effective.py 的 matched_grants / subject_filter、perm/data.py 的 level_of / type_level_of / accessible 在 user.user_type == 'digital' 时只匹配 user 主体（不展开部门链），且不看数据编码级授权。一处判断，所有接口（授权快照、check、accessible、知识库主体展开）自动一致。

「全员可用」类资源的做法：在用户中心建岗位 数字员工通用（如通用知识库只读、内置 MCP 只读），给数字员工授岗位 —— 仍是显式授权，且一处维护。

3.4 管理台

  • 用户列表：加「类型」筛选（人 / 数字员工），数字员工带 🤖 标记，列出负责人、来源应用、外部引用（可点回 Atlas 的 Agent 页）。
  • 详情页：基本信息只读（由来源应用维护）；可停用 / 启用（管理员紧急止血用）；没有「重置密码」「登录日志」。
  • 授权：「授权管理」里选人器可以选到数字员工（带标记）；授部门时提示「数字员工不继承部门授权」。用户中心自身的角色在选人器里过滤掉数字员工。
  • 有效权限页：与人相同（角色来源、操作码、可访问的数据对象），便于回答「这个 Agent 到底能干什么」。
  • 负责人离职：负责人被停用时，数字员工不自动停用（Agent 可能还在被别人使用），列表标出「负责人已停用」，并在用户中心待办里提示管理员改派负责人。

4. 用户中心：开放接口

沿用 /open/v1 的应用令牌鉴权（OpenAppDep）。写接口只允许来源应用操作自己创建的数字员工（source_app_uuid = 调用方），其他应用只读。

接口说明
POST /open/v1/digital-employees 新请求 {external_ref, name, owner_id, dept_id?, description?}；dept 缺省 = 负责人部门，必须在调用应用的可访问范围内。
幂等：(调用应用, external_ref) 已存在则返回已有的（200），否则 201。返回 {id, account, name, dept_id, owner_id, status}
GET /open/v1/digital-employees/{id} · GET …?external_ref= 新查询；后者用于补偿（Atlas 不确定是否已建成时先查）
PATCH /open/v1/digital-employees/{id} 新改 name / description / owner_id / dept_id（Agent 改名、转交所有者时同步）
POST /open/v1/digital-employees/{id}/disable · /enable 新Agent 归档 / 恢复时调用；停用后授权快照 status=disabled，所有判定为无权限
GET /open/v1/users 改新增参数 types=human,digital，缺省只返回 human —— 已接入应用的选人器行为不变，想选数字员工的应用显式开启
GET /open/v1/users/{id} · /users/{id}/authz 改返回体加 user_type、owner_id、source_app；数字员工的授权快照按 3.3 计算
POST /open/v1/auth/verify-password 改数字员工一律返回「账号不可登录」（与不存在同样的错误码，不泄露类型）
/open/v1/data-permissions*不变：subject_type=user + 数字员工 uid 即可授权；以 dept 为主体的授权对数字员工不生效（3.3）

不提供「经开放接口给数字员工授角色」：角色是功能权限，必须在用户中心由有权限的人授（§6）。否则任何接入应用都能把自己的 Agent 提权。

6. 给数字员工配置权限

原则：谁拥有资源，谁决定数字员工能不能用它；功能权限（角色）只有权限管理员能授。Agent 的所有者不能自己给自己的 Agent 提权。

角色归角色，数据权限归数据权限。角色（→ 操作码）只表达「能不能做某类事」；「对哪些数据有什么级别」一律是数据权限，分两个粒度：
  • 数据授权：对某一条数据（某个知识库、某个 Agent、某个团队）。
  • 数据编码级授权（「全部数据授权」）：对某编码下的全部数据，如「全部智能体 · Owner」。有效级别 = max(单条, 全部)；不计入单条数据的「至少一名 Owner」，也不出现在持有人列表里。
原先的「数据管理员操作码」（agent:manage_all、mcp:manage_all、TeamFlow team:manage_all）把两个领域混在了一起，已由数据编码级授权取代（用户中心迁移 u0003，存量持有人按原范围换成「全部 · Owner」）。本文中「平台侧能管全部 Agent 的人」都指持有「全部智能体 · Owner」的人。
权限在哪配谁能配示例
功能权限（角色 / 岗位 → 操作码）用户中心「授权管理」用户中心权限管理员（与给人授角色相同）给「工单助手」授 TeamFlow 的 task:create；授岗位「数字员工通用」
数据权限（知识库、MCP 服务、TeamFlow 团队…）资源所在应用的「共享」界面（选人器选到数字员工），或用户中心数据权限页该数据对象的 OWNER（含持有该编码「全部数据 · Owner」的人）HR 知识库所有者把库共享给「HR 助手」（只读）
Agent 自己（AtlasAgent）上的权限Atlas Agent 详情「共享」Agent OWNER见 §8，这是「人对 Agent」的权限，不是数字员工的

6.1 Atlas 里的「身份」面板

  • Agent 详情新增「身份」页签（READ 可见）：数字员工账号、负责人、身份模式、有效权限摘要（调用户中心授权快照 + 各数据编码的 accessible：可读的知识库、可用的 MCP 服务、所在 TeamFlow 团队）。
  • OWNER 可见「去用户中心授权」链接（跳到该 uid 的授权页，需要对方有权限）与「申请权限」（P2：提交给用户中心权限管理员的工单）。
  • 配置 Agent 时的一致性提示：Agent 配了某个知识库 / MCP 服务，但数字员工对它没有 READ → 保存时提示「运行时这个知识库不可用」（不阻止保存：授权可能稍后才到）。

7. 运行时：Agent 的有效权限

7.1 公式

run 的发起情形delegated（默认）autonomous（需批准）
用户在 Atlas 对话发起人 ∩ 数字员工数字员工
服务账号带代表用户（X-Atlas-Acting-User）代表用户 ∩ 数字员工数字员工
无人发起：服务账号不带代表用户、TeamFlow 系统投递、定时任务数字员工数字员工
Agent 被归档 / 数字员工停用 / 未绑定数字员工数字员工侧视为空权限：依赖授权的工具全部不可用（未绑定只出现在迁移完成前，见 §12）
为什么默认取交集：数字员工的权限是给「这个 Agent 能做什么」设的上限，不是给使用者的额外权限。若只看数字员工，能用 HR 助手的任何人都能问出 HR 知识库里自己无权看的内容 —— 这是典型的「代理人困惑」（confused deputy），而且提示注入会把它放大。取交集后：Agent 永远不超过自己的授权，用户也永远拿不到自己没有的数据。
autonomous 的正当用途：Agent 本来就是为了「在受控范围内替大家查一份大家不能直接看的资料」（如对外客服 Agent 读内部产品库）。这时数据所有者在共享给数字员工时就知道它会被所有使用者间接使用 —— 所以开启 autonomous 要持有「全部智能体 · Owner」的人批准（不能是这个 Agent 自己的 OWNER 自批）、在共享界面显著标出、并审计每次访问（§10）。

7.2 各资源的判定落点

资源现状改为判定时机

7.3 实现：run 级身份上下文

run 开始（执行器 _prepare） ├─ initiator = run.created_by（人 / 代表用户）或 None（无人发起） ├─ agent_uid = agent.digital_employee_uid ├─ mode = agent.identity_mode └─ RunIdentity(subjects = [agent_uid] + ([initiator] if mode=delegated and initiator else [])) │ ├─ 授权快照：每个 subject 一份（用户中心 /users/{id}/authz，进程内缓存 60 s， │ authz:invalidate 广播即时失效 —— 与横向扩展设计 §7.3 同一个频道） ├─ 装配期：MCP 服务、知识库挂载按「所有 subject 都有 READ」过滤 → 被滤掉的进 notices（前端可见） ├─ 工具调用期：知识库检索把 subjects 原样传给知识库服务；业务系统调用带 acting_subject └─ 写入 run：run.agent_subject = agent_uid、run.identity_mode = mode（审计与复现用）

与现状的唯一结构差别是：「当前身份」从一个 user_id 变成一组 subject，判定一律「每个 subject 都满足」。单人场景退化为现在的行为，代码路径只有一条。

14. 风险、权衡与待确认

风险缓解
借 Agent 越权（代理人困惑）默认 delegated 交集；autonomous 需批准且编辑收紧到 OWNER（§8）
Agent 所有者给自己的 Agent 提权开放接口不提供授角色；数据权限只能由资源 OWNER 授；用户中心自身的管理角色不可授给数字员工
数字员工悄悄继承部门权限不继承部门授权（3.3），所有权限可逐项追溯
上线后 Agent 能力突然缩水迁移时按现有配置显式共享 + 开关灰度（§12）
多了一层授权查询，run 启动变慢授权快照与 accessible 结果按 subject 缓存 60 s，失效靠广播；交集只在本地算
用户中心不可用时无法创建 Agent与登录同一个硬依赖，接受；创建幂等，可重试
孤儿数字员工（Atlas 建一半退出）external_ref 幂等 + 维护者每日对账停用
