1. 目标与范围

能力要回答的问题验收标准（以第 2 节的示例会话为准）
链路追踪这一轮做了哪些步骤、各花多久、哪里出错每一轮对应一条 trace，包含模型调用、工具调用、委派；委派出去的子 run 能找到，并且能跳回父 run
会话这段对话从头到尾发生了什么整段会话（包括委派给子智能体的工作）落在同一个 Session 里，按时间顺序回放
token 与费用每一轮、每个会话、每个用户花了多少钱，花在哪个模型上Langfuse 显示的总 token 与 Atlas 的 run 表一致（误差为 0），费用按 DeepSeek 的价格（含缓存价）计算
对话内容查看模型当时收到了什么、回答了什么，工具的参数和结果是什么开关打开时能看到用户输入、最终回答、每次模型调用的输入输出、工具的参数和结果；开关关闭时这些一个字都不出现

不在范围内：评估（打分、LLM-as-a-Judge）、数据集与实验、Langfuse 的提示词管理（Atlas 的提示词由智能体版本快照管理）。

2. 示例会话

全文以这个会话为例。用户和「开发协调者（委派 CLI）」对话：主智能体是 Native（deepseek-chat），它把动手的工作委派给 ACP 子智能体 cli-hand（Pod 里的 Claude Code，权限模式 auto）。

用户（第 1 轮）：在工作区写一个 hello.py，打印当前时间，然后运行它告诉我输出
主智能体：思考，然后调用 task(cli-hand, "新建 hello.py …")
　└ 子智能体 cli-hand（另一个 run，在子会话里）：Write hello.py → Bash python hello.py → 汇报
主智能体：read_file hello.py 确认
助手：已创建 hello.py，运行输出为 2026-10-04 10:21:05…
用户（第 2 轮）：把输出改成中文格式
主智能体：再次委派给 cli-hand（持久会话，记得上一轮的上下文）
　└ 子智能体：Edit hello.py → Bash 运行 → 汇报
助手：已改为中文格式，输出为 2026年10月04日 10时22分…

对象id说明

第 1 轮子 runR1'在 T' 上，parent_run_id = R1

本节只说"映射成什么"。映射靠哪些字段实现、Langfuse 按什么规则归档，见第 5 节：没有那些字段，下面的映射一条都不会自动发生。

AtlasLangfuse映射规则

5. 字段设计：Langfuse 如何把 OTel 数据归档

结论先说：用 OTel 采集了 trace，Langfuse 并不会自动具备会话、用户、费用、对话内容这些能力。 OTel 只负责把 span 送到 Langfuse。Langfuse 拿到的是一堆带属性的 span，它要按自己约定的字段规则去读这些属性， 才知道"这些 span 是哪个会话的""这一步是不是模型调用""用了多少 token""输入输出是什么"。 属性名不对、写错位置、或者干脆没写，对应的功能就不会出现，而且不会报错，只是界面上什么都没有。 所以必须有一份字段设计，第 4 节的映射关系全靠这一节的字段来实现。

5.1 不做字段设计，只接 OTel，Langfuse 里能得到什么

以现在 Atlas 已经发出的 span（第 3 节）为例，直接接进 Langfuse：

能力能不能得到原因
按请求看 span 树、耗时、错误✅ 能靠 OTel 原生的 trace id、span id、父 span id、起止时间、状态，任何后端都认
trace 名称⚠️ 勉强默认取根 span 的名字（invoke_agent acp-delegator），能看，但不是为检索设计的
Session（按会话回放）❌ 没有Langfuse 不认识 Atlas 的 gen_ai.conversation.id 是不是会话 待验证 V2；不写它认识的会话字段，trace 就不属于任何 Session
按用户统计❌ 没有现在根本没有用户字段
token 用量⚠️ 部分Langfuse 识别 OTel GenAI 标准的 gen_ai.usage.input_tokens / output_tokens；缓存和推理 token 的标准属性能不能识别，待验证 V4
费用⚠️ 不一定只对被认作 Generation、并且模型名能在价格表里匹配上的 span 计算；DeepSeek 不在默认价格表里，所以是 0
对话内容❌ 没有现在没有采集（P7），而且 Langfuse 只认特定的内容字段
observation 类型（模型调用 / 工具 / Agent）⚠️ 靠推断不显式指定时，Langfuse 按有没有模型名、用量来推断，可能把根 span 当成模型调用，导致费用重复（P4）

5.2 字段规则分两层

层内容规则由谁定需要设计吗
第一层：OTel 原生结构trace_id、span_id、parent_span_id、span 名、起止时间、状态、span 事件、resourceOTel 标准，所有后端都一样结构本身不用设计，但 trace_id 怎么生成要设计：它决定了哪些 span 算同一条 trace（6.3 节）
第二层：属性语义(a) OTel GenAI 标准属性 gen_ai.*：模型名、token 用量、工具名、操作类型OTel 语义约定（目前还在 incubating 阶段）Atlas 已经遵循（semconv.py）。Langfuse 识别其中一部分，换别的后端也能用
(b) Langfuse 专有属性 langfuse.*：会话、用户、trace 名称、trace 输入输出、observation 类型、标签、元数据、环境Langfuse 自己定，只有 Langfuse 认识必须设计。会话、用户这类概念在 OTel 标准里没有对应的、Langfuse 能识别的写法
(c) 其他属性，比如 atlas.run_idAtlas 自定义Langfuse 不解读，原样放进 metadata 展示，可以查看，但不参与任何功能

所以回答"字段规则是不是依赖 Langfuse"：归组类的字段（会话、用户、trace 级的输入输出、observation 类型）依赖 Langfuse 的规则；模型和用量类的字段尽量用 OTel 标准，Langfuse 认就行。Langfuse 的规则会随版本变化，所以第 12 节把这些都列为待验证，并且规定所有 langfuse.* 字段名只出现在 semconv.py 这一个文件里。

5.3 归档规则：span → trace → session

问题Langfuse 的规则Atlas 的做法
一个 span 怎么归到一条 trace？ 按 OTel 的 trace_id：trace_id 相同的 span 就是同一条 trace，Langfuse 的 trace id 就是它的 32 位十六进制。这是 OTel 原生规则，不需要任何属性 Langfuse 里没有"run"这个概念。要让"一个 run = 一条 trace"，唯一的办法是让这个 run 的所有 span 共用同一个 trace_id。
现状：每一段执行都随机生成 trace_id，所以挂起后续跑的 run 会变成两条 trace（P2）。
设计：trace_id = run_id 的 128 位整数（6.3 节）。子 run 有自己的 run id，自然是另一条 trace。
trace 内部的树怎么来？ 按 span_id 和 parent_span_id 建父子关系，每个 span 是一个 observation。没有父 span（或者父 span 不在这条 trace 里）的是顶层 observation
trace 的名称和输入输出从哪来？ 优先读 langfuse.trace.name、langfuse.trace.input、langfuse.trace.output；没有就取根 span 的名字和输入输出。这些字段要写在哪个 span 上才生效（只认根 span，还是任意 span 都行）待验证 V7 名称写智能体 slug；输入写在第 1 段的根 span 上，输出写在最后一段的根 span 上
一条 trace 怎么归到一个 session？ Session 不是一个需要创建的对象，它只是 trace 上的一个 sessionId 字符串：sessionId 相同的 trace 就是同一个 Session。OTel 进来的数据，sessionId 来自 span 属性 langfuse.session.id（也接受通用的 session.id）。没有这个属性，trace 就不属于任何 Session langfuse.session.id = 根会话 id（thread.stream_thread_id），写在每一段的根 span 上。父 run R1、R2 和子 run R1'、R2' 都写 T，于是归到同一个 Session
一条 trace 怎么归到一个用户？ 同上，langfuse.user.id（或 user.id） thread.created_by，同样写在每一段的根 span 上

5.6 字段设计的规则

  1. 归组字段写在每一段的根 span 上：trace_id（由上下文继承）、session、user、trace 名称和元数据。不依赖 Langfuse 是否会把属性从一个 span 传播到整条 trace（V7）。
  2. 用量只写在 Generation 上：其他 span 一律不带 gen_ai.usage.*，从根本上避免重复计费。
  3. 标准优先，专有兜底：能用 gen_ai.* 表达的（模型、用量、工具名）不用 langfuse.*；只有 OTel 标准里没有对应写法的概念（会话、用户、trace 输入输出、observation 类型、标签、元数据）才用 Langfuse 专有属性。
  4. observation 类型显式指定：不靠 Langfuse 推断，推断规则会随版本变化。
  5. 后端专有的字段名只在 semconv.py 里出现：Langfuse 升级、或者以后换别的后端，只改这一个文件。
  6. 内容类字段全部受档位控制，并且在 Collector 发往 Jaeger 的管道里删除（第 10 节）。
  7. 值的类型：OTel 属性只支持字符串、数字、布尔值和它们的数组；输入输出、复杂的元数据都要先序列化成 JSON 字符串。

6.3 用 run id 派生 trace id

# telemetry/run_trace.py（示意）
from opentelemetry.trace import NonRecordingSpan, SpanContext, TraceFlags, set_span_in_context

def _trace_context(run_id: UUID):
    """让这个 run 的所有段都落进同一条 trace：trace id = run id 的 128 位整数。"""
    parent = SpanContext(
        trace_id=run_id.int,               # UUID 是 128 位，OTel trace id 也是 128 位
        span_id=_span_id_of(run_id),       # 从 run id 派生一个固定的"虚拟父 span"
        is_remote=True,
        trace_flags=TraceFlags(TraceFlags.SAMPLED),
    )
    return set_span_in_context(NonRecordingSpan(parent))

span = tracer().start_span(name, context=_trace_context(run_id), ...)
  • 好处：Atlas 里的 run id 去掉横线就是 Langfuse / Jaeger 里的 trace id，从 Atlas 界面可以直接拼出跳转链接。
  • 代价：每一段的根 span 都挂在一个"虚拟父 span"下面，这个父 span 本身不会上报。Jaeger 会显示一条"缺少父 span"的提示，Langfuse 能否把它们正常当作顶层 observation 待验证。如果不行，退而求其次：只派生 trace id、不设父 span（要自定义 IdGenerator）。

10. Collector 管道设计

现在两条出口共用一个脱敏处理器（P8）。改成两条管道，同一份数据分别处理：

# deploy/local/otel/collector-langfuse.yaml（示意）
service:
  pipelines:
    traces/jaeger:                     # APM：永远不带内容
      receivers: [otlp]
      processors: [attributes/strip-content, attributes/strip-langfuse, resource, batch]
      exporters: [otlp_grpc/jaeger]
    traces/langfuse:                   # LLM 维度：内容由 server 的档位决定，这里不再删
      receivers: [otlp]
      processors: [resource, batch]
      exporters: [otlp_http/langfuse]

processors:
  attributes/strip-content:            # 现有，再补上新增的内容字段
    actions:
      - {key: gen_ai.input.messages, action: delete}
      - {key: gen_ai.output.messages, action: delete}
      - {key: langfuse.trace.input, action: delete}
      - {key: langfuse.trace.output, action: delete}
      - {key: langfuse.observation.input, action: delete}
      - {key: langfuse.observation.output, action: delete}
  • 为什么脱敏放在 server、而不是 Collector：Collector 的 core 版没有 redaction / transform 处理器，要换成 500 MB 以上的 contrib 版（compose 注释里刻意避开了）。正则脱敏在 server 端做，改动小，还能写单元测试。
  • 为什么 Jaeger 那条也要删 langfuse.* 内容字段：langfuse.trace.input 这些也是内容，不删的话就绕过了 Jaeger 的脱敏规则。
