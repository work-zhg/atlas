Agent Management

Agent 管理设计

Agent 定义的版本化、工具集装配、能力推导与生命周期。这个模块是 capabilities 的唯一所有者 —— 前端据此决定显示哪些按钮，所以它必须是算出来的结论，而不是手填的配置。

版本不可变能力派生装配灰度

01定位与边界

Agent 管理回答三个问题：这个智能体是什么（定义）、它能做什么（能力）、它变了之后存量会话怎么办（版本）。

一条分界线推导出全部能力差异

上下文由谁持有。这是 native 与 acp 唯一的本质区别，也是整份设计里所有不对称的来源：

上下文在哪直接后果
native服务端的 Message 表，每轮重建输入可截断、可改写、可复制 → 编辑类能力全部成立
acpCLI 进程内，服务端只有句柄动不了它 → 编辑类能力全部不成立

这不是策略选择，是机制事实。把它当实现细节抹平，只会得到一个两边都不好用的抽象。

不在本文范围

  • Session / Run 的对象模型 —— 见会话管理
  • Agent 实际执行的链路 —— 见运行时链路
  • 技能内容本身的编写与评审 —— 本文只管「哪个 Agent 挂哪些技能」
  • MCP server 的注册、启停与安全审查 —— 本文只管「哪个 Agent 引用哪些 server」
  • 用户自建 Agent —— 本期不做，见 §10

02定义模型

CREATE TABLE agents (
  agent_id         TEXT        NOT NULL,
  version          INT         NOT NULL,
  status           TEXT        NOT NULL,   -- draft | published | deprecated

  -- 展示
  name             TEXT        NOT NULL,
  description      TEXT,
  icon             TEXT,

  -- 行为（改动即需新版本，见 §03）
  type             TEXT        NOT NULL,   -- native | acp —— 创建后不可改
  cli_type         TEXT,                   -- acp: claude-code | codex | … 不可改（§07）
  system_prompt    TEXT,
  tools            JSONB       NOT NULL,   -- 内置工具名列表
  mcp_servers      JSONB,                  -- 启用的 MCP server 引用
  skills           JSONB,                  -- 技能集合

  -- 运行时装配
  launch           JSONB,                  -- acp: 镜像 / command / args / env
  model_default    TEXT,                   -- 默认模型，会话可覆盖（§08）

  -- 能力（派生，非手填，见 §07）
  caps_declared    JSONB       NOT NULL,
  caps_probed      JSONB,                  -- acp: initialize 探测，覆盖 declared
  probed_at        TIMESTAMPTZ,

  -- 审计
  created_by       TEXT        NOT NULL,
  created_at       TIMESTAMPTZ NOT NULL,
  published_at     TIMESTAMPTZ,

  PRIMARY KEY (agent_id, version)
);

-- 一个 agent 同时只能有一个 draft
CREATE UNIQUE INDEX uq_agent_draft ON agents (agent_id)
  WHERE status = 'draft';
type 与 cli_type 创建后不可修改

不是「改了要发新版本」，而是根本不能改。

native 与 acp 的执行路径、上下文归属、能力集、运行时装配方式全都不同 —— 把一个 native 改成 acp，等于换了个完全不同的东西，而存量会话还引用着它的 agent_id。cli_type 同理：换 CLI 会换掉整组探测能力（§07）。

要换机制或换 CLI，建一个新的 agent_id。这比允许修改再去处理一堆边界情况简单得多，代价只是多一个标识符。

draft 可变，published 不可变

版本一旦 published 就永不修改 —— 因为 sessions.agent_version 指着它，改了等于篡改存量会话的历史行为，而且会话的 capabilities 快照会与实际不符。

但调提示词在开发期是高频动作，每改一个字就发一版不现实。所以留一个 draft：可反复修改、不能被任何 Session 引用、只能通过「试用」入口验证（§09）。满意了再发布成新版本。

顾问与助理是称呼，不是字段

文档里常说的「顾问」与「助理」，指的是两种典型用法，数据模型里只有 type：

顾问  ≈ type = native   进程内执行，出谋划策
助理  ≈ type = acp      经 ACP 驱动 CLI，实际干活

之所以不把角色做成字段，是因为它推导不出任何东西 —— 真正决定能力的是 type（§07）。多一个字段只会多一处可能与实际不符的地方。

03版本化：什么进版本

这是这份设计里最需要想清楚的一条划分。划错了，要么版本爆炸（改个图标都发版），要么存量会话行为被悄悄改变。

判断标准

能改变 Agent 行为的进版本；只影响展示或单次执行的不进。

字段进版本理由
type / cli_type不可改根本不能修改，要换就建新的 agent_id（§02）
system_prompt是行为的主要决定因素
tools是能力边界
mcp_servers是同上
skills是影响行为；但技能内容本身另有版本，见下
launch是镜像版本变化会改变 CLI 行为
model_default否见下
name / description / icon否纯展示，改了不影响任何已发生的事
caps_*否派生值，不是配置（§07）

为什么 model 不进版本

把模型选择做成版本维度会很难受：同一个 Agent 想试三个模型就要三个版本，而它们的提示词、工具、技能完全一样 —— 版本号失去了「行为变更」的含义。

所以 model_default 只是默认值，会话创建时可覆盖，实际使用的模型记在 sessions.model 上。想固定某个 Agent 只能用某模型，那是策略问题，用配置约束而不是版本。

技能是个双层版本问题

Agent 版本记的是「挂了哪些技能」，但技能内容本身会独立更新。于是同一个 Agent 版本，在技能更新前后的实际行为可能不同 —— 版本不可变的承诺出现了缺口。

两种处理，看对确定性的要求：

  • 引用技能版本（严格）—— skills 里存 name@version，完全可复现，代价是技能更新要逐个 Agent 发版
  • 引用技能名（宽松）—— 技能更新自动生效，代价是 Agent 版本不再完全决定行为

建议宽松起步、为关键 Agent 提供固定版本的选项。技能更新通常是修正与增强，强制逐个发版会让技能迭代寸步难行。但这个取舍要写在文档里，别让人以为「版本号一样行为就一样」。

04三个时刻

Agent 定义从写下到真正跑起来，经过三个时刻。把每件事放在正确的时刻做，是这个模块设计的主要内容 —— 校验放晚了就成了运行时事故，解析放早了就无法响应配置变更。

05工具与 MCP 装配

两类 Agent 的工具来源不同

nativeacp
主要工具平台内置工具（tools 列表）CLI 自带（文件读写、命令执行）
我们能控制的全部只有 MCP server 列表与粗粒度闸门
装配时机create_agent(tools=…)session/new 的 mcpServers

发布时校验

for t in agent.tools:
    if t not in tool_registry:
        raise PublishRejected(f"未知工具：{t}")

for s in agent.mcp_servers:
    if s not in mcp_registry or not mcp_registry[s].enabled:
        raise PublishRejected(f"MCP server 不可用：{s}")
    record_tool_fingerprint(agent, s)      # 见 §06

if agent.type == "acp":
    assert agent.cli_type and agent.launch
else:
    assert agent.cli_type is None and agent.launch is None

MCP 配置指向 Higress

运行时渲染 mcpServers 时，每个 server 表达为指向 Higress MCP 网关的 HTTP 端点（运行时链路 §07），而不是直连。这样 acp 类型的工具调用也纳入统一的鉴权、限流、配额与出站审计。

闸门不能替代审批

allowedTools 之类的静态白名单决定「能不能调」，ACP 的 request_permission 决定「这一次准不准」。把审批省掉只留白名单，等于把逐次确认降级成一次性授权（运行时链路 §2.6）。

06MCP 引用的稳定性

MCP server 的工具列表会变，而 Agent 版本管不住它

§03 承诺「同一个 Agent 版本行为一致」。但 mcp_servers 里存的是 server 的引用，它提供哪些工具是连上去之后才知道的 —— server 升级后多了或少了工具，同一个 Agent 版本看到的工具集就变了。

这和技能的双层版本问题（§03）是同一类缺口，但更隐蔽：技能更新至少是我们自己发起的，MCP server 可能是第三方在维护。

处理：记录工具指纹

发布时把每个引用的 MCP server 的工具名集合哈希记进 Agent 版本：

mcp_servers = [
  { "name": "github",
    "tool_fingerprint": "sha256:a3f…",   // 发布时快照
    "fingerprint_at": "2026-09-18T…" }
]
  • 指纹变化时告警，并把依赖它的 Agent 标为待复核 —— 不是自动拦截，因为多数变化是无害的新增
  • 记进可观测性，让「某个 Agent 最近行为变了」能追到 MCP server 升级这个原因
  • 对确定性要求高的 Agent，可以选择指纹不匹配就拒绝启动会话

这不是安全机制，是可复现性机制：目的是让「同一个版本表现不同」这件事可被发现、可被解释，而不是悄无声息。

07capabilities 是派生的

不是手填的配置，是计算出来的结论

capabilities 决定前端显示哪些按钮（会话管理 §04）。如果它是管理界面上的一组勾选框，就必然会和实际能力脱节 —— 有人勾了 regenerate 但 Agent 是 acp，前端就会显示一个点了会失败的按钮。

它应当由 type 与探测结果推导，管理界面只读展示。

推导规则

全部来自 §01 那条分界线 —— 上下文由谁持有：

能力取值依据
regenerate
edit_history
branch
compact
rollback_on_cancel		type == native服务端持有上下文，每轮重建输入 → 截断、改写、复制、压缩都只是改输入
in_run_inputtype == acpRun 进行中插入自由文本。native 的 Run 内交互是结构化决策，不是对话
needs_approval由 spec 决定
bool(require_approval_for)		★ 与 type 正交 —— 两类 Agent 都能做 Run 内审批，见下方修正
resume_mid_run恒为 False两类都不支持
resume_sessionnative: True
acp: 探测		native 的 Message 在库里；acp 取决于 adapter 能力位
 
is_native = (type == "native")

caps.regenerate         = is_native
caps.edit_history       = is_native
caps.branch             = is_native
caps.compact            = is_native
caps.rollback_on_cancel = is_native
caps.in_run_input       = not is_native
caps.needs_approval     = bool(spec.limits.require_approval_for)   ← 由 spec 决定
caps.resume_mid_run     = False
caps.resume_session     = True if is_native else probe()

除 needs_approval 与 resume_session 外，全部由 type 一个字段决定 —— 这正是把角色做成字段没有意义的原因（§02）。

修正 · 来自 atlas 的落地

本节原先写的是 caps.needs_approval = not is_native，理由是「native 无 checkpoint，挂不住」。在 atlas 上落地时被证伪：它的 native agent 有完整的 Run 内审批 —— 中间件在图内挂起、拒绝作为工具结果回给模型继续跑，bash 与编码委派还是强制入审批列表，写在 schema 层。

病根是把两件事塞进了一个能力位。「Run 内能否挂起等人」两类都能；「挂起时接受什么」才是 type 推导的 —— native 接受结构化决策（允许一次 / 总是允许 / 拒绝），acp 还能接受自由文本。前者归 needs_approval 且由 spec 决定，后者归 in_run_input 且由 type 决定。完整论证见详细设计 §02。

capabilities 与具体 CLI 强相关

Claude Code 和 Codex 的能力集大概率不同

caps_probed 来自 ACP initialize 的响应，而那是每个 adapter 各自实现的。Claude Code 的 adapter 可能声明 sessionCapabilities.resume，Codex 的可能不声明 —— 于是同样是 acp 类型，一个能无损恢复会话，另一个每次冷启动都丢上下文。

这个差异用户是能感知到的（一个刷新后接着聊，一个提示「会话已重启」），所以它必须在 Agent 这一层就区分开。

处理：不同 CLI = 不同 agent_id

这一点其实已经由现有模型保证了 —— launch 配置不同就是不同的 Agent 定义。cli_type 字段只是把它显式化、可查询：

agent_id = "code-assistant-claude"
  type     = "acp"
  cli_type = "claude-code"
  launch   = { adapter: "@zed-industries/claude-agent-acp", … }
  caps_probed = { resume_session: "native", … }     ← 探测所得

agent_id = "code-assistant-codex"
  type     = "acp"
  cli_type = "codex"
  launch   = { adapter: "codex-acp", … }
  caps_probed = { resume_session: "none", … }         ← 可能不同
不要做成「一个 Agent，运行时选 CLI」

看起来更灵活，实际会坏在两处：

  • capabilities 无法在建会话时确定 —— 而 会话管理 §04 要求它随会话快照投影给前端，前端据此决定按钮。选 CLI 之后能力才知道，就意味着按钮要在会话开始后才能渲染。
  • sessions.agent_version 钉不住行为 —— 同一个版本在不同 CLI 上表现不同，版本不可变的承诺失效。

用户想选「用 Claude Code 还是 Codex」，那就在 Agent 列表里给他两个可选项，而不是在一个 Agent 内部开关。多一个 agent_id 的成本，远低于把不确定性引入能力契约。

declared 与 probed

acp 的 resume_session 取决于 adapter 声明的 sessionCapabilities.resume 与 agentCapabilities.loadSession，要真正连上才知道（运行时链路 §03）。

caps_declared   发布时按 type 推导的保守值
caps_probed     首次 initialize 握手后写回，覆盖 declared
probed_at       探测时间

未探测时对外一律下发保守值（resume_session = "none"）
探测结果会过期

adapter 升级、镜像更新、本地设备上装了不同版本的 CLI —— 都会让 caps_probed 与实际不符。

所以探测结果要绑定到具体的 launch 配置（镜像摘要或命令+版本），配置变了就作废重探。本地部署下同一 Agent 在不同设备上的探测结果甚至可能不同，此时应取最保守的那个对外下发 —— 宁可少声明一项能力，也不要让用户点了按钮才发现不支持。

08技能与模型

技能绑定

Agent 定义里的 skills 决定它能看到哪些技能。两类的下发方式完全不同：

nativeacp
下发方式进程内直接装载卷挂载或 --plugin-dir（§08）
生效时机下一轮Pod / 进程启动时
在途会话不受影响（版本已钉住）不受影响
按 Agent 下发不同技能集，别用同一个卷挑挑拣拣

运行时链路 §08 已提过：在一个大卷里用 subPath 挑技能，会让「这个 Agent 到底能看到哪些技能」散落在部署模板里。能力边界应当是可查询的配置，不是挂载表的副产品。

模型

agents.model_default    Agent 的默认模型
      ↓ 会话创建时可覆盖
sessions.model          该会话实际使用的模型
      ↓ 运行时
指向 Higress 的 LLM 网关，而非模型厂商

所有模型调用经 Higress（系统架构 §06），所以 Agent 定义里填的是网关侧的模型标识，不是厂商的原始模型名。换供应商、做降级转移对 Agent 定义透明。

acp 的模型可能不受我们控制

native 的模型由 create_agent(model=…) 直接决定。但 acp 跑在 CLI 里，模型能否由我们指定取决于 adapter 暴露了什么（ACP 的 session/set_config_option 或 modes）—— 这是 运行时链路 §12 的验证项。

若不可控，model_default 对 acp 就只是记录性字段，实际模型由 CLI 自身配置决定。此时管理界面不该显示成可选项，否则用户改了没反应，且无从得知为什么。

09生命周期与灰度

draft ──发布（全量校验）──→ published ──发新版──→ published(v+1)
  ↑                             │                      │
  └────── 从某版本派生 ──────────┘                      │
                                ↓                      ↓
                          deprecated ←────────── 不再作为新会话的默认
                                ↓
                          存量会话仍可继续（版本已钉住）

版本升级不影响在途会话

这是 sessions.agent_version 钉住版本带来的直接好处：发布 v2 时，所有引用 v1 的会话继续按 v1 的定义运行，提示词、工具、能力集都不变。

新建会话默认解析最新的 published 版本。用户不会看到「聊着聊着 Agent 性格变了」，这在提示词频繁迭代的阶段尤其重要。

灰度

方式适用
试用 draft开发者自测。指定用户可用 draft 建会话，这类会话应当标记出来，避免混进正常数据与评估样本
按用户灰度新版本先对部分用户生效，其余仍解析旧版本
回滚把上一版重新标为最新 published。不要删除问题版本 —— 引用它的存量会话需要它继续存在
deprecated 不等于可删除

只要还有 Session 引用某个版本，它的定义就必须保留 —— 否则会话无法恢复、capabilities 无法解析、审计无法回溯「当时它是怎么配置的」。

deprecated 的语义是「不再作为新会话的默认」，不是「删掉」。真正的清理要等到引用它的会话全部结束或归档，而那通常是很久以后的事。Agent 定义是审计证据，不是可以随手清理的缓存。

10权限

角色能做什么
平台管理员定义与发布 Agent、管理工具注册表与 MCP server 注册表
租户管理员在平台提供的 Agent 中选择本租户启用哪些；调整非行为字段
普通用户选择已启用的 Agent 建会话；会话级覆盖模型（若允许）
本期不做用户自建 Agent

用户自建意味着任意组合提示词、工具与 MCP server，而这些组合的行为边界需要一套完整的工具授权模型才能说清 —— 那是独立的一块设计。

先把平台定义的 Agent 跑稳。在只有少数几个 Agent 的阶段，自建带来的灵活性远不如它带来的不确定性多。

审计

发布是一次会影响所有用户的变更，必须留痕：谁在什么时候发布了哪个版本、改了什么（与上一版的 diff）、校验结果如何。出问题时第一个要查的就是「最近发了什么版」。

11待验证清单

#验证项影响
1 MCP server 的工具列表能否稳定取到（用于指纹），以及升级后变化是否可靠检出 决定 §06 的可复现性机制能否自动化，还是只能靠人工复查
2 acp 的模型能否经 ACP 的 set_config_option / modes 指定 决定 model_default 对 acp 是可配项还是记录项（§08）
3 同一 Agent 在不同设备/镜像上的 caps_probed 差异幅度 决定「取最保守值」是否够用，还是要按设备分别下发
4 技能引用版本 vs 引用名的实际影响 —— 技能更新后 Agent 行为变化有多大 决定 §03 的宽松策略是否可接受

建议的实现顺序

  1. 先做定义 + 版本 + 发布校验 —— 版本不可变是下游一切承诺的地基。
  2. 再做 capabilities 推导 —— 前端依赖它，且它是纯计算，没有外部依赖。
  3. 然后是探测回写 —— 需要运行时链路先能跑通 initialize。
  4. 灰度与回滚最后 —— 在只有少数几个平台定义的 Agent 时，手工切换最新版本已经够用。
