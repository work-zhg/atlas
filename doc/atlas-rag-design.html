1. 目标、范围与原则

项内容
要解决的问题智能体需要「服务所有用户的领域知识」。记忆设计已经划清：跨用户的 Agent 知识不走 Mem0，走 RAG（记忆设计 §01）
对齐 Dify 的部分知识库、处理规则、三种分段结构、两种索引技术、四种检索方式、两种重排、多库编排、元数据与过滤、召回测试、分段管理、摘要索引、多模态、外部知识库、知识流水线、对外 API
Atlas 的差异① 权限：P1 先用本服务的成员表（与 Dify 的仅自己 / 全团队 / 部分成员同构），Atlas 权限 P2 上线后换成用户中心数据权限；② 可信入库：可选的入库审核（记忆设计要求跨用户知识来源受控、可溯源、可撤回）；③ 多一个 Git 仓库数据源（TeamFlow 产物就在 Gitee）；④ 知识流水线不依赖 Dify 的工作流引擎，用配置化的步骤链实现
不做Dify 的 30 种向量库（保留同样的抽象接口，先实现 Qdrant）；Dify 插件市场（数据源 / 解析器在 Atlas 里是内置实现 + 配置）
许可证边界Dify 采用改过的 Apache 2.0（多租户运营需授权、前端品牌与交互设计受保护）。本设计只借鉴结构与算法思路，不拷贝 Dify 代码与界面外观；实现全部自写

3. 总体架构

与 Dify 的对应：Dify 是 api（Flask）+ worker（Celery）同一份代码两种启动方式；Atlas 新增 atlas-knowledge，同样是 api（FastAPI）+ worker（Celery）同一个镜像。atlas-server 只做「把知识库接到智能体」，不承载入库与检索逻辑。

7.2 清洗（CleanProcessor）

去控制字符（总是）；remove_extra_spaces（连续空白 / 3 个以上换行压缩）；remove_urls_emails（可选）。规则同 Dify。

7.3 切分器与三种索引处理器

FixedRecursiveCharacterTextSplitter 同 Dify：先按用户分隔符切，超长块按 ["\n\n","。",". "," ",""] 递归细分，相邻块按重叠拼接；长度按字符计（Dify 当前的 EnhanceRecursiveCharacterTextSplitter 也是 len，规则里的字段名仍叫 max_tokens）。自定义长度范围 50 ~ ATLAS_KB_MAX_SEGMENTATION_LENGTH（默认 4000）。
实现中修正了 Dify 的两处问题：递归切分的分隔符按字面量匹配（Dify 把 ". " 当正则）；非 ASCII 分隔符（如「，」）不再被 unicode_escape 解成乱码。

8.3 向量化

  • CacheEmbedding（同 Dify）：文档向量先查 kb_embedding_cache，未命中再批量计算并回填；查询向量缓存在 Redis（600s）。
  • 本地 fastembed 是 CPU 推理：worker 按 CPU 核数设并发；api 侧只算查询向量，开销小。模型文件在镜像构建时预下载（同现有 Dockerfile 的做法）。
  • BM25 稀疏向量：jieba 搜索引擎模式分词、去停用词，词用 blake2b 取 4 字节作稀疏下标；文档侧权重 = BM25 的 TF 部分（k1=1.2、b=0.75），查询侧每词 1，IDF 交给 Qdrant 的 IDF modifier。不用 fastembed 的 Qdrant/bm25：它的分词器不切中文。

11. 权限与可信入库

11.1 用户中心登记（追加到 auth/catalog.py）

操作码名称默认角色
kb:create新建知识库ATLAS_BUILDER、ATLAS_ADMIN
kb:manage_all管理全部知识库ATLAS_ADMIN
kb:review审核入库文档ATLAS_ADMIN
kb:settings知识库平台设置（模型、解析、配额、数据源 key）ATLAS_ADMIN

菜单：knowledge「知识库」📚 /knowledge（BUILDER、ADMIN）；系统设置下加「知识库设置」。数据编码 AtlasKnowledgeBase，权限级别 read / write / owner。

11.2 判定规则

动作条件
看到 / 检索 / 召回测试owner，或数据权限 read 及以上，或 kb:manage_all
上传文档、编辑分段、改设置owner / write / kb:manage_all
删除库、改可见范围owner / kb:manage_all
智能体绑定某库编辑智能体的人对该库有 read
智能体运行时检索按智能体的绑定，不按对话用户。用户能用这个智能体就能间接读到它绑定的库 —— 这是有意的（领域知识服务所有用户），所以绑定时前端明确提示「该库内容会对所有可用此智能体的人可见」
服务账号按服务账号被授予的数据权限（用户中心可给服务账号授权）

可见范围与 Dify 的映射：仅自己 = 无授权；全团队 = 授权给根部门（含下级）read；部分成员 = 授权给指定人员 / 部门。

11.3 可信入库（Atlas 扩展）

  • 库级开关 review_required（被智能体绑定的库默认开）：文档入库完成后 review_status=pending，分段 enabled=false；有 kb:review 或库 owner 审核通过后批量启用。
  • 编辑分段也重新进入待审（只影响该分段）。
  • 溯源：每个分段可追到文档、上传人、数据源（文件 / URL / repo@commit）、审核人；撤回 = 停用或删除文档，立即从检索中消失（payload 过滤）。

16. 风险与限制

风险影响应对
本地 CPU 向量化慢大批量入库耗时长；bge-small-zh 效果一般worker 独立扩容；平台设置可切换到网关的向量模型；换模型触发重建
Celery 与 asyncio 混用事件循环与连接池在 prefork 子进程里要正确初始化在 worker_process_init 里建循环与引擎；只用 prefork 池；补集成测试
智能体绑定 = 间接授权库内容对所有能用该智能体的人可见绑定时明示；默认开审核；检索日志可审计
PDF 版式复杂（表格、扫描件）解析质量差Unstructured 选项；P3 流水线里可接 OCR 步骤
新服务增加运维面多 3 个 Deployment同镜像不同命令；健康检查与 OTel 沿用现有约定
与 Dify 的差异全文检索实现、无工作流节点、流水线无画布差异只在实现层；数据结构、接口形状、检索语义保持一致
许可证照搬代码或界面有法律风险只借鉴设计，代码自写，界面用 Atlas 自己的风格
