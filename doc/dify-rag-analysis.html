1. 一句话概括

Dify 的知识库是一条「数据源 → 解析 → 清洗分段 →（增强）→ 向量 / 关键词索引」的异步入库流水线，加上一套「多库编排 → 多路召回 → 重排序 → 按索引结构组装」的同步检索链路。它的特点不在算法新颖，而在工程完整：三种分段结构、两种索引技术、四种检索方式、两种重排、30 种向量库、元数据过滤、召回测试、可编排的知识流水线，以及把检索外包给自建服务的外部知识库接口。

2. 总体架构

组件技术说明
后端Python（Flask）+ SQLAlchemy知识库 API、检索逻辑；入库由 Celery 异步任务执行（tasks/document_indexing_task.py 等）
关系库PostgreSQL知识库、文档、分段、子块、元数据、向量缓存、关键词表、召回记录
向量库可插拔，30 种默认 Weaviate；Qdrant、Milvus、pgvector、Elasticsearch、OpenSearch、Chroma、OceanBase、TiDB 及各云厂商（datasource/vdb/vector_type.py）
Redis—查询向量缓存、文档暂停标记、关键词表写锁
模型经「模型供应商」抽象向量模型、重排模型、问答生成 / 摘要 / 路由用的大模型，都按租户配置

4. 入库流程

上传 / 同步文档 → 建 Document 行（waiting）→ Celery 任务 DocumentIndexingService.run ① extract 解析成若干 Document（文本 + 元数据 + 图片） 状态 parsing ② transform 清洗 + 分段（+ 问答生成 / 摘要 / 附件） 状态 splitting ③ admission 向量空间配额检查（按租户的向量存储额度） ④ count 按向量模型分词器统计每段 token ⑤ save 分段写入关系库（document_segments / child_chunks） ⑥ load 写向量库或关键词表 状态 indexing ⑦ complete 记录 token 与耗时 状态 completed 每个阶段前后检查 Redis 暂停标记（document_{id}_is_paused）；失败记 error，可从 splitting / indexing 阶段恢复

代码：services/knowledge/indexing/execution.py（阶段编排）、adapters/execution.py（各阶段实现）。

  • 阶段化与可恢复：状态机记在 Document 上，任务崩溃后由恢复任务（recover_document_indexing_task）从中间阶段续跑，不用从头解析。
  • 估算：入库前可以预览分段效果并估算 token / 费用（indexing/estimate.py）。
  • 同步：Notion、网页等在线来源可以定时同步（document_indexing_sync_task），按内容哈希判断是否变化。

5. 解析与清洗

类别实现
默认解析器（ETL_TYPE=dify）PDF：pypdfium2（文本 + 内嵌图片）；Word：python-docx；Excel / CSV：pandas；HTML、Markdown、纯文本各有解析器
Unstructured（ETL_TYPE=Unstructured）调 Unstructured API，覆盖 doc / ppt / pptx / eml / msg / epub / xml 等更多格式
在线来源Notion（API）、网页（Firecrawl / Jina Reader / WaterCrawl）
知识流水线解析步骤可以换成插件（如 MinerU、Unstructured、LlamaParse 一类），见 §11.1
清洗（cleaner/clean_processor.py）去多余空白 / 换行、去 URL 与邮箱（可选）、去控制字符；分段后再去掉开头的分隔符号

解析结果统一成 core/rag/models/document.py 的 Document：page_content + metadata（doc_id、doc_hash、document_id、dataset_id …）+ 可选的 children（子块）与 attachments（图片）。

6. 分段：三种索引结构

6.1 切分算法

FixedRecursiveCharacterTextSplitter（splitter/fixed_text_splitter.py） 1. 先按用户指定的分隔符切（默认 "\n\n"；自动模式为 "\n"） 2. 超过 max_tokens 的块，按 ["\n\n", "。", ". ", " ", ""] 依次递归细分 3. 相邻块按 chunk_overlap 重叠 · 长度以向量模型的分词器计 token（from_encoder），不是按字符 · 自定义长度限 50 ~ INDEXING_MAX_SEGMENTATION_TOKENS_LENGTH（默认 4000）

6.2 三种结构（index_processor/processor/）

结构入库检索时返回适合
普通（paragraph）分段 → 每段一个向量（或进关键词表）命中的分段本身一般文档
父子（parent_child）先切父块（段落模式按段切；全文模式整篇为一个父块），每个父块再切子块；只有子块向量化命中子块 → 返回所属父块（并标出命中的子块）「小块匹配准、大块上下文全」：手册、规范、长文档
问答（qa）分段后让大模型为每段生成若干问答对（线程池并发）；索引问题，答案存在元数据命中问题 → 返回答案FAQ、客服；用户提问和问题文本更相似

父子模式要求高质量索引；全文模式适合短文档（父块就是整篇）。

7. 增强：问答对、摘要索引、多模态

能力原理代价
问答对生成LLMGenerator.generate_qa_document：按文档语言生成「问题 / 答案」，正则解析每段一次大模型调用
摘要索引（2026-01）为分段生成摘要并额外向量化（summary_index/summary_index.py）；检索时摘要命中映射回原分段，用摘要分数（retrieval_service.py 的 is_summary 处理）每段一次大模型调用 + 一倍向量
多模态解析时提取图片为附件，Vector.create_multimodal 用多模态向量模型向量化；支持以图检索（QueryType.IMAGE_QUERY）需要多模态向量模型

8. 建索引：向量与关键词

索引技术实现
高质量（high_quality）分段按文本哈希分成 10 组，10 个线程并行：向量化（CacheEmbedding：先查 embeddings 表，命中就复用）→ 写向量库（Vector.create）。父子模式只写子块。向量库按知识库分 collection（可多个知识库共享一个 collection binding）
经济（economy）不调用向量模型：jieba 抽关键词（TF-IDF 抽取，可手工编辑分段关键词）→ 更新倒排表（关键词 → 分段 id）。写入用 Redis 锁串行，防并发覆盖
  • 全文检索不是 Dify 自建的倒排，而是借向量库自身的全文能力（如 Weaviate 的 BM25、Elasticsearch / OpenSearch 的 match、pgvector 上的 PostgreSQL 全文）；不支持全文的向量库就不能用全文 / 混合检索。
  • 分段级操作：启用 / 停用 / 编辑分段都有对应的异步任务（enable_segment_to_index_task 等），编辑后重新向量化；删除文档时同步删向量与关键词。

9. 检索与重排序

9.1 四种检索方式（datasource/retrieval_service.py）

方式原理
语义检索查询向量化（Redis 缓存 10 分钟）→ 向量库相似度检索 → 分数阈值过滤
全文检索向量库的全文 / BM25 检索
混合检索语义与全文在线程池里并行 → 合并去重（按 doc_id）→ 重排序（必须）
关键词检索经济模式：jieba 抽查询关键词 → 查倒排表 → 按命中关键词数排序

9.2 两种重排序（rerank/）

模式原理说明
重排模型（reranking_model）把（查询, 候选）交给重排模型（Cohere、Jina、bge-reranker 等，经模型供应商调用）打分效果最好；多知识库混合不同索引方式时必须用它
加权（weighted_score）分数 = 向量权重 × 余弦相似度 + 关键词权重 × 关键词相似度。向量相似度对候选重新算向量（有缓存）；关键词相似度在候选集合内部用 jieba 抽词、算 TF-IDF 向量的余弦（注释称 BM25，实际是候选集内的 TF-IDF 余弦）不额外依赖重排模型；要求参与的知识库用同一个向量模型

9.3 组装结果

  • 父子：子块命中 → 取父分段内容，记录命中的子块及分数（format_retrieval_documents）。
  • 问答：返回答案（metadata.answer）。
  • 摘要：摘要命中 → 映射回原分段。
  • 首尾重排（data_post_processor/reorder.py）：奇数位顺序 + 偶数位倒序，把相关度高的放到上下文首尾，对应「长上下文中间易被忽略」。
  • 引用：返回来源文档、分段、分数，前端展示引用与归属；分段命中次数累加。

10. 多知识库、元数据过滤与上层接入

10.1 多知识库（retrieval/dataset_retrieval.py）

模式原理
单路召回（single）大模型当路由：把各知识库的名称 + 描述交给它，用函数调用（FunctionCallMultiDatasetRouter）或 ReAct（ReactMultiDatasetRouter）选出一个库再检索。依赖描述写得好
多路召回（multiple，默认）各知识库并行召回 → 合并 → 统一重排序（重排模型或加权）→ Top K / 阈值

10.2 元数据过滤

模式原理
关闭—
自动把元数据字段定义交给大模型，让它从用户问题里抽取过滤条件（如「2025 年的财报」→ 时间、类别条件）
手动在应用 / 节点里配置固定条件（支持变量），先按条件筛出文档 id，再在这些文档里检索

10.3 上层怎么用

  • 对话 / 文本生成应用：在上下文里挂知识库，每轮自动检索并拼进提示词。
  • 工作流：「知识检索」节点（workflow/nodes/knowledge_retrieval），输出结果变量给后续节点。
  • Agent：知识库包装成工具（to_dataset_retriever_tool），由模型决定何时检索。
  • 服务 API：知识库的增删改查、文档上传、分段管理、检索（召回测试接口）。

11. 知识流水线、外部知识库与运维功能

11.1 知识流水线（Knowledge Pipeline）

把入库流程本身做成可视化工作流：数据源节点（本地文件 / 在线文档 / 网页爬取 / 云盘，四类，见 core/datasource，多为插件）→ 解析、清洗、自定义处理节点（可用插件或代码节点）→ 分段节点 → 知识库节点（knowledge_index，按普通 / 父子 / 问答写入）。有内置模板和自定义模板；每次执行有日志（document_pipeline_execution_logs）。它解决的是「不同文档要不同处理」——例如合同走 OCR + 字段抽取，FAQ 走问答生成。

11.2 外部知识库 API

Dify 不做入库，只按约定调用你自己的检索服务：请求带 knowledge_id、query、retrieval_setting（top_k、score_threshold）和可选的元数据条件，返回带分数的片段列表。召回测试、应用接入都照常可用。适合「已有 RAG 系统，只想用 Dify 做编排」。

11.3 运维与质量

功能说明
召回测试（Hit Testing）输入问题，按当前检索配置跑一次，展示命中分段与分数；记录到 dataset_queries（services/hit_testing_service.py）
分段管理查看、编辑、停用分段；编辑关键词；父子模式下编辑子块；修改后自动重建索引
文档管理暂停 / 恢复入库、重试、启用 / 停用、归档；长期未使用的文档自动停用（dataset_auto_disable_logs，按套餐）
配额向量空间额度检查（入库第 ③ 步）、限流记录（rate_limit_logs）
权限知识库可见范围：仅自己 / 全团队 / 部分成员（dataset_permissions）；服务 API 用知识库 API Key

12. 对 Atlas 的启示

12.1 值得借鉴

点为什么
文档状态机 + 分阶段可恢复的入库大文档入库动辄几分钟，失败从中间续跑；暂停 / 重试是运营刚需
父子分段（含全文模式）「小块匹配、大块返回」是性价比最高的效果提升之一
混合检索 + 重排模型，加权作为无模型时的退路中文场景下纯向量对专有名词、编号不敏感，全文 / 关键词补召回
向量缓存（模型 + 文本哈希）重建索引、编辑分段时省大量向量调用
召回测试与召回记录调参与排查「为什么没检到」的唯一手段；对应 Atlas 记忆设计里「浏览是观察质量的唯一手段」的思路
元数据过滤（手动 + 自动）按时间、类别、项目缩小范围，比单纯调 Top K 有效
外部知识库接口反向用：Atlas 的检索服务也可以按这个形状提供接口，便于被其他平台接入

12.2 不宜照搬

点原因
直接集成 Dify 作为 Atlas 的 RAG入库、权限、模型调用都和 Dify 的工作区 / 应用模型耦合；用户与权限要与 Atlas、用户中心打通，成本高
许可证改过的 Apache 2.0：未经书面授权不能用其源码运营多租户环境；使用其前端不得移除 Logo / 版权信息；另声明交互设计受外观专利保护。借鉴思路与信息结构可以，照搬代码与界面外观要谨慎
30 种向量库的抽象层Atlas 已有 Qdrant（记忆在用），先专注一种；抽象层按需再加
经济模式（jieba 关键词表）Qdrant 原生支持稀疏向量（BM25 / SPLADE），可直接做混合检索，不必另维护倒排表
自动入库、无审核Atlas 记忆设计已定：跨用户的 Agent 知识必须来源受控、入库有审、可溯源可撤回；Dify 的知识库没有审核环节，要自己加

12.3 如果 Atlas 自建，映射关系

DifyAtlas 对应
Celery 入库任务 + 文档状态机atlas-config 的入库流水线（与技能、MCP 同为平台资产），或独立 worker
向量库（默认 Weaviate）Qdrant：稠密 + 稀疏混合检索
模型供应商的向量 / 重排模型fastembed（bge 系列向量 + 重排），镜像里已有 bge-small-zh
默认解析器 / UnstructuredMarkItDown（普通文档）+ Docling / MinerU（复杂 PDF、扫描件）
知识库可见范围用户中心数据权限：数据编码 AtlasKnowledgeBase（读 / 写 / 所有者）
应用上下文 / Agent 工具原生 Agent 挂只读检索工具；ACP CLI 经 MCP 调用（与记忆的读取路径一致）
召回测试知识库管理页的召回测试 + 召回记录
