Permissions

权限管理设计

Agent、MCP、技能三类资源的授权模型。核心问题是 MCP —— 它的权限既不是授予 Agent，也不是授予个人，而是两者的交集，因为「能不能用」和「能看到什么」是两个正交的问题。

三层可见性访问权 × 数据权交集委派不提权

01三类资源，三种性质

Agent、MCP、技能都需要管控，但它们的权限性质完全不同，套同一套模型会得到一个既繁琐又漏洞百出的设计。

资源权限回答什么授予给谁
Agent 能不能用它建会话 人（经角色/组）
MCP ① 能不能用这个 server
② 用它能访问到什么数据		 Agent 配置 ∩ 用户授权
见 §04
技能 — 不做独立授权，随 Agent 走
见 §06
判断依据：这个资源本身会不会触达外部数据

Agent 是入口，控制「谁能发起」就够了。技能 是方法论，不提供新的执行能力（MCP 管理 §01）。只有 MCP 会真的去够外部系统里的数据 —— 所以只有它需要两个维度。

02三层可见性

所有资源都经过同样的三层收敛。这一层解决的是「有什么可用」，不是「这个人能不能用」。

① 平台提供    平台定义的 Agent / 内置技能 / 平台 MCP server
      ↓ 租户管理员选择
② 租户启用    本租户实际开放的子集 + 租户自建的资源
      ↓ 角色授权
③ 用户授予    这个用户被允许使用的子集

有效资源 = ① ∩ ② ∩ ③
三层是收敛，不是覆盖

下层只能收窄上层，不能放宽。租户管理员不能启用平台没提供的 Agent，也不能给用户授予租户未启用的 MCP。

这条听起来显然，但实现上容易出错 —— 常见的错法是把「用户授权」做成独立的白名单表，然后忘了与租户启用状态做交集。结果是租户下线了某个 server，已被单独授权的用户还在用。

租户自建资源的命名空间

租户可以自建技能（技能管理 §10）与 MCP server。它们的标识必须带租户前缀，否则两个租户各有一个 code-review 或 github，解析时就会撞车。

03Agent 权限

Agent 的权限最简单：能不能用它建会话。授予对象是人，经角色实现。

CREATE TABLE role_agents (
  tenant_id  TEXT NOT NULL,
  role_id    TEXT NOT NULL,
  agent_id   TEXT NOT NULL,
  PRIMARY KEY (tenant_id, role_id, agent_id)
);

校验发生在建会话时

POST /sessions  { agent_id: "code-assistant-claude" }
   ↓
校验：该 agent 在本租户已启用？用户的角色被授予了它？
   ↓ 否 → 403，且不要在错误里泄露该 agent 是否存在
   ↓ 是 → 建会话，钉住 agent_version
会话建立后不再复查 Agent 权限

权限在建会话时校验一次，之后该会话一直有效 —— 即使用户的角色后来被收回。

理由是一致性：会话已经钉住了 agent_version（Agent 管理 §04），中途因权限变更而让会话不可用，用户会遇到「聊到一半突然报错」。要立即断开的场景（离职、安全事件），应当走显式的会话终止，而不是依赖下一次隐式校验。

但 MCP 权限不同 —— 它每轮都要复查，见 §08。

04MCP：两个正交的问题

「MCP 权限授予 Agent 还是个人」这个问法本身混了两件事

拆开之后答案就清楚了：

回答什么由谁决定
访问权能不能用这个 server Agent 配置 ∩ 用户授权
数据权用它能看到哪些数据 由 credential_scope 决定（§05）

访问权为什么必须取交集

只看一边会出什么问题
只授予 Agent
Agent 配了就能用		 用户只要能用某个配了敏感 server 的 Agent，就能通过它越权。Agent 成了提权通道 —— 而 Agent 的配置是管理员做的，他未必考虑过每个使用者的权限
只授予个人
用户有权就能用		 Agent 的能力边界变得不确定。一个为「查文档」设计的 Agent，会因为某个用户恰好有数据库权限而突然能查库 —— Agent 的行为不再由它的定义决定
两边各自表达不同的意图

Agent 配置 = 能力边界：这个 Agent 设计上该用哪些工具。它由 Agent 定义者决定，是产品设计的一部分。

用户授权 = 行使边界：这个人有没有资格触达这些系统。它由组织的权限体系决定，与 Agent 无关。

两者是正交的意图，所以必须都满足：有效 server = Agent.mcp_servers ∩ 用户被授予的 server。

后果：同一个 Agent，不同用户的工具集不同

这是交集模型的直接结果，也是它唯一需要产品上处理的代价：用户 A 和用户 B 用同一个 Agent 问同样的问题，可能得到不同答案，因为 A 能调 GitHub 而 B 不能。

必须让用户知道，否则就是「时灵时不灵」

如果不告知，用户 B 只会觉得这个 Agent 有时候能查代码有时候不能。能力缺失必须归因：

  • 会话界面上标出「本 Agent 的部分工具因权限未启用」，并给出申请入口
  • 模型侧也要知道 —— 否则它会尝试调用一个不存在的工具，或者编造做不到的理由

05凭证作用域决定严格程度

一条实用规则

platform 作用域的 server，访问权必须严格控制；user 作用域的，访问权可以宽松。

这不是偷懒 —— 而是因为 user 作用域下越权在结构上不可能发生：用户没授权就调不通，授权了也只能看到 OAuth 允许的范围。多加一层访问权控制只是在做重复的事。

反过来，platform 作用域下访问权一旦放行，就没有第二道关了。MCP 管理 §06 的判断标准在这里再强调一次：这个 server 访问的数据是否因用户而异？是的话就该用 user 作用域，而不是靠访问权去补。

06技能不做独立授权

技能随 Agent 走，不单独授予用户

用户能不能用某个技能 = 他能不能用挂了这个技能的 Agent。不设技能级的用户授权。

三条理由

  • 技能不提供新的执行能力 —— 它是「怎么做」的指引，真正的能力来自工具与 MCP。控制了那两处，技能层再加一道是重复的。
  • 模型自主选择，授权难以生效 —— 技能是模型按 description 自己挑的（技能管理 §08）。在模型选择的那一刻做权限判断，要么把没权限的技能从索引里摘掉（那等于按用户改变 Agent 行为），要么选中后再拒绝（模型会困惑并重试）。两种都不好。
  • 会让「Agent 对不同用户表现不同」的复杂度进一步上升 —— MCP 的交集模型已经引入了这个代价（§04），再叠一层技能维度，同一个 Agent 的实际行为将变得难以预测与支持。
真需要区分时，拆成两个 Agent

如果某个技能涉及敏感操作（比如「发布到生产环境」），正确做法是把它拆到一个单独的 Agent，用 Agent 权限控制谁能用 —— 而不是在技能层做授权。

这样 Agent 的能力边界仍然由它的定义完整决定，权限模型也不需要多一个维度。多一个 Agent 的成本，远低于让技能层也变得因人而异。

技能仍然需要的两种管控

管控性质
租户可见性资源归属，不是用户授权。租户自建的技能只对本租户可见（技能管理 §10）
安全审查内容管控，不是权限。技能含可执行脚本，审查按代码审查做（技能管理 §05）

07有效工具集的计算

def effective_mcp_servers(agent, session):
    configured = set(agent.mcp_servers)              # 能力边界
    tenant_ok  = enabled_for_tenant(session.tenant_id)   # 租户启用
    user_ok    = granted_to_user(session.user_id)        # 行使边界

    servers = configured & tenant_ok & user_ok

    # user 作用域的 server，还要检查该用户是否已完成 OAuth
    return [s for s in servers
            if s.credential_scope == "platform"
            or has_valid_credential(session.user_id, s)]

被过滤掉的工具，怎么告诉模型

方式安全性体验
完全过滤
工具不出现在定义里		 不暴露存在性 模型不知道有这回事，只会说「我做不到」，用户不知道是能力问题还是权限问题
保留但拒绝
调用时返回权限错误		 暴露了工具存在 模型能说「这需要 GitHub 授权，请到设置里连接」
按 server 的敏感度选，不是全局二选一

未授权（OAuth 没连）→ 保留并明确报错。用户本来就该知道这个能力存在，只是需要授权。

无权限（角色未授予）→ 完全过滤。这种情况下「有这个工具但你不能用」本身就是不该泄露的信息 —— 尤其当 server 名字能透露内部系统的存在时。

区分依据是「不知道它存在」会不会造成困惑：前者会（用户自己能解决），后者不会（本来就不该他用）。

08校验点

时机校验什么为什么在这里
建会话时Agent 权限一次性，之后不复查（§03）
每轮装配时MCP 有效集合权限变更要能当轮生效
网关调用时再校验一次纵深防御，见下
MCP 权限必须每轮复查，与 Agent 不同

Agent 权限在建会话后不再复查（为了会话一致性），但 MCP 权限每轮都要重算。理由是两者的风险不对称：

  • Agent 权限被收回，最坏是这个人继续用一个他不该用的 Agent 聊天
  • MCP 权限被收回，意味着他还能继续读不该读的数据

对 native 每轮重新装配工具集是天然的（每轮都在构造 agent）。对 acp 麻烦一些 —— mcpServers 是建会话时传入的快照（MCP 管理 §05），所以撤销必须在网关侧生效，见下。

网关是最后一道，也是 acp 唯一的一道

Higress 在每次 MCP 调用时用 session-scoped-token 解析身份，再校验一次访问权。这既是纵深防御，也是 acp 类型撤销权限的唯一手段 —— 因为它的工具列表在会话开始时就固定了，改注册表或改 Agent 配置都影响不到进行中的会话。

身份只能由网关从令牌解析

与记忆服务同一条规则（记忆 §09）：user_id 绝不能出现在工具参数或请求体里，网关解析后强制覆盖，收到的同名字段一律丢弃。

否则模型在处理不可信文本（代码仓库、网页、工具输出）时可能被诱导指定他人身份 —— 而权限检查会老老实实按那个身份放行。

09委派不提权

subagent 用发起用户的权限，不是被委派 Agent 的权限

native Agent 可以把任务委派给其他 Agent，包括 acp 类型（native Agent §07）。如果 subagent 按它自己的配置获得权限，委派就成了一条提权路径：

用户 U 无 github 权限
  → 用 Agent A（无 github）建会话
  → A 委派给 Agent B（配了 github）
  → B 读到了 U 无权访问的数据

而这条路径模型可以自己发起，甚至可能被提示词注入诱导。

规则

subagent 的有效权限 = 发起会话的用户的权限
                     ∩ subagent 自身 Agent 配置
                     ∩ 父 Agent 的可委派白名单
  • 用户权限不变 —— 委派链条再长，能触达的数据始终不超过发起人的权限
  • 可委派白名单 —— 在父 Agent 定义里声明能派给谁（native Agent §06），不让模型自由选任意 agent_id
  • 递归同样受限 —— subagent 再委派时规则一样，且受深度上限约束
用户凭证要能传递到 subagent

user 作用域的 MCP server 需要该用户的 OAuth 凭证。subagent（尤其是跑在独立 Pod 里的 acp subagent）调用时，网关要能从它的 session-scoped-token 解析出同一个发起用户。

所以委派时签发的令牌必须携带原始用户身份，而不是重新以「系统」身份签发。这一点做错了，表现是 subagent 的 user 作用域工具全部调不通 —— 或者更糟，以平台身份调通了。

10审计

要留痕的三类事件

事件记录什么
授权变更谁在什么时候给谁授予/收回了什么。这是权限体系里最需要回溯的东西
拒绝被拒绝的访问尤其要记 —— 大量拒绝可能是配置错误，也可能是探测行为
实际调用谁、经哪个 Agent、调了哪个 server 的哪个工具。经 Higress 统一采集
审计要能回答「这个数据是怎么被访问的」

出了数据泄露事件时，需要追的链路是：哪个用户 → 哪个会话 → 哪个 Agent → （可能经过哪个 subagent）→ 哪个 MCP server → 什么数据。

这条链路上每一环都要有记录，且能用 session_id / run_id 串起来（可观测性 §06）。缺任何一环，事后都说不清楚。尤其是委派 —— 如果不记录 subagent 是被谁派出去的，链路就断在中间。

与可观测性的分工

审计日志与遥测不是同一套数据：遥测可采样、可设 TTL、为排查性能而生；审计必须全量、长期保留、为追责而生。

实现上可以共用采集管道（都经 Collector），但存储与保留策略必须分开。把审计记录混在会被采样丢弃的 trace 里，是个到用时才会发现的错误。

11待验证清单

#验证项影响
1 Higress 能否在每次 MCP 调用时做访问权校验 —— 而不只是转发 这是 acp 撤销权限的唯一手段（§08），做不到就无法在会话中途收回权限
2 委派时的令牌签发 —— 能否携带原始用户身份并被网关正确解析 §09 的核心，做错了会导致提权或功能不可用
3 每轮重算有效工具集的开销 —— 权限查询是否会拖慢装配 决定是否需要带失效的权限缓存
4 「部分工具不可用」的提示对模型行为的影响 —— 会不会导致它反复尝试或胡乱解释 决定 §07 的告知方式与措辞

建议的实现顺序

  1. 先做 Agent 权限 + 三层可见性 —— 最简单，且是所有资源的公共基础。
  2. 再做 MCP 访问权的交集计算 —— native 侧先跑通，因为它每轮装配天然支持。
  3. 然后是网关侧校验 —— acp 的权限撤销依赖它，且必须先完成 §11 第 1 项验证。
  4. 委派的权限传递最后 —— 在 subagent 功能上线之前完成即可，但不能晚于它。
