日期：2026-10-12 · 关联：RAG 评测体系设计、可观测性设计、挂起与恢复、ACP 详设
目标：评测的是 Agent 的工程能力（harness），不是模型。模型固定，只换包在模型外的那一层工程——循环、上下文管理、工具、错误恢复、断点续跑、审批、记忆、子智能体、沙箱——看它让同一个模型多做成了多少事、花了多少代价、出了多少事故。

1. 目标与边界

Agent 的表现 ≈ 模型能力 × 工程能力。评模型的做法是固定 harness 换模型；评工程正相反：固定模型、换 harness，分数差就是工程的贡献。公开榜单（SWE-bench、Terminal-Bench）本身就按「agent × 模型」组合排名，同一模型在不同 harness 下可以差十几个百分点——这部分差距就是本文要量的东西。

要回答的问题对应设计
Atlas 的 harness 比「裸循环」强多少？增益对照：Atlas 原生 vs 最简基线（§4）
跑在 Atlas 里会不会比直接跑同一个 CLI 差？平台损耗对照：Atlas ACP(Claude Code) vs 直接运行 Claude Code（§4）
和业界其他 harness 比在什么位置？横比：同一模型下 Atlas vs Claude Code / OpenHands 等（§4）
哪项工程设计真有用、哪项是负担？消融：逐项关闭压缩、子智能体、记忆、知识库……（§4）
出故障时能不能扛住？工程专项：故障注入、杀 Pod 续跑、审批中断、上下文溢出（§12）
失败到底卡在哪个工程环节？轨迹分析与失败归因（§13）
与 RAG 评测的关系：同一套框架（bench/：运行器、断点续跑、统计、报告复用），同一套方法论——RAG 把链路拆成检索 / 生成分别评；Agent 拆成结果（做没做成，校验脚本判）与过程（哪个工程环节出了问题，轨迹判）。知识库作为 Agent 的一项能力时，它的质量由 RAG 评测负责，这里只评「Agent 有没有用好它」。

不在范围内：模型本身的能力排名；平台的功能完备性清单（那是验收，不是评测）；纯性能压测（QPS、并发上限，另做）。

2. 原则

原则说明
只控制一个变量一组对照里只有 harness 不同：同一模型（同一网关、同一参数）、同一任务环境镜像、同一工具集、同一预算、同一校验脚本。模型与参数进实验快照
只走公开接口评 Atlas 只用它的 HTTP API（建智能体、会话、run、事件流、审批、轨迹），不 import 任何 atlas 包（沿用 import-linter 约束）。这样评的就是用户真实看到的那个平台
结果用程序判，过程用轨迹判「做成没有」一律由任务自带的校验脚本判（测试、状态比对），不让 LLM 判对错；LLM 只用于过程归因，且要人工校准（§13）
每题多次Agent 方差远大于 RAG：每题至少 3 次（正式 5 次），报 pass@1 均值、pass^k 与置信区间
成本与成功率一起报成功率高但贵三倍不一定更好：报 token、费用、耗时，画成功率—成本图
完全隔离每次试验全新会话、全新执行环境；任务结束清理。不复用上一次的工作区
预算是评测协议，不是平台限制任务预算（步数 / token / 墙钟）由评测运行器执行：超预算记为失败并调用取消接口。不为评测在平台里加超时——平台「不设运行 / 审批上限、断联恢复」的原则不变
可复现实验快照：任务集版本、镜像 digest、智能体配置快照（agent_version）、模型、网关、预算、随机种子；原始轨迹全部落盘，可离线重判

3. 现状约束（评测前必须知道的）

按当前代码梳理出的、直接影响评测设计的事实：

事实影响处理
原生智能体的 bash（模型侧工具名 execute）未实现：Docker 实现已移除，K8s Pod 沙箱未接入（tool_registry.py 中 implemented=False） 原生智能体目前跑不了需要执行命令的任务（Terminal-Bench、SWE-bench） 任务集分两类（§6）：命令行类先只评 ACP；工具 / API 类原生与 ACP 都评。沙箱接入后原生自动加入命令行类。这本身就是评测要暴露的工程缺口
原生智能体的文件系统是对象存储实现，不能按内容搜索、单次读写有上限代码类任务原生侧天然吃亏报告里单列「工具能力差异」，不把它混进 harness 结论
勾了 bash 会强制 execute 进审批列表无人值守评测会卡在审批适配器按「审批策略」自动处理（§9.2），审批次数与等待时间计入指标
ACP 智能体的执行环境是 Pod 镜像（cli.image = CLI + adapter + bridge）任务需要自己的环境（依赖、文件、服务）为每个任务构建「任务镜像 + Atlas 智能体层」的派生镜像（§8.1）
LimitSpec 有默认 max_steps=40、max_total_tokens 等默认值可能先于任务预算截断，导致不公平实验配置显式给出 limits（不小于任务预算）并进快照；被平台限制截断的单独计数
每个 run 有归档轨迹（GET /v1/runs/{id}/trace）与 OTel 链路（run 为根）过程指标有现成数据源过程指标以归档轨迹为准；OTel 链路做补充（耗时细节、知识库检索漏斗）
同一会话串行（已有运行中的 run 时返回 409）；run 可挂起续跑多轮任务（模拟用户）要等上一轮结束适配器按事件流等待终态，再发下一轮

4. 被测方与对照设计

4.1 被测方

代号被测方说明
atlas-nativeAtlas 原生智能体Atlas 自己的 harness（engine kernel + 中间件：压缩、子智能体、审批、记忆、知识库、技能、MCP）
atlas-acp:<cli>Atlas ACP 智能体在 Atlas 的 Pod 里跑外部 CLI（Claude Code 等），Atlas 负责会话、挂起续跑、审批、文件、观测
direct:<cli>直接运行同一 CLI不经 Atlas，同一任务镜像、同一模型下直接跑 CLI（可借助 Terminal-Bench 的运行框架 Harbor）
baseline:mini最简基线mini-SWE-agent 风格：只有 bash、线性对话、无压缩无子智能体。代表「模型裸跑」的水平
other:<name>其他 harness（可选）OpenHands 等开源 agent，用于横比

4.2 四种对照

增益 atlas-native vs baseline:mini 同模型 → Atlas harness 带来的提升 平台损耗 atlas-acp:claude vs direct:claude 同模型 → 跑在 Atlas 里有没有变差（期望 ≈ 0） 横比 atlas-native / acp vs direct:* / other:* 同模型 → 在业界的位置 消融 atlas-native vs atlas-native − 某能力 同模型 → 每项工程设计的边际贡献 （可移植性：以上任一对照换 2～3 个模型重复，看结论是否随模型改变）
为什么「平台损耗」很重要：ACP 的卖点是「把成熟 CLI 原样搬进平台并加上会话、审批、续跑」。如果 Atlas 里的 Claude Code 比直接跑的成功率低，说明桥接、权限模式、文件同步或提示注入在拖后腿——这类问题只有这个对照能发现。

7. 统一任务模型

各任务集由导入器转成统一格式（var/bench/agent-tasks/<suite>/<task_id>/）：

task.yaml
  id: tbench/fix-git-merge          # 全局唯一：<suite>/<原始 id>
  suite: terminal-bench@2.0
  category: cli | tool | dialog | security | eng
  tags: [git, long-horizon]
  instruction: |                    # 第一轮发给 Agent 的话
    ...
  environment:
    image: ghcr.io/…@sha256:…       # 任务环境（命令行类）；工具类为空
    workdir: /app
    mcp_servers: [tau2-airline]     # 工具类：由任务环境服务提供的 MCP 工具（§8.2）
  user_simulator:                   # 多轮任务（τ²）：模拟用户的设定；单轮为空
    persona: …
    goal: …
    max_turns: 30
  verifier:
    kind: script | state | callable # 命令行类跑测试脚本；工具类比对数据库终态
    command: bash /tests/run.sh
  budget: {max_steps: 200, max_tokens: 2_000_000, wall_s: 1800}
  faults: []                        # 工程专项（§12）才有：注入什么、何时注入
  expected_behavior: []             # 工程专项的期望行为断言
  license: Apache-2.0

一次试验（trial）的产物：

trial.json
  task_id, variant, model, trial_index, seed
  outcome: success | failure | budget_exceeded | infra_error | platform_limit
  verifier: {passed, score, output_tail}
  usage: {input_tokens, output_tokens, cache_read, cost_usd}
  timing: {wall_s, first_action_s}
  counts: {model_calls, tool_calls, tool_errors, approvals, compactions, subagent_calls}
  refs: {thread_id, run_ids, trace_ids}   # 回到 Atlas 与 Jaeger / Langfuse 查原始现场
trajectory.jsonl                           # 归一化轨迹（§11.2）
raw/                                       # 原始事件流与归档轨迹，离线重判用

8. 任务环境

8.1 命令行类：任务镜像 + 智能体层

Terminal-Bench / SWE-bench 的每道题都有自己的环境镜像，而 Atlas ACP 的执行环境是 cli.image。做法是派生镜像：在任务镜像之上叠加 Atlas 智能体层（CLI + adapter + bridge），得到这道题专用的 ACP 镜像，通过智能体配置的 cli.image 指定。

任务镜像（题目自带 Dockerfile） + 智能体层（与 atlas-acp-bridge 镜像同版本的 CLI / adapter / bridge） = bench/<task>:<digest> ──▶ 推到本机仓库 ──▶ 每个 trial 用它建 ACP 会话 direct / baseline 用同一个任务镜像（Harbor 在容器里装各自的 agent），保证环境一致
  • 派生镜像按（任务镜像 digest, 智能体层版本）缓存，只构建一次。
  • 校验在 Agent 结束后、在同一个执行环境里跑（Atlas 侧经会话 Pod 执行校验命令；见 §9.1 的取环境方式），与 Harbor 的做法一致。
  • 原生智能体沙箱接入后，同一派生镜像作为原生的沙箱镜像，命令行类即可加入原生对照。

8.2 工具类：任务环境服务（MCP）

τ²-bench、AgentDojo、BFCL 的工具是 Python 函数加一个可变的领域状态（数据库）。把它们包成一个评测侧的 MCP 服务（bench-env），按 trial 隔离状态：

POST /trials                      → {trial_id, mcp_url, token}   # 初始化一份领域状态
MCP  {mcp_url}                    → 该任务集的工具（get_reservation、cancel_order…）
GET  /trials/{id}/state           → 终态，给校验器比对
POST /trials/{id}/faults          → 设置故障注入规则（§12）
DELETE /trials/{id}
  • Atlas 原生与 ACP 都通过智能体配置挂上这个 MCP 服务（mcp: 工具），direct 侧 CLI 也挂同一个——三方看到的工具定义逐字相同。
  • 工具描述与参数 schema 取自任务集原文，不做改写（改写就成了在评提示工程）。
  • MCP 服务同时记录每次工具调用（参数、结果、耗时），作为轨迹之外的第二份独立记录，用于核对。

8.3 多轮任务：模拟用户

τ²-bench 一类任务需要「用户」与 Agent 多轮对话。模拟用户由运行器驱动：Agent 一轮结束（run 终态）→ 把 Agent 的回复交给用户模拟模型 → 得到下一句 → 新建下一个 run。用户模拟模型固定且与被测模型分开，参数进快照；用户说出结束语或到达轮数上限即结束。

9. 被测方适配器

class AgentPlatform(Protocol):
    name: str
    async def prepare(self, variant: VariantConfig, task: Task) -> Prepared   # 建智能体 / 镜像 / 工具
    async def start(self, prepared: Prepared, trial: TrialCtx) -> Session     # 新会话
    async def turn(self, session: Session, message: str) -> TurnResult        # 一轮：发消息 → 等终态
    async def exec_in_env(self, session: Session, command: str) -> ExecResult # 在执行环境里跑校验
    async def collect(self, session: Session) -> RawTrace                     # 原始事件 / 归档轨迹 / 用量
    async def cancel(self, session: Session) -> None                          # 超预算时取消
    async def cleanup(self, session: Session) -> None

9.1 Atlas 适配器（只用公开 API）

步骤接口说明
建智能体POST /v1/agents每个 variant 一个评测专用智能体（名称前缀 bench:，可整体清理）；配置快照取 agent_version_id 写进实验快照
新会话POST /v1/threads每个 trial 一个会话 → 全新 Pod / 工作区
发一轮POST /v1/threads/{id}/runs（带 Idempotency-Key）立即返回 run_id

审批POST /v1/runs/{id}/approvals/{aid}按审批策略自动决定
取轨迹GET /v1/runs/{id}/trace、GET /v1/runs/{id}归档轨迹（含子 run）与用量
取消POST /v1/runs/{id}/cancel超预算时由运行器调用
在环境里跑校验见右命令行类：评测专用的「校验」智能体变体复用同一会话的执行环境发一条只执行校验脚本的指令，不经过被测 Agent。若平台后续提供会话级执行接口，改用接口（P2 评估，见 §18）
取文件GET /v1/threads/{id}/files / download需要产物文件的任务

身份：评测专用服务账号（Bearer atlas_sk_…），只授予建智能体、建会话所需的权限。

9.2 审批策略

策略行为用途
approve_all全部批准（默认）能力评测：不让审批成为变量；审批次数与等待时间仍计入指标
policy按规则批 / 拒（如拒绝 rm -rf、拒绝写工作区外路径）安全评测：看被拒后能否改道完成
deny_first每类操作第一次拒绝、之后批准工程专项：审批被拒后的恢复
delayed延迟 N 分钟再批工程专项：长时间等待审批后能否续上（不设审批上限的验证）

对 direct 与 baseline：用各自 CLI 的等价权限模式（如 Claude Code 的权限设置），使「能做什么」与 Atlas 侧一致；做不到等价的在报告里注明。

9.3 外部适配器

  • direct / baseline / other：通过 Harbor（Terminal-Bench 官方运行框架）或各自 CLI 在同一任务镜像的容器里运行；以 K8s Job 形式跑在本机集群（不在宿主机起常驻进程）。
  • 它们的轨迹格式各不相同，由各自的解析器转成统一轨迹（§11.2）；解析不了的字段留空，报告里标「不可比」。

  • 矩阵展开：variant × task × trial → 独立 trial，打乱顺序执行（避免时段因素系统性偏向某个 variant）。

11. 判分：结果与过程

11.1 结果

  • 命令行类：任务自带测试脚本的退出码 / 通过比例；工具类：领域状态终态与标准答案比对（τ²-bench 的判法）；安全类：效用与攻击是否成功两个布尔。
  • 假成功：Agent 最后一条消息声称完成（裁判模型二分类或关键词）但校验失败 → 单独计数。这是工程上最伤用户信任的一类失败。

11.2 统一轨迹

把各家原始记录归一化成一个步骤序列，过程指标都在它上面算：

{"i": 12, "kind": "model_call", "input_tokens": 18234, "output_tokens": 410, "cache_read": 15000, "latency_ms": 5200}
{"i": 13, "kind": "tool_call", "tool": "execute", "args_digest": "…", "ok": false, "error": "exit 127", "latency_ms": 340}
{"i": 14, "kind": "approval", "tool": "execute", "decision": "approve", "wait_ms": 20}
{"i": 15, "kind": "compaction", "before_tokens": 150000, "after_tokens": 61000}
{"i": 16, "kind": "subagent", "name": "researcher", "run_id": "…", "ok": true}
{"i": 17, "kind": "message", "role": "assistant", "text_digest": "…"}

Atlas 侧由归档轨迹（TraceEvent）转换；参数与正文只存摘要（digest）和长度，原文保留在 raw/ 里供人工复核。

11.3 过程指标的算法

指标算法
工具错误率ok=false 的工具调用 / 全部工具调用；按错误类型（参数校验、执行失败、超时、权限）分组
重复调用率同一工具、同一参数摘要在 5 步内重复出现的次数 / 工具调用数
打转连续 N 步（默认 6）没有任何「新信息」（新工具、新参数、新文件）→ 记一次打转
恢复率工具出错后 K 步内（默认 3）出现成功的同目标调用（同工具或语义等价工具）的比例
首个有效动作时间从发消息到第一次「改变环境」的工具调用（写文件、执行命令、写型 API）

12. 工程专项测试（atlas-eng）

每个场景 = 一个简单、模型稳能做成的基础任务 + 一个注入条件 + 期望行为断言。基础任务要简单：失败只能归因于工程，而不是模型不会做。

场景注入方式期望行为（断言）指标
工具瞬时故障bench-env 让某工具前 2 次返回 500 / 超时重试或换路后完成；不声称已完成恢复率、额外步数、假成功率
工具返回错误数据某次返回字段缺失 / 类型错误识别异常并核实，不把脏数据写进结果脏数据写入次数

杀 Pod 续跑任务进行到第 N 步时删除会话 Pod平台恢复执行环境并从断点继续完成；已完成的副作用不重复执行续跑成功率、重复副作用次数、恢复耗时

大量干扰工具额外挂 50 个无关 MCP 工具仍选对工具工具选择准确率、token 增量
子智能体委派可并行分解的任务，配置 ephemeral 子智能体委派并汇总，结果正确；子 run 失败时主 Agent 能处理成功率、墙钟加速比、子 run 失败处理率
需求模糊指令缺关键参数，模拟用户知道答案先问再做，而不是猜澄清率、猜错率
断联重连评测客户端中途断开 SSE，稍后带游标重连事件不丢不重，run 不受影响事件缺口数

故障注入点集中在三处，都在平台外部，不改平台代码：bench-env（工具层）、网关故障代理（模型层，评测时把智能体的模型网关指向一个可编程代理）、kubectl（基础设施层：删 Pod、重启 Deployment）。

杀 Pod / 重启 server 这类场景有副作用：只在评测专用环境跑，不在开发者正在用的本机集群上跑（会影响别人的会话）。运行器启动时检查环境标记，不满足就跳过这类场景。

13. 轨迹分析与失败归因

对每个失败的 trial 归一个主因（可附次因），用固定分类：

类别典型表现通常对应的工程环节
理解错需求做了别的事；漏了约束系统提示词、澄清策略
规划失误步骤顺序错、遗漏子目标、过早结束待办 / 规划机制
工具误用参数错、选错工具、忽略工具报错工具描述与 schema、工具数量
上下文丢失忘了前面读过的信息；压缩后丢关键事实压缩策略
错误未恢复报错后放弃或原样重试打转重试 / 恢复机制
假成功声称完成但校验失败完成前自检
委派失败子智能体结果没被正确使用、子 run 失败未处理子智能体机制
环境 / 权限缺依赖、权限不足、审批卡住执行环境、权限模式
超预算步数 / token / 时间用尽效率
平台错误Pod、网关、桥接异常平台稳定性（infra_error）
  • 先规则后模型：能用规则判的先判（超预算、平台错误、工具报错未处理、打转）；剩下的交给裁判模型读压缩后的轨迹归类，输出类别、证据步骤号与一句理由。
  • 人工校准：每次实验抽 10%（至少 20 个）失败 trial 人工归类，计算与裁判的一致率（Cohen's κ）；κ < 0.6 时不发布归因结论，先改归因提示词。多智能体场景可参照 MAST 失败分类补充类别。
  • 产出：每个 variant 的失败构成堆叠图；配对比较时给出「A 比 B 少了哪类失败」——这就是工程改进的落点。

项目做法指标
间接提示词注入AgentDojo：工具返回里夹带攻击指令攻击成功率（越低越好）、注入下的任务效用

15. 统计与报告

  • 成功率：每题 k 次的均值 → 题目层面平均；bootstrap（按题重采样）给 95% 置信区间。
  • pass^k：k 次全成功的题目占比；与 pass@1 一起报，差距大说明不稳定。
  • 配对比较：同一道题上两个 variant 的成功率差，按题配对做置换检验或配对 bootstrap；只报「显著 / 不显著」与效应大小，不只报平均分。
  • 成本：每个 variant 的「成功率—平均费用」散点与帕累托前沿；单位成功成本（总费用 / 成功次数）。
  • 分层：按任务集、类别、标签（长程、git、多轮…）分别出结果，避免被大类掩盖。
  • 回归门槛：平台改动后跑「回归子集」（BFCL 多轮 + atlas-eng 的快速场景 + T-Bench 小子集），关键指标显著下降即判定回归。

报告（md + html）首页：实验快照、各 variant 的成功率 / pass^k / 成本、四种对照的结论、平台错误与安全门槛；后续页面：分层结果、失败构成、典型失败案例（附 Atlas 会话链接与链路链接）。

18. 风险与限制

风险说明缓解
原生智能体缺沙箱命令行类任务短期内只能评 ACP，原生的核心对照（增益）在命令行类上暂时缺位工具类任务先评原生；沙箱接入列为评测前置依赖之一
「在环境里跑校验」的方式Atlas 目前没有会话级的直接执行接口，借道校验智能体发指令有被模型改写的风险校验指令用固定脚本、检查执行回显与退出码；P2 评估是否需要一个仅限服务账号的会话执行接口
等价性direct 侧的权限模式、提示词与 Atlas 侧不完全等价逐项列出差异；平台损耗结论附带「已知差异」
成本每题 5 次 × 多 variant × 长任务，token 费用与集群资源都不小先子集再全集；回归子集控制在小时级；缓存派生镜像
方差小子集 + 高方差容易得出伪结论配对比较 + 置信区间；不显著就不下结论
数据污染公开题可能在模型训练集里同模型对照时偏差在两边抵消，影响的是绝对分而非差值；绝对分只作参考
任务集版本漂移公开任务集会修题、换镜像注册表记录版本与镜像 digest；跨版本结果不直接比较
破坏性专项的副作用杀 Pod、重启 server 会影响同集群的其他会话只在评测专用环境运行，运行器检查环境标记
许可证各任务集许可证不同，部分镜像含第三方代码导入时登记许可证；任务数据不入库，只入导入脚本
