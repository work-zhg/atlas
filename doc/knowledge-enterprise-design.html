知识库企业级能力设计（核心模块）

日期：2026-10-14 · 关联：知识库详细设计（现有架构与流水线）、RAG 评测体系、上下文管理设计
范围：文档解析、分段、向量化与索引、检索、生成与引用、知识更新与数据源、评测与反馈七个核心模块。
不在本期：OCR（扫描件与图片型 PDF 只检测、标记，不识别）；横向的企业级要求（水平扩容、多租户、安全合规、运营看板）。

结论先行：现有的入库流水线、结构感知分段、稠密 + BM25 混合检索、检索漏斗与评测框架是可靠的骨架，本设计不重写，只在已有阶段上扩展。三处最大的短板依次是：
  1. 文档理解：PDF 只取文本层（双栏读串、页眉页脚混入、表格拍平）——决定效果上限；
  2. 检索的准确与可控：不能按业务元数据过滤、没有文档级权限、口语化和多轮提问没有改写；
  3. 可信回答与知识保鲜：没有可追溯引用与拒答；知识只能手动上传，不能从源系统增量同步。
每一项改进都要能在检索漏斗上看到候选质量的变化，并在评测集上用配对比较证明有效，否则不默认开启。

1. 目标与原则

目标衡量方式
真实企业文档（双栏 PDF、带表格的报表、PPT、Wiki）能被正确理解解析质量指标；评测集上召回率（Recall@k）、MRR 的提升
检索结果准确、可控：按业务条件过滤，只返回调用者有权看到的内容，只返回生效版本过滤 / 权限 / 版本类评测题的通过率；越权检索为 0
回答可信：每个结论可追溯到原文，没有依据时明确拒答引用正确率、忠实度（faithfulness）、无答案题的拒答率
知识保鲜：源系统的变化自动、增量地反映到知识库同步延迟、增量同步时重新向量化的比例

原则

  • 渐进扩展：沿用现有流水线五阶段、表结构、Qdrant 布局和检索漏斗；新能力作为新阶段或新选项挂上去，默认行为不变。
  • 每项开关都要被评测证明：查询改写、上下文补全、问答对索引这些会增加成本的能力，按知识库开关；在评测集上配对比较显著提升后，才考虑默认开启。
  • 可观测：每个新阶段都写进检索记录（漏斗）和链路 span，失败可以定位到阶段。
  • 成本可控：用到 LLM 的步骤（上下文补全、问答对、改写、图片描述、忠实度校验）都有缓存（按内容哈希）、批量和预算上限，失败时降级为不做，而不是让入库或检索失败。
  • 权限在服务端判定：过滤条件、权限范围由服务端根据调用者身份决定，永远不交给模型生成。

2. 现状盘点

模块已有缺口

评测检索评测（Recall / Precision / MRR / NDCG）+ RAGAS；配置化实验只有样例集；无线上反馈；改配置不会自动评测；无分段质量分析

4. 文档解析

4.1 统一中间表示 DocIR

现在各解析器直接输出纯文本，结构信息（标题、表格、页码）要么丢失、要么由结构感知分段再从文本里猜一遍。改为所有解析器输出统一的块序列 DocIR，分段直接消费结构：

DocIR = [Block]
Block {
  type:   heading | paragraph | list_item | table | code | image | caption | quote
  text:   str                 # table 为 Markdown；image 为描述（有的话）
  level:  int | None          # heading 层级
  table:  {rows, header_rows} | None   # 结构化表格（合并单元格已展开）
  page:   int | None          # 来源页码（PDF / PPTX 页）
  bbox:   [x0, y0, x1, y1] | None      # 页内坐标，用于引用高亮（§8.2）
  asset:  str | None          # 图片在对象存储里的 key
  attrs:  {...}               # 解析器附加信息（字体大小、是否加粗、列号……）
}
  • 兼容：保留现有「纯文本 → 结构感知分段」路径；DocIR 渲染成 Markdown 后也能走老路径。结构感知分段新增一个入口直接接收 Block 序列，跳过从文本里识别标题这一步。
  • 落库：DocIR 以 JSON 存到对象存储（{dataset}/{document}/docir.json），用于重新分段（换分段规则时不必重新解析）和前端的解析预览。

4.2 解析器路由与插件化

类型解析器说明
PDF（默认）版面感知解析器（基于 pypdfium2 / pdfplumber 的字符坐标）轻量、CPU 即可；做阅读顺序、页眉页脚、标题识别、简单表格（§4.3–4.4）
PDF（高级）Docling / MinerU（版面模型）复杂版面、复杂表格的效果更好但更重；按处理规则选用，跑在独立的 worker 队列（kb.parse.heavy），不阻塞普通入库
DOCX现有（python-docx）输出改为 DocIR；补图片抽取
PPTX新增（python-pptx）每页：标题 → heading，文本框按位置排序 → paragraph / list_item，表格 → table，备注 → paragraph（标注「备注」），图片 → image
Markdown新增（markdown-it）原生标题、列表、表格、代码块；链接保留为属性
邮件（EML / MSG）新增主题、发件人、时间进元数据；正文按 HTML / 文本解析；附件作为子文档入库（带 parent_document）
网页 URL新增抓取后用正文抽取（readability 类算法）去掉导航、广告，再按 HTML 解析
XLSX / CSV / HTML / 纯文本现有输出改为 DocIR（XLSX / CSV 的工作表作为 table 块）

解析器实现统一接口 parse(data, meta) -> DocIR，按 MIME 与处理规则里的 parser 选项路由；新增格式只需注册一个解析器。

4.3 版面分析（默认 PDF 解析器）

问题做法
双栏 / 多栏读串行按字符坐标聚成文本行和文本块；按块的 x 坐标做列聚类，列内自上而下、列间自左而右排出阅读顺序；跨栏的标题、图表按纵向位置插入
页眉、页脚、页码混入正文统计每页顶部 / 底部区域的文本，跨页重复（容忍数字变化）的判定为页眉页脚并剔除；页码单独识别
断行与连字符同一段内的换行合并；英文行尾连字符拼接；中文行尾不加空格
标题识别字号显著大于正文、加粗、独占一行、编号模式（复用现有中文编号正则）综合打分；字号聚类得到层级。PDF 自带书签（outline）时优先用书签确定标题与层级
扫描件（不做 OCR）某页文本层为空或字符数极少、但页面有大图 → 标记为「扫描页」，计入解析质量（§4.7），文档进入待审核，提示需要 OCR

4.4 表格

  • 抽取：默认解析器用线条与对齐检测简单表格（pdfplumber 的表格检测）；高级解析器用版面模型处理无框线、跨页、合并单元格。结果为结构化 {rows, header_rows}，合并单元格展开填充。
  • 跨页表格：相邻两页、列数相同、后一页首行不是表头 → 合并成一张表，表头沿用前一页。
  • 分段规则（§5.3）：小表整表一个分段；大表按行切，每块都带表头与表名（现有「表格行加表头」的上下文前缀沿用）。
  • 表格摘要（可选）：大表额外生成一段摘要（LLM，描述表的主题、维度、关键数字），作为一个检索入口指向整表，解决「问汇总性问题时匹配不到任何一行」。

4.5 图片

  • 抽取文档内嵌图片（PDF / DOCX / PPTX），存对象存储；就近的图注（「图 3-1 …」）作为 caption 块关联。
  • 图片描述（可选，按知识库开关）：用多模态模型生成描述（流程图写出步骤和分支，架构图写出组件和关系，截图写出界面要素），作为 image 块的文本参与分段和检索；检索命中时把原图作为引用附件返回。
  • 过滤：尺寸过小、装饰性图片（图标、分隔线）、页眉 logo（跨页重复）不处理。
  • 成本：按图片内容哈希缓存描述；单文档图片数上限；超出只保留图注。

4.6 解析结果的定位信息

每个 Block 保留 page 和 bbox（PDF / PPTX）或字符区间（文本类）；分段时汇总成分段的 source_locator（§11），供引用跳转和高亮（§8.2）。

4.7 解析质量检测

指标含义处置
空文本页比例无文本层的页（疑似扫描件）超过阈值 → 待审核，提示需要 OCR
乱码率不可打印字符、私有区字符、高频替换符的比例（字体编码问题）超过阈值 → 待审核；可尝试高级解析器
标题识别数长文档一个标题都没识别出提示：结构感知分段将退化为按段落切
表格、图片数识别到的表格与图片展示在解析预览里供人工核对
剔除的页眉页脚被剔除的文本展示，便于发现误删

指标写入文档的 parse_report（§11）；复用现有的审核状态（review_status），异常文档进入「待审核」，前端提供 DocIR 预览（按块高亮类型）。

5. 分段

5.1 分段方式

方式状态适用
普通分段（分隔符 + 长度 + 重叠）已有纯文本、无结构的内容
结构感知分段（标题栈）已有，改为直接消费 DocIR有标题结构的文档（默认）
父子分段已有需要兼顾召回精度与上下文完整性
语义分段新增长篇无标题的文本（会议纪要、聊天记录导出、报告正文）

语义分段：按句切分 → 计算相邻句（或滑动窗口）的向量相似度 → 在相似度显著下降处（低于分位数阈值）断开 → 再按长度上下限合并或拆分。作为结构感知分段在「无标题小节」内部的切分方式之一，不单独成为一种文档形态。

5.2 原子块

表格（小表）、代码块、公式、列表（短列表）作为原子块不被切开；超过长度上限的表格按行切（带表头），代码块按函数 / 空行边界切。

5.3 上下文补全

现有：子块向量的前缀 = 标题路径（表格行再加表头），正文仍是原文。扩展为三级，按知识库开关：

级别内容成本
L0（现有，默认）标题路径 + 表头无
L1（新增，默认开）L0 + 文档标题 + 文档级元数据（如产品线、生效日期）无
L2（新增，按库开关）L1 + LLM 生成的一句话分段上下文：说明这一段在全文中讲什么、指代对象是谁（Contextual Retrieval）每个分段一次 LLM 调用；文档全文作为固定前缀，利用 prompt cache 降本；按「文档哈希 + 分段哈希」缓存

上下文只参与向量化（稠密与 BM25 都用），不改变返回给模型的正文；存在 context 字段（子块已有，分段新增）。

5.4 问答对索引（qa_model）

  • 入库时由 LLM 为每个分段生成若干个「用户可能会怎么问」的问题（带答案要点）；问题作为额外的检索入口，命中后回到对应分段。
  • 复用子块路径：问题存为 kb_child_chunk，type = question；检索时「命中子块 → 回到父分段」的逻辑原样复用，不新建检索链路。
  • 人工可编辑、新增问题（FAQ 类知识库常见需求）；人工问题不会被重新生成覆盖。
  • 适用：FAQ、制度、产品说明；按知识库开关。

5.5 多粒度索引

同一个分段可以有多个检索入口，统一写为 Qdrant 的 point，payload 用 kind 区分：

kind内容命中后
chunk分段正文（或子块）回到分段
question生成或人工维护的问题回到分段
summary大表摘要、长小节摘要回到整表 / 整个小节
image图片描述回到所在分段，附带原图

同一分段被多个入口命中时，按分段去重、取最高分；漏斗记录里保留是哪种入口命中的，用于评估每种入口的贡献。

6. 向量化与索引

6.1 模型提供方

提供方场景
fastembed（现有）本地 ONNX 推理，开发与小规模
openai_compatible（新增）OpenAI 兼容的 embedding 接口：模型网关、TEI、vLLM、云厂商。生产默认
重排：tei_rerank / cohere_compatible（新增）独立部署的重排服务（如 bge-reranker-v2-m3）或云端重排 API
  • 远程提供方：批量请求、并发上限、指数退避重试、按 token 计费统计；启动时校验向量维度与知识库记录一致。
  • 推荐配置（生产）：中文 / 中英混合场景的 embedding 选多语言、长上下文的模型（如 bge-m3），重排选 bge-reranker-v2-m3 一类交叉编码器；以评测集结果为准，不写死。

6.2 换模型：索引版本与原子切换

现在每个知识库记录了模型，但换模型只能「删了重建」，期间知识库不可用。引入索引版本：

kb_index_version
  dataset_uuid, version, provider, model, dim, collection_name,
  status: building | active | retired, progress, created_at, activated_at
  1. 新建版本（status=building），创建新 collection；
  2. 后台任务用新模型为所有分段 / 子块 / 问题重新向量化，写入新 collection（分段内容不变，只重做向量；embedding 缓存按「模型 + 文本哈希」生效）；
  3. 完成后可先在评测集上对比新旧版本；确认后原子切换 active 指针；旧版本保留一段时间用于回滚，之后清理；
  4. 构建期间的新增与更新：同时写入新旧两个版本（双写），保证切换时不丢数据。

6.3 Payload 扩展

为支持过滤（§7.2–7.4），point 的 payload 增加以下字段，并建立 payload 索引：

字段用途
kind入口类型（§5.5）
meta.*文档元数据（按知识库的元数据字段定义建索引）
acl可访问主体标签数组（§7.4）
valid_from / valid_to / is_current版本与时效（§7.5）

元数据或权限变更时只更新 payload（Qdrant set_payload），不重新向量化。

7. 检索

7.1 查询理解（新增阶段 ⓪）

能力做法触发
对话改写结合最近几轮对话，把「那它的报销标准呢」改写成独立完整的问题调用方传入了对话历史，且问题含指代或过短
多查询生成 2–3 个不同表述的查询分别召回，结果用 RRF 合并按库开关；或首轮召回最高分低于阈值时自适应触发一次
HyDE先让模型写一段假设性答案，用它去做语义召回按库开关（术语差异大的场景）
问题分解复合问题（对比、多条件、多跳）拆成子问题，分别检索；结果按子问题分组返回LLM 判定为复合问题时
过滤条件抽取按知识库的元数据字段定义，从问题里抽出过滤条件（「2026 版」→ version_year = 2026）知识库定义了可抽取的元数据字段
多库路由按库的描述（及描述的向量）为问题选出最相关的 N 个库；低置信度时回退到全部库绑定的库超过阈值（如 5 个）
  • 查询理解用一次结构化输出的 LLM 调用完成（同时产出改写、是否分解、过滤条件），控制延迟；结果按「问题 + 历史」哈希缓存。
  • 每一步都写进漏斗：原问题、改写结果、子问题、抽取的过滤条件、路由选中的库及理由。
  • 降级：LLM 失败或超时，直接用原问题检索，不让检索失败。
  • LLM 抽取的过滤条件只能收窄、不能放宽，并且只作用于业务元数据；权限和版本过滤由服务端强制附加，与 LLM 无关。

7.2 元数据过滤

  • 字段定义：知识库级的元数据字段（名称、类型 string / number / date / enum、是否多值、是否允许 LLM 抽取）；内置字段：来源、作者、文档类型、更新时间、生效时间。
  • 赋值：文档级赋值（上传时、批量编辑、连接器从源系统映射）；分段继承文档元数据，必要时可以在分段上覆盖。
  • 过滤表达式：接口里支持 and / or / eq / in / range / exists，转成 Qdrant filter；多库检索时只对定义了该字段的库生效。

7.3 结果多样性

  • 每文档上限：同一文档最多返回 N 个分段，避免 top_k 被一篇文档的相邻分段占满。
  • MMR：在重排后的候选上按「相关性 − 与已选结果的相似度」挑选，可调 λ。
  • 相邻合并：同一文档里位置相邻、都被命中的分段合并成一个结果，减少碎片、保留连贯上下文。

7.4 文档级权限

  • 权限标签：文档有可访问主体列表（用户、部门、角色、用户组），或标记为「库内公开」。写入分段和 point 的 acl 字段（如 ["public"] 或 ["u:123", "d:45", "r:hr"]）。
  • 来源：手动设置；连接器从源系统读取（如 Wiki 空间 / 页面权限）；或引用用户中心的数据权限。
  • 检索时：服务端根据调用者身份展开主体集合（用户 id + 所属部门（含上级）+ 角色 + 用户组），作为 filter 强制附加：acl 与主体集合有交集，或为 public。展开结果短时缓存。
  • Agent 调用：以发起对话的终端用户身份检索，而不是以智能体或服务账号身份，避免「通过 Agent 看到自己本来看不到的文档」。
  • 权限变更：只更新 payload，不重新向量化；变更即时生效。
  • 库级权限（现有）照旧，作为第一道判定；文档级权限在库级之内进一步收窄。

7.5 版本与时效

  • 文档版本：同一份文档的新版本作为新文档入库，并通过 version_group 关联；新版本完成入库后，旧版本自动标记为「已被取代」（is_current = false）。
  • 生效区间：valid_from / valid_to（手动设置或连接器映射）；到期后自动下线。
  • 检索默认只返回当前版本且在生效区间内的分段；接口支持 as_of（按某个时间点检索）和 include_superseded（查历史版本）。
  • 引用里标注版本和生效时间，避免把作废版本当成依据。

7.6 召回合并

多查询、子问题、多入口（§5.5）都会产生多路结果：先按分段去重，再用 RRF（倒数排名融合）合并成一个候选列表进入重排。现有的混合检索合并逻辑保持不变，多查询的合并在其外层。

7.7 漏斗阶段（更新后）

query_understanding → semantic / full_text（各子查询）→ merged（RRF）→ rerank → threshold
  → diversity → assemble → reorder → final
（每个阶段的过滤条件、权限范围、命中入口类型都写进记录）

8. 生成与引用

新增问答接口，提供「检索 + 生成 + 引用」的一体化能力，供不经过 Agent 的业务系统直接使用；同时把引用所需的结构（分段 id、定位信息）加进检索结果，让 Agent 也能引用。

8.1 问答流程

问题（+ 对话历史）→ 检索（§7）→ 证据充分性判断 ──不足──▶ 拒答（§8.3）
                                      │
                                     充足
                                      ▼
                         生成（带编号的证据，要求逐句引用）
                                      ▼
                         引用校验（编号必须存在）→ 忠实度校验（§8.4，可选）
                                      ▼
                         流式返回：答案 + 引用列表 + 检索记录 id

8.2 可追溯引用

  • 证据以编号 [1] [2] 提供给模型，提示词要求每个结论后标注引用编号；生成后校验编号必须在证据范围内，非法编号去掉并记录。
  • 引用定位：每个引用返回文档名、版本、标题路径、页码、页内区域（bbox）或字符区间，以及命中的原文片段；前端跳转到原文并高亮。
  • 图片证据返回原图链接；表格证据返回结构化表格。

8.3 拒答

  • 检索侧判断：重排后的最高分低于阈值、或没有结果 → 不调用生成，直接返回「知识库中没有找到相关内容」，并附上相近的主题或建议换个问法。
  • 生成侧约束：提示词要求证据不足时明确说明，而不是凭常识补全；回答里区分「知识库中的内容」和「推断」。
  • 拒答的问题记入查询日志（零结果 / 低分查询），作为补充知识的线索（§10.4）。

8.4 忠实度校验（可选）

  • 把回答拆成陈述句，逐句检查是否能被其引用的证据支持（LLM 判定；或用 NLI 模型降本）。
  • 两种模式：标注（不被支持的句子标为「未找到依据」）、拦截（不被支持的比例超过阈值时改为拒答）。
  • 默认异步执行：结果写入问答记录，用于质量统计；对高风险知识库（制度、合规）可以开启同步拦截。

  • 数据源（kb_data_source）绑定到知识库：类型、配置、凭据引用（凭据不明文入库）、同步计划（定时 / 手动 / webhook）、游标、字段映射（源字段 → 元数据字段）。
  • 同步任务（kb_sync_run）：每次同步一条记录，含新增 / 更新 / 删除 / 跳过 / 失败数和明细；跑在 Celery，复用入库流水线。

9.2 增量更新

  1. 文档级：源端版本或 ETag 没变 → 跳过；变了 → 重新获取，比较 content_hash（已有字段），内容没变只更新元数据。
  2. 分段级：内容变了 → 重新解析和分段，按分段内容哈希与旧分段比对：
    • 没变的分段保留（id 不变，向量不重做，引用与反馈记录不丢）；
    • 新增的分段向量化写入；删除的分段从库表与向量库里删除；
    • embedding 缓存按「模型 + 文本哈希」命中，进一步减少重复计算。
  3. 记录本次重新向量化的比例，作为增量效果的指标。

9.3 删除与过期

  • 源端删除 → 同步删除（或按配置先归档，保留一段时间）；
  • valid_to 到期 → 定时任务把文档下线（enabled = false），从检索中移除；
  • 连续多次同步失败的文档标记异常，不删除已有内容，等待人工处理。

9.4 知识冲突检测（P3）

离线任务：对不同文档中向量相似度很高的分段对，用 LLM 判断是否存在矛盾（数字、日期、规则不一致）；疑似冲突进入审核队列，由知识管理员决定保留哪一份（或标记旧版本为已取代）。

10. 评测与反馈

10.1 评测集

  • 黄金测试集：按知识库维护，每题包含问题、期望命中的分段（或文档）、参考答案；题型覆盖事实、表格、跨段、多跳、过滤条件、权限、版本、无答案（应拒答）。
  • 来源：从查询日志里挑真实问题人工标注；由 LLM 基于文档生成候选题，人工审核后入集；线上反馈里的失败案例（§10.2）。
  • 公开评测集：导入 CRUD-RAG、MultiHop-RAG 等，作为通用能力的基线（复用现有评测框架的导入器机制）。

10.2 线上反馈

  • 反馈接口：针对一次检索或问答（关联检索记录 id）提交点赞 / 点踩、原因（没找到、找错了、答错了、引用不对、内容过期）、纠正内容。
  • 反馈与检索漏斗关联：点踩的记录可以直接看到每个阶段的候选，定位问题环节。
  • 失败反馈经人工确认后进入黄金测试集。

10.3 改配置自动评测

修改处理规则（分段策略）、索引版本（换模型）、检索配置（检索方式、重排、阈值、查询改写开关）时，自动在该知识库的黄金测试集上跑一轮评测，与当前配置按题配对比较（复用 Agent 评测的配对 bootstrap）：检索指标和忠实度没有显著下降才允许生效；显著下降时提示并保留原配置。

10.4 分段质量分析

分析发现的问题
从未被召回的分段切分不当、内容无用、或缺少检索入口（可考虑生成问题）
常被召回但很少被引用的分段相关性误判、内容噪声（如目录、免责声明）
零结果 / 低分查询聚类知识缺口：需要补充的主题
高频点踩的文档内容过期或错误

结果按周汇总，作为知识运营的待办清单。

与设计不同 / 未覆盖：

  • 双写没有补偿队列：重建结束时会清掉新 collection 里库中已不存在的 point，并补扫构建期间新完成的文档；双写本身失败会让该文档入库失败（可重试）。
  • 主体展开失败时降级为只用 u:用户（只看公开文档与直接授权给本人的文档），而不是只看 public。
  • 用户组（g:）标签已支持写入与过滤，但用户中心还没有用户组，展开结果里暂时没有。
  • 查询理解抽取的过滤条件可能把结果过滤成空：目前不回退，漏斗里能看到抽取了什么。
  • 文档权限只能手动设标签，还没有引用用户中心的数据权限（§7.4 的第三种来源）。
  • 前端：只有漏斗页认识新环节；DocIR 预览、增强开关、元数据字段、文档权限与版本、索引版本都只有接口，没有管理页面。
  • 多查询且未开重排时，分数阈值不生效（RRF 分数与相似度不可比）。
