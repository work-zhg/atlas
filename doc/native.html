Native Agent

native Agent 设计

用 LangChain 的 create_agent 在 Server 进程内编排，Message 是唯一事实源；执行环境是一个会话级的 Kubernetes Pod；可以把子任务委派给 subagent，包括 acp 类型的 Agent。

create_agentMessage 事实源会话级 SandboxSubagent
这份设计改变了「顾问」这个称呼的含义

早先文档里把 native 简称为「顾问」，暗示它只出谋划策、不动手。加上 sandbox 与 subagent 之后，这个称呼不再准确 —— native Agent 能写文件、跑命令、委派任务，能力不比 acp 少，只是编排权在我们手里。

后文一律用 native，不用「顾问」。Agent 管理 §02 里那组角色别名建议一并淡化。

01定位与边界

native 与 acp 的区别不在能力多少，而在编排权在谁手里：

nativeacp
编排我们写的图（create_agent）成品 CLI 内部
上下文Message 表，每轮重建CLI 进程内
工具集完全由我们装配CLI 自带 + MCP
执行环境会话级 Sandbox Pod会话级 CLI Pod
提示词我们控制CLI 的，我们只能附加
能否 regenerate能（但见 §08）不能
选 native 还是 acp

要精细控制 agent 行为，选 native：提示词、工具集、中间件、记忆注入、委派策略都在我们手里，能针对场景调优。

要立刻获得一个成熟编码 agent 的全部能力，选 acp：Claude Code 在代码理解与多步编辑上的积累，短期内自己写是追不上的。

两者不是替代关系。典型用法是 native 做业务编排，把重型编码任务委派给 acp subagent（§07）。

02执行模型

构造与执行

from langchain.agents import create_agent

agent = create_agent(
    model=model,                      # 指向 Higress
    tools=builtin + sandbox + delegate,
    system_prompt=prompt,
    middleware=[MemoryMiddleware(), SkillIndexMiddleware(), …],
    # checkpointer 省略 → 无状态图，Message 表是唯一事实源
)

# 每轮：从 Message 表重建输入
history = await messages.load(session_id)
history.append(HumanMessage(content=user_input))

async for mode, chunk in agent.astream(
    {"messages": history}, stream_mode=["messages", "updates"]):
    await events.publish(run_id, translate(mode, chunk))

不传 thread_id —— 无 checkpointer 时它没有意义。完整论证见会话管理 §05，包括「为什么不存 checkpoint」与由此带来的 interrupt() 不可用。

03Sandbox：会话级 Pod

Pod 的模板与生命周期归执行环境管理组件

创建、就绪、回收、卷分配、配额与 acp Pod 共用同一套机制，见执行环境管理设计。本节只讲 native sandbox 特有的部分：与 Server 的交互方式、目录语义、按需创建。

一个会话一个 Pod，不是一次 Run 一个

Run 级的 Pod 看起来更干净（每轮环境全新），但代价不可接受：

  • 每轮都付冷启动 —— 镜像拉取 + 挂卷，用户每说一句话都要等几秒到几十秒
  • 工作目录失去连续性 —— 上一轮创建的文件下一轮就没了，多步任务根本没法做
  • 与 acp 的模型不一致 —— 那边已经是会话级 Pod（运行时链路 §09），两套生命周期会让调度与回收逻辑翻倍

Server 与 Pod 的交互

Pod 里跑一个轻量 sandbox 守护进程，Server 通过它执行命令与读写文件 —— 而不是直接用 K8s 的 exec API。

K8s exec API自有守护进程（推荐）
流式输出可以但接口原始按需设计
超时与取消要自己包原生支持
文件操作只能靠 cat / tar 拼直接 API
并发与资源不可控可限并发、可记账
依赖需要 API Server 权限只需 Pod 网络可达

连接方式与 acp 一致：Server 主动连 Pod（云上），或 Pod 内 Bridge 外拨（本地部署形态）。接入控制沿用 运行时链路 §09 —— K8s 默认网络是平的，Pod 端点必须认证。

资源与隔离

  • 按会话隔离 —— 一个 Pod 只服务一个会话，凭证与工作区天然不跨会话
  • 网络策略 —— 默认禁止出站，需要访问外网的工具经 Higress 或显式放行；沙箱能跑任意命令，出站不设限等于给了一条旁路
  • 资源上限 —— CPU / 内存 / 磁盘都要设，且 OOMKill 要与其他退出原因分开监测（可观测性 §07）
  • idle 回收 —— 与 acp 同样的 TTL 策略，会话置 cold，下次提交时重建

04Pod 目录结构

/home/agent/                          # HOME，固定
├── workspace/                        ← OSS 卷（rw，per-session）· cwd
│   ├── inputs/                       # 用户上传的文件
│   ├── outputs/                      # 产出，可下载 / 可展示
│   └── …                             # agent 自由使用的临时区
│
├── skills/                           ← 技能只读卷（ro）· 见 §05
│   └── <skill-name>/
│       ├── scripts/                  # 模型会真的执行这些
│       ├── references/
│       └── data/
│
├── .cache/                           # emptyDir，pip / npm 缓存，不持久
└── .config/                          # ConfigMap 投射，工具配置

三类存储，三种性质

路径存储为什么
workspace/OSS（rw）产出要长期留存、要能下载、要跨 Pod 重建存活
skills/只读卷全局共享、读多写零；按 Agent 区分技能集时用独立卷，别在大卷里 subPath 挑
.cache/emptyDir纯加速，丢了无所谓；放 OSS 只会拖慢
inputs / outputs 的划分不是装饰

outputs/ 是契约位置：前端从这里取可下载的产物，present_files 之类的工具也只认这里。如果让 agent 把产出随手放在 workspace/ 根下，前端就得靠猜或者靠模型自己说路径 —— 后者不可靠。

提示词里要明确写清这个约定，并在工具描述里重复一次。目录约定只有被模型稳定遵守才有价值。

workspace 用 OSS，别把 .cache 也放上去

运行时链路 §04 论证过：对象存储的追加写是「下载整个对象 → 改 → 整体上传」。pip install 这类操作会产生成千上万个小文件，放在 OSS 挂载上会慢到不可用。

workspace/ 是低频写的产出，适合 OSS；.cache/ 是高频小文件，必须用 emptyDir。丢了缓存只是下次慢一点，把它放错地方是每次都慢。

05技能的双路下发

技能不能只进提示词 —— 它的脚本要能跑

技能管理 §07 说 native 的技能是「进程内装载」，这不完整。实测一个真实技能的 SKILL.md 里直接写着：

python "…/skills/ui-ux-pro-max/scripts/search.py" "<query>" --domain <domain>

模型会照做。所以技能的 scripts/、references/、data/ 必须在 sandbox 里存在且可访问，否则技能一用就报错。

两条路，各送各的

技能的组成送到哪为什么
frontmatter（name + description）提示词索引模型选择技能的唯一依据，常驻上下文
SKILL.md 正文提示词（命中后）指令内容，由我们构造进上下文
scripts/ references/ data/Sandbox Pod 的 skills/ 卷模型要执行它们、要读它们

路径必须对得上

提示词里的技能指令会写绝对路径。Pod 内的技能挂载点必须与提示词里声明的一致，否则模型按提示词去执行就会找不到文件。

提示词里注入：  技能根目录 = /home/agent/skills/<name>
Pod 挂载点：    /home/agent/skills/<name>/     ← 必须一致

由于技能来源不同（平台内置、租户上传）而写法可能不统一，装配时应当把技能内容里的路径占位符统一替换成实际挂载路径，而不是指望每个技能作者都写对。

技能脚本跑在 sandbox 里，是有副作用的执行

技能的脚本能做的事和任何命令一样多。技能管理 §05 要求「含脚本的技能必须人工审查」，在 native 这里的具体含义是：那段脚本会在我们的 Pod 里、用我们的网络与配额运行。

网络策略（§03）是第二道防线 —— 即使审查漏了，默认禁止出站也能挡住数据外传。

06Subagent

native Agent 可以把子任务委派给另一个 Agent。委派是父 Run 内的一次工具调用，不建独立 Session。

为什么不建独立 Session

作为工具调用（选定）作为独立 Session
用户心智父 agent 干活的一部分会话列表被子会话污染
归属产出回到父 Run 的 Message要额外设计关联与回流
可追溯事件流可折叠展示完整但过重
实现成本低高

对象归属

父 Run
├─ Message(assistant)          「我来委派一个子任务」
├─ tool_call: delegate         工具调用，subagent 执行
│   └─ Event 子流              ← 可折叠展示，带 parent_tool_call_id
│       ├─ subagent.started
│       ├─ message.delta …     子 agent 的过程
│       └─ subagent.ended
├─ Message(tool)               子任务结论，作为工具结果
└─ Message(assistant)          父 agent 基于结论继续
只有结论进 Message，过程留在 Event

子 agent 可能跑很多轮、调很多工具。把这些全塞进父会话的 Message 账本，会让父 agent 的下一轮上下文被子任务的细节淹没 —— 而它只需要知道结论。

所以：过程作为 Event 子流（可展开查看，随 Run 一起被清理），只有最终结论固化成一条 tool Message。这和 会话管理 §02 的 Message / Event 分层是同一条原则。

约束

  • 递归深度上限 —— subagent 还能再委派的话，要设硬上限（建议 2 层），否则一次提问可能引爆成几十个 Pod
  • 并发上限 —— 父 agent 一次可能想派多个子任务，要限并发，且计入会话与租户配额
  • 可委派的 Agent 白名单 —— 在父 Agent 定义里声明能派给谁，而不是让模型自由选任意 agent_id；否则提示词注入可以诱导它去调用一个权限更大的 Agent
  • 超时 —— 子任务必须有独立超时，且超时后父 agent 要能得到明确的失败结果而非一直等

07委派给 acp subagent

这是这套设计里最有价值的组合：native 做业务编排，把重型编码任务交给 acp。业务逻辑由我们精细控制，编码能力直接用成品 CLI 的。

与 native subagent 的差异

native subagentacp subagent
执行位置Server 进程内另起一个图独立的 CLI Pod
Sandbox共用父会话的 Pod自己的工作区，需显式传递文件
启动成本接近零一次 Pod 冷启动
审批无（工具由我们装配）需一路穿回用户
适用轻量子任务、并行检索多步编码、仓库级改动
审批链路变长了，必须确保能穿回用户

acp subagent 会发 session/request_permission，这条请求要经过：

CLI → adapter → Bridge → Server → 父 Run → SSE → 用户
                                    ↑ 必须正确路由到发起委派的那个会话

关键是路由：请求带的是子执行的标识，要能映射回父会话的 SSE 流。做错了的表现是审批请求消失、子任务静默超时 —— 而用户只看到「卡住了」。

对应地，父 Run 在等待子任务审批期间的状态要如实反映：这段时间属于「等人」，不是「系统慢」（可观测性 §04）。

工作区不共享，要显式传递

acp subagent 有自己的 Pod 与工作区，看不到父会话 sandbox 里的文件。所以委派时要明确传递输入、回收产出：

delegate(agent="code-assistant-claude",
         task="…任务描述…",
         inputs=["workspace/spec.md"],      # 复制进子 Pod
         outputs=["src/**"])                 # 完成后取回父 workspace

如果两边都挂同一个 OSS 前缀看起来能省掉复制，但那会让两个 Agent 并发写同一份数据 —— 宁可复制，也不要共享可写卷。

与「任务移交」的区别

系统架构 §09 说明本期不做顾问到助理的会话移交。委派不是移交：

  • 移交 —— 会话的归属从 A 换成 B，需要上下文传递与产出回流的完整设计
  • 委派 —— 会话始终属于父 Agent，子 Agent 只是被调用一次的执行单元

委派可以做，因为它的边界清晰：一次调用、一个结论、不改变会话归属。

08重跑语义与 sandbox 状态

regenerate 的前提在有 sandbox 之后不再成立

Agent 管理 §07 推导出 native 支持 regenerate，依据是「上下文由服务端持有，每轮重建输入」。这一条仍然成立 —— 但它只保证输入相同，不保证环境相同。

有了会话级 sandbox，情况变成：

第一次跑：  空目录 → agent 创建 report.md → 完成
regenerate：report.md 已存在 → agent 看到的环境与第一次不同

所以 regenerate 不是「重来一次」，而是「在已被上一次修改过的环境上再跑一次」。结果可能与第一次不同，也可能重复执行副作用（再发一次请求、再提交一次）。

三种处理，我推荐第一种

方案代价说明
接受并明确告知低 UI 上说明「重新生成不会撤销已做的改动」。用户自己判断是否可接受 —— 多数场景下重跑一次生成文档、重算一次分析都是无害的
sandbox 快照回滚高 每轮前打快照，regenerate 时回滚。实现复杂（OSS 卷的快照语义、大文件成本），且对已发出的外部请求无效
有 sandbox 就关掉 regenerate中 最安全，但把 native 最有价值的能力之一关掉了，而多数场景其实用不着回滚
诚实地说明，比悄悄降级或过度保护都好

用户点「重新生成」时的预期是「换个答案」，不是「撤销刚才做的事」。只要 UI 说清楚这一点，方案一就是对的 —— 它保留了能力，也没有骗人。

反过来，如果因为担心而默默把 regenerate 关掉，用户会疑惑为什么这个 Agent 没有重试按钮；如果不说明就允许重跑，用户会惊讶于文件被改了两次。两种沉默都比一句说明差。

编辑历史同理，且更严重

编辑历史会重放该轮之后的所有轮次，在有 sandbox 时意味着一连串操作被重新执行。建议：编辑历史只允许编辑最后一轮，或者在编辑跨越了含 sandbox 操作的轮次时给出更强的警告。

09生命周期与降级

Pod 生命周期

首个需要 sandbox 的工具调用 → 按需创建 Pod
                               （纯对话的会话不该白占一个 Pod）
会话活跃                      → Pod 保持
idle 超时                     → 销毁 Pod，会话置 cold；workspace 在 OSS 上，无损
下次需要 sandbox              → 重建 Pod，挂回同一 OSS 前缀
会话删除                      → 销毁 Pod + 按保留策略处理 workspace
按需创建，不是建会话就起 Pod

native 的很多会话可能全程用不到 sandbox（纯咨询、纯检索）。建会话就起 Pod 会把成本浪费在这些会话上。

第一次调用 sandbox 工具时再创建，代价是那一次工具调用会慢几秒 —— 可以在提示词里让模型知道「首次使用沙箱会有启动延迟」，或在 UI 上给出状态提示。

Sandbox 不可用时的降级

情况行为
Pod 创建失败sandbox 工具返回明确的错误给模型，让它知道沙箱不可用并调整策略 —— 而不是让整个 Run 失败
Pod 中途消失当前工具调用失败；下次调用触发重建；提示模型「环境已重置」
命令超时杀掉进程，返回超时错误与已产生的输出
OOMKill与普通失败区分上报（可观测性 §09），重建后可继续

共同原则：让模型知道发生了什么，而不是让 Run 直接失败。模型通常能在沙箱不可用时换一种方式回答，或者明确告诉用户做不了 —— 这两种都比一个技术错误强。

10待验证清单

#验证项影响
1 Pod 冷启动的实际耗时 —— 镜像拉取、挂卷、守护进程就绪各占多少 决定 §09 的「按需创建」是否可接受，以及要不要预热池
2 技能脚本在 sandbox 里的实际可用性 —— 依赖（Python 版本、第三方包）是否齐全 决定 §05 的技能卷是否还要带运行时依赖，或镜像要预装什么
3 acp subagent 的审批路由 —— 请求能否正确穿回父会话的 SSE 流 §07 的核心风险，做错了表现为静默超时
4 OSS 挂载在 workspace/ 上的实际写入性能 —— 中等数量文件的读写延迟 决定 §04 的存储划分是否要再细分
5 委派的实际效果 —— native 能否稳定地把任务描述清楚，使 acp subagent 产出可用结果 决定 §07 的组合是否真的比直接用 acp 更好

建议的实现顺序

  1. 先做无 sandbox 的 native —— create_agent + Message 事实源 + 只读工具，验证对象模型与事件流。这是整套抽象最小的可验证切片。
  2. 再加 sandbox —— Pod 生命周期、目录结构、按需创建；此时 §08 的重跑语义说明要同期上线。
  3. 然后是技能的双路下发 —— 需要 sandbox 先能跑。
  4. 最后做 subagent —— 先 native subagent（成本低、无审批链路），再 acp subagent。
