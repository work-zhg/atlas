1. 现状与问题

#现状（已对照代码）后果
G1 高没有认证：身份来自请求头 X-User-Id，缺省落到 default_user_id（identity.py）任何能访问接口的人都能冒充任何人
G2 高会话列表不按用户过滤；按 id 读写会话、消息、事件流、run 都不检查归属（repositories/thread.py）所有人能看、能订阅、能删除别人的会话
G3 高审批不检查谁能批审批形同虚设
G4 中智能体全局可见、谁都能改无法共享给指定人 / 部门，也挡不住误改
G5 中用户没有统一来源：app_user 只种了一个默认用户；用户中心的人员与 Atlas 没有对应归属指向不存在的用户；无法按部门授权
G6 中配置服务（技能、MCP 注册表）由浏览器直连（CONFIG_API_BASE，8020），开发模式下角色固定 admin谁都能注册 MCP、发布技能
G7 中TeamFlow 以一个固定 X-User-Id 调用 Atlas服务身份无凭据；Atlas 侧不知道是哪个人在操作；用户记忆跨团队串味（见 TeamFlow 流程上下文 §6）
G8 中run 没有发起人字段会话共享或服务代表用户操作时，分不清是谁发起的这一轮

2. 目标与非目标

目标非目标
  1. 用户来自用户中心：用用户中心的账号登录；人员、部门、角色只在用户中心维护。
  2. Atlas 作为接入应用登记到用户中心：操作码、菜单、角色、数据编码按用户中心的模型表达。
  3. 会话及其下一切数据按所有者隔离（G2、G3）。
  4. 智能体、MCP 服务可以按人 / 部门授权使用与维护（G4）。
  5. 服务调用有凭据，并能声明「代表哪位用户」（G7）。
  6. 浏览器经同源网关访问 atlas-server 与 atlas-config；配置服务按操作码鉴权（G6）。
  7. 本机开发体验不变（dev 模式）。
  • Atlas 自建账号、密码、组织、角色维护：都在用户中心。
  • 自建 OIDC / 令牌签发：不做；以后 SSO 接 Keycloak，只替换登录这一步。
  • 多租户：一套部署一个组织；租户维度以后再加。
  • 会话多人共享：第 3 期；本期预留 run.created_by。
  • 计费：只记录归属，不定价。

3. 总体架构

组件职责不做什么
用户中心权威：人员、部门、账号状态、密码校验；Atlas 的角色 / 操作码 / 菜单授权；智能体与 MCP 服务的数据权限（谁对哪个对象有读 / 写 / 所有者）不知道会话、run 这些运行时数据
atlas-server · auth识别主体：用户会话（Cookie）、服务账号（API Key）、dev 请求头；维护用户投影；缓存授权快照不存密码、不签发通用令牌
atlas-server · authz三类判定：操作码（这类事能不能做，来自快照）、数据权限（这个智能体 / MCP 服务能不能用、能不能改，问用户中心）、归属（这个会话是不是你的，本地判定）—
atlas-server · 内部接口为 atlas-config 校验浏览器会话（/internal/v1/auth/introspect，内部令牌）不对浏览器开放（网关屏蔽 /internal/*）
atlas-config技能、MCP 注册表、配置审计；浏览器经网关直连；按操作码鉴权不维护登录、不接用户中心
与 旧方案 的区别：旧方案由「配置平面 Java iam + BFF」登录并签发 RS256 令牌，运行时只验签。现在配置平面是 Python、用户中心已经存在且约定「接入走开放接口、不自建 OIDC」，所以改为 atlas-server 直接用用户中心开放接口登录并维护会话，模式与 AI TeamFlow 相同（同一套经验、同一类代码）。

4. 身份：三类主体

主体凭据Principal适用
用户会话 Cookie atlas_session（HttpOnly）+ 写请求 CSRF 双提交kind=user、user_id（= 用户中心用户 id）、姓名、部门、操作码集合Atlas 前端
服务账号Authorization: Bearer atlas_sk_…（只存哈希）kind=service、service_id、服务账号的操作码；可带「代表用户」acting_userTeamFlow 等后端服务（§10）
devX-User-Id 请求头，缺省默认用户；角色固定 adminkind=user本机开发、单测。auth_mode=dev 且监听非本机地址时拒绝启动（旧方案是警告，这里收紧）

4.1 用户登录（与 TeamFlow 相同的做法）

浏览器 POST /atlas/api/v1/auth/login {account, password}
  → atlas-server 调用户中心 POST /open/v1/auth/verify-password（应用令牌）
  → 用户中心返回用户；再取 GET /open/v1/users/{id}/authz（授权快照：can_access、角色、操作码、菜单）
  → can_access = false（不在 Atlas 的可访问范围）→ 403「没有使用 Atlas 的权限」
  → upsert app_user（id = 用户中心用户 id）→ 建 auth_session → Set-Cookie atlas_session + atlas_csrf
后续请求：Cookie → auth_session（未过期）→ 快照（进程内缓存 ≤ 5 分钟，过期向用户中心刷新）→ Principal
  • 会话有效期 12 小时（滑动续期）；登出删除会话行。
  • 快照刷新时发现账号停用或失去应用访问权 → 删除该用户全部会话，本次请求 401。
  • 以后接 SSO（Keycloak）：只把「校验密码」换成 OIDC 登录回调，其余（会话、快照、投影）不变。

4.2 后台执行

run 在后台任务里执行，没有请求；身份取会话所有者（现状如此，保持）。所有者被停用后，执行器不再为他启动新的 run。

5. 用户与用户中心打通

项设计
主键app_user.id 直接用用户中心的用户 id（UUID）。业务表的 created_by、对象存储路径 {user}/{thread}/…、Pod 配额标签、记忆的 user_id 都是它，与用户中心无需再映射。external_id 同值保留（兼容旧代码）
投影字段账号、姓名、邮箱、部门 id 与名称、状态（active / disabled）、最近访问时间、资料同步时间
登记时机首次登录自动登记（JIT）；被授权共享智能体但还没登录过的人，在授权时按用户中心资料登记（只读展示用）
同步登录与快照刷新时更新资料（以用户中心为准）；停用 → 投影标 disabled、清会话。用户中心的变更通知（Webhook，用户中心 P1）上线后改为即时
删除 / 离职投影不删，只标 disabled：历史会话、审批要能显示是谁；数据移交另立流程
部门不在 Atlas 存部门树；授权时从用户中心通讯录（/open/v1/depts/tree、/open/v1/users）选人选部门
角色不存库：来自用户中心授权快照（存一份就会出现「用户中心已收回、Atlas 还写着有」）

7. 数据权限

7.1 哪些资源走用户中心的数据权限

资源走用户中心？理由
智能体是 数据编码 AtlasAgent，一个智能体一条要按人 / 部门共享；数量适中；授权需要在用户中心统一审计
MCP 服务（平台凭据）是 数据编码 AtlasMcpServer平台凭据下「谁能用」是唯一防线（权限管理 §05）；用户凭据（OAuth）的服务不需要，OAuth 本身就是边界
技能否不做独立授权，随智能体走（权限管理 §06）
会话、run、消息、事件、审批、文件、子会话、Pod否，本地归属个人数据、数量大、创建频繁；放进用户中心既慢又没必要。按根会话所有者判定（§7.4）
记忆否只属于本人（现状已按 user_id 隔离；身份可信后才真正成立）
模型目录、服务账号否平台配置，用操作码控制

7.2 智能体：级别语义

级别能做什么
READ 使用在列表里看到已启用的智能体；用它新建会话；被别的智能体当作子智能体调用不需要使用者另有授权（委派按父智能体定义走）
WRITE 编辑使用 + 查看草稿、编辑并保存新版本
OWNER 所有者编辑 + 启用 / 归档 + 调整授权（加人、加部门、改级别）；至少保留一个所有者
数据管理员（agent:manage_all）看全部、改全部、调整任意授权；内置智能体只有它能改
  • 创建即授权：新建智能体时，Atlas 调用户中心写入「创建者 = OWNER」。
  • 全员可用：授「根部门 · 含下级 · READ」即可，不另设「公开」标记（一个概念只有一处事实）。内置「通用助手」迁移时默认这样授。
  • 状态叠加：草稿只对 WRITE 及以上可见；归档只对 OWNER 与数据管理员可见；已启用对 READ 可见。
  • 列表：调用户中心 /open/v1/data-permissions/accessible?data_code=AtlasAgent&user_id=…&min=READ，按用户缓存 60 秒，再与状态叠加过滤。
  • 何时校验：建会话时校验一次 READ；会话建立后不再复查（会话已钉住版本；中途收回不让用户聊到一半报错，与 权限管理 §03 一致）。要立即断开走显式终止。
  • 改名同步：智能体改名时同步数据对象名称（PATCH /open/v1/data-objects），用户中心里的授权列表显示正确名称。

7.3 MCP 服务

  • 有效服务 = 智能体配置的服务 ∩ 本人对服务有 READ（平台凭据）—— 访问权的交集模型沿用 权限管理 §04。
  • 每轮运行开始时复查（MCP 权限要及时收回，与智能体不同）；被收回的工具对模型隐藏，并在界面标出「部分工具因权限未启用」。
  • OWNER 维护服务配置与工具审核；mcp:manage_all 是数据管理员。

7.4 会话类数据：归属链（沿用旧方案 7.3）

所有者 = 根会话.created_by
  根会话 ─ run · message · run_event · approval · run_file · 子会话（委派）· 会话 Pod · 工作区文件
判定：资源 id → 所在会话 → 根会话所有者，与 Principal 比较（一条 JOIN 查询）
  · 用户主体：所有者 = 本人
  · 服务账号：所有者 = 该服务账号（TeamFlow 的节点会话归 TeamFlow，权限在 TeamFlow 判定）
管理员默认也不能读别人的会话（对话是个人数据）；排障走单独的审计入口（第 3 期）

7.5 拒绝时返回什么

情形返回理由
资源不属于你 / 对智能体没有 READ404不泄露对象是否存在
能看到但级别不够（如 READ 去编辑）403对象已经可见，没有泄露问题
操作码不够（如成员去建智能体）403不涉及具体资源

9. 配置服务的访问

浏览器直接访问 atlas-config（经网关同源路径 /atlas-config-api），不经 atlas-server 转发。atlas-config 不维护登录：

环节做法
识别用户uc 模式取浏览器带来的 atlas_session Cookie（atlas-server 登录时设置，Path=/，同源下两个服务都收得到），调 atlas-server POST /internal/v1/auth/introspect（带内部令牌）拿回用户 id 与操作码；成功结果缓存 30 秒（权限收回最多滞后 30 秒）
写请求CSRF 双提交（X-Atlas-CSRF = atlas_csrf Cookie），与 atlas-server 相同
鉴权按操作码（替换原 admin ⊃ builder 三级）：看技能目录 = 构建类操作码之一；上传技能 skill:upload；审核 / 发布 / 下线 skill:review；看 MCP 注册表 = mcp:manage 或智能体相关操作码；注册 / 工具审核 mcp:manage；审计 audit:view
dev 模式不变：读 X-User-Id，操作码全有
运行时 → 已发布内容/internal/* 共享令牌，不变

MCP 服务的数据权限（§7.3，P2）由 atlas-server 在运行时判定；atlas-config 不调用用户中心（保持配置服务无外部依赖）。

10. 服务账号与 TeamFlow 接入

10.1 服务账号

项设计
是什么Atlas 自己的主体（不是用户中心的人员）：名称、密钥（atlas_sk_ 前缀，只显示一次，只存哈希）、操作码（默认 chat:use）、可用智能体范围、是否允许「代表用户」、默认关闭记忆、状态
谁管理管理员（service_account:manage）在「系统设置 · 服务账号」创建、停用、轮换密钥
可用智能体范围all_enabled（所有已启用的智能体）或指定列表。服务账号不是用户中心的人员，无法被授予数据权限，所以范围在 Atlas 配置
代表用户（X-Atlas-Acting-User）可选，值为用户中心用户 id。只在服务账号允许时生效：① 列智能体时返回「服务范围 ∩ 该用户可用」，便于业务系统只让用户挑他自己能用的；② 记入 run.created_by 与审计。不改变会话归属，不用于读该用户的会话或记忆
会话归属服务账号建的会话归服务账号；谁能看、谁能操作由业务系统（如 TeamFlow）判定
记忆服务账号建的会话默认 memory: "off"（不抽取、不注入、不挂检索工具）—— 避免同一服务身份下不同团队的记忆串味
git 凭据档案atlas-cluster 的 allowed_users 改为允许的服务账号 id（原来是那个固定 UUID）

10.2 TeamFlow 的改动

现在改为
X-User-Id: 3a08906c-…Authorization: Bearer <服务账号密钥>（放 .env 的 ATLAS_TF_ATLAS_API_KEY）
不知道是谁操作人机协同代理转发时带 X-Atlas-Acting-User = 当前 TeamFlow 用户（同一个用户中心 id）；监督器的系统投递不带
团队接入 Agent 时列出全部已启用智能体带上团队管理员作为代表用户：只列出他自己在 Atlas 能用的智能体
节点会话开着用户记忆服务账号默认关闭（不需要 TeamFlow 再传参数）

11. 数据模型变更（atlas-server）

表变更
app_userid = 用户中心用户 id；新增 account、email、dept_id、dept_name、status（active / disabled）、last_seen_at（最多 10 分钟写一次）、updated_at
auth_session（新）token_hash、user_id、expires_at、created_at、last_used_at、user_agent；Cookie 里只放随机令牌，库里存哈希
service_account（新）id、name、key_prefix、key_hash、operations、agent_scope（all_enabled / list）、agent_ids、allow_acting、memory_default、status、created_by、last_used_at
thread新增 owner_kind（user / service）、memory（on / off）；索引 (created_by, updated_at DESC, id DESC) WHERE parent_thread_id IS NULL（会话列表）
run新增 created_by（发起人：用户本人，或服务账号代表的用户，系统投递为空）；存量回填为会话所有者
智能体 / MCP 的授权不建本地表：在用户中心；Atlas 只缓存（按用户 60 秒）

POST /v1/auth/login · POST /v1/auth/logout用户中心账号登录 / 登出
GET /v1/me当前主体：用户资料、操作码、菜单、用量摘要
GET /v1/agents/{id}/grants · PUT …/grants智能体授权的查看与调整（OWNER / 数据管理员），转为用户中心数据权限读写
GET /v1/directory/users?q= · GET /v1/directory/depts授权时选人选部门（转发用户中心通讯录）
/v1/service-accounts（CRUD、轮换密钥）管理员
POST /internal/v1/auth/introspect服务间：atlas-config 校验浏览器会话（内部令牌；网关不对外）

12.2 行为变化

接口变化
GET /v1/threads只返回本主体的根会话
会话、消息、事件流、run、取消、审批、文件、预览不属于本主体 → 404
POST /v1/threads校验智能体 READ（或服务账号范围）；服务账号建的会话 memory=off
GET /v1/agents只返回可用的（叠加状态）；带 X-Atlas-Acting-User 时取交集
POST /v1/agents、PATCH、/status操作码 + 数据权限级别（§7.2）
全部接口auth_mode=uc 下 X-User-Id 被忽略并从 OpenAPI 移除

13. 前端

  • 登录页（用户中心账号）；未登录跳登录；后端不可达显示与 TeamFlow 相同的 BackendDown 状态。
  • 菜单按授权快照渲染；按钮显隐只是体验，权限在服务端。
  • 智能体详情「共享」：选人 / 选部门（含下级）+ 级别（使用 / 编辑 / 所有者），即用户中心数据权限。
  • 系统设置：模型目录、服务账号（创建时只显示一次密钥）、审计。
  • 部署时去掉构建期写死的 NEXT_PUBLIC_USER_ID；运行时与配置服务都走同源路径（/atlas-api、/atlas-config-api），带 Cookie 与 CSRF 头。

14. 网关与部署

项设计
同源前端 Pod 的 nginx：/atlas-api/ → atlas-server（SSE 关闭缓冲）、/atlas-config-api/ → atlas-config；/atlas-api/internal/ 返回 404
Cookieatlas_session：HttpOnly、SameSite=Lax、Path=/（两个服务都要收到）、生产环境 Secure
用户中心凭据Atlas 应用的 App Key / Secret 放 .env，部署时建成 K8s Secret（与 TeamFlow 相同）
atlas-server 配置AUTH_MODE=dev|uc、UC_BASE_URL、UC_APP_KEY / UC_APP_SECRET（Secret）、SESSION_HOURS、AUTHZ_SNAPSHOT_TTL_S、AUTH_COOKIE_SECURE；uc 模式缺 App Key 拒绝启动
atlas-config 配置ATLAS_CONFIG_AUTH_MODE=dev|uc、ATLAS_CONFIG_SERVER_URL、ATLAS_CONFIG_INTERNAL_TOKEN（与 atlas-server 的 CONFIG_INTERNAL_TOKEN 同值）、ATLAS_CONFIG_INTROSPECT_TTL_S
登记python -m atlas_server register-uc --account admin：操作码、菜单、角色、数据编码幂等同步；首次输出 App Key / Secret

15. 上线与存量数据

步骤内容
1在用户中心登记 Atlas 应用（操作码、菜单、角色、数据编码 AtlasAgent / AtlasMcpServer），给人员授角色
2存量归属：默认用户名下的会话、智能体、记忆，迁移到指定的用户中心账号（管理员执行一次性脚本，按 id 改写 created_by 与对象存储前缀）
3存量智能体写入数据权限：创建者 = OWNER；内置智能体 = 根部门含下级 READ；其余已启用的按评审决定（默认全员 READ，保持现有可见性不突变）
4创建 TeamFlow 服务账号；TeamFlow 已有会话的 created_by（固定 UUID）改写为该服务账号 id，cluster 的 allowed_users 同步更新
5切换 AUTH_MODE=uc 与 ATLAS_CONFIG_AUTH_MODE=uc，前端走同源网关

16. 安全清单

  • uc 模式下不接受 X-User-Id；dev 模式只能监听本机地址，否则拒绝启动。
  • 会话令牌、服务账号密钥只存哈希；密钥只显示一次；支持轮换与停用。
  • 写请求 CSRF 双提交；Cookie HttpOnly + SameSite。
  • X-Atlas-Acting-User 只在服务账号允许时生效，且只影响列表交集与审计，不扩大任何访问。
  • 不属于你的资源一律 404；授权变更（智能体共享、服务账号）记审计。
  • 记忆检索的 user_id 由服务端从会话所有者取，不来自参数；服务账号会话关闭记忆。
  • atlas-config 在 uc 模式只认 atlas-server 校验过的会话；会话校验接口只接受内部令牌，网关屏蔽 /internal/*。
