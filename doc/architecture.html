Architecture

系统架构设计

一套服务端抽象同时承载两类 Agent：进程内的顾问（出谋划策）与运行在 Kubernetes Pod 中的助理（实际干活）。前端只面对一套对象模型和一套事件流。

ClientServerHigressMem0K8s PodOSSOTel · Langfuse

01设计目标与边界

平台要在同一套会话抽象下跑两种性质完全不同的 Agent。它们的差异不在模型，而在上下文由谁持有：

顾问 · native

内置 Agent，进程内执行

  • 出谋划策：分析、方案、评审、答疑
  • 工具集限只读，不写文件、不执行命令
  • 产出即 Message 本身
  • 重跑安全 → 可 regenerate / 可编辑历史

助理 · acp

外部 CLI，Pod 内经 ACP 驱动

  • 实际干活：写代码、改文件、跑命令
  • 每个危险动作需人工审批（ACP request_permission）
  • 产出是 OSS 上的文件 + Message 摘要
  • 重跑危险 → 不可 regenerate
这条分界线决定了整份设计

后文几乎每一处不对称 —— 能力矩阵、审批回路、状态机、持久化策略 —— 都能回溯到「上下文由谁持有」这一条。它不是策略选择，是机制事实。把它当成实现细节去抹平，会得到一个两边都不好用的抽象。

不在本文范围

  • Session / Run / Message / Event 的对象模型与接口契约 —— 见会话管理设计
  • Server → Bridge → CLI 的链路实现、K8s 与存储细节 —— 见运行时链路设计
  • 顾问与助理之间的任务移交 —— 本期明确不做，见 §09
  • 模型选型、提示词工程、技能内容本身

03组件职责

组件形态职责
ClientWeb / App唯一的用户界面。只消费一套对象模型与一套事件流，通过 capabilities 感知能力边界，不感知 Agent 实现差异。
Agent 管理Server 模块Agent 定义与版本、capabilities 的唯一所有者、工具与 MCP 装配、发布校验。见Agent 管理设计。
会话管理Server 模块Session / Run 状态机、Message 账本、Event 流、审批回路、幂等准入与并发控制。核心，见会话管理设计。
MCP 管理Server 模块MCP Server 注册与启停、工具发现与缓存、按 Agent 下发工具子集。调用本身经 Higress。
记忆管理Server 模块记忆的抽取、写入与召回策略；Mem0 的调用方与上下文注入点。
技能管理Server 模块技能包的安装、校验、按 Agent 启用。顾问与助理的技能集可以不同。
执行环境管理Server 模块Pod 模板与生命周期。为 acp Pod、native sandbox Pod、本地设备提供统一的执行环境抽象：模板渲染、创建与回收、卷编排、配额与连接注册。见执行环境管理设计。
可观测性Server 模块按 OTel GenAI 语义约定产生 span 与指标，经 OTLP 导出。见 §07。
Higress网关双职责：LLM 网关 + MCP 网关。所有出站调用的收口点。见 §06。
Mem0外部服务长期记忆存储与检索。
BridgePod 内进程ACP client + WebSocket 端点。把 ACP 的 session/update 翻译成平台 Event，把平台指令翻译成 ACP 请求。
CLI 进程Pod 内进程Claude Code / Codex 等 ACP-compatible CLI。真正干活的那个。
OSS对象存储会话工作区。Pod 挂载，销毁重建后文件仍在。

04两类 Agent 的部署形态

顾问 · native助理 · acp
执行位置Server 进程内独立 Kubernetes Pod
构造方式create_agent(...) 编译出的图调度 Pod，Bridge 起 CLI 子进程
与 Server 的连接函数调用WebSocket
启动成本接近零镜像拉取 + CLI 初始化 + OSS 挂载
状态归属无常驻状态，Message 表即全部上下文在 CLI 进程内，Server 只有句柄
工作区无OSS 挂载卷

空闲回收不适用idle TTL 销毁 Pod，会话置 cold
Pod-per-session 的代价

换来了凭证隔离与调度简化，代价是冷启动延迟与常驻成本。会话数量大且多数空闲时，缩容 TTL 与预热池的取舍需要实测数据来定，不要凭感觉设。这也是为什么低成本、高频次的咨询类交互应当走顾问而不是助理 —— 不只是能力问题，也是成本问题。

05协议选型

连接协议理由
Client ↔ ServerSSE + REST 事件下行用 SSE，指令上行用 REST。审批与追问是分钟级低频交互，不值得为它引入 WebSocket 的连接管理、心跳与代理层兼容负担。用 POST + fetch 流式读取而非 EventSource（后者不能带 header 与 body）。
Server ↔ PodWebSocket 高频双向：Bridge 持续上报 session/update，Server 下发 prompt、审批结果与取消。两端都是自有服务，无代理层兼容负担。
Bridge ↔ CLIACP over stdio 由 CLI 侧决定，不是我们的选择。Bridge 作为 ACP client 实现反向请求（request_permission、fs/*）。
Server → HigressHTTP LLM 与 MCP 调用统一收口。
Server → CollectorOTLP 旁路遥测，不在主调用链上。
SSE 的缓冲陷阱

Client ↔ Server 这一跳的 SSE 必须在反向代理处关闭 buffering 与压缩，否则流式输出会成段卡顿 —— 表现为「转半天圈然后一整段蹦出来」，很容易被误判为模型慢。Server ↔ Pod 走 WebSocket，不受此影响。

06出站收口：Higress

Higress 同时是 LLM 网关与 MCP 网关。所有出站流量 —— 顾问的模型调用、助理的模型调用（如果 CLI 也配置走网关）、以及全部 MCP 工具调用 —— 都经过它。

收口买到了什么

  • 鉴权与密钥托管 —— 模型密钥不散落在 Server 与各 Pod 的环境变量里
  • 限流与配额 —— 按租户、按 Agent、按会话的用量控制只实现一次
  • 成本核算 —— token 计量在网关侧统一采集，不依赖各调用方自觉上报
  • 故障转移 —— 模型降级与多供应商切换对上层透明
  • 出站审计 —— 合规场景下「什么数据发给了哪个外部模型」有单一审计点
代价：它是出站单点

网关故障会同时掐断推理与工具两条链路。因此它的可用性等级必须按两条链路中要求最高的那条来定，不能因为它叫「网关」就按基础设施的默认等级对待。多副本、健康检查、以及「网关不可用时是否允许直连降级」都要在上线前有明确答案 —— 而后者一旦允许，上面列的五项收益会在降级期间同时失效，这个取舍要写进预案而不是临场决定。

07可观测性

采集标准用 OpenTelemetry GenAI 语义约定，后端用 Langfuse。

为什么是语义约定而不是自定义字段

遥测在四个地方产生：Server（会话与 Run 的编排）、Higress（模型与工具调用的实际出站）、Bridge（ACP 翻译与生命周期）、以及 Claude Code 自身。只有共用同一套语义约定，这四处的 span 才能拼成一条完整调用链。

CLI 内部不是黑盒

实测确认 Claude Code 原生支持标准 OTel 导出（CLAUDE_CODE_ENABLE_TELEMETRY 配合完整的 OTEL_EXPORTER_OTLP_* 环境变量），可以配置成上报到我们自己的 Collector —— 工具执行耗时、审批等待时长、上下文压缩事件、token 与成本都能拿到。

所以「它为什么改了这个文件」这类问题在助理侧是可追查的，而不是只剩「进去了」和「出来了」。接入方式、具体能拿到哪些指标、以及关联维度上的错配，见可观测性设计 §05。

关联维度

四层 span 用同一组 ID 串联，它们正好是会话管理里已有的对象主键，不用另造：

session_id   贯穿整个会话
run_id       贯穿一轮对话
message_seq  定位到具体一条消息

Bridge 在把 ACP session/update 翻译成平台 Event 的同时，应按同一语义约定产生 span 并携带这组 ID。架构图中未画出 Pod → Collector 的线（避免与 K8s 块交叉），但它是必需的。

完整的采集架构、trace 结构、指标清单、隐私分档与告警策略，见可观测性设计。

08存储与持久化

数据存储说明
Message数据库会话内容账本，展示的唯一真相，永久保留
Session / Run / Agent数据库状态机与元数据
Event数据库过程流，只保留最后一个 Run，可 TTL 清理
会话工作区文件OSS助理的产出。Pod 挂载，销毁重建后仍在
长期记忆Mem0跨会话的用户与领域记忆
Checkpoint不存顾问不落 checkpoint，见下
顾问不存 checkpoint

Message 已经是完整的会话内容，checkpoint 会成为冗余的第二份真相 —— 而两份真相就需要对齐规则，对不上时是静默降级而非报错。顾问的上下文本就每轮重建，因此不需要「精确恢复到中断点」这项 checkpoint 的核心价值。create_agent 不传 checkpointer 即为无状态，每轮传入完整 Message 列表，与这个模型天然契合。

实质损失只有一项：一轮跑到一半中断后无法续跑，只能整轮重来。连带后果是顾问的追问不能在 Run 内挂起 —— 详见会话管理 §05。

OSS 上的文件不等于上下文

Pod 销毁重建后 OSS 上的产出文件仍在，但会话上下文不在 OSS 上 —— 它在 CLI 进程内存里，随 Pod 一起消失。能否恢复只取决于 CLI 是否实现 ACP 的 loadSession。把「文件还在」误当成「上下文还在」，会导致产品上给用户错误的预期。

09架构决策与代价

决策买到了代价
顾问 / 助理角色分离能力、审批、成本三条线都有清晰依据两类 Agent 的 UI 语义不完全一致，需 capability 驱动
顾问不存 checkpoint单一真相源，无双源对齐问题Run 中断后整轮重来
Pod-per-session凭证隔离、无需 sticky 路由冷启动延迟与常驻成本
Higress 双职责收口鉴权限流成本审计只实现一次出站单点，可用性要求被拉高
Client 用 SSE 而非 WS代理友好、实现简单反向代理必须正确配置缓冲
OTel 语义约定三层链路可拼接Bridge 必须配合上报，否则链路断在最关键处

已排除的范围

不做任务移交

一个 Session 只绑定一个 Agent，本期不实现顾问到助理的移交。跨角色协作由用户手工完成 —— 从顾问会话复制方案，到助理会话发起新任务。

这保持了 Session 与 Agent 的严格一对一，两边的能力矩阵因此各自成立，不需要引入 parent_session_id、上下文传递格式、产出回流这一整套概念。移交机制需要先有真实用例才能定得对，过早设计只会得到一个没人用的抽象。
