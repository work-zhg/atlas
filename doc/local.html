Local Deployment

本地部署设计

助理也可以跑在用户自己的电脑上。协议链路与云上 Pod 完全一致 —— 同样是 Bridge 经 ACP 驱动 CLI，只是换了个执行位置。差异集中在连接方向、工作区归属、凭证与信任边界。

驱动模式连接反转租约授权
本期范围：只做驱动模式

平台发起 Run，在用户机器上执行。用户自己在终端里起的会话，平台不观察、不同步、不展示。

曾评估过「镜像」方案（监听 CLI 的 transcript 文件，把用户在终端的对话同步到网页端），已排除 —— 理由见 §01。

01定位与范围

本地部署解决的是「助理需要访问用户本机环境」的场景：真实的代码仓库、本地服务、内网资源、用户自己的开发工具链。这些东西搬不进云上 Pod，所以让助理去它们那里。

协议链路与云上完全相同（运行时链路 §02）：Bridge 作为 ACP client 拉起 adapter，adapter 驱动 Claude Code。本文只写不同的那部分。

为什么排除了镜像方案

镜像的设想是：监听 ~/.claude/projects/**/*.jsonl，把用户在自己终端里的对话同步到网页端。实测后排除，三条理由按分量排序：

  1. 拿不到 token 级流式，且最差情况很难看。实测一次 400 词回复：文件在 4.41s 建立，随后约 15 秒零增长，19.85s 时整段 5571 字节一次落盘。transcript 按 content block 完成时写入，生成期间完全不动 —— 网页端会静默十几秒然后整段蹦出来。
  2. 与驱动模式并存会分叉对话。两个 claude 进程持有同一会话时，各自有独立的内存上下文、互不可见，却追加进同一个文件。此时 transcript 记录的是两段发散的对话，继续同步只会污染 Message 账本。
  3. 依赖未文档化的内部格式。transcript 的结构、字段与写入时机都是 Claude Code 的内部实现，随版本变化，而它会成为 Message 的来源 —— 核心数据路径不该建在这种地基上。
排除镜像带来的连带简化

不再需要解析 transcript，于是 Message 的来源回到 ACP session/update —— 一个有明确语义的文档化协议，云上和本地走同一条路径，会话管理 §11 的固化清单原样适用。

同时去掉了 messages.origin / source_uuid 两个字段、transcript 解析器、版本探测、以及一整套宽容解析要求。少了一个会随上游版本漂移的依赖。

如果确实需要「本地终端的对话在网页端可见」

claude --remote-control [name] 与 settings.json 的 remoteControlAtStartup 是 Anthropic 的第一方功能，用途正是把本地会话投到别处查看与控制。它走 Anthropic 自己的通道，我们用不上，但值得先确认它是否已经满足需求 —— 若是，这块就不必自建。

02拓扑：连接反转

连接管理

  • 设备注册 —— Bridge 首次连接时注册为一台设备，绑定到用户。同一用户可有多台，发起会话时需要选择目标设备。
  • 连接注册表 —— Server 侧把 session_id → 设备连接 与云上的 session_id → Pod 收敛成同一个抽象。不要按 Pod 名硬编码查找，否则本地场景要另写一套。
  • 心跳与重连 —— 断线期间会话置 cold，设备回来后按 §03 的能力位恢复。
  • 离线提交 —— 用户在网页端对一台离线设备发起 Run，应当立即拒绝并说明设备离线，而不是排队等待。排队会让用户以为任务在跑。

03设备配对与信任

Bridge 与 Server 建立的是一条能在用户电脑上执行任意命令的通道。它的接入控制不是锦上添花，是这条链路的前提。

威胁模型：两个方向都要防

方向攻击后果
冒充设备
连上 Server		 攻击者注册一个假 Bridge，声称是用户 X 的设备 收到本该发往该用户机器的 prompt；回传伪造的执行结果与消息
冒充 Server
驱动 Bridge		 攻击者让用户的 Bridge 连到自己控制的服务端 在用户电脑上任意执行命令、读写授权目录内的全部文件
第二个方向危害更大，却最容易被忽略

通常只想着「别让坏人连上我的服务」，但这条链路里被冒充的服务端等于拿到一台机器的 shell。Bridge 必须验证 Server 的身份，而不只是 Server 验证 Bridge。

配对流程

1. 用户在网页端（已认证会话）点击「添加设备」
2. Server 生成配对码：短时效 · 一次性 · 绑定到该用户
     只在这个已认证会话里展示，不经任何其他渠道下发

3. 用户在自己机器上执行：
     bridge pair <code> --server https://<固定域名>

4. Bridge 向用户确认：
     「即将把本机绑定到 账号 alice@corp（组织 ACME）
       服务端 https://platform.corp
       绑定后该服务端可在本机执行命令。确认？」

5. TLS 校验通过后，用配对码换取长期设备凭证
6. Server 记录 device → user 绑定；配对码立即作废
7. 后续连接一律使用设备凭证

配对码的性质

  • 短时效 —— 分钟级过期，不是小时级。它是一次握手的引子，不是长期凭证。
  • 一次性 —— 兑换后立即作废，无论成功与否。
  • 绑定到生成它的用户 —— 不是通用邀请码。
  • 只在已认证会话里展示 —— 不发邮件、不发 IM、不进日志。
  • 高熵，或低熵配严格限流 —— 若为方便手输而用短码，必须配合按用户与按 IP 的尝试次数限制，否则可被枚举。
配对码钓鱼是最现实的攻击

攻击者不需要破解任何东西，只需要让用户运行一条命令：「你的环境有问题，执行这个修复一下」 —— 里面是攻击者自己的配对码和服务端地址。用户照做，攻击者就获得了这台机器的命令执行权。

技术手段拦不住用户主动运行命令，唯一的防线是第 4 步的确认提示：必须明确显示绑定到哪个账号、哪个组织、哪个服务端域名，并说明授予了什么权限。一个只说「确认配对？(y/N)」的提示等于没有。

配套的产品规则：配对码只能来自用户自己的已认证会话，任何「别人给你一个码」的场景都应当在文档与提示里明确标记为不正常。

双向验证

谁验证谁手段
Bridge 验证 Server TLS 证书校验 + 服务端域名固定在配置里；拒绝 ws:// 明文连接；自托管场景下固定 CA 或证书指纹
Server 验证 Bridge 设备凭证放在 WS 握手的 header 里校验 —— 不是连上之后再认证。未通过直接拒绝握手，不进入任何业务逻辑

设备凭证

  • per-device —— 一台一份，不共享。
  • 存在 OS keychain —— 退而求其次才是受限权限的文件，不要明文放在用户目录。
  • 可轮换 —— 定期换发，旧凭证留重叠宽限期。
  • 撤销即时生效 —— 用户点「移除设备」后，正在保持的连接要立刻断开，而不只是阻止下次连接。长连接场景下这两者差别很大。

会话必须绑定到设备

§04 说过来自本地设备的数据都是不可信输入。配对让这条要求可以落地：

收到设备 D 发来的关于 session S 的消息
  → 校验 S 的 owner == D 绑定的用户      # 不是就丢弃
  → 校验 S 当前的执行设备 == D            # 不是就丢弃
  → 才进入业务处理

不要因为消息里带了 session_id 就相信它属于这个设备。一台被攻破的设备不应能读写同一用户在另一台设备上的会话，更不用说别人的会话。

凭证被复制怎么办

设备凭证毕竟是一串可以被拷走的数据。无法根除，但要可发现、可处置：

  • 展示活跃设备 —— 名称、最近连接时间、IP 与大致位置，用户自己能看出异常。
  • 并发异常告警 —— 同一设备凭证从不同 IP 同时连接，是明确的可疑信号。
  • 一键撤销 —— 发现异常时用户能立即断掉，不需要联系管理员。

Bridge 的本地监听面

本机的其他进程也是攻击者

如果 Bridge 在本机监听端口（比如提供本地控制界面或状态接口），同机的任何进程、以及多用户机器上的其他账号都能连上它。

优先用 Unix domain socket 配文件权限；必须用 TCP 时只绑 127.0.0.1 并要求本地令牌（令牌文件权限 0600）。这条容易漏，因为「本机」听起来像是安全的。

04与云上 Pod 的差异

云上 Pod用户电脑
连接方向Server 主动连 PodBridge 主动外拨
ACP 链路完全相同 —— Bridge spawn adapter，adapter 驱动 CLI
工作区OSS 挂载，平台管理用户的真实目录，授权范围内
CLI 状态目录NAS 卷，per-session用户的 ~/.claude，与他自己的会话共用
凭证平台 Secret，指向 Higress用户自己的订阅，直连厂商
隔离Pod 边界无 —— 与用户其他进程同机
信任我们控制不可信，可被篡改
会话独占天然（一 Pod 一会话）需租约，见 §04
生命周期idle TTL 销毁 Podidle 关闭 adapter 进程
信任边界是最根本的差异

Pod 是我们调度、我们控制的；用户的 Bridge 跑在他自己的机器上，可以被替换、被代理、被逆向。Server 收到的一切来自本地设备的数据都是不可信输入 —— 要做字段校验、大小限制、速率配额，不能沿用对 Pod 的信任假设。

具体地：不要因为消息声称属于某个 session_id 就相信它；要校验该设备是否确实持有那个会话的租约、以及该会话是否属于这个用户。

05会话独占与租约

云上一个 Pod 一个会话，独占是天然的。本地不是 —— 用户随时可能在自己的终端 claude --resume 一个平台正持有的会话。

并发持有会分叉对话，必须拦住

两个 claude 进程持有同一会话时，各自有独立的内存上下文、互不可见，却追加进同一个 transcript。两边的下一轮都会带着自己视角的历史去请求模型，越走越远。这不是「体验降级」，是对话分叉。

检测：claude agents --json

这是受支持的枚举接口（明确标注 for scripting、不需要 TTY），实测输出：

[{ "pid": 284674, "cwd": "/root/workspace/deer-flow",
   "kind": "interactive", "sessionId": "1eb27252-…",
   "name": "deer-flow-23", "status": "busy", "startedAt": … }]

Bridge 知道自己 spawn 的子进程 PID，于是能判断某个 sessionId 是被我们的 adapter 持有，还是被用户的终端持有。内部文件 ~/.claude/sessions/<pid>.json 有更多字段（entrypoint、peerProtocol），可作补充但不作主依据 —— 它是未文档化的内部状态。

租约规则

取得租约 → 平台可驱动该会话
  ├─ 未被任何活进程持有        → 直接取得
  ├─ 被我们自己的 adapter 持有  → 已持有，继续
  └─ 被用户终端持有          → 拒绝，网页端提示「该会话正在本地终端使用中」

释放租约 → session/close 让 agent 收尾，再退出 adapter 进程
  触发：idle TTL，或用户在网页端显式「移交到本地」
租约是协作式的，不是强制的

用户随时可以在自己的终端 resume 一个平台正持有的会话，那是他的机器、他的 CLI，没有任何机制能阻止。Bridge 应当持续监测，发现外来进程接管时：把当前 Run 标记为冲突、网页端显示告警、停止把 ACP 事件当作权威、并主动 session/close 退出以避免继续加剧分叉。

给一个显式的「移交到本地」按钮，让用户主动释放而不是猜 idle TTL 何时到。交接点明确后，冲突就从「随时可能发生」变成「只在用户无视提示时发生」。

本地已存在的会话能否被接管

要驱动一个已存在的 CLI 会话，需要 session/resume 或 session/load。但用户在终端起的会话从未经过 ACP，没有 ACP sessionId —— 能否直接拿 Claude Code 的原生 sessionId 去调，取决于 adapter 的 ID 空间是否与 CLI 一致（§08 第 2 项）。

本期不提供这个入口。网页端只展示平台自己发起的会话。

06工作区与配置

工作区就是用户的真实目录

没有 OSS 挂载。session/new 的 cwd 指向用户授权的某个本地目录，additionalDirectories 默认为空。

cwd 决定了助理能改哪些文件

云上写坏了大不了重建 Pod；本地写坏的是用户的真实代码。因此：

  • 目录必须由用户显式授权，平台不得自行选择或扩大范围
  • additionalDirectories 默认为空，每增加一个都要用户单独确认
  • 审批回路不能省 —— §2.6 的规则在本地更重要，绝不能自动批准

CLI 状态目录与用户共用

adapter 拉起的仍是用户机器上的 claude，读写他自己的 ~/.claude。这与云上「per-session NAS 卷」不同 —— 平台会话的 transcript 和用户自己的会话混在同一个目录树里。

后果：不要假设能按目录清理平台会话的状态；要清理得靠 session/delete（若 adapter 支持），而不是删文件。

MCP 与技能

  • MCP —— 仍由 session/new 的 mcpServers 传入。若要指向 Higress，前提是用户机器能访问到内网网关；否则只能直连或不配。
  • 技能 —— 用户机器上的 ~/.claude/skills/ 是他自己的。平台若要下发技能，须经用户同意后写入，或用 --plugin-dir 之类的会话级机制（取决于 adapter 是否暴露）。不要静默修改用户的技能目录。

07授权与隐私

去掉镜像后隐私面收窄了很多 —— 平台只看得到自己发起的会话，不读用户的历史、不枚举他的项目。但仍有两处需要明确授权：

授权项范围
设备接入安装 Bridge 并绑定到账号。可随时解绑，解绑后立即断连。
目录访问逐个目录授权，作为 cwd 或 additionalDirectories 的候选。未授权目录不得出现在任何会话里。
  • 默认最小 —— 安装 Bridge 不等于授权任何目录，要有独立的添加步骤。
  • 可见的状态 —— 用户应随时能看到：哪些目录已授权、当前有哪些活跃会话、各自在动哪个目录。
  • 本地可中断 —— Bridge 要有本地的「立即停止」入口，不依赖网络可达。用户在自己机器上必须能单方面叫停。
可观测性也要跟着收敛

本地 Bridge 上报 OTel 在技术上没问题，但涉及用户隐私与网络。只上报与平台会话相关的 span（session_id、run_id、时长、消息计数），不上报本地环境信息、路径内容或用户其他进程的状况。

08治理缺口

本地会话的模型调用绕过 Higress

用户机器上的 Claude Code 用他自己的订阅或 API key，直连模型厂商。于是 系统架构 §06 里 LLM 网关的五项收益 —— 鉴权、限流、配额、成本核算、出站审计 —— 在本地会话上全部失效。

这不一定是问题（用户用自己的额度干自己的活本就合理），但必须是明确的决定而非意外发现。如果产品上有用量统计或合规审计的承诺，本地会话是一块盲区，口径要先说清楚。

相比之下 MCP 还有救：session/new 的 mcpServers 由我们传入，只要用户机器能访问 Higress，工具调用仍可收口。这是本地场景下唯一还能守住的治理点，值得优先保证网络可达性。

审计记录仍然完整

好消息是：审批决定、工具调用、消息内容都经 ACP 流回 Server 并落进 Message 账本（会话管理 §11 的固化清单）。「谁在什么时候批准了什么」这条审计链在本地场景下不受影响 —— 缺的只是模型侧的用量与出站数据审计。

09待验证清单

除 运行时链路 §12 的通用项外，本地场景另有：

#验证项影响
1 两个 claude 进程同时 resume 同一会话时的实际行为 —— CLI 自身是否有锁或告警 决定 §04 租约要做到多严格，以及能否依赖 CLI 自己拦一道
2 能否用 Claude Code 原生 sessionId 调 ACP session/resume / load 决定将来能否接管用户已有的本地会话
3 adapter 在用户机器上的安装与升级方式 —— 随 Bridge 分发，还是依赖用户环境 决定版本一致性与故障排查成本
4 Windows / macOS 上的进程管理、路径与文件权限差异 决定 Bridge 的跨平台实现成本
5 断线重连期间 adapter 进程的处置 —— 保活还是关闭 影响短暂网络抖动时的用户感受与资源占用

建议的上线顺序

  1. 先在云上把驱动模式跑通 —— 同一套 ACP 链路，云上环境可控，问题更容易定位。
  2. 再做连接反转与设备注册 —— 这是本地场景唯一的结构性新增。
  3. 然后是授权与租约 —— 前者是上线前提，后者决定并发安全。
  4. 最后处理跨平台 —— 先支持一个平台跑顺，再铺开。
