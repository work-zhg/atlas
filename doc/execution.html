Execution Environment

执行环境管理设计

Pod 模板与生命周期的归属组件。它为三类执行环境 —— acp 的 CLI Pod、native 的 sandbox Pod、用户的本地设备 —— 提供同一套抽象，让上层只需要问「这个会话在哪执行、准备好了没有」。

模板生命周期卷编排配额连接注册

01定位与边界

这个组件解决的是「归属」问题

Pod 的创建、回收、目录结构、卷挂载，此前散落在运行时链路 §09（acp 的 K8s 管理）与 native Agent §03（sandbox Pod）两处 —— 描述了该怎么做，却没有组件拥有它。

结果是两套几乎相同的生命周期逻辑会被分别实现：一套在 acp 链路里，一套在 native 链路里。而它们要处理的问题完全一样：模板、配额、就绪探测、idle 回收、卷分配、异常重建。

职责

  • 模板管理 —— 各类执行环境的 Pod 骨架：镜像基线、资源、探针、安全上下文、网络策略
  • 生命周期 —— 创建、就绪、健康、空闲回收、销毁、异常重建
  • 卷编排 —— 按会话分配 OSS / NAS 前缀并挂载
  • 调度与配额 —— 租户上限、并发控制、优先级、预热池
  • 连接注册 —— session → 执行位置 的唯一真相

不在本文范围

  • Pod 内部的进程与协议 —— acp 见运行时链路，native 见 native Agent
  • 具体的目录结构语义 —— 本文只管挂载，语义归各自的文档
  • 设备配对与信任 —— 见本地部署 §03

02三类执行环境，一套抽象

Runtime 对象

CREATE TABLE runtimes (
  runtime_id    TEXT        PRIMARY KEY,
  session_id    TEXT        NOT NULL,
  kind          TEXT        NOT NULL,   -- acp_pod | native_sandbox | device
  state         TEXT        NOT NULL,   -- §05

  -- Pod 类（kind != device）
  template_id   TEXT,
  template_ver  INT,
  pod_name      TEXT,
  node          TEXT,

  -- device 类
  device_id     TEXT,

  -- 通用
  endpoint      TEXT,                   -- 连接地址或连接句柄
  volumes       JSONB,                  -- 已分配的 OSS / NAS 前缀（§06）
  created_at    TIMESTAMPTZ NOT NULL,
  ready_at      TIMESTAMPTZ,
  last_active   TIMESTAMPTZ,
  terminated_at TIMESTAMPTZ
);

-- 一个会话同时只有一个活跃 runtime
CREATE UNIQUE INDEX uq_runtime_active ON runtimes (session_id)
  WHERE state NOT IN ('terminated', 'failed');

runtimes 是 本地部署 §02 说的「连接注册表」的落地 —— 它把 session → Pod 与 session → 设备连接 收敛成同一张表，见 §08。

03模板管理

模板是某类执行环境的通用骨架。它回答的不是「跑什么」，而是「在什么条件下跑」。

CREATE TABLE runtime_templates (
  template_id   TEXT        NOT NULL,
  version       INT         NOT NULL,
  kind          TEXT        NOT NULL,   -- acp_pod | native_sandbox
  cli_type      TEXT,                   -- acp_pod: claude-code | codex …

  base_image    TEXT,                   -- 基础镜像（可被 launch 覆盖）
  resources     JSONB       NOT NULL,   -- requests / limits
  probes        JSONB       NOT NULL,   -- 就绪与存活探针
  volumes       JSONB       NOT NULL,   -- 卷结构与挂载点
  security      JSONB       NOT NULL,   -- securityContext：非 root、只读根文件系统…
  network       JSONB       NOT NULL,   -- NetworkPolicy：默认禁止出站
  grace_period  INT         NOT NULL,   -- terminationGracePeriodSeconds
  idle_ttl      INT         NOT NULL,

  created_by    TEXT        NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (template_id, version)
);
模板管安全基线，Agent 管业务

这条分工决定了谁能改什么：

模板（平台运维）agent.launch（Agent 定义者）
内容探针、安全上下文、网络策略、资源上限、卷结构镜像、command、args、env
改动影响全部同类 Pod仅该 Agent
谁负责平台安全与运维Agent 定义者

如果让 Agent 定义者能改 securityContext 或 NetworkPolicy，安全基线就形同虚设 —— 任何一个 Agent 的定义失误都会变成集群级的风险。

模板不被会话钉住

与 Agent 版本的处理方式刻意不同

sessions.agent_version 钉住 Agent 版本，因为 Agent 决定行为，用户能感知；而模板决定运行条件，用户感知不到，且更新通常是安全修复。

所以模板变更不影响运行中的 Pod（它已经创建了），但下次重建时立即采用新版本，不需要等 Agent 发版。runtimes.template_ver 记录实际用的版本，仅供审计与排查。

反过来如果钉住，一次安全基线更新就要等所有 Agent 逐个发版才能铺开 —— 那正是安全修复最不能接受的节奏。

04渲染：模板 + launch

def render_pod_spec(session, agent, template):
    spec = template.to_pod_spec()

    # Agent 侧只能填这几处
    spec.image    = agent.launch.image  or template.base_image
    spec.command  = agent.launch.command
    spec.args     = agent.launch.args
    spec.env     += render_env(agent.launch.env, session)

    # 会话相关，由本组件填
    spec.volumes  = allocate_volumes(session)           # §06
    spec.labels   = { session_id, agent_id, tenant_id } # 运维定位
    spec.env     += [
        AGENT_ENDPOINT_TOKEN,         # 接入控制（runtime §09）
        OTEL_EXPORTER_OTLP_ENDPOINT,  # 可观测性（observability §05）
        OTEL_RESOURCE_ATTRIBUTES,     # platform.session_id=…
    ]
    return spec
launch 里的字段必须校验，不能直接展开

agent.launch 是 Agent 定义的一部分，虽然由管理员填写，但它不该有能力覆盖模板的安全字段。渲染时要：

  • 白名单字段 —— 只取 image / command / args / env，其余一律忽略
  • 镜像来源校验 —— 只允许可信仓库，防止指向任意外部镜像
  • env 键名过滤 —— 禁止覆盖平台注入的键（令牌、OTel 配置），否则可以关掉遥测或伪造身份

校验发生在 Agent 发布时（Agent 管理 §04 的「三个时刻」），渲染时只是再确认一次 —— 但两处都要做，因为模板可能在 Agent 发布之后变更。

05生命周期状态机

            ┌─────────────────────────────────┐
            ↓                                 │
none ──→ provisioning ──→ ready ──→ active ⇄ idle
            │                │         │       │
            ↓                ↓         │       ↓ TTL 到期
         failed          failed        └──→ terminating ──→ terminated
状态含义会话侧对应
none尚未创建cold
provisioning调度中、拉镜像、挂卷starting
ready探针通过，可接受连接active
active有活跃 Run
idle已就绪但无活跃 Run，计时中active
terminating优雅关闭中cold
terminated已销毁，卷保留cold
failed无法创建或不可恢复cold 或 lost
runtime 消失 ≠ 会话丢失

terminated 时会话是 cold 而不是 lost —— 因为卷还在（§06），重建后工作区无损。

只有卷也没了、或 CLI 侧的会话状态无法恢复时才是 lost。这个区分很重要：cold 对用户应当完全透明（运行时链路 §10），lost 必须明确告知。把两者混为一谈，会导致每次 idle 回收都给用户弹一次「会话已重启」。

创建时机：两类不同

创建时机理由
acp_pod会话首个 Run 提交时CLI 就是 agent 本身，没它什么都做不了
native_sandbox首次调用 sandbox 工具时很多 native 会话全程用不到沙箱（native Agent §09），建会话就起是浪费

就绪判定要验到底

探针只检查端口在监听是不够的（运行时链路 §09）。ready 的含义是「现在把流量打进来不会失败」，所以要覆盖：进程可用、认证有效、卷可写、依赖目录非空。

宁可 Pod 起不来，也不要起来一个坏的 —— 前者是一次明确的失败，后者是用户提交后卡住再报错。

06卷编排

卷的分配归本组件，卷里的目录语义归各自的文档（运行时链路 §05、native Agent §04）。

卷存储分配规则
工作区OSSoss://<bucket>/tenants/<t>/sessions/<s>/
CLI 状态
仅 acp		NASnas://<fs>/tenants/<t>/sessions/<s>/claude/
技能只读卷按 Agent 的技能集合选择对应卷
缓存emptyDir不分配，随 Pod 生灭
挂载凭证只授予该会话的前缀

Pod 拿到的存储凭证必须只能访问本会话的前缀，不是整个 bucket。这样即使 Pod 被攻破（尤其是跑着任意命令的 sandbox），也读不到其他会话的数据。

这是 Pod-per-session 隔离模型在存储侧的落实 —— 隔离了计算却共享存储凭证，等于没隔离。

卷的生命周期长于 Pod

Pod terminated  → 卷保留（会话 cold，重建后无损）
会话 deleted    → 按保留策略处理：立即删 / 归档 / 保留 N 天

会话删除时工作区怎么处理是独立的产品决策，不能默认继承 Pod 的生命周期（本地部署与 运行时链路都提过这点）。用户可能删了会话但还想要产出文件。

07调度与配额

配额的三个层次

层次防什么
租户级 Pod 数一个租户的批量会话把集群占满
用户级并发会话单个用户开几十个会话，每个占一个 Pod
集群总量兜底，超过就拒绝新建而不是让调度器排队
配额耗尽要立即拒绝，不要排队

K8s 调度器在资源不足时会让 Pod 处于 Pending，而用户那边看到的是「一直在准备环境」。与其让他等一个可能永远不来的 Pod，不如立刻告诉他配额满了。

所以本组件要在提交给 K8s 之前做配额检查，而不是依赖 ResourceQuota 的拒绝 —— 后者的错误信息也无法转达给用户。

冷启动与预热池

冷启动是这套架构最直接的体验成本（native Agent §10 与 运行时链路 §12 都把它列为待实测项）。

手段效果代价
镜像预拉显著低，节点上常驻镜像层
预热池最显著空闲 Pod 持续占资源
延长 idle TTL中回收变慢，占用上升
预热池只对同质 Pod 有效

预热的前提是提前知道要建什么。native 的 sandbox Pod 高度同质（同一个基础镜像），预热效果好；acp 的 Pod 因 cli_type 与 launch 而异，要为每种组合各留一个池，成本迅速上升。

建议：先给 native_sandbox 做预热池，acp 侧靠镜像预拉 + 合理 TTL。等有数据表明某个 cli_type 的使用频次足够高，再单独为它开池。

08连接注册表

session → 执行位置 的唯一真相

本地部署 §02 要求把 session → Pod 与 session → 设备连接 收敛成同一抽象，理由是不要按 Pod 名硬编码查找，否则本地场景要另写一套。

runtimes 表就是这个抽象。上层（会话管理、Run 调度）只问一件事：这个会话的 runtime 在哪、就绪了没有，不关心它是 Pod 还是一台笔记本。

async def ensure_runtime(session) -> Runtime:
    rt = get_active_runtime(session.session_id)
    if rt and rt.state in ("ready", "active", "idle"):
        return rt

    if session.runtime_kind == "device":
        return await wait_device_online(session.device_id)   # 不创建，只等
    return await provision_pod(session)                      # 创建

Server 无状态，注册表有状态

把映射放在共享存储里（而非 Server 进程内存），Server 才能无状态水平扩容：任何副本都能查到某会话的 runtime 并连上去。

对 device 类还要多一层：设备连接是某个 Server 副本持有的长连接，所以注册表要记 bridge_instance，让请求能路由到持有该连接的副本。这是本地场景唯一残留的粘性（本地部署 §02）。

09故障处理

故障状态转移处理
镜像拉取失败provisioning → failed不重试（多半是配置错），告警并返回明确错误
探针长时间不通过provisioning → failed销毁重建一次；再失败则放弃
Pod 被驱逐 / 节点故障* → none会话置 cold，下次需要时重建，卷无损
OOMKillactive → none与其他退出分开统计；重建可继续，但反复 OOM 说明规格不足或需要压缩上下文
存储不可用* → failed不要降级为「无卷启动」—— 那会让 agent 以为工作区是空的而重做一遍
不要在卷挂载失败时降级启动

一个看似合理的容错是「卷挂不上就先起来，让用户能聊天」。但对有工作区的会话，这是最糟的选择 —— agent 看到空目录，会以为之前的工作从未发生，然后重新做一遍，覆盖掉 OSS 上还在的文件（等卷恢复后）。

宁可明确失败。「环境暂时不可用，请稍后重试」比「悄悄丢失工作成果」好得多。

优雅终止

terminationGracePeriodSeconds 要留够：拒绝新请求、把当前 Run 标记为中断并上报、刷完 OTel span。

但不要把数据持久性依赖在这段时间里 —— 节点故障与抢占不给这个窗口（运行时链路 §04）。持久性靠卷，不靠优雅关闭。

10本地设备的特殊性

本地设备在 runtimes 表里是一等公民，但它的几乎每个操作语义都不同：

操作Pod本地设备
创建渲染 spec 并提交给 K8s不创建，只等它连上来
模板决定运行条件不适用 —— 环境是用户的
资源限制我们设定管不了
卷我们挂载用户授权的本地目录
回收删除 Pod关闭 adapter 进程
信任我们控制不可信输入
离线设备要立即拒绝，不要等

Pod 创建失败可以重试，但设备离线是等不来的 —— 用户的笔记本可能合着盖子。对离线设备发起的 Run 应当立即拒绝并说明设备离线，而不是排队等待（本地部署 §02）。

这是 ensure_runtime() 里 device 分支与 Pod 分支最实质的差别：一个是创建，另一个只是确认。

共用的部分

尽管差异很多，这些仍然共用：状态机（§05）、连接注册（§08）、idle 回收的触发逻辑、以及对上层的接口。这正是把三类环境放进同一个抽象的价值 —— 会话管理与 Run 调度完全不需要知道执行位置的种类。

11待验证清单

#验证项影响
1 冷启动各阶段耗时 —— 调度、拉镜像、挂卷、探针就绪各占多少 决定 §07 要不要做预热池，以及做在哪一类上
2 OSS / NAS 的 CSI 驱动在大量并发挂载下的表现 卷挂载是冷启动的主要不确定项，也是失败率最高的一环
3 会话级存储凭证的粒度 —— 能否只授予单个前缀而非整个 bucket §06 隔离的实现基础，做不到就要换存储方案
4 模板变更的灰度方式 —— 安全基线更新如何在不影响存量会话的前提下铺开 决定 §03 的「不钉住」策略是否需要补充灰度机制
5 预热池的实际命中率 —— 预热的规格与真实请求的匹配程度 决定预热池的成本是否划算

建议的实现顺序

  1. 先做 native_sandbox 的完整生命周期 —— 它最同质、最可控，是验证模板与状态机的最佳切片。
  2. 再接 acp_pod —— 复用同一套逻辑，主要增量是 cli_type 维度的模板与 NAS 卷。
  3. 然后是配额与预热 —— 在有真实负载数据之后再调，提前优化没有依据。
  4. device 类最后 —— 它与 Pod 的差异最大，且依赖本地部署的设备配对先完成。
