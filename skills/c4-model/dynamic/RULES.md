# Dynamic（sequence 风格）

C4 的 Dynamic 图有 collaboration 和 sequence 两种画法，表达的信息相同。本技能只画 **sequence 风格**：参与者从左到右排开，交互按先后从上到下排列。

## 这张图回答什么

静态结构图（Context、Container、Component）里的元素，在**运行时**怎样协作，完成一个具体的功能、用户故事或用例。比如「用户登录时依次发生了什么」。

读者包括团队内外的技术和非技术人员，参与者选得越粗，读者范围越广。

**这类图要少画。** 只给有代表性、反复出现的交互模式，或者交互复杂、只看静态图理解不了的功能画。不要给每个功能都画一张。

## 范围与元素

| 项 | 内容 |
|---|---|
| Scope | 一个具体的功能、用户故事、用例或场景 |
| Participants | 自己选层级：可以是软件系统、container 或 component，也可以混用，并加上发起交互的人员 |
| Boundaries | 用边界框表示参与者所在的系统或 container，可以嵌套 |

### 参与者怎么选

- 按想讲的粒度选一层：讲系统之间的协作就用软件系统；讲一个系统内部就用 container；讲一个 container 内部就用 component。混用时，用边界框把 component 圈进它们所属的 container。
- 每个参与者都必须是静态图里已有的元素，名字、类型、技术和静态图一致。静态图里没有的东西，先回去补静态图，或者说明为什么没有。
- 外部系统和人员的颜色要和静态图一致：在 `color` 里写明它在静态图里的颜色。人员依次是 `#297e06`、`#1a849c`……；外部系统依次是 `#ed8609`、`#bf101d`、`#8411bd`、`#5b6770`、`#b8336a`……，都按静态图里的出现顺序分配，`tag` 相同的颜色相同。不写 `color` 时，模板会按本图里的出现顺序重新分配，颜色就可能对不上。
- 只放这个场景里真正参与交互的元素，没参与的不画。

## 图必须反映现实

画 sequence 图最容易犯的错，是画成「理想中的流程」，而不是代码真实的调用。

### 先对上代码，再画

- **每个参与者都能在代码里找到**：画 component 时，要能指出它对应的类、模块或包。图上有一个「Security Component」，代码里就要有对应的东西。对应不上，说明图和代码之间有断层（model-code gap）：要么改图，要么在 `description` 里说明对应关系。
- **每条消息都对应真实的交互**：一次函数调用、一个 HTTP 请求、一条 SQL、一次消息发布。画现有系统时，沿着代码的调用路径逐条核对（入口路由 → 服务 → 下游客户端），不要凭记忆。
- **顺序就是代码执行的顺序**：先发生的在上面。异步的交互（后台任务、消息队列、事件推送）要在 `description` 或 `technology` 里写明，不要画得像同步调用一样。

### 技术写出来

- 跨进程的消息必须写 `technology`（如「JSON/HTTPS」「SQL/TCP」「SSE」「Redis Streams」），数据库消息可以直接写 SQL 语句当说明。写出技术能逼出关键问题：两个进程靠什么通信？谁发起？为什么是这个技术？
- 前期设计还没定下来时，写候选方案，如「gRPC 或 JSON/HTTPS」，让待决策的地方显式可见。
- 不要因为「大家都知道」「会让图变乱」就省掉技术。

### 你会这样写代码吗？

画完问自己：前期设计时问「我们会这样写代码吗？」，描述现有系统时问「代码真是这么写的吗？」。两个常见情况：

- **共享组件**：一个共享库被打包进多个 container，它不是一个独立运行的进程。不要把它画成边界外的单独参与者，那会被误解成一个独立的服务。要把它画在每个使用它的 container 边界里，并在名字或 `tag` 上标明是共享组件。
- **分层是否被绕过**：如果读请求从表示层直接访问数据访问层、绕过了服务层（比如采用了 CQRS），就照实画这条消息，并在说明里写明意图。不要为了「分层好看」画成都经过服务层。

## 消息

- 消息按 `messages` 数组的顺序自动编号，编号就是先后顺序。
- `description` 写做什么，按「源 + 描述 + 目标」读要通顺，如「Submits credentials to」「Returns user data to」。返回消息也单独画一条。
- 跨进程的消息必须写 `technology`，包括 container 之间、软件系统之间、component 和 container 或软件系统之间的消息；component 之间和人员发起的消息可以不写。
- 自己调用自己（如开始一个后台任务）画成回到自己生命线的回环。
- 只画这个场景的关键交互，不要把每次日志、每次缓存读取都画出来。

## 图面要求

模板已经自动完成以下几项，只需在数据里给齐内容：

- **标题**：「Dynamic View: 系统名 - 场景」或「动态图：系统名 - 场景」，比如「动态图：Agent 平台 - 发送一条消息」，语言和图上文字保持一致。
- 参与者头上下各画一排，写名字和 `[类型: 技术]`；人员和数据库画成图标。
- 边界框标题居中，写名字和 `[类型]`。
- 每条消息写「编号: 说明」，下一行写 `[技术]`。
- 图下方有图例：每种参与者、边界、消息各一项。

## 样式（模板内置）

- 白底。container、component、in-scope 系统和边界都用蓝色 `#1168bd`；人员、外部系统用 `color` 指定的颜色（不写则按出现顺序分配）。
- 生命线是灰色细虚线；消息是 `#444` 虚线加实心小箭头，同步、异步、返回都用这一种线。
- 标题在左下角，图例在图的下方。

## 数据格式

模板里只改 `<script type="application/json" id="c4-model">` 这一段：

```jsonc
{
  "title": "Dynamic View: Internet Banking System - Backend",   // 必填
  "description": "一行补充说明",                                // 可选，显示在标题下
  "boundaries": [                         // 可选：边界框，可以嵌套
    { "id": "ibs", "name": "Internet Banking System", "type": "Software System" },
    { "id": "backend", "name": "Backend", "type": "Container: Java and Spring Boot", "in": "ibs" }
  ],
  "participants": [                       // 从左到右的顺序就是数组顺序
    {
      "id": "signIn",                     // 必填，唯一，消息里用它引用
      "kind": "component",                // person | system | container | component
      "name": "Sign In API",
      "technology": "Spring MVC",         // container、component 必填
      "shape": "database",                // 可选：仅 container，画成数据库图标
      "in": "backend",                    // 可选：所在的边界
      "scope": true,                      // 可选：仅 system，表示 in-scope 系统，画成蓝色
      "tag": "同级服务",                   // 可选：图例文字，tag 相同颜色相同
      "color": "#8411bd"                  // 可选：和静态图保持一致的颜色
    }
  ],
  "messages": [                           // 数组顺序 = 编号顺序
    { "from": "ui", "to": "signIn", "description": "Submits credentials to",
      "technology": "JSON/HTTP" }         // 跨进程必填
  ]
}
```

模板自带的示例是 c4model.com 的网银登录 sequence 图，数据和原图一致。

## 布局

- 不用写坐标：参与者按 `participants` 的顺序从左到右排，列间距按参与者宽度和消息说明的宽度自动撑开。
- 参与者的顺序按交互的走向排：发起方（人员、前端）在最左，被调用的依次往右，存储和外部系统在最右。这样大部分请求消息从左往右走，返回消息从右往左走。
- 同一边界里的参与者在数组里必须相邻，嵌套的边界也一样，否则边界框会把别的参与者框进去。
- 消息说明太长会把列撑得很宽，写短一点；超过约 260px 会自动断行。
- 消息超过 20 条时，图会很长：只保留关键交互，或者按阶段拆成几张图。

## 校验结果（`<html data-c4-status>`）

| 状态 | 含义 |
|---|---|
| `error` | 数据不合规：缺字段、`kind` 取值不对、container 或 component 缺 technology、边界缺 name 或 type、边界嵌套成环、边界里没有参与者、同一边界的参与者不相邻、边界外的参与者和边界框重叠、消息端点不存在、消息缺 description、跨进程的消息缺 technology |
| `warn` | 消息超过 20 条；某个参与者没有参与任何消息；边界标题比边界还宽 |
| `ok` | 全部通过；页面顶部不显示提示框 |

每条问题会以 `<li data-level="error|warn">` 的形式显示在页面顶部的提示框里。
